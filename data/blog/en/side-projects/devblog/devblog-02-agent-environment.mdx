## 0. Introduction

I came to write this post while playing twenty questions. To some people twenty questions is just a game. Seen another way, it is an optimization problem in natural-language information retrieval: find the answer with 20 yes/no questions, that is, 20 bits. If every question splits the candidates exactly in half, 20 questions can pick one out of about a million (2^20). The same game becomes a completely different problem depending on how you look at it. A small change in wording, in other words a difference in framing.

That reminded me that I had been describing my own AI agent environment to people as "nothing special, I stuff in markdown files and tell it to read what it needs". That is not wrong. Said differently, the same thing is [context engineering](glossary:context-engineering): [agentic retrieval](glossary:agentic-retrieval) running on a [hierarchical index](glossary:hierarchical-index).

So I am writing this post to put the structure into proper words.

In restaurant terms, two branches share one recipe book, and three cooks read only the one-page rule sheet on the wall when they start, pulling the recipes they need off the shelf themselves. The recipe book is the [dotfiles](glossary:dotfiles) repo, the two branches are the Windows and macOS [clones](glossary:clone), the three cooks are [Claude Code](glossary:claude-code), [Codex](glossary:codex) and [Antigravity](glossary:antigravity), the rule sheet on the wall is the [system prompt](glossary:system-prompt), and pulling a recipe off the shelf yourself is [agentic retrieval](glossary:agentic-retrieval).

I use three [AI coding agents](/en/blog/cs-fundamentals/ai/ai-07-01-ai-agent/#ai-agent), [Claude Code](glossary:claude-code), [Codex](glossary:codex) and [Antigravity](glossary:antigravity), and switch between two machines, a Windows desktop and a MacBook. School assignments, this blog, team projects and personal repos are all open at the same time, there are many [skills](glossary:skill), and the instructions change as I go. This whole environment lives in one repo, `~/dotfiles`.

This post walks through that structure in order, starting from the big picture. Numbers that change are collected, with a date, in the table in section 13.

## 1. The big picture

![Overall map: two computers share one dotfiles repo on GitHub, and three agents read the instructions, memory and worklog in it](/static/images/devblog-04-agent-environment/overview.svg)

_Overall map: two computers share one [dotfiles](glossary:dotfiles) repo on GitHub, and three agents read the instructions, [memory](glossary:agent-memory) and worklog in it_

The GitHub private repo `seren-wib/dotfiles` is shared by two [clones](glossary:clone), one on Windows and one on macOS. The three agents, [Claude Code](glossary:claude-code), [Codex](glossary:codex) and [Antigravity](glossary:antigravity), read from it when a session starts and write new content when it ends. The repo's contents come in three kinds.

- **Instructions**: rules the agent receives as its [system prompt](glossary:system-prompt) in every session. The sources are in `agents/`.
- **[memory](glossary:agent-memory)**: where facts are written down. Only current state and references go here.
- **worklog**: what is left to do and what was done. One `WORK.md` per unit of work (key).

On top of these come [hooks](glossary:hook) (scripts that run automatically at set points), [skills](glossary:skill) (manuals for specific tasks), [MCP](glossary:mcp) registration scripts and a [symlink](glossary:symbolic-link) list.

The information is split into three layers.

![Three layers: L0 is loaded every session, L1 is retrieved when needed, L2 is the deep record](/static/images/devblog-04-agent-environment/three-layers.svg)

_Three layers: L0 is loaded every session, L1 is retrieved when needed, L2 is the deep record_

- **L0 Always loaded**: what goes into the [system prompt](glossary:system-prompt) every session. The persona, the shared rules, the per-agent rules, the global [memory](glossary:agent-memory) index (file names with one-line descriptions), and [skill](glossary:skill) names with their descriptions.
- **L1 Retrieved on demand**: what the agent opens with the `Read` tool when a topic comes up. [Skill](glossary:skill) bodies, global [memory](glossary:agent-memory) bodies, the project `MEMORY.md`, `WORK.md`.
- **L2 Deep record**: what is searched with `grep` only when a question comes up. `worklog/<key>/history/`, `memory/log/YYYY-MM.md`, transcripts of finished sessions, the [git](glossary:git) log.

Showing only names in the upper layer and opening the lower layer only for what is needed is called [progressive disclosure](glossary:progressive-disclosure). The lower the layer, the larger it is and the less often it is read. There is one reason for the design: text in L0 is multiplied by the number of sessions and becomes cost, while L1 and L2 cost only the sessions that use them.

## 2. What is always carried

That page is the [system prompt](glossary:system-prompt). [Claude Code](glossary:claude-code) reads `~/.claude/CLAUDE.md`, [Codex](glossary:codex) `~/.codex/AGENTS.md`, and [Antigravity](glossary:antigravity) `~/.gemini/GEMINI.md` at session start. All three files are assembled from the same sources (section 6).

The assembled result is in this order:

1. Persona (`agents/persona.md`)
2. Shared rules (`agents/shared.md`): four sections, on how to work, the environment, per-session cost, and [memory](glossary:agent-memory) rules
3. Per-agent rules (`agents/claude.md` and so on)
4. Global [memory](glossary:agent-memory) index (`memory/global/MEMORY.md`)

The length a model can see at once (the [context window](glossary:context-window)) is fixed, and every character that goes in is counted as [input tokens](glossary:token). The [system prompt](glossary:system-prompt) goes in again with every request, so whatever is in it is multiplied by the number of sessions and requests. Keep appending long markdown files to the instructions to "tell the agent everything about me", and rules that will never be used are read every time.

This cost is bigger than it looks. In my environment, opening an empty session lays down about 50,000 [tokens](glossary:token) before anything is asked, and roughly half of that is [MCP](glossary:mcp) tool lists. That is my own measurement; it has not yet been broken down into [system prompt](glossary:system-prompt), instructions, [memory](glossary:agent-memory) index, [skill](glossary:skill) descriptions and [hook](glossary:hook) output.

So what goes into L0 is decided by the "per-session cost" section of the shared rules. Everything loaded into every session is [input tokens](glossary:token): instruction files, the global index, [MCP](glossary:mcp) tool lists, [plugin](glossary:plugin) [skill](glossary:skill) descriptions, and messages injected by [hooks](glossary:hook). The rules are:

- Before adding anything, ask first "does every session need this?". If not, send it somewhere that opens only when needed (L1), such as a [memory](glossary:agent-memory) body or a [skill](glossary:skill) body.
- [MCP](glossary:mcp) never goes in the user scope; it is added in the local scope only for the folders that need it.
- claude.ai [connectors](glossary:connector) come first. The same tool never comes in through two paths.
- [Plugins](glossary:plugin) and [connectors](glossary:connector) that are not used are turned off.

Section 9 covers the [MCP](glossary:mcp) rules in detail. Designing what the model is shown, when, and how much is called [context engineering](glossary:context-engineering). Where it differs from writing one good instruction file ([prompt engineering](glossary:prompt-engineering)) is that the structure decides what goes in every time and what is pulled out only when needed.

The global index looks like this (example values):

```text
## State (open only the matching file)
- [me/profile](~/.claude/memory/me/profile.md) — identity, stack
- [me/tools](~/.claude/memory/me/tools.md) — subscriptions, machine setup

## References
- [refs-env](~/.claude/memory/refs-env.md) — OS quirks, auth locations
```

Each line holds only a file name and one short [hook](glossary:hook). These lines are loaded into all three agents in every session, so per character they are the most expensive lines in the repo.

## 3. Pulling out what is needed

![In vector RAG a retriever picks similar chunks and attaches them; in agentic retrieval the model looks at the index and opens files itself](/static/images/devblog-04-agent-environment/retrieval-compare.svg)

_In [vector RAG](glossary:rag) a retriever picks similar [chunks](glossary:chunking) and attaches them; in [agentic retrieval](glossary:agentic-retrieval) the model looks at the index and opens files itself_

There are two ways to retrieve. The first is vector [RAG](/en/blog/cs-fundamentals/ai/ai-07-02-rag/#1-ragretrieval-augmented-generation) (Retrieval-Augmented Generation). The question is turned into a vector by an [embedding](/en/blog/cs-fundamentals/ai/ai-06-01-llm/#2-embedding) model, the [top-k](glossary:top-k-retrieval) document [chunks](glossary:chunking) with the highest similarity are picked from a [vector DB](glossary:vector-database), and they are attached to the context. The retriever decides what to look at. The second is the [agentic retrieval](glossary:agentic-retrieval) this environment uses. The index is already in the context (L0), the model decides "this topic means this file", and it opens the whole file with the `Read` tool. The model itself decides. In twenty-questions terms, the index is the list of questions and opening one file is asking one question.

The index is hierarchical:

- one line in the global index → the body of `me/*.md` or `refs-*.md`
- a [skill](glossary:skill)'s name and description → the `SKILL.md` body → helper files in that [skill](glossary:skill) folder (for `session-flow`, per-situation files such as `archive.md` and `pr-merge.md`)
- the project [memory](glossary:agent-memory) path given by the session start [hook](glossary:hook) → `MEMORY.md` → split topic files once it passes 3 KB

[Skills](glossary:skill) are the typical example of this structure. [Claude Code](glossary:claude-code) puts only each [skill](glossary:skill)'s `name` and `description` into the [system prompt](glossary:system-prompt) and opens the body when the task comes up. I have 11 [skills](glossary:skill) (table in section 5); their bodies add up to tens of KB, but what goes into every session is a few lines of descriptions.

I did not use [vector RAG](glossary:rag) because of scale and dependencies.

- **Scale**: there are a few dozen [memory](glossary:agent-memory) and [skill](glossary:skill) documents. At that size a file name and a one-line description are enough to choose, and there are not enough documents to need similarity search.
- **Dependencies**: no [embedding](glossary:embedding) model, no vector store, no re-indexing every time a document changes. All it needs is folders, markdown and [git](glossary:git), and all three agents can read files.
- **Maintainability**: what was read and when stays in the transcript as `Read` calls. If the wrong file was opened, fixing one index line is enough.

It has costs too. If the model misreads the index, it does not open the file it needs. Opening a file takes a tool call. If the documents grew into the thousands, the index itself would overflow L0 and this approach would stop fitting. So each index line is written so that it shows "when to open this", and the global files are capped at 10 (section 5).

## 4. The folder is the address

![The cwd goes through path encoding to become the Claude Code auto-memory folder, and the same key finds the memory and worklog](/static/images/devblog-04-agent-environment/folder-routing.svg)

_The [cwd](glossary:current-working-directory) goes through path encoding to become the [Claude Code](glossary:claude-code) auto-memory folder, and the same key finds the [memory](glossary:agent-memory) and worklog_

[Memory](glossary:agent-memory) and worklog are partitioned by [cwd](glossary:current-working-directory). They are split per work folder, and the folder name is the key.

[Claude Code](glossary:claude-code) already creates an auto-memory folder per folder. The path is `~/.claude/projects/<encoded path>/memory/`, where the encoding replaces every non-alphanumeric character in the path with `-` (the repo root for a [git](glossary:git) repo). That folder is created separately on each machine, so left alone, the Mac knows nothing about [memory](glossary:agent-memory) written on Windows.

So the `memory-sync.js` [hook](glossary:hook) moves the folder to `memory/<key>/` in the repo and puts a [symlink](glossary:symbolic-link) in its original place. There are two ways for the other machine to find the same project:

- **[git](glossary:git) repo**: by remote URL. With "remote URL → key" in `memory/repos.txt`, a [clone](glossary:clone) on the other machine links itself the first time an agent opens it, even at a different path.
- **folders that are not [git](glossary:git) repos** (such as the school iCloud folder): by the path for each OS in `memory/paths.txt`. `-` if it does not exist on one OS.

The worklog uses the same key, as in `worklog/vercel-blog/WORK.md`. `worklog/INDEX.md` holds the work currently open ("In progress") and a table that turns the names I use into folders (for example "blog → `~/projects/vercel-blog`").

When a session starts, the [hook](glossary:hook) puts one line into the context: "this folder's project [memory](glossary:agent-memory) path, worklog path". The agent reads the `MEMORY.md` at that path first. The reason for the design is scalability. However many projects there are, only the current folder's path line goes into L0, and other projects' [memory](glossary:agent-memory) is not visible at all.

## 5. Where the rules live

Each kind of information has its own storage location and load time.

| Kind                            | Where                                  | Loaded              | Example                                            |
| ------------------------------- | -------------------------------------- | ------------------- | -------------------------------------------------- |
| Rules for every session         | `agents/*.md` → assembled instructions | L0, every session   | Commit only when told, check dates with `date +%F` |
| Format and procedure for a task | `claude/skills/<name>/SKILL.md`        | L1, for that task   | Publishing to the blog, README format              |
| Rules for one folder only       | that folder's `CLAUDE.md`              | in that folder only | The repo's publishing pipeline                     |
| Current state, references       | `memory/`                              | L1                  | Account locations, pitfalls hit before             |
| To do, done                     | `worklog/<key>/WORK.md`                | L1                  | `## 할 일`, `## 한 일`                             |
| Past records                    | `history/`, `memory/log/`              | L2                  | Finished stages, history of decision changes       |

Only two kinds of thing go into [memory](glossary:agent-memory):

- **State**: facts as of now. Current values only, without the process or how it got there.
- **References**: IDs, paths, account locations and pitfalls you need for the work that are not in any repo.

What stays out is decided too. Working rules go to the instructions or a [skill](glossary:skill), process and history to the log, to-dos to the worklog. "Would I make a mistake in another folder without knowing this?" separates global from project [memory](glossary:agent-memory). Files are grouped by kind, never one file per fact. There are size limits: 2.5 KB per global file, 10 global files, 3 KB for a project `MEMORY.md`.

A project `MEMORY.md` looks like this (example values; the section names are Korean, State and References):

```markdown
# Project memory — example-repo

## 상태

- Deploy: automatic on merge to main, a preview per PR
- Posts published with empty sections: ch3, ch5

## 참조

- Hosting project id: prj_XXXX
- Build pitfall: .md files don't show up, only .mdx
```

And `WORK.md` (sections: Seats, To do, Done):

```markdown
## 자리

- Lead: `<name> Lead`

## 할 일

- [ ] Post 16 waiting for review

## 한 일

- 2026-11-25 Home Lead reopened the project (<session name>)
```

There are 11 [skills](glossary:skill):

| [skill](glossary:skill) | What it does                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------- |
| `session-flow`          | Recording sessions, handover, archiving, running slots                                            |
| `pr-workflow`           | Issues, branches, splitting commits, PRs, merging                                                 |
| `project-docs`          | Stage documents (plan, SRS, SDD, test, installation and maintenance plans), decision records, TDD |
| `docs-style`            | Checklists, comparison tables, report Google Docs                                                 |
| `blog-post`             | Blog post rules (one voice, two layers, cross-links, masking)                                     |
| `readme-style`          | README format for public repos                                                                    |
| `profile-edit`          | GitHub, blog and LinkedIn profiles                                                                |
| `lms-sync`              | Pulling course files and dates from the school LMS                                                |
| `demo-recording`        | Recording demo videos with [Playwright](glossary:playwright)                                      |
| `teruten`               | Turning the exam security program on the Mac on and off                                           |
| `unity-mcp-setting`     | Connecting [MCP](glossary:mcp) to a Unity project                                                 |

The reason for the design is maintainability. When a rule changes there is one place to fix. If the blog rules change, only `blog-post` changes, and the per-session instructions are untouched.

## 6. Why changing instructions don't cause drift

![memory-sync.js build combines four sources into instruction files for the three agents](/static/images/devblog-04-agent-environment/source-build.svg)

_memory-sync.js build combines four sources into instruction files for the three agents_

Instructions keep source and [build artifact](glossary:build-artifact) separate. The sources are `persona.md`, `shared.md`, `claude.md`, `codex.md` and `gemini.md` in `agents/`, plus `memory/global/MEMORY.md`; the build artifacts are `claude/CLAUDE.md`, `codex/AGENTS.md` and `gemini/GEMINI.md`. `node ~/.claude/hooks/memory-sync.js build` concatenates the sources in order and writes the three files.

- Only [Claude Code](glossary:claude-code) understands `@` imports, so `CLAUDE.md` gets the single line `@~/dotfiles/agents/persona.md` instead of the persona text. The [Codex](glossary:codex) and [Antigravity](glossary:antigravity) files get the persona text itself.
- A "Generated by ... Edit those" comment sits at the top of each file, so the file itself says not to edit it directly.
- If the content is unchanged, the file is not rewritten. Running build any number of times gives the same result ([idempotent](glossary:idempotency)).
- The [hooks](glossary:hook) run build on every pull and push. The artifacts are committed too, so a freshly cloned machine works even before any [hook](glossary:hook) has run.

This structure is why three agents and two machines see the same rules even when the instructions keep changing. There is one place to edit, the source, and the machine takes care of the rest.

The change history goes in `memory/log/YYYY-MM.md`. When an agent overwrites a state value or finishes a piece of work, it writes one line itself: `- date [folder/file] what: before → after (why)`. State files keep only current values, and "why did I change that?" is found by `grep`ping the log (L2).

It is also kept in step with the claude.ai app [memory](glossary:agent-memory). Every day at 04:44 (KST), a scheduled cloud task reads `tasks/memory-tidy.md` and makes the global `me/*.md` files and the app [memory](glossary:agent-memory) identical. It backs up the app side first, follows whichever side changed since the last sync commit, and merges line by line when both changed. No cleanup or compression runs automatically.

## 7. Two computers, three agents

![The clones on both machines pull and push with the GitHub repo, and the install scripts create symlinks from links.txt](/static/images/devblog-04-agent-environment/two-machines.svg)

_The [clones](glossary:clone) on both machines pull and push with the GitHub repo, and the install scripts create [symlinks](glossary:symbolic-link) from links.txt_

The two machines sync through [git](glossary:git) and connect through [symlinks](glossary:symbolic-link). The originals live in the repo, and the real places where each tool looks for its settings (`~/.claude/`, `~/.codex/`, `~/.gemini/`, the [VS Code](glossary:vs-code) user folder) hold only links. One file, `links.txt`, decides what is linked where. It has 24 lines.

```text
claude/CLAUDE.md                  ~/.claude/CLAUDE.md
claude/hooks                      ~/.claude/hooks
claude/skills/blog-post           ~/.claude/skills/blog-post
memory/global                     ~/.claude/memory
codex/AGENTS.md                   ~/.codex/AGENTS.md
vscode/settings.json              {vscode}/settings.json
```

Both `install.ps1` (Windows) and `install.sh` (macOS) read this file. Existing files are moved to `~/.dotfiles-backup/<timestamp>/` before the link is made. On Windows without admin rights or Developer Mode, a [junction](glossary:junction) is used instead of a [symlink](glossary:symbolic-link).

The reasons for the design:

- **Maintainability**: when a new link target appears, add one line to `links.txt` and update the README table. The two install scripts are not edited separately.
- **Portability**: every path is written relative to `~` or `$HOME`, and `node` is preferred over `python`/`python3`, whose names differ by OS. All [hooks](glossary:hook) are [node](glossary:nodejs) scripts.
- **Safety**: credentials, sessions, conversation history, caches, sqlite files and build outputs (`*.vsix`) are blocked by `.gitignore`. Line endings and encoding follow `.gitattributes`: [LF](glossary:line-ending) and [UTF-8](glossary:utf-8) without [BOM](glossary:bom) by default, and a [BOM](glossary:bom) only for `.ps1` files that contain Korean, with [CRLF](glossary:line-ending) (Windows PowerShell 5.1 misreads [UTF-8](glossary:utf-8) without a [BOM](glossary:bom)).
- **Visibility**: the repo is private, because [memory](glossary:agent-memory) holds personal state.

The repo also holds settings outside the agents: the [VS Code](glossary:vs-code) extension list (`vscode/extensions.txt`), a local extension that adds [Antigravity](glossary:antigravity) shortcut buttons, and two Windows scheduled tasks (a stretch reminder at :50 every hour, and copying photos into folders by year). The scheduled tasks are not linked; their register scripts are run once.

## 8. hook

![Where hooks run during one session: SessionStart, UserPromptSubmit, PostToolUse, Stop](/static/images/devblog-04-agent-environment/hook-timeline.svg)

_Where [hooks](glossary:hook) run during one session: SessionStart, UserPromptSubmit, PostToolUse, Stop_

[Hooks](glossary:hook) are commands attached to an agent's lifecycle events (session start, prompt submit, after a tool runs, end of a response). If the instructions say "[git](glossary:git) pull when a session starts", the model may forget, but a [hook](glossary:hook) runs regardless of the model. In [Claude Code](glossary:claude-code), 4 scripts are registered in 5 places.

| event                            | script                | What it does                                                                                                                                                          |
| -------------------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SessionStart`                   | `memory-sync.js pull` | [git](glossary:git) pull `~/dotfiles`, repair broken links, rebuild instructions, print one line with this folder's [memory](glossary:agent-memory) and worklog paths |
| `UserPromptSubmit`               | `persona-examples.js` | Inject 2 example dialogues on the first prompt and every third prompt (section 11)                                                                                    |
| `PostToolUse` (Bash, PowerShell) | `pr-merged.js`        | If the command that just ran merged or closed a PR, tell the agent to sync local and record it first                                                                  |
| `Stop`                           | `memory-sync.js push` | Rebuild instructions, register new project [memory](glossary:agent-memory), commit only `memory/`, `worklog/`, `agents/` and the instruction files, then push         |
| `Stop`                           | `notify-done.js`      | A Windows toast notification when a response ends (does nothing on the Mac)                                                                                           |

`memory-sync.js` is over 600 lines so that it can fail quietly:

- **push runs as a [detached process](glossary:detached-process).** The agent does not wait for the push to finish.
- **A [lock](glossary:lock) file** keeps pull and push from touching [git](glossary:git) at the same time.
- **It does not commit when other files are [staged](glossary:staging-area).** That way an automatic commit never splits a commit I am making by hand.
- **On a [conflict](glossary:merge-conflict)**, it [rebases](glossary:rebase) again so that only overlapping hunks follow the remote, and keeps the old local state on a local `sync-conflict/<time>` branch. The next session start shows that name in one line.
- **The automatic commit author** is `dotfiles autosync <autosync@dotfiles.invalid>`, an address no GitHub account owns, so it stays out of the contribution graph.
- Results and failures go to `<tmp>/dotfiles-memory-sync/sync.log`.

[Codex](glossary:codex) [hooks](glossary:hook) the same scripts in `codex/hooks.json` on `SessionStart` (pull), `UserPromptSubmit` (persona) and `Stop` (push). [Antigravity](glossary:antigravity) has different [hook](glossary:hook) events, so pull (actually pulling only once every 10 minutes) and the persona go on `PreInvocation`, and push on `Stop`. The same script takes a `claude|codex|antigravity` argument and answers in each agent's output format (plain text, `additionalContext` JSON, `ephemeralMessage` JSON).

[Hook](glossary:hook) output is also an L0 cost, so there are rules: the session start [hook](glossary:hook) prints one path line, and the persona [hook](glossary:hook) two examples every third prompt. [Hooks](glossary:hook) do not repeat what is already in the instructions.

## 9. MCP

[MCP](/en/blog/cs-fundamentals/ai/ai-07-01-ai-agent/#model-context-protocol-mcp) (Model Context Protocol) servers are connections that let an agent use outside services such as Google Drive, a calendar or Notion as tools, and every connected server's tool list goes into the [system prompt](glossary:system-prompt) (L0). So the rule is "the same tool never comes in through two paths". Roughly half of the 50,000 tokens of an empty session from section 2 come from here.

| Agent                               | How it gets them                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Claude Code](glossary:claude-code) | The claude.ai account's [connectors](glossary:connector) and [plugins](glossary:plugin) (Google Workspace, Notion, Slack, [Playwright](glossary:playwright) and others) come first. No local [MCP](glossary:mcp) in the user scope. Only what a [connector](glossary:connector) can't do is added from that folder with `claude mcp add --scope local`. Right now that is two places, the Roblox folder and the Unity folder. |
| [Codex](glossary:codex)             | Only its own account [plugins](glossary:plugin). No local [MCP](glossary:mcp).                                                                                                                                                                                                                                                                                                                                                |
| [Antigravity](glossary:antigravity) | It has no account [connectors](glossary:connector), so it gets every local launcher and remote [endpoint](glossary:endpoint).                                                                                                                                                                                                                                                                                                 |

The [Antigravity](glossary:antigravity) config is never edited by hand. `mcp/sync.mjs` reads the shared service list and generates the [Codex](glossary:codex) and [Antigravity](glossary:antigravity) configs. `gemini/mcp_config.json` is a template in the repo; the real config (`~/.gemini/config/mcp_config.json`) contains [OAuth](glossary:oauth) settings, so it is only generated on each machine and never committed. `mcp/roblox.mjs` and `mcp/google-calendar.mjs` are launchers that start their servers from home-relative paths. [VS Code](glossary:vs-code) has a single Unity [MCP](glossary:mcp) in `vscode/mcp.json`.

Authentication is separate per client and never copied. Token files live outside the repo and are set up by hand on each machine. [Plugins](glossary:plugin) and [connectors](glossary:connector) are turned on when there is a use for them and turned off after a month without use.

The reasons for the design are dependencies and cost. Leaving [Claude Code](glossary:claude-code) to the account [connectors](glossary:connector) means no servers to run on each machine, and folder-scoped servers grow the tool list only in that folder.

## 10. Session layout

![Under the Home Lead there is a Lead per project, and under that PM, FE and BE slots and work sessions](/static/images/devblog-04-agent-environment/session-hierarchy.svg)

_Under the Home Lead there is a Lead per project, and under that PM, FE and BE slots and work sessions_

Sessions are arranged in a hierarchy. In the [Claude Code](glossary:claude-code) desktop app a session can start other sessions, which are nested under it.

1. **Home Lead**: one, in home (`~`). Opens and closes projects and keeps "In progress" in `worklog/INDEX.md`.
2. **Project Lead** (`<name> Lead`): one per open project, running in the project root. It only divides the work and never edits code itself.
3. **Slots and work sessions**: role seats I asked for, such as PM, FE and BE, and work sessions the Lead hands one task each. This post, too, was written by a work session that the blog Lead started.

A few rules hold the structure together:

- **Leads hold no state.** Open projects are in `INDEX.md`, and a project's slots and work are in that key's `WORK.md`. So any Lead can have its conversation replaced and keep working just by reading the files.
- **The slot stays; only the conversation is replaced.** A replacement is a handover, not an ending. The next conversation starts from `WORK.md`, not from the old conversation.
- **Reports go up only**, with `SendMessage`. A work session reports to the session that started it, a Project Lead to the Home Lead.
- **Records are written in the turn where something changed.** When the app automatically archives a session left idle, no model runs, so trying to write just before archiving misses it.
- **Finished sessions** are archived, and a link to the transcript is kept under `session-archive/<YYYY-MM>/<key>/` with a readable name (`archive-link.js`). This folder differs per machine and is not in [git](glossary:git).

The reason for the design is close to testability. Because state lives only in files, what a session knows can be checked in `WORK.md` instead of in the conversation.

## 11. Persona

The persona is set with a [persona prompt](glossary:persona-prompt) and few-shot examples. `agents/persona.md` sets the background, attitude and tone: an old friend who speaks casually, in short sentences, with some teasing. It looks like a joke, but it has functions:

- **Term correction**: when I blur a technical term or answer back with the analogy, it accepts that and then makes me say it again with the right term, at most one per answer. The two-layer structure of this post, starting with an analogy and ending with terms, comes from the same rule.
- **Keeping the tone**: it keeps long explanations from slipping back into an assistant voice.

In long sessions the persona fades ([persona drift](glossary:persona-drift)). The [system prompt](glossary:system-prompt) is at the very beginning, and as the conversation grows, recent messages carry relatively more weight. So the `persona-examples.js` [hook](glossary:hook) injects two example dialogues from `agents/examples.md` again on the first prompt and every third prompt. There are 8 examples; they rotate in a fixed order, with some appearing more often. The instruction file keeps only 2 examples permanently, and the [hook](glossary:hook) rotates the rest. That is cheaper than putting all 8 in L0.

Text that goes into files (commit messages, code comments, documents) does not use the persona's tone. Neither does this post.

## 12. Limits and next steps

The limits of the current structure:

- **It relies on index quality.** The model picks a file from one index line, so a vague description means it does not open the file it needs. There is no way to measure this yet.
- **L0 was not measured item by item.** The only [token](glossary:token) figure is about 50,000 for a whole empty session; everything else was measured in bytes. Korean has a different byte-to-token ratio from English, so per-item cost can't be stated precisely from byte counts.
- **Sync [conflicts](glossary:merge-conflict)**: when both machines edit the same file at the same time, a [conflict](glossary:merge-conflict) happens. On the day I wrote this, the Windows [clone](glossary:clone) had a [conflict](glossary:merge-conflict) in one `worklog/` file. Cases the [hook](glossary:hook) cannot resolve automatically have to be cleaned up by hand.
- **[Hook](glossary:hook) features differ per agent.** [Antigravity](glossary:antigravity)'s [hook](glossary:hook) input format is undocumented, so one received input is saved to a file and the code is matched to it.
- **[Memory](glossary:agent-memory) cleanup is not automatic.** There used to be a daily automatic cleanup, but it is off now; agents overwrite values in the turn where they change and leave a log line. Whether the size limits are exceeded is checked by a person.

Two things to try next: measure how many [tokens](glossary:token) each part of L0 takes at session start and add it to the table below, and test with a few questions whether the right file gets opened from one index line.
