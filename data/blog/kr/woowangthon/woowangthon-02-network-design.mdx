> 시리즈 2편. 학교 PC를 손에 넣기 전후로 클러스터 설계가 어떻게 바뀌었는지다. 프로젝트 전체 그림은 [Woowangthon 0](/kr/blog/woowangthon/woowangthon-00-overview/)에 있다.

## 한 줄 요약

클러스터 설계는 열흘 동안 크게 네 번 바뀌었다. 바뀐 이유는 대부분 **전제가 틀려서**였다. 강의실 PC라고 생각했는데 전용 PC였고, 와이파이로 나가야 한다고 생각했는데 벽에 랜 포트가 있었다. 그중 하나는 내가 정한 적도 없는 전제였다. 나와 같이 계획서를 쓰던 AI 에이전트가 짐작으로 채운 빈칸이 확정처럼 적혀 있었다. 그 뒤로 계획서의 모든 줄에 상태 표시를 붙였다.

## 1. 첫 번째 그림: 강의실 PC를 빈 시간에 빌린다

10월 26일, 처음 그린 그림의 전제는 이랬다.

- 학교 실습실 PC는 수업 시간에만 쓰이고 나머지 시간에는 논다
- 그러니 수업이 없는 시간에 그 PC들을 빌려 클러스터에 붙인다
- PC는 언제 꺼질지 모르고, 학교 방화벽 안에 있고, 학생 코드는 믿을 수 없다

이 전제에서 나온 설계가 [1편](/kr/blog/woowangthon/woowangthon-01-docs-and-prs/#1-첫날-혼자-올린-문서-셋)에서 닫힌 ADR-002 제안이다. 정적 사이트는 Cloudflare R2에 올리고, 서버가 필요한 앱만 실습실 PC의 k3s에 띄우고, PC가 모자라면 클라우드 VM으로 넘긴다. 그보다 먼저 떠올린 안은 k3s 리더를 아예 클라우드 VM에 두고, 학교 PC는 켜져 있을 때만 워커로 붙는 모양이었다.

PC가 남의 것이고 언제 꺼질지 모른다는 전제는 설계 곳곳에 흔적을 남겼다.

| 전제에서 나온 것               | 이유                                                     |
| ------------------------------ | -------------------------------------------------------- |
| 라이브 USB로 부팅              | 수업용 PC의 내장 디스크를 건드리면 안 된다               |
| 노드마다 자원 40% 상한         | 수업 중인 학생이 같은 PC를 쓴다                          |
| 켜짐 감지, 켜져 있을 때만 참여 | PC가 수업 시간표에 따라 꺼진다                           |
| 교수님께 물을 것 목록          | 강의실 DHCP와 고정 IP, 강의실 시간표, USB 부팅 허용 여부 |

이 표의 네 줄은 나중에 전부 사라진다.

## 2. 두 번째 그림: 노드끼리는 스위치로

10월 30일에 팀 다이어그램이 페이지별로 나뉘어 올라왔고, 나는 노드끼리 어떻게 이을지를 따로 팠다. 문제는 학교 와이파이였다. 학교 와이파이에는 **클라이언트 격리**가 걸려 있다. 같은 와이파이에 붙은 기기끼리 서로 보이지 않게 막는 기능이다. 카페 와이파이에서 옆 사람 노트북이 안 보이는 것과 같다. 쿠버네티스 노드는 서로 쉬지 않고 통신해야 하니, 학교 와이파이에 세 대를 붙이는 것만으로는 클러스터가 안 된다.

세 가지 안을 놓고 비교했다.

| 안              | 방법                                                | 걸리는 점                                                |
| --------------- | --------------------------------------------------- | -------------------------------------------------------- |
| A 스위치        | 설정 없는 기가비트 스위치에 랜선으로 세 대를 묶는다 | 장비를 사야 한다. 스위치가 꺼지면 노드끼리 끊긴다        |
| B 동방 와이파이 | 격리가 없는 동아리 공유기 와이파이에 붙인다         | 그 공유기가 언제 꺼질지 모른다. 유선보다 느리고 흔들린다 |
| C Tailscale     | 노드끼리도 Tailscale 사설망으로 묶는다              | 격리 때문에 직접 못 붙으면 해외 중계 서버를 거친다       |

C안은 매력적이었다. 원격 접속용으로 어차피 Tailscale을 깔 거라 추가 장비가 없다. 하지만 노드끼리 오가는 건 원격 접속과 양이 다르다. 클러스터 신호, 다른 워커에 있는 Pod끼리 통신, 리더에서 이미지 받기, 그리고 DB 볼륨 복제가 전부 이 길을 탄다. DB에 쓸 때마다 반대쪽 워커의 사본까지 해외 중계 서버를 찍고 와야 쓰기가 끝난다. 학교 인터넷이 잠깐만 끊겨도 노드끼리 서로 안 보이게 되고, 리더는 멀쩡히 돌던 앱을 다른 노드에 다시 띄우기 시작한다.

그래서 10월 31일 A안으로 정하고, 그날 바로 스위치와 랜선 4개를 샀다. B와 C는 현장에서 스위치가 안 될 때만 꺼내는 예비로 남겼다.

여기서 인터넷은 어떻게 나가느냐가 남았다. 계획서에는 이렇게 적혀 있었다. "스위치는 학교망에 연결하지 않는다. 인터넷은 PC마다 학교 와이파이로 나간다." 이 줄은 팀 시스템 정의서에도 그대로 들어갔다. 이 줄이 어디서 왔는지는 4절에서 이야기한다.

## 3. 세 번째 그림: 서버가 클러스터에 닿는 길

학교 PC 쪽이 정해지자, 이번에는 AWS에 있는 플랫폼 서버가 학교 PC에 어떻게 닿을지가 문제였다. 학교로 들어오는 포트는 열지 않으므로 연결은 학교 안에서 밖으로 걸어야 한다.

팀 다이어그램의 첫 안은 리더에 에이전트를 하나 두는 것이었다. 에이전트가 플랫폼 서버로 WebSocket 연결을 걸어 두고, 서버는 그 연결로 "이거 배포해" 같은 지시를 보낸다. 지표는 리더의 Prometheus가 서버 쪽 시계열 DB로 밀어 보내고(remote_write), 로그는 별도 수집기가 밖으로 보낸다.

11월 1일 디스코드에서 이걸 바꿨다. 근거는 이미 정해 둔 것 하나였다. **원격 접속용으로 세 노드에 Tailscale을 깔기로 했다.** 그러면 플랫폼 서버도 같은 사설망에 들어오면 된다. 서버가 사설망 주소로 리더의 쿠버네티스 API를 직접 부르면, 에이전트를 새로 짤 필요가 없다. 지표도 서버가 리더의 Prometheus에 직접 물어보면 되니 시계열 DB를 하나 더 세울 이유가 없다.

| 항목                      | 다이어그램 첫 안                           | 바뀐 안                                                                                            |
| ------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 서버 → 클러스터 지시      | 리더 에이전트가 서버로 WebSocket 상시 연결 | 서버가 Tailscale로 리더의 쿠버네티스 API를 직접 부른다                                             |
| 지표                      | 리더 → 서버 쪽 시계열 DB로 밀어 보냄       | 서버가 리더의 Prometheus에 직접 조회. 2주 보관                                                     |
| 레지스트리                | 미정 (문서엔 ECR)                          | GHCR, 이미지 공개 ([1편](/kr/blog/woowangthon/woowangthon-01-docs-and-prs/#3-한-사실이-열-파일에)) |
| 학교에서 밖으로 거는 연결 | 5개                                        | 4개                                                                                                |

서버가 쿠버네티스 API를 직접 부르는 만큼 권한은 좁혔다. 서버는 학생 프로젝트 공간(`proj-<id>`) 안의 자원과 그 공간을 만들고 지우는 것만 할 수 있고, 비밀값(Secret)은 쓰기만 할 수 있다. 서버가 털려도 시스템 영역과 비밀값을 못 건드리게 하려는 것이다. 서버 코드에서는 쿠버네티스 호출을 한 모듈에 모아 두기로 했다. 나중에 에이전트 방식으로 돌아가야 하면 그 모듈만 바꾸면 된다.

다음 날에는 백업을 내렸다. 학생 볼륨을 클러스터 밖(R2)에 백업하고 리더 상태를 스냅샷으로 남기는 계획이 있었는데, 대회가 끝나면 PC를 반납한다. PC가 통째로 사라지는 경우까지 막는 건 심사와 상관이 없다. 워커 하나가 꺼졌을 때 다른 워커가 받는 것만 남기고 나머지는 후순위로 내렸다.

## 4. 네 번째 그림: PC를 받은 날

11월 3일, 학교 PC 세 대를 받았다. 받고 나서 확인한 것들이 하루 만에 앞의 전제를 여럿 뒤집었다.

| 확인한 것                                                              | 사라진 것                                                           |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 강의실 PC가 아니라 **우리 전용으로 따로 받은 PC**. 24시간 켜 둬도 된다 | 켜짐 감지, 40% 자원 상한, 강의실 시간표 질문                        |
| OS가 내장 디스크에 깔려 있고 재부팅해도 남는다                         | 라이브 USB 부팅 갈래                                                |
| 동아리방 벽에 **학교 유선 랜 포트**가 있다                             | "인터넷은 PC마다 와이파이"                                          |
| 학교 와이파이는 학번 로그인(802.1X) 방식                               | 웹 로그인이라 무인 운영이 안 될 거라는 걱정. 와이파이는 예비로 남김 |

사양도 생각보다 훨씬 좋았다. i7-13700K(24스레드), 메모리 125GiB, NVMe 1TB, RTX 3080. 학생 프로젝트 둘을 돌리기에는 넘친다. 덕분에 DB 볼륨을 두 워커에 복제하는 방식(Longhorn 사본 2)을 고민 없이 고를 수 있었다.

### 정한 적 없는 전제

벽 랜 포트 이야기를 꺼내자 같이 계획서를 쓰던 AI 에이전트(Claude Code)는 이걸 설계 변경으로 받았다. "스위치를 학교망에 연결하지 않는다"가 원래 설계였으니까. 그런데 나는 처음부터 벽 포트에 스위치를 물릴 생각이었다. 그 줄을 정한 적이 없었다.

거슬러 올라가 보니 이렇게 된 일이었다. "학교 와이파이에는 격리가 있다"는 전제에서 에이전트가 빈칸을 채웠다. 노드끼리는 격리된 사설망으로 묶고 인터넷은 따로 나가는 모양, 내가 [클라우드컴퓨팅 과제](/kr/blog/cloud-computing/cloud-computing-hw2-kvm-vm-cluster/#0-실습-환경)에서 VM 클러스터를 만들 때 쓴 모양이다. 그럴듯한 짐작이었고, 계획서에 다른 결정들과 똑같은 말투로 적혔다. 그 뒤로 나도 팀도 그걸 결정으로 읽었다. 팀 시스템 정의서에도 그대로 들어갔다.

틀린 짐작 자체보다, 짐작이 결정과 구분되지 않았다는 게 문제였다.

## 5. 모든 줄에 상태를 붙이다

그래서 계획서 맨 앞의 전제 표 모든 줄에 상태를 붙였다.

| 상태        | 뜻                                                                    |
| ----------- | --------------------------------------------------------------------- |
| **확정**    | 정했고, 바꿀 조건이 없다                                              |
| **예정**    | 정했지만 시험이나 바깥 확인이 남았다. 어느 단계에서 확인되는지 적는다 |
| **결정 전** | 팀과 정한다                                                           |
| **미정**    | 서버 담당과 정한다                                                    |
| **미확인**  | 현장에서 봐야 안다                                                    |

지금 계획서의 몇 줄은 이렇게 생겼다.

| 항목         | 내용                                                                         | 상태    |
| ------------ | ---------------------------------------------------------------------------- | ------- |
| 노드 간 연결 | 스위치. 노드끼리 쓰는 고정 주소를 학교 주소와 같은 랜 카드에 얹는다          | 확정    |
| 공개 터널    | Cloudflare Tunnel. 학교망이 터널 포트(7844)를 통과시키는지 3단계에서 본다    | 예정    |
| 로그 저장    | 최근 몇 줄만으로는 새벽 사고를 못 본다는 반론이 나와 다시 제안 중            | 결정 전 |
| PC 원상복구  | 디스크 이미지로 되돌린다. 원상복구가 반납 조건인지는 빌려준 분께 물어야 한다 | 예정    |

규칙은 하나다. **현장에서 보지 않은 것은 미확인이다.** 에이전트가 채운 빈칸이든 내가 채운 빈칸이든 같다. 이 표시 덕분에 PC를 받고 이틀 동안 바뀐 것들(벽 포트로 인터넷이 되는지, 와이파이 카드가 있는지)이 어디를 건드리는지 바로 보였다.

계획서는 지금 85번째 버전이다. 대부분은 이런 전제 하나가 바뀌면서 연달아 고친 흔적이다.

## 6. 벽 포트가 바꾼 것

벽 포트에 스위치를 물리면 인터넷이 유선으로 들어와 편해진다. 대신 새 문제도 같이 들어온다.

- **유선에는 격리가 없다.** 학교망의 다른 기기가 우리 PC의 SSH와 쿠버네티스 포트에 바로 닿는다. 그래서 들어오는 연결은 방화벽이 기본으로 거부하고, 스위치 망과 사설망만 허용한다(3단계)
- **노드 주소는 학교 주소와 따로 둔다.** 학교가 준 주소는 바뀔 수 있다. 노드끼리 쓰는 고정 주소(`192.168.77.x`)를 같은 랜 카드에 하나 더 얹고, k3s는 그 주소를 쓰게 한다. 이 주소에는 게이트웨이를 넣지 않는다. 넣으면 인터넷으로 가는 길이 그쪽으로 빠진다
- **벽으로 가는 선은 딱 한 줄.** 두 줄이 되면 고리가 생겨 동아리방 망 전체가 먹통이 될 수 있다
- **스위치가 두 번째 단일 장애점이 된다.** 리더 다음이다. 스위치 전원이 잠깐 나가면 노드끼리 끊기고 인터넷도 같이 끊긴다

## 7. 바뀌지 않은 것

네 번 뒤집히는 동안에도 처음부터 끝까지 그대로인 것이 있었다.

- 리더 1대 + 워커 2대. 리더가 꺼지면 새 배포가 멈추는 건 감수한다(PC가 셋뿐이라 리더를 셋 둘 수 없다)
- 학교로 들어오는 포트는 0개. 바깥과의 연결은 전부 학교 안에서 밖으로 건다
- 학생 코드 빌드는 학교 밖에서 한다. 학교 PC는 실행만 한다
- 지표는 Prometheus가 모으고 Grafana가 보여 준다
