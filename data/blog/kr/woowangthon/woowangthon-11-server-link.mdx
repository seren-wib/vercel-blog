> 시리즈 11편. 구축 6단계(바깥이랑 잇기) 중 플랫폼 서버가 클러스터에 붙는 길, 구축 09다. [10편](/kr/blog/woowangthon/woowangthon-10-public-entry/)을 쓸 때는 이 일을 [Woowangthon 0](/kr/blog/woowangthon/woowangthon-00-overview/)에 한 줄로만 남겼는데, 다음 날 조치 권한까지 붙으면서 글 하나가 됐다. 클러스터 쪽은 11월 10~11일에 끝났고, 서버가 올라갈 EC2는 아직 없다.

## 한 줄 요약

AWS에 있을 플랫폼 서버가 학교 리더의 쿠버네티스 API를 부를 계정을 만들고, 그 계정을 학생 공간(`proj-`) 안으로 묶었다. RBAC는 네임스페이스 이름으로 거르지 못해서 검사 규칙을 겹쳤다. 비밀값은 "쓰기만" 주려 했는데 patch 하나로 값이 읽히는 길이 있었고, 읽기는 검사 규칙이 아예 못 봤다. 시험 스크립트는 셀프 리뷰에서, 거절을 기대하던 요청이 규칙이 꺼진 날엔 로컬 모델 공간을 통째로 지울 수 있었다는 게 드러났다. 지금 111개 시험이 통과한다. 다만 EC2에서 실제로 닿는지는 아직 아무도 못 봤다.

## 1. 서버가 클러스터에 붙는 길

[2편에서 바꾼 그림](/kr/blog/woowangthon/woowangthon-02-network-design/#3-세-번째-그림-서버가-클러스터에-닿는-길)대로, 플랫폼 서버는 Tailscale 사설망에 들어와 리더의 쿠버네티스 API(`:6443`)를 직접 부른다. [7편의 회의](/kr/blog/woowangthon/woowangthon-07-leader-vllm/#1-회의에서-바뀐-것)에서 배포는 리더의 배포 실행기 몫으로 갔고, 서버에 남은 일은 넷이다.

| 서버가 하는 일   | 클러스터에서 필요한 것                                                                                               |
| ---------------- | -------------------------------------------------------------------------------------------------------------------- |
| 학생 공간 만들기 | 네임스페이스와 [양식 객체](/kr/blog/woowangthon/woowangthon-09-student-space/#1-학생-공간-하나에-들어가는-것) 만들기 |
| 비밀값 넣기      | 학생 `.env`를 Secret으로 쓰기                                                                                        |
| 상태 보기        | 공간 안 Pod · 로그 · Deployment 읽기, 노드 읽기                                                                      |
| 조치             | 학생 서비스 끄기 · 다시 켜기 · 재시작                                                                                |

이 계정의 토큰은 클러스터 밖, AWS의 EC2에 놓인다. 인터넷에서 요청을 받는 서버라 학교 PC보다 공격받을 일이 많은 자리다. 그래서 설계의 질문은 하나였다. **이 토큰이 새면 어디까지 무너지나.** 답이 "학생 공간 안에서 서비스를 끄고 켜는 것까지"여야 한다. 시스템 공간, 로컬 모델, 다른 학생의 비밀값, 공간의 자원 상한과 차단 규칙은 건드리지 못해야 한다.

EC2는 아직 없었다. 그래도 내 몫은 서버가 붙을 자리를 만들어 두는 것이라 EC2를 기다릴 이유가 없었다. 계정, 권한, 검사 규칙은 리더에서 만들고, 시험은 내 데스크탑에서 실제 토큰으로 리더의 Tailscale 주소를 불러서 한다. 출발지만 EC2가 아닐 뿐 같은 길이다. EC2가 있어야만 볼 수 있는 건 마지막에 따로 모았다(9절).

## 2. RBAC는 이름으로 거르지 못한다

계정은 운영 공간 `platform`의 ServiceAccount `platform-server` 하나에, 만료 없는 토큰 하나다. 대회 기간에 갱신할 인증 정보를 두지 않으려고 그렇게 했다. 토큰이 새면 리더에서 그 Secret을 지우면 폐기된다.

권한을 적다가 바로 막혔다. 서버는 `proj-<id>` 공간을 만들고 지워야 한다. 그런데 쿠버네티스의 권한(RBAC)에는 "이름이 `proj-`로 시작하는 네임스페이스만"이라는 조건을 걸 자리가 없다. 네임스페이스 삭제를 주면 `kube-system`이든 `vllm`이든 다 지울 수 있다. Secret 쓰기도 아직 없는 공간에 미리 줄 수가 없으니 클러스터 전체로 줘야 한다.

그래서 권한은 넓게 주고, 그 위에 **검사 규칙**(ValidatingAdmissionPolicy)을 겹쳤다. 요청이 저장되기 직전에 조건식으로 거르는 쿠버네티스 기본 기능이다.

| 검사 규칙                    | 통과 조건                                                                    |
| ---------------------------- | ---------------------------------------------------------------------------- |
| `wanggane-platform-server`   | 서버 계정의 쓰기 · 삭제는 `proj-` 공간에서만. 공간 라벨은 보안 등급 둘뿐     |
| `wanggane-space-quota` 외 둘 | 상한 · 기본값 · 차단 규칙은 이름과 값이 양식과 같을 때만                     |
| `wanggane-space-readers`     | 읽기 권한 연결은 이름 · 역할 · 대상 계정이 양식과 같을 때만 (4절)            |
| `wanggane-student-pods`      | `proj-` 공간의 Pod는 `NET_RAW`를 빼고 API 토큰을 끈 것만. 모든 계정에 걸린다 |

마지막 줄은 [9편에서 미뤄 둔](/kr/blog/woowangthon/woowangthon-09-student-space/#4-양식에서-뺀-serviceaccount) 것이다. Pod 규칙은 바로 거절로 켜지 않고 경고 모드(`Warn, Audit`)로 먼저 올렸다. `proj-demo`의 시험 앱은 경고 없이 다시 떴고, 규칙을 어긴 맨 Pod에만 경고가 붙었다. 그걸 보고 거절 모드로 바꿨다.

이 구조에는 순서가 생긴다. 서버 계정을 `proj-` 안에 묶는 건 검사 규칙 하나뿐이다. 규칙이 꺼진 채로 계정이 있으면 그 토큰은 어느 공간의 Secret이든 쓰고 네임스페이스를 지울 수 있다. 그래서 **규칙을 먼저 적용하고 계정을 나중에, 없앨 때는 계정부터** 지운다. 이 순서는 매니페스트 맨 위 주석과 설계 문서에 적었다.

### 양식 값을 규칙에 베끼지 않는다

상한 · 기본값 · 차단 규칙이 "양식과 같은 값"인지 보려면 규칙이 양식 값을 알아야 한다. 값을 규칙에 그대로 적으면 양식을 고칠 때마다 두 군데를 고쳐야 하고, 언젠가 한쪽만 고친다.

그래서 양식 파일(`Infra/student/space.yaml`)을 이름만 바꿔 `student-template`이라는 기준 공간에 적용해 두고, 규칙이 그 공간의 객체와 비교하게 했다(`paramKind`). 처음 쓴 비교식 `object.spec == params.spec`은 타입 검사에서 걸렸다.

```text
found no matching overload for '_==_' applied to '(NetworkPolicy634666355.spec, NetworkPolicy635355785.spec)'
```

같은 NetworkPolicy인데 두 쪽에 서로 다른 타입 이름이 붙어서 비교가 안 된다. 양쪽을 `dyn()`으로 감싸니 통과했다.

차단 규칙은 값만이 아니라 이름까지 묶었다. NetworkPolicy는 여러 개면 허용이 합쳐진다. 값이 똑같은 규칙 옆에 "전부 허용" 규칙을 다른 이름으로 하나 더 만들면 차단이 풀린다.

## 3. 쓰기만 준다는 게 쓰기만이 아니었다

비밀값은 처음부터 "쓰기만"이었다. [2편](/kr/blog/woowangthon/woowangthon-02-network-design/#3-세-번째-그림-서버가-클러스터에-닿는-길)에도 그렇게 적었다. 서버는 학생 `.env`를 넣기만 하고 다시 읽을 일이 없다. 그래서 계획의 권한은 Secret 만들기 · 고치기 · patch였다. 읽기(`get`)는 없다.

만들다가 걸렸다. patch 요청의 응답은 **바뀐 뒤의 객체 전체**다. 아무것도 안 바꾸는 빈 patch를 하나 보내면 응답에 Secret 값이 통째로 돌아온다. 읽기 권한 없이 읽힌다. 통째로 바꾸기(PUT)의 응답은 서버가 보낸 값뿐이라 이런 길이 없다.

patch를 뺐다. 서버는 처음엔 만들기(POST)를 보내고, 이미 있다는 `409`가 오면 통째로 바꾸기(PUT)로 다시 보낸다. 서버 쪽 클러스터 호출 모듈(#118)을 내가 짤 때 이 순서를 그대로 넣었고, 실제 리더에서 `POST 201`, 두 번째에 `409` → `PUT 200`을 확인했다. 대가도 있다. 서버는 PUT 뒤에 키가 제대로 바뀌었는지 읽어 볼 수 없다. 응답 `200`까지가 서버가 아는 전부다.

Secret에는 규칙을 하나 더 걸었다. 타입이 `Opaque`이고 이름이 `<서비스>-secrets` 모양일 때만 통과한다. 서비스 계정 토큰 타입 Secret을 만들면 쿠버네티스가 그 안에 API 토큰을 찍어 준다. 학생 공간 안에서 새 토큰을 찍어 내는 길을 막은 것이다.

![check.sh의 Secret 묶음. 읽기 · 목록 · patch · 삭제는 권한이 없어 거절, 다른 이름 · 토큰 타입 · proj- 밖 Secret과 vLLM 키 덮어쓰기는 검사 규칙이 거절. Pod · Deployment · Middleware 만들기도 권한이 없다](/static/images/woowangthon-11-server-link/check-secrets.svg)

_괄호 안은 거절한 쪽이다. rbac는 권한이 없어서, policy는 검사 규칙이 막아서_

## 4. 읽기는 검사 규칙이 못 본다

1차로 만든 계정에는 읽기가 하나도 없었다. 그런데 서버는 학생 Pod 상태를 화면에 보여 주고, 로그를 AI에 넘기고, 조치가 먹었는지 Deployment를 봐야 한다.

여기서 검사 규칙이 쓸모없어진다. 검사 규칙은 쓰기 요청에만 걸리고 읽기는 아예 안 본다. 읽기를 클러스터 전체로 주면 서버 토큰 하나로 이런 것까지 읽힌다.

- `kube-system`의 Traefik 로그: 어느 학생 사이트에 누가 들어왔는지
- `vllm`의 로그: AI 서버가 로컬 모델에 보낸 요청 흔적
- 다른 운영 공간의 Pod 목록과 구성

서버가 관리하는 건 학생 앱뿐이다. 시스템 공간은 운영자인 내가 SSH로 본다. 그래서 읽기를 `proj-` 공간으로 좁히기로 했다. 방법은 공간마다 권한을 따로 거는 것이다. 읽기 역할 `proj-reader`를 하나 두고, 서버가 공간을 만들 때 그 공간에 권한 연결(RoleBinding) `platform-server-read`를 같이 만든다. 학생 공간 양식의 객체가 넷에서 다섯이 됐다(배포 실행기용 연결이 붙어 지금은 여섯이다). 서버가 연결할 수 있는 역할은 `proj-reader` 하나뿐이고(RBAC `bind`), 검사 규칙이 연결의 이름 · 역할 · 대상 계정을 기준 공간 것과 비교한다. 공간에 속하지 않는 노드만 클러스터 범위로 읽는다.

리더에 적용하다가 이게 났다.

```text
The rolebindings "platform-server-read" is invalid: : ValidatingAdmissionPolicy 'wanggane-space-readers'
with binding 'wanggane-space-readers' denied request: failed to configure binding:
no params found for policy binding with `Deny` parameterNotFoundAction
```

기준 객체가 없으면 거절하도록(`parameterNotFoundAction: Deny`) 해 뒀는데, 그 거절이 서버 계정만이 아니라 **모든 계정**에 걸렸다. 쿠버네티스는 "이 요청이 서버 계정의 것인가"를 보기 전에 기준 객체부터 찾는다. 그래서 운영자인 내가 기준 객체 자체를 넣는 요청까지 거절됐다. 1차 규칙 셋도 같은 구조였는데, 그때는 기준을 규칙보다 먼저 넣어서 드러나지 않았던 것이다. 기준 공간 `student-template`만은 규칙이 건너뛰게 고쳤다.

좁힌 읽기는 서버 쪽 코드에도 흔적을 남겼다. 서버가 만들지 않은(또는 이미 지운) 공간을 읽으면 `404`가 아니라 `403`이 온다. 연결이 없으니 "없다"가 아니라 "권한 없다"로 보인다. 팀장 TaeTaeJin의 운영자 API(#121)는 리뷰에서 이 `403`도 빈 목록으로 다루게 고쳤다.

## 5. 거절을 기대하던 시험이 지울 수도 있었다

시험 스크립트 `Infra/platform/check.sh`는 운영자 기기에서 돈다. 대부분은 리더의 kubectl로 서버 계정을 흉내 내서(impersonation) 하고, 마지막 묶음만 실제 토큰으로 리더의 Tailscale 주소를 부른다. 토큰은 셸 변수에만 두고 찍지 않는다.

1차 PR([woowangthon/WOOWANGTHON_TEAM_18#87](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/87))을 올리고 셀프 리뷰(에이전트의 코드 리뷰)를 돌렸다. 아홉 개가 나왔고, 제일 무서운 건 시험 스크립트 안에 있었다.

"`vllm` 공간 삭제가 거절되는가", "vLLM API 키 Secret 덮어쓰기가 거절되는가"를 시험하는 줄이 **진짜 요청**이었다. 검사 규칙이 켜져 있으면 거절되니 무해하다. 그런데 이 스크립트가 제일 필요한 날은 규칙이 고장 났거나 경고 모드로 내려 둔 날이다. 그날 돌리면 `vllm` 공간이 지워진다. 모델 볼륨과, 리더에서 만들어 Secret에만 둔 하나뿐인 API 키까지 같이.

실제 객체를 겨누는 거절 시험은 전부 server dry run으로 바꿨다. 검사 규칙은 똑같이 판정하고, 통과하더라도 아무것도 저장되지 않는다. 규칙이 꺼져 있으면 시험이 실패할 뿐이다.

[9편의 거짓 PASS](/kr/blog/woowangthon/woowangthon-09-student-space/#7-시험하지-않고도-통과할-수-있었다)와 짝이 되는 얘기다. 그때는 시험이 아무것도 안 재고 통과할 수 있었고, 이번엔 시험이 막으려던 사고를 시험이 낼 수 있었다. 둘 다 같은 에이전트가 쓰고 같은 리뷰가 잡았다.

나머지 지적도 고쳤다.

| 지적                                        | 고친 것                                       |
| ------------------------------------------- | --------------------------------------------- |
| 토큰 자동 마운트를 꺼도 손으로 넣을 수 있다 | projected 볼륨의 `serviceAccountToken`도 거절 |
| 토큰이 curl 인자로 넘어간다                 | 프로세스 목록에 보이는 자리라 stdin으로       |
| 라벨 고치기 시험이 사실은 읽기 거절만 봤다  | 직접 patch로 시험                             |
| 맥에서 안 돌 수 있다                        | gawk 다중 문자 구분자 · `base64 -d`를 안 쓰게 |
| 되돌리는 순서가 PR 본문에 거꾸로 적혔다     | 계정부터 지운다로 바로잡음                    |

스크립트를 쓰면서 "엉뚱한 이유로 통과하는 거절"도 둘 걸렀다. `proj-`라는 이름은 검사 규칙까지 가기 전에 이름 형식 오류로 거절되고, `kube-system` 삭제는 쿠버네티스가 스스로 막는다. 둘 다 "규칙이 막았다"의 증거가 아니다. 앞의 것은 시험에서 빼고, 뒤의 것은 이유를 `builtin`으로 따로 세게 했다. 거절 시험은 거절된 이유까지 맞아야 통과한다.

## 6. 끄기, 켜기, 재시작

다음 날 TaeTaeJin의 운영자 강제 중지 API(#121)가 먼저 머지됐다. 서버 계정에 끄기 권한이 없어서, 중지 부분은 항상 `CLUSTER_FORBIDDEN`을 돌려주는 자리 채움이었다. TaeTaeJin이 디스코드로 제안을 보냈다. `deployments/scale` 하위 리소스의 `get` · `patch` · `update`를 `proj-reader`에 넣자, scale로는 레플리카 수만 바뀌니 검사 규칙은 필요 없어 보인다는 내용이었다.

`proj-reader`에 넣자는 건 그대로 받았다. 공간마다 이미 있는 읽기 연결이 그 역할을 가리키니, 역할만 고치면 이미 만든 공간에도 바로 걸린다. 공간 양식도 서버의 공간 만들기 코드도 안 바뀐다. 이름이 "reader"인데 끄기가 들어가는 어긋남은 주석과 문서에 적고 감수했다.

두 군데는 좁혔다. 에이전트는 서버가 PATCH만 부르니 `get`과 `update`는 필요 없다고 봤다. 그리고 "레플리카만 바뀐다"는 "0만"이 아니다. 토큰이 새면 공간 상한 안에서 늘릴 수도 있다. 그래서 `patch`만 주고, 서버 계정의 scale 요청은 레플리카 0일 때만 통과하는 규칙(`wanggane-platform-server-scale`)을 더했다.

시험을 먼저 넣고 적용 전에 돌려서 새 줄만 실패하는 걸 보는 순서로 했다. 실패 메시지가 예상과 달랐다.

```text
FAIL scale it to 0: Error from server (Forbidden): deployments.apps "web" is forbidden: User
"system:serviceaccount:platform:platform-server" cannot get resource "deployments/scale" ...
```

`patch`가 아니라 `get`에서 막혔다. 시험에 쓴 `kubectl patch --subresource=scale`은 patch 전에 scale 객체를 먼저 읽는다. TaeTaeJin의 목록에 `get`이 있었던 데는 이유가 있었다. `get`을 다시 넣었다. 보이는 건 레플리카 수뿐이다. `update`는 끝까지 안 줬다.

하나 더, Scale 객체는 0일 때 `spec.replicas` 칸을 아예 비워서 보낸다. "0일 때만"을 `replicas == 0`으로 쓰면 정상적인 중지 요청이 거절된다. 빈 값도 0으로 보게 적었다. 이렇게 [woowangthon/WOOWANGTHON_TEAM_18#125](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/125)가 들어갔고 시험은 87개가 됐다.

같은 날 저녁 재개와 재시작([woowangthon/WOOWANGTHON_TEAM_18#134](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/134))을 붙였다. 학생 운영 제어가 재시작 · 중지/재개로 정해져 있고, AI 도구도 같은 둘을 부른다. 시험은 101개가 됐다.

- **재개**: scale 규칙을 "0만"에서 "0 · 1"로 넓혔다. 2 이상은 여전히 `422`다. 재개 전에 자리가 있는지는 서버가 본다.
- **재시작**: `kubectl rollout restart`는 Deployment 본체에 patch를 보내 Pod 템플릿에 `restartedAt` 주석을 붙인다. 그러려면 Deployment patch 권한이 필요한데, 이건 이미지 · 명령 · 볼륨까지 바꿀 수 있는 권한이다. 털린 서버 토큰이 학생 공간에서 다른 코드를 돌리거나 Secret을 마운트하는 Pod를 띄울 수 있게 된다.

그래서 재시작 규칙(`wanggane-platform-server-restart`)은 Pod 템플릿의 `restartedAt` 주석 말고는 아무것도 못 바꾸게 했다. Pod spec 전체, Pod 라벨과 다른 주석, replicas · selector · strategy · 롤아웃 설정을 옛 객체와 하나씩 비교한다. 비교 대상은 지금 버전 DeploymentSpec의 필드 전부라, 나중 버전이 새 필드를 더하면 그 필드는 안 본다. 이건 알려진 한계로 적었다.

![check.sh의 조치 묶음. 0으로 끄기, 다시 1로 켜기, 2는 거절, rollout restart 뒤 restartedAt이 붙음. 이미지 · replicas · 라벨 · 다른 주석 · 롤아웃 멈추기는 검사 규칙이, PUT · 삭제와 다른 공간의 scale · 재시작은 권한이 거절](/static/images/woowangthon-11-server-link/check-actions.svg)

## 7. 같은 리더에 다른 브랜치가 먼저 올라가 있었다

같은 날 밤, 다른 세션이 구축 11(모니터링)의 첫 조각으로 서버 계정에 CPU · 메모리 사용량 읽기 권한을 붙이고 있었다([13편](/kr/blog/woowangthon/woowangthon-13-metrics/) 이야기다). 그 브랜치는 `main`에서 따였고, 손대기 전에 기존 시험부터 돌렸더니 세 줄이 실패했다.

![main 기준 check.sh 실행. scale을 1로 올리기가 받아들여지고, Deployment 본체 patch가 권한이 아닌 다른 이유로 거절되고, 실제 토큰의 scale 1이 422 대신 200](/static/images/woowangthon-11-server-link/check-stacked.svg)

_두 번째 줄의 나머지는 PodSecurity 경고 문구라 잘랐다_

시험이 기대한 건 `main`의 상태, "0만 된다, 본체 patch는 권한 없음"이다. 그런데 리더에는 재개 · 재시작 권한이 이미 들어가 있었다. 그 브랜치는 아직 푸시 전이었고, 적용만 리더에 먼저 했던 것이다.

여기서 그 세션이 `main` 기준의 계정 파일을 그대로 적용했으면 어떻게 됐을까. `kubectl apply`는 역할의 규칙 목록을 파일 내용으로 덮는다. 재개 · 재시작 권한이 소리 없이 지워지고, 그 사실은 다음에 누가 시험을 돌릴 때까지 아무도 몰랐을 것이다. 그 세션은 적용 전에 브랜치를 재개 · 재시작 커밋 위로 옮겨 쌓은 뒤 적용했다. PR도 그 순서대로 #134 → #133으로 머지됐다.

레포는 브랜치가 여럿이어도 리더는 하나다. 리더에 적용하는 순간 그 브랜치가 클러스터의 "지금"이 된다. 기존 시험을 손대기 전에 한 번 돌려 보는 습관이 여기서 값을 했다.

마지막으로 11월 12일에 이 글을 쓰면서 같은 스크립트를 다시 돌렸다. 111개 전부 통과, 1분 6초 걸렸다. 실제 토큰 묶음은 이렇다.

![check.sh의 실제 토큰 묶음. 공간 만들기 dry run 201, 이미 있는 공간 409, proj- 아닌 이름 422, Secret 읽기 403, 끄기 · 켜기 · 재시작 dry run 200, scale 2는 422, 사용량 읽기 200, vllm은 403, 틀린 토큰 401, ALL PASS](/static/images/woowangthon-11-server-link/check-token.svg)

서버가 받는 응답은 이걸로 구분된다. 권한이 없으면 `403`, 검사 규칙에 걸리면 `422`(메시지에 규칙 이름과 이유), 이미 있으면 `409`, 토큰이 틀리면 `401`이다. 이 표는 서버 쪽 이슈에 그대로 넘겼다.

## 8. 사설망 접근 규칙

[4편에서 깐 Tailscale](/kr/blog/woowangthon/woowangthon-04-remote-access/#4-길-tailscale)은 그때까지 기본 정책이었다. 모든 기기가 모든 기기에 전부 닿는다. 학교 PC에서 내 데스크탑으로도 연결을 걸 수 있다는 뜻이다. EC2가 들어오면 그 기기도 마찬가지가 된다.

규칙 파일은 레포의 `Infra/tailscale/acl.hujson`에 두고, 레포가 공개라 주소 자리는 비워 뒀다. 주소는 관리 화면에 붙여 넣을 때만 채운다. 열어 둔 길은 이것뿐이다.

| 출발            | 도착                                  |
| --------------- | ------------------------------------- |
| 운영자 기기     | 세 노드 SSH, 리더 API                 |
| 서버 태그 (EC2) | 리더 API `:6443`만                    |
| 리더            | EC2의 GoCD 서버 `:8153`만 (11월 11일) |

정책 파일 안에 시험 블록을 넣어 뒀다. "운영자 기기에서 세 노드 SSH가 된다", "서버 태그에서 SSH와 내 데스크탑은 안 된다" 같은 것이고, 하나라도 어긋나면 관리 화면이 저장 자체를 거절한다. 내 SSH를 끊는 규칙은 저장될 수 없다. 노드를 고칠 때 [끊기기 전에 되돌리기부터](/kr/blog/woowangthon/woowangthon-05-node-prep/#3-끊기기-전에-되돌리기부터) 걸어 둔 것과 같은 생각이다.

11월 10일에 넣었고 한 번에 저장됐다. 넣은 뒤 데스크탑에서 세 노드 SSH와 sudo가 되고, 워커 1에서 리더의 사설망 주소 22번으로는 이제 안 닿고, 노드 대역으로는 그대로 닿는 걸 확인했다. 두 시험 스크립트도 다시 통과했다. 그 전에는 학교 PC가 뚫리면 내 개인 기기까지 타고 올 길이 있었다. 이제 없다.

이 규칙이 노드끼리 사설망으로 닿는 길을 닫아서, [9편의 대조 공간 시험](/kr/blog/woowangthon/woowangthon-09-student-space/#5-막혔다는-걸-어떻게-아나) 한 줄을 뺐다. 차단 규칙이 없는 대조 공간에서도 그 길은 이제 안 닿는다.

리더에서 EC2의 GoCD로 가는 줄은 배포 실행기가 일감을 받아 오는 길이다([12편](/kr/blog/woowangthon/woowangthon-12-deploy-executor/)). 태그 기준이라 EC2가 없어도 파일에 미리 넣어 둘 수 있었다. 관리 화면에는 아직 안 넣었다.

## 9. EC2가 없어서 못 본 것

클러스터 쪽은 끝났지만 "서버가 붙는다"는 아직 증명되지 않았다. 내 데스크탑에서 실제 토큰으로 부른 것은 권한 시험이다. "EC2에서 출발한 요청이 리더에 도착하는가"는 다른 질문이고, 거기엔 리더에서 볼 수 없는 것들이 끼어 있다.

- EC2가 서버 태그를 달고 사설망에 들어오는가. 가입용 일회용 키는 쓸 기기가 생기는 날 만들어 바로 쓴다. 미리 만들어 두면 그동안 쓸 데 없는 비밀이 어딘가에 굴러다닌다.
- 접근 규칙의 서버 태그 줄이 실제로 리더 `:6443`만 여는가. 정책 안 시험은 통과했지만 태그를 단 기기로 재 본 적은 없다.
- EC2 쪽 방화벽(보안 그룹)이 Tailscale의 나가는 연결을 막지 않는가.
- 서버가 리더 인증서를 클러스터 CA로 검증해 내는가. 데스크탑의 curl로는 됐다.
- 토큰을 EC2의 비밀 설정에 넣는 날, 화면에 안 찍고 리더에서 바로 옮기는가.
- 리더에서 EC2 `:8153`으로 나가는 길.
- 서버 코드의 실제 끄기 · 켜기 · 재시작 호출. 클러스터 권한만 들어갔고 서버 쪽 호출은 서버 담당이 붙인다.

알려진 구멍도 하나 남았다. 서버 계정은 공간만 만들고 상한 · 차단 규칙을 안 만들 수 있다. 검사 규칙은 만들어지는 것의 값만 본다. 서버 계정은 Pod를 만들 수 없어서 그 공간에 앱이 뜨려면 배포 실행기를 거쳐야 하니, 실행기가 배포 전에 셋이 있는지 확인하기로 했다.

## 10. 정리

| 겪은 일                                            | 배운 것                                                                                              |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 네임스페이스 이름으로 권한을 줄 수 없었다          | RBAC로 못 거르는 조건은 검사 규칙으로 겹친다. 그 규칙이 유일한 울타리면 적용과 삭제 순서를 못 박는다 |
| 양식 값을 규칙에 두 번 적어야 했다                 | 기준 객체를 두고 비교한다. 두 벌을 맞추는 일은 언젠가 한쪽이 빠진다                                  |
| Secret "쓰기만"에 patch를 넣었다                   | 응답이 무엇을 돌려주는지까지 본다. 빈 patch 하나로 읽힌다                                            |
| 읽기를 클러스터 전체로 줄 뻔했다                   | 검사 규칙은 읽기를 못 본다. 읽기는 공간마다 권한 연결로 좁힌다                                       |
| 기준 객체가 없자 운영자까지 막혔다                 | 기준은 계정 조건보다 먼저 찾는다. 기준을 두는 자리는 규칙에서 빼 둔다                                |
| 거절 시험이 규칙이 꺼진 날엔 실제로 지울 수 있었다 | 피해를 낼 수 있는 거절 시험은 dry run으로 보낸다. 시험이 막으려는 사고를 시험이 내면 안 된다         |
| `patch`만 주면 될 줄 알았다                        | 쓰는 도구가 그 전에 무엇을 읽는지 시험이 먼저 알려 준다. 시험을 적용보다 먼저 돌린다                 |
| 재시작에 Deployment patch가 필요했다               | 넓은 권한은 바꿀 수 있는 필드를 하나로 묶는 규칙과 같이 준다                                         |
| 손대기 전 시험이 세 줄 실패했다                    | 리더는 하나다. 적용하기 전에 리더가 어느 브랜치 상태인지부터 본다                                    |

TaeTaeJin은 중지 권한 PR을 보고 "적용해서 다음 PR로 올리겠다"고 승인했다. 에이전트는 그 제안을 줄이다가 맞는 줄인 `get`까지 지웠고, 그걸 바로잡은 건 사람이 아니라 먼저 돌린 시험이었다. 동료가 되려면 남의 말을 고칠 때도 자기 말을 고칠 때만큼 의심해야 한다.

다음은 [12편](/kr/blog/woowangthon/woowangthon-12-deploy-executor/), 리더에서 실제로 배포하는 실행기다. 사용량 읽기를 포함한 모니터링은 [13편](/kr/blog/woowangthon/woowangthon-13-metrics/)에 있다. EC2가 사설망에 들어오는 날, 9절의 목록을 하나씩 지운다.
