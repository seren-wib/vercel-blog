### 문서끼리 어긋난 두 곳

여러 사람이 동시에 쓰면 같은 사실이 문서마다 다르게 적힌다. #36 본문에 내가 남긴 "확인이 필요한 사항" 두 개가 그 예다.

- **취소 반려 뒤 상태.** 요구사항은 "반려하면 요청 전 상태(`PAID` 또는 `PREPARING`)로 돌아간다"인데, 스키마에는 요청 전 상태를 저장할 칼럼이 없었다.
- **재고 차감 시점.** 요구사항과 `create_order` 알고리즘은 주문 생성 때 차감, 테이블 명세서는 결제(`PAID`) 때 차감이었다.

둘 다 10월 11일 회의에서 정하고 #41로 반영했다. 첫째는 요청 전 상태를 담는 `status_before_cancel` 칼럼을 테이블 명세에 더하는 쪽으로, 둘째는 주문 생성 때 조건부 UPDATE 하나로 차감하는 쪽으로 정했다. 최종 구현에서 첫째는 그 칼럼에 CHECK 제약 `ck_orders_cancel_request_previous`까지 붙었고(#104), 둘째는 주문 생성 트랜잭션 안의 `decrease_stock`으로 남았다(#100). [4편](/kr/blog/coffee-shop/coffee-shop-04-backend-features/)에 자세히 있다.

## 3. 11월 17일: 단계 문서로 다시 쓰기

도서관으로 치면 HW1·HW2 문서는 각자 자기 책상에 쌓아 둔 책이었다. 다시 쓰기는 그 책을 한 서가에 분류 번호를 붙여 꽂는 일이다. 번호가 있어야 다른 문서와 코드가 "그 책 몇 쪽"이라고 가리킬 수 있다.

![문서 재구성 다이어그램. 왼쪽 옛 구조: docs/backend, docs/frontend, docs/architecture.md에 HW1·HW2 문서가 흩어져 있다. 오른쪽 새 구조: docs/specs 아래 spmp, srs, sdd, stp, sip, smp 여섯 폴더. SRS가 DR, FR, NFR, UC ID를 정하고 SDD, STP, 테스트 이름, PR 본문이 그 ID를 인용한다](/static/images/coffee-shop-01-requirements-design/docs-layout.svg)

서가는 `docs/specs/`, 분류 번호는 요구사항 ID(`DR-`, `FR-`, `NFR-`, `UC-`)다. 이 비유는 여기까지만 쓴다.

#60과 #62는 확인 기준을 본문에 적었다. SRS는 범위 밖 ID 참조 0건, SDD는 FR·NFR·DR·UC가 전부 한 번 이상 인용되고 빠진 ID 0건이었다.

다시 쓴 이유는 셋이다.

- **ID가 없으면 추적이 안 된다.** "주문 취소 요구사항"이 어느 테스트로 확인되는지 말하려면 요구사항에 번호가 있어야 한다.
- **실행 환경이 바뀌었다.** HW1은 "로컬 PC에서만 실행, 외부 서버 배포 안 함"이었다. 시연을 운영 서버로 하기로 하면서 배포·보안 요구사항이 새로 생겼다.
- **문서를 단계별로 나눠야 구현 세션이 필요한 것만 읽는다.** 구현은 Claude Code 세션 여러 개가 맡았다. 세션마다 `docs/specs/README.md`부터 읽고 자기 절만 열게 했다.

## 4. ID가 코드까지 이어지는 방식

SRS가 ID를 정하면 나머지가 그 ID를 인용한다. 테스트 함수 이름이 제일 확실한 연결이다.

| 요구사항 | 테스트 함수                                            | 확인하는 것                                                          |
| -------- | ------------------------------------------------------ | -------------------------------------------------------------------- |
| NFR-8    | `test_nfr8_token_lifetimes`                            | 액세스 토큰 1,800초, 리프레시 토큰 604,800초                         |
| NFR-9    | `test_nfr9_every_private_route_needs_token`            | URL 설정을 전부 돌며 토큰 없는 요청이 401인지                        |
| NFR-15   | `test_nfr15_last_stock_concurrent_orders`              | 재고 1개에 동시 주문 10건이면 성공 1, 409 9                          |
| DR-19    | `test_dr19_disallowed_transitions_raise_invalid_state` | 허용 표 밖의 (동작, 상태) 쌍이 전부 `INVALID_STATE`(API에선 409)인지 |

NFR-9 테스트는 URL 설정을 직접 훑어서, 나중에 경로가 추가돼도 테스트를 고치지 않고 덮는다(#83). 이렇게 짜 둔 덕에 주소 API(#87), 관리자 API(#95, #104)가 들어올 때마다 새 경로가 자동으로 검사됐다.

### 교수님 피드백: 부품 ID와 클래스 명세

SDD 피드백은 두 가지였다. 화면의 UI 부품마다 번호를 달 것, 클래스·메서드 명세를 따로 둘 것.

- 6절 화면 16개에 `6.x.0 화면 전체` 소절과 부품 소절 72개(`6.1.1 SCR-01-01 검색창`)를 달았다. 와이어프레임 14장에는 같은 ID 배지 62개를 draw.io 원본에 넣고 다시 내보냈다.
- 새 12절에 백엔드 공개 함수 55개, 내부 함수 29개, 클래스 92개를 적었다. 스크립트로 `backend/`의 `def`·`class`와 대조해 이름 누락 0, 시그니처 불일치 0을 확인했다(#129).
- 1~11절 번호는 그대로 두었다. 다른 문서가 절 번호로 가리키는 곳이 많아서다.

## 6. 다음에 다르게 할 것

- **ID는 첫 문서부터.** HW1 때 ID를 붙였으면 11월 17일의 다시 쓰기가 옮기기 수준으로 끝났다.
- **실행 환경 전제는 일찍 의심한다.** "로컬에서만"이라는 한 줄이 CI/CD 요구사항을 마감 사흘 전까지 비워 뒀다.
- **문서 사이 사실은 한 곳에만.** 재고 차감 시점처럼 두 문서에 같은 사실이 있으면 언젠가 갈라진다. 다시 쓴 뒤에는 한 곳에 적고 나머지는 ID로 가리켰다.
