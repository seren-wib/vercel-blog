## 0. Introduction

> Part 13 of the series. Build stage 7 (monitoring), build 11, from the night of November 11 to the early hours of the 12th. What we are building and why is in [Woowangthon 0](/en/blog/hackathon/woowangthon/woowangthon-00-overview/). The previous post is [part 12](/en/blog/hackathon/woowangthon/woowangthon-12-deploy-executor/).

The student [CPU](glossary:cpu) and memory view, the operator page's usage numbers and the cost estimate all need [metrics](glossary:metrics). So I decided to add [metrics](glossary:metrics) collection to the leader.

In restaurant terms, one person sticks a thermometer in every kitchen and writes the readings in a ledger, and another turns that ledger into a status board in the dining room. The owner cannot enter the ledger room and only gets numbers through a serving hatch. The recorder is [Prometheus](glossary:prometheus), the status board is [Grafana](glossary:grafana), the owner is the platform server, the hatch is the [service proxy](glossary:service), and the guest list that allows the hatch is [RBAC](glossary:rbac).

I installed [Prometheus](glossary:prometheus) and [Grafana](glossary:grafana) on the leader and let the platform server query [metrics](glossary:metrics) over the private network. At first I postponed the install behind the demo path, and reversed that a little over an hour later. The rights were right, but an [admission policy](glossary:validatingadmissionpolicy) refused the server's query with [422](glossary:http-status-code), and the [review](glossary:code-review) bot caught that the [metrics](glossary:metrics) [namespace](glossary:namespace) was wide open inside the cluster. So I closed it. Less than 40 minutes later I opened [Grafana](glossary:grafana) again on a public address, to put it in the operator page. The self [review](glossary:code-review) I ran right after caught one path that opened without a login, and a way for student apps to put [Grafana](glossary:grafana) inside their own pages.

## 1. Postponed, then installed the same day

Three things use the [metrics](glossary:metrics): the screen where a student sees their app's [CPU](glossary:cpu) and memory, usage on the operator page, and cost estimates. Spotting trouble right after a deploy (memory over the limit, restart loops) is done by the platform server watching [Pods](glossary:pod) and events directly, so it does not go through [Prometheus](glossary:prometheus).

All three are P1, though. The team has a rule, "no P1 before P0 runs end to end", and the deploy P0 path had not run end to end even once, because the [EC2](glossary:amazon-ec2) instance for the platform server did not exist yet. The agent recommended postponing the [Prometheus](glossary:prometheus) and [Grafana](glossary:grafana) install behind the demo path, and doing one small thing first. I took that as it was.

The small thing was a read right on `metrics.k8s.io`. [k3s](glossary:k3s) ships [metrics-server](glossary:metrics-server) by default (the thing behind `kubectl top`), so current [CPU](glossary:cpu) and memory of nodes and [Pods](glossary:pod) can be read without [Prometheus](glossary:prometheus). The operator API already had a `usage` field, and the server was filling it with `not_collected`. The server owner (TaeTaeJin) had written in an issue that he needed "read rights on node and [Pod](glossary:pod) usage". I added a node usage read to the [platform server account](/en/blog/hackathon/woowangthon/woowangthon-11-server-link/), and a [Pod](glossary:pod) usage read to the student [namespace](glossary:namespace) read role.

The checks all passed (111 for the server account). The self [review](glossary:code-review) that came next doubted that pass. The new allow checks only looked at whether the request was accepted. If [metrics-server](glossary:metrics-server) died and returned an empty list, it was still PASS. Same shape as [the check in part 9 that passed without measuring anything](/en/blog/hackathon/woowangthon/woowangthon-09-student-space/#7-it-could-pass-without-testing). Now node usage passes only when exactly three entries carry values. That is team repo [#133](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/133).

#133 contained the sentence "[Prometheus](glossary:prometheus) and [Grafana](glossary:grafana) are installed after P0." A little over 20 minutes after merging it, I reversed that order. [EC2](glossary:amazon-ec2) has to wait on the server side, and this is work the cluster side can finish in the meantime. It does not push the demo path back either. I did not delete "after P0" from the design doc; I left the history as "postponed, then changed the same day".

## 2. The way k3s installs Traefik

I used the [kube-prometheus-stack](glossary:kube-prometheus-stack) [chart](glossary:helm) (93.1.1, [Prometheus Operator](glossary:prometheus-operator) v0.95.1, [Grafana](glossary:grafana) 13.3.0). [Prometheus](glossary:prometheus), [Grafana](glossary:grafana), [node-exporter](glossary:node-exporter) (reads the nodes), [kube-state-metrics](glossary:kube-state-metrics) (reads the state of [Kubernetes](glossary:kubernetes) objects) and the default dashboards come as one bundle.

It goes in through the [k3s](glossary:k3s) [Helm](glossary:helm) controller. Apply one HelmChart object and [k3s](glossary:k3s) starts an install job that installs the [chart](glossary:helm). That is how [k3s](glossary:k3s) puts in [Traefik](/en/blog/hackathon/woowangthon/woowangthon-10-public-entry/#2-one-traefik-on-each-worker). No [helm](glossary:helm) and no release state is left on my machine.

The first install failed. The job ran for over three minutes and nothing appeared in the [metrics](glossary:metrics) [namespace](glossary:namespace). The install job's [Pod](glossary:pod) had died once on worker 1 and was running again, and its log had a line where fetching the [chart](glossary:helm) file from a GitHub release asset address failed. The [chart](glossary:helm) repository's index lives on GitHub Pages, but the files themselves come from GitHub's release [CDN](glossary:cdn). That did not come down over the school network. I switched to fetching the same [chart](glossary:helm) from its [OCI](glossary:oci) address on [GHCR](glossary:ghcr), and the job finished in about 30 seconds. [GHCR](glossary:ghcr) is where the [image cache](/en/blog/hackathon/woowangthon/woowangthon-08-image-cache/#1-why-a-cache) pulls images from, so the path from the school network was already proven.

A lot is switched off on [k3s](glossary:k3s).

| Switched off                                                                                   | Why                                                                                                                                        |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| [etcd](glossary:etcd) · scheduler · controller-manager · [kube-proxy](glossary:kube-proxy)     | [k3s](glossary:k3s) runs these inside its own single process. There is no separate target to scrape, so left on they always show as "down" |
| [Alertmanager](glossary:alertmanager)                                                          | The cluster sends no alerts (section 6)                                                                                                    |

| [Prometheus](glossary:prometheus) admin API                                                    | An API that deletes [metrics](glossary:metrics). Off, as the [chart](glossary:helm) default                                                |

Storage is [k3s](glossary:k3s)'s [local-path](glossary:persistentvolume) (a folder on the node): 30Gi requested for [Prometheus](glossary:prometheus), 2Gi for [Grafana](glossary:grafana). Retention is two weeks. But just like [the cache volume's 50Gi in part 8 was not a limit](/en/blog/hackathon/woowangthon/woowangthon-08-image-cache/#6-what-the-reviewer-ai-caught-refused-vs-no-answer), [local-path](glossary:persistentvolume) does not enforce [volume](glossary:persistentvolume) size. 30Gi is only a request. The leader's disk also holds [etcd](glossary:etcd) and the model [volume](glossary:persistentvolume). So [Prometheus](glossary:prometheus) itself also gets a 20 GB size cap. Whichever fills first, two weeks or 20 GB, the oldest data goes.

[node-exporter](glossary:node-exporter) has to look into the host, so the [metrics](glossary:metrics) [namespace](glossary:namespace) runs at [privileged](glossary:pod-security-standards), not at [the baseline of student namespaces](/en/blog/hackathon/woowangthon/woowangthon-09-student-space/#1-what-goes-into-one-student-space). Everything else runs on the leader. The scrape targets are [node-exporter](glossary:node-exporter) and the [kubelet](glossary:kubelet) ([Pod](glossary:pod) usage) on the three nodes, [kube-state-metrics](glossary:kube-state-metrics), the API server, [CoreDNS](glossary:coredns), [Traefik](glossary:traefik) on the two workers, and [cloudflared](glossary:cloudflare-tunnel). The [cloudflared](glossary:cloudflare-tunnel) [namespace](glossary:namespace) has [the NetworkPolicy added in part 10](/en/blog/hackathon/woowangthon/woowangthon-10-public-entry/#the-leaders-firewall-doesnt-stop-cloudflared), so I added one rule letting only [Prometheus](glossary:prometheus) in on the [metrics](glossary:metrics) port (2000).

Right after the install [Grafana](glossary:grafana) was using about 450Mi of memory. The limit I had first set was 512Mi, too tight, so I raised it to 1Gi.

## 3. The rights say yes, and still 422

The platform server is on AWS and reaches the leader's API over the private network. Instead of opening one more port for [Prometheus](glossary:prometheus), it goes through the leader API's [service proxy](glossary:service), a feature where the API server forwards the request to a [Service](glossary:service) on the caller's behalf.

```text
GET /api/v1/namespaces/monitoring/services/monitoring-prometheus:9090/proxy/api/v1/query?query=...
```

The rights ([RBAC](glossary:rbac)) given to the server account are `get` on `services/proxy` for that one [Service](glossary:service) name, nothing else. Through the same path `POST` is [403](glossary:http-status-code), and so is [Grafana](glossary:grafana). Reading [Pods](glossary:pod) and [Secrets](glossary:secret) in the [metrics](glossary:metrics) [namespace](glossary:namespace) is refused too.

A query with the real server token came back [422](glossary:http-status-code). Not [403](glossary:http-status-code) (no right), [422](glossary:http-status-code). It passed the rights check and was refused by the [admission policy](glossary:validatingadmissionpolicy) ([ValidatingAdmissionPolicy](glossary:validatingadmissionpolicy)) after it. The [platform server account](/en/blog/hackathon/woowangthon/woowangthon-11-server-link/) carries a rule: "the server writes only inside `proj-` [namespaces](glossary:namespace)". That rule looks at create, update, delete, and [CONNECT](glossary:connect-method). Calls like exec, running a command inside a [Pod](glossary:pod), are [CONNECT](glossary:connect-method).

When the [Kubernetes](glossary:kubernetes) API server hands a [service proxy](glossary:service) call to admission, it counts it as [CONNECT](glossary:connect-method), even when the HTTP method is `GET`. So a read-only [metrics](glossary:metrics) query was caught as "writing outside `proj-`". The rights allowed it; the rule refused it.

I added one exception to the rule, naming exactly that call.

```yaml
- name: isPrometheusQuery
  expression: >-
    request.operation == 'CONNECT' && request.resource.group == '' && request.resource.resource == 'services'
    && request.subResource == 'proxy' && request.namespace == 'monitoring' && request.name == 'monitoring-prometheus:9090'
```

When the agent tried to apply this on the leader, the automatic approval check stopped it as "weakening a security rule". Not a wrong call. It is the first path where the server token reaches outside `proj-`. The cost is clear too: through it, the metric numbers of every [namespace](glossary:namespace) can be read (the local model's, the system ones). Logs, [Secrets](glossary:secret) and objects are still `proj-` only. I could have put a proxy in front that filters queries by [namespace](glossary:namespace), but that is one more part to stand up and test. If what leaks is only numbers, I would write that cost down and accept it. I checked that and told it to apply.

After the apply I ran all four checks: [metrics](glossary:metrics) 23, server account 111, deploy executor 63, student [namespaces](glossary:namespace) 31, all PASS. That night I merged a few [PRs](glossary:pull-request) that stayed inside my own part without a teammate's approval, but not this one ([#138](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/138)). A change that adds an exception to an [admission policy](glossary:validatingadmissionpolicy) needs the server owner to look at it at least once.

## 4. The check script was wrong first

Apart from the [422](glossary:http-status-code), almost every check failed at first. Most of it was the check script's fault.

![First run: every collection check got nothing, the service proxy query hit a bash syntax error, the real-token query got 422. Second run: only Traefik and cloudflared got nothing, and the service proxy query was refused by ValidatingAdmissionPolicy wanggane-platform-server](/static/images/woowangthon-13-metrics/first-check.svg)

_Two runs while fixing the check script. `...` stands for passing lines left out_

**On the first run the query broke.** The check script runs on my machine (Windows), and the query goes through the leader's shell over [SSH](glossary:ssh) to the API. [PromQL](glossary:promql) is full of parentheses, quotes and braces. They broke on the way through the remote shell and Windows argument passing; the bash syntax error is that. Now the query goes in on [standard input](glossary:stdin), not as a command-line argument, and everything except letters and digits is [percent-encoded](glossary:percent-encoding).

**On the second run the labels were wrong.** Only [Traefik](glossary:traefik) and [cloudflared](glossary:cloudflare-tunnel) said "nothing". Those two are not from the [chart](glossary:helm); I attached them myself with [PodMonitors](glossary:podmonitor), and the check looked for `job="traefik"`. The job name a [PodMonitor](glossary:podmonitor) sets is `<namespace>/<name>`, so `monitoring/traefik`. I asked [Prometheus](glossary:prometheus) for its list of job names and matched it.

What was left was the [422](glossary:http-status-code) from section 3.

## 5. The open metrics namespace the review bot caught

As in [part 8](/en/blog/hackathon/woowangthon/woowangthon-08-image-cache/#6-what-the-reviewer-ai-caught-refused-vs-no-answer), the [review](glossary:code-review) bot ([CodeRabbit](glossary:coderabbit)) does not come to this repo on its own. I called it on #138. Three comments came.

The heaviest was "the [metrics](glossary:metrics) [namespace](glossary:namespace) has no inbound [NetworkPolicy](glossary:networkpolicy)". I checked it myself. From inside a [Pod](glossary:pod) of the local model's [namespace](glossary:namespace), I called [Prometheus](glossary:prometheus) and [Grafana](glossary:grafana), and both answered 200. The [Prometheus](glossary:prometheus) API has no login. Narrowing the server account down to a single `get` meant nothing in front of a path that does not go through the [service proxy](glossary:service).

A few hours earlier, under "what we don't do" in the design doc, the agent had written this: no [NetworkPolicy](glossary:networkpolicy) for the [metrics](glossary:metrics) [namespace](glossary:namespace), because student [namespaces](glossary:namespace) [cannot reach in-cluster ranges thanks to their own block rules](/en/blog/hackathon/woowangthon/woowangthon-09-student-space/#5-how-do-you-know-its-blocked). That reasoning only thought about student [Pods](glossary:pod). Besides student [namespaces](glossary:namespace), the cluster has [namespaces](glossary:namespace) for ops tools like the local model, the [tunnel](glossary:cloudflare-tunnel) and the image cache. The reasoning left their [Pods](glossary:pod) out entirely. I read that sentence and let it pass, too.

The fix is one [NetworkPolicy](glossary:networkpolicy): the [metrics](glossary:metrics) [namespace](glossary:namespace) only lets in traffic from [Pods](glossary:pod) of the same [namespace](glossary:namespace). [Prometheus](glossary:prometheus) scraping its own parts and [Grafana](glossary:grafana) asking [Prometheus](glossary:prometheus) stay inside the [namespace](glossary:namespace), so they still work. So do the server's [service proxy](glossary:service) and the operator's port forward: both are traffic from the leader itself to a [Pod](glossary:pod), and the policy engine always lets a node reach its own [Pods](glossary:pod). [node-exporter](glossary:node-exporter) uses the host network, so it is not covered by this rule but by [the host firewall](/en/blog/hackathon/woowangthon/woowangthon-05-node-prep/#inbound).

![Before the policy, Prometheus and Grafana answer 200 from another namespace. After applying the policy the check still says FAIL (command terminated with exit code 1). A direct call shows Connection refused. After fixing the check, both PASS as out of reach](/static/images/woowangthon-13-metrics/reach.svg)

_Before the policy, after it, and after fixing the check_

The check still failed after the policy went in. The check again. I had written "blocked" as a connection timeout, but what actually came back was an immediate Connection refused. [k3s](glossary:k3s)'s policy engine ([kube-router](glossary:kube-router)) does not drop blocked connections; it refuses them. [Exactly what part 9 had already shown](/en/blog/hackathon/woowangthon/woowangthon-09-student-space/#5-how-do-you-know-its-blocked). The new script missed what I had learned then. At first it only looked at the last line of the output, so it did not even show that message. It took two fixes.

The other two comments: one was that the checks passed even with [Grafana](glossary:grafana) or the [Operator](glossary:prometheus-operator) missing entirely. I added checks that the four components and the three [node-exporters](glossary:node-exporter) are Ready. The other was "P1 work before P0"; I answered that I had set that order and written down why. The [metrics](glossary:metrics) checks became 30.

Had I merged this [PR](glossary:pull-request) that night without approval, the open [metrics](glossary:metrics) [namespace](glossary:namespace) would have gone into main as it was.

## 6. Putting Grafana in the operator page

That night the direction changed in the team's Discord. TaeTaeJin takes the operator dashboard, in the platform's operator page (FE). The alerts I meant to send to Discord from [Grafana](glossary:grafana) rules moved to the platform side too: alert together when a metric anomaly calls the AI, done if time allows. So the cluster sends no alerts. A cut [tunnel](glossary:cloudflare-tunnel) cannot be seen from inside the leader, so it is watched through Cloudflare's own [tunnel](glossary:cloudflare-tunnel) notifications, not through [cloudflared](glossary:cloudflare-tunnel)'s connection count metric. In [part 10's internet-cut test](/en/blog/hackathon/woowangthon/woowangthon-10-public-entry/#7-cutting-the-leaders-internet-502-then-530) that value never dropped to 0.

There were two ways to show [metrics](glossary:metrics) on the operator page. The server takes values from [Prometheus](glossary:prometheus) and the FE draws its own charts (the query path already exists), or [Grafana](glossary:grafana)'s screens go in as an [iframe](glossary:iframe). I chose [Grafana](glossary:grafana). If we only take numbers and draw them ourselves, there is no reason to install [Grafana](glossary:grafana). You install it for its screens.

The cost is that [Grafana](glossary:grafana) has to come outside. One path into the [namespace](glossary:namespace) I had just closed.

- **Address**: `grafana.stairnoworks.com`. The path is the same as student addresses ([tunnel](glossary:cloudflare-tunnel) → [Traefik](glossary:traefik) → [Ingress](glossary:ingress)). [The wildcard record](/en/blog/hackathon/woowangthon/woowangthon-10-public-entry/#1-the-way-in-for-visitors) already points at the [tunnel](glossary:cloudflare-tunnel), so [DNS](glossary:dns) stays as it is and only one [Ingress](glossary:ingress) is added.
- **The way in**: [NetworkPolicy](glossary:networkpolicy) `grafana-from-traefik`. [Traefik](glossary:traefik)'s [Pods](glossary:pod) reach [Grafana](glossary:grafana)'s port 3000 and nothing else. [Prometheus](glossary:prometheus) has no public address (`prometheus.stairnoworks.com` is 404).
- **[Grafana](glossary:grafana) settings**: `root_url` set to the public address, and `allow_embedding` on so it stops sending the header that blocks [iframes](glossary:iframe) (`X-Frame-Options`).

How to log in was left. At first I said to go with [JWT](glossary:jwt) login. [Grafana](glossary:grafana) takes an address for the [public keys](glossary:jwks) it verifies [JWTs](glossary:jwt) with, and we can give it the same one the platform server uses to verify its login tokens ([Supabase](glossary:supabase)). No new server API needed. Put the operator's login token on the [iframe](glossary:iframe) address as `?auth_token=` and [Grafana](glossary:grafana) opens straight away.

The catch was that "on the address". An [iframe](glossary:iframe) cannot attach request headers, so the token has to ride in the URL. That token is not [Grafana](glossary:grafana)-only; it is the operator's token that also works on the platform API, valid until it expires (an hour by default). URLs leave more traces than headers: access logs, developer tools, screen sharing. And without [JWT](glossary:jwt), the operator only has to log in to [Grafana](glossary:grafana) inside the [iframe](glossary:iframe) once; the browser remembers the session. So [JWT](glossary:jwt) was deferred.

Six public-address checks took the [metrics](glossary:metrics) checks to 36. A dashboard address without a login goes to the login page, and the API answers [401](glossary:http-status-code). I wrote in the design doc that "nothing opens without a login".

## 7. The self review right after opening it

Right on the commit that opened the public address, I ran the agent's [code review](glossary:code-review). It found nine things. Three were heavy.

**[Grafana](glossary:grafana)'s own `/metrics` was open without a login.** Hitting it directly gave 200 and 868 KB. Not the cluster's [metrics](glossary:metrics) but [Grafana](glossary:grafana)'s own, yet it holds the exact build and commit, plugins and their versions, user and dashboard counts, and login counters. The doc's "nothing opens" was wrong. I switched off [Grafana](glossary:grafana)'s [metrics](glossary:metrics) endpoint, and the [Prometheus](glossary:prometheus) scrape of it with it.

**Student apps could put [Grafana](glossary:grafana) inside their own pages.** `allow_embedding` only removes `X-Frame-Options`; it does not say who may embed. With no header filling that gap, any site could put [Grafana](glossary:grafana) in an [iframe](glossary:iframe). The problem is the student addresses. `<slug>.stairnoworks.com` and `grafana.stairnoworks.com` are different [origins](glossary:origin) but, to the browser, the same [site](glossary:site), since they sit under the same registrable domain. So the operator's [Grafana](glossary:grafana) login [cookie](glossary:cookie) ([SameSite](glossary:samesite-cookie)=Lax) is sent inside an [iframe](glossary:iframe) on a student app as well. If a student app lays [Grafana](glossary:grafana) underneath as a [transparent iframe](glossary:clickjacking), an operator visiting that app could have their clicks land on a logged-in [Grafana](glossary:grafana).

One [Traefik](glossary:traefik) [Middleware](glossary:middleware) stops it: [Grafana](glossary:grafana)'s responses get `Content-Security-Policy: frame-ancestors 'self' https://app.stairnoworks.com`. Now only [Grafana](glossary:grafana) itself and the platform page may embed [Grafana](glossary:grafana).

**There was only an admin account.** Opening the operator page with it means a viewing screen that can delete dashboards, change data sources and add accounts. I added a script (`make-viewer.sh`) that creates a view-only account, `viewer`. Its password is made on the leader and kept only in a [Secret](glossary:secret). The operator page opens with this account. I got one wrong while writing the checks, too: I expected [403](glossary:http-status-code) for the view-only account listing data sources, and got 200. [Grafana](glossary:grafana) allows that for viewers by design. I changed the check to reading settings ([403](glossary:http-status-code)).

The rest was small. `Secure` on the [cookie](glossary:cookie), an [HSTS](glossary:hsts) header. And the checks, once more: the [iframe](glossary:iframe) header check passed whenever the response had no `X-Frame-Options`, so with the [tunnel](glossary:cloudflare-tunnel) down and curl getting nothing, "missing" meant PASS. Part 9's false PASS showed up here too. I also added a check on the [NetworkPolicy](glossary:networkpolicy)'s shape, that only [Traefik](glossary:traefik) → [Grafana](glossary:grafana) 3000 is open. Two of the nine I did not fix; they are written down as known limits in the design doc.

_The public address checked again from my desktop while writing this post_

## 8. What is still unverified
