> 시리즈 15편. 구축 6단계(바깥이랑 잇기) 중 리더의 배포 실행기가 EC2의 GoCD 서버에 등록된 11월 12일 오후 이야기다. 같은 날 그보다 먼저 EC2가 사설망에 들어온 이야기는 [14편](/kr/blog/woowangthon/woowangthon-14-ec2-joins/)에, 실행기 계정과 Pod 매니페스트는 [12편](/kr/blog/woowangthon/woowangthon-12-deploy-executor/)에, 전체 그림은 [Woowangthon 0](/kr/blog/woowangthon/woowangthon-00-overview/)에 있다.

## 한 줄 요약

GoCD 서버가 EC2에 떴고, 리더의 실행기 Pod를 올려 등록까지 마쳤다. 걸린 건 둘이다. 하나는 매니페스트 머리말의 키 목록이다. 서버보다 먼저 쓴 머리말에는 키가 둘이었는데, 그 사이 들어온 배포 작업 스크립트가 하나를 더 쓰고 있었다. 다른 하나는 첫 부팅이다. Pod는 금방 Running이 됐는데 등록은 6분 반 뒤에야 됐다. 실행기 본체와 플러그인을 서버에서 받아 오는데, 사설망 길이 도쿄 중계 서버를 돌고 있었다. 고장이 아니라 느린 것이었다. 실제 배포 파이프라인은 아직 한 번도 안 돌았다.

## 1. 서버가 생겼다

[12편](/kr/blog/woowangthon/woowangthon-12-deploy-executor/#10-아직-아무도-못-본-것)은 "GoCD 서버가 들어갈 EC2가 아직 없다"로 끝났다. 11월 12일 오후 3시 48분쯤, EC2를 맡은 TaeTaeJin이 그 EC2에 GoCD 서버 26.1.0과 플랫폼 서버를 띄웠다. 버전과 포트(8153)는 12편에서 답이 안 와서 내가 정한 값인데, 서버가 그대로 맞춰 올라왔다. 그보다 먼저 [14편](/kr/blog/woowangthon/woowangthon-14-ec2-joins/#3-연결-거부가-반가운-이유)에서 리더 → EC2의 8153이 연결 거부였던 건, 길은 열렸는데 받을 서버가 아직 없어서였다. 이제 그 자리에 서버가 있다.

GoCD 포트는 EC2의 사설망(Tailscale) 주소에만 열었다. 설치 스크립트가 처음엔 `127.0.0.1`에 묶었다가 설정이 끝나면 사설망 주소로 옮긴다. 확인은 양쪽에서 했다.

| 어디서                  | 무엇을                           | 결과                 |
| ----------------------- | -------------------------------- | -------------------- |
| 리더 호스트             | 사설망 주소의 `/go/api/version`  | 26.1.0               |
| 리더 호스트             | 사설망 주소의 health             | OK                   |
| 인터넷(운영자 데스크탑) | EC2 공인 주소의 8153, 3000(서버) | 둘 다 연결 시간 초과 |

인터넷에서는 GoCD도 플랫폼 서버도 안 보인다. 플랫폼 서버는 Cloudflare 터널로만 나간다. [10편의 방문자 주소](/kr/blog/woowangthon/woowangthon-10-public-entry/)와 같은 방식이다.

## 2. 키는 둘이 아니라 셋이었다

서버를 띄운 TaeTaeJin이 요청을 보냈다. 리더에 Secret `gocd-agent`를 만들고 실행기를 적용해 달라는 것이었다. 그리고 키가 셋이라고 적었다.

매니페스트 머리말에는 둘이었다. GoCD 서버 주소(`GO_SERVER_URL`)와 자동 등록 키(`AGENT_AUTO_REGISTER_KEY`)다. 실행기가 서버에 붙는 데는 이 둘이면 된다. 셋째 `PIPELINE_NOTIFY_TOKEN`은 배포 작업 스크립트(`Infra/gocd/job.sh`)가 쓴다. 단계가 끝날 때마다 플랫폼 서버에 결과를 알리는데, 그때 내미는 토큰이다.

머리말은 11월 11일, 서버가 없을 때 계획을 보고 쓴 것이다. 작업 스크립트는 다음 날 서버 쪽 PR로 들어왔다. 그 사이에 키 목록이 코드와 어긋났다. 머리말대로 둘만 넣었으면 어떻게 됐을지도 따져 봤다. 매니페스트는 Secret을 통째로 env로 읽는다(`envFrom`). 키가 하나 없어도 Pod는 뜨고 등록도 된다. 그러다 첫 배포에서 단계 하나가 끝나고 작업 스크립트가 결과를 알리려는 순간 토큰이 없어 실패했을 것이다. 등록까지 잘 되니 그전에는 아무도 모른다.

값의 원본은 AWS Parameter Store의 `/wcp/gocd/` 아래에 있다. GoCD 설치 스크립트는 같은 값을 EC2의 `leader-agent.env` 파일에도 세 줄로 남긴다. 서버 주소만은 원본이 없어서 EC2의 사설망 주소로 직접 적었다. 이름이 아니라 주소인 이유는, Pod는 클러스터 DNS를 쓰는데 클러스터 DNS는 사설망의 기기 이름을 모르기 때문이다.

## 3. 값을 화면에 안 찍고 Secret 만들기

[11편](/kr/blog/woowangthon/woowangthon-11-server-link/#9-ec2가-없어서-못-본-것)에서 "토큰을 옮기는 날, 화면에 안 찍고 옮기는가"를 남은 일로 적었다. 이번이 그 날이었다. 흐름은 이렇다.

```bash
v() { aws ssm get-parameter --name "/wcp/gocd/$1" --with-decryption \
        --query Parameter.Value --output text | tr -d '\r\n'; }
{ printf 'GO_SERVER_URL=%s\n' 'http://<EC2 사설망 주소>:8153/go'
  printf 'AGENT_AUTO_REGISTER_KEY=%s\n' "$(v AGENT_AUTO_REGISTER_KEY)"
  printf 'PIPELINE_NOTIFY_TOKEN=%s\n' "$(v PIPELINE_NOTIFY_TOKEN)"
} | ssh k3s-leader 'sudo k3s kubectl -n deploy create secret generic gocd-agent --from-env-file=/dev/stdin'
```

값은 Parameter Store에서 나와 파이프로만 흐르고, 리더의 kubectl이 표준 입력에서 읽는다. 화면에도, 명령 줄에도, 파일에도 안 남는다.

`tr -d '\r\n'`이 있는 이유는 운영자 기기가 Windows라서다. Windows용 `aws`는 출력 끝에 CR을 붙일 수 있다. 값 끝에 CR이 하나 붙으면 등록 키도 토큰도 서버가 아는 값과 한 글자 달라진다. 눈에 안 보이는 글자라 "키가 틀렸다"로만 보이고, 원인을 찾기 어렵다.

줄바꿈이 안 붙었는지는 값을 안 보고 확인했다. Secret에 들어간 값은 base64로 저장되니, 그 길이만 본다.

![deploy 공간의 Pod와 Secret. deploy-executor Pod 하나가 Running, 재시작 0. Secret gocd-agent는 키 3개. 키마다 base64 길이: AGENT_AUTO_REGISTER_KEY 48, GO_SERVER_URL 36, PIPELINE_NOTIFY_TOKEN 88](/static/images/woowangthon-15-gocd-registration/secret.svg)

_글을 쓰며 리더에서 다시 본 결과. 값은 안 꺼내고 키 이름과 base64 길이만 찍었다_

| 키                        | 원래 길이 | base64 길이 | 한 글자 더 붙었다면 |
| ------------------------- | --------- | ----------- | ------------------- |
| `GO_SERVER_URL`           | 27        | 36          | 40                  |
| `AGENT_AUTO_REGISTER_KEY` | 36        | 48          | 52                  |
| `PIPELINE_NOTIFY_TOKEN`   | 64        | 88          | 88                  |

base64는 3바이트를 4글자로 바꾼다. 27과 36은 3의 배수라 한 바이트만 늘어도 길이가 4 늘어난다. 그런데 토큰은 64바이트다. 64와 65는 둘 다 88글자가 된다(끝의 `=` 개수만 다르다). 길이만으로는 토큰 끝의 줄바꿈을 못 잡는다. 이 글을 쓰면서 리더에서 세 값을 풀어 CR · LF 개수만 세어 봤고, 셋 다 0이었다.

## 4. Running인데 목록에 없다

Secret 다음은 적용이다.

```bash
ssh k3s-leader 'sudo k3s kubectl apply -f -' < Infra/executor/agent.yaml
```

오후 4시 23분, Pod는 금방 Running이 됐다. [12편의 init 컨테이너](/kr/blog/woowangthon/woowangthon-12-deploy-executor/#8-실행기-pod-우리-이미지를-만들지-않는다)가 node와 helm을 꺼내 두고 실행기가 떴다. 그런데 GoCD의 실행기 목록에는 몇 분이 지나도 안 나타났다. Running인데 등록이 안 되면 길이 막혔거나 키가 틀린 것처럼 보인다.

로그를 보면 둘 다 아니었다.

![실행기 로그. 16시 23분(로그는 UTC 07:23)에 launcher가 시작하고 agent.jar를 받기 시작한다. 268332 ms 뒤에 다 받고, 플러그인 묶음은 34 ms, tfs-impl.jar는 122027 ms. 첫 부팅 391977 ms 만에 실행기 본체를 띄우고, 1초 안에 등록 여섯 줄이 이어진다. This agent is now approved by the server, Successfully registered agent](/static/images/woowangthon-15-gocd-registration/first-boot.svg)

_실행기 Pod 안의 로그. 시각은 UTC라 9시간을 더하면 한국 시각이다. 줄 앞의 클래스 이름과 md5 값은 줄였다_

GoCD 실행기 이미지에는 실행기 본체가 없다. 처음 뜨는 프로그램(launcher)은 서버에서 `agent.jar`(약 27MB)와 플러그인을 받아 온 뒤에야 본체를 띄운다. 그 다운로드가 6분 반을 먹었다. `agent.jar` 하나에 4분 28초, 플러그인 `tfs-impl.jar` 하나에 2분이다. 서버 응답 자체는 요청하고 0.1초 만에 왔다(`Got server response`). 길은 열려 있었고, 느렸을 뿐이다.

느린 이유는 사설망 경로였다. 리더에서 EC2까지가 직접 연결이 아니라 Tailscale의 도쿄 중계 서버(DERP)를 거치고 있었다. [4편에서 학교 PC와 내 기기 사이가 중계였던 것](/kr/blog/woowangthon/woowangthon-04-remote-access/#직접-연결이-아니라-중계)과 같은 모양이다. 그때 "플랫폼 서버 쪽 지연은 6단계에서 다시 잰다"고 적었는데, 이렇게 재게 됐다. 리더 호스트에서 같은 서버로 curl을 돌려 보니 60초에 5.5MB, 초당 90KB 남짓이었다. 명령 몇 줄에는 티가 안 나는 길이 27MB 앞에서는 4분이 된다.

다 받고 본체가 뜨자 등록은 1초 안에 끝났다. 자동 등록 키를 내밀고, 서버가 승인하고, 등록 정보를 받았다. 그리고 등록 직후 경로가 직접 연결로 바뀌었다. 지금 리더에서 EC2로 `tailscale ping`을 치면 중계 없이 5ms다(5절 그림). 중계가 왜 그때만 붙었는지는 모른다. Tailscale은 처음엔 중계로 붙고 직접 길을 찾으면 옮겨 가는데, 이번엔 그게 늦었던 것으로 보인다.

하나 더 남는다. 실행기의 작업 폴더는 `emptyDir`이다. [12편](/kr/blog/woowangthon/woowangthon-12-deploy-executor/#8-실행기-pod-우리-이미지를-만들지-않는다)에서 배포 한 번을 파이프라인 한 번으로 보고 일부러 그렇게 했다. 그 말은 Pod가 다시 뜰 때마다 27MB와 플러그인을 처음부터 받는다는 뜻이다. 길이 또 중계로 돌면 또 6분 반이다. 시연 직전에는 이 Pod를 재시작하지 않는다. 매니페스트 머리말에도 그렇게 적어 뒀다.

## 5. 등록 확인은 리더를 거쳐서

등록됐는지는 GoCD의 Agents API로 본다. 그런데 운영자 데스크탑에서는 8153에 못 닿는다. [11편의 사설망 접근 규칙](/kr/blog/woowangthon/woowangthon-11-server-link/#8-사설망-접근-규칙)은 EC2의 8153을 리더에만 열었다. 이 규칙을 내 확인 편하자고 넓히지는 않았다.

그래서 리더를 거쳤다. GoCD 관리자 비밀번호도 Parameter Store에 있다. 데스크탑에서 꺼내 SSH의 표준 입력으로 넘기고, 리더의 curl이 설정 파일 대신 표준 입력에서 읽게 했다(`curl -K -`). 비밀번호는 리더의 명령 줄에도(`ps`에 보인다), 디스크에도 안 남는다. 서버 주소는 리더에서 방금 만든 Secret에서 읽었다.

![운영자 데스크탑에서 리더를 거쳐 부른 Agents API. k3s-leader-executor는 이름표 leader, Enabled, Idle, 26.1.0. 옆에 wcp-aws-agent는 이름표 aws, Enabled, Idle. 리더에서 EC2로 tailscale ping은 직접 연결로 5ms. EC2 공인 주소의 8153과 3000은 8초 만에 시간 초과](/static/images/woowangthon-15-gocd-registration/agents.svg)

_글을 쓰며 다시 부른 결과. Agents API의 JSON에서 이름, 이름표, 상태, 버전만 뽑았다. 주소는 가렸다_

실행기가 둘 보인다. `wcp-aws-agent`는 EC2에서 도는 실행기로, 이름표가 `aws`다. 학생 레포로 이미지를 만드는 Build 단계를 맡는다. `k3s-leader-executor`가 이번에 붙은 리더의 실행기로, 이름표가 `leader`다. Prepare부터 Switch까지 클러스터에 쓰는 단계는 이 이름표를 달고 리더로 온다. [12편의 표](/kr/blog/woowangthon/woowangthon-12-deploy-executor/#1-실행기를-리더에-두는-이유)가 처음으로 실물 둘이 됐다.

## 6. 문서에 남긴 것

적용한 날 바로 팀 레포에 이슈([woowangthon/WOOWANGTHON_TEAM_18#164](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/issues/164))를 열고 PR([woowangthon/WOOWANGTHON_TEAM_18#166](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/166))로 고쳐 머지했다.

| 고친 곳                        | 내용                                                                      |
| ------------------------------ | ------------------------------------------------------------------------- |
| `agent.yaml` 머리말            | 키 셋과 각 값의 출처, 넣는 명령, 첫 부팅 6분 반과 재시작 주의             |
| 클러스터 설계 §8               | 실행기 Pod를 리더에 적용했고 `leader`로 등록됨                            |
| 클러스터 설계 §12              | 비밀값 표에 배포 알림 토큰 추가, 원본은 Parameter Store `/wcp/gocd/`      |
| AI 사용 범위 표                | 실행기 시작 · 등록 · 8153 길은 확인됨. 실제 파이프라인 작업은 아직 미검증 |
| 플랫폼 호스팅 문서 · 작업 파일 | 같은 내용과 첫 부팅 기록                                                  |

AI 사용 범위 표는 무엇을 직접 확인했고 무엇을 아직 안 했는지 남기는 문서라, 둘을 나눠 적었다. "실행기가 붙었다"를 "배포가 된다"로 읽히게 두면 안 된다.

## 7. 아직 한 번도 안 돈 것

12편 끝에 남긴 목록을 다시 보면, 이번에 지운 건 셋이다. 실행기 프로세스가 이 설정으로 뜨는 것, 자동 등록 키로 등록되는 것, Pod에서 사설망의 8153까지 가는 길. 남은 건 이렇다.

- **실제 배포 파이프라인.** Prepare → Render → Apply → Verify → Switch가 리더 실행기에서 도는 것을 아직 한 번도 못 봤다. 등록은 일을 받을 준비가 됐다는 뜻이지 일을 해낸다는 뜻이 아니다. 같은 공식 이미지에 node · helm을 얹은 시험용 실행기가 로컬 GoCD 서버에서 Prepare 작업을 받은 적은 있다. 하지만 리더에서, 실행기 계정의 권한과 [12편의 검사 규칙](/kr/blog/woowangthon/woowangthon-12-deploy-executor/#4-권한이-못-막는-것은-검사-규칙이) 아래에서는 아니다.
- **배포 작업이 리더로만 가는지.** 이름표 `leader`를 단 작업이 `aws` 실행기로 새지 않는지는 작업이 실제로 와야 안다.
- **시험 파이프라인.** 학생 앱 시험 배포용 `student-trial`은 GoCD에도 레포에도 아직 정의가 없다.

끝까지 배포해 보는 시험은 EC2 담당 TaeTaeJin이 맡았다. AI 담당(suda5936)의 작업이 들어온 뒤에, 플랫폼 서버에서 배포를 걸어 리더 실행기가 학생 공간에 올리고 Verify까지 통과하는지를 본다. 그 이야기는 다음 글이다.

이번 일에서 남는 건 두 장면이다. 머리말은 이번 구축을 같이 한 에이전트가 계획을 보고 쓴 것인데, 계획이 코드보다 하루 늦었다. 그걸 잡은 건 검사가 아니라 요청을 보낸 팀원이었다. 그리고 6분 반 동안 Running인데 목록에 없던 Pod. 에이전트든 사람이든 "안 된다"고 말하기 전에 로그에서 서버가 응답했는지, 사설망이 중계인지부터 봐야 했다. 동료가 되는 조건이 실수하지 않는 게 아니라면, 그 순서를 지키는 쪽일 것이다.

## 8. 정리

| 겪은 일                                           | 배운 것                                                                                                         |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 머리말에는 키가 둘, 작업 스크립트는 셋을 썼다     | 서버보다 먼저 쓴 목록은 서버 쪽 코드가 들어오면 다시 맞춘다. `envFrom`은 키가 빠져도 조용히 뜬다                |
| Windows `aws` 출력에 CR이 붙을 수 있었다          | 비밀값을 파이프로 옮길 때는 `tr -d '\r\n'`을 붙이고, 들어간 뒤 base64 길이로 확인한다                           |
| 64바이트 토큰은 한 글자 늘어도 base64 길이가 같다 | 길이 확인은 3의 배수일 때만 확실하다. 아니면 풀어서 줄바꿈 개수만 센다                                          |
| Running인데 6분 반 동안 등록이 안 됐다            | GoCD 실행기는 첫 부팅에 본체와 플러그인을 서버에서 받는다. 로그의 `Got server response`가 있으면 길은 열려 있다 |
| 리더 → EC2가 도쿄 중계로 초당 90KB였다            | 느린 전송을 고장으로 읽기 전에 `tailscale status`로 중계인지 직접인지 본다                                      |
| 작업 폴더가 `emptyDir`라 재시작마다 다시 받는다   | 시연 직전에는 실행기 Pod를 재시작하지 않는다                                                                    |
| 데스크탑에서 8153에 못 닿는다                     | 확인하려고 접근 규칙을 넓히지 않는다. 열린 길(리더)을 거치고, 비밀번호는 표준 입력으로만 넘긴다                 |
| 등록이 됐다                                       | 등록은 일을 받을 준비까지다. 배포 파이프라인은 한 번도 안 돌았다고 문서에 따로 적는다                           |

6단계에서 클러스터 쪽은 이걸로 다 했다. 남은 건 배포가 처음부터 끝까지 한 번 도는 것이다. 그 뒤로는 대회와 반납이 남았다.
