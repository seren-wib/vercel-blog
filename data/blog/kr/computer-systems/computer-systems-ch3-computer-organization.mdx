# 3.1 컴퓨터의 구성과 자료처리

**컴퓨터의 구성 → 기억장치 계층 → 데이터 처리 과정 → 저장 프로그램 방식**

## 3.1.1 컴퓨터 구조

**1. 컴퓨터의 구성과 CPU**

- 컴퓨터의 구성

  | 요소           | 역할                                 |
  | -------------- | ------------------------------------ |
  | **CPU**        | 명령어를 해석·실행하고 데이터를 처리 |
  | **주기억장치** | 실행 중인 프로그램과 데이터 저장     |
  | **입출력장치** | 외부와 데이터를 주고받음             |
  | **버스(Bus)**  | 구성요소 사이에서 정보 전달          |

- CPU
  - 프로그램의 명령어를 해석하고 실행하는 핵심 처리장치
  - 주기억장치에서 명령어와 데이터를 가져와 처리
  - 핵심 역할: **명령어 실행, 데이터 처리, 동작 제어**

  | 구성요소                   | 역할                                        |
  | -------------------------- | ------------------------------------------- |
  | **제어장치(Control Unit)** | 명령어 해석, 동작 순서를 제어하는 신호 생성 |
  | **연산장치(ALU)**          | 산술·논리·비교·비트 이동 연산 수행          |
  | **레지스터(Register)**     | 즉시 사용할 값과 중간 결과를 임시 저장      |
  - **예시**: c = a + b라면 **제어장치**가 값을 가져오고 덧셈하도록 지시하고, **레지스터**가 a, b를 보관하고, **ALU**가 더한 뒤 결과를 레지스터에 넣는다.
  - 부록: 마이크로프로세서(Microprocessor): CPU의 주요 기능을 하나의 집적회로(IC)에 구현한 프로세서

- 레지스터
  - 사용 이유: 주기억장치보다 훨씬 빠르기 때문에
  - **범용 레지스터**: 변수 값, 계산 결과 등 다양한 용도로 사용
  - **특수 목적 레지스터**: 정해진 역할 수행. 예를 들어 PC, IR 등이 있다.

    | 특수 목적 레지스터           | 저장하는 내용                            |
    | ---------------------------- | ---------------------------------------- |
    | **PC(Program Counter)**      | 다음에 가져올**명령어의 주소**           |
    | **IR(Instruction Register)** | 현재 해석하거나 실행 중인**명령어 자체** |
    - PC가 가리키는 주소에서 명령어를 가져와 IR에 넣고 해석한다.
    - PC는 일반적으로 다음 명령어 주소로 바뀌지만, 분기하면 다른 주소로 바뀔 수 있다.

**2. 컴퓨터의 기억장치 계층**

- 계층 표
  - 기억장치는 **속도·용량·비트당 가격**이 서로 트레이드오프 → 여러 종류를 계층적으로 구성
  - CPU에 가까울수록 빠르고 작고 비쌈, 멀수록 느리고 크고 쌈 → 자주 쓰는 데이터는 CPU 가까이

  | 계층         | CPU와 거리  | 속도            | 용량      | 비트당 비용 |
  | ------------ | ----------- | --------------- | --------- | ----------- |
  | 레지스터     | 가장 가까움 | 가장 빠름       | 가장 작음 | 가장 비쌈   |
  | 캐시 메모리  | 매우 가까움 | 매우 빠름       | 작음      | 비쌈        |
  | 주기억장치   | 중간        | 빠름            | 큼        | 중간        |
  | 보조기억장치 | 멂          | 상대적으로 느림 | 매우 큼   | 저렴        |

- **캐시 메모리(Cache Memory)**: CPU 칩 내부의 고속 메모리
  - 자주 쓸 명령어·데이터의 **복사본**을 임시 저장
  - 주기억장치 접근 횟수를 줄여 CPU와 주기억장치의 속도 차이를 완화

- 캐시 히트 / 미스: 데이터 필요 시 CPU → 캐시 먼저 확인
  - **Cache Hit**: 캐시에 있음 → 바로 사용
  - **Cache Miss**: 없음 → 하위 캐시나 주기억장치에서 가져옴

- **지역성(Locality)**: 최근 또는 인접한 데이터를 다시 쓸 가능성이 높은 성질. 캐시가 잘 동작하는 이유
  - **시간 지역성(Temporal)**: 최근 쓴 데이터는 곧 다시 씀. 예: 반복문 카운터 i
  - **공간 지역성(Spatial)**: 어떤 위치를 쓰면 그 주변도 곧 씀. 예: 배열 순차 탐색
  - 배열은 연속 저장 → arr[0] 읽을 때 주변 원소도 캐시로 옴 → arr[1], arr[2]는 Hit
  - 연산 횟수가 같아도 메모리 접근 방식에 따라 실행 시간이 달라짐

- L1 / L2 / L3

  | 구분 | 위치·특징             | 속도            | 용량      |
  | ---- | --------------------- | --------------- | --------- |
  | L1   | 각 코어에 가장 가까움 | 가장 빠름       | 가장 작음 |
  | L2   | 보통 각 코어 가까이   | 빠름            | L1보다 큼 |
  | L3   | 보통 여러 코어가 공유 | 상대적으로 느림 | 가장 큼   |
  - L1 → L2 → L3 → DRAM 갈수록 느려지고 커짐 (실제 구성은 CPU 설계마다 다름)

**3. 데이터 연산처리 과정**

- 데이터 연산의 기본 흐름: CPU가 계산하려면 데이터를 CPU 내부로 가져와야 함
  1. **캐시 확인**: 있으면 Cache Hit → 바로 사용, 없으면 Cache Miss → 주기억장치(DRAM)에서 가져옴
  2. **레지스터에 저장**: ALU는 레지스터 값만 갖고 계산
  3. **ALU에서 연산**: 제어장치가 수행할 연산 결정, ALU가 레지스터 데이터로 계산
  4. **결과 저장**: 먼저 레지스터에 들어간다. 필요 시 캐시, 주기억장치에 반영
  - 데이터 이동 경로: **주기억장치 ↔ 캐시 ↔ 레지스터 ↔ ALU**

- **버스(Bus)**: CPU, 기억장치, 입출력 장치 사이에 정보 전달하는 공용 통신 경로, 데이터, 주소, 제어 신호도 다닌다.

  | 버스                       | 전달하는 정보             | 예시                            |
  | -------------------------- | ------------------------- | ------------------------------- |
  | **주소 버스(Address Bus)** | 접근할 위치               | "메모리의 어느 위치인가?"       |
  | **데이터 버스(Data Bus)**  | 실제 데이터               | 변수 값, 명령어, 읽어 온 데이터 |
  | **제어 버스(Control Bus)** | 동작을 지정하는 제어 신호 | 읽기, 쓰기, 인터럽트            |

- 메모리 읽기 (예: 주소 1000의 값)
  1. **주소 전달** CPU → 주기억장치: 주소 버스로 1000
  2. **읽기 제어 신호 전달** CPU → 주기억장치: 제어 버스로 Read
  3. **데이터 전달** 주기억장치 → CPU: 데이터 버스로 해당 주소의 데이터

- 메모리 쓰기: CPU → 주기억장치로 **주소 + 저장할 데이터 + 쓰기 제어 신호** 전달
- **저장 프로그램 방식(Stored-Program Concept)**
  - 초기 전자식 컴퓨터: 작업 바꾸려면 배선·스위치 변경 → 복잡하고 오래 걸림
  - 명령어도 데이터처럼 0과 1 비트 패턴으로 표현
  - 프로그램과 데이터를 주기억장치에 함께 저장
  - CPU는 가져온 비트 패턴이 명령어인지 데이터인지 실행 상황에 따라 해석
  - 의미: 배선 안 바꾸고 프로그램만 바꾸면 다른 작업 가능 → 현대 범용 컴퓨터의 핵심 원리

- **폰 노이만 구조(Von Neumann Architecture)**: 프로그램과 데이터를 같은 주기억장치에 저장하고 CPU가 순차적으로 가져와 처리하는 구조
  - 명령어 처리와 데이터 접근 모두 메모리와 통신 필요
  - **폰 노이만 병목(Bottleneck)**: **CPU 처리 속도에 비해 메모리 접근이 느리면 CPU가 데이터를 기다리는 시간 발생**

# 3.2 기계어

**CPU는 비트패턴으로 표현된 명령어를 해석하고 실행**

## 3.2.1 기계어와 기계 명령

- **기계어(Machine Language)**: CPU가 직접 이해하고 실행할 수 있는 명령어
  - 0과 1의 비트패턴으로 표현, 각 비트패턴이 CPU가 수행할 작업을 나타냄
  - CPU 종류에 따라 사용할 수 있는 기계 명령이 다름

- **기계 명령(Machine Instruction)**: CPU가 수행하는 하나의 기본 작업
  - 간단한 명령들이 모여 복잡한 일 수행. 모든 프로그램은 결국 기계 명령들로 변환되어야 함
  - 예: 기억장치 → CPU로 가져오기, 기억장치에 저장, 두 데이터 연산, 레지스터 간 이동, 실행할 명령어 위치 변경

- **기계 명령 구조**: **무엇을** 할지 + **어떤 데이터를 대상으로** 할지

  | 구성                  | 의미                    | 예                                   |
  | --------------------- | ----------------------- | ------------------------------------ |
  | **연산 코드(Opcode)** | 수행할 동작의 종류      | 데이터 이동, 저장, 연산, 분기        |
  | **피연산자(Operand)** | 명령을 수행할 대상 정보 | 데이터, 레지스터 번호, 기억장치 주소 |
  - 예: `ADD R3, R1, R2` → ADD: 덧셈(Opcode), R1·R2: 입력 피연산자, R3: 결과 저장할 목적지 레지스터

## 3.2.2 기계 명령의 종류

- **데이터 이동 명령(Data Transfer)**: 레지스터 ↔ 메모리, 레지스터 ↔ 레지스터로 데이터 이동
  - 원래 데이터가 없어지는 게 아니라 값이 **복사**됨
  - **LOAD**: 메모리 → 레지스터 (`LOAD R1, [A]`)
  - **STORE**: 레지스터 → 메모리 (`STORE R1, [C]`)
  - **MOVE(MOV)**: 레지스터 사이 복사 (`MOV R2, R1`: R1 값을 R2로)
  - I/O 명령: 키보드·디스크·네트워크 장치와 데이터 주고받음. ISA와 시스템에 따라 처리 방식 다름

- **산술·논리 명령(Arithmetic / Logic)**: 데이터에 계산이나 논리 연산 수행
  - ADD / SUB, MUL / DIV: 사칙연산 (`ADD R3, R1, R2`: R3 ← R1 + R2)
  - AND / OR / XOR: 비트 단위 논리 연산
  - SHIFT: 비트를 왼쪽/오른쪽으로 이동
  - ROTATE: 밀려난 비트를 반대쪽으로 다시 넣음

- **제어 명령(Control)**: 데이터 계산이 아니라 프로그램 실행 순서를 변경
  - **조건부 분기(Conditional Branch)**: 조건에 따라 다음 명령 변경. C의 if, while, for 구현
  - **무조건 분기(Unconditional Jump)**: 조건 없이 지정 위치로 이동. 함수 호출, 반복·분기 구조
  - 프로그램 실행 종료(HALT)
  - 예: `CMP R1, R2` → `BNE END` (다르면 END로) → `MOV R3, #1` (같으면 R3에 1)

- 덧셈 예 C = A + B: Memory A/B → Registers → ADD → Register → Memory C

  | 단계              | 명령             |
  | ----------------- | ---------------- |
  | 메모리 A를 R1으로 | `LOAD R1, [A]`   |
  | 메모리 B를 R2로   | `LOAD R2, [B]`   |
  | R1 + R2 → R3      | `ADD R3, R1, R2` |
  | R3를 메모리 C에   | `STORE R3, [C]`  |
  | 멈춤              | `HALT`           |

- 나눗셈 예 C = A / B: Memory A, B → Registers → **0 검사** → DIV → Register → Memory C

  | 단계                        | 명령                |
  | --------------------------- | ------------------- |
  | 메모리 A를 R1으로           | `LOAD R1, [A]`      |
  | 메모리 B를 R2로             | `LOAD R2, [B]`      |
  | R2가 0이면 오류 처리로 이동 | `JUMP R2, DIV_ZERO` |
  | R1 / R2 → R3                | `DIV R3, R1, R2`    |
  | R3를 메모리 C에             | `STORE R3, [C]`     |
  | 멈춤                        | `HALT`              |

- C 코드 한 문장도 여러 개의 기계 명령으로 나뉘어 실행됨 (명령어 형식은 개념적 예, 실제는 ISA마다 다름)

## 3.2.3 RISC와 CISC

- **명령어 집합(Instruction Set)**: CPU가 이해하고 실행할 수 있는 명령들의 집합
  - 지원 연산, 명령어 표현 방식, 사용 가능한 레지스터 등이 정의됨
  - 기계어는 모든 컴퓨터에서 같은 언어가 아님. CPU가 다르면 같은 작업도 다른 기계 명령으로 표현

- **ISA(Instruction Set Architecture, 명령어 집합 아키텍처)**: 소프트웨어가 CPU를 사용하기 위해 따라야 하는 규칙. CPU와 프로그램 사이의 약속
  - 정의 내용: 명령어 종류, 명령어 비트 형식, 사용 가능 레지스터, 데이터 표현 방식, 메모리 주소 지정 방식, 분기·예외 처리 방식
  - 컴파일러는 목표 CPU의 ISA 규칙에 맞는 기계어로 번역해야 함

- CPU 명령어 설계의 두 접근 방식
  - **RISC(Reduced Instruction Set Computer)**: 단순하고 규칙적인 명령어 중심
  - **CISC(Complex Instruction Set Computer)**: 다양하고 복합적인 명령어 지원

- **RISC 특징**: 단순하고 규칙적인 명령어 → 효율적인 CPU 구현
  - 단순한 명령어: 명령 하나가 단순한 작업, 복잡한 작업은 여러 명령 조합
  - 규칙적인 명령어 형식: 형식·실행 방식이 일정 → 해석·처리 구조 설계 쉬움
  - 레지스터 중심 연산
  - **Load-Store 구조**: 메모리 → LOAD → Register → ADD → Register → STORE → Memory
  - 대표: Arm(스마트폰·태블릿·임베디드·PC·서버), RISC-V(개방형 ISA), PowerPC(과거 Apple Macintosh)

- **CISC 특징**: 다양하고 복합적인 명령어 → 명령 하나로 더 많은 작업
  - 단순한 것부터 복잡한 기능까지 다양한 명령어
  - 명령어 길이·형식이 서로 다를 수 있음
  - 일부 명령어는 메모리 데이터를 직접 연산에 사용
  - 명령 하나가 메모리 접근 + 연산 등 여러 동작 포함
  - 대표: x86 / x86-64 (Intel·AMD, 데스크톱·노트북·서버)

- ADD 비교 (메모리 A + B → C)
  - RISC: `LOAD R1, [A]` → `LOAD R2, [B]` → `ADD R3, R1, R2` → `STORE R3, [C]`
  - CISC(x86): `MOV EAX, [A]` → `ADD EAX, [B]` (메모리 B를 직접 읽어 더함) → `MOV [C], EAX`

  | 구분        | RISC 계열                | CISC 계열                                |
  | ----------- | ------------------------ | ---------------------------------------- |
  | 명령어      | 비교적 단순·규칙적       | 다양하고 복합적                          |
  | 연산        | 레지스터 ↔ 레지스터 중심 | 메모리 값을 피연산자로 직접 사용 가능    |
  | 메모리 접근 | Load / Store로 분리      | 한 명령어에 메모리 접근 + 연산 포함 가능 |
  | 대표 ISA    | Arm, RISC-V              | x86 / x86-64                             |
  | 활용        | 모바일·임베디드·PC·서버  | PC·서버                                  |
  - 현대 프로세서는 서로의 장점을 받아들여 발전. RISC = 단순한 CPU, CISC = 느린 CPU라는 뜻 아님. 차이는 명령어 집합 설계 방식

- **ARM 아키텍처**: Arm이 개발한 RISC 계열 ISA. 에너지 효율 중시, 현대 대표 RISC 계열
  - Arm: CPU 아키텍처·코어 등 반도체 설계 IP를 개발·제공하는 기업
  - 여러 기업이 라이선스·IP로 프로세서·SoC 개발: Apple M 시리즈(Mac), Qualcomm Snapdragon(스마트폰·PC), Samsung Exynos(스마트폰)
  - IP(Intellectual Property): 재사용할 수 있는 반도체 설계
  - SoC(System on a Chip): CPU, GPU, 메모리 제어기 등 여러 기능을 하나의 칩에 통합

## 3.2.4 가상 기계어

- 가상 컴퓨터 구성
  - 주기억장치 256개 셀, 주소 00 ~ FF
  - 범용 레지스터 16개, 번호 0 ~ F. 그 외 PC, 명령 레지스터(IR)
  - 명령어 길이 16비트 = 2바이트 = 16진수 4자리

- 명령어 구조
  - **명령 코드(op-code)**: 처음 4비트, 어느 명령인지 (16개 명령 가능)
  - **피연산자(operand)**: 나머지 12비트 = 4비트(레지스터 번호) + 8비트(메모리 주소/값)

  | 비트 위치 | 15 ~ 12        | 11 ~ 8      | 7 ~ 0          |
  | --------- | -------------- | ----------- | -------------- |
  | 필드      | op-code        | 레지스터    | 주소/값        |
  | **35A7**  | 0011 (3) STORE | 0101 (5) R5 | 1010 0111 (A7) |
  - 16진수 한 자리 = 4비트 → 명령어 16비트 = 16진수 4자리

  | 명령 | 형식         | 의미                                 |
  | ---- | ------------ | ------------------------------------ |
  | 1RXY | LOAD R, MEM  | R ← 주소 XY의 값                     |
  | 2RXY | LOAD R, VAL  | R ← 값 XY (1바이트)                  |
  | 3RXY | STORE R, MEM | 주소 XY ← R의 값                     |
  | 40RS | MOVE R, S    | S ← R의 값                           |
  | 5RST | ADD R, S, T  | R ← S + T (2의 보수 덧셈)            |
  | 6RST | ADDF R, S, T | R ← S + T (부동소수점 덧셈)          |
  | 7RST | OR R, S, T   | R ← S OR T                           |
  | 8RST | AND R, S, T  | R ← S AND T                          |
  | 9RST | XOR R, S, T  | R ← S XOR T                          |
  | AR0X | ROT R, X     | R을 X비트만큼 rotate right           |
  | BRXY | JUMP R, ADDR | R = R0이면 주소 XY로 분기            |
  | B0XY | 무조건 분기  | 주소 XY로 분기 (R0 = R0이라 항상 참) |
  | C000 | HALT         | 중단                                 |

- 해석 예
  - **35A7**: 3 = STORE, 5 = 레지스터 5, A7 = 주소 → 5번 레지스터 내용을 주소 A7에 저장
  - **B34C**: 3번 레지스터가 0번 레지스터와 같으면 주소 4C로 분기
  - **B04C**: 무조건 주소 4C로 분기
  - 분기가 실행되면 PC가 순차 증가 대신 지정된 주소로 변경됨

- 사용 예: c = a + b

  | 기계 명령 | 설명                                     |
  | --------- | ---------------------------------------- |
  | 156C      | 주소 6C의 값을 5번 레지스터에 LOAD       |
  | 166D      | 주소 6D의 값을 6번 레지스터에 LOAD       |
  | 5056      | 5번 + 6번 (2의 보수 덧셈) → 0번 레지스터 |
  | 306E      | 0번 레지스터 값을 주소 6E에 STORE        |
  | C000      | 멈춤                                     |

- **해독 순서: Opcode 확인 → 필드 분리 → 레지스터/주소 해석 → 데이터 흐름 추적**

# 3.3 프로그램의 실행

**프로그램은 주기억장치에 적재된 뒤 PC가 가리키는 명령어를 한 번에 하나씩 인출·해석·실행하며 진행**

## 3.3.1 프로그램 실행에 필요한 레지스터

- **프로그램 실행의 기본 흐름**: 소스 코드가 아니라 컴파일된 **기계어 명령어들의 순서**로 실행
  - 저장장치의 실행 파일 → 실행 요청 → 운영체제가 코드·데이터를 **주기억장치(RAM)**에 적재 → CPU가 명령어 인출 → 해석·실행 → 다음 명령어 인출 반복
  - 다음에 실행할 명령어를 찾는 기준: **PC(Program Counter)**

- 주요 레지스터

  | 레지스터                     | 역할                                                    | 예                                    |
  | ---------------------------- | ------------------------------------------------------- | ------------------------------------- |
  | **PC(Program Counter)**      | 다음에 실행할 **명령어의 주소** 저장                    | `PC = A0` (주소 A0부터 저장된 명령어) |
  | **IR(Instruction Register)** | 현재 실행(처리) 중인 **명령어 자체** 저장               | `IR = 156C`                           |
  | **범용 레지스터**            | 연산할 데이터와 연산 결과를 임시 저장 (메모리보다 빠름) | `R5`, `R6`, `R0`                      |
  | **상태 레지스터**            | 연산 결과의 상태 정보 저장 → 이후 조건 분기에 사용      | 0 여부, 음수 여부, 자리올림 등        |
  - PC가 항상 일정한 값만큼만 증가하는 것은 아님 (명령어 길이가 다르거나 분기 명령어가 실행되면 다른 주소로 변경)

- **상태 레지스터와 조건 분기**: 비교·연산 수행 → 상태 레지스터에 결과 상태 기록 → 조건 분기 명령어가 이를 확인해 다음 명령어를 계속 실행할지 다른 주소로 이동할지 결정

  | 플래그(Flag)      | 저장하는 상태                                                     |
  | ----------------- | ----------------------------------------------------------------- |
  | **Zero Flag**     | 연산 결과가 0인지 (예: 두 값 비교 결과가 같으면 0 → 분기 시 확인) |
  | **Negative Flag** | 연산 결과가 음수인지                                              |
  | **Carry Flag**    | 덧셈에서 자리올림이 발생했는지                                    |
  | **Overflow Flag** | 표현 범위를 넘는 오버플로가 발생했는지                            |

## 3.3.2 기계 주기

- **기계 주기(Machine Cycle)**: CPU가 각 명령어를 실행하기 위해 **인출(Fetch) → 해석(Decode) → 실행(Execute)**을 반복하는 과정

![기계 주기](/static/images/computer-systems-ch3-computer-organization/machine-cycle.svg)

- 단계별 동작
  1. **① 인출(Fetch)**: **PC**가 가리키는 메모리 주소에서 명령어를 읽어 **IR**에 저장하고, **PC는 다음 명령어 주소로 즉시 갱신**
  2. **② 해석(Decode)**: **제어장치**가 **IR**의 비트 패턴을 해석해 수행할 연산(LOAD, ADD, STORE, JUMP, HALT 등)과 필요한 피연산자 결정
  3. **③ 실행(Execute)**: 해석 결과에 따라 실제 동작(데이터 이동, 산술 연산, 저장, 분기 등) 수행 → 끝나면 다시 다음 명령어 인출

## 3.3.3 프로그램 실행 과정

- 더하기 연산 실행 예 (`[6C] + [6D] → [6E]`)
  - 가상 기계어 명령어 1개 = **2바이트(16비트)**, 주기억장치 한 셀 = **1바이트** → 명령어 하나가 두 셀 차지, 순차 실행 시 **PC는 2씩 증가** (`A0 → A2 → A4 → A6 → A8`)

![프로그램 실행 인출 과정](/static/images/computer-systems-ch3-computer-organization/program-execution-fetch.svg)

| 순서 | 명령어 (`[주소]`)  | 시작 PC | ① 인출(Fetch)              | ② 해석(Decode)   | ③ 실행(Execute) |
| ---- | ------------------ | ------- | -------------------------- | ---------------- | --------------- |
| 1    | `156C` (`[A0:A1]`) | `A0`    | `IR ← 156C`, **`PC ← A2`** | `LOAD R5, [6C]`  | `R5 ← [6C]`     |
| 2    | `166D` (`[A2:A3]`) | `A2`    | `IR ← 166D`, **`PC ← A4`** | `LOAD R6, [6D]`  | `R6 ← [6D]`     |
| 3    | `5056` (`[A4:A5]`) | `A4`    | `IR ← 5056`, **`PC ← A6`** | `ADD R0, R5, R6` | `R0 ← R5 + R6`  |
| 4    | `306E` (`[A6:A7]`) | `A6`    | `IR ← 306E`, **`PC ← A8`** | `STORE R0, [6E]` | `[6E] ← R0`     |
| 5    | `C000` (`[A8:A9]`) | `A8`    | `IR ← C000`, **`PC ← AA`** | `HALT`           | 프로그램 종료   |

- **순차 실행과 분기 실행**
  - **순차 실행**: 기본적으로 PC를 다음 명령어 주소로 갱신하며 순서대로 실행
  - **분기 실행**: 조건문·반복문·함수 호출(`if`, `while`, `for`, `switch`)은 **분기 명령어**로 **PC 값을 변경**해 구현
  - 예 (`if (x == 0) y = 1; else y = 2;`): `x`와 `0` 비교 → 상태 레지스터에 결과 저장 → 비교 결과에 따라 `then` 또는 `else` 블록 주소로 분기(PC 변경) → 실행 후 `if-else` 다음 주소로 이동
  - 프로그램의 흐름 제어 = **PC를 어느 주소로 갱신할 것인가**의 문제

# 3.4 연산 명령

**CPU의 연산은 고정된 비트 수 안에서 ALU가 수행하는 비트패턴 변환 + 상태 플래그 기록 과정**

- 연산 명령의 구분
  | 구분 | 대표 명령 | 주요 용도 |
  | ----------------------- | ------------------------------------------- | -------------------------- |
  | **논리 연산** | `AND`, `OR`, `XOR`, `NOT` | 특정 비트 검사·설정·반전 |
  | **자리이동 연산** | `SHL`, `SHR`, `SAR`, `ROL`, `ROR` | 비트 이동, 비트 조작 |
  | **산술 연산** | `ADD`, `SUB`, `MUL`, `DIV` | 정수 및 실수 계산 |
  | **비교 연산** | `CMP`, `TEST` | 조건 분기 전 결과 확인 |

## 3.4.1 논리 연산

- **논리 연산(Logical Operation)**: 각 비트 위치에 독립적으로 수행되는 연산. 숫자 크기 계산보다 **비트 상태 조작**에 사용

  | 연산          | 결과가 1이 되는 조건 | 비트 마스킹(Masking) 활용                               | 예 (`x = 01011001`)                                    |
  | ------------- | -------------------- | ------------------------------------------------------- | ------------------------------------------------------ |
  | **AND (`&`)** | 두 비트가 모두 1     | **원하는 비트만 남기기(추출)** / 나머지 0 제거          | `01011001 & 00001111 = 00001001` (하위 4비트 추출)     |
  | **OR (`\|`)** | 둘 중 하나 이상이 1  | **특정 비트를 1로 설정**                                | `01011001 \| 10000000 = 11011001` (최상위 비트 1 설정) |
  | **XOR (`^`)** | 두 비트가 서로 다름  | **특정 비트 반전**(마스크가 1인 위치만 뒤집기), 값 비교 | `01011001 ^ 00000001 = 01011000` (최하위 비트 반전)    |
  | **NOT (`~`)** | 입력 비트의 반대     | **모든 비트 반전**                                      | `~01011001 = 10100110`                                 |

- **비트 상태 확인**: 특정 비트가 0인지 1인지 스위치처럼 확인 (`AND` 사용)
  - 홀수·짝수 판별: 가장 오른쪽 비트(최하위 비트)를 `n & 1`로 확인 → `1`이면 홀수(`0111 & 0001 = 0001`), `0`이면 짝수(`0110 & 0001 = 0000`)
  - 활용: 장치 준비 상태 확인, 파일 접근 권한, 옵션 활성화 여부, 여러 참/거짓 상태를 정수 하나에 저장

## 3.4.2 자리이동과 회전 연산

- **자리이동(Shift)과 회전(Rotate)**: 비트를 왼쪽/오른쪽으로 이동. 일반 Shift는 밀려난 비트를 버리고 빈자리를 채우며, Rotate는 밀려난 비트를 반대편 끝으로 다시 넣음

![오른쪽 자리이동과 회전 비교](/static/images/computer-systems-ch3-computer-organization/shift-rotate.svg)

| 종류                   | 방향·명령     | 빈자리 처리                                  | 효과 및 주 사용 대상                                                                 |
| ---------------------- | ------------- | -------------------------------------------- | ------------------------------------------------------------------------------------ |
| **논리적 왼쪽 이동**   | `SHL` (`<<`)  | 오른쪽 빈자리에 **항상 0** 삽입              | 범위 내면 **×2 효과** (비트가 폭을 넘으면 상위 비트 소실 → 항상 2배는 아님)          |
| **논리적 오른쪽 이동** | `SHR` (`>>`)  | 왼쪽 빈자리에 **항상 0** 삽입                | **unsigned 정수**에서 **÷2 몫** 효과 (`54(00110110) >> 1 → 27(00011011)`)            |
| **산술적 오른쪽 이동** | `SAR`         | 왼쪽 빈자리에 **최상위 부호 비트(MSB) 복제** | **signed(2의 보수) 정수**의 부호 유지 + **÷2 효과** (`-12(11110100) → -6(11111010)`) |
| **왼쪽/오른쪽 회전**   | `ROL` / `ROR` | 밀려난 비트를 **반대쪽 끝으로 다시 삽입**    | 비트 재배치, 암호화 비트 혼합, 해시 함수 (`ROL`: MSB→LSB, `ROR`: LSB→MSB)            |

- **C 언어 시프트 연산(`<<`, `>>`) 주의점**
  - `unsigned` 값의 오른쪽 이동(`>>`)은 `0`이 채워지는 논리적 이동
  - 음수 `signed` 정수의 `>>` 결과는 C 구현에 따라 차이가 있을 수 있고, `<<`에서 범위를 벗어나면 안전하지 않음 → **비트 조작 목적이면 `unsigned int`, `uint32_t` 사용이 안전**

## 3.4.3 산술 연산

- **정수 사칙연산**: 결국 이진 덧셈·뺄셈·자리이동의 조합
  - **덧셈(`ADD`)**: ALU가 각 비트의 합과 자리올림(carry) 계산
  - **뺄셈(`SUB`)**: 별도 뺄셈 회로 대신 **2의 보수를 더해 덧셈 회로 재사용** (`A - B = A + (-B)`)
  - **곱셈(`MUL`)**: 각 비트를 확인하며 왼쪽 이동 후 더하는 **Shift + Add** 방식 (예: `13 × 5 = 13 × (4 + 1) = (13 << 2) + 13`)
  - **나눗셈(`DIV`)**: 나누는 값을 반복해서 빼며 몫 비트를 결정하는 **Shift + Subtract** 방식

- **정수 연산 vs 부동소수점 연산**

  | 구분      | 정수(Integer) 연산 (`29 + 13`) | 부동소수점(Floating Point) 연산 (`3.14 + 2.75`)                                    |
  | --------- | ------------------------------ | ---------------------------------------------------------------------------------- |
  | 표현 방식 | 정수 비트패턴                  | 부호, 지수, 가수                                                                   |
  | 처리 과정 | 이진 덧셈 중심 (직접 계산)     | **지수 크기 비교·맞춤(작은 쪽 가수 이동) → 가수 덧셈/뺄셈 → 결과 정규화 → 반올림** |
  | 주요 문제 | Overflow                       | 반올림 오차, 정밀도 손실 (`0.1 + 0.2 == 0.3`이 참이 아닐 수 있는 이유)             |

## 3.4.4 연산 결과와 상태 정보

- **Carry vs Carry Flag(CF)**
  - **Carry**: 비트 덧셈에서 한 자리 합이 2 이상일 때 다음 자리로 전달되는 내부 올림수
  - **Carry Flag(CF)**: 모든 내부 carry가 아니라 **최상위 비트(MSB) 밖으로 나간 최종 carry-out**만 기록 (`저장 가능한 비트 폭 밖으로 값이 나갔는가?`)

- **Carry Flag(CF) vs Overflow Flag(OF) 비교**
  - CPU 가산기는 `signed`와 `unsigned`를 구분해 더하지 않고, **같은 비트패턴을 더한 뒤 CF와 OF를 모두 기록**함 → 프로그래머/명령어가 **어떻게 해석하느냐**에 따라 확인할 플래그가 다름

  | 구분           | Carry Flag (CF)                                                                            | Overflow Flag (OF)                                                                           |
  | -------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
  | 판단 기준      | **최상위 비트 밖으로 carry**가 나갔는가?                                                   | **signed 정수로 해석했을 때** 표현 범위를 벗어났는가? (예: 양수+양수=음수, 음수+음수=양수)   |
  | 주로 쓰는 해석 | **unsigned 연산** 범위 초과 판단                                                           | **signed 연산** 범위 초과 판단                                                               |
  | 8비트 범위     | `0 ~ 255`                                                                                  | `-128 ~ 127`                                                                                 |
  | 대표 예        | `255(11111111) + 1 = 00000000` → **`CF = 1`, `OF = 0`** (signed로는 `-1 + 1 = 0`이라 정상) | `127(01111111) + 1 = 10000000` → **`CF = 0`, `OF = 1`** (signed로는 `-128`이 되어 부호 역전) |
  - 8비트 연산별 `CF` / `OF` 정리:
    - `1 + 1` (`0000 0010`): `CF = 0`, `OF = 0`
    - `255 + 1` (`0000 0000`): `CF = 1`, `OF = 0`
    - `127 + 1` (`1000 0000`): `CF = 0`, `OF = 1`
    - `128 + 128` (`10000000 + 10000000 = 0000 0000`): **`CF = 1`, `OF = 1`** (MSB 밖 올림 발생 + signed로는 `-128 + (-128) = 0` 양수로 부호 역전)

- **상태 플래그와 조건 분기(`CMP`)**
  - 비교 연산(`CMP a, b`)은 내부적으로 **뺄셈(`a - b`)**을 수행해 상태 플래그를 기록
  - `a - b == 0` (`Zero Flag = 1`) → `a == b` / 음수면(`signed`) `a < b` / 양수면 `a > b`
  - 고급 언어의 `if`, `while`, `for` 조건문 = **비교 연산(`CMP`) + 상태 플래그 검사 + 조건 분기 명령**으로 실행

# 3.5 I/O 제어와 데이터 전송

**I/O 제어기가 CPU 대신 장치를 다루고, Handshaking·인터페이스로 안정적으로 전송, Interrupt·DMA로 CPU 부담을 줄임**

## 3.5.1 I/O 제어기와 주변장치

![I/O 요청 경로](/static/images/computer-systems-ch3-computer-organization/io-path.svg)

- **I/O 제어기(I/O Controller)**: CPU와 주변장치 사이에서 통신을 중개하는 하드웨어. 예: 프린터 상태를 레지스터에 담아 두고 CPU가 읽게 함
  - 그림에서: HARDWARE 아래 초록 박스
- 필요한 이유: 장치마다 데이터 형태·속도·동작 방식이 다름 → CPU가 다 직접 처리하면 제어 구조가 복잡해짐
  - 키보드(입력이 비정기적), 프린터(CPU보다 매우 느림), SSD(블록 단위 읽기·쓰기), 네트워크(데이터가 비정기적으로 도착)
- **I/O 요청 경로**: 응용 프로그램 → 운영체제(파일 시스템) → 디바이스 드라이버 → I/O 제어기 → 주변장치
  - 응용 프로그램·OS·드라이버는 CPU가 실행하는 소프트웨어, 제어기·주변장치는 하드웨어
  - 응용 프로그램은 장치를 직접 제어 안 함
  - 예: `fprintf(fp, "Hello\n")` → OS 파일 시스템이 처리 → CPU가 드라이버 실행 → 드라이버가 제어기 레지스터에 명령·데이터 전달 → 제어기가 SSD와 데이터 주고받음
- I/O 제어기 역할: ① 명령 전달 ② 데이터 전달(CPU·메모리 ↔ 장치 중계) ③ 상태 관리(준비·동작·완료·오류) ④ 장치 특성 처리(속도·통신 방식 맞춤)
  - 예: USB Controller(USB 메모리·키보드·마우스), Storage Controller(SSD), Network Interface Controller, Graphics Controller
- **Controller vs Device Driver**

  | 구분 | Controller                         | Device Driver                                            |
  | ---- | ---------------------------------- | -------------------------------------------------------- |
  | 정체 | **하드웨어**                       | **소프트웨어**                                           |
  | 위치 | 메인보드, 확장카드, 장치 내부      | 운영체제 내부                                            |
  | 역할 | 장치와 실제 데이터 전송, 상태 관리 | OS의 I/O 요청을 제어 명령으로 변환, 제어기 레지스터 접근 |
  | 예   | USB Controller, SSD Controller     | USB Driver, Printer Driver                               |

- 제어기 내부 레지스터
  - 그림에서: I/O Controller 박스 안 세 줄

  | 레지스터                   | 역할                               | 프린터 예          |
  | -------------------------- | ---------------------------------- | ------------------ |
  | **Control Register**       | 장치가 수행할 명령·제어 정보       | 출력 시작, 초기화  |
  | **Status Register**        | 장치의 현재 상태·오류              | Ready, Busy, Error |
  | **Data Register / Buffer** | CPU ↔ 제어기 사이 데이터 임시 저장 | 출력할 데이터 일부 |
  - 레지스터 기반 제어 순서: Status로 준비 확인 → Data에 출력 데이터 기록 → Control에 명령 기록 → 제어기가 장치 동작시키고 Status 갱신 (Data·Control 순서는 장치마다 다를 수 있음)

## 3.5.2 CPU와 I/O 제어기의 통신

- **시스템 인터커넥트**: CPU·메모리·I/O 제어기를 잇는 통신 경로. CPU는 여기를 통해 제어기 레지스터를 읽고 씀
  - **버스(Bus)**: 여러 장치가 데이터를 주고받는 통로. 현대 컴퓨터는 버스 하나가 아니라 여러 통신 경로 사용
- 주고받는 정보

  | 구분        | 의미        | I/O 제어기 예                         |
  | ----------- | ----------- | ------------------------------------- |
  | **Address** | 접근할 위치 | Control / Status / Data Register 주소 |
  | **Data**    | 실제 데이터 | 출력 데이터, 입력 데이터              |
  | **Control** | 수행할 동작 | Read, Write, Enable                   |
  - 제어기는 필요하면 Interrupt로 CPU에 상태 변화 알림

- 현대 시스템 연결 예: CPU ↔ 메모리는 Memory Interface, CPU(SoC) ↔ I/O 제어기는 PCI Express, I/O 제어기 ↔ 주변장치는 USB·SATA

## 3.5.3 장치 간 데이터 전송과 Handshaking

- **Handshaking**: 두 장치가 제어 신호·상태 정보를 주고받아 언제 보내고 언제 받을지 맞추는 과정. 예: 프린터가 Ready일 때만 데이터 보냄
  - 목적: 수신 준비 확인, 정상 전달 확인, 속도 다른 장치 간 전송 시점 조정, 데이터 손실·오류 방지
- I/O 제어기와 프린터의 Handshaking: 1. 제어기가 프린터 상태 확인 → 2. Ready면 출력 데이터 전달 → 3. 출력 시작 명령 → 4. 프린터 처리 중 Busy → 5. 끝나면 Ready/Complete로 갱신
  - CPU에 완료 알리는 방법은 3.5.5 (Polling, Interrupt)

## 3.5.4 직렬·병렬 통신과 I/O 인터페이스

![병렬 통신과 직렬 통신](/static/images/computer-systems-ch3-computer-organization/parallel-serial.svg)

- **병렬 통신(Parallel)**: 여러 전송선으로 여러 비트를 동시에 보냄. 예: 선 8개면 한 번에 8비트
  - 그림에서: 위쪽, 선 4개로 1010을 T 만에
  - 예전 병렬 프린터 포트, 일부 내부 메모리 인터페이스
- **직렬 통신(Serial)**: 하나의 경로(Lane)로 비트를 시간 순서대로 보냄
  - 그림에서: 아래쪽, Lane 하나로 1010을 4T 동안
  - 대표: USB, SATA, PCI Express, Thunderbolt
- **Skew**: 병렬 통신에서 동시에 출발한 비트들이 서로 다른 시점에 도착하는 현상
  - 원인: 전송선 길이 차이, 선마다 전기적 특성 차이, 주변 신호 간섭, 송·수신 회로 지연 차이
  - 문제: 다 도착하기 전에 읽으면 잘못된 값. 고속일수록 한 비트 읽는 간격이 짧아져서 작은 차이도 오류
- 병렬 vs 직렬

  | 구분           | 병렬 통신                                 | 직렬 통신                           |
  | -------------- | ----------------------------------------- | ----------------------------------- |
  | 전송 방식      | 여러 선으로 여러 비트 동시에              | Lane 하나로 비트를 순서대로         |
  | 전송선 수·배선 | 많음, 복잡                                | 적음, 단순                          |
  | 장점           | 같은 신호 속도면 여러 비트 동시 전송      | 높은 신호 속도, 배선 단순           |
  | 주요 문제      | **Skew**, 신호 간섭(Crosstalk), 배선 복잡 | 고속 신호 복원, 인코딩, 동기화 필요 |
  | 거리·고속화    | 길어지거나 빨라질수록 동기화 어려움       | 고속·장거리에 유리                  |
  | 현대 활용      | 메모리 인터페이스 등 짧은 내부 연결       | USB, SATA, PCIe, Thunderbolt        |
  - 이론상 같은 신호 속도면 병렬이 유리하지만, 실제 고속 시스템은 신호 무결성·확장성 때문에 고속 직렬이 대세

- **Lane**: 독립적인 직렬 통신 경로 하나. 여러 개를 같이 써서 대역폭 확장
  - 예: PCIe x1 / x4 / x16 = Lane 1 / 4 / 16개
  - PCIe x4는 4비트 병렬 버스가 아니라 직렬 Lane 4개를 묶은 링크. 각 Lane 안에서는 직렬
- **Data Rate**: 단위 시간 동안 통신 경로로 전송되는 데이터 양. 단위 bps (Kbps = 10³, Mbps = 10⁶, Gbps = 10⁹ bps)
  - **Maximum Data Rate**: 인터페이스 규격의 이론상 최대 전송률
  - **Throughput**: 실제 시스템에서 달성되는 전송률. **Maximum Data Rate ≥ Throughput**
  - Throughput이 낮아지는 이유: 프로토콜 오버헤드(패킷 헤더·오류 검출 정보), 저장장치 성능, CPU·OS 처리 부담, 공유 자원·대역폭 경쟁, 케이블·포트 규격, 작은 파일 반복 처리
- 표준 I/O 인터페이스: 예전엔 장치마다 포트·연결 방식이 달라서 표준화함
  - 장점: 서로 다른 장치를 공통 규격으로 연결, 추가·교체 쉬움, 호환성 향상
- **USB(Universal Serial Bus)**: 주변장치 연결용 대표 직렬 인터페이스
  - **Host 중심**: PC(Host)가 통신 관리, 장치가 마음대로 통신 시작 못 함
  - **Plug and Play**: 꽂으면 OS가 자동 인식·설정
  - **Hot Plugging**: 전원 안 끄고 연결·분리, 전력 공급도 함
  - 속도: USB 2.0 480 Mbps, USB 3.2 Gen 1 5 Gbps, Gen 2 10 Gbps
- **FireWire(IEEE 1394)**: 고속 실시간 전송용 직렬 인터페이스
  - **Peer-to-Peer**: 장치끼리 직접 통신. 예: 캠코더 ↔ 외장 저장장치
  - 영상·음성처럼 지속적이고 예측 가능한 전송이 중요한 멀티미디어용. FireWire 400 / 800 = 400 / 800 Mbps
  - 지금은 USB·Thunderbolt에 밀려 거의 안 씀
- USB vs FireWire

  | 구분           | USB                            | FireWire                      |
  | -------------- | ------------------------------ | ----------------------------- |
  | 기본 통신 방식 | 직렬                           | 직렬                          |
  | 통신 관리      | **Host 중심**                  | **Peer-to-Peer**              |
  | 대표 활용      | 키보드, 마우스, 저장장치, 웹캠 | 예전 캠코더, 전문 오디오 장비 |
  | 핵심 특징      | 범용성, 호환성, Plug and Play  | 실시간 멀티미디어 전송        |
  - 핵심 차이는 속도보다 **누가 통신을 시작하고 관리하냐**

## 3.5.5 Polling과 Interrupt

![Polling과 Interrupt 비교](/static/images/computer-systems-ch3-computer-organization/polling-interrupt.svg)

- 필요한 이유: CPU는 빠른데 I/O 장치는 느리고 완료 시간도 일정하지 않음 → CPU가 완료를 알 방법 필요
- **Polling**: CPU가 제어기 Status Register를 반복해서 읽으며 상태 확인. "Ready야?" 계속 물어봄
  - 그림에서: 위쪽 노란 Status? Busy 반복
  - 과정: CPU가 작업 요청 → Status 읽기 → Busy면 다시 읽기 → Ready면 다음 작업
  - 구조 단순, 짧고 예측 가능한 작업엔 괜찮음. 장치가 느릴수록 확인하느라 CPU 시간 낭비
- **Interrupt**: 작업이 끝나면 I/O 장치(제어기)가 CPU에 인터럽트 요청을 보냄. "끝났어"
  - 그림에서: 아래쪽 빨간 화살표
  - 과정: CPU가 작업 요청 → 장치 작업하는 동안 CPU는 다른 작업 → 완료되면 제어기가 인터럽트 요청 → CPU가 하던 일 잠시 멈추고 인터럽트 처리 루틴 실행 → 이전 작업으로 복귀
  - CPU가 계속 확인 안 해도 됨, 완료 시간이 길거나 예측 어려울 때 적합. 인터럽트 처리 자체 비용은 있음
- Polling vs Interrupt

  | 구분        | Polling                     | Interrupt                          |
  | ----------- | --------------------------- | ---------------------------------- |
  | 완료 확인   | CPU가 장치 상태를 반복 확인 | 장치가 CPU에 완료를 알림           |
  | CPU 대기    | 반복 확인에 CPU 시간 사용   | 다른 작업 가능                     |
  | 장점        | 구조 단순                   | CPU 활용 효율 높음                 |
  | 단점        | 장치 느리면 CPU 시간 낭비   | 인터럽트 처리 비용                 |
  | 적합한 상황 | 짧고 단순한 I/O             | 완료 시간이 길거나 예측 어려운 I/O |
  - Interrupt를 써도 대량 데이터 전송 자체는 CPU가 직접 해야 하는 문제 남음 → 3.5.6 DMA
  - Handshaking = 전송 상대끼리 속도·타이밍 맞추기 / Polling·Interrupt = CPU가 I/O 상태·완료 확인하기

- 프린터 인쇄 전체 흐름
  1. 사용자가 응용 프로그램에서 인쇄 요청
  2. OS의 **Print Spooler**가 출력 작업을 **Spool Queue**에 저장
  3. OS가 Queue의 첫 작업 선택
  4. CPU가 Printer Driver 실행, 제어기 Status Register 확인
  5. 준비 상태면 출력 데이터를 Data Register / Buffer에 기록
  6. Control Register에 출력 시작 명령 기록
  7. 제어기가 프린터에 데이터·명령 전달, 프린터 출력
  8. 출력 끝나면 제어기가 Status Register 갱신 + Interrupt 발생
  9. OS가 완료 처리, Spool Queue 다음 작업 시작

## 3.5.6 DMA(Direct Memory Access)

![CPU 직접 전송과 DMA 전송](/static/images/computer-systems-ch3-computer-organization/dma-transfer.svg)

- DMA 없이 대용량 전송(CPU 직접 전송): 제어기가 데이터 일부 준비 → CPU가 제어기에서 읽기 → CPU가 메모리에 기록 → 끝날 때까지 반복
  - 그림에서: 왼쪽, 빨간 CPU가 모든 데이터를 거쳐감
  - 문제: 데이터 많을수록 CPU 개입 증가, 데이터 옮기는 데 명령 실행 시간 사용, 다른 프로그램 처리 시간 감소
- **DMA**: CPU는 전송 조건만 설정하고, **DMA Controller**가 I/O 장치 ↔ 메모리 대량 데이터를 직접 옮기는 방식. 예: SSD 파일을 메모리로 읽는 동안 CPU는 다른 일
  - 그림에서: 오른쪽, 초록 DMA 경로
  - 목적: CPU 반복 개입 감소, 전송 중 CPU가 다른 작업, 저장장치·네트워크 대량 전송 효율 향상
  - 활용: SSD·디스크 대용량 읽기·쓰기, 네트워크 패킷 송수신, 고해상도 영상·오디오, GPU ↔ 메모리
  - 현대엔 DMA 기능이 I/O 제어기 안에 통합된 경우 많음
- DMA 동작 과정 (SSD → 메모리)
  1. CPU: I/O·DMA 전송 설정
  2. Storage Controller / DMA: 저장장치에서 데이터 읽기
  3. DMA: 메모리로 데이터 직접 전송
  4. CPU: 그동안 다른 명령 실행
  5. 전송 완료: 보통 Interrupt로 CPU에 알림
  6. CPU: 메모리에 저장된 데이터 사용
- CPU가 설정하는 정보: **시작 메모리 주소**(데이터 놓을·읽을 위치), **전송 크기**(바이트·블록 수), **전송 방향**(장치 → 메모리 / 메모리 → 장치), **제어 정보**(전송 시작, 완료 통지 방식)
- CPU 직접 전송 vs DMA

  | 구분         | CPU 직접 전송    | DMA 전송                       |
  | ------------ | ---------------- | ------------------------------ |
  | 데이터 이동  | CPU가 계속 관여  | DMA가 수행                     |
  | CPU 역할     | 하나하나 읽고 씀 | 전송 설정 + 완료 후 처리       |
  | 대량 전송 시 | CPU 부담 증가    | CPU는 다른 명령 동시 수행 가능 |

## 3.5.7 시스템 자원 공유와 DMA의 한계

- CPU와 DMA 둘 다 주기억장치에 접근 → DMA 전송 중에도 CPU가 명령어·데이터 접근 가능, 인터커넥트·메모리 대역폭 공유 → 동시에 요청하면 순서 조정 필요
- **Bus Arbitration**: 여러 장치가 같은 통신 자원을 동시에 쓰려 할 때 사용 순서 정하는 과정. 예: CPU와 DMA가 동시에 메모리 접근 요청

  | 기준      | 설명                           |
  | --------- | ------------------------------ |
  | 우선순위  | 중요한 장치·긴급한 요청 먼저   |
  | 순환 방식 | 요청한 장치에 차례대로 기회    |
  | 공정성    | 특정 장치가 계속 기다리지 않게 |
  | 성능      | 전체 시스템 처리량 높이는 쪽   |

- DMA 장점: CPU의 반복 데이터 이동 감소, 대용량 I/O에서 CPU 부담 감소, 전송 중 CPU가 다른 명령 수행, 저장장치·네트워크·그래픽 대량 전송에 효과적
- DMA 한계: DMA도 메모리·인터커넥트 사용, 대량 DMA면 CPU와 메모리 접근 경쟁, 설정·완료 처리 오버헤드, 아주 작은 전송은 설정 비용이 더 클 수 있음
  - DMA는 CPU의 이동 부담을 줄일 뿐, 메모리·인터커넥트 대역폭을 늘려주진 않음
- **폰 노이만 병목(von Neumann bottleneck)**: CPU와 메모리 사이 데이터 전달 능력이 제한돼서 전체 성능을 막는 현상. 예: CPU가 빨라도 메모리에서 데이터가 늦게 오면 대기
  - 원인: CPU가 명령어와 데이터를 둘 다 메모리에서 가져와 처리하는 구조
  - DMA 쓴다고 폰 노이만 병목이 없어지진 않음

  | 구분      | DMA                        | 폰 노이만 병목                 |
  | --------- | -------------------------- | ------------------------------ |
  | 핵심 문제 | CPU의 I/O 데이터 이동 부담 | CPU ↔ 메모리 간 전송 성능 제한 |
  | 주요 대상 | I/O 장치 ↔ 메모리          | CPU ↔ 메모리                   |
  | 해결·완화 | DMA로 직접 데이터 전송     | 캐시, 메모리 계층, Prefetching |
  | 결과      | CPU 개입 감소              | CPU의 메모리 대기 감소         |
