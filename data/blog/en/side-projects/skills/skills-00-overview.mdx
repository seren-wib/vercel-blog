> Part 0 of the series. What a [skill](glossary:skill) is, why I moved rules out of the [instruction files](glossary:instruction-file) instead of keeping them all there, and how I manage them. Each [skill](glossary:skill) gets its own post in parts 1 to 11.

## 0. Introduction

I use three agents, [Claude Code](glossary:claude-code), [Codex](glossary:codex) and [Antigravity](glossary:antigravity), on both Windows and a Mac. All of their settings live in one personal repo called [dotfiles](glossary:dotfiles). Because I kept adding rules to the [instruction files](glossary:instruction-file) that the agents read in every conversation, each session was paying input [tokens](glossary:token) for rules about jobs it would not do that day. So I moved the rules that matter for only one kind of task out.

In restaurant terms, the [instruction file](glossary:instruction-file) is a note stuck on the kitchen wall and a [skill](glossary:skill) is a recipe book in a drawer. The cook sees the note the whole time, so it has to be short; the recipe book is pulled out only for that dish, so it can be long. The label on each drawer tells you which dish the recipe book is for. So the wall note is the [instruction file](glossary:instruction-file), the recipe book in the drawer is the [skill](glossary:skill), the label is the `description`, and the cook is the agent.

The repo now holds 13 [skills](glossary:skill), and the series covers 11 of them, one per post. The repo is private, so this series summarizes its rules and quotes them briefly instead of linking. The sources are records, not memory: git commits to the [skill](glossary:skill) folders, the memory change log (`memory/log/`) and the work records (`worklog/`). Where no record gives a reason for a decision, I wrote "no record". Numbers that change are collected with their date in the table in section 6.

## 1. The structure of a skill

![Fixed input every session vs files opened only when needed](/static/images/skills-00-overview/context-loading.svg)

_Left: input that goes into every session. Right: files read only when the task matches_

- **[Instruction file](glossary:instruction-file)**: a file loaded whole into the [context window](glossary:context-window) when a session starts. [Claude Code](glossary:claude-code) reads `CLAUDE.md`, [Codex](glossary:codex) reads `AGENTS.md`, [Antigravity](glossary:antigravity) reads `GEMINI.md`.
- **[Skill](glossary:skill)**: one folder with one `SKILL.md`. The [frontmatter](glossary:frontmatter) at the top holds `name` and `description`, and the body below is the rules. Scripts or sub-documents can sit in the same folder.

Every session, [Claude Code](glossary:claude-code) puts only each [skill](glossary:skill)'s `name` and `description` into a list. It loads the body through the [Skill](glossary:skill) tool when the current task matches the `description`. Sub-files (`setup.md`, `sites/*.md` and the like) are opened only when the body points to them ("for this case, open this file"). The fixed cost is just `name` and `description`; the heavy parts are read step by step when needed.

```text
~/.claude/skills/blog-post/
└── SKILL.md      # ---
                  # name: blog-post
                  # description: (abridged) Rules for publishing to the blog ... Use when uploading a note to the blog, ...
                  # ---
                  # (body: the rules)
```

## 2. Why rules left the instruction files

The problem was **input [tokens](glossary:token) paid as a fixed cost in every session**. The [instruction file](glossary:instruction-file), the global memory index, the [skill](glossary:skill) list, the [MCP](glossary:mcp) tool list and [hook](glossary:hook) messages all go into the model input each time a conversation starts. If the blog rules sit in the [instruction file](glossary:instruction-file), a session pays for them even when it writes no blog post. Today 12 sessions started at once just to write this series. A fixed input is multiplied by the number of sessions.

The records show this order.

The rule added to the instructions on 2026-10-15 is still unchanged. It lists what is loaded every session and makes the agent ask whether something is needed in every session before adding it. If not, it goes somewhere that opens only when needed, and the rule names three such places: memory note bodies, folder-scoped [MCP](glossary:mcp) servers and [skills](glossary:skill).

The 2026-11-13 commit message states the reason for [skills](glossary:skill) directly: rules and gotchas that matter for only one kind of task load when that task comes up, instead of sitting in global memory.

![Instruction file size vs total SKILL.md size](/static/images/skills-00-overview/instructions-vs-skills.svg)

_Blue: the Codex instruction file (persona, shared, agent part and memory index all included). Green: all SKILL.md files combined_

The result shows in the sizes. Measured on [Codex](glossary:codex)'s `AGENTS.md`, which is assembled into one file including the persona, the [instruction file](glossary:instruction-file) has stayed between 21 and 24 KB since 2026-10-15. Over the same period the `SKILL.md` total grew from 7.0 KB to 86.2 KB. The rules that were added piled up in [skills](glossary:skill) instead of the fixed input. The per-session cost on the [skill](glossary:skill) side is the 13 `description` lines, 5,765 B in total.

These numbers are bytes. [Tokens](glossary:token) were measured only once: on 2026-11-20, [Claude Code](glossary:claude-code)'s `/context` showed about 74k of a 128.5k-[token](glossary:token) [context window](glossary:context-window) as fixed input. Those 74k include the system prompt and tool definitions, and there is no record measuring the [instruction file](glossary:instruction-file)'s share alone.

## 3. Where agents/ ends and skills begin

The source files in `agents/` go through `memory-sync.js build` into the assembled [instruction files](glossary:instruction-file), while [skills](glossary:skill) are linked in separately from `claude/skills/<name>/`.

![agents/ sources, assembled instruction files, skill folders](/static/images/skills-00-overview/agents-and-skills.svg)

_Instruction files are assembled from agents/, skill folders are linked in with symlinks_

- **Sources**: `agents/persona.md` (voice), `agents/shared.md` (rules shared by all three agents), `agents/claude.md`, `codex.md` and `gemini.md` (per-agent parts), and the global memory index.
- **Assembly**: `node ~/.claude/hooks/memory-sync.js build` joins these four in order into `claude/CLAUDE.md`, `codex/AGENTS.md` and `gemini/GEMINI.md`. Editing the output by hand is overwritten by the next build.
- **[Skills](glossary:skill)**: they live in `claude/skills/<name>/` and one line in `links.txt` [symlinks](glossary:symbolic-link) each to `~/.claude/skills/<name>`. `install.ps1` on Windows and `install.sh` on the Mac read the same `links.txt`.

`agents/shared.md` decides where a rule goes. A rule to follow in every session gets one line in `agents/`, a format used only for a particular job becomes a [skill](glossary:skill), and a rule that holds only in one folder goes into that folder's `CLAUDE.md`.

In this setup the [skill](glossary:skill) folders are linked only into `~/.claude/skills`. [Codex](glossary:codex) and [Antigravity](glossary:antigravity) do not get the [skill](glossary:skill) list automatically, so the shared instructions in `agents/shared.md` have one line listing each [skill](glossary:skill)'s name with a short description. From that line, the two agents open `~/.claude/skills/<name>/SKILL.md` by path when they do that task. There is one copy of each [skill](glossary:skill) file, and all three agents follow the same rules.

## 4. Making and editing a skill

1. Create `~/dotfiles/claude/skills/<name>/SKILL.md`. The `description` says both what the [skill](glossary:skill) does and when to use it ("Use when ..."), because the agent decides whether to open the [skill](glossary:skill) from that sentence alone.
2. Add one line to `links.txt`, the name to the `README.md` table and an entry to the [skill](glossary:skill) list in `agents/shared.md`, then reassemble the instructions.
3. Keep only always-on rules in `SKILL.md`. Situational procedures, setup steps and per-site notes go to sub-files that the body points to. `session-flow` (2026-11-20, 29,962 B → 7,908 B) and `project-docs` (same day, `setup.md` split out) were divided this way.
4. When and why a rule changed stays in commit messages and `memory/log/`. That is where this series got its sources.

There are 67 commits to the [skill](glossary:skill) folders up to 2026-11-28. Of those, 33 are in `session-flow` alone. The procedure for opening and closing sessions kept changing as I used it. The story is in [part 6](/en/blog/side-projects/skills/skills-06-session-flow/).
