## 2. 토큰 갱신: 한 번만, 다 같이 기다리기

액세스 토큰은 30분이면 만료된다([3편](/kr/blog/side-projects/coffee-shop/coffee-shop-03-backend-foundation/#4-회원과-인증83)). 만료된 채로 화면이 API를 세 개 동시에 부르면 셋 다 401을 받는다. 셋이 각자 리프레시를 보내면 리프레시도 세 번 나간다.

은행 창구로 치면, 번호표가 만료된 손님 세 명이 동시에 새 번호표를 뽑으러 가는 대신 한 명만 다녀오고 나머지는 그 번호표를 같이 쓰는 방식이다.

![토큰 갱신 다이어그램. 요청 A, B, C가 동시에 401을 받는다. 첫 번째가 refreshAccess()로 POST /api/auth/token/refresh/를 보내고 그 Promise를 refreshing 변수에 둔다. B와 C는 같은 Promise를 기다린다. 새 액세스 토큰이 오면 셋 다 _retried 표시를 달고 한 번씩 다시 보낸다. 리프레시가 실패하면 토큰을 지우고 /login?next=로 보낸다](/static/images/coffee-shop-05-frontend/token-refresh.svg)

번호표는 액세스 토큰, 한 명만 다녀오는 건 진행 중인 리프레시 Promise 하나를 공유하는 것이다. 이 비유는 여기까지만 쓴다.

`api/client.js`의 응답 인터셉터가 이렇게 한다.

- 401이고, 이미 다시 보낸 요청(`_retried`)이 아니고, 로그인·리프레시 요청 자체가 아니면 갱신을 시도한다
- 진행 중인 갱신이 있으면 그 Promise를 같이 기다리고, 없으면 새로 만든다. 끝나면 비운다
- 새 토큰으로 원래 요청을 **한 번만** 다시 보낸다. `_retried` 표시가 무한 반복을 막는다
- 리프레시 토큰이 없거나 갱신이 실패하면 토큰을 지우고 `/login?next=<지금 경로>`로 보낸다

토큰 키를 읽고 쓰는 파일도 `auth/tokenStore.js` 하나뿐이다. 토큰 안 `role` 값으로는 관리자 메뉴를 보여 줄지만 정한다. 실제 차단은 서버가 관리자 요청마다 DB의 역할을 다시 보고 403을 내는 것이다(NFR-10).

## 3. 주문과 결제 화면

결제 화면이 제일 까다로웠다. 결제창은 브라우저를 다른 페이지로 보냈다가 돌려보내고, 사람이 중간에 창을 닫을 수도 있다.

![주문/결제 화면 흐름 다이어그램. 첫 클릭은 POST /api/orders/로 주문을 만들고 바로 결제를 시작해 토스 결제창을 연다. 두 번째 클릭부터는 이미 만든 주문으로 결제만 다시 연다. 결제창이 successUrl로 돌아오면 /checkout/result가 confirm을 한 번만 보낸다. PG_ERROR면 다시 확인 버튼, PAYMENT_MISMATCH면 실패 안내. 창을 닫으면 requestPayment()가 USER_CANCEL로 실패해 주문/결제 화면에 취소 안내가 뜨고, failUrl로 돌아온 실패는 결과 화면이 fail API로 기록한다. 주문은 상세 화면에서 다시 결제할 수 있다](/static/images/coffee-shop-05-frontend/checkout-flow.svg)

- **첫 클릭은 주문 생성 + 결제창, 두 번째부터는 결제만.** 결제창을 닫고 다시 누를 때마다 주문이 새로 생기면 재고가 그만큼 잠긴다. 이미 만든 주문이 있으면 결제만 다시 연다(#115).
- **결제 확인은 한 번만.** `/checkout/result`는 `useRef`로 확인 요청을 한 번만 보낸다. React StrictMode는 개발 모드에서 effect를 두 번 돌리는데, 그때도 한 번이다. 서버의 확인 API가 어차피 멱등이라 두 번 가도 망가지진 않지만, 화면에 결과가 두 번 깜빡이지 않게 막았다.
- **느린 PG와 실패를 구분한다.** 502 `PG_ERROR`는 "결제사 응답이 늦다, 다시 확인" 버튼을, 409 `PAYMENT_MISMATCH`는 실패 안내를 보여 준다.
- **창 닫기는 오류로 받는다.** 4편 스파이크 5단계에서 본 대로 창을 닫으면 `failUrl`로 가지 않는다. 그래서 `lib/pay.js`가 `requestPayment()`의 `USER_CANCEL` 오류를 직접 받아 주문/결제 화면에 "결제를 취소했습니다."를 띄운다. 결제창이 `failUrl`로 돌려보낸 실패만 결과 화면이 실패 기록 API(`/api/payments/fail/`)로 남긴다.

### 버튼은 서버가 정한다

내 주문 상세의 버튼(취소, 취소 요청, 다시 결제)은 서버 응답의 `can_*` 값으로 그린다. 관리자 주문 상세의 버튼(준비, 발송, 배송 완료, 취소 승인·반려)도 서버의 `allowed_actions`에 있는 것만 보인다(#119).

화면이 상태 표를 따로 들고 있으면, 백엔드가 전환 규칙을 고칠 때 화면이 틀린 버튼을 보여 준다. 규칙을 서버 한 곳에 두고 화면은 결과만 받으면 그 어긋남이 생길 자리가 없다. 버튼이 보여도 서버가 다시 조건부 UPDATE로 확인하니, 오래된 화면에서 누른 버튼은 409로 끝난다.

## 4. 결제 끔 상태에서의 확인

시연용 토스 테스트 키가 아직 없어서 운영 서버는 결제가 꺼져 있다(6편). 이 상태로 #115를 확인했다. 결제를 누르면 503 `PAYMENTS_DISABLED` 안내가 뜨고, 주문은 상세 화면에서 나중에 결제할 수 있는 상태로 남는다.

그래서 **실제 토스 결제창은 이 프론트엔드에서 한 번도 열어 보지 않았다.** 결제 확인, 실패, 재결제 흐름은 vitest의 가짜 응답으로만 확인했다. 결제창 응답 자체는 4편 스파이크(별도 페이지, SDK 2.10.0)로 쟀지만, 이 화면과 붙여서 돈 적은 없다.
