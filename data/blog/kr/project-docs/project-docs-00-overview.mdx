> 시리즈 0편. 템플릿이 무엇인지, 왜 만들었는지, 어떻게 쓰는지를 한 번에 정리한다. 각 결정의 경위는 1~4편에 있다.

## 0. 들어가며

나는 새 프로젝트를 시작하면 문서 여섯 개를 같은 양식으로 쓴다. 계획서, 요구사항 명세서, 설계 명세서, 테스트 계획서, 설치 계획서, 유지보수 계획서다. 처음부터 이랬던 건 아니다. 반년 전 이 블로그를 만들 때는 DB 스키마, API 명세, 화면 구조 문서만 있었고, 그걸로 충분하다고 생각했다.

이 연재는 그 사이에 무슨 일이 있었는지를 다시 찾아 적은 것이다. 근거는 기억이 아니라 기록이다. 규칙 파일의 git 커밋, 프로젝트마다 남긴 worklog, 메모리 변경 이력, 그리고 결정을 내린 날의 세션 기록이다. 이유가 어디에도 적혀 있지 않은 결정은 "기록 없음"으로 남겼다.

글은 두 층으로 읽힌다. 절마다 비유 한두 문장과 다이어그램으로 시작하고, 그다음엔 정식 용어와 실제 경로, 숫자로 넘어간다. 바뀌는 숫자는 "숫자로 보기" 표에 날짜와 함께 모았다.

## 1. 템플릿이 뭔가

비유하면 집 짓는 순서마다 서류 한 장씩 있는 셈이다. 무엇을 지을지 정하는 계획서, 집주인이 원하는 걸 적은 요구서, 도면, 검사 계획, 입주 절차, 수리 규칙.

## 2. 왜 만들었나

비유하면 공책을 과목마다 다르게 쓰다가, 공책이 늘수록 어디에 뭘 적었는지 못 찾게 돼서 한 가지 양식으로 맞춘 것이다.

용어로 말하면 네 가지 문제가 있었고, 각각이 지금 양식의 한 부분이 됐다.

| 문제                                                      | 지금 양식에서 답                                          | 편                                                             |
| --------------------------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------- |
| 개발할수록 필요한 문서가 늘었다                           | 단계마다 문서 하나, 새 프로젝트는 양식부터 복사           | [1편](/kr/blog/project-docs/project-docs-01-growing-docs/)     |
| 무엇을 왜 정했는지, 무엇을 버렸는지가 흩어졌다            | SDD·SPMP·SRS 안의 날짜 붙은 결정 기록                     | [2편](/kr/blog/project-docs/project-docs-02-decision-records/) |
| 문서를 쓸 때마다 절 구성과 이름이 달라질 수 있었다        | IEEE/ISO 표준의 절 구성, 파일 54개짜리 양식               | [3편](/kr/blog/project-docs/project-docs-03-standards/)        |
| 두 컴퓨터, 사람과 에이전트, 레포와 Google Docs가 어긋났다 | 레포가 원본, Google Docs는 push마다 덮어쓰는 한 방향 사본 | [4편](/kr/blog/project-docs/project-docs-04-docs-sync/)        |

## 3. 어떻게 쓰나

비유하면 단계마다 검사 도장을 받아야 다음 공정으로 넘어가는 공장이다.

용어로는 **단계 게이트(stage gate)**다. 각 단계 문서가 확정돼야 다음 단계를 시작하고, 코드는 SRS와 SDD가 확정된 뒤에야 쓴다. 구현은 TDD로 한다.

1. 새 프로젝트는 쓸 문서부터 고른다. 작은 도구나 정적 사이트는 계획서와 SRS를 한 문서로 합치고 API·DB 절에 "해당 없음"을 쓴다. 로그인, 결제, DB가 있으면 여섯 개를 다 쓴다.
2. 요구사항은 인터뷰로 받는다. 개인 프로젝트에서도 내가 의뢰인 역할을 하고 에이전트가 질문한다.
3. 양식을 복사한 뒤 첫 글자를 쓴다. 절 이름과 번호, 표 열이 프로젝트마다 같아진다.

파일은 레포에 이렇게 놓인다.

```text
docs/specs/
├── README.md            # 파일 전체 목록과 ID 범위
├── spmp/                # 1-identification.md … 8-decisions.md
├── srs/                 # 3-functional/ 는 영역마다 파일 하나
├── sdd/                 # 4-components/, 5-modules/ 는 부품·모듈마다 파일 하나
├── stp/
├── sip/
└── smp/
```

요구사항에는 번호가 붙는다(`FR-12`). 테스트 이름, PR 본문, SDD의 기능 소절이 이 번호로 서로를 가리킨다. 요구사항 하나를 찾을 때는 문서를 다 읽지 않고 `grep -rn "FR-12" docs/specs`로 그 줄만 연다.

## 4. 지금 쓰는 곳

이 양식은 2026-11-16 이후 시작하거나 옮겨 온 프로젝트에 쓴다. 그 전에 시작한 프로젝트는 원래 구조를 그대로 둔다. 숫자는 맨 아래 표에 있다.

- **coffee-shop**: 소프트웨어공학 팀 과제([커피샵 연재](/kr/blog/coffee-shop/coffee-shop-00-overview/)). 평면 구조 문서 41개를 이 양식으로 처음 옮긴 프로젝트다. 경위는 [1편](/kr/blog/project-docs/project-docs-01-growing-docs/)에 있다.
- **design-system**, **open-calls**: 2026-11-19부터 같은 양식을 쓰는 개인 프로젝트(비공개 레포).
- **account.stairno.com**: 양식의 본보기가 된 프로젝트. 다만 본보기가 된 건 이 양식보다 먼저 쓴 문서 넷이라서, 지금도 예전 구조다.
