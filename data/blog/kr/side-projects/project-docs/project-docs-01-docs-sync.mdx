> 시리즈 1편. 템플릿 전체 그림은 [Project Docs 0](/kr/blog/side-projects/project-docs/project-docs-00-overview/)에 있다.

## 0. 들어가며

계획서·[SRS](glossary:srs)·[SDD](glossary:sdd) 같은 단계 문서는 팀원과 교수님이 [Google Docs](glossary:google-docs)로 읽고, 코드와 테스트가 가리키는 원본은 [Repository](glossary:repository)에 있어야 한다. 손으로 맞추면 언제든 갈라지므로, 원본을 하나로 정하고 사본은 기계가 만들게 했다.

식당으로 비유하면 처음엔 홀 게시판에 메뉴를 직접 쓰고 공책엔 메모만 했다. 그러다 주방 레시피북만 고치고, 복사 담당이 즉석 출입증으로 게시판의 같은 자리에 새 사본을 붙이게 바꿨다. 레시피북은 [Single source of truth](glossary:single-source-of-truth)인 레포의 [Markdown](glossary:markdown), 복사 담당은 [GitHub Actions](glossary:github-actions)의 [Workflow](glossary:workflow), 즉석 출입증은 [OIDC](glossary:oidc)와 [Workload Identity Federation](glossary:workload-identity-federation)이 내주는 [Short-lived token](glossary:short-lived-token), 게시판은 Google Docs다.

한 일: 10월 17일 Google Docs 원본으로 시작해 하루 만에 레포 Markdown으로 뒤집었고, 11월 16일 절마다 파일 하나로 쪼개 커밋했다. 11월 17일 [Coffee Shop](/kr/blog/side-projects/coffee-shop/coffee-shop-00-overview/)에 `main`으로 [Push](glossary:push)될 때마다 문서 6개를 같은 Doc에 덮어쓰는 Workflow를 처음 붙였다. 이 글은 그 흐름과 첫 실행 뒤 고친 것까지 다룬다.

## 1. Google Docs에서 레포로 원본 옮기기

2026-10-17 절차에서는 Google Docs가 원본이었다. 레포에는 README, CONTRIBUTING, 짧은 노트만 두고 계획서·SRS·SDD는 전부 Google Docs에 썼다.

다음 날 10-18 순서를 뒤집었다. 원본은 로컬 Markdown이고, Google Docs는 단계가 끝날 때나 남에게 보여 주기 전에 한 번 맞춘다. 이유는 규칙 파일에 괄호로 남아 있다. account.stairno.com에서 [Pull request](glossary:pull-request)마다 Google Docs를 맞추니 너무 느렸다. 에이전트가 쓰는 Google Docs 커넥터는 문서 안 위치를 지정해 고치는 방식뿐이라, 고칠 때마다 문서 하나에 수백 KB를 읽어야 했다. 이때 문서 넷을 `docs/specs/`에 두되 `.gitignore`로 커밋하지 않았는데, 이유는 기록에 없다.

## 2. 절마다 파일 하나로

2026-11-16 새벽, 커밋하지 않던 단일 파일 넷을 커밋하는 절별 파일로 바꿨다. 문서를 코드처럼 다루는 [Docs as code](glossary:docs-as-code)다. 이유는 둘이다.

- **두 컴퓨터**: 윈도우 데스크톱과 맥북을 번갈아 쓴다. 문서가 커밋되지 않으면 한쪽에서 고친 걸 다른 쪽이 모른다. 커밋하면 [두 컴퓨터가 Git으로 맞추는 구조](/kr/blog/side-projects/devblog/devblog-02-agent-environment/#7-두-컴퓨터-세-에이전트)를 문서도 그대로 탄다.
- **에이전트가 읽는 양**: 문서가 파일 하나면 한 절을 보려고 전체를 읽는다. 절마다 파일이면 `docs/specs/README.md`에서 파일 이름을 보고 필요한 파일만 연다.

보안도 따졌다. private 레포는 계정이 나 하나라서 그대로 커밋한다. public 레포에서는 아직 안 고친 보안 구멍, 관리자 주소, 내부 호스트, 운영 절차, 의뢰인이 비공개를 요청한 내용을 빼고 그 자리에 `(Google Docs에만 있음)`이라고 적는다. 비밀값과 개인정보는 어느 레포에도 넣지 않는다.

## 3. 동기화 방향 정하기

![동기화 방향을 정한 이유: 버린 안은 Google Docs 먼저, 고른 안은 repo 원본에서 한 방향 자동](/static/images/project-docs-04-docs-sync/why-one-way.svg)

_동기화 방향을 정한 이유: 버린 안은 Google Docs 먼저, 고른 안은 repo 원본에서 한 방향 자동_

같은 날 Google Docs를 먼저 쓰고 레포로 옮기는 안도 검토했다. 맥과 윈도우 사이 동기화만 보면 자연스러워 보였다. 하지만 네 가지 이유로 버리고 [One-way sync](glossary:one-way-sync)를 골랐다.

| 버린 이유                                 | 내용                                                                                 |
| ----------------------------------------- | ------------------------------------------------------------------------------------ |
| 통째로 읽어야 한다                        | 에이전트가 Doc 하나를 다 읽어야 한 절을 본다                                         |
| 위치 계산 API                             | Docs [API](glossary:api)는 문서 안 위치(index)로 고쳐서 느리고 쉽게 깨진다           |
| [PR](glossary:pull-request) 규칙이 깨진다 | 코드와 그 코드의 설계 변경을 한 [Pull request](glossary:pull-request)로 묶을 수 없다 |
| 어긋남이 방향만 바뀐다                    | 사람이 옮기는 한, 어느 쪽이 먼저든 언젠가 어긋난다                                   |

대가도 셋이다. 인증 설정이 필요하고, 덮어쓸 때마다 Google Docs 댓글의 위치가 풀리고, 표 서식이 단순해진다. 그래서 규칙이 붙었다. 사람은 Google Docs를 고치지 않고 댓글만 단다. 댓글에는 레포를 고쳐서 답하고, 그 Doc을 다시 만드는 [Merge](glossary:merge) 전에 열린 댓글부터 처리한다.

## 4. Workflow가 하는 일

![repo에서 Google Docs로, 한 방향: push, GitHub Actions, OIDC와 WIF, Google Doc](/static/images/project-docs-04-docs-sync/sync-flow.svg)

_repo에서 Google Docs로, 한 방향: push, GitHub Actions, OIDC와 WIF, Google Doc_

`docs-sync.yml`은 `main`에 Push되고 `docs/specs/`, `docs/images/`, `.github/google-docs.json` 중 하나라도 바뀌면 돈다. 수동 실행(`workflow_dispatch`)도 된다.

1. [Mermaid](glossary:mermaid) 코드 블록을 `mmdc`(mermaid-cli 11.4.2)로 [PNG](glossary:png)로 렌더링한다. 한글이 깨지지 않게 `fonts-noto-cjk`를 먼저 설치한다.
2. Google Docs는 [SVG](glossary:svg)를 못 보여 주므로 그 커밋의 SVG는 `images.weserv.nl`로 PNG로 받는다(공개 레포라 가능).
3. 문서 폴더마다 `README.md`의 목록 순서대로 절 파일을 이어 붙여 [HTML](glossary:html) 하나로 만든다. 파일 목록 표만 빼고 나머지 표는 둔다. 그림은 [Data URI](glossary:data-uri)로 넣는다.
4. 맨 위에 [Commit hash](glossary:commit-hash)(커밋 SHA)를 찍는다. Doc을 열면 어느 커밋에서 만들어졌는지 보인다.
5. [Google Drive API](glossary:google-drive-api) [PATCH](glossary:patch) `/upload/drive/v3/files/<id>`로 같은 Doc ID에 덮어쓴다. 새 파일을 만들지 않으니 공유 링크가 안 바뀐다. Drive가 `text/html` 본문을 Google Docs 형식으로 바꿔 준다.

다이어그램을 Mermaid로 그리는 것도 이 흐름 때문이다. [GitHub](glossary:github)이 바로 렌더링하고, [Diff](glossary:diff)에 변경이 보이고, Workflow가 그림으로 바꿀 수 있다. draw.io SVG는 Diff로 무엇이 바뀌었는지 안 보여서 버렸다.

Doc 여섯 개(SPMP, SRS, SDD, STP, SIP, SMP)는 내 계정으로 먼저 만들어 둔다. Workflow가 쓰는 [Service account](glossary:service-account)에는 Drive 저장 용량이 없어서 새 Doc을 만들 수 없기 때문이다. 문서 이름과 Doc ID의 짝은 `.github/google-docs.json`에 적는다.

## 5. 키 없는 인증

첫 버전은 Service account의 JSON 키를 레포 [Secret](glossary:secret)에 넣는 방식이었다. 키가 새면 Drive 쓰기 권한이 같이 샌다. 2026-11-17 Coffee Shop에 처음 붙이던 날 WIF로 바꾸고 만들어 둔 키는 지웠다. 규칙에는 "JSON 키를 다시 만들지 않는다"는 결과만 있고 바꾼 이유 문장은 없다. 그날 작업은 맥 세션에서 한 것으로 보여 윈도우 쪽 기록에서는 못 찾았다.

동작은 이렇다. GitHub Actions가 실행마다 발급하는 OIDC 토큰을 [Google Cloud](glossary:google-cloud)가 확인하고, 조건이 맞으면 Service account의 Short-lived token을 내준다. 조건은 레포 소유자가 `seren-wib`인지다. 그래서 내 레포라면 어느 레포든 같은 설정을 쓰고, 레포마다 Secret을 넣을 필요가 없다. Secret은 0개다.

## 6. 첫 실행 뒤 그림 고치기

같은 날 첫 실행이 Google Docs 여섯 개를 갱신했다. 열어 보니 그림이 문제여서 Pull request 세 개로 고쳤다.

![그림 크기 맞추기 다이어그램. 본문 영역은 가로 624px, 세로 864px. 1600px 폭 PNG는 #65 전에는 본문을 넘쳤고, #65는 폭만 줄였고, #69는 scale = min(624/w, 864/h, 1)로 두 방향을 맞춘다](/static/images/coffee-shop-02-docs-sync/image-fit.svg)

| PR  | 증상                                                             | 고친 것                                                                                      |
| --- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| #65 | 1600px 폭 PNG가 본문을 넘쳤다                                    | PNG 헤더(IHDR)에서 실제 크기를 읽어 `width=min(w, 624)`와 비율에 맞는 `height`를 px로 박는다 |
| #66 | 실행 44027929044에서 SDD의 Mermaid PNG 15장 한글이 전부 네모     | Mermaid 렌더 전에 `fonts-noto-cjk` 설치. draw.io SVG 15장은 원래 멀쩡했다                    |
| #69 | 세로로 긴 `create_order` 흐름도가 468×1168pt로 648pt 본문을 넘음 | 높이도 864px로 제한: `scale = min(624/w, 864/h, 1)`                                          |

#65에서 `%` 폭을 쓰지 않은 이유는 Google Docs가 HTML을 가져올 때 `%` 폭과 `max-width`를 무시하고 px만 받기 때문이다. 그래서 PNG 앞 24바이트 안의 IHDR 청크에서 가로·세로를 읽었다. #69의 계산은 테스트 3개로 확인했다. 1248×400은 624×200, 600×2000은 259×864, 300×100은 그대로다. 이 스크립트는 다른 프로젝트에서도 쓰려고 dotfiles의 project-docs 스킬에 원본을 두고 레포에는 사본을 넣었다.

#66과 #69는 `docs-sync.yml`과 `.github/scripts/build-docs.mjs`를 고쳤는데 둘 다 트리거 경로(`paths`) 밖이다. Merge만으로는 다시 돌지 않아서 직후 수동 실행으로 한 번씩 돌렸다.

취소 10회는 실패가 아니다. `concurrency: docs-sync`, `cancel-in-progress: true`로 문서 Pull request가 잇달아 Merge되면 앞 실행을 끊고 마지막 커밋만 올린다. 어차피 덮어쓰는 구조라 중간 결과는 남길 이유가 없다.

한계: 과제 제출본은 이 Doc과 따로 만들었다. 표지, 쪽 나누기, 그림 앞 제목을 다음 쪽으로 넘기지 않는 설정이 필요한데 HTML 업로드로는 쪽 나누기 CSS가 무시된다. 최종 제출본(SRS 86쪽, 설계 명세서 129쪽)은 같은 Markdown에서 따로 빌드하고 Docs API로 쪽 나누기를 넣었다. 동기화 Doc은 "지금 `main`이 무엇을 말하는가"를 보는 용도다.

## 8. 느낀 점

원본을 하나로 정하니 "어느 쪽이 맞냐"는 질문이 없어졌다.
