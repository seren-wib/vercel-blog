> 시리즈 1편. 클러스터를 만지기 전, 팀이 문서로 부딪힌 첫 열흘이다. 프로젝트 전체 그림은 [Woowangthon 0](/kr/blog/woowangthon/woowangthon-00-overview/)에 있다.

## 한 줄 요약

10월 26일부터 11월 3일 아침까지 팀 레포에 PR이 열네 개 올라왔고, 그중 코드가 든 PR은 하나도 없었다. 전부 문서였다. 내가 첫날 혼자 올린 설계 문서 셋은 결정 전이라는 이유로 닫혔고, 그 뒤로는 "언제 쓰고, 어디에 한 번만 쓰는가"를 정하는 데 시간을 썼다. 덕분에 코드가 들어오기 시작한 뒤로는 문서 때문에 다툴 일이 거의 없었다.

## 1. 첫날 혼자 올린 문서 셋

킥오프 이틀 뒤인 10월 26일, 나는 PR 세 개를 연달아 올렸다.

| PR                                                              | 내용                                                                                                                                                                         |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [#2](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/2) | 시스템 구성도와 흐름, 그리고 "정해야 할 것" 19개                                                                                                                             |
| [#4](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/4) | ADR-002 시스템 아키텍처 제안. 정적 사이트는 [Cloudflare R2](/kr/blog/cloudflare/cloudflare-00-basics/#r2)에, 서버가 필요한 앱은 학교 실습실 PC의 k3s에, 클라우드 VM은 예비로 |
| [#5](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/5) | ADR-001 기술 스택 제안. 영역별 선택과 이유                                                                                                                                   |

팀이 쓰기로 한 AI 리뷰 봇(CodeRabbit)이 푸시할 때마다 코멘트를 달았다. 쓸 만한 지적도 있었지만, 제안 문서를 구현할 명세처럼 읽고 "이 부분을 설계하세요"를 계속 요구했다. 결국 PR마다 리뷰를 멈췄다(`@coderabbitai pause`).

사람 쪽 답은 더 짧았다. [TaeTaeJin](https://github.com/TaeTaeJin)이 "회의와 학교 문의 뒤에 정할 사안이라 보류하는 게 좋겠다"며 PR을 draft로 돌렸고, 다른 PR에는 혼자 고민하느라 고생했으니 내일 회의에서 같이 정하자고 남겼다. 다음 날 아침 나는 셋 다 닫고 내용을 Notion으로 옮겼다.

돌아보면 순서가 틀렸다. ADR은 **정한 것**을 이유와 함께 남기는 문서다. 그런데 나는 아무도 정하지 않은 것을 "제안됨" 상태로 올렸다. 내용이 틀려서 닫힌 게 아니라 결정을 거치지 않아서 닫혔다. 실제로 "학교 PC에서 k3s를 돌린다"는 큰 줄기는 살아남았지만, "정적 사이트는 R2에"는 나중에 팀이 폐기했다. 결과물을 학교 밖에 두면 "학교 자원으로 돌린다"는 강점이 사라지기 때문이다. 혼자 정했으면 그 안이 문서에 그대로 박혀 있었을 것이다.

같은 날 머지된 내 PR이 하나 있긴 하다. [#3](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/3), "레포 규칙이 개인 에이전트 지침보다 우선한다"는 한 줄이다. 팀원마다 자기 AI 코딩 에이전트에 개인 지침을 넣어 쓰는데, 그 지침이 팀 규칙과 부딪히면 팀 규칙을 따르라는 뜻이다.

## 2. 문서 구조를 다시 짠 PR

10월 27일 TaeTaeJin이 문서 구조 전체를 다시 짠 [#7](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/7)을 올렸다. 이 팀에서는 사람만 문서를 읽지 않는다. 팀원 각자의 AI 에이전트도 같은 문서를 읽고 일한다. 그래서 구조의 기준이 둘이었다. 사람이 찾기 쉬운가, 그리고 에이전트가 매번 읽어도 부담이 없는가.

| 바뀐 것                  | 내용                                                                                                                  |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `CLAUDE.md` 한 곳이 입구 | 에이전트와 팀원이 작업 전에 읽는 단일 진입점. 매 세션 필요한 규칙만 남기고 61줄로 줄였다                              |
| `CONTRIBUTING.md` 분리   | 브랜치, 커밋, PR 때만 필요한 규칙은 여기로                                                                            |
| 커밋 전에 규칙 읽기 강제 | 에이전트가 `CONTRIBUTING.md`를 읽기 전에는 `git commit`과 PR 생성을 막는 훅(hook). 안내 문장 한 줄은 무시될 수 있어서 |
| 요구사항 명세(SRS)       | 유즈케이스(UC) → 기능 요구사항(FR) → 비기능 요구사항(NFR) → 데모 시나리오 순서                                        |
| ADR 상태                 | "제안됨 → 채택됨" 단계를 없앴다. 회의에서 정한 뒤 쓰고, 머지되면 확정                                                 |

마지막 줄이 1절에 대한 팀의 답이다. 제안은 회의와 Notion에서 하고, 레포에는 정해진 것만 들어온다.

나는 이 PR을 끝까지 읽고 리뷰를 남겼다. 에이전트로 같이 읽었기 때문에, 내가 직접 확인한 부분과 AI만 확인한 부분을 구분해 표시했다. 머지 전에 고치자고 한 것 중 하나가 FR 번호였다. 처음 안은 `FR-<UC 번호>-<순번>`이었다. 그런데 같은 문서에 "ID는 한 번 붙이면 바꾸지 않는다"와 "한 UC에 우선순위가 섞이면 UC를 쪼갠다"가 같이 있었다. UC를 쪼개면 옮겨 가는 FR은 번호를 바꾸거나(첫 규칙 위반) 예전 UC 번호를 단 채 남는다(형식 위반). 그래서 UC와 상관없는 연번 `FR-NNN`으로 바꾸자고 했고, 그대로 들어갔다.

반대로 받아들여지지 않은 제안도 있다. 로컬과 CI에서 테스트를 두 번 돌리는 것, PR을 열기 전에 뮤테이션 테스트를 돌리는 것이다. 3주짜리 대회에서는 과하다는 판단이었고, 지금 보면 맞는 판단이었다.

## 3. 한 사실이 열 파일에

10월 31일 TaeTaeJin이 시스템 정의서를 올렸다([#12](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/12)). 사용자, 구성요소, 흐름, 인프라를 한 문서에 정의하고, 기술 스택 ADR과 다이어그램 수정까지 들어 있었다.

인프라 쪽을 읽다가 문제가 보였다. 컨테이너 레지스트리가 AWS ECR로 적혀 있었는데, 머지 시점 기준으로 **ECR이라는 단어가 파일 10개, 25줄에** 나왔다. 시스템 정의서, ADR, AI 사용 범위 문서, 그리고 다이어그램 일곱 장이다. 게다가 이건 정한 적이 없는 값이었다. 10월 29일 회의에서 클라우드는 AWS로 하자고 했고, 그 말이 레지스트리도 ECR이라는 뜻으로 옮겨 적힌 것이다.

다음 날 디스코드에서 레지스트리를 GHCR(GitHub 컨테이너 레지스트리), 이미지 공개로 정했다. 기준은 "학교 PC에 만료되는 자격증명을 두지 않는다"였다.

- 비공개 ECR은 이미지를 받는 토큰이 12시간마다 만료된다. 그러면 학교 PC에 토큰을 갱신하는 작업과 AWS 자격증명이 올라가야 한다
- 비공개 GHCR은 무료 한도(저장 500MB, 전송 월 1GB)가 학생 앱 이미지 두세 개면 끝난다
- 공개 GHCR은 받을 때 토큰이 필요 없다. 학생 코드가 이미지 안에서 보이는 건 감수했다. 어차피 공개 레포만 받는다

25줄을 고쳐 달라고 리뷰를 다는 대신, 나는 #12를 그대로 승인했다. 작성자에게 25줄을 비우라고 하는 것보다, 머지한 뒤 내가 인프라 부분을 한 번에 다시 쓰는 게 빨랐다. 대신 원인을 막는 규칙을 하나 제안했다.

> **기술 스택은 시스템 정의서 §3 표 한 곳에만 쓴다.** 다른 문서와 다이어그램은 "컨테이너 레지스트리"처럼 구성요소 이름만 쓴다.

이 규칙은 [#20](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/20)으로 들어갔다. 이제 레지스트리를 또 바꾸면 표 한 칸과 ADR 하나만 고치면 된다.

## 4. ADR 규칙

같은 PR에서 ADR 규칙도 정했다.

- **ADR 하나에 결정 하나.** "학생 볼륨을 어떻게 지키나"처럼 질문 하나가 결정 하나다. 도구 하나 고르는 가벼운 선택은 ADR 없이 표 한 줄로 끝낸다
- **머지된 ADR 본문은 고치지 않는다.** 바뀌면 새 ADR을 쓰고, 예전 ADR은 상태 줄만 바꾼다. 기술 스택을 통째로 묶은 ADR-001은 이제 `유효 (일부 대체: 레지스트리 → 003)`이다

이어서 [#21](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/21)로 클러스터 ADR 넷을 올렸다. 레지스트리(GHCR), 플랫폼 서버와 클러스터의 연결(Tailscale), 학교 PC 3대의 k3s 구성, 지표(리더의 Prometheus)다. 넷 다 회의나 디스코드에서 먼저 합의한 것이다. 1절에서 배운 순서대로다.

## 5. 그림도 같은 병

다이어그램도 같은 문제를 앓았다. 팀 다이어그램에는 물리 네트워크(⑤)와 클러스터(⑥)가 따로 있었고, 둘 다 내 구축 계획과 어긋나 있었다. 강의실 PC 40% 자원 상한, 동아리방 공유기 LAN, 리더의 WebSocket 에이전트 같은 것들이다. 이 이야기는 [2편](/kr/blog/woowangthon/woowangthon-02-network-design/)에서 한다.

[#15](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/15)에서 둘을 한 장으로 합쳐 다시 그렸다. 그리면서 원칙을 하나 세웠다. **그림에는 구조만 넣는다.** 구역, 역할 한 줄짜리 상자, 번호 붙인 선, 장애가 나면 무엇이 끊기는지 정도다. 설정값이나 규칙을 그림에 넣으면 그림이 계획서의 두 번째 사본이 되고, 사본은 반드시 어긋난다. 이어서 [#22](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/22)에서 시스템 정의서, AI 사용 범위 문서, SRS의 인프라 부분을 구축 계획에 맞췄다.

## 6. 포크 PR은 새 워크플로를 못 돌린다

11월 3일 오후, 드디어 코드가 들어왔다. TaeTaeJin이 웹 프로젝트 셋업([#23](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/23))과 디자인 시스템([#24](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/24))을 올렸다. 그런데 #23에 같이 넣은 [CI](/kr/blog/devops/devops-00-basics/#ci) 워크플로가 한 번도 돌지 않았다.

이 팀은 각자 레포를 포크해서 PR을 올린다. 확인해 보니 포크에서 온 PR은 그 PR이 새로 추가한 워크플로를 돌리지 않았다. #23이 머지되어 워크플로가 `main`에 들어가자 `main` 푸시에서 돌기 시작했고, #24의 다음 푸시부터 PR에서도 돌았다. 정확한 규칙은 공식 문서에서 찾지 못했지만, 이 레포에서는 이렇게 동작했다.

그래서 워크플로를 추가하거나 고치는 PR은 CI로 스스로를 증명할 수 없다. 그런 PR은 로컬에서 `pnpm verify`(린트 → 테스트 → 빌드)를 돌려 확인하고, 다음 PR이나 `main` 푸시의 실행을 한 번 더 본다.

## 7. 정리

| 겪은 일                                     | 남긴 규칙                                        |
| ------------------------------------------- | ------------------------------------------------ |
| 결정 전에 ADR을 올렸다가 닫혔다             | 제안은 회의와 Notion에서. 레포에는 정해진 것만   |
| 에이전트가 규칙 안내를 놓칠 수 있다         | 꼭 지켜야 할 것은 문장 말고 훅으로 막는다        |
| FR 번호가 UC에 묶여 ID 불변 규칙과 부딪혔다 | FR은 UC와 상관없는 연번                          |
| 정하지 않은 ECR이 파일 10개에 퍼졌다        | 기술 스택은 한 표에만, 나머지는 구성요소 이름    |
| 그림이 계획서와 어긋났다                    | 그림에는 구조만                                  |
| 포크 PR에서 새 워크플로가 안 돌았다         | 워크플로 PR은 로컬에서 확인하고 다음 실행을 본다 |

처음에는 코드 없이 열흘을 보내는 게 불안했다. 지금은 그 열흘 덕분에 나머지 기간에 문서로 다툴 일이 줄었다고 본다. 다음 글부터는 학교 PC 이야기다.
