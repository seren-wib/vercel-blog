This homework covers the labs in chapters 13 to 15 of the textbook. The first half deploys OpenStack on a single node with Kolla-Ansible and creates instances from the dashboard and the command-line tools. The second half builds a container network (the setup on slide p67) by hand with Linux network namespaces. I first installed OpenStack inside a Rocky VM as the slides do, but gave up after running the deployment 8 times over more than 6 hours. That process is written up separately in [section 5](#5-problems-during-the-lab).

# 0. Lab Environment

I used the same Ubuntu host as since HW2 (Ubuntu 24.04 aarch64 on UTM on an Apple M3 Mac, 9.7GiB of memory, 6 vCPUs). Because the host is aarch64, I used aarch64 builds of every image, and I noted under each figure where commands differ from the slides.

- **OpenStack**: Installed directly on the Ubuntu host instead of adding one more VM level. Installing it inside a Rocky VM makes a three-level nesting of Mac → UTM → Ubuntu → KVM → Rocky, and the deployment never finished because of timeouts.
- **Linux containers**: Done in a Rocky Linux 10.2 aarch64 VM, `lxc.cloud.org`, created on the host's KVM.

# 1. Preparing the OpenStack Installation

## Interface for the External Network

The slides hand enp0s8, one of two NICs, entirely over to the neutron external network. This host has only one NIC, enp0s1, and handing it over would cut off access to the host, so I created a veth pair with NetworkManager and used one end (veth1) as the external interface.

```bash
ip -br addr | grep -v vnet
sudo nmcli con add type veth con-name veth0 ifname veth0 veth.peer veth1 ipv4.method disabled ipv6.method disabled
sudo nmcli con add type veth con-name veth1 ifname veth1 veth.peer veth0 ipv4.method disabled ipv6.method disabled
ip -br link show type veth
```

## Preparing the Host

Kolla runs libvirt in the `nova_libvirt` container, and if the libvirt installed on the host in HW6 is still running, prechecks stops. I turned off every libvirt unit on the host and checked the firewall and time synchronization. Units given as a glob are not disabled, so I listed them one by one.

```bash
sudo systemctl disable --now libvirt-guests.service libvirtd.service virtlockd.service virtlogd.service \
  libvirtd-admin.socket libvirtd-ro.socket libvirtd.socket virtlockd-admin.socket virtlockd.socket \
  virtlogd-admin.socket virtlogd.socket
systemctl is-active libvirtd libvirtd.socket virtlogd
sudo ufw status
timedatectl | grep -E 'synchronized|NTP'
```

## globals.yml

Five values changed compared with the slides.

- `kolla_base_distro: "ubuntu"`: The host is Ubuntu, so I used the Ubuntu builds of the container images too.
- `network_interface: "enp0s1"`, `neutron_external_interface: "veth1"`
- `enable_haproxy: "no"`, `kolla_internal_vip_address: "192.168.64.4"`: With a single node, I turned off the load balancer (haproxy·keepalived) and set the VIP to the host IP.
- `openstack_tag_suffix: "-aarch64"`: With the default `""`, it pulls the `2026.2-ubuntu-noble` tag, which has no arm64 manifest.

```bash
sed -i -e 's/^#kolla_base_distro:.*/kolla_base_distro: "ubuntu"/' \
  -e 's/^#network_interface:.*/network_interface: "enp0s1"/' \
  -e 's/^#neutron_external_interface:.*/neutron_external_interface: "veth1"/' \
  -e 's/^#\?kolla_internal_vip_address:.*/kolla_internal_vip_address: "192.168.64.4"/' \
  -e 's/^#enable_haproxy:.*/enable_haproxy: "no"/' globals.yml
echo 'openstack_tag_suffix: "-aarch64"' >> globals.yml
```

allowed_origin = http://192.168.64.4,http://localhost:8080

# 5. Problems During the Lab

## Problem 1. Deployment Inside the Rocky VM Never Finished

At first I created a Rocky VM (`openstack`, 8GiB, 4 vCPUs) as in the slides and installed all-in-one inside it. The slides have two levels, x86 PC → VirtualBox → Rocky, but in this environment it becomes three levels of nesting: Mac → UTM → Ubuntu → KVM → Rocky. On top of that, Kolla starts dozens of containers.

bootstrap-servers and prechecks passed. These were the measurements 37 minutes after deploy started.

| Measurement                             | Value                         |
| --------------------------------------- | ----------------------------- |
| Rocky load average (4 vCPUs)            | 28–33, I/O wait 0             |
| Ubuntu host CPU steal                   | 55–59%                        |
| CPU of the VM process on the Mac        | 285%                          |
| 50 runs of `/bin/true` (Ubuntu / Rocky) | 0.013 s / 0.908 s (about 70×) |
| `python3 -c pass` (Rocky)               | 2.9 s                         |

The bottleneck was neither disk nor network but the cost of going through three layers of virtualization every time a process is created. From then on, Kolla's timeout defaults broke one by one.

| Run | Time        | Result                           | What broke and the fix                                                                                                                                                                     |
| --- | ----------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | 12:29–13:20 | Stuck at rabbitmq for 25 minutes | The healthcheck `rabbitmq-diagnostics ping`, run every 30 seconds, never finished and 22 piled up → `enable_container_healthchecks: "no"`                                                  |
| 2   | 13:28–13:55 | Failed (ok=33)                   | Containers created in run 1 kept their healthcheck settings and piled up again, `docker ps` 40 seconds → `kolla-ansible destroy` (3 min 26 s)                                              |
| 3   | 14:00–14:37 | Failed (ok=204)                  | keystone bootstrap rc=1 after 4 min 59.8 s. The same command run by hand succeeded in 37 seconds                                                                                           |
| 4   | 14:37–15:43 | Failed (ok=232)                  | `ovs-vsctl -t 5` didn't finish within 5 seconds, SIGALRM → `timeout: 60` on the openvswitch·ovn-controller roles                                                                           |
| 5   | 15:46–16:25 | Failed (ok=287)                  | nova API 503. The keepalived check (2-second interval, FAULT after 2 failures) didn't finish in time, 49 FAULTs, each dropping the VIP for 20–40 seconds → interval 10, timeout 60, fall 6 |
| 6   | 16:28–16:52 | Failed (ok=281)                  | Same 503 with 0 FAULTs. The nova_api uwsgi started while the VIP was missing in run 5 stayed in a `no python application found` state → `docker restart nova_api nova_metadata`            |
| 7   | 16:56–17:49 | Failed (ok=343)                  | Docker API ReadTimeout (default 120 seconds) in the neutron restart handler. Load average 128–144, 3 min 41 s for one `docker ps -q` → `docker_client_timeout: 600`, worker count 1        |
| 8   | 17:56–18:46 | Stopped                          | Most containers restarting because of changed settings, load average 113                                                                                                                   |

Run 7 reached ok=343, so a few more runs might have finished the deployment itself. I stopped there anyway for two reasons.

- There is no `/dev/kvm` inside Rocky, so nova has to start instances with TCG (software emulation). With emulation on top of a place where process creation is 70 times slower, there was no telling whether the instance labs would work.
- What the homework asks for is "the result of building OpenStack", and the Rocky VM in the slides is a means of building it.

So I deleted the Rocky VM, removed one level, and installed directly on the Ubuntu host. Ubuntu has `/dev/kvm`, so nova uses KVM directly. With the same Kolla version, the first deployment finished with failed=0 in 13 minutes 22 seconds.

Three lessons remain.

- Each added level of nesting breaks, in turn, timeout defaults that were assumed to be "long enough". The order was healthcheck 30 seconds → `ovs-vsctl` 5 seconds → keepalived 2 seconds → Docker API 120 seconds.
- Kolla deploy does not restart containers whose settings haven't changed. A service that failed at startup (uwsgi that couldn't load the app) stays that way even if the deployment is run again, so it has to be restarted by hand.
- Failure messages print the command line as is, and that command line contains service passwords in plain text. I wrote the log to a file and showed only PLAY RECAP on screen.

## Problem 2. cirros Hangs at virtio_blk

The first instance created on the Ubuntu host hung during boot right after the `virtio_blk` message. CPU was at 100% and the guest clock didn't go past 9 seconds. cirros 0.6.3 was the same.

It is the same symptom as the MSI interrupt problem under nested virtualization that I hit when installing Rocky aarch64 on KVM in [HW6](/en/blog/cs-fundamentals/cloud-computing/cloud-computing-hw6-kvm-live-migration/#installing-a-rocky-vm-on-kvm). As then, adding `pci=nomsi` to the kernel arguments makes it use legacy interrupts instead of MSI. cirros aarch64 boots with GRUB from the EFI partition, so I copied the image, attached it to a block device with `qemu-nbd`, mounted the EFI partition, and appended `pci=nomsi` to the end of the kernel line in `EFI/ubuntu/grub.cfg`.

```bash
modprobe nbd max_part=16
cp /root/cirros-0.5.1-aarch64-disk.img /root/cirros-nomsi.img
qemu-nbd --connect /dev/nbd0 /root/cirros-nomsi.img
lsblk -o NAME,SIZE,FSTYPE,LABEL /dev/nbd0
```

After mounting the EFI partition (vfat) and editing `grub.cfg`, I disconnected it and registered the image again.

```bash
qemu-nbd --disconnect /dev/nbd0
openstack image delete cirros
openstack image create --disk-format qcow2 --container-format bare --public --file /root/cirros-nomsi.img cirros
```

After switching to this image, the login prompt appeared within 60 seconds. The mycirros uploaded from the dashboard is the same file.

## Problem 3. docker and dbus Modules Missing in prechecks

prechecks failed at the `import docker` and `import dbus` checks. Kolla-Ansible handles Docker and systemd with the virtual environment's Python, and the virtual environment didn't have the two packages. `dbus-python` needs to be built, so I installed the header packages first.

```bash
apt-get install -y libdbus-1-dev libglib2.0-dev pkg-config
pip install docker dbus-python
```

## Problem 4. Dashboard Image Upload Blocked by CORS

When uploading mycirros from the dashboard, the browser sends the file directly to glance, and that request was blocked by CORS. Connecting from the Mac through an SSH tunnel made the origin `http://localhost:8080`, while glance only allowed the origin `http://192.168.64.4`. I added the tunnel address to `allowed_origin` in `glance.conf` and reconfigured glance only (34 seconds).

```bash
kolla-ansible reconfigure -i ./all-in-one -t glance
```

## Problem 5. Empty VNC Console

The dashboard "Console" tab only showed "Display output is not active". This is because aarch64 cirros outputs to the serial port, not the display (VGA). In the dashboard I viewed the serial output in the "Log" tab, and used `virsh console` for console input.

# 6. Linux Container Networking

I cloned the Rocky Linux 10 VM to create `lxc.cloud.org` and followed the network namespace lab in slide Ch15 (pages 29–75) to build the setup in the p67 figure. It puts a bridge br0 (10.0.100.1) in the root network namespace, attaches namespaces netns1·netns2 with veth, and sends traffic out through NAT.

```text

                 └─ brif2 ⇄ veth2 10.0.100.102 [netns2]
```

## Connecting Through a Bridge

A veth pair only connects two ends. When there are more namespaces, a bridge goes in the root and the opposite end (brif) of each namespace's veth is plugged into the bridge.

```bash

ip link set br0 up
ip link add brif1 type veth peer name veth1
ip link add brif2 type veth peer name veth2
ip link set veth1 netns netns1
ip link set veth2 netns netns2
ip netns exec netns1 ip a add 10.0.100.101/24 dev veth1
ip netns exec netns2 ip a add 10.0.100.102/24 dev veth2
ip netns exec netns1 ip link set dev veth1 up
ip netns exec netns2 ip link set dev veth2 up
```

## External Access with NAT

Going outside needs three more things: a default route in the namespaces pointing to br0, IP forwarding in the root, and masquerade that rewrites the 10.0.100.0/24 source to the enp1s0 address.

```bash
ip netns exec netns1 ip route add default via 10.0.100.1
ip netns exec netns2 ip route add default via 10.0.100.1
sysctl -w net.ipv4.ip_forward=1
firewall-cmd --permanent --zone=public --add-masquerade
firewall-cmd --permanent --zone=public --add-rich-rule='rule family="ipv4" source address="10.0.100.0/24" masquerade'
firewall-cmd --reload
ip netns exec netns1 ping -c 2 8.8.8.8
```

## Ch14-3. A Case Where a Container-Based Service Is More Efficient

I chose Spotify's move to Kubernetes as the case. Spotify ran its containers with Helios, an orchestration tool it built in-house, and then moved to Kubernetes. According to the CNCF case study, after the move Kubernetes' bin-packing and multi-tenancy raised CPU utilization 2–3 times on average, and the time to create a new service and get capacity ready for deployment dropped from nearly an hour to seconds or minutes. Doing the same thing with VMs would mean starting a full OS for every service, which would not reach this density and speed.

There are four reasons container-based services are better.

- **Density (resource efficiency)**: Containers share the host kernel and only isolate (namespaces) and limit (cgroups) at the process level, so unlike VMs they don't keep a separate guest OS kernel, memory and boot disk per service. More services can therefore be packed tightly onto one node (bin-packing), and Spotify's 2–3× CPU utilization improvement is this effect.
- **Performance overhead**: Felter et al. (2015) at IBM Research compared KVM VMs and Docker containers on the same hardware and reported that containers performed equal to or better than VMs in almost every measurement. This is because VM I/O goes through the hypervisor one more time, and they added that both need tuning for I/O-intensive workloads.
- **Startup time and deployment speed**: Containers start processes without booting an OS, so they start in seconds. Services with hundreds of microservices deploy, scale and roll back often, and this speed led to Spotify's shorter service creation time.
- **Portability and consistency**: The application and its libraries are bundled into one image, and the same image is used in development, testing and production. Images are smaller than VM images, so they are easier to pull from a registry and to version.

However, containers share the kernel, so their isolation is weaker than VMs. When mutually untrusted users share one host or a different OS kernel is needed, VMs are better, which is why running containers on top of VMs is common in practice.

References

- CNCF, "Spotify Case Study," 2019. https://www.cncf.io/case-studies/spotify/
- W. Felter, A. Ferreira, R. Rajamony, J. Rubio, "An Updated Performance Comparison of Virtual Machines and Linux Containers," IEEE ISPASS 2015, pp. 171–172.
