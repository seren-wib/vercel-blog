This assignment follows Chapter 4 of the textbook, "Creating an [HTCondor](glossary:htcondor) cluster on [VirtualBox](glossary:virtualbox)": build three [virtual machines](glossary:vm) and set up [SSH key](glossary:ssh-key) authentication. The problem was that my laptop is an **Apple M3 ([ARM64](glossary:arm64)) Mac**. I couldn't use x86 [VirtualBox](glossary:virtualbox) [VMs](glossary:vm) as-is, so I switched the [hypervisor](glossary:hypervisor) to **[KVM](glossary:kvm)/[libvirt](glossary:libvirt)**.

# 0. Lab Environment

```text
macOS (Apple M3)
└─ UTM (Apple Virtualization, nested virtualization)
   └─ Ubuntu 24.04 ARM64   (host yoosung-vm, the "Ubuntu host" in the lecture)
      └─ KVM + libvirt     (replaces VirtualBox)
         ├─ main    Rocky Linux 10.2   192.168.56.101    main.cloud.org
         ├─ work1   Rocky Linux 10.2   192.168.56.102    work1.cloud.org
         └─ work2   Rocky Linux 10.2   192.168.56.103    work2.cloud.org
```

What changed compared to the textbook ([VirtualBox](glossary:virtualbox)):

| Textbook ([VirtualBox](glossary:virtualbox))                               | This environment ([KVM](glossary:kvm)/[libvirt](glossary:libvirt))                                                  |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| [Host-only](glossary:host-only-network) adapter vboxnet0 (192.168.56.0/24) | [libvirt](glossary:libvirt) isolated network cloud56 ([bridge](glossary:network-bridge) virbr56, host 192.168.56.1) |
| [NAT](glossary:nat) adapter                                                | [libvirt](glossary:libvirt) default [NAT](glossary:nat) network (192.168.122.0/24)                                  |
| `VBoxManage clonevm`                                                       | `virt-clone --auto-clone`                                                                                           |
| Interfaces enp0s3 / enp0s8                                                 | enp1s0 ([NAT](glossary:nat)) / enp2s0 (private [static IP](glossary:static-ip-address))                             |

**[Kernel argument](glossary:kernel-parameter) `pci=nomsi`**: under [nested virtualization](glossary:nested-virtualization), [MSI](glossary:msi) [interrupts](glossary:interrupt) from the guest's [virtio](glossary:virtio) devices were not delivered, so Rocky hung during boot. I fixed it by adding `pci=nomsi` to the [kernel arguments](glossary:kernel-parameter) so the guest uses legacy [INTx](glossary:intx) [interrupts](glossary:interrupt) (details [at the bottom](#appendix-rocky-boot-hang-under-nested-virtualization)). Once GRUB_TIMEOUT=0 is set, you can no longer type [kernel arguments](glossary:kernel-parameter) by hand in the [GRUB](glossary:grub) menu, so I made this argument permanent in the [bootloader](glossary:bootloader) first and only then changed the timeout to 0.

**Order of work**: set GRUB_TIMEOUT=0 on the original [VM](glossary:vm) `rocky-base` → clone it into three → set a [static IP](glossary:static-ip-address), [hostname](glossary:hostname) and `/etc/hosts` on each [VM](glossary:vm). The actual order was (b) → (c) → (a), but below is organized in the order of the assignment items.

# 1. Creating VMs for the HTCondor Cluster

## (a) Assigning Private Static IPs

I gave the private network interface `enp2s0` a [static IP](glossary:static-ip-address) (192.168.56.101–103/24) with [NetworkManager](glossary:networkmanager). It's an internal network that doesn't go outside, so no gateway was set. I changed the [hostname](glossary:hostname) at the same time.

```bash
sudo nmcli con mod enp2s0 ipv4.method manual ipv4.addresses 192.168.56.101/24 connection.autoconnect yes
sudo nmcli con up enp2s0
sudo hostnamectl set-hostname main.cloud.org
```

## (b) Boot Timeout 0 (GRUB_TIMEOUT=0)

Before cloning, on the original [VM](glossary:vm) (`rocky-base`) I changed `GRUB_TIMEOUT` in `/etc/default/grub` to 0 and regenerated `/boot/grub2/grub.cfg` with `grub2-mkconfig`.

`/etc/default/grub` is the settings file used to generate grub.cfg; what [GRUB](glossary:grub) actually reads at boot is `grub.cfg`. So after editing it you must regenerate.

```bash
sudo sed -i 's/^GRUB_TIMEOUT=.*/GRUB_TIMEOUT=0/' /etc/default/grub
sudo grub2-mkconfig -o /boot/grub2/grub.cfg
sudo reboot
```

## (c) Cloning 3 VMs from the Command Line

Instead of `VBoxManage clonevm` I used [libvirt](glossary:libvirt)'s `virt-clone`. It must be run with the original shut down. `--auto-clone` copies the disk file ([qcow2](glossary:qcow2)) and the [UEFI](glossary:uefi) variable file (VARS.fd) under new names and generates new [MAC addresses](glossary:mac-address).

```bash
sudo virsh shutdown rocky-base
sudo virt-clone --original rocky-base --name main --auto-clone
sudo virt-clone --original rocky-base --name work1 --auto-clone
sudo virt-clone --original rocky-base --name work2 --auto-clone
virsh list --all
```

From the host I connected to the three [VMs](glossary:vm) over [SSH](glossary:ssh) with a password and checked with `hostname` that each was the right [VM](glossary:vm). ![Password SSH login](/static/images/cloud-computing-hw2-kvm-vm-cluster/22.webp)

_Host → main, work1, work2 [SSH](glossary:ssh) login (password authentication)_

> **The three [VMs](glossary:vm) have the same [host key](glossary:ssh-host-key).** The [ED25519](glossary:ed25519) [host key](glossary:ssh-host-key) [fingerprint](glossary:fingerprint) is `SHA256:C+o0I1…` on all of them. [virt-clone](glossary:virt-clone) copies the disk as-is, so the `/etc/ssh/ssh_host_*` keys get cloned too. That's why from the second connection on you get the message "this key is also known by other names". It's fine for the lab, but in real operation you should regenerate [host keys](glossary:ssh-host-key) after cloning so the servers can be told apart.

# 2. SSH Key Authentication (Ch04-Extra)

## (a) Connecting from the Host to the Three VMs with a Private Key

I generated an [ED25519](glossary:ed25519) key pair on the host and registered the [public key](glossary:public-key-authentication) in `~/.ssh/authorized_keys` on the three [VMs](glossary:vm) with `ssh-copy-id`. After that, logins are authenticated with the host's [private key](glossary:public-key-authentication) (`~/.ssh/id_ed25519`), so no password is asked. The [private key](glossary:public-key-authentication) never leaves the host; only the [public key](glossary:public-key-authentication) is copied to the [VMs](glossary:vm).

```bash
ssh-keygen -t ed25519
ssh-copy-id yoosung@192.168.56.101
ssh-copy-id yoosung@192.168.56.102
ssh-copy-id yoosung@192.168.56.103
```

## Problems Hit While Cloning

- **Serial log path conflict**: the cloned [VMs](glossary:vm) inherited the original's serial log path (`/var/log/rocky-base-serial.log`) as-is, so starting the second [VM](glossary:vm) failed with "Device or resource busy". I fixed it by dumping the config with `virsh dumpxml`, changing the path per [VM](glossary:vm) name, and re-registering it with `virsh define`.
- **Same [host key](glossary:ssh-host-key)**: as mentioned in (h) above, the [SSH host key](glossary:ssh-host-key) is the same on all three because of disk cloning.

# Appendix. Rocky Boot Hang Under Nested Virtualization

What I was stuck on the longest was the [Rocky Linux](glossary:rocky-linux) guest hanging 7–8 seconds into kernel boot. To give the conclusion first: under [nested virtualization](glossary:nested-virtualization), **[MSI](glossary:msi) [interrupts](glossary:interrupt) were not delivered to the guest**, and a single guest [kernel argument](glossary:kernel-parameter), `pci=nomsi`, fixed it. I fixed it without turning off [KVM](glossary:kvm), so the setup didn't have to change either.

## Symptoms

When a [Rocky Linux](glossary:rocky-linux) 10.2 [aarch64](glossary:arm64) guest was started with [KVM](glossary:kvm), it hung 7–8 seconds into kernel boot and went no further. The domain state was running and cpu.time kept rising. The [VM](glossary:vm) is on and using CPU, but it just doesn't boot. With 2 cores, an [RCU stall](glossary:rcu-stall) warning was printed after 60 seconds as well.

```text
[     7.300568] pcieport 0000:00:01.1: PME: Signaling with IRQ 51
[    67.306241] rcu: INFO: rcu_preempt detected stalls on CPUs/tasks:
[    67.346763] rcu:     Possible timer handling issue on cpu=0 timer-softirq=151
[    67.354764] rcu: rcu_preempt kthread starved for 6002 jiffies!
[    67.434740] rcu: Sending NMI from CPU 1 to CPUs 0:
```

The graphical console only showed `Display output is not active`, so there was no way to find the cause. Only after switching the [serial console](glossary:serial-console) output to be saved to a file did I get the log above. I compared how far the boot got by the size of the serial log file. On a normal boot the log keeps growing all the way to the installer screen.

## Two Problems Solved First

Before I even saw the boot hang, two other problems came up.

**① [Secure Boot](glossary:secure-boot) firmware**

If you give `virt-install` only `--boot uefi`, [libvirt](glossary:libvirt) picks `AAVMF_CODE.ms.fd`, which has Microsoft keys enrolled. This firmware rejects unsigned kernels, giving this error:

```text
error: ../../grub-core/loader/efi/linux.c:723:failed to install protocols.
Failed to boot both default and fallback entries.
```

I fixed it by specifying firmware with [Secure Boot](glossary:secure-boot) disabled. I also confirmed that `secureboot: Secure boot disabled` appears in the guest kernel log.

```text
--boot loader=/usr/share/AAVMF/AAVMF_CODE.no-secboot.fd,loader.readonly=yes,loader.type=pflash,loader.secure=no,nvram.template=/usr/share/AAVMF/AAVMF_VARS.fd
```

**② Graphical console doesn't show up**

An [aarch64](glossary:arm64) guest shows nothing on the [SPICE](glossary:spice) console, just `Display output is not active`. On top of that, `--cdrom` can't pass [kernel arguments](glossary:kernel-parameter). I changed the install method like this:

- `--location <ISO>`: extracts vmlinuz and initrd.img from the ISO and boots them directly. Since it skips [GRUB](glossary:grub), it also avoids the error in ①.
- `--graphics none` + `--extra-args "console=ttyAMA0,115200 inst.text"`: runs the installer in serial text mode.
- `--serial pty,log.file=<path>`: saves serial output to a file. `virsh console` often misses early output depending on when you attach, so it looks like a blank screen. Only by saving to a file could I see the boot log from the start.

Only after solving these two could I properly look at the hang at 7–8 seconds.

## Root Cause Analysis

I narrowed down the cause by changing one condition at a time over four runs.

| Run | What changed                                                             | Serial log size | Result           |
| --- | ------------------------------------------------------------------------ | --------------- | ---------------- |
| 1   | [vCPU](glossary:vcpu) 2 (baseline)                                       | 46,222 B        | Hung at 7.30 s   |
| 2   | [vCPU](glossary:vcpu) 1                                                  | —               | Hung at 8.22 s   |
| 3   | `--virt-type qemu` ([TCG](glossary:tcg) [emulation](glossary:emulation)) | 115,139 B       | Reached normally |
| 4   | Keep [KVM](glossary:kvm) + `pci=nomsi`                                   | 98,182 B        | Reached normally |

**Hypothesis 1. Timer problem in the [nested](glossary:nested-virtualization) environment (wrong)**

At first, seeing `Possible timer handling issue on cpu=0` in the [RCU stall](glossary:rcu-stall) message, I suspected a timer delivery failure. I also found `kvm [1]: Hyp nVHE mode initialized successfully` in L1 ([Ubuntu](glossary:ubuntu))'s dmesg. On ARM hardware [KVM](glossary:kvm) usually comes up in [VHE](glossary:vhe) mode, but here it was [nVHE](glossary:vhe). That means Apple's virtualization provides EL2 for nesting but not the [VHE](glossary:vhe) feature, so I thought timers might have problems too.

But runs 1 and 2 hung on different lines, so it was hard to see it as a problem with one specific driver. And both times, right before hanging, it was waking up [PCI](glossary:pci) devices. So I treated the [RCU stall](glossary:rcu-stall) as a symptom that followed from failing to receive [interrupts](glossary:interrupt), and dropped this hypothesis.

**Hypothesis 2. A problem with [nested](glossary:nested-virtualization) [KVM](glossary:kvm) itself (narrowed the scope)**

With the same ISO, kernel and firmware, running without [KVM](glossary:kvm) under [TCG](glossary:tcg) [emulation](glossary:emulation) with `--virt-type qemu` got all the way into the installer normally (run 3). The only thing changed was [KVM](glossary:kvm), so the problem is on the [nested virtualization](glossary:nested-virtualization) side. But [TCG](glossary:tcg) is 10–20× slower, so it's unusable for the lab; I used it only to isolate the cause.

**Hypothesis 3. [MSI](glossary:msi) [interrupt](glossary:interrupt) delivery failure (the actual cause)**

Since both runs hung at [PCI](glossary:pci) devices, I suspected the [interrupt](glossary:interrupt) path. On ARM, [PCI](glossary:pci) devices send [interrupts](glossary:interrupt) via [MSI-X](glossary:msi) and the [interrupt](glossary:interrupt) controller ([GIC](glossary:gic)) receives them. I confirmed this in L1's dmesg.

```text
GICv2m: range[mem 0x1fff0000-0x1fff0fff], SPI[128:255]
kvm [1]: GICv3: no GICV resource entry
kvm [1]: disabling GICv2 emulation
```

L1 had no [ITS](glossary:gic) to handle [MSI](glossary:msi) and was using the older [GICv2m](glossary:gic). In this setup [MSI](glossary:msi) doesn't reach the guest, so it appears the guest couldn't receive the [interrupts](glossary:interrupt) sent by [virtio](glossary:virtio)-pci devices and hung right there.

## Fix

I added a single `pci=nomsi` to the guest [kernel arguments](glossary:kernel-parameter). With this, the guest receives [interrupts](glossary:interrupt) via legacy [INTx](glossary:intx) instead of [MSI](glossary:msi) and doesn't use the problematic path at all.

```text
--extra-args "console=ttyAMA0,115200 inst.text pci=nomsi"
```

| Condition                        | Serial log | Result                     |
| -------------------------------- | ---------- | -------------------------- |
| [KVM](glossary:kvm), no argument | 46,222 B   | Hung at 7–8 s              |
| [KVM](glossary:kvm), `pci=nomsi` | 98,182 B   | Reached installer normally |

Why I chose this approach

- No need to turn off [KVM](glossary:kvm). It doesn't slow down like [TCG](glossary:tcg).
- The setup doesn't change. The only addition is one line of guest [kernel arguments](glossary:kernel-parameter).
- The downside is slightly slower I/O. [INTx](glossary:intx) is less efficient than [MSI](glossary:msi), but it was no problem for a 3-[VM](glossary:vm) lab.

## Settings Needed to Reproduce

| -------------------------------------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
