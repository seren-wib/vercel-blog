## 0. 들어가며

소프트웨어공학 팀 과제로 커피 원두 쇼핑몰 `coffee-shop`을 만들었다. 평가가 코드보다 문서라서 [SRS](glossary:srs)와 [SDD](glossary:sdd)가 각각 10%였고, 그래서 2026-09-15부터 두 달은 거의 문서만 썼다. 구현과 [Deployment](glossary:deployment)는 마지막 열흘에 몰렸다. 레포는 공개 [seren-wib/coffee-shop](https://github.com/seren-wib/coffee-shop)이고, 이 글은 [Claude Code](glossary:claude-code)가 커밋·[PR](glossary:pull-request)·작업 기록을 읽고 썼다.

식당으로 비유하면 처음 두 달은 메뉴판과 주방 설계도를 그려 심사받는 기간이었고, 마지막 열흘은 주방과 홀을 지어 문을 여는 기간이었다. 주문서마다 번호를 붙여 홀과 주방이 같은 번호로 부르게 했고, 주방이 하나뿐이라 주문은 문 앞에 한 줄로 세웠고, 새 가게를 다 꾸민 뒤에야 간판을 바꿔 달았다. 메뉴판과 설계도는 [SRS](glossary:srs)와 [SDD](glossary:sdd), 심사는 과제 제출과 교수님 피드백, 시공은 구현 [PR](glossary:pull-request), 주문서 번호는 요구사항 ID, 한 줄 세우기는 [SQLite](glossary:sqlite)의 [Write lock](glossary:write-lock) 대기([BEGIN IMMEDIATE](glossary:begin-immediate) [Transaction](glossary:transaction)), 간판은 `current` [Symbolic link](glossary:symbolic-link)다.

아래는 일어난 순서대로 문서, [Backend](glossary:backend), [Frontend](glossary:frontend), [Deployment](glossary:deployment)를 적고, 숫자는 11절 표에 모았다.

## 2. 요구사항과 설계 문서

### HW1과 HW2

9월 22일부터 10월 11일까지가 HW1(요구사항), 11월 6일부터 9일까지가 HW2(설계)다. 역할은 폴더로 갈렸다(`docs/backend/`, `docs/frontend/`). 그림은 `.drawio.svg`로 통일했다(#31). [GitHub](glossary:github)에서 그림으로 바로 보이고 [draw.io](glossary:drawio)로 열면 그대로 고칠 수 있는데, `.drawio`는 [GitHub](glossary:github)에서 XML로만 보이기 때문이다.

여럿이 동시에 쓰니 같은 사실이 문서마다 달랐다. #36 본문에 두 개를 "확인이 필요한 사항"으로 남겼고, 10월 11일 회의에서 정해 #41로 반영했다.

- **취소 반려 뒤 상태.** 요구사항은 요청 전 상태(`PAID` 또는 `PREPARING`)로 돌아가라는데 스키마에 저장할 칼럼이 없었다. `status_before_cancel` 칼럼을 더했고, 최종 구현에서는 [CHECK constraint](glossary:check-constraint) `ck_orders_cancel_request_previous`까지 붙었다(#104).
- **재고 차감 시점.** 요구사항과 `create_order` 알고리즘은 주문 생성 때, 테이블 명세서는 결제 때였다. 주문 생성 [Transaction](glossary:transaction) 안의 [Conditional UPDATE](glossary:conditional-update) 하나로 차감하기로 했다(#100).

HW2 제출본은 Google Docs 합본이었고 그림을 PNG로 넣으며 두 번 고쳤다. [draw.io](glossary:drawio)를 PNG로 바꾸면 한글 라벨이 깨져서 HTML 라벨로 바꿨고(#55), 화면 흐름도가 제출본 2쪽에 안 들어가 두 줄 배치로 압축한 합본용 그림을 따로 만들었다(#57).

#60은 범위 밖 ID 참조 0건, #62는 FR·[NFR](glossary:non-functional-requirement)·DR·UC가 전부 한 번 이상 인용되고 빠진 ID 0건이었다. 다시 쓴 이유는 셋이다.

- **ID가 없으면 추적이 안 된다.** "주문 취소 요구사항"이 어느 테스트로 확인되는지 말하려면 번호가 있어야 한다. 그래서 [Requirements traceability](glossary:requirements-traceability)를 ID로 걸었다.

- **단계별로 나눠야 구현 세션이 필요한 것만 읽는다.** 세션마다 `docs/specs/README.md`부터 읽고 자기 절만 열게 했다.

용어는 [SRS](/kr/blog/cs-fundamentals/software-engineering/software-engineering-ch4-requirements-analysis/#433-3단계-요구사항-명세software-requirements-specification-srs)의 [Domain requirement](glossary:domain-requirement)([도메인 요구사항](/kr/blog/cs-fundamentals/software-engineering/software-engineering-ch4-requirements-analysis/#412-도메인-요구사항))는 옵션 가격·배송비·주문 상태 전환 같은 업무 규칙, [Non-functional requirement](glossary:non-functional-requirement)([비기능적 요구사항](/kr/blog/cs-fundamentals/software-engineering/software-engineering-ch4-requirements-analysis/#42-비기능적-요구사항))는 응답 시간·보안·[Concurrency](glossary:concurrency) 같은 품질이다.

- 1~11절 번호는 그대로 두었다. 다른 문서가 절 번호로 가리키는 곳이 많아서다.

## 3. SQLite 동시 주문 Spike

설계 단계에서 제일 큰 위험이 DB였다. [SQLite](glossary:sqlite)는 파일 전체에 [Write lock](glossary:write-lock)을 하나만 둔다. 재고 1개짜리 원두에 주문 10건이 동시에 들어오면 어떻게 되는지 모르고 주문 코드를 짤 수는 없었다.

![SQLite 트랜잭션 모드 비교 다이어그램. DEFERRED는 BEGIN 뒤 읽기로 시작했다가 쓰기 잠금으로 올라가려는 순간 다른 연결이 먼저 커밋했으면 대기 없이 SQLITE_BUSY를 받아 500이 된다. IMMEDIATE는 BEGIN 때 바로 쓰기 잠금을 요청하고, 잠금이 풀릴 때까지 timeout 20초 안에서 기다린 뒤 조건부 UPDATE로 재고를 확인해 진 쪽은 409를 받는다](/static/images/coffee-shop-03-backend-foundation/sqlite-modes.svg)

`spikes/sqlite-concurrent-order/`에 커밋했다(#73). 설계 문서의 `create_order`를 그대로 쓰고, [gunicorn](glossary:gunicorn) sync 워커 3개 앞에서 스레드 10개가 동시에 `POST /api/orders/`를 보낸다. 조건마다 10건씩 30라운드, 라운드마다 데이터를 다시 넣었다.

| 조건                                            | [201](glossary:http-status-code) | [409](glossary:http-status-code) | [500](glossary:http-status-code) | 재고가 틀린 라운드 | [p95](glossary:percentile-latency)(로컬) |
| ----------------------------------------------- | -------------------------------- | -------------------------------- | -------------------------------- | ------------------ | ---------------------------------------- |
| [IMMEDIATE](glossary:transaction), 300건        | 30                               | 270                              | 0                                | 0                  | 41.96 ms                                 |
| [DEFERRED](glossary:transaction)(기본값), 300건 | -                                | -                                | 68(30라운드 중 29라운드에서)     | 0                  | 안 비교함                                |

환경은 [WSL2](glossary:wsl) Ubuntu(논리 CPU 16개), [Python](glossary:python) 3.14.4, [Django](glossary:django) 6.1.1, [gunicorn](glossary:gunicorn) 27.0.1, [SQLite](glossary:sqlite) 3.46.1이다. [t3.micro](glossary:amazon-ec2)에서는 안 재서 [p95](glossary:percentile-latency)는 로컬 값이다.

- **재고는 두 모드 다 맞았다.** 재고를 지키는 건 [Transaction](glossary:transaction) 모드가 아니라 `WHERE stock_quantity >= n` [Conditional UPDATE](glossary:conditional-update)와 [Rollback](glossary:rollback)이다. 이 설계는 그대로 간다.
- **[DEFERRED](glossary:transaction)의 [500](glossary:http-status-code)은 `timeout`으로 못 막는다.** 읽기로 시작한 [Transaction](glossary:transaction)이 쓰기로 올라가는 사이 다른 연결이 커밋했으면 [SQLite](glossary:sqlite)는 기다려도 소용없다고 보고 즉시 `SQLITE_BUSY`(`database is locked`)를 돌려준다. 20초를 기다리지 않고 바로 왔다(서버 처리 최대 16.86 ms). 그래서 `transaction_mode="IMMEDIATE"`가 필수 설정이 됐다.

## 4. CI와 Branch protection

기능 코드가 하나도 없을 때 [CI](glossary:ci)부터 넣었다(#77). 테스트가 0개여도 형식 검사와 [Database migration](glossary:database-migration) 검사는 첫 모델 [PR](glossary:pull-request)부터 의미가 있다. `backend` 작업은 `black --check`, `makemigrations --check`, 메모리 [SQLite](glossary:sqlite) 테스트, 파일 [SQLite](glossary:sqlite) 동시성 테스트이고, `frontend` 작업은 `prettier --check`, `oxlint`, `vitest`, `vite build`다.

동시성 테스트를 따로 도는 이유는 메모리 [SQLite](glossary:sqlite)에서는 연결끼리 같은 DB를 못 보기 때문이다. 그래서 `test_settings_file.py`로 파일 DB 설정을 뒀다. 이 설정이 공유 `DATABASES` 딕셔너리를 import 시점에 고쳐서 메모리 실행이 `KeyError: 'MIRROR'`로 깨졌고, `deepcopy`로 고쳤다. [CI](glossary:ci)에는 저장소 [Secret](glossary:secret)이 없고 테스트는 `config/test_settings.py`의 가짜 값으로 돈다.

같은 날 `main`에 [Branch protection](glossary:branch-protection)을 걸었다.

| 설정                                      | 값                      |
| ----------------------------------------- | ----------------------- |
| 필수 검사                                 | `backend`, `frontend`   |
| [PR](glossary:pull-request) 필수, 승인 수 | 필수, 0                 |
| enforce admins                            | 켬(관리자도 우회 못 함) |
| [Force push](glossary:force-push), 삭제   | 막음                    |
| strict(최신 main 맞추기)                  | 꺼짐                    |

승인이 0인 이유는 사람이 혼자 머지하는 구조라서다. 대신 [CI](glossary:ci)를 통과하지 못하면 아무도 못 넣는다.

## 5. 모델, 인증, 재고, 배송지

모델은 HW1의 `backend/schema.sql`을 버리고 [SDD](glossary:sdd) 5절에서 새로 짰다(#80, +1,623 / -590줄). SQL 파일과 [Django](glossary:django) 모델이 따로 있으면 둘 중 하나가 거짓말을 하게 된다. 제약은 전부 `Meta.constraints`로 옮겨 [Database migration](glossary:database-migration)이 만들게 했다.

| 기본 권한                         | `IsAuthenticated`(공개 [API](glossary:api)만 명시적으로 연다)                                |
| 응답 형식                         | JSON 렌더러만                                                                                |

| [Django admin](glossary:django)   | `DEBUG`일 때만 붙인다                                                                        |

제약 이름만 봐도 규칙이 보인다. `uq_user_addresses_one_default`(기본 배송지는 하나), `uq_payments_order_success`(주문 하나에 성공 결제는 하나), `ck_orders_shipped_fields`(발송 상태면 송장 필드 필수).

인증(#83)은 [JWT](glossary:jwt)다. [Token claim](glossary:token-claim)에는 `user_id`와 `role`만 넣었다. 화면이 관리자 메뉴를 보여 줄지 정하는 데 그 둘이면 충분하고, 토큰 내용은 누구나 디코드할 수 있다.

- **로그인 실패 응답은 하나다.** 없는 이메일이든 틀린 비밀번호든 같은 [401](glossary:http-status-code) `INVALID_CREDENTIALS`다(NFR-7). 응답이 다르면 가입된 이메일을 알아낼 수 있다.
- **가입에는 개인정보 동의가 필요하다.** `privacy_agreed`가 없으면 거절하고 시각을 `privacy_agreed_at`에 남긴다(FR-58).
- **[Throttling](glossary:throttling) 테스트의 함정.** `override_settings`로 제한값을 바꿔도 안 먹었다. [DRF](glossary:django-rest-framework)가 `THROTTLE_RATES`를 import 시점에 읽어 둬서, 테스트는 `ScopedRateThrottle.THROTTLE_RATES`를 직접 패치한다.
- **관리자 계정은 가입 [API](glossary:api)로 못 만든다.** 서버에서 `manage.py create_admin --email ...`으로만 만든다.

재고 서비스(#85)는 `decrease_stock`, `increase_stock`, `set_stock`, `stop_sales`, `resume_sales` 다섯 개다. 전부 [Conditional UPDATE](glossary:conditional-update) 한 문장이고 바뀐 행이 0이면 `DomainError`를 낸다. 배송지(#87)는 "주소가 있는 회원은 기본 배송지가 정확히 하나"를 두 겹으로 지킨다. 서비스가 새 기본값을 세우기 전에 옛 값을 먼저 지우고, 그래도 둘이 되면 [Partial unique index](glossary:partial-unique-index)가 막는다.

## 6. 주문 상태 전환과 주문 생성

규칙은 하나로 통일했다. **상태를 바꾸는 코드는 전부 [Conditional UPDATE](glossary:conditional-update)이고, 바뀐 행이 0이면 [409](glossary:http-status-code)다.** 주문은 상태 일곱 개를 오간다.

![주문 상태 전환 다이어그램. PENDING에서 결제 성공이면 PAID, 회원 취소면 CANCELLED. PAID에서 관리자 준비면 PREPARING. PAID와 PREPARING에서 회원이 취소 요청하면 CANCEL_REQUESTED, 요청 전 상태를 status_before_cancel에 저장. CANCEL_REQUESTED에서 관리자 승인이면 PG 취소 뒤 CANCELLED, 반려면 요청 전 상태로. PREPARING에서 발송이면 SHIPPED, SHIPPED에서 배송 완료면 DELIVERED. 표에 없는 전환은 409 INVALID_STATE](/static/images/coffee-shop-04-backend-features/order-states.svg)

```python:backend/orders/services.py
# 결제 대기 주문을 회원이 바로 취소할 때
updated = Order.objects.filter(
    pk=order.pk, order_status=OrderStatus.PENDING
).update(order_status=OrderStatus.CANCELLED)
if updated == 0:
    order.refresh_from_db()
    raise invalid_state(order.order_status, "취소할")
```

읽고 → 확인하고 → 쓰는 세 단계로 짜면 두 요청이 동시에 "확인"을 통과할 수 있다. 조건을 `WHERE`에 넣으면 확인과 쓰기가 한 문장이라 그 틈이 없다. 관리자 주문의 모든 전환은 헬퍼 하나를 거치고, `test_dr19_...`가 허용 표 밖의 쌍을 전부 돌며 `INVALID_STATE`인지 본다(#104). 취소 반려는 `status_before_cancel`을 [F expression](glossary:f-expression)으로 되돌린다. 이 칼럼이 빈 `CANCEL_REQUESTED` 행은 [CHECK constraint](glossary:check-constraint)가 아예 못 만들게 막는다. 리뷰에서 "요청 전 상태가 없는 취소 요청을 반려하면 [500](glossary:http-status-code)"이 나와 붙인 제약이다.

주문은 장바구니 전체로 만든다(#100). 한 [Transaction](glossary:transaction) 안에서 이렇게 간다.

1. [IMMEDIATE](glossary:transaction) [Write lock](glossary:write-lock) 아래에서 장바구니를 읽는다
2. 항목마다 판매 상태와 재고를 확인하고, 문제 있는 `cart_item_ids`를 **전부** 모아 [409](glossary:http-status-code)(`NOT_AVAILABLE` 또는 `OUT_OF_STOCK`)로 돌려준다. 하나씩 알려 주면 손님이 고칠 때마다 다음 문제를 하나씩 만난다
3. 주문 번호 `ORD-YYYYMMDD-NNN`(서울 날짜 기준 일련번호)을 매긴다
4. 항목마다 `decrease_stock`으로 재고를 뺀다. 하나라도 실패하면 전체 [Rollback](glossary:rollback)
5. 상품 이름과 가격을 주문 항목에 [Snapshot](glossary:snapshot)으로 복사한다. 나중에 가격이 바뀌어도 주문은 그대로다

[Concurrency test](glossary:concurrency-test) `test_nfr15_last_stock_concurrent_orders`는 3절 [Spike](glossary:spike)의 기대값을 그대로 박았다. 파일 [SQLite](glossary:sqlite)에서 스레드 10개로 로컬 3회 모두 [201](glossary:http-status-code) 1건, [409](glossary:http-status-code) 9건, 재고 0, 주문 1행이었다.

#100 리뷰에서 8건이 나와 전부 고쳤다. 주문 번호 충돌만 [409](glossary:http-status-code) `RETRY`로 바꾸고 다른 제약 위반은 [500](glossary:http-status-code)으로 남겼다(전부 `RETRY`로 뭉개면 버그가 숨는다).

상품 쪽은 목록(#91)이 한 쪽 20개에 최신순, `STOPPED` 숨김, 검색·원산지·가격대·로스팅 필터를 AND로 묶는다. 목록과 상세가 같은 쿼리 함수 `customer_products()`를 써서 "중지 상품 숨김" 규칙이 갈라지지 않고, 옵션 3개짜리 상세는 쿼리 2번이다. [Seed data](glossary:seed-data) `seed_demo`(#99)는 기본값으로 원두 100개, 회원 50명, 주문 [500](glossary:http-status-code)건을 고정 시드로 만든다. 주문은 상태 7개에 71~72건씩 나뉘고 파일 [SQLite](glossary:sqlite)에서 1.71초(1회 측정)였다. 데이터가 있는 DB는 거부하고 `DEBUG=False`면 `--force`가 필요하다.

## 7. 결제: 먼저 재고, 그다음 코드

결제창은 브라우저가 열고 [Payment approval](glossary:payment-approval)은 서버가 [Toss Payments](glossary:toss-payments) [API](glossary:api)로 한다. 승인 응답 모양과 두 번 취소했을 때의 오류를 모르고 짜면 추측으로 짜게 되어서, 결제 코드 전에 [Spike](glossary:spike)를 돌렸다(#92, #105).

![결제 흐름 다이어그램. 브라우저가 POST /api/orders/id/payments/로 결제를 시작하면 서버가 READY 결제 행을 만든다. 브라우저가 토스 결제창을 열고 성공하면 successUrl로 paymentKey, orderId, amount를 받는다. 브라우저가 POST /api/payments/confirm/을 보내면 서버가 금액을 시작 금액과 비교하고, 같을 때만 트랜잭션 밖에서 토스 confirm API를 부른다. status가 DONE이면 결제 SUCCESS, 주문 PAID. 금액이 다르면 PG를 부르지 않고 CANCELLED, 409 PAYMENT_MISMATCH](/static/images/coffee-shop-04-backend-features/payment-flow.svg)

테스트 결제 두 건(각 1,000원)으로 쟀다. 원본 호출 9건은 `paymentKey`를 가려 `spikes/toss-confirm-cancel/results/calls.jsonl`에 있다.

| 단계 | 확인                                | 결과                                                                                                     |
| ---- | ----------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 2    | 승인                                | 200 `DONE`, `method: "간편결제"`, `approvedAt`에 +09:00(1,313 ms / 551 ms)                               |
| 3    | 전액 취소, 다른 키로 두 번째 취소   | 200 `CANCELED`(585 ms), 두 번째는 400 `ALREADY_CANCELED_PAYMENT`(215 ms)                                 |
| 4    | 결제창과 다른 금액으로 승인         | [403](glossary:http-status-code) `FORBIDDEN_REQUEST`(211 ms). 결제는 남아 있어 맞는 금액으로 다시 승인됨 |
| 5    | 결제창을 X로 닫기                   | `failUrl`로 안 가고 `requestPayment()`가 `USER_CANCEL`로 실패(2회 모두)                                  |
| 6    | 10분 지난 결제 승인                 | 안 쟀다                                                                                                  |
| 7    | 같은 `Idempotency-Key`로 취소 두 번 | 둘 다 200, 같은 본문(616 ms / 89 ms). 취소는 1건                                                         |

- **4단계가 설계를 바꿨다.** 원래는 "승인한 뒤 금액이 다르면 [PG](glossary:payment-gateway)에서 취소"였는데 [Toss](glossary:toss-payments)가 다른 금액의 승인 자체를 [403](glossary:http-status-code)으로 거절해서 그 경로에 닿지 않는다. 확인 요청 금액이 결제 시작 때와 다르면 **[PG](glossary:payment-gateway)를 부르지 않고** 결제를 `CANCELLED`로 닫고 [409](glossary:http-status-code) `PAYMENT_MISMATCH`를 돌려주게 바꿨다(#105). 승인 뒤 취소 경로는 [PG](glossary:payment-gateway)가 다른 `totalAmount`를 보고하는 경우의 방어로 남겼다.
- **7단계가 취소 승인의 순서를 정했다.** 같은 [Idempotency key](glossary:idempotency-key)(`cancel-<payment_id>`)로 다시 보내면 첫 결과가 오니, **[PG](glossary:payment-gateway) 취소를 먼저 하고 DB를 나중에** 바꿔도 끊긴 요청을 안전하게 다시 보낼 수 있다.
- **5단계는 화면 규칙이 됐다.** `failUrl`만 보면 창 닫기를 놓치니 `requestPayment()`의 오류를 직접 받는다(8절).
- 6단계는 문서에 "공개 문서 기준 10분 지나면 승인 실패" 가정으로 미결에 남겼다.

결제 코드(#102)의 규칙은 셋이다.

- [Toss](glossary:toss-payments)를 부르는 코드는 `orders/pg.py`의 `TossPaymentsClient` 하나뿐이고, 테스트는 `FakePaymentsClient`를 쓴다.
- [PG](glossary:payment-gateway) 호출은 DB [Transaction](glossary:transaction) 밖에서 한다. 외부 호출이 [Timeout](glossary:timeout) 10초까지 걸릴 수 있는데 그동안 [SQLite](glossary:sqlite) [Write lock](glossary:write-lock)을 잡고 있으면 다른 주문이 전부 멈춘다.
- [Toss](glossary:toss-payments) `status == "DONE"`만 승인으로 본다. [Timeout](glossary:timeout), 5xx, JSON이 아닌 응답, 끊긴 연결은 결제를 `READY`로 두고 [502](glossary:http-status-code) `PG_ERROR`를 돌려준다.

#102 리뷰에서 8건이 나왔고 고칠 때마다 옛 코드에서 실패하는 [Regression test](glossary:regression-test)를 먼저 붙였다. 제일 무거운 건, 승인 중인 결제를 새 결제 시도가 대체하면 성공 결제가 없는데도 주문이 `PAID`가 될 수 있는 경우였다.

## 8. 프론트엔드 화면

화면은 [Wireframe](glossary:wireframe)(HW1)으로 흐름을, 디자인 캔버스(BeanShop UI, 18장)로 모양을 정한 뒤 11월 23일 하루에 [PR](glossary:pull-request) 다섯 개(#111, #113, #115, #117, #119)로 만들었다. 원칙은 **화면은 판단하지 않는다**였다. 어떤 버튼을 보여 줄지, 결제를 다시 해도 되는지는 서버가 응답에 담아 주고 화면은 그대로 그린다.

### 토큰 갱신: 한 번만, 다 같이 기다리기

[Access token](glossary:access-token)은 30분이면 만료된다. 만료된 채로 화면이 [API](glossary:api)를 세 개 동시에 부르면 셋 다 [401](glossary:http-status-code)을 받고, 각자 [Refresh token](glossary:refresh-token)을 보내면 갱신이 세 번 나간다.

![토큰 갱신 다이어그램. 요청 A, B, C가 동시에 401을 받는다. 첫 번째가 refreshAccess()로 POST /api/auth/token/refresh/를 보내고 그 Promise를 refreshing 변수에 둔다. B와 C는 같은 Promise를 기다린다. 새 액세스 토큰이 오면 셋 다 _retried 표시를 달고 한 번씩 다시 보낸다. 리프레시가 실패하면 토큰을 지우고 /login?next=로 보낸다](/static/images/coffee-shop-05-frontend/token-refresh.svg)

`api/client.js`의 응답 [Interceptor](glossary:interceptor)가 이렇게 한다.

- [401](glossary:http-status-code)이고, 이미 다시 보낸 요청(`_retried`)이 아니고, 로그인·갱신 요청 자체가 아니면 갱신을 시도한다
- 진행 중인 갱신이 있으면 그 [Promise](glossary:promise)를 같이 기다리고, 없으면 새로 만든다. 끝나면 비운다
- 새 토큰으로 원래 요청을 **한 번만** 다시 보낸다. `_retried`가 무한 반복을 막는다
- [Refresh token](glossary:refresh-token)이 없거나 갱신이 실패하면 토큰을 지우고 `/login?next=<지금 경로>`로 보낸다

토큰 키를 읽고 쓰는 파일은 `auth/tokenStore.js` 하나뿐이다. 토큰 안 `role`은 관리자 메뉴를 보여 줄지만 정하고, 실제 차단은 서버가 관리자 요청마다 DB의 역할을 다시 보고 [403](glossary:http-status-code)을 내는 것이다(NFR-10).

### 주문과 결제 화면

결제창은 브라우저를 다른 페이지로 보냈다가 돌려보내고, 사람이 중간에 창을 닫을 수도 있다.

![주문/결제 화면 흐름 다이어그램. 첫 클릭은 POST /api/orders/로 주문을 만들고 바로 결제를 시작해 토스 결제창을 연다. 두 번째 클릭부터는 이미 만든 주문으로 결제만 다시 연다. 결제창이 successUrl로 돌아오면 /checkout/result가 confirm을 한 번만 보낸다. PG_ERROR면 다시 확인 버튼, PAYMENT_MISMATCH면 실패 안내. 창을 닫으면 requestPayment()가 USER_CANCEL로 실패해 주문/결제 화면에 취소 안내가 뜨고, failUrl로 돌아온 실패는 결과 화면이 fail API로 기록한다. 주문은 상세 화면에서 다시 결제할 수 있다](/static/images/coffee-shop-05-frontend/checkout-flow.svg)

- **첫 클릭은 주문 생성 + 결제창, 두 번째부터는 결제만.** 결제창을 닫고 다시 누를 때마다 주문이 새로 생기면 재고가 그만큼 잠긴다(#115).
- **결제 확인은 한 번만.** `/checkout/result`는 `useRef`로 확인 요청을 한 번만 보낸다. [StrictMode](glossary:strictmode)가 개발 모드에서 effect를 두 번 돌려도 마찬가지다. 서버 확인 [API](glossary:api)가 [Idempotency](glossary:idempotency)를 지켜 두 번 가도 망가지진 않지만, 결과가 두 번 깜빡이지 않게 막았다.
- **느린 [PG](glossary:payment-gateway)와 실패를 구분한다.** [502](glossary:http-status-code) `PG_ERROR`는 "다시 확인" 버튼을, [409](glossary:http-status-code) `PAYMENT_MISMATCH`는 실패 안내를 보여 준다.
- **창 닫기는 오류로 받는다.** 7절 5단계 결과대로 `lib/pay.js`가 `USER_CANCEL` 오류를 직접 받아 "결제를 취소했습니다."를 띄운다. `failUrl`로 돌아온 실패만 결과 화면이 `/api/payments/fail/`로 남긴다.

버튼도 서버가 정한다. 내 주문 상세의 취소·취소 요청·다시 결제는 응답의 `can_*` 값으로, 관리자 주문 상세의 준비·발송·배송 완료·취소 승인·반려는 `allowed_actions`에 있는 것만 그린다(#119). 화면이 상태 표를 따로 들고 있으면 [Backend](glossary:backend)가 전환 규칙을 고칠 때 틀린 버튼이 나온다. 그래도 오래된 화면에서 누른 버튼은 서버의 [Conditional UPDATE](glossary:conditional-update)에서 [409](glossary:http-status-code)로 끝난다.

운영 서버는 결제가 꺼져 있어서(9절) #115를 이 상태로 확인했다. 결제를 누르면 [503](glossary:http-status-code) `PAYMENTS_DISABLED` 안내가 뜨고 주문은 상세 화면에서 나중에 결제할 수 있는 상태로 남는다. **실제 [Toss](glossary:toss-payments) 결제창은 이 [Frontend](glossary:frontend)에서 한 번도 열어 보지 않았다.** 결제 확인·실패·재결제 흐름은 [vitest](glossary:vitest)의 [Mock](glossary:mock) 응답으로만 확인했다.

## 9. 되돌릴 수 있는 Deployment

### 키가 없어도 서버는 뜨게(#108)

이 프로젝트 전용 [Toss](glossary:toss-payments) 테스트 키가 아직 없었다. 키가 없으면 서버가 못 뜨는 구조면 쇼핑몰 전체가 결제 하나에 묶인다. 그래서 `TOSS_SECRET_KEY`가 비어 있으면 `PAYMENTS_ENABLED`가 거짓이 되게 했다. 결제 시작·확인·관리자 취소 승인은 [PG](glossary:payment-gateway)와 DB에 닿기 전에 [503](glossary:http-status-code) `PAYMENTS_DISABLED`로 멈추고, 나머지는 그대로 돈다. [Kill switch](glossary:kill-switch)를 코드 경로가 아니라 키 유무 하나로 정한 셈이다.

반대로 위험한 설정에는 서버가 아예 안 뜨게 했다(`config/checks.py`). `DEBUG`가 꺼졌는데 `ALLOWED_HOSTS`가 비면 시작 거부, `TOSS_SECRET_KEY`가 `test_`로 시작하지 않아도 시작 거부다. 라이브 키가 잘못 들어가 진짜 돈이 오가는 일을 시작 단계에서 막는다. 새 테스트 6개는 모두 바꾸기 전 코드에서 실패하는 걸 확인했다.

### deploy.sh

![배포 스크립트 다이어그램. /srv/coffee-shop/releases 아래에 태그마다 폴더가 있다. deploy.sh는 새 태그를 새 폴더에 clone하고 main 조상인지 확인, venv와 pip install, 프론트엔드 빌드와 version.txt, 배포 전 DB 백업, migrate를 한 뒤 current 심볼릭 링크를 새 폴더로 바꾼다. 헬스 체크와 version.txt가 맞으면 끝, 아니면 current를 직전 폴더로 되돌린다. DB와 .env는 릴리스 폴더 밖에 있다](/static/images/coffee-shop-06-deploy/release-switch.svg)

`deploy/deploy.sh release-YYYYMMDD-N`은 [Release tag](glossary:release-tag) 하나를 받아 새 폴더에 올리고, [Health check](glossary:health-check)가 통과해야만 `current` [Symbolic link](glossary:symbolic-link)를 넘긴다.

1. 태그 형식 확인(틀리면 [Exit code](glossary:exit-code) 2), `.env`가 없으면 멈춤
2. 태그를 `releases/<태그>/`에 clone하고 커밋이 `main`의 조상인지 확인(아니면 지우고 멈춤)
3. [Backend](glossary:backend) venv와 `pip install`, [Frontend](glossary:frontend) `npm ci`와 빌드. 빌드에 커밋 해시를 담은 `version.txt`를 넣는다
4. [Deployment](glossary:deployment) 전 [Database backup](glossary:database-backup), `migrate`
5. `current.new`를 만들고 `mv -T`로 `current`와 바꾼다(교체가 한 번에 일어난다)
6. `/api/health/`와 [nginx](glossary:nginx)가 내주는 `version.txt`가 이 커밋인지 확인. 실패하면 `current`를 직전 릴리스로 되돌리고, DB를 되돌려야 하면 백업 경로를 알려 준다
7. 릴리스는 최근 3개만 남긴다

DB 파일과 `.env`는 릴리스 폴더 밖(`/srv/coffee-shop/data/`, `/srv/coffee-shop/.env`)에 있어 링크를 바꿔도 그대로다. 같은 [PR](glossary:pull-request)에 [nginx](glossary:nginx) 설정 틀, 보안 헤더, 쿼리 문자열을 뺀 로그 형식, [Cloudflare](glossary:cloudflare) 주소 대역에서 온 요청만 [CF-Connecting-IP](glossary:cf-connecting-ip)를 믿게 하는 스크립트, [systemd](glossary:systemd) 유닛(앱, 매일 04:00 백업 타이머), [journald](glossary:journald) 크기 제한, 처음 설치용 `install.sh`가 들어갔다.

## 10. 자동 Deployment(CD)

#127 뒤로는 `main`에 머지하는 것이 사람이 하는 유일한 단계다.

![자동 배포 다이어그램. main에 push되면 ci 워크플로가 돌고, 성공하면 deploy 워크플로가 workflow_run으로 시작한다. DEPLOY_ENABLED가 true일 때만 진행한다. 다음 release-YYYYMMDD-N 태그를 고르고, GitHub OIDC로 IAM 역할을 받은 뒤 태그를 push한다. SSM Run Command(AWS-RunShellScript)로 EC2에서 deploy.sh 태그를 돌리고 결과를 출력한다. 마지막으로 Cloudflare를 거쳐 version.txt를 읽어 커밋과 같은지 본다. 22번 포트는 GitHub에 열지 않고, SSM 에이전트가 밖으로 443을 쓴다](/static/images/coffee-shop-06-deploy/cd-flow.svg)

`.github/workflows/deploy.yml`의 규칙이다.

- **언제 도나.** `ci`가 `main` push에서 성공했을 때(`workflow_run`) 또는 수동 실행. 자동 실행은 그 커밋이 더는 `main` 끝이 아니거나, 이미 릴리스 태그가 있거나, 지난 태그 뒤로 문서만 바뀌었으면 건너뛴다.
- **자격 증명이 먼저, 태그가 나중.** [IAM](glossary:aws-iam-role) 역할을 못 받으면 태그도 안 남는다.
- **[SSH](glossary:ssh)가 아니라 [SSM](glossary:aws-systems-manager).** [GitHub Actions](glossary:github-actions) 러너에 22번 포트를 열지 않는다. 서버의 [SSM](glossary:aws-systems-manager) 에이전트가 밖으로 443을 열어 명령을 받아 간다. 역할 권한은 이 레포 `main`에서 온 요청만, 그 인스턴스 하나에 `AWS-RunShellScript`로 `ssm:SendCommand`하는 것과 결과 읽기뿐이다.
- **한 번에 하나.** `concurrency: deploy-production`, `cancel-in-progress: false`. 중간에 끊기면 안 되니 다음 실행은 기다린다.
- **오래 사는 비밀이 없다.** Actions [Secret](glossary:secret) 세 개(역할 ARN, 인스턴스 ID, 운영 URL)는 비밀이 아니라 식별자인데, 공개 레포 로그에서 가려지게 [Secret](glossary:secret)에 넣었을 뿐이다.
- **기본은 꺼짐.** 저장소 변수 `DEPLOY_ENABLED`가 `true`일 때만 돈다. AWS 설정 전에 머지해도 아무 일도 안 일어난다.

태그 고르는 셸은 임시 레포에서 다섯 경우(첫 [Deployment](glossary:deployment), `ci` 재실행, 문서만 바뀜, `-10` 다음 번호, 이미 태그 있는 커밋의 수동 실행)로 돌려 봤다. AWS 쪽은 설정이 끝나야 돈다.

`manage.py check --deploy` 경고 넷(`SECURE_HSTS_SECONDS`, `SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`)은 HTTP → [HTTPS](glossary:https) 전환을 지금 [Cloudflare](glossary:cloudflare)가 하고 있어 [Django](glossary:django) 쪽에서도 켤지 아직 정하지 않았다.
