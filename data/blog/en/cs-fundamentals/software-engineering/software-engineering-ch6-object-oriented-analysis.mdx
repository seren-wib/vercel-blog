# 6. Object-Oriented Analysis: Preliminary Design

## 6.2 UML

### 6.2.1 UML Overview

**[UML](glossary:uml)**: the standard modeling language for drawing a system design as diagrams. A common language so analysts, designers and developers can talk while looking at the same picture

### 6.2.2 UML Diagram Types

![UML 2.5 diagram classification](/static/images/software-engineering-ch6-object-oriented-analysis/uml-diagram-types.svg)

**[UML](glossary:uml) 2.5 diagrams**: two groups, structure and behavior, 14 in total

- **[Structure diagrams](glossary:structure-diagram)**: the static structure of the system. What exists and how it is connected, no flow of time (e.g. [class diagram](glossary:class-diagram))
  - Types: [class](glossary:class-diagram), object, package, composite structure, [component](glossary:component-diagram), [deployment](glossary:deployment-diagram), profile (7)
- **[Behavior diagrams](glossary:behavior-diagram)**: how the system moves as time passes (e.g. [sequence diagram](glossary:sequence-diagram))
  - Types: [use case](glossary:use-case-diagram), [activity](glossary:activity-diagram), [state machine](glossary:state-machine-diagram), interaction (4)
  - Interaction diagrams split into: [sequence](glossary:sequence-diagram), [communication](glossary:communication-diagram), timing, interaction overview (4)
- The three used in this chapter: [use case](glossary:use-case-diagram) → behavior, [class](glossary:class-diagram) → structure, [sequence](glossary:sequence-diagram) → behavior (interaction)

### 6.2.3 UML Tools

- Both commercial and open source: [StarUML](glossary:staruml), [Draw.io](glossary:drawio), [Visio](glossary:microsoft-visio), [Lucidchart](glossary:lucidchart), etc.
- The representative one is [StarUML](glossary:staruml)

### 6.2.4 StarUML

**[StarUML](glossary:staruml)**: the most popular commercial [UML](glossary:uml) software. Aims at agile, concise modeling

- Features: multi-platform (Mac, Windows, Linux), [UML](glossary:uml) 2.x compliant, [SysML](glossary:sysml), [ERD](glossary:er-diagram), [DFD](glossary:dfd) and [flowcharts](glossary:flowchart), open API, export to HTML docs

## 6.3 Functional Modeling: Use Case Diagram

### 6.3.1 Use Case Diagram

**[Functional modeling](glossary:functional-modeling)**: drawing "what" the system does from the user's point of view. In object-oriented analysis it is expressed with a [use case diagram](glossary:use-case-diagram)

**[Use case](glossary:use-case)**: one function the system performs to give an [actor](glossary:actor) a result (e.g. Register Course). One [GUI](glossary:gui) menu = one [use case](glossary:use-case)

![Use case diagram notation](/static/images/software-engineering-ch6-object-oriented-analysis/usecase-notation.svg)

- **[Actor](glossary:actor)**: a role outside the system that interacts with it. A stick figure. Not only people but also external systems (DB, character recognition system) are [actors](glossary:actor)
  - In the figure: the Student stick figure, the Personal Information System box
- **[Use case](glossary:use-case)**: an ellipse with a name. Two or more [actors](glossary:actor) may attach to one [use case](glossary:use-case)
- **System boundary**: a large rectangle. [Use cases](glossary:use-case) inside, [actors](glossary:actor) outside. The name is written as `<System Name>`
- **External system**: a name inside a rectangle, placed outside the boundary
- **Line ([association](glossary:association))**: between an [actor](glossary:actor) and a [use case](glossary:use-case). "This [actor](glossary:actor) performs this [use case](glossary:use-case)"
- **[include](glossary:include-relationship)**: dashed arrow + `<<include>>`. A sub [use case](glossary:use-case) that **always** runs when the base runs (e.g. Register Course → Login, Recognize → preprocessing, segmentation, classification, output)
  - Direction: base → included
- **[extend](glossary:extend-relationship)**: dashed arrow + `<<extend>>`. An exceptional or optional extension. It **may not be called** even when the base runs (e.g. Purchase Item ← No Change Left, Register Course ← Add to Cart)
  - Direction: extension → base. Opposite of [include](glossary:include-relationship)
- **[Generalization](glossary:generalization)**: solid line + hollow triangle, child → parent. [Inheritance](glossary:inheritance) that lifts the common part up to a parent
  - Four kinds: [actor](glossary:actor) [generalization](glossary:generalization) (student, professor → person), [use case](glossary:use-case) [generalization](glossary:generalization) (Pay Bill → pay by card, pay by balance), between two [extend](glossary:extend-relationship) [use cases](glossary:use-case), between two [include](glossary:include-relationship) [use cases](glossary:use-case)
  - [Actor](glossary:actor) [generalization](glossary:generalization) helps find [inheritance](glossary:inheritance) in the next step, the [class diagram](glossary:class-diagram)
- Slide note: p.29–30 treats register, cancel, change and view course as [extends](glossary:extend-relationship) of Login, while p.32 says Register Course [includes](glossary:include-relationship) Login. When drawing, stay consistent: **required means [include](glossary:include-relationship), optional means [extend](glossary:extend-relationship)**
- [Front-end](glossary:frontend)/[back-end](glossary:backend) (p.41): [use case](glossary:use-case) = a [front-end](glossary:frontend) (JSP, PHP, app) menu action, [class](glossary:class) [method](glossary:operation) = [back-end](glossary:backend) (Java, C#, Python) [insert, delete, update, retrieve](glossary:crud)

### 6.3.4 Benefits of Use Case Diagrams

1. Estimate system **complexity and cost** from the list of business goals
2. Capture **real requirements** early in design
3. Scenarios in **natural language**, so even customers and managers understand
4. Identifying extension [use cases](glossary:use-case) and exceptions makes complex requirements easier to define, **saving developer time**
5. Identifying the development **boundary** prevents scope from growing or shrinking
6. Focus on "**what**", not "how", which prevents premature design
7. [Use cases](glossary:use-case) convert directly into **[test cases](glossary:test-case)**

### 6.3.5 Use Case Specification

|          | [Use case](glossary:use-case)                                        | [User story](glossary:user-story)                                                        |
| -------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Focus    | **How the system works**, the sequence of user-system interactions   | The **benefit** gained from an activity, what the user will do                           |
| Detail   | Concrete. Later becomes a **[method](glossary:operation) algorithm** | Less documented, details left out on purpose                                             |
| Used for | Developers and testers understanding every system step               | Starting conversations in **[agile](glossary:agile)** ([Scrum](glossary:scrum)) meetings |

- Both identify users and describe goals, but they are not interchangeable

![Use case specification template](/static/images/software-engineering-ch6-object-oriented-analysis/usecase-spec-template.svg)

- One specification table per ellipse in the diagram
- It has a Method Name → a [use case](glossary:use-case) leads to a [method](glossary:operation). Brief Processing Descriptions lead to the 6.6 algorithm specification
- Specific Requirements hold [non-functional requirements](glossary:non-functional-requirement) (cash transfer within 30 minutes)

## 6.4 Structural Modeling: Class Diagram

### 6.4.1 Elements of a Class Diagram

**[Structural modeling](glossary:structural-modeling)**: drawing the static skeleton of the system (what exists and how it is connected). Tools are [class](glossary:class-diagram), object, [deployment](glossary:deployment-diagram), package, composite structure and [component diagrams](glossary:component-diagram); the [class diagram](glossary:class-diagram) is used the most

![Class box structure](/static/images/software-engineering-ch6-object-oriented-analysis/class-box.svg)

- **[Class](glossary:class) box**: a rectangle with three compartments
  - In the figure: name, [attributes](glossary:attribute), [operations](glossary:operation) from the top
- **[Class](glossary:class) name**: top compartment. First letter uppercase (slide notation: `Class 학생(Student)`)
- **[Attributes](glossary:attribute)**: middle compartment. First letter lowercase (e.g. student number, name, address, phone, department)
  - [Access modifiers](glossary:access-modifier): [private](glossary:access-modifier), [protected](glossary:access-modifier), [public](glossary:access-modifier). [Attributes](glossary:attribute) are usually [private](glossary:access-modifier)
- **[Operations](glossary:operation)**: bottom compartment. First letter lowercase, following words capitalized (e.g. getName, setAddress)
  - Basic [operations](glossary:operation): [insert, delete, update, retrieve](glossary:crud)
- In analysis you may leave the [operations](glossary:operation) compartment empty and draw only up to [attributes](glossary:attribute) (p.47 right; the example diagrams have two compartments too)

### 6.4.2 Types of Relationships Between Classes

![Class relationship symbols](/static/images/software-engineering-ch6-object-oriented-analysis/class-relationships.svg)

**Relationships between [classes](glossary:class)**: logical connections between [classes](glossary:class). Six types per the slides

| Relationship                                               | Line   | End                         | Meaning                                                                           | Example                                           |
| ---------------------------------------------------------- | ------ | --------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------- |
| [Association](glossary:association)                        | solid  | open arrow                  | 1:1, 1:N, N:1, N:M correspondence                                                 | Department 1 — \* Student                         |
| [Inheritance](glossary:inheritance)                        | solid  | hollow triangle             | is-a, child → parent                                                              | Student → Person                                  |
| [Specialization](glossary:specialization) / implementation | dashed | hollow triangle             | put the parent first, then find the children                                      | Person → Student, Professor                       |
| [Dependency](glossary:dependency)                          | dashed | open arrow                  | a change in one [class](glossary:class)'s structure or behavior affects the other | when one [class](glossary:class) contains another |
| [Aggregation](glossary:aggregation)                        | solid  | hollow diamond (whole side) | has-a, the part can live on its own                                               | Department ◇— Student                             |
| [Composition](glossary:composition)                        | solid  | filled diamond (whole side) | consist-of, a part of. Deleting the whole deletes the parts                       | Computer ◆— CPU, memory                           |

- **[Association](glossary:association) [multiplicity](glossary:multiplicity)**: write `1`, `*`, `0~*` at both ends of the line
  - 1:1 student - record, 1:0~N employee - dependents, 1:N department - student, N:1 student - department, N:M student - offered course
- **Expressing N:M**: [E-R](glossary:er-diagram) uses a diamond (Takes); a [class diagram](glossary:class-diagram) puts an **[association class](glossary:association-class)** in the middle (`Takes`: student number, offered course number, type, year, semester, grade) and splits both sides into 1:N
- **[Generalization](glossary:generalization) vs [specialization](glossary:specialization)**: same diagram and implementation, only the direction of discovery differs
  - [Generalization](glossary:generalization): look at student and professor and extract the common part into person (bottom-up)
  - [Specialization](glossary:specialization): put person first and find student and professor (top-down)
- **[Aggregation](glossary:aggregation) vs [composition](glossary:composition)**: [aggregation](glossary:aggregation) is a special case of [association](glossary:association), [composition](glossary:composition) a special case of [aggregation](glossary:aggregation). The difference is whether the part's lifecycle is bound to the whole
- Slide note: the p.49 symbol table draws [aggregation](glossary:aggregation) and [composition](glossary:composition) with dashed lines, but the p.54–55 examples use solid lines. The dashed triangle on p.49 ([specialization](glossary:specialization)) is the interface realization symbol in real [UML](glossary:uml)

### 6.4.3 Class Diagram Example: Course Registration System

![Course registration system class diagram](/static/images/software-engineering-ch6-object-oriented-analysis/class-course-registration.svg)

- Order: requirements table (p.57) → extract [classes](glossary:class) from nouns (p.58 cloud: student, staff, department, syllabus, course list, offered course, space) → [E-R](glossary:er-diagram) → [class diagram](glossary:class-diagram)
- Every N:M becomes an [association class](glossary:association-class): Takes (student - offered course), Teaches (professor - offered course), AssignRoom (offered course - classroom), DoubleMajor (student - department)

  - Student - department is N:1, but minors, double majors, teacher training and convergence majors exist, so put **two [associations](glossary:association)** between the two [classes](glossary:class) (one direct line + one through DoubleMajor)

## 6.5 Dynamic Modeling: Sequence Diagram

### 6.5.1 Design Target of Sequence Diagrams

**[Dynamic modeling](glossary:dynamic-modeling)**: drawing how the system moves over time (timing and order of work, control flow)

- **State**: a situation an object is in under some condition during its life (e.g. order "awaiting payment")
- **Transition**: a change of state (awaiting payment → paid)
- **Event**: the occurrence that triggers a transition (clicking the pay button)
- **Action**: a basic operation triggered by an event that is not interrupted
- Diagrams for [dynamic modeling](glossary:dynamic-modeling)
  - **Interaction diagrams**: [sequence diagram](glossary:sequence-diagram), collaboration diagram (the [communication diagram](glossary:communication-diagram) in [UML](glossary:uml) 2)
  - **[State transition diagram](glossary:state-machine-diagram)**
  - Slide note: p.64 says "the [state transition diagram](glossary:state-machine-diagram) is subdivided into two kinds", but it is the interaction side that splits in two (p.65)

**[Sequence diagram](glossary:sequence-diagram)**: a time-ordered drawing of **which messages, and when,** users, screens, objects and external systems exchange while one [use case](glossary:use-case) runs (e.g. press the register button: menu → look up offered course → cart → save registration)

- Placed next to its [use case](glossary:use-case) to help understand that [use case](glossary:use-case)'s processing algorithm
- In the end it is the **order of [method](glossary:operation) calls** between [front-end](glossary:frontend) objects

![Sequence diagram design target](/static/images/software-engineering-ch6-object-oriented-analysis/sequence-design-target.svg)

- **Design target = every [use case](glossary:use-case)**: one [sequence diagram](glossary:sequence-diagram) per [use case](glossary:use-case)
  - In the figure: each [front-end](glossary:frontend) [use case](glossary:use-case) box at the bottom is one [sequence diagram](glossary:sequence-diagram), calling [CRUD](glossary:crud) [methods](glossary:operation) of the [back-end](glossary:backend) [classes](glossary:class) at the top
- Links: 6.3 [use case](glossary:use-case) = [front-end](glossary:frontend) menu, 6.4 [class](glossary:class) = [back-end](glossary:backend) data and [CRUD](glossary:crud), 6.5 [sequence](glossary:sequence-diagram) = the order of [method](glossary:operation) calls when one menu is pressed

![How to read a sequence diagram](/static/images/software-engineering-ch6-object-oriented-analysis/sequence-notation.svg)

- **[Actor](glossary:actor)**: stick figure, far left
- **Object**: rectangle, `:ClassName` (e.g. `:Student` = some object of the Student [class](glossary:class)). Menu screens also stand as objects
- **[Lifeline](glossary:lifeline)**: vertical dashed line below an object. Time flows downward
- **Message**: solid arrow + method name (e.g. `check(id, pwd)`)
- **Reply**: dashed arrow + return value (e.g. `ok`, `Not exists`)
- **Self call**: a curved arrow returning to itself. Processing inside one object (e.g. `Input data`, `Choose(sectionId)`)

## 6.6 Representing Method Algorithms

### 6.6.1 Ways to Represent Algorithms

- Four ways: [pseudocode](glossary:pseudocode), [flowchart](glossary:flowchart), natural language (English, Korean), ordinary programming language

**[Pseudocode](glossary:pseudocode)**: "fake code" mixing natural language with programming language structure. More precise and concise than natural language, but there is no standard (e.g. `IF stock > 0 THEN sell ELSE soldOut ENDIF`)

### 6.6.2 Specifying Algorithms in the Requirements Analysis Phase

**[Method](glossary:operation) algorithm specification**: attaching a header comment block + body algorithm to each [method](glossary:operation) (e.g. [insertionSort](glossary:insertion-sort) header block + [insertion sort](glossary:insertion-sort) code)

- Header block fields: Method ID, Interface (function signature), Function (one line on what it does), Parameter, Return value
- Goes into [SRS](glossary:srs) item 9, "[method](glossary:operation) algorithm specification of [classes](glossary:class)", in this form for each [method](glossary:operation)

## 6.8 Software Requirements Specification (SRS) Template

- Overall flow: overview → what (functional, domain) → how well (non-functional) → how it meets the outside (interfaces) → how to build it (preliminary design) → review, conclusion. Items 1–5 are chapter 4 requirements analysis, items 6–9 are chapter 6 preliminary design

**[SRS](/en/blog/cs-fundamentals/software-engineering/software-engineering-ch4-requirements-analysis/#433-step-3-requirements-specification-software-requirements-specification-srs)**: the results of requirements analysis bundled into one document. The baseline where the development team and the customer agree "this is what we build"

### 6.8.1 Overview

- 1.1 development goals, 1.2 development scope and content, 1.3 product value, 1.4 target customers, 1.5 usage scenarios, [1.6 work breakdown structure (WBS)](/en/blog/cs-fundamentals/software-engineering/software-engineering-ch3-project-planning/#34-work-planning-and-scheduling), 1.7 glossary

### 6.8.2 [Functional Requirements](/en/blog/cs-fundamentals/software-engineering/software-engineering-ch4-requirements-analysis/#411-functional-requirements)

- [2.1 use case analysis](#63-functional-modeling-use-case-diagram), 2.2 [data processing flow diagram](glossary:dfd), 2.3 system tasks, 2.4 management functions, 2.5 transaction processing tasks, 2.6 details of tasks performed on every screen

### 6.8.3 [Domain Requirements](/en/blog/cs-fundamentals/software-engineering/software-engineering-ch4-requirements-analysis/#412-domain-requirements)

- No sub-items. The rules of the business domain itself (e.g. at most 24 credits per semester)

### 6.8.4 [Non-functional Requirements](/en/blog/cs-fundamentals/software-engineering/software-engineering-ch4-requirements-analysis/#42-non-functional-requirements)

- 15 items: performance, reliability, load and stress, security, operation (capacity), usability, compatibility, stability and availability, scalability, maintainability, installation, recovery, legal regulation and environment, risk analysis and constraints, documentation deliverables

- 5.1 user interface requirements and [GUI](glossary:gui) specification (or design), 5.2 hardware, 5.3 software, 5.4 communication

## 6.9 SRS Evaluation Criteria

**[SRS](glossary:srs) evaluation criteria**: standards for judging how well a requirements specification is written. Per the slides, the [IEEE 830](glossary:ieee-830):2009 quality model, 6 criteria

| Criterion                         | In one line                                                                                                                                                                                                                                         | Violation example                                                                                       |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Completeness                      | Is everything needed there, nothing missing (requirements, [classes](glossary:class) and [methods](glossary:operation), [use cases](glossary:use-case), figure and table labels, term and acronym definitions, all preliminary design deliverables) | glossary missing, a [use case](glossary:use-case) with no [sequence diagram](glossary:sequence-diagram) |
| Correctness (clarity)             | Is what's written a truly needed requirement, written accurately                                                                                                                                                                                    | a feature the customer never wanted                                                                     |
| Consistency                       | No conflicts or ambiguity inside the document (internal) or with higher-level documents (external)                                                                                                                                                  | max 24 credits in one place, 21 in another                                                              |
| Verifiability (traceability)      | After building, can you confirm and trace that requirements are met                                                                                                                                                                                 | "respond quickly" (write "within 3 seconds" to make it verifiable)                                      |
| Modifiability                     | Can it be changed easily, completely and consistently while keeping structure and style                                                                                                                                                             | the same requirement scattered in several places, so fixing one leaves the others out of sync           |
| Readability and understandability | Can stakeholders easily extract and understand the content                                                                                                                                                                                          | only acronyms and jargon with no explanation                                                            |

- Completeness vs correctness: is anything missing vs is what's there right
- Consistency vs verifiability: do requirements conflict vs can you check them after building
- [SRS](glossary:srs) item 10, "requirements review results", is filled using these 6 criteria
