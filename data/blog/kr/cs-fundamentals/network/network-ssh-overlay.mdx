> 폰·맥·데스크탑 세 대를 밖에서도 [SSH](glossary:ssh)로 오가려다 막힌 일을 원인부터 설정, 실제로 쓰는 비상 경로까지 정리했다. 2026-11-27에 데스크탑 설정을 끝내고 결과로 고쳐 썼다. 패킷이 계층마다 어떤 일을 겪는지는 [계층으로 본 네트워크](/kr/blog/cs-fundamentals/network/network-tcp-ip-layers/)에, [SSH](glossary:ssh) 연결 단계는 [웹 요청 하나가 서버까지 가는 전체 과정의 SSH 접속](/kr/blog/cs-fundamentals/network/network-web-request-journey/#15-ssh-접속)에 있다. 이 글은 그 두 글의 [NAT](glossary:nat)·포트·[SSH](glossary:ssh) 절을 실제 문제에 대 본 것이다.

# 0. 한눈에 보기

결론부터 쓰면, **망은 처음부터 있었고 [SSH](glossary:ssh) server가 없었다.** 데스크탑은 이미 [Tailscale](glossary:tailscale)로 맥과 이어져 있었는데, 데스크탑에는 접속을 받을 [sshd](glossary:sshd)가 없었고 Windows [firewall](glossary:firewall)이 들어오는 패킷을 버리고 있었다.

# 1. 상황

이 망에 넣은 기기는 세 대다. 이 글에서는 실제 이름 대신 아래 이름을 쓴다.

| 이름      | 기기             | 주로 있는 곳 | [SSH](glossary:ssh) 역할 |
| --------- | ---------------- | ------------ | ------------------------ |
| `phone`   | 폰(iOS)          | 들고 다님    | client만                 |
| `laptop`  | 맥               | 학교 Wi-Fi   | server + client          |
| `desktop` | Windows 데스크탑 | 집           | server + client          |

- iOS는 앱이 [sshd](glossary:sshd)를 띄워 접속을 받을 수 없다. 그래서 폰은 나가는 쪽(client)만 하고, 받는 쪽(server)은 맥과 데스크탑 둘이다.
- 패드도 처음엔 넣으려 했는데 잘 쓰지 않아서 이번 망에서 뺐다.

목적은 하나다. 밖에서 [Claude Code](glossary:claude-code)를 폰으로 이어 쓰는 [Remote Control](glossary:remote-control)이 꺼지면 폰에서는 다시 켤 방법이 없다. 그때 폰에서 [SSH](glossary:ssh)로 데스크탑에 들어가 다시 켜려는 것이다(8절).

어디서든 이 세 대 사이를 [SSH](glossary:ssh)로 오가고 싶었다. 데스크탑은 이미 [tailnet](glossary:tailscale)([Tailscale](glossary:tailscale)로 묶인 내 기기들의 네트워크)에 붙어 있었고, 맥에서 `tailscale ping`을 보내면 바로 답이 왔다.

```text
$ tailscale ping desktop
pong from desktop (100.x.y.z) via 203.0.113.x:41641 in 24ms
```

`via <IP:포트>`는 [relay](glossary:relay-server)를 거치지 않고 두 기기가 **직접(direct)** 이어졌다는 뜻이다. 그런데 같은 주소로 [SSH](glossary:ssh)(22)와 [RDP](glossary:rdp)(3389)을 열면 둘 다 한참 기다리다 끊겼다.

```text
$ ssh user@100.x.y.z
ssh: connect to host 100.x.y.z port 22: Operation timed out
```

## timed out과 refused는 다르다

문 앞까지 갔는데 아무 대답이 없는 것과, 누가 나와서 "여기 아니에요" 하고 문을 닫는 것의 차이다. 대답 없음이 **[drop](glossary:packet-drop)**, 문 닫기가 **[RST](glossary:tcp-rst)**다.

- 패킷이 도착했는데 그 포트에서 listen하는 프로그램이 없으면, OS의 TCP 스택이 **[RST](glossary:tcp-rst)**를 돌려준다. 클라이언트는 즉시 `Connection refused`를 받는다.
- 중간에서 누가 패킷을 **조용히 버리면([drop](glossary:packet-drop))** 클라이언트는 SYN을 몇 번 다시 보내다가 포기한다. 그게 `Operation timed out`이다.

그러니 [timed out](glossary:connection-timeout)은 "포트가 닫혔다"보다 "**누가 버리고 있다**"에 가깝다. 버리는 쪽은 보통 [firewall](glossary:firewall)이다. 여기서부터 어디서 버리는지를 계층별로 갈랐다.

# 2. 원인 가르기

건물 비유로 보면 확인할 게 셋이다. 건물까지 길이 있나, 경비실 명단에 내가 있나, 들어가려는 방 문이 열려 있고 안에 사람이 있나. 길은 [overlay](glossary:overlay-network)의 [L3](glossary:osi-model) 경로, 경비실 명단은 [Tailscale](glossary:tailscale) [ACL](glossary:acl), 방 문은 OS [firewall](glossary:firewall), 안에 있는 사람은 [sshd](glossary:sshd)다.

![이번에 확인한 네 군데: overlay 경로와 ACL은 통과, OS 방화벽과 sshd에서 막힘](/static/images/network-ssh-overlay/layer-checkpoints.svg)

_맥에서 데스크탑 22번으로 가는 패킷이 지나는 검문 네 곳. 초록은 통과, 빨강은 막힌 곳이다._

## 확인 1: overlay 경로 — 통과

`tailscale ping` 24 ms, direct. 두 기기 사이 [WireGuard](glossary:wireguard) 터널은 살아 있다.

다만 `tailscale ping`은 tailscaled([Tailscale](glossary:tailscale) 데몬)끼리 주고받는 [ping](glossary:ping)이라, OS의 [firewall](glossary:firewall)이나 [sshd](glossary:sshd)까지는 가지 않는다. 그래서 이 결과가 말해 주는 건 "[L3](glossary:osi-model) 경로가 있다"까지다. 22번이 열렸는지는 이걸로 알 수 없다.

## 확인 2: Tailscale ACL — 통과

처음엔 [ACL](glossary:acl)을 의심했다. [Tailscale](glossary:tailscale)은 관리 콘솔의 [ACL](glossary:acl)(정책 파일)을 각 기기에 **[packet filter](glossary:packet-filter)**로 내려보내고, 기기의 tailscaled가 그 규칙에 안 맞는 패킷을 버린다. 이것도 [drop](glossary:packet-drop)이라 [timed out](glossary:connection-timeout)이 난다.

그래서 맥이 실제로 받은 규칙을 봤다.

```bash
tailscale debug netmap
```

출력의 [packet filter](glossary:packet-filter) 부분에 데스크탑 ↔ 맥 사이 포트 **0-65535 허용** 규칙이 있었다. [ACL](glossary:acl)이 22번을 막고 있던 게 아니다. 다만 그때 정책에는 폰 → 맥을 허용하는 규칙이 없어서, 폰에서 맥으로 가는 패킷은 이 [packet filter](glossary:packet-filter)에서 막혔다. 이건 7절에서 [ACL](glossary:acl)을 바꿔 풀었다.

## 확인 3: OS — 여기서 막힘

남은 건 데스크탑 OS다.

- **[sshd](glossary:sshd)가 없었다.** Windows에는 [OpenSSH](glossary:openssh) **Client**만 기본으로 있고 **Server**는 따로 설치해야 한다. 22번에서 listen하는 프로그램이 없었다.
- **[Windows Defender Firewall](glossary:windows-defender-firewall)이 [drop](glossary:packet-drop)했다.** listen하는 프로그램이 없으면 원래는 [RST](glossary:tcp-rst)가 와야 하는데 [timed out](glossary:connection-timeout)이 났다. [firewall](glossary:firewall)이 들어오는 패킷을 먼저 버렸기 때문이다. 3389도 같은 이유로 [timed out](glossary:connection-timeout)이었다.

맥도 확인해 보니 시스템 설정의 **원격 로그인**이 꺼져 있었다. macOS의 [sshd](glossary:sshd)는 원격 로그인을 켜야 뜬다. 반대 방향(데스크탑 → 맥)도 처음부터 안 됐을 거라는 뜻이다.

## 결론

망은 처음부터 있었다. 비어 있던 건 그 위의 두 칸, **들어오는 포트를 허용하는 [firewall](glossary:firewall) 규칙**과 **접속을 받을 [SSH](glossary:ssh) server**였다.

# 3. 계층마다 필요한 것

택배로 치면 세 가지가 다 있어야 물건이 손에 들어온다. 주소로 찾아갈 수 있어야 하고(길), 건물 출입이 허락돼야 하고(출입), 받는 사람이 본인 확인을 해야 한다(신원). 길은 [L3](glossary:osi-model) [reachability](glossary:reachability), 출입은 [L4](glossary:osi-model) 포트·[firewall](glossary:firewall)·[ACL](glossary:acl), 신원은 [L7](glossary:osi-model) [SSH](glossary:ssh) 인증이다.

| 계층                     | 필요한 것              | 직접 [SSH](glossary:ssh)일 때                                                                                      | [Tailscale](glossary:tailscale) 위 [SSH](glossary:ssh)일 때                                                  |
| ------------------------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| [L3](glossary:osi-model) | 상대에게 닿는 경로     | [public IP](glossary:public-ip-address), 공유기 [port forwarding](glossary:port-forwarding), [DDNS](glossary:ddns) | [Tailscale](glossary:tailscale)이 [NAT traversal](glossary:nat-traversal)·[DERP relay](glossary:derp)로 해결 |
| [L4](glossary:osi-model) | 포트를 통과시키는 규칙 | 공유기 포워딩 규칙 + OS [firewall](glossary:firewall)                                                              | [Tailscale](glossary:tailscale) [ACL](glossary:acl) + OS [firewall](glossary:firewall)                       |
| [L7](glossary:osi-model) | 누구인지 확인·암호화   | [SSH](glossary:ssh) 인증([public key](glossary:public-key-authentication))과 암호화                                | 똑같이 [SSH](glossary:ssh) 인증과 암호화                                                                     |

[SSH](glossary:ssh)가 해결하는 건 **[L7](glossary:osi-model)뿐**이다. [SSH](glossary:ssh)는 연결이 맺어진 뒤의 인증과 암호화를 맡지, 상대 기기까지 가는 길을 만들어 주지 않는다.

## L3: 닿을 수 있나

- 집 데스크탑은 공유기 뒤의 [사설 IP](/kr/blog/cs-fundamentals/network/network-tcp-ip-layers/#사설-ip-공인-ip-nat)를 쓴다. 밖에서 먼저 들어오는 패킷은 [NAT](glossary:nat) 변환표에 항목이 없어서 버려진다. 들어오게 하려면 공유기에 **[port forwarding](glossary:port-forwarding)**을 걸고, 집 [public IP](glossary:public-ip-address)가 바뀌면 따라가도록 **[DDNS](glossary:ddns)**까지 붙여야 한다([NAT 뒤의 PC에 접속할 때](/kr/blog/cs-fundamentals/network/network-web-request-journey/#nat-뒤의-pc에-접속할-때)).
- 학교 Wi-Fi의 맥은 **학교 [NAT](glossary:nat)** 뒤에 있다. 학교 공유기는 내 장비가 아니라 [port forwarding](glossary:port-forwarding)을 걸 수 없다. 통신사 [CGNAT](/kr/blog/cs-fundamentals/network/network-tcp-ip-layers/#사설-ip-공인-ip-nat) 뒤의 폰도 같다. 밖에서 이 기기들로 직접 들어오는 건 원천적으로 불가능하다.

## L4: 들어갈 수 있나

[L3](glossary:osi-model) 경로가 있어도 [포트](/kr/blog/cs-fundamentals/network/network-tcp-ip-layers/#포트-번호와-다중화) 22를 통과시키는 규칙이 경로 위 모든 곳에 있어야 한다. 직접 [SSH](glossary:ssh)면 공유기 포워딩 규칙과 OS [firewall](glossary:firewall), [Tailscale](glossary:tailscale)이면 [Tailscale](glossary:tailscale) [ACL](glossary:acl)과 OS [firewall](glossary:firewall)이다. 이번엔 OS [firewall](glossary:firewall)이 막았다.

## L7: 누구인가

연결이 22번까지 닿으면 그다음은 [SSH](glossary:ssh)다. [host key](glossary:host-key)로 서버를 확인하고, [private key](glossary:public-key-authentication) 서명으로 사용자를 확인하고, 세션 키로 암호화한다.

## Tailscale이 L3에서 하는 일

![직접 노출은 공유기 포트를 인터넷 전체에 열고, overlay는 모든 기기가 밖으로만 연결을 연다](/static/images/network-ssh-overlay/direct-vs-overlay.svg)

_위: 공유기 [port forwarding](glossary:port-forwarding)으로 22를 연 경우. 아래: [Tailscale](glossary:tailscale). 빨간 선은 밖에서 들어오는 연결, 초록 선은 안에서 밖으로 연 연결이다._

- **[overlay network](glossary:overlay-network)**: 기존 인터넷 위에 가상 네트워크를 한 겹 더 얹는 것. 각 기기는 `100.x.y.z` 주소를 하나씩 받는다. 이 주소는 [CGNAT](/kr/blog/cs-fundamentals/network/network-tcp-ip-layers/#사설-ip-공인-ip-nat)과 같은 100.64.0.0/10 대역에서 나온다.
- **[WireGuard](glossary:wireguard)**: 기기 사이 트래픽은 [WireGuard](glossary:wireguard) 터널(UDP)로 암호화돼서 간다. [VPN](/kr/blog/cs-fundamentals/network/network-web-request-journey/#14-vpn-쓸-때)과 같은 캡슐화인데, 중앙 [VPN](glossary:vpn) 서버를 거치지 않고 기기끼리 바로 잇는다(mesh).
- **[coordination server](glossary:coordination-server)**: 각 기기의 [WireGuard](glossary:wireguard) [public key](glossary:public-key-authentication)와 현재 바깥 주소(endpoint)를 모아서 다른 기기들에 나눠 준다. 데이터는 지나가지 않는다.
- **[NAT traversal](glossary:nat-traversal)**: 양쪽이 동시에 상대의 바깥 주소로 UDP를 쏜다. 각자 "안에서 밖으로" 보낸 패킷이라 양쪽 [NAT](glossary:nat) 변환표에 항목이 생기고, 상대가 보낸 패킷이 그 항목을 타고 들어온다([UDP hole punching](glossary:udp-hole-punching)). `tailscale ping`의 `via 203.0.113.x:41641`이 이렇게 뚫린 direct 경로다.
- **[DERP relay](glossary:derp)**: [hole punching](glossary:udp-hole-punching)이 안 되는 [NAT](glossary:nat)(대칭형 [NAT](glossary:nat), UDP 차단)에서는 [Tailscale](glossary:tailscale)의 [relay](glossary:relay-server) 서버를 거친다. HTTPS(TCP 443) 위로 가서 웬만한 [firewall](glossary:firewall)은 통과하고, 대신 [relay](glossary:relay-server)를 돌아가니 지연이 늘어난다. 내용은 [WireGuard](glossary:wireguard)로 암호화된 채라 [relay](glossary:relay-server)도 못 읽는다.
- 모든 연결을 기기가 **밖으로** 연다. 그래서 공유기에 여는 **들어오는 포트는 0개**다.

# 4. 맡기는 게 더 간편한 이유: 계층마다 떠안는 일

"사설망([overlay](glossary:overlay-network)) 위에 [SSH](glossary:ssh)가 얹힌다"까지만 알면 [Tailscale](glossary:tailscale)은 [SSH](glossary:ssh) 밑에 깔린 망 하나로 보인다. 그런데 그 망을 내가 직접 굴리면 계층마다 할 일이 따로 생긴다.

아파트로 치면 건물 관리를 직접 하느냐, 관리사무소에 맡기느냐의 차이다. 직접 하면 단지 앞 도로, 정문 경비, 출입카드 발급과 회수를 다 내가 한다. 맡기면 그건 관리사무소가 하고, 내 방 열쇠만 내가 챙긴다. 도로는 [L3](glossary:osi-model) [reachability](glossary:reachability), 정문은 [L4](glossary:osi-model) 포트·[firewall](glossary:firewall), 출입카드는 기기 키를 나눠 주는 **[control plane](glossary:control-plane)**, 방 열쇠는 [L7](glossary:osi-model) [SSH](glossary:ssh)다.

![계층마다 self-hosted면 내가 하는 일과 managed면 사라지는 일. L7 SSH는 양쪽 다 내 몫](/static/images/network-ssh-overlay/self-hosted-vs-managed.svg)

_왼쪽은 [self-hosted](glossary:self-hosting) [WireGuard](glossary:wireguard)로 할 때 내가 떠안는 일, 오른쪽은 [Tailscale](glossary:tailscale) 같은 [managed](glossary:managed-service) 서비스에 맡겼을 때 남는 일이다. 맨 위 [L7](glossary:osi-model) 줄은 양쪽이 같다._

| 칸                                                             | [self-hosted](glossary:self-hosting)로 하면 내가 떠안는 일                                                                                                                                                                                    | [managed](glossary:managed-service)([Tailscale](glossary:tailscale))에 맡기면                                                        |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| [L3](glossary:osi-model) [reachability](glossary:reachability) | [public IP](glossary:public-ip-address) 확보(집에 없으면 VPS), IP가 바뀌면 [DDNS](glossary:ddns), [NAT traversal](glossary:nat-traversal) 직접 구성, 안 되는 구간을 위한 [relay](glossary:relay-server) 서버 운영, 기기마다 터널 IP 배정·기록 | 기기마다 고정 100.x IP 자동 배정, [NAT traversal](glossary:nat-traversal) 자동, 직접 연결이 안 되면 [DERP relay](glossary:derp) 제공 |
| [L4](glossary:osi-model) 포트·[firewall](glossary:firewall)    | 공유기 [port forwarding](glossary:port-forwarding)(UDP 51820), 공유기와 OS [firewall](glossary:firewall) 규칙, 열어 둔 포트 관리                                                                                                              | 공유기에 여는 포트 0개, 기기 사이 허용 범위는 [ACL](glossary:acl) 정책 파일 하나                                                     |
| [control plane](glossary:control-plane)(기기 키)               | 기기마다 키 쌍 생성, 상대 피어의 [public key](glossary:public-key-authentication)·endpoint를 설정 파일에 적어 배포, 기기를 잃어버리면 모든 피어 설정에서 그 키를 지워 폐기                                                                    | 로그인 한 번으로 기기 추가, 관리 콘솔에서 지우면 모든 기기에서 빠짐                                                                  |
| [L7](glossary:osi-model) [SSH](glossary:ssh)                   | [sshd](glossary:sshd) 설치, [public key](glossary:public-key-authentication) 등록, 비밀번호 로그인 끄기                                                                                                                                       | **똑같이 내 몫**                                                                                                                     |

- **[L3](glossary:osi-model)**: [self-hosted](glossary:self-hosting)는 결국 "밖에서 닿을 수 있는 점" 하나가 필요하다. 집 공유기의 [public IP](glossary:public-ip-address)든 VPS든, 그 점을 확보하고 주소가 바뀌면 따라가는 것까지 내가 한다. 학교 [NAT](glossary:nat) 뒤 맥처럼 그 점을 못 만드는 기기는 서버를 거쳐서만 붙는다. [managed](glossary:managed-service)는 그 점([coordination server](glossary:coordination-server), [DERP](glossary:derp))을 회사가 운영한다.
- **[L4](glossary:osi-model)**: [self-hosted](glossary:self-hosting) [WireGuard](glossary:wireguard)는 서버 역할 기기의 UDP 포트 하나는 열어야 한다. [managed](glossary:managed-service)는 모든 기기가 밖으로만 연결을 열어서 열린 포트가 없고, 누가 어디까지 닿는지는 [ACL](glossary:acl) 파일 하나로 정한다. 단, 각 기기의 OS [firewall](glossary:firewall)은 어느 쪽이든 내가 설정한다(7절의 Windows 규칙).
- **[control plane](glossary:control-plane)**: [WireGuard](glossary:wireguard)는 피어끼리 서로의 [public key](glossary:public-key-authentication)를 알아야 한다. 세 대를 서로 다 이으면([full mesh](glossary:full-mesh)) 피어 쌍이 3×2÷2 = 3개, 각 설정 파일에 다른 두 대씩 적으니 항목이 6개다(계산값). 기기가 n대면 n(n−1)개로 늘어난다. 기기 하나를 추가하거나 잃어버릴 때마다 나머지 설정을 다 고친다. 서버 하나를 가운데 두면([hub-and-spoke](glossary:hub-and-spoke)) 항목은 줄지만 모든 트래픽이 그 서버를 거친다. [managed](glossary:managed-service)는 이 키 교환·배포·폐기를 [coordination server](glossary:coordination-server)가 대신한다.
- **[L7](glossary:osi-model)**: [SSH](glossary:ssh)는 [overlay](glossary:overlay-network)가 무엇이든 똑같다. 맡겨도 [sshd](glossary:sshd), 키, 비밀번호 끄기는 내가 한다([Tailscale SSH](glossary:tailscale)를 쓰면 이것도 맡길 수 있지만 Windows 서버는 지원하지 않는다).

## 종속의 대가와 출구

맡긴 만큼 기대는 곳이 생긴다.

- **외부 회사**: [coordination server](glossary:coordination-server)와 [DERP](glossary:derp)를 회사가 운영한다. 회사의 정책·무료 요금제 조건이 바뀌면 따라가야 하고, 회사 쪽 장애 때는 새 기기 등록이나 키 갱신이 멈출 수 있다. 기기 목록과 접속 메타데이터도 회사가 본다(트래픽 내용은 [WireGuard](glossary:wireguard)로 암호화돼서 못 본다).
- **계정 하나**: [tailnet](glossary:tailscale) 전체가 로그인 계정 하나([identity provider](glossary:identity-provider))에 묶인다. 그 계정이 잠기면 새 기기를 못 붙인다.

대신 출구가 있다. 회사에 맡긴 건 **[L3](glossary:osi-model)와 [control plane](glossary:control-plane)**뿐이고, 실제로 패킷을 나르는 [data plane](glossary:data-plane)은 표준 [WireGuard](glossary:wireguard)다. 그래서 떠날 때는 그 두 칸만 갈아끼우면 된다.

- **[Headscale](glossary:headscale)**: [Tailscale](glossary:tailscale) 클라이언트는 그대로 두고 [control plane](glossary:control-plane)만 내 서버로 바꾼다.
- **[self-hosted](glossary:self-hosting) [WireGuard](glossary:wireguard)**: [L3](glossary:osi-model)와 [control plane](glossary:control-plane)을 전부 내가 맡는다(위 표 왼쪽).
- 어느 쪽이든 [L7](glossary:osi-model) [SSH](glossary:ssh) 설정([sshd_config](glossary:sshd), `authorized_keys`, [SSH key](glossary:ssh-key))은 그대로 쓴다. [L4](glossary:osi-model) OS [firewall](glossary:firewall) 규칙도 그대로인데, 새 터널 대역이 100.64.0.0/10이 아니면 `-RemoteAddress` 값만 바꾼다.

# 5. 다른 방법과 비교

선택지는 넷이었다. 단점은 전부 적는다.

| 방법                                                                                            | 단점                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ① 공유기 [port forwarding](glossary:port-forwarding)으로 [SSH](glossary:ssh) 직접 노출          | 22번이 인터넷 전체에 열려 [brute-force](glossary:brute-force-attack) 봇이 계속 두드린다. [attack surface](glossary:attack-surface)가 가장 크다. [sshd](glossary:sshd) 취약점이 바로 노출된다. 집 [public IP](glossary:public-ip-address)가 바뀌면 [DDNS](glossary:ddns)가 필요하다. 학교 [NAT](glossary:nat) 뒤 맥, [CGNAT](glossary:cgnat) 뒤 폰은 이 방법으로 아예 못 받는다 |
| ② [self-hosted](glossary:self-hosting) [WireGuard](glossary:wireguard)                          | 공유기에 UDP 51820 forwarding이 필요하다(포트 하나는 열린다). 기기 추가·교체마다 키 배포를 내가 한다. [public IP](glossary:public-ip-address)가 바뀌면 [DDNS](glossary:ddns), 공유기 설정과 관리도 내 몫이다. 서버 역할 기기가 꺼지면 전체가 끊긴다. 서버가 없는 학교 [NAT](glossary:nat) 뒤 기기끼리는 직접 못 잇는다                                                         |
| ③ [Headscale](glossary:headscale)(오픈소스 [coordination server](glossary:coordination-server)) | [public IP](glossary:public-ip-address)가 있는 VPS가 필요하다(비용, OS 업데이트, 백업). 서버가 죽으면 새 기기 등록·키 갱신이 멈춘다. [relay](glossary:relay-server)([DERP](glossary:derp))도 직접 띄우거나 공용 [relay](glossary:relay-server)에 기대야 한다. 클라이언트는 [Tailscale](glossary:tailscale) 앱을 그대로 쓰지만 공식 기능 일부가 늦게 따라온다                   |
| ④ [Tailscale](glossary:tailscale)                                                               | 외부 회사의 [coordination server](glossary:coordination-server)에 종속된다. 회사 정책·무료 요금제 조건이 바뀌면 따라가야 한다. 계정([identity provider](glossary:identity-provider))이 잠기면 새 기기를 못 붙인다. 기기 목록·접속 메타데이터를 그 회사가 본다                                                                                                                  |

④를 골랐다.

- **확장성**: 기기 하나를 추가하면 로그인 한 번으로 [tailnet](glossary:tailscale)에 붙는다. 공유기 규칙이나 키 배포를 손댈 일이 없다. [NAT](glossary:nat) 종류와 상관없이(학교, [CGNAT](glossary:cgnat)) 붙는다.
- **유지보수성**: 공유기에 열린 포트가 0개라 지킬 [attack surface](glossary:attack-surface)가 [SSH](glossary:ssh) server 자체로 줄어든다. [public IP](glossary:public-ip-address) 변경, [DDNS](glossary:ddns), 서버 패치를 내가 하지 않는다.
- **종속성**: 외부 회사에 기대는 게 단점이지만, 밑단이 표준 [WireGuard](glossary:wireguard)라 [L3만 갈아끼우면 된다](#종속의-대가와-출구). [Headscale](glossary:headscale)이나 [self-hosted](glossary:self-hosting) [WireGuard](glossary:wireguard)로 옮겨도 [L4](glossary:osi-model) [firewall](glossary:firewall) 규칙과 [L7](glossary:osi-model) [SSH](glossary:ssh) 설정(키, [sshd_config](glossary:sshd))은 그대로 쓴다.
- **테스트 용이성**: `tailscale ping`([L3](glossary:osi-model)), `tailscale debug netmap`([ACL](glossary:acl)), `ssh -v`([L7](glossary:osi-model))로 계층을 하나씩 떼어 확인할 수 있다. 이번 원인도 이 순서로 찾았다.

# 6. 검문 두 개: defense in depth

건물에 들어갈 때 출입증(건물)과 방 열쇠(방)를 따로 보는 것과 같다. 출입증을 잃어버려도 방은 안 열리고, 열쇠를 잃어버려도 건물에 못 들어온다. 출입증은 **[WireGuard](glossary:wireguard) 키**, 방 열쇠는 **[SSH key](glossary:ssh-key)**다.

| 검문                            | 무엇을 확인하나                                                    | 키가 있는 곳                                                                                   |
| ------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| [WireGuard](glossary:wireguard) | 이 패킷이 [tailnet](glossary:tailscale)에 등록된 **기기**에서 왔나 | 기기마다 tailscaled가 만든 키                                                                  |
| [SSH](glossary:ssh)             | 접속하려는 **사용자**가 맞나                                       | 사용자의 `~/.ssh/` [private key](glossary:public-key-authentication), 서버의 `authorized_keys` |

두 검문은 서로 독립이다. [tailnet](glossary:tailscale) 기기 하나가 털려도 그 기기에 내 [SSH](glossary:ssh) [private key](glossary:public-key-authentication)가 없으면 다른 기기에 로그인하지 못하고, [SSH](glossary:ssh) [private key](glossary:public-key-authentication)가 새도 [tailnet](glossary:tailscale) 밖에서는 22번까지 닿지 못한다. 이렇게 서로 다른 층의 방어를 겹치는 걸 **[defense in depth](glossary:defense-in-depth)**라고 한다. 그래서 [Tailscale](glossary:tailscale) 안이라도 [SSH](glossary:ssh) 비밀번호 로그인은 끄고 [public key](glossary:public-key-authentication)만 쓴다. [SSH key](glossary:ssh-key)도 기기마다 따로 둬서, 기기 하나가 털리면 그 기기 키만 지우면 되게 했다(7절).

# 7. 실제 설정

## 맥: 원격 로그인 + 공개키만

1. 시스템 설정 → 일반 → 공유 → **원격 로그인**을 켠다. 이때 [sshd](glossary:sshd)가 뜬다.
2. 접속할 기기의 [public key](glossary:public-key-authentication)를 맥의 `~/.ssh/authorized_keys`에 넣는다.
3. **새 터미널에서 키로 로그인되는지 먼저 확인한다.** 비밀번호부터 끄고 키가 안 먹으면 [lockout](glossary:lockout)이다. 확인하는 동안 기존 세션은 닫지 않는다.
4. `/etc/ssh/sshd_config.d/`에 파일을 하나 만들어 비밀번호 인증을 끈다.

```text:/etc/ssh/sshd_config.d/010-key-only.conf
PasswordAuthentication no
KbdInteractiveAuthentication no
```

- macOS의 [sshd](glossary:sshd)는 [PAM](glossary:pam)을 거친다(`UsePAM yes`). `PasswordAuthentication no`만 끄면 [PAM](glossary:pam)이 [keyboard-interactive](glossary:keyboard-interactive-authentication) 방식으로 비밀번호를 다시 묻는다. 그래서 **둘 다** 꺼야 한다.
- `sshd_config` 맨 위가 `Include /etc/ssh/sshd_config.d/*`이고, [sshd](glossary:sshd)는 같은 옵션을 **처음 읽은 값**으로 쓴다. 본 파일을 고치지 않고 이 폴더에 넣으면 macOS 업데이트가 본 파일을 덮어써도 설정이 남는다.
- 적용된 값은 `sudo sshd -T | grep -i authentication`으로 확인한다.

## Windows 데스크탑: OpenSSH Server + tailnet만 + 공개키만

2026-11-27에 끝냈다. 데스크탑은 Windows 11이고, 설치된 [sshd](glossary:sshd)는 [OpenSSH](glossary:openssh) for Windows 9.5다. 관리자 [PowerShell](glossary:powershell)에서 했다.

```powershell
# OpenSSH Server 설치, 시작, 부팅 때 자동 시작
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Start-Service sshd
Set-Service -Name sshd -StartupType Automatic

# 22번은 tailnet 대역에서 오는 것만 허용
New-NetFirewallRule -Name OpenSSH-Server-Tailnet -DisplayName 'OpenSSH Server (tailnet only)' `
  -Direction Inbound -Protocol TCP -LocalPort 22 `
  -RemoteAddress 100.64.0.0/10 -Action Allow

# 설치가 만든 기본 규칙(모든 주소 허용)은 끈다
Disable-NetFirewallRule -Name OpenSSH-Server-In-TCP
```

- 설치 전 `OpenSSH.Server` capability는 `NotPresent`였고, 설치 뒤 `Installed`, [sshd](glossary:sshd)는 `Running`·`Automatic`이 됐다.
- [OpenSSH](glossary:openssh) Server를 설치하면 22번을 **모든 주소**에서 허용하는 기본 규칙 `OpenSSH-Server-In-TCP`가 같이 생긴다. 이걸 켜 둔 채로 위 규칙을 더하면 좁힌 의미가 없다. Windows [firewall](glossary:firewall)은 허용 규칙 중 하나만 맞아도 통과시킨다. 그래서 끄고, 원격 주소가 100.64.0.0/10([Tailscale](glossary:tailscale)이 쓰는 [CGNAT](glossary:cgnat) 대역)인 규칙만 남겼다.
- 이 대역은 통신사 [CGNAT](glossary:cgnat)도 쓰는 대역이라, 더 좁히려면 [Tailscale](glossary:tailscale) 인터페이스로도 제한할 수 있다(`-InterfaceAlias Tailscale`). 이번엔 하지 않았다.

### 함정: 관리자 계정은 다른 파일을 읽는다

데스크탑 계정이 **관리자 그룹**이면 [sshd](glossary:sshd)는 `~/.ssh/authorized_keys`를 보지 않는다. Windows의 기본 `sshd_config` 맨 아래에 이런 블록이 있기 때문이다.

```text:C:\ProgramData\ssh\sshd_config
Match Group administrators
       AuthorizedKeysFile __PROGRAMDATA__/ssh/administrators_authorized_keys
```

그래서 [public key](glossary:public-key-authentication)는 `C:\ProgramData\ssh\administrators_authorized_keys`에 넣는다. 이 파일은 [ACL](glossary:acl)이 SYSTEM과 Administrators만이어야 [sshd](glossary:sshd)가 읽는다. 상속된 권한이 남아 있으면 키가 맞아도 무시된다.

```powershell
icacls.exe "C:\ProgramData\ssh\administrators_authorized_keys" /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"
```

관리자 계정으로 [SSH](glossary:ssh) 로그인하면 [UAC](glossary:uac) 확인 없이 **관리자 토큰**을 가진 세션이 열린다([Termius](glossary:termius) 탭 제목에 `관리자:`가 붙는다). [SSH key](glossary:ssh-key) 하나가 곧 관리자 권한이라는 뜻이라, 비밀번호 로그인을 끄는 게 더 중요해진다.

### 비밀번호 인증 끄기

키 로그인을 먼저 확인한 뒤 `C:\ProgramData\ssh\sshd_config` **맨 위**에 두 줄을 넣고 `Restart-Service sshd`를 했다.

```text:C:\ProgramData\ssh\sshd_config
PasswordAuthentication no
KbdInteractiveAuthentication no
```

- 맥과 같은 이유로 맨 위다. [sshd](glossary:sshd)는 같은 옵션을 처음 읽은 값으로 쓰고, 파일 아래쪽 `Match` 블록 안에 넣으면 그 조건에만 걸린다.
- 확인: 맥에서 비밀번호로 접속을 시도하면 `Permission denied (publickey)`로 거절됐다(1/1). 서버가 허용하는 인증 방법 목록에는 `publickey` 하나만 남았다.
- **[Tailscale SSH](glossary:tailscale)**([Tailscale](glossary:tailscale)이 [SSH](glossary:ssh) server 역할까지 대신하는 기능)는 Windows를 서버로 지원하지 않는다. 그래서 데스크탑은 [OpenSSH](glossary:openssh) Server를 직접 쓴다.

## 폰: Termius + Biometric Key

폰의 [SSH](glossary:ssh) client는 **[Termius](glossary:termius)**다. 키는 [Termius](glossary:termius)의 **Biometric Key**를 썼다. 폰의 [Secure Enclave](glossary:secure-enclave) 안에서 만든 [ECDSA](glossary:ecdsa) P-256 키라 [private key](glossary:public-key-authentication)를 파일로 꺼낼 수 없고, 쓸 때마다 생체 인증을 거친다. [public key](glossary:public-key-authentication)만 복사해서 맥의 `authorized_keys`(2026-11-26)와 데스크탑의 `administrators_authorized_keys`(2026-11-27)에 넣었다.

### 함정: Too many authentication failures

폰 → 데스크탑은 처음 세 번 실패했다. 데스크탑 [sshd](glossary:sshd) 로그를 `LogLevel DEBUG3`로 올려 보니, [Termius](glossary:termius)가 `userauth` 요청을 `method none`으로만 7번 보내고 `publickey`는 한 번도 안 보냈다. [sshd](glossary:sshd)가 허용 횟수를 넘겼다고 끊은 게 `Too many authentication failures`였다.

원인은 [Termius](glossary:termius) 설정이었다. 호스트에 **Identity**(사용자 이름과 키를 묶은 항목)를 붙이면서 키가 빠진 채 저장돼 있었다. 키가 없으니 보낼 서명도 없었던 것이다. 호스트 설정에 Username과 Key를 직접 지정하자 바로 붙었다.

## 기기별 키와 SSH config

- 키는 기기마다 따로 만들었다. 데스크탑에는 맥 키([ed25519](glossary:ed25519))와 폰 키(Biometric Key) 두 줄이 있고, 맥에는 데스크탑 키(패스프레이즈 있음)와 폰 키가 있다. 기기 하나를 잃어버리면 다른 기기들에서 그 키 한 줄만 지우면 된다.
- 맥과 데스크탑은 같은 [dotfiles](glossary:dotfiles) 레포를 쓴다. 그 레포에 [SSH config](glossary:ssh-config) 조각 파일 하나를 두고, 각 기기 `~/.ssh/config` 첫 줄에서 `Include`한다.

```text:~/.ssh/config
Include dotfiles/tailnet.conf
```

```text:~/.ssh/dotfiles/tailnet.conf
Host desktop
  HostName desktop
  User <desktop 계정>
  IdentityFile ~/.ssh/<desktop용 키>
  IdentitiesOnly yes

Host laptop
  HostName laptop
  User <맥 계정>
  IdentityFile ~/.ssh/<맥용 키>
  IdentitiesOnly yes
```

- `HostName`은 [Tailscale](glossary:tailscale) [MagicDNS](glossary:magicdns) 이름이다. IP(100.x)를 적지 않아서 주소가 바뀌어도 그대로 쓴다.
- `IdentitiesOnly yes`는 지정한 키만 내민다. 에이전트에 키가 여러 개 있으면 하나씩 다 시도하다가 위 함정처럼 `Too many authentication failures`로 끊길 수 있다.
- `~/.ssh/dotfiles`는 레포 폴더로 가는 링크다. 맥은 [symbolic link](glossary:symbolic-link), Windows는 **폴더 [junction](glossary:junction)**을 썼다. Windows에서 파일 [symbolic link](glossary:symbolic-link)를 만들려면 관리자 권한(또는 개발자 모드)이 필요한데, 폴더 [junction](glossary:junction)은 그렇지 않다.
- 이제 `ssh desktop`, `ssh laptop` 한 단어로 붙는다.

## 접속 시험

전부 [MagicDNS](glossary:magicdns) 이름으로 접속했다.

| 방향          | 결과                                     | 날짜       |
| ------------- | ---------------------------------------- | ---------- |
| 폰 → 맥       | 성공                                     | 2026-11-26 |
| 맥 → 데스크탑 | 성공 1/1                                 | 2026-11-27 |
| 데스크탑 → 맥 | 성공 1/1                                 | 2026-11-27 |
| 폰 → 데스크탑 | 처음 3번 실패(위 함정), 설정 고친 뒤 1/1 | 2026-11-27 |

## Tailscale ACL

```json
{
  "acls": [
    {
      "action": "accept",
      "src": ["autogroup:member"],
      "dst": ["autogroup:self:*"]
    }
  ]
}
```

- `autogroup:member`: [tailnet](glossary:tailscale)의 사용자. `autogroup:self`: **그 사용자 본인 소유** 기기. 내 기기끼리는 모든 포트로 오갈 수 있고, 나중에 다른 사람을 [tailnet](glossary:tailscale)에 초대해도 그 사람은 내 기기에 못 닿는다.
- 2026-11-26에 정책을 위 한 줄로 교체했다. 2절에서 본 데스크탑 ↔ 맥 허용 규칙은 교체 전 정책에서 나온 것이고, 교체 전엔 폰 → 맥 규칙이 없어 [packet filter](glossary:packet-filter)에서 막혔다. 저장한 뒤 맥의 [packet filter](glossary:packet-filter) 출발지에 폰·데스크탑·맥 세 대가 다 들어온 걸 확인했다.
- 지금 [tailnet](glossary:tailscale) 사용자는 나 하나(Owner 1명, 초대 대기 0명)다.
- 포트를 22로 좁히지 않은 건 [L4](glossary:osi-model) 제한을 각 기기 OS [firewall](glossary:firewall)에서 하기 때문이다.

# 8. Remote Control이 꺼졌을 때: SSH로 다시 켜기

이 망을 만든 이유가 이 절이다. 나는 데스크탑에서 돌리는 [Claude Code](glossary:claude-code)를 밖에서 Claude 앱으로 이어 쓴다([Remote Control](glossary:remote-control)). 그런데 데스크탑 쪽 [Remote Control](glossary:remote-control) 프로세스가 꺼지면 폰에서는 다시 켤 방법이 없다. 그때 폰에서 [SSH](glossary:ssh)로 들어가 다시 켠다.

전화로 집에 있는 물건을 켜는 것과 비슷하다. 전화기 너머로 내가 직접 손을 뻗으면 전화를 끊는 순간 그 손도 같이 사라진다. 그래서 집에 있는 사람에게 "켜 줘"라고 부탁만 하고 끊는다. 전화는 **[SSH](glossary:ssh) 세션**, 직접 뻗은 손은 **[SSH](glossary:ssh) 세션의 [child process](glossary:child-process)**, 집에 있는 사람은 **로그인 세션에서 도는 [scheduled task](glossary:task-scheduler)**이다.

![SSH 세션에서 바로 띄운 프로세스는 SSH와 같이 죽고, 예약 작업으로 띄운 프로세스는 로그인 세션에 남는다](/static/images/network-ssh-overlay/remote-control-recovery.svg)

_위: [SSH](glossary:ssh) 세션 안에서 바로 띄우면 [SSH](glossary:ssh)가 끊길 때 같이 죽는다. 아래: [scheduled task](glossary:task-scheduler)를 실행만 하고 나오면 로그인 세션에서 계속 돈다._

## SSH 세션 안에서는 된다, 하지만 오래 못 간다

- [SSH](glossary:ssh) 세션 안에서도 `claude` CLI는 돌아간다. [public key](glossary:public-key-authentication)로 로그인한 세션에서도 `claude auth status`가 `loggedIn: true`였고, `claude remote-control`을 띄우면 `Connected`까지 갔다.
- 문제는 수명이다. [SSH](glossary:ssh) 세션에서 띄운 프로세스는 그 세션의 자식이라 **[SSH](glossary:ssh)가 끊기면 같이 죽는다**. iOS는 백그라운드로 간 [Termius](glossary:termius)를 금방 멈추고, 그러면 [SSH](glossary:ssh)가 끊긴다. 폰으로 [Remote Control](glossary:remote-control)을 쓰려면 Claude 앱으로 넘어가야 하니, 그 사이에 [Termius](glossary:termius)가 멈추면 방금 띄운 [Remote Control](glossary:remote-control)도 같이 죽는다.
- GUI 앱(Claude 데스크톱 앱)을 [SSH](glossary:ssh)에서 띄우면 **[session 0](glossary:session-0)**에 뜬다. [session 0](glossary:session-0)은 서비스가 도는 세션이라 화면이 없어서, 실행은 되는데 아무도 볼 수 없다.

## 예약 작업으로 넘기기

그래서 실제 실행은 로그인된 데스크탑 세션(사용자가 로그인해 있는 대화형 세션)에서 도는 **[scheduled task](glossary:task-scheduler)** 둘에 맡겼다.

| 작업                  | 하는 일                                                                                            |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| `ClaudeRemoteControl` | 옛 [Remote Control](glossary:remote-control) 프로세스를 끄고 `desktop-rc`라는 이름으로 새로 띄운다 |
| `ClaudeAppStart`      | Claude 데스크톱 앱을 띄운다                                                                        |

폰에서는 [SSH](glossary:ssh)로 들어가 한 줄만 치고 나온다.

```powershell
schtasks /Run /TN ClaudeRemoteControl
```

[scheduled task](glossary:task-scheduler)는 [SSH](glossary:ssh) 세션이 아니라 로그인 세션에서 실행되니까 [SSH](glossary:ssh)가 끊겨도 산다. 이 한 줄 뒤에 폰 Claude 앱 Code 탭에 `desktop-rc`가 뜨는 걸 확인했다.

## 함정: /End는 손자를 못 죽인다

처음엔 작업을 멈췄다 다시 돌리려고 `schtasks /End`를 썼다. 그런데 `/End`는 작업이 직접 띄운 `cmd`만 끝내고, 그 `cmd`가 띄운 `claude`는 부모를 잃은 채 남는다(**[orphan process](glossary:orphan-process)**). 옛 [Remote Control](glossary:remote-control)이 살아 있으니 새로 띄운 쪽이 바로 종료됐다.

- 스크립트가 시작하자마자 옛 `remote-control` 프로세스를 직접 찾아 끈다.
- 작업 설정의 `MultipleInstances`를 `StopExisting`으로 둬서, 이미 돌고 있으면 그걸 멈추고 새로 시작한다.
- `/Run`을 두 번 연달아 해서 두 번 다 프로세스가 1개로 교체되는 걸 확인했다(2/2).

## 재부팅에 대비한 것, 그리고 대가

데스크탑이 재부팅되면 로그인 세션 자체가 없어서 [scheduled task](glossary:task-scheduler)도 못 돈다. 그래서 로그인부터 자동으로 되게 했다.

1. **[Autologon](glossary:autologon)**: Sysinternals [Autologon](glossary:autologon)으로 켰다. 비밀번호는 레지스트리 평문이 아니라 [LSA secret](glossary:lsa-secret)에 들어간다. Windows Hello 전용 로그인 옵션을 켜 두면 [Autologon](glossary:autologon)이 안 먹어서 그 옵션은 껐다.
2. 로그인하면 Claude 앱이 시작 프로그램으로 뜨고, `ClaudeRemoteControl`이 로그인 1분 뒤 자동으로 돈다.
3. AC 전원일 때 절전·최대 절전은 원래 "안 함"이었다.

**재부팅 시험은 하지 않았다.** 위 순서가 재부팅 뒤 실제로 이어지는지는 안 쟀다. 안 되면 그때 고친다.

대가도 있다. [Autologon](glossary:autologon)에 [BitLocker](glossary:bitlocker)까지 꺼져 있어서, **데스크탑 앞에 앉은 사람은 바로 로그인된다.** 집 안에 있는 기기라 이건 감수했다. 밖에서 들어오는 길은 여전히 [tailnet](glossary:tailscale) + [public key](glossary:public-key-authentication) 두 검문(6절)을 거친다.

# 9. 부록: orphan 노드와 `-1`

[tailnet](glossary:tailscale) 기기 목록을 보다가 해커톤 때 붙인 [k3s](glossary:k3s) 노드 세 대가 그대로 남아 있는 걸 발견했다. 실제 서버는 이미 없는데 [tailnet](glossary:tailscale)에는 등록이 살아 있는 **[orphan](glossary:orphan-node)** 노드다.

이게 문제가 되는 경우가 있다. [Tailscale](glossary:tailscale)은 기기 이름이 겹치면 새로 붙은 쪽 이름 뒤에 `-1`을 붙인다. 같은 hostname으로 기기를 다시 붙이면 원래 이름은 [orphan](glossary:orphan-node)이 쥐고 있고, 새 기기는 `desktop-1` 같은 이름을 받는다. 이름으로 기기를 가리키던 [ACL](glossary:acl)이나 [SSH](glossary:ssh) 설정은 꺼져 있는 [orphan](glossary:orphan-node)을 가리키게 된다.

- [orphan](glossary:orphan-node)은 관리 콘솔의 기기 목록에서 지운다. [k3s](glossary:k3s) 노드 세 대는 2026-11-26에 Remove했고, [tailnet](glossary:tailscale) 기기는 6대에서 3대가 됐다(맥에서 `tailscale status`로 확인).
- 기기를 다시 붙였다면 [orphan](glossary:orphan-node)을 지운 뒤 새 기기 이름에서 `-1`을 떼고, 그 이름을 쓰는 설정이 맞는 기기를 가리키는지 다시 본다.
