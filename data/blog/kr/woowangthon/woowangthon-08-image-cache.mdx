> 시리즈 8편. 구축 5단계(학생 앱 받을 틀)의 첫 조각, 리더에 이미지 캐시를 둔 날이다. 리더 GPU 작업은 [7편](/kr/blog/woowangthon/woowangthon-07-leader-vllm/)에, 전체 그림은 [Woowangthon 0](/kr/blog/woowangthon/woowangthon-00-overview/)에 있다.

## 한 줄 요약

학생 앱 이미지는 GitHub의 레지스트리(GHCR)에 올라간다. 워커 둘이 같은 이미지를 학교망으로 따로 받지 않게, 리더에 GHCR을 대신 받아 두는 캐시를 띄웠다. 두 번째 워커는 1.1초 만에 받았다. 캐시가 꺼지면 노드가 GHCR에서 직접 받는 것도 시험했는데, AI 리뷰어가 "꺼진 것"과 "대답이 없는 것"은 다르다고 짚었다. 다시 재 보니 30초를 더 기다렸다.

## 1. 왜 캐시를 두나

학생이 배포하면 빌드는 AWS에서 하고, 이미지는 GHCR에 올라간다. 워커는 그 이미지를 받아서 띄운다. 워커가 둘이라 같은 이미지를 두 번 받을 일이 생긴다. 워커 하나가 꺼져서 앱이 다른 워커로 옮겨 갈 때가 그렇다.

학교망에서 GHCR은 느렸다. 6편에서 [워커 하나가 GitHub 다운로드에서 멈췄던 것](/kr/blog/woowangthon/woowangthon-06-k3s-install/#6-워커-하나는-다운로드가-멈췄다)과 같은 동네다. 그래서 리더가 GHCR에서 한 번 받아 두고, 워커는 스위치 망(초당 약 940Mbit)으로 리더에서 가져가게 했다.

캐시는 끌어오기(pull-through) 방식이다. 노드가 "이 이미지 줘"라고 하면 캐시가 가진 게 있으면 바로 주고, 없으면 GHCR에서 받아 오면서 넘겨준 뒤 7일 동안 들고 있는다. 제품은 Docker가 만든 레지스트리의 오픈소스판(CNCF Distribution, `registry:3.1.2`)이다. 설정 파일 하나로 끝나고, 학생 이미지는 공개라 GHCR 로그인 정보가 필요 없다.

## 2. 캐시를 어디에 묶나

캐시는 리더의 노드 주소 `192.168.77.11:5000`에서 받는다. 쿠버네티스에서 Pod를 노드의 포트에 여는 방법은 두 가지다.

| 방법        | 어떻게                                           | 방화벽                                                                                                                                        |
| ----------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| hostPort    | 노드 포트로 온 걸 Pod 주소로 바꿔서 넘긴다       | 바꿔서 넘기는 길이 방화벽의 "들어오는 연결" 검사를 [비켜 간다](/kr/blog/woowangthon/woowangthon-06-k3s-install/#3-방화벽을-비켜-가는-두-옆길) |
| hostNetwork | Pod가 노드의 네트워크를 그대로 쓴다(주소도 같다) | 노드에서 직접 도는 프로그램과 똑같이 방화벽이 걸린다                                                                                          |

hostNetwork를 골랐다. 그리고 캐시 프로그램이 노드 주소 하나에만 귀를 열게 했다. 학교망 주소로 오는 건 애초에 받지 않고, 방화벽도 노드 대역에서 오는 것만 들인다.

대가는 하나다. 학생 공간에 걸 보안 등급(baseline)이 hostNetwork를 금지한다. 그래서 캐시 공간만 등급을 풀었다. 대신 컨테이너는 일반 사용자로 돌고, 특수 권한(capability)은 하나도 없고, 파일 시스템은 읽기 전용이다. 등급을 푼 건 "노드 네트워크를 쓴다" 하나 때문이다.

## 3. 노드가 캐시를 먼저 보게

노드 셋에 `/etc/rancher/k3s/registries.yaml`을 깔았다. 내용은 네 줄이다.

```yaml
mirrors:
  ghcr.io:
    endpoint:
      - 'http://192.168.77.11:5000'
```

k3s는 이걸 읽어서 컨테이너 런타임(containerd)이 보는 설정을 만든다. 만들어진 파일에서 캐시는 `host`, GHCR은 `server`로 들어간다. 런타임은 `host`를 먼저 시도하고 `server`를 마지막에 쓴다.

![k3s가 만든 ghcr.io용 hosts.toml. 캐시 주소가 host로, 원래 주소 https://ghcr.io가 server로 들어 있다. containerd는 host를 먼저 쓰고 server를 마지막에 쓴다](/static/images/woowangthon-08-image-cache/hosts-toml.svg)

캐시가 죽으면 GHCR로 넘어간다는 게 이 `server` 줄이다. 따로 설정할 게 없다.

이 파일을 바꾸면 k3s를 다시 켜야 한다. [5편의 순서](/kr/blog/woowangthon/woowangthon-05-node-prep/#3-끊기기-전에-되돌리기부터)대로 w2 → w1 → 리더 한 대씩 했다. k3s를 다시 켜도 돌던 컨테이너는 그대로라 Pod 재시작은 0이었다. 리더는 쿠버네티스 API가 2초 만에 돌아왔다.

## 4. 두 번째 워커는 1초

시험 이미지는 GHCR의 작은 공개 이미지(34.8MB)를 썼다. w1에 먼저 띄우고, 끝나자마자 w2에 같은 이미지를 띄웠다.

![시험 Pod 두 개의 이미지 받기 기록. w1은 1분 53초, w2는 1.1초](/static/images/woowangthon-08-image-cache/pull-events.svg)

캐시 로그로 확인했다. 캐시가 GHCR에서 뭔가를 새로 받아 올 때마다 남기는 줄이 있는데, w1 때만 9줄이 찍히고 w2 때는 한 줄도 없었다. w2는 전부 캐시에서 받았다.

캐시를 0개로 내리고 w1의 이미지를 지운 뒤 다시 받으니, 런타임이 캐시에 연결을 거절당하고 바로 GHCR로 넘어가 44초에 받았다. 학교망 주소에서 리더 5000번으로는 연결이 안 됐다. 끝나는 기준 셋을 다 넘었다.

## 5. 처음 받는 건 캐시 쪽이 더 느렸다

숫자를 나란히 놓으면 이상한 게 하나 보인다.

| 받은 길                    | 걸린 시간 |
| -------------------------- | --------- |
| 캐시를 거쳐 처음 (캐시 빔) | 1분 53초  |
| 캐시에서 (두 번째 워커)    | 1.1초     |
| GHCR에서 직접 (캐시 꺼짐)  | 44초      |

처음 한 번은 캐시를 거치는 쪽이 직접 받는 것보다 두 배 넘게 느렸다. 캐시가 GHCR에서 받으면서 넘겨주는 만큼 한 단계가 더 끼고, 학교망의 GHCR 속도도 그때그때 달랐다(6절). 한 번 잰 숫자라 원인을 단정하진 않았다. 그래도 할 일은 분명하다. 데모 전에 쓸 이미지를 한 번 받아 두면 이 1분 53초는 심사위원 앞에서 안 나온다. 이건 알려진 한계로 문서에 적었다.

## 6. 리뷰어 AI가 잡은 것: 거절과 무응답

PR을 열었는데 리뷰 봇(CodeRabbit)이 오지 않았다. 대신 "이 레포는 스타가 10개 미만이라 자동 리뷰를 안 한다"는 안내가 달렸다. 지난주까지는 PR을 열면 알아서 왔는데, 봇 쪽 무료 정책이 바뀐 것 같다. 리뷰를 부르는 코멘트를 달자 지적 셋이 왔다. 셋 다 맞았다.

| 지적                                                                         | 맞나                                                                                                                         |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 문서에 "캐시는 나가는 연결이 443 · 53만 열려 있다"고 썼는데 방화벽 표와 다름 | 맞다. 노드에서 도는 프로그램에는 80, 시간 동기화, Tailscale 포트도 열려 있다. 캐시가 실제로 쓰는 게 443 · 53일 뿐이다        |
| 볼륨 50Gi는 상한이 아니다                                                    | 맞다. 지금 쓰는 저장 방식(local-path)은 노드의 폴더 하나라 크기를 막지 않는다. 캐시에도 크기 제한이 없어 7일이 유일한 정리다 |
| "리더가 꺼져도 직접 받는다"는 시험한 사실이 아니다                           | 맞다. 아래                                                                                                                   |

세 번째가 제일 아팠다. 4절에서 시험한 건 캐시를 0개로 내린 경우다. 그때 리더는 켜져 있으니까, 5000번에 아무도 없다고 바로 "거절"을 돌려준다. 런타임은 거절을 받자마자 다음 주소로 넘어간다. 그런데 리더 전원이 나가면 거절을 돌려줄 놈도 없다. 런타임은 대답 없는 주소에 연결을 걸어 놓고 기다린다.

그래서 리더가 꺼진 걸 흉내 냈다. w1에서 리더 5000번으로 가는 패킷을 조용히 버리게(DROP) 하고 같은 이미지를 받았다. 혹시 몰라 5분 뒤 저절로 풀리는 예약을 먼저 걸었다.

![w1의 containerd 로그. 캐시가 꺼졌을 때는 connection refused 뒤 바로 넘어가 44초, 대답이 없을 때는 30초 뒤 i/o timeout이 나고 모두 216.6초](/static/images/woowangthon-08-image-cache/fallback.svg)

30초를 기다린 뒤에 GHCR로 넘어갔고, 모두 3분 37초가 걸렸다. 30초를 빼도 3분 6초인데, 몇 분 전에 같은 이미지가 44초였다. 학교망에서 GHCR 속도가 그때그때 다르다는 뜻이다. 문서에는 "캐시에 닿지 않으면 받을 때마다 30초를 먼저 기다린다, 리더 전원을 실제로 끈 시험은 아니다"로 적었다.

이 PR의 문서는 AI 에이전트가 썼고, 틀린 문장을 잡은 것도 AI 리뷰어다. 대회 주제가 "AI는 동료가 될 수 있을까?"인데, 이번엔 동료끼리 서로 검토한 셈이다. 다만 리뷰어를 부른 것도, 머지 버튼을 누른 것도 사람이다.

## 7. 배포 흐름에서 남은 질문

같은 날 밤, AI 담당(suda5936)의 배포 흐름 설계 문서가 머지됐다. 단계 이름은 W0~W7이다.

- **W4 빌드**는 AWS에서 이미지를 만들어 GHCR에 올리는 데까지다. 이번에 만든 캐시가 그 이미지를 받는다.
- **W5 배포**는 리더의 실행기가 이미지 태그와 배포 설정을 받아 쿠버네티스용 파일을 만들고 적용한다. [7편의 회의 결정](/kr/blog/woowangthon/woowangthon-07-leader-vllm/#1-회의에서-바뀐-것) 그대로다.
- **W6 동작 확인**의 자리가 흔들리고 있다. 설계 문서의 마지막 커밋은 플랫폼 서버(AWS)로 뺐는데, 머지 직후 디스코드에서 AI 담당이 리더에 W5와 같이 두는 게 낫겠다고 했다. 팀장(TaeTaeJin)은 정리해서 알려 달라고 했다.

클러스터 쪽에서는 리더로 오는 게 편하다. 7편에서 정한 실행기 계정 설계에 동작 확인용 읽기가 이미 들어 있고, AWS에서 학생 앱까지 들어오는 길을 새로 열 필요가 없다. 하나 물어볼 게 남았다. 배포 끝에 한 번 확인하는 건지, 배포 뒤에도 계속 도는 감시까지 리더에 두는 건지다. 뒤쪽이면 리더에 상시 프로그램이 하나 는다. 계획에는 "결정 전"으로 적어 뒀다.

## 8. 정리

| 겪은 일                               | 배운 것                                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------------------------- |
| 캐시를 노드 포트에 열어야 했다        | hostPort는 방화벽을 비켜 간다. hostNetwork에 노드 주소 하나만 묶으면 방화벽이 그대로 걸린다 |
| 두 번째 워커는 1.1초, 처음은 1분 53초 | 캐시는 두 번째부터 이득이다. 데모 전에 쓸 이미지를 한 번 받아 둔다                          |
| 캐시가 꺼진 경우만 시험했다           | 거절과 무응답은 다르다. 장애는 일어날 모양 그대로 흉내 낸다(이번엔 DROP)                    |
| 볼륨 크기를 적었는데 상한이 아니었다  | local-path는 크기를 막지 않는다. 쌓이는 건 디스크 알림으로 본다                             |
| 리뷰 봇이 안 왔다                     | 스타 10개 미만 레포는 이제 코멘트로 불러야 한다                                             |

5단계의 첫 조각이 끝났다. 다음은 학생 공간 양식이다. 학생 앱이 뜰 공간을 만들고 자원 상한과 차단 규칙을 건다. 상한 값은 플랫폼 서버 담당과 먼저 맞춰야 한다.
