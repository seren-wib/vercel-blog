## In one paragraph

The wireframes (HW1) set the flow, a design canvas (BeanShop UI, 18 screens) set the look, and the screens were built in one day across five pull requests. One principle: **the screens do not decide.** Which buttons to show and whether a payment may be retried come from the server in the response, and the screen draws what it gets.

## 2. Token refresh: once, and everyone waits

The access token expires after 30 minutes ([post 3](/en/blog/coffee-shop/coffee-shop-03-backend-foundation/#4-members-and-auth-83)). If a screen calls three APIs at once with an expired token, all three get 401. If each sends its own refresh, three refreshes go out.

At a bank counter: instead of three customers with expired queue tickets all going to get a new one at the same time, one goes and the others share that ticket.

![Token refresh diagram. Requests A, B and C get 401 at the same time. The first calls refreshAccess(), which sends POST /api/auth/token/refresh/ and keeps the Promise in the refreshing variable. B and C wait on the same Promise. When the new access token arrives, all three are marked _retried and sent once more. If the refresh fails, the tokens are cleared and the user goes to /login?next=](/static/images/coffee-shop-05-frontend/token-refresh.svg)

The queue ticket is the access token, and one person going is sharing the one refresh Promise in flight. The analogy stops here.

The response interceptor in `api/client.js` does this:

- On a 401 that is not already a retried request (`_retried`) and not the login or refresh call itself, try a refresh
- If a refresh is in flight, wait on that Promise; if not, start one. Clear it when it settles
- Resend the original request with the new token **once**. The `_retried` mark prevents a loop
- With no refresh token or a failed refresh, clear the tokens and go to `/login?next=<current path>`

The only file that reads or writes the token keys is `auth/tokenStore.js`. The `role` inside the token only decides whether to show the admin menu. The real block is the server checking the role in the database on every admin request and returning 403 (NFR-10).

## 3. Checkout and payment screens

The payment screens were the hardest. The payment window sends the browser to another page and back, and a person can close the window halfway.

![Checkout flow diagram. The first press creates the order with POST /api/orders/, starts the payment and opens the Toss window. Later presses only reopen payment for the order already created. When the window returns to successUrl, /checkout/result sends confirm once. PG_ERROR shows a check-again button, PAYMENT_MISMATCH a failure notice. Closing the window makes requestPayment() reject with USER_CANCEL and the checkout screen shows a cancel notice; a failure returned to failUrl is recorded by the result screen with the fail API. The order can be paid again from its detail screen](/static/images/coffee-shop-05-frontend/checkout-flow.svg)

- **First press creates the order and opens the window; later presses only pay.** If every press after closing the window created a new order, that much stock would be locked each time. When an order already exists, only payment reopens (#115).
- **Confirm only once.** `/checkout/result` sends the confirm request once using `useRef`. React StrictMode runs effects twice in development, and it is still once. The server's confirm API is idempotent anyway, so two calls would not break anything, but this keeps the result from flashing twice.
- **A slow PG is not a failure.** 502 `PG_ERROR` shows a "the payment provider is slow, check again" button; 409 `PAYMENT_MISMATCH` shows a failure notice.
- **A closed window arrives as an error.** As step 5 of the spike in post 4 showed, closing the window does not go to `failUrl`. So `lib/pay.js` catches the `USER_CANCEL` error from `requestPayment()` itself and the checkout screen shows "결제를 취소했습니다." (payment cancelled). Only a failure the window sends back to `failUrl` is recorded by the result screen through the failure API (`/api/payments/fail/`).

### The server decides the buttons

The buttons on my order detail (cancel, request cancel, pay again) are drawn from the `can_*` values in the server response. The buttons on the admin order detail (prepare, ship, delivered, approve or reject cancel) show only what the server lists in `allowed_actions` (#119).

If the screens kept their own copy of the state table, they would show the wrong buttons the day the backend changed a transition rule. With the rules in one place on the server and the screens taking only the result, there is no place for that drift. Even when a button shows, the server checks again with a conditional UPDATE, so a button pressed on a stale screen ends in 409.

## 4. Checking with payments off

There is no Toss test key for the demo yet, so payments are off on the production server (post 6). #115 was checked in that state: pressing pay shows the 503 `PAYMENTS_DISABLED` notice, and the order stays payable later from its detail screen.

So **the real Toss payment window has never been opened from this frontend.** Confirm, failure and retry flows were checked only with fake responses in vitest. The window's responses themselves were measured by the spike in post 4 (a separate page, SDK 2.10.0), but never wired to these screens.

## Glossary

| Term                                                                   | Meaning                                                                                              |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| SPA                                                                    | A web app that loads one page and lets browser JavaScript switch screens                             |
| [JWT](/en/blog/auth/auth-00-basics/#jwt)                               | A signed JSON token. Here, the access and refresh tokens                                             |
| Interceptor                                                            | A function axios runs before a request goes out or after a response comes back                       |
| Promise                                                                | A JavaScript object holding the result of async work that finishes later                             |
| StrictMode                                                             | A React feature that runs effects twice in development to expose side effects                        |
| Lazy loading                                                           | Fetching a screen's code only when the user enters it. The first bundle gets smaller                 |
| Theme token                                                            | A name for a design value such as a color, font or spacing. Screen code uses the name, not the value |
| [Payment switch](/en/blog/payments/payments-00-basics/#payment-switch) | One key or setting that turns the whole payment feature on or off                                    |
