## 한 줄 요약

`pr-workflow`는 AI 코딩 에이전트가 이슈를 만들거나, 브랜치를 따거나, 커밋·PR을 만들거나, 머지하거나, 브랜치를 정리하기 직전에 여는 스킬이다. 일의 순서(이슈 → 브랜치 → PR → 머지 → 브랜치 갱신), 한 번에 PR 하나, 커밋 나누는 법, 구조를 바꿀 땐 규칙 문서 먼저, 브랜치 갱신 다섯 단계, 봇 리뷰 분류를 담고 있다. 처음엔 전역 메모리에 흩어져 있던 규칙 여섯 개였고, 2026-11-13에 스킬 하나로 묶었다.

## 1. 일의 순서

비유하면 할 일 쪽지를 먼저 붙이고, 내 작업대에서 만들고, 검토 요청서를 내고, 검사를 통과하면 합치고, 마지막에 작업대를 치우는 순서다.

![Order of work: GitHub issue, branch, PR, CI 뒤 merge, branch update. trivial change는 issue를 건너뛴다](/static/images/skills-05-pr-workflow/order-of-work.svg)

_Order of work: issue → branch → PR → merge → branch update. 사소한 변경만 issue를 건너뛴다_

쪽지는 [이슈](/kr/blog/dev/devops/devops-00-basics/#이슈), 작업대는 [브랜치](/kr/blog/dev/devops/devops-00-basics/#브랜치), 검토 요청서는 [PR](/kr/blog/dev/devops/devops-00-basics/#pr), 작업대 정리는 브랜치 갱신(5절)이다.

1. 메인 레포에 GitHub 이슈를 만든다.
2. 남의 레포면 내 fork에서, 내 레포면 레포 안에서 upstream `main` 기준으로 브랜치를 딴다.
3. PR 본문에 이슈를 건다. 이 PR로 이슈가 끝나면 `Fixes #N`(머지하면 이슈가 자동으로 닫힌다), 이슈 하나를 PR 여러 개로 나눠 처리하면 `Part of #N`.
4. 머지 직후 바로 브랜치 갱신을 해서 로컬 `main`을 원격과 맞춘다. worktree에서 일했으면 메인 체크아웃도 맞춘다. 그다음에 후속 작업(문서 미러 등)을 한다.

**PR 하나에 작업 하나.** 서로 상관없는 작업은 한 PR에 합치지 않는다.

이 순서는 2026-10-31 해커톤(우왕톤) 팀 레포에서 생겼다. 에이전트가 이슈 없이 README 링크 한 줄짜리 PR을 열었고, 나는 이슈가 먼저라고 했다. 그 뒤 일반적인 관행을 같이 따져 봤다. 이슈는 논의나 공유가 필요한 일을 추적하는 도구이고, 한 줄짜리 변경은 그 PR 자체가 기록이다. 그래서 예외를 하나 뒀다.

| 사소한 변경 (이슈 없이 PR)          | 사소하지 않은 변경 (이슈 먼저)    |
| ----------------------------------- | --------------------------------- |
| 오타, 링크 하나                     | 결정이 필요한 것                  |
| 아무도 알 필요 없는 한 줄 문서 수정 | 한 번 앉아서 끝나지 않는 것       |
|                                     | 다른 사람이 이어받을 수도 있는 것 |

크기 판단은 에이전트가 한다. 나한테 "이거 이슈 만들 만큼 큰가요?"라고 묻지 않고, 정한 뒤 어느 쪽으로 했는지만 말한다. 같은 날 관련 없는 다이어그램 PR에 그 링크 수정을 합치자는 안도 나왔는데, PR 하나에 목적 하나라서 합치지 않았다.

## 2. 한 번에 PR 하나

비유하면 창구 하나에 줄을 서는 것이다. 앞사람 일이 끝나야 다음 사람이 창구에 선다. 다만 서로 다른 서류를 내는 사람은 같이 서 있어도 된다.

![One PR at a time: deploy가 따라오는 PR은 merge와 deploy 확인 뒤 다음 PR을 연다. docs-only PR은 겹치지 않으면 같이 열고 merge 순서를 본문에 적는다](/static/images/skills-05-pr-workflow/one-pr-at-a-time.svg)

_deploy가 따라오는 PR은 한 줄로, 서로 다른 파일을 고치는 docs-only PR은 같이 열어 둘 수 있다_

창구는 release 브랜치, 줄은 PR 순서다.

- 지금 PR을 CI 통과 뒤 머지하고, 그 배포까지 확인한 다음에 다음 PR을 연다.
- 대기 중인 작업은 요청받은 순서대로 한다. 작업 중에 새 요청이 오면, 따로 말하지 않는 한 지금 것부터 끝낸다.
- [CI](/kr/blog/dev/devops/devops-00-basics/#ci)가 도는 동안 다음 작업을 로컬에서 준비한다. 로컬에서는 바뀐 테스트와 format, type, migration 검사만 돌린다. 전체 테스트는 CI 몫이다.

규칙의 이유는 한 가지다. 변경 하나하나가 따로 들어가고 따로 배포돼야, 나중에 기록과 배포를 따라가기 쉽다. 두 PR을 "같이" 머지하라는 뜻으로 받아들인 적이 있어서, 지금 PR을 먼저 머지하라는 뜻이라고 규칙에 못 박았다.

예외는 2026-11-02 우왕톤에서 생겼다. 배포가 없는 docs-only PR은 서로 다른 파일이나 줄을 고치면 같이 열어 둘 수 있다. 대신 뒤에 연 PR 본문에 머지 순서를 적는다. 이 글이 속한 스킬 연재가 그 예외 그대로다. 글 하나에 PR 하나씩, 각자 다른 파일을 만들기 때문에 같이 열려 있고, 머지는 번호 순서로 한다.

[Git Flow](/kr/blog/dev/devops/devops-00-basics/#git-flow) 레포는 그 레포의 `CONTRIBUTING.md`를 따른다. 보통은 `main`이 릴리스(PR과 CI 필수, merge commit, 머지하면 배포, 태그 `vX.Y.Z`)이고, `develop`이 기본 브랜치다. `feature/*`는 CI를 기다리지 않고 `develop`으로 들어간다. Stairno가 이렇게 바꾼 과정은 [Stairno 4편의 Git Flow 절](/kr/blog/side-projects/stairno/stairno-04-payments/#6-중간에-바꾼-것-git-flow)에 있다.

레포별 예외도 한 줄 있다. Stairno는 운영 환경 쓰기와 배포가 따라오는 머지를 내가 직접 한다. 이 블로그 PR은 에이전트가 머지해도 된다.

## 3. 커밋 나누기

비유하면 요리 한 접시가 PR 하나이고, 재료 손질, 맛 보기, 굽기 같은 단계가 커밋 하나씩이다. 접시를 반찬 하나씩 따로 내지 않는다.

![Splitting commits: refactor, 실패하는 test, feat 순서의 커밋이 한 branch에 쌓여 PR 하나가 된다](/static/images/skills-05-pr-workflow/commit-slices.svg)

_한 branch 안에서 refactor → test → feat 조각이 쌓여 PR 하나가 된다_

접시는 branch와 PR, 단계는 커밋이다.

- **branch와 PR 하나 = 사용자가 쓸 수 있는 기능 하나.** 그 기능의 API, 화면, 테스트, 명세 수정이 같이 들어간다. 변경은 300~800줄쯤이고, 1000줄을 넘으면 나눌 곳을 찾는다.
- 그 기능에만 쓰이는 어댑터나 작은 수정은 같은 branch의 커밋으로 넣는다. 다음 PR을 풀어 주기만 하는 작은 PR은 만들지 않는다.
- branch 안에서는 조각마다 실패하는 `test` 커밋, 그다음 `feat` 커밋 순서다([TDD](/kr/blog/dev/devops/devops-00-basics/#tdd)). 동작을 바꾸지 않는 이동은 그 쌍 앞에 따로 `refactor` 커밋으로 둔다. 커밋 하나하나가 혼자 revert될 수 있어야 한다.
- 스테이징은 경로를 하나하나 적는다. `git add -A`는 쓰지 않는다. 이 줄의 이유를 적은 기록은 없다.

이 규칙은 관심사별로 잘게 쪼갠 작은 PR 14개가 CI와 배포 대기만 늘린 뒤에 생겼다. 기능 하나를 통째로 리뷰하고 통째로 되돌릴 수 있으면서, 조각마다 CI와 배포를 기다리지는 않는 크기를 고른 게 300~800줄이다.

## 4. 규칙 문서 먼저

비유하면 이사하기 전에 새 집 지도부터 고쳐서 돌려 보는 것이다. 지도가 확정돼야 짐을 어디에 둘지 다툼이 없다.

![Rule docs before a restructure: PR 1에서 CLAUDE.md와 규칙 문서를 고쳐 merge한 뒤, PR 2에서 파일을 옮긴다](/static/images/skills-05-pr-workflow/rule-docs-first.svg)

_규칙 문서 PR을 먼저 머지하고, 파일 이동은 다음 PR에서 한다_

지도는 규칙 문서, 이사는 파일 이동이다. 이름 규칙, 폴더 구조, 경로 같은 관례가 바뀌면 `CLAUDE.md`, 그 파일이 import하는 문서, 다른 instruction file을 먼저 고쳐 그것만으로 PR을 낸다. 그 PR이 CI를 통과해 머지된 다음에야 이동 branch를 시작한다.

이 블로그에 그대로 남아 있다. 2026-10-10 [#44](https://github.com/seren-wib/vercel-blog/pull/44)는 `docs/agent/publish_pipeline.md` 한 파일만 고쳤다(13줄 추가, 9줄 삭제). 글 파일명에 카테고리 접두사를 붙이고 이미지를 글별 폴더로 묶는다는 규칙이다. 같은 날 그다음 [#45](https://github.com/seren-wib/vercel-blog/pull/45)가 그 규칙대로 119개 파일을 옮겼다.

반대 사례도 있다. 2026-11-28 상위 카테고리를 만든 [#163](https://github.com/seren-wib/vercel-blog/pull/163)은 구조 설명 문서 커밋과 글 이동 커밋이 한 PR에 같이 들어갔다. 왜 이번엔 나누지 않았는지는 기록이 없다.

## 5. 브랜치 갱신

비유하면 공용 책상 정리다. 끝난 서류는 묻지 않고 치우고, 아직 쓰는 것만 왜 남기는지 적어 둔다.

![Branch update: fetch --prune, ff main, push fork main, delete merged, drop stashes 다섯 단계와 squash merge 판정 기준](/static/images/skills-05-pr-workflow/branch-update.svg)

_브랜치 갱신 다섯 단계. squash merge는 `git branch --merged`에 안 잡혀서 PR 상태로 판정한다_

책상은 로컬과 원격의 branch, 끝난 서류는 머지된 branch다. 내가 "브랜치 갱신"이라고 하면 에이전트는 아래를 한 번에 하고, 삭제에 대해 따로 묻지 않는다.

1. 모든 remote에 `git fetch --prune`.
2. 로컬 `main`을 `upstream/main`으로 fast-forward. 커밋 안 한 수정이 있으면 버리지 말고 stash한 뒤 upstream에 이미 그 내용이 있는지 본다.
3. fork의 `main`도 똑같이 push.
4. 머지된 branch를 로컬과 원격(fork, 내 레포면 `origin`) 양쪽에서 지운다(`git push origin --delete <b>`). 끝나면 `main`과 아직 작업 중인 branch만 남는다.
5. 내용이 이미 `main`에 있는 stash는 버린다.

끝나면 지운 branch와 남긴 branch를 짧은 목록 하나로 보고하고, 남긴 것엔 이유를 붙인다.

4단계에 함정이 둘 있다.

- **squash merge.** squash로 머지하면 `main`에는 새 커밋 하나만 생기고 branch의 커밋은 들어가지 않는다. 그래서 `git branch --merged`가 머지된 branch를 못 찾는다. 그래서 판정 기준을 바꿨다. PR이 `MERGED`이고 그 PR의 `headRefOid`(GitHub가 기억하는 PR 마지막 커밋)가 branch 끝과 같거나, branch 끝이 이미 `upstream/main` 안에 있으면 머지된 것으로 본다. branch 끝이 PR head보다 앞서 있으면, 그 뒤 커밋 내용이 다른 PR로 이미 들어갔는지 확인하고 지운다.
- **worktree.** git은 worktree에 체크아웃된 branch를 `git branch -D`로 지우지 못한다. 그래서 `git worktree remove`를 먼저 하고, 마지막에 `git worktree prune`.

이 절은 두 번 넓어졌다. 2026-11-12에는 로컬 branch만 지우고 fork의 원격 branch는 남겨 뒀었는데, 나는 갱신이라면 fork 쪽까지 정리하는 게 당연하고 지울 때마다 묻는 건 필요 없다고 했다. 그래서 fork까지, 묻지 않고로 바뀌었다. 2026-11-19에는 내 비공개 레포 하나에 로컬 branch 24개, 원격 22개가 남아 있었고 그중 22개가 이미 머지된 것이었다. 규칙이 fork만 말하고 있어서 내 레포의 `origin`은 정리 대상에서 빠져 있었다. 그날 4단계에 "내 레포면 `origin`"을 넣었고, 1절 4번 "머지 직후 바로 브랜치 갱신"도 같은 날 들어갔다. 머지 뒤에 세션이 어떻게 이어지는지는 [CH6. session-flow](/kr/blog/side-projects/skills/skills-06-session-flow/)에 있다.

## 6. 봇 리뷰 분류

비유하면 자동 맞춤법 검사기다. 빨간 줄이 다 맞는 건 아니라서, 고칠지 말지는 사람이 고른다.

![Bot reviews: bot 코멘트를 right, half right, wrong으로 나눠 각각 고치기, 묻기, 반영 안 함. human review는 언제나 답한다](/static/images/skills-05-pr-workflow/bot-triage.svg)

_bot 코멘트는 세 갈래로 나누고, 사람 리뷰는 전부 답한다_

맞춤법 검사기는 CodeRabbit 같은 AI 리뷰 봇이다. 봇 코멘트는 조언이지 머지를 막는 관문(gate)이 아니다.

- 먼저 맞음 / 반만 맞음 / 틀림으로 나눠 나에게 보여 준다.
- 맞는 건 고친다. 반만 맞는 건 고칠지 묻는다. 틀린 건 반영하지 않는다.
- 봇에 답글은 내가 달라고 할 때만 단다.
- 사람(팀원) 리뷰는 이 분류와 상관없이 언제나 답한다.

이 규칙은 우왕톤에서 왔다. 팀 레포 `AGENTS.md` 5절에 "봇 리뷰는 조언이지 게이트가 아니다"가 있었고, 지적마다 따라가면 문서가 봇 취향으로 바뀌고 커밋만 늘어난다는 게 이유였다. 실제로 첫 주에 봇이 제안 문서를 구현 명세처럼 읽고 설계를 계속 요구해서 리뷰를 멈춘 일은 [Woowangthon 1편](/kr/blog/hackathon/woowangthon/woowangthon-01-docs-and-prs/#1-첫날-혼자-올린-문서-셋)에 있다. 2026-11-06에는 수정 커밋을 push하자 봇이 요청 없이 다시 리뷰한 것도 봤다. 봇 리뷰가 PR당 한 번이라는 가정이 틀렸다는 기록이다.

## 용어 정리

| 용어                                                       | 뜻                                                                      |
| ---------------------------------------------------------- | ----------------------------------------------------------------------- |
| [이슈](/kr/blog/dev/devops/devops-00-basics/#이슈)         | GitHub에서 할 일이나 버그를 적어 두는 글                                |
| [PR](/kr/blog/dev/devops/devops-00-basics/#pr)             | 내 branch의 변경을 `main`에 합쳐 달라는 요청                            |
| fork                                                       | 남의 레포를 내 계정으로 복제한 것. 거기서 branch를 따고 PR을 보낸다     |
| upstream                                                   | fork의 원본 레포를 가리키는 remote 이름                                 |
| `Fixes #N` / `Part of #N`                                  | PR 본문에서 이슈를 거는 말. `Fixes`는 머지 때 이슈를 자동으로 닫는다    |
| fast-forward                                               | 새 merge commit 없이 branch 끝만 앞으로 옮기는 갱신                     |
| squash merge                                               | branch의 커밋을 하나로 합쳐 `main`에 넣는 머지                          |
| `headRefOid`                                               | GitHub가 기억하는 PR head 커밋의 해시                                   |
| worktree                                                   | 한 레포에서 여러 branch를 서로 다른 폴더에 동시에 체크아웃하는 git 기능 |
| stash                                                      | 커밋하지 않은 수정을 잠시 치워 두는 git 기능                            |
| [Git Flow](/kr/blog/dev/devops/devops-00-basics/#git-flow) | `main`(릴리스)과 `develop`(통합)을 나눠 쓰는 branch 모델                |
| [TDD](/kr/blog/dev/devops/devops-00-basics/#tdd)           | 실패하는 테스트를 먼저 쓰고 그걸 통과시키는 코드를 쓰는 방식            |
| docs-only PR                                               | 코드 없이 문서만 바꾸는 PR. 배포가 따라오지 않는다                      |
| bot review                                                 | AI 리뷰 봇이 PR에 다는 자동 코멘트                                      |
