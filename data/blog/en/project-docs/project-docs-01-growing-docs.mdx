## In one line

When I built this blog in May 2026, the documents were roughly a DB schema, an API spec, and a page structure. I thought that would be enough for development. But as assignments and projects piled up, I kept needing a place for requirements, decision reasons, tests, and deployment procedures, and by mid-November it had become a template of six documents. The first project moved into that template finished its migration in one day with five PRs.

## 3. Course order as my procedure

As an analogy, I pinned the process chart from class next to my own workbench.

In formal terms, I turned the **SDLC stages** into personal working rules. On 2026-10-17, a "project procedure" file appeared in the agent memory. The file says it was set up when starting the stairno.com hub documents, and that its basis was chapters 3–6 of Software Engineering. The stages were planning, requirements, design, implementation, deployment, and maintenance, with one output attached to each stage. The plan came from [chapter 3 project planning](/en/blog/software-engineering/software-engineering-ch3-project-planning/), and the SRS from [chapter 4 requirements specification](/en/blog/software-engineering/software-engineering-ch4-requirements-analysis/#433-step-3-requirements-specification-software-requirements-specification-srs).

The next day, 10-18, I wrote four documents for account.stairno.com following this procedure: `plan.md` at 179 lines, `srs.md` at 382, `sdd.md` at 534, and `test-deploy.md` at 507, for 1,602 lines in total. These four later became the model for the template. At this point Google Docs was the source, but that same day the repo's Markdown became the source of truth. How that happened is in [Part 4](/en/blog/project-docs/project-docs-04-docs-sync/).

## 4. From four to six

As an analogy, the exam plan and the moving plan that had shared one notebook each got a notebook of their own.

In technical terms, the rule of one document per SDLC stage was carried through to testing, deployment and maintenance. In the early hours of 2026-11-16, when I turned this procedure into an agent skill, the documents went from four to six. The plan got the name SPMP, and `test-deploy.md`, where testing and deployment had been mixed together, was split into three: a test plan (STP), an installation plan (SIP), and a maintenance plan (SMP).

The reason for the split was that I decided to follow convention. A convention probably has its reasons, and I figured I would only learn what is good about it by writing one the conventional way. That decision and the standard each document follows are covered separately in [Part 3](/en/blog/project-docs/project-docs-03-standards/).

## 5. Migrating via docs/old

As an analogy, it is the order you follow when moving house: put everything in boxes first, move items one by one into the drawers of the new house, then throw away the empty boxes.

![Migrating via docs/old: #59 move old docs and lay the frame, #60·#62 fill in SRS and SDD, #64 sync, #68 delete old docs](/static/images/project-docs-01-growing-docs/migration.svg)

_Migrating via docs/old: #59 move old docs and lay the frame, #60·#62 fill in SRS and SDD, #64 sync, #68 delete old docs_

In formal terms, it is a migration that isolates the existing documents as **source material** and rewrites them into the new template. I moved coffee-shop in this order over one day, 2026-11-17.

| PR                                                      | What it did                                                                | Size                   |
| ------------------------------------------------------- | -------------------------------------------------------------------------- | ---------------------- |
| [#59](https://github.com/seren-wib/coffee-shop/pull/59) | Moved the existing `docs/` to `docs/old/` and laid the `docs/specs/` frame | +557 / −10, 94 files   |
| [#60](https://github.com/seren-wib/coffee-shop/pull/60) | Rewrote the SRS                                                            | +554 / −35             |
| [#62](https://github.com/seren-wib/coffee-shop/pull/62) | Rewrote the SDD                                                            | +2,292 / −51           |
| [#64](https://github.com/seren-wib/coffee-shop/pull/64) | Google Docs sync CI                                                        | +173 / −7              |
| [#68](https://github.com/seren-wib/coffee-shop/pull/68) | Deleted `docs/old/`                                                        | +49 / −2,345, 66 files |

Writing the SRS first is a rule, because the requirement numbers are the keys that connect the other documents. The rewritten SRS contained 24 domain requirements, 57 functional requirements, 35 non-functional requirements, and 14 use cases. The SDD was written with these numbers attached.

The description of #68, which deleted the old documents, gave the reason in one line: the stage documents replace the old files, and git history keeps the old files. So the new documents have no lines like "see draft no. N", and nothing points to `docs/old/`. That way, deleting the old folder breaks no links. The same day, this order became the skill's migration rule: move the old documents to `docs/old/`, copy the template, fill in the SRS first, and delete `docs/old/`.

## 6. Still growing

As an analogy, settling on a notebook format was not the end; every time the teacher points out a blank, a new column appears.

In technical terms, this is a revision of the template. Early on 2026-11-28, the SDD template gained one section and one rule. The trigger was two pieces of feedback from the professor on the coffee-shop SDD: the parts in the wireframes had no numbers, and the class and method specs were mixed in with the component design.

- **Screen part IDs**: every UI part in the screen design gets an ID like `SCR-01-01`, and the wireframes show the same ID. Section numbers can shift, but IDs don't.
- **Class and module spec section**: following the code structure, one file per module records each public function's signature, return values and exceptions, and requirement IDs. Once written, it is checked by script against the list of `def` and `class` in the code.

These went into coffee-shop through [#129](https://github.com/seren-wib/coffee-shop/pull/129) (+1,059 / −50) and [#130](https://github.com/seren-wib/coffee-shop/pull/130). Repos that already had an SDD did not renumber their sections and appended the new section at the end. So in coffee-shop the class spec is section 12, and design rationale stays in section 11.

## Glossary

| Term                                                                                                                        | Meaning                                                                        |
| --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Design artifact                                                                                                             | A document on "how to build it", such as a schema, API spec, or page structure |
| Flat structure                                                                                                              | Documents stacked side by side under one folder with no split by type or stage |
| SDLC stages                                                                                                                 | Planning, requirements, design, implementation, deployment, maintenance        |
| [Domain requirement](/en/blog/software-engineering/software-engineering-ch4-requirements-analysis/#412-domain-requirements) | A business rule that applies across the whole system (`DR-n`)                  |
| Source material                                                                                                             | Old documents that are only read when filling in new ones                      |
| Screen part ID                                                                                                              | A number that doesn't shift, given to a UI part on a screen, like `SCR-01-01`  |
