HW4까지는 맥 안의 VM으로 HTCondor 클러스터를 만들었다. 이번엔 교재 9장대로 클러스터를 AWS EC2로 옮겼다. main과 worker 인스턴스를 만들고, worker를 머신 이미지(AMI)로 떠 둔 다음, Ubuntu 호스트에서 SDK 프로그램으로 인스턴스를 시작·중지·생성하면 Condor Pool의 노드 수가 따라 바뀌는지 확인했다. 교재는 Java SDK를 쓰지만 과제에서 다른 언어 SDK를 허용해서 Python boto3로 작성했다. 뒤쪽에는 8·9장 연습문제 답을 정리했다.

# 0. 실습 환경

HTCondor 클러스터는 AWS EC2 위에 만들었고, 인스턴스를 제어하는 프로그램은 HW2~HW4에서 쓰던 Ubuntu 호스트(UTM 위의 Ubuntu 24.04 ARM64 VM)에서 돌렸다. 인스턴스는 모두 x86_64(t3.small)지만, 제어 프로그램은 AWS API를 HTTPS로 호출할 뿐이라 호스트가 ARM64여도 상관없다.

```text
macOS (Apple M3)
└─ UTM ─ Ubuntu 24.04 ARM64 (yoosung-vm, 강의의 "Ubuntu 호스트")
         ├─ AWS CLI v2 (aarch64), Python 3.12 + boto3  ← aws_control.py
         └─ SSH (cloud-test.pem), HTTPS (EC2 API)
                │
AWS 서울 리전 ap-northeast-2, 기본 VPC 172.31.0.0/16
├─ htcondor-main    t3.small  Rocky 10.2  172.31.12.47  main
├─ htcondor-worker  t3.small  Rocky 10.2  172.31.11.85  worker
└─ AMI aws-htcondor-worker로 생성한 worker   172.31.6.235  worker
```

# 1. AWS 준비

## AWS CLI 설치

슬라이드 66쪽은 x86_64용 설치 파일을 받지만 이 호스트는 aarch64라서 `awscli-exe-linux-aarch64.zip`을 받았다. 또 슬라이드 명령의 `-o "awscliv2.zip“`는 닫는 따옴표가 둥근 따옴표(U+201C)라 그대로 붙여 넣으면 셸이 문자열을 닫지 못한다. 일반 따옴표로 입력했다.

```bash
uname -m
curl "https://awscli.amazonaws.com/awscli-exe-linux-aarch64.zip" -o "awscliv2.zip"
sudo apt install unzip -y
unzip -q awscliv2.zip
sudo ./aws/install
aws --version
```

## 자격 증명 설정

슬라이드 67~70쪽은 루트 사용자의 액세스 키를 만든다. 루트 키는 결제·계정 해지까지 계정의 모든 권한을 갖고 정책으로 제한할 수도 없어서, AWS도 생성 화면에서 "권장하지 않음" 경고를 띄운다(슬라이드 69쪽 4번 체크박스). 그래서 IAM에서 콘솔 로그인 없이 AmazonEC2FullAccess 정책만 붙인 사용자 cloud-hw를 만들고, 그 사용자의 액세스 키(사용 사례: CLI)를 발급했다. 이 키로는 EC2만 다룰 수 있다.

`aws configure`에 키와 리전(ap-northeast-2), 출력 형식(json)을 넣으면 `~/.aws/credentials`·`~/.aws/config`에 저장되고, AWS CLI와 boto3가 둘 다 이 파일을 읽는다. `aws sts get-caller-identity`로 이 키가 `user/cloud-hw`로 인증되는 것을 확인했다. 키는 끝 4자리만 보이게 가려져 출력된다.

```bash
aws configure
aws configure list; aws sts get-caller-identity
```

## 보안 그룹

8장 슬라이드 18~21쪽처럼 이름이 HTCondor인 보안 그룹을 만들고 인바운드 규칙 두 개를 넣었다. SSH(22)는 Ubuntu 호스트에서 접속해야 하므로 Anywhere(0.0.0.0/0)로 뒀다. HTCondor 포트(9618)는 슬라이드에선 Anywhere지만, 노드끼리는 VPC 사설망 주소로 통신하고 설정이 `ALLOW_WRITE = *`라서 인터넷 전체에 열면 누구나 Pool에 노드를 붙일 수 있다. 그래서 기본 VPC 대역(172.31.0.0/16)만 허용했다.

```bash
SG=$(aws ec2 create-security-group --group-name HTCondor --description "HTCondor pool (SSH + 9618)" --query GroupId --output text); echo $SG
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 22   --cidr 0.0.0.0/0     --query Return
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 9618 --cidr 172.31.0.0/16 --query Return
aws ec2 describe-security-groups --group-ids $SG --query "SecurityGroups[0].IpPermissions[].[IpProtocol,FromPort,ToPort,IpRanges[0].CidrIp]" --output table
```

## 키 페어

8장 슬라이드 28~29·34쪽대로 cloud-test RSA 키 페어를 만들어 개인 키를 `~/Downloads/cloud-test.pem`에 저장하고, SSH가 받아들이도록 소유자만 읽을 수 있게 `chmod 400`했다. 슬라이드는 `cat`으로 개인 키 전체를 출력하지만, 개인 키가 화면에 남지 않도록 첫 줄만 확인했다.

```bash
aws ec2 create-key-pair --key-name cloud-test --key-type rsa --key-format pem --query KeyMaterial --output text > cloud-test.pem
ls -l cloud-test.pem; head -1 cloud-test.pem
chmod 400 cloud-test.pem; ls -l cloud-test.pem
```

# 2. HTCondor 클러스터 구성

## main 인스턴스 생성과 접속

Rocky Linux 10.2 x86_64 AMI, t3.small, 키 페어 cloud-test, 보안 그룹 HTCondor로 인스턴스를 만들고 이름 태그를 htcondor-main으로 붙였다(슬라이드 6~15쪽). `wait instance-running`으로 Pending → Running을 기다린 다음 사설·공인 DNS를 확인하고, 슬라이드처럼 rocky 계정으로 접속했다. Rocky 이미지는 root 로그인이 막혀 있다.

```bash
AMI=ami-0e86f920feb0e6b17      # Rocky-10-EC2-Base-10.2-20260525.0.x86_64
MAIN=$(aws ec2 run-instances --image-id $AMI --instance-type t3.small --key-name cloud-test --security-groups HTCondor \
       --tag-specifications "ResourceType=instance,Tags=[{Key=Name,Value=htcondor-main}]" --query "Instances[0].InstanceId" --output text)
aws ec2 wait instance-running --instance-ids $MAIN
aws ec2 describe-instances --instance-ids $MAIN --query "Reservations[0].Instances[0].[InstanceId,InstanceType,State.Name,PrivateDnsName,PublicDnsName]" --output text
ssh -i "cloud-test.pem" rocky@ec2-15-165-74-33.ap-northeast-2.compute.amazonaws.com
```

## main에 HTCondor 설치와 설정

HTCondor 25.0 저장소 패키지를 설치하고(EPEL이 같이 설치된다) condor를 설치했다(슬라이드 16~19쪽). `condor_config.local`은 슬라이드와 같은 여섯 줄이고, `CONDOR_HOST`에는 main 자신의 사설 DNS 이름을 넣었다. main은 Pool의 중앙 관리자라서 COLLECTOR·NEGOTIATOR가, 작업 제출을 받으니 SCHEDD가, 작업도 실행하니 STARTD가 같이 뜬다. 서비스를 시작하자 `condor_status`에 main 슬롯 하나가 나타났고, 재부팅 후에도 뜨도록 enable했다.

```bash
sudo su -
dnf install -y https://research.cs.wisc.edu/htcondor/repo/25.0/htcondor-release-current.el10.noarch.rpm
dnf install -y condor
cd /etc/condor/config.d
printf "%s\n" "ALLOW_WRITE = *" "CONDOR_HOST = $(hostname)" "DAEMON_LIST = MASTER, SCHEDD, STARTD, COLLECTOR, NEGOTIATOR" \
  "SEC_PASSWORD_FILE = /etc/condor/passwords.d/POOL" "SEC_DEFAULT_AUTHENTICATION_METHODS = PASSWORD,FS" \
  "SEC_DAEMON_AUTHENTICATION_METHODS = PASSWORD,FS" > condor_config.local
systemctl start condor; condor_status
systemctl enable condor; systemctl status condor
```

## main → worker SSH 키

Pool 비밀번호 파일을 main에서 worker로 복사하려고 main의 rocky 계정이 worker에 키로 접속할 수 있게 했다(슬라이드 29~31쪽). 두 노드에서 ed25519 키를 만들고(빈 암호), main의 공개 키를 worker의 `~/.ssh/authorized_keys`에 추가했다. 이 파일의 첫 줄은 인스턴스 생성 때 AWS가 넣은 cloud-test 키다. main에서 worker의 사설 DNS로 접속되는 것을 확인했다. 보안 그룹의 22번 규칙이 VPC 안 접속도 허용한다.

```bash
ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519          # main, worker 각각
cat ~/.ssh/id_ed25519.pub                                   # main
echo "ssh-ed25519 AAAA... rocky@ip-172-31-12-47..." >> ~/.ssh/authorized_keys   # worker
ssh rocky@ip-172-31-11-85.ap-northeast-2.compute.internal   # main → worker
```

## Pool 비밀번호 공유와 2대 확인

두 노드 설정이 데몬 간 인증을 PASSWORD 방식으로 하므로, 같은 Pool 비밀번호 파일을 둘 다 가져야 서로를 믿는다(슬라이드 32~35쪽). main에서 `condor_store_cred add -c`로 Pool 비밀번호를 만들면 `/etc/condor/passwords.d/POOL`(root만 읽기)이 생긴다. 비밀번호는 무작위 문자열로 넣고 기록하지 않았다. 이 파일을 rocky 소유로 복사해 scp로 worker의 `/tmp`에 보내고, worker에서 같은 위치로 옮겨 권한을 600·root로 되돌렸다. 두 노드의 md5가 같은 것을 확인하고 condor를 재시작하자 `condor_status`에 2대가 나타났다(중간에 생긴 문제는 아래 문제 1).

```bash
condor_store_cred add -c                                   # main, root
cp /etc/condor/passwords.d/POOL /home/rocky/POOL; chown rocky:rocky /home/rocky/POOL; exit
scp /home/rocky/POOL rocky@ip-172-31-11-85.ap-northeast-2.compute.internal:/tmp/ && rm /home/rocky/POOL
mkdir -p /etc/condor/passwords.d && mv /tmp/POOL /etc/condor/passwords.d/          # worker, root
chmod 600 /etc/condor/passwords.d/POOL; chown root:root /etc/condor/passwords.d/POOL
md5sum /etc/condor/passwords.d/POOL; systemctl restart condor                    # 양쪽
condor_status                                                                    # main
```

## Python boto3로 작성

Java 대신 Python용 AWS SDK인 boto3로 작성했다(`~/cloud_project/aws_control.py`, 156줄). 교재의 Java SDK v1(1.11.x)은 2025년 말에 지원이 끝났고, boto3는 Ubuntu 패키지(`python3-boto3`)로 설치돼서 JDK·라이브러리 묶음을 따로 받을 필요가 없다. 메뉴와 출력 형식은 슬라이드 42~63쪽 화면에 맞췄다. 프로그램은 실행할 때 `boto3.client("ec2")` 하나를 만들고, 자격 증명과 리전은 앞에서 설정한 `~/.aws` 파일에서 읽는다. 메뉴별로 호출하는 EC2 API는 다음과 같다.

| 메뉴                 | boto3 호출 (EC2 API)                | 동작                                                                                   |
| -------------------- | ----------------------------------- | -------------------------------------------------------------------------------------- |
| 1. list instance     | `describe_instances` (페이지네이터) | 모든 인스턴스의 ID·Name 태그·타입·상태·사설 IP                                         |
| 2. available zones   | `describe_availability_zones`       | 현재 리전의 가용 영역 ID·이름과 개수                                                   |
| 3. start instance    | `start_instances`                   | 입력한 ID의 인스턴스 시작                                                              |
| 4. available regions | `describe_regions`                  | 계정에서 쓸 수 있는 리전과 EC2 엔드포인트                                              |
| 5. stop instance     | `stop_instances`                    | 입력한 ID의 인스턴스 중지                                                              |
| 6. create instance   | `run_instances`                     | 입력한 AMI로 t3.small·cloud-test·HTCondor 인스턴스 1대 생성, Name 태그 htcondor-worker |
| 7. reboot instance   | `reboot_instances`                  | 입력한 ID의 인스턴스 재부팅                                                            |
| 8. list images       | `describe_images(Owners=["self"])`  | 내 계정이 만든 AMI 목록                                                                |
| 99. quit             | —                                   | 종료                                                                                   |

API 오류(권한 없음, 잘못된 ID 등)는 `ClientError`로 잡아 메시지만 출력하고 메뉴로 돌아가고, 숫자가 아닌 입력은 `concentration!`을 출력하고 무시한다. create의 키 페어·보안 그룹·타입은 환경 변수로 바꿀 수 있다. 전체 소스는 다음과 같다.

```python:aws_control.py
#!/usr/bin/env python3
"""Amazon AWS Control Panel using SDK (boto3).

HW5 / Ch9 "AWS dynamic resource management" tool. Same menu as the
textbook's Java version (awsTest.java), written with the AWS SDK for Python.

Credentials and default region come from ~/.aws (set with `aws configure`).
Settings for "create instance" can be overridden with environment variables:
  AWS_KEY_NAME        key pair name           (default: cloud-test)
  AWS_SECURITY_GROUP  security group name     (default: HTCondor)
  AWS_INSTANCE_TYPE   instance type           (default: t3.small)
"""
import os
import sys

import boto3
from botocore.exceptions import BotoCoreError, ClientError

KEY_NAME = os.environ.get("AWS_KEY_NAME", "cloud-test")
SECURITY_GROUP = os.environ.get("AWS_SECURITY_GROUP", "HTCondor")
INSTANCE_TYPE = os.environ.get("AWS_INSTANCE_TYPE", "t3.small")

ec2 = boto3.client("ec2")

MENU = """
------------------------------------------------------------
           Amazon AWS Control Panel using SDK
------------------------------------------------------------
  1. list instance                2. available zones
  3. start instance               4. available regions
  5. stop instance                6. create instance
  7. reboot instance              8. list images
                                 99. quit
------------------------------------------------------------"""


def name_tag(tags):
    for t in tags or []:
        if t["Key"] == "Name":
            return t["Value"]
    return "-"


def list_instances():
    print("Listing instances....")
    pages = ec2.get_paginator("describe_instances").paginate()
    for page in pages:
        for res in page["Reservations"]:
            for i in res["Instances"]:
                print(
                    f"[id] {i['InstanceId']}, "
                    f"[name] {name_tag(i.get('Tags')):<15}, "
                    f"[type] {i['InstanceType']}, "
                    f"[state] {i['State']['Name']:>10}, "
                    f"[private IP] {i.get('PrivateIpAddress', '-')}"
                )


def available_zones():
    print("Available zones....")
    zones = ec2.describe_availability_zones()["AvailabilityZones"]
    for z in zones:
        print(f"[id] {z['ZoneId']}, [region] {z['RegionName']:>15}, [zone] {z['ZoneName']:>15}")
    print(f"You have access to {len(zones)} Availability Zones.")


def available_regions():
    print("Available regions ....")
    for r in ec2.describe_regions()["Regions"]:
        print(f"[region] {r['RegionName']:>15}, [endpoint] {r['Endpoint']}")


def start_instance(iid):
    print(f"Starting .... {iid}")
    ec2.start_instances(InstanceIds=[iid])
    print(f"Successfully started instance {iid}")


def stop_instance(iid):
    ec2.stop_instances(InstanceIds=[iid])
    print(f"Successfully stop instance {iid}")


def reboot_instance(iid):
    print(f"Rebooting .... {iid}")
    ec2.reboot_instances(InstanceIds=[iid])
    print(f"Successfully rebooted instance {iid}")


def create_instance(ami):
    res = ec2.run_instances(
        ImageId=ami,
        InstanceType=INSTANCE_TYPE,
        KeyName=KEY_NAME,
        SecurityGroups=[SECURITY_GROUP],
        MinCount=1,
        MaxCount=1,
        TagSpecifications=[{
            "ResourceType": "instance",
            "Tags": [{"Key": "Name", "Value": "htcondor-worker"}],
        }],
    )
    iid = res["Instances"][0]["InstanceId"]
    print(f"Successfully started EC2 instance {iid} based on AMI {ami}")


def list_images():
    print("Listing images....")
    for img in ec2.describe_images(Owners=["self"])["Images"]:
        print(f"[ImageID] {img['ImageId']}, [Name] {img.get('Name', '-')}, "
              f"[Owner] {img['OwnerId']}, [State] {img['State']}")


ACTIONS = {
    1: (list_instances, None),
    2: (available_zones, None),
    3: (start_instance, "Enter instance id: "),
    4: (available_regions, None),
    5: (stop_instance, "Enter instance id: "),
    6: (create_instance, "Enter ami id: "),
    7: (reboot_instance, "Enter instance id: "),
    8: (list_images, None),
}


def main():
    while True:
        print(MENU)
        try:
            choice = int(input("Enter an integer: ").strip())
        except ValueError:
            print("concentration!")
            continue
        except EOFError:
            return
        if choice == 99:
            print("bye!")
            return
        if choice not in ACTIONS:
            print("concentration!")
            continue
        func, prompt = ACTIONS[choice]
        try:
            if prompt:
                arg = input(prompt).strip()
                if not arg:
                    continue
                func(arg)
            else:
                func()
        except (ClientError, BotoCoreError) as e:
            print(f"Error: {e}")


if __name__ == "__main__":
    sys.exit(main())
```

# 5. 실습 중 생긴 문제

## 문제 1. Pool 비밀번호를 맞춘 뒤에도 worker가 안 보임

**증상**: 두 노드의 POOL md5가 같은데 main의 `condor_status`에 main 1대만 있었다. worker의 `/var/log/condor/StartLog`에 `attempt to connect to <172.31.12.47:9618> failed: Connection refused`, `TCP connection to collector ... failed`가 찍혀 있었다.

**원인**: POOL 파일을 설치한 worker를 main보다 먼저 재시작해서, worker가 처음 등록하려던 시점에 main의 collector가 재시작 중이라 연결이 거부됐다. startd는 정기 갱신(기본 5분) 때 다시 보내므로 기다리면 붙지만, 그 전까지는 Pool에 없다.

**해결**: main을 재시작한 다음 worker를 한 번 더 재시작하니 바로 2대가 됐다. 슬라이드 34쪽 순서(main → worker)대로 하면 안 생긴다.

## 문제 2. AWS 요청이 갑자기 인증 실패

**증상**: 실습 도중 Ubuntu 호스트의 aws 명령이 `AuthFailure`, `SignatureDoesNotMatch: Signature expired: 20261027T111114Z is now earlier than 20261027T114023Z`로 실패했다.

**원인**: Ubuntu VM의 시계가 실제보다 44분 늦어 있었다. 맥이 잠자기에 들어간 동안 VM 시계가 멈췄던 것으로 보인다. AWS는 서명에 들어간 요청 시각이 서버 시각과 15분 넘게 차이 나면 재전송 공격으로 보고 거부한다.

**해결**: `sudo systemctl restart systemd-timesyncd`로 NTP 동기화를 다시 해서 시계를 맞추자 바로 인증됐다.

# 6. 연습문제

## Ch8-9. AWS에서 제공하는 다양한 AMI

> 아마존 AWS에서 제공하는 다양한 AMI에 대해서 조사하고 특징을 설명하라.

AMI(Amazon Machine Image)는 인스턴스를 띄울 때 쓰는 템플릿으로, 루트 볼륨의 스냅샷(OS와 설치된 소프트웨어), 시작 권한(누가 이 AMI를 쓸 수 있는지), 인스턴스에 붙일 볼륨 매핑 정보로 이루어진다. 같은 AMI로 여러 인스턴스를 띄우면 모두 같은 상태로 시작하므로, 이번 실습에서 HTCondor가 설치된 worker를 AMI로 만들어 두고 메뉴 6(create instance)으로 똑같은 worker를 하나 더 띄울 수 있었다. AMI는 누가 만들어 어디에 공개했는지에 따라 다음 네 가지로 나뉜다.

| 구분                       | 내용 / 예                                                                                                                                       | 특징                                                                                                                                                                                                                                                                     |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

그 밖에 특정 용도로 미리 맞춰 둔 AMI도 있다. 딥러닝 프레임워크와 GPU 드라이버를 넣은 Deep Learning AMI, 컨테이너 서비스용으로 Docker·에이전트를 넣은 ECS/EKS 최적화 AMI, 컨테이너 실행만을 위한 최소 OS인 Bottlerocket 등이다.

AMI를 고를 때는 다음 속성을 함께 확인해야 한다.

- **아키텍처**: x86_64(Intel·AMD) 또는 arm64(AWS Graviton). 인스턴스 타입과 맞아야 한다. 이번에는 t3.small을 쓰려고 x86_64 Rocky AMI를 골랐다(호스트 Ubuntu가 aarch64인 것과는 상관없음).
- **루트 디바이스 유형**: EBS 기반은 중지(stop)·시작이 가능하고 디스크 내용이 남는다. 인스턴스 스토어 기반은 중지할 수 없고 종료하면 데이터가 사라진다. 지금은 대부분 EBS 기반이다.
- **가상화 유형·부팅 모드**: 현재 세대 인스턴스는 HVM만 지원하며, 부팅 모드는 Legacy BIOS·UEFI 중 인스턴스 타입이 지원하는 것이어야 한다.
- **리전**: AMI는 리전마다 따로 있고 ID도 다르다. 같은 Rocky 10.2라도 서울 리전의 ID를 써야 하며, 다른 리전에서 쓰려면 AMI를 복사(copy-image)해야 한다.

## Ch8-13. AWS 인스턴스 타입의 종류와 특징

> AWS에서 제공하는 인스턴스 타입(예: t3.nano)은 어떤 것이 있고 특징은 무엇인지 설명하라.

인스턴스 타입은 인스턴스에 할당되는 vCPU 수, 메모리, 스토리지, 네트워크 성능의 조합이다. 이름은 `패밀리 + 세대 + (추가 속성) . 크기` 형식이다. 예를 들어 t3.nano는 T 패밀리(버스트형 범용) 3세대의 nano 크기이고, c7gn.xlarge는 C 패밀리(컴퓨팅 최적화) 7세대, g(Graviton 프로세서), n(네트워크 강화)의 xlarge 크기다. 숫자가 클수록 최신 세대로, 같은 가격에 성능이 더 좋다.

| 분류            | 대표 패밀리              | 특징·용도                                                                                                                                                                                                             |
| --------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 범용            | T, M, Mac                | CPU·메모리 균형(vCPU 1개당 메모리 약 4GiB). M은 웹 서버, 중소 규모 DB 등 일반 작업. T는 평소엔 기준 성능 아래로 쓰다가 필요할 때 CPU를 순간적으로 끌어올리는 버스트형으로 가장 저렴함. Mac은 macOS 실행용 전용 호스트 |
| 컴퓨팅 최적화   | C                        | vCPU 대비 메모리가 적음(약 2GiB). 배치 처리, 과학 계산, 동영상 인코딩, 게임 서버처럼 CPU를 오래 많이 쓰는 작업. HTCondor 작업 노드로 쓰기 좋음                                                                        |
| 메모리 최적화   | R, X, z, u-(High Memory) | vCPU 대비 메모리가 큼(R 약 8GiB, X 약 16GiB 이상). 인메모리 DB(Redis, SAP HANA), 대용량 분석. z는 높은 클럭 주파수                                                                                                    |
| 가속 컴퓨팅     | P, G, Inf, Trn, F        | GPU(P: 머신러닝 학습·HPC, G: 그래픽·추론), AWS 자체 칩(Inferentia: 추론, Trainium: 학습), FPGA(F) 장착. 가장 비쌈                                                                                                     |
| 스토리지 최적화 | I, D, H                  | 인스턴스에 직접 붙은 로컬 NVMe SSD·HDD로 디스크 입출력이 매우 빠름. NoSQL DB, 데이터 웨어하우스, 분산 파일 시스템                                                                                                     |
| HPC 최적화      | Hpc                      | 고성능 컴퓨팅용. 노드 간 저지연 네트워크(EFA)를 갖춰 대규모 병렬 계산에 맞음                                                                                                                                          |

이름 중간의 추가 속성은 다음과 같다: g AWS Graviton(Arm) 프로세서, a AMD 프로세서, i Intel 프로세서, d 로컬 NVMe 스토리지 포함, n 네트워크 대역폭 강화, e 메모리·스토리지 추가, flex 가격을 낮춘 유연형. 크기는 nano &lt; micro &lt; small &lt; medium &lt; large &lt; xlarge &lt; 2xlarge … 순으로 커지며, 한 단계 오를 때마다 대체로 자원과 요금이 두 배가 된다. metal은 가상화 없이 물리 서버 전체를 쓰는 베어메탈이다.

문제의 예인 T3 패밀리는 크기별로 다음과 같다.

| 타입                   | vCPU  | 메모리      | vCPU당 기준 성능 |
| ---------------------- | ----- | ----------- | ---------------- |
| t3.nano                | 2     | 0.5 GiB     | 5%               |
| t3.micro               | 2     | 1 GiB       | 10%              |
| t3.small               | 2     | 2 GiB       | 20%              |
| t3.medium              | 2     | 4 GiB       | 20%              |
| t3.large               | 2     | 8 GiB       | 30%              |
| t3.xlarge / t3.2xlarge | 4 / 8 | 16 / 32 GiB | 40%              |

T 패밀리는 기준 성능보다 적게 쓰는 동안 CPU 크레딧이 쌓이고, 순간적으로 CPU를 많이 쓸 때 크레딧을 소모해 100%까지 올린다. T3는 기본이 Unlimited 모드라 크레딧이 바닥나도 성능은 유지되지만, 기준을 넘긴 사용량만큼 추가 요금이 붙는다. 그래서 평소 한가한 개발·테스트 서버에는 싸고 적당하지만, CPU를 계속 100% 쓰는 계산 작업에는 C나 M 패밀리가 더 경제적이다. 이번 실습에서는 HTCondor 데몬 여러 개를 띄우기에 1GiB는 빠듯해 t3.small(2 vCPU, 2GiB)을 썼고, `condor_status`에 슬롯 메모리가 1711MB로 표시됐다(OS와 커널이 쓰는 몫을 뺀 값).

## Ch9-3. 툴에서 condor_status 바로 실행하기

> condor_status 명령을 프로그램 툴에서 직접 실행시킬 수 있도록 변경하라.

실습에서는 툴에서 start·stop·create를 한 뒤 Pool이 바뀌었는지 보려고 main 인스턴스의 SSH 창으로 옮겨 가 `condor_status`를 따로 입력했다. 이걸 툴 안에서 바로 하도록 메뉴 `9. condor status`를 추가했다(`aws_control.py`).

`condor_status`는 Collector가 돌고 있는 main 노드에서 실행해야 한다. 툴이 도는 Ubuntu 호스트에는 HTCondor가 없고, 보안 그룹에서 9618 포트를 VPC 내부(172.31.0.0/16)에만 열어 둬서 바깥에서 Collector에 직접 물어볼 수도 없다. 그래서 툴이 SSH로 main에 접속해 명령을 실행하고 결과를 받아 출력하게 했다.

1. **주소 조회**: EC2 API `describe_instances`로 Name 태그가 htcondor-main이고 상태가 running인 인스턴스를 찾는다. main의 공인 DNS 이름은 중지·시작할 때마다 바뀌므로 고정값으로 두지 않고 매번 조회한다.
2. **원격 실행**: 찾은 주소로 `ssh -i cloud-test.pem rocky@<공인 DNS> condor_status`를 실행한다(Python `subprocess`). 주소가 바뀌어도 멈추지 않게 처음 보는 호스트 키는 자동으로 받아들이고(`StrictHostKeyChecking=accept-new`), 접속 10초·전체 60초 제한을 뒀다.
3. **결과 출력**: 표준 출력을 그대로 보여 주고, 실패하면 SSH의 오류 메시지를 출력한다. main이 꺼져 있으면 `htcondor-main is not running.`을 출력한다.

```python:aws_control.py
MAIN_NAME = os.environ.get("AWS_MAIN_NAME", "htcondor-main")
KEY_FILE = os.path.expanduser(os.environ.get("AWS_KEY_FILE", "~/Downloads/cloud-test.pem"))
SSH_USER = os.environ.get("AWS_SSH_USER", "rocky")

def condor_status():
    # The public DNS name changes on every stop/start, so look it up each time.
    res = ec2.describe_instances(Filters=[
        {"Name": "tag:Name", "Values": [MAIN_NAME]},
        {"Name": "instance-state-name", "Values": ["running"]},
    ])
    insts = [i for r in res["Reservations"] for i in r["Instances"]]
    if not insts:
        print(f"{MAIN_NAME} is not running.")
        return
    host = insts[0].get("PublicDnsName") or insts[0].get("PublicIpAddress")
    print(f"Running condor_status on {MAIN_NAME} ({insts[0]['InstanceId']}) ....")
    try:
        r = subprocess.run(
            ["ssh", "-i", KEY_FILE,
             "-o", "StrictHostKeyChecking=accept-new",
             "-o", "ConnectTimeout=10",
             f"{SSH_USER}@{host}", "condor_status"],
            capture_output=True, text=True, timeout=60,
        )
    except subprocess.TimeoutExpired:
        print("Error: condor_status timed out")
        return
    print(r.stdout, end="")
    if r.returncode != 0:
        print(f"Error: {r.stderr.strip()}")

ACTIONS = {
    ...
    8: (list_images, None),
    9: (condor_status, None),   # added
}
```

메뉴에도 `9. condor status` 줄을 추가했다. 이제 "5 stop instance → 9 condor status → 3 start instance → 9 condor status"처럼 한 화면 안에서 인스턴스 조작과 Pool 변화를 이어서 확인할 수 있다. 키 파일 위치·접속 사용자·main 이름은 환경 변수(`AWS_KEY_FILE`, `AWS_SSH_USER`, `AWS_MAIN_NAME`)로 바꿀 수 있게 해서 다른 계정이나 클러스터에도 그대로 쓸 수 있다.

다른 방법으로는 AWS Systems Manager의 Run Command(`ssm.send_command`)로 SSH 없이 명령을 보내는 방법이 있다. 키 파일을 들고 다닐 필요가 없고 22번 포트를 닫아도 되지만, 인스턴스에 SSM 에이전트와 IAM 역할을 따로 붙여야 하고(이번 Rocky AMI에는 에이전트가 없음) 결과를 다시 조회해야 해서, 이미 SSH로 운영 중인 이번 환경에는 SSH 방식이 간단하다.

## Ch9-12. 가상머신 API를 제공하는 국내 클라우드

> 가상머신을 제어할 수 있는 API를 제공하는 국내 클라우드 서비스 제공자에 대해 조사하고 내용을 요약하라.

국내 주요 클라우드 사업자도 AWS처럼 콘솔 외에 API·CLI·SDK로 가상머신을 만들고 켜고 끌 수 있게 한다. 사업자마다 인증 방식과 API 체계가 다른데, 크게 AWS처럼 액세스 키로 요청에 서명하는 방식(네이버 클라우드)과 OpenStack처럼 먼저 토큰을 받아 요청 헤더에 넣는 방식(NHN Cloud, 카카오클라우드)으로 나뉜다.

| 사업자                      | 가상머신 API                                                                                                                                                                                                                     | 인증·특징                                                                                                                                                                                                                                                                  |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 네이버 클라우드 플랫폼(NCP) | Server API(REST). VPC 환경은 `/vserver/v2/` 아래 `createServerInstances`, `startServerInstances`, `stopServerInstances`, `rebootServerInstances`, `getServerInstanceList` 등. CLI, Java·Python 등 SDK, Terraform 프로바이더 제공 | 콘솔에서 발급한 Access Key·Secret Key로 요청을 HmacSHA256 서명해 `x-ncp-apigw-signature-v2` 헤더에 넣고, 타임스탬프·액세스 키 헤더를 함께 보냄. 서버 시각과 5분 넘게 차이 나면 거부(AWS의 서명 방식과 비슷함). API 이름 체계가 이번 실습의 boto3 함수와 거의 일대일로 대응 |
| NHN Cloud                   | OpenStack 기반. Compute(Instance) API가 OpenStack Nova와 호환되며, 리전(판교 kr1, 평촌 kr2 등)마다 엔드포인트가 다름                                                                                                             | 계정 비밀번호와 별도인 API 비밀번호를 설정하고, Identity API(`POST /v2.0/tokens`)에 테넌트 ID·사용자·API 비밀번호를 보내 토큰을 받은 뒤 `X-Auth-Token` 헤더로 호출. OpenStack 호환이라 OpenStack CLI·SDK·Terraform 도구를 그대로 쓸 수 있음                                |
| 카카오클라우드              | OpenStack 기반 Virtual Machine 서비스. REST API, CLI, Terraform 제공                                                                                                                                                             | 콘솔 프로필에서 프로젝트별 액세스 키를 발급(IAM 역할에 따라 권한 결정, 보안 키는 생성 때만 조회 가능). `https://iam.kakaocloud.com/identity/v3/auth/tokens`로 토큰을 받아 응답 헤더 `X-Subject-Token`의 값을 사용, 12시간 후 만료                                          |
| KT Cloud                    | Open API로 서버 생성·시작·정지·삭제(예: `deployVirtualMachine`). Python SDK 예제 제공                                                                                                                                            | API 키·비밀 키로 요청에 서명. 서버를 만들 때 템플릿 ID(OS), 서비스 오퍼링 ID(사양), 존을 지정하는 CloudStack 계열 구조                                                                                                                                                     |

정리하면, 국내 사업자도 가상머신의 생성·시작·중지·재부팅·조회를 모두 API로 제공하므로, 이번 과제의 동적 자원 관리 툴에서 boto3 호출 부분만 각 사업자의 API로 바꾸면 같은 메뉴를 그대로 만들 수 있다. 특히 NHN Cloud와 카카오클라우드는 OpenStack 표준 API를 따르므로 OpenStack SDK 하나로 두 곳을 함께 다룰 수 있고, 네이버 클라우드는 AWS와 비슷한 키 서명 방식이라 AWS 툴의 구조를 옮기기 쉽다. 공공기관용으로는 네이버 클라우드·NHN Cloud·KT Cloud 모두 별도의 공공 리전(CSAP 인증)을 두고 같은 형태의 API를 제공한다.
