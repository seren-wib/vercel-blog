# 4. Index construction

## 4.1 Introduction

**How do we build an [inverted index](/en/blog/cs-fundamentals/information-retrieval/information-retrieval-ch1-boolean-retrieval/#12-inverted-index) for a very large collection → first, the hardware constraints**

1. Hardware basics
   - Many IR design decisions are dictated by hardware constraints
   - **Memory access is much faster than disk** (roughly 10×)
   - **Disk [seek](glossary:disk-seek) = idle time**: no data is transferred while the disk head is positioning
   - One [seek](glossary:disk-seek) (5 ms) = the time to transfer 250,000 bytes → seeks are overwhelmingly expensive
   - **One big chunk > many small chunks**: disk → memory transfer is fast only if you cut down the number of seeks
   - Disk I/O is block-based: whole blocks are read and written, not small pieces. Block size 8KB \~ 256KB
   - IR servers: several GB of memory, several TB of disk
   - **[Fault tolerance](glossary:fault-tolerance) is expensive** → many ordinary machines are cheaper than one expensive machine that never fails (leads into [4.4 distributed indexing](#44-distributed-indexing))

2. The [RCV1](glossary:reuters-rcv1) collection
   - Shakespeare's collected works are too small → use **[Reuters RCV1](glossary:reuters-rcv1)** as the example for scalable [index construction](glossary:index-construction)
   - English newswire articles from 1995\~1996 (one year). Example: "Extreme conditions create rare Antarctic clouds"

   | Symbol | Statistic                                                                                                                           | Value       |
   | ------ | ----------------------------------------------------------------------------------------------------------------------------------- | ----------- |
   | N      | documents                                                                                                                           | 800,000     |
   | L      | [tokens](glossary:token) per document                                                                                               | 200         |
   | M      | [terms](/en/blog/cs-fundamentals/information-retrieval/information-retrieval-ch2-term-vocabulary-postings/#22-terms) (= word types) | 400,000     |
   |        | bytes per [token](glossary:token) (incl. spaces/punctuation)                                                                        | 6           |
   |        | bytes per [token](glossary:token) (without)                                                                                         | 4.5         |
   |        | bytes per [term](glossary:term)                                                                                                     | 7.5         |
   | T      | non-positional [postings](glossary:postings-list)                                                                                   | 100,000,000 |
   - Exercise: how often does a [term](glossary:term) occur on average = total [tokens](glossary:token) N × L = 160,000,000 / M 400,000 = **400 times**
   - Exercise: why 4.5 bytes per [token](glossary:token) vs 7.5 bytes per [term](glossary:term) = frequent words (the, of, a) are short. The [token](glossary:token) average counts short words countless times, the [term](glossary:term) average counts each word only once
   - Exercise: number of [positional postings](glossary:positional-index) = one per position = number of [tokens](glossary:token) = **160,000,000**

3. Exercise: why doesn't this algorithm work for very large collections
   - The [ch1 approach](/en/blog/cs-fundamentals/information-retrieval/information-retrieval-ch1-boolean-retrieval/#12-inverted-index) (load all [postings](glossary:postings-list) into memory and sort) fails once the [postings](glossary:postings-list) don't fit in memory → we have to use disk → [4.2 BSBI](#42-bsbi-algorithm)

## 4.2 BSBI algorithm

**How to sort [postings](glossary:postings-list) that don't fit in memory by using the disk**

1. Goal: build an [inverted index](glossary:inverted-index)
   - [dictionary](glossary:dictionary) ([term](glossary:term)) → [postings](glossary:postings-list) (list of docIDs). Example: Brutus → 1 2 4 11 31 45 173 174

2. The [ch1 approach](/en/blog/cs-fundamentals/information-retrieval/information-retrieval-ch1-boolean-retrieval/#12-inverted-index): sort in memory
   - While parsing documents, list ([term](glossary:term), [docID](glossary:docid)) pairs → sort by [term](glossary:term) (then by [docID](glossary:docid)) → group identical [terms](glossary:term) into [postings](glossary:postings-list) lists
   - Example: Doc 1 `I did enact julius caesar ...`, Doc 2 `so let it be with caesar ...` → after sorting: ambitious 2, be 2, brutus 1, brutus 2, capitol 1, caesar 1, caesar 2, ...

3. Why it fails for large collections
   - Documents are parsed one at a time → no [term](glossary:term)'s [postings](glossary:postings-list) are complete until the last document
   - Keep all [postings](glossary:postings-list) in memory and sort at the end? Not for a large collection → **intermediate results must be stored on disk**
   - Run the same algorithm on disk? No. Sorting on disk needs **too many seeks** and is slow → we need **[external sorting](glossary:external-sorting)**

4. External sorting ([RCV1](glossary:reuters-rcv1))

   ![BSBI: sort each block in memory, write it to disk, and merge at the end](/static/images/information-retrieval-ch4-index-construction/bsbi.svg)
   - What to sort: T = 100 million non-positional [postings](glossary:postings-list)
   - **One [posting](glossary:postings-list) = 12 bytes**: termID 4 + [docID](glossary:docid) 4 + [term](glossary:term) frequency 4
   - **Block = 10 million [postings](glossary:postings-list)** (120MB, fits in memory easily) → [RCV1](glossary:reuters-rcv1) has 10 blocks
   - For each block: (i) accumulate [postings](glossary:postings-list) (ii) sort in memory (iii) write to disk
   - At the end, **merge** the blocks into one long sorted result
   - In the figure: blue dashed box = memory (one block at a time), orange = disk files f1 \~ f10 → merge → final index

5. Merging two blocks
   - Each block is already sorted → compare the heads of the two blocks and take the smaller one first (two pointers, like the [intersection from ch1](/en/blog/cs-fundamentals/information-retrieval/information-retrieval-ch1-boolean-retrieval/#13-processing-boolean-queries))

   - The blocks as they are: Block 1 = brutus d3, caesar d4, noble d3, with d4 / Block 2 = brutus d2, caesar d1, julius d1, killed d2
   - Comparison: [term](glossary:term) first (alphabetical), and if the [terms](glossary:term) are equal, the smaller [docID](glossary:docid)

   | Step | Head of Block 1 | Head of Block 2 | Taken out |
   | ---- | --------------- | --------------- | --------- |
   | 1    | brutus d3       | brutus d2       | brutus d2 |
   | 2    | brutus d3       | caesar d1       | brutus d3 |
   | 3    | caesar d4       | caesar d1       | caesar d1 |
   | 4    | caesar d4       | julius d1       | caesar d4 |
   | 5    | noble d3        | julius d1       | julius d1 |
   | 6    | noble d3        | killed d2       | killed d2 |
   | 7    | noble d3        | (end)           | noble d3  |
   | 8    | with d4         | (end)           | with d4   |
   - Merged result = the order things were taken out: brutus d2, brutus d3, caesar d1, caesar d4, julius d1, killed d2, noble d3, with d4

6. Algorithm

   ```text
   BSBIndexConstruction()
   n = 0
   while (all documents have not been processed)
     n = n + 1
     block = ParseNextBlock()
     BSBI-Invert(block)
     WriteBlockToDisk(block, f_n)
   MergeBlocks(f_1, ..., f_n; f_merged)
   ```

   - ParseNextBlock: reads documents and collects one block's worth of (termID, [docID](glossary:docid)) pairs
   - BSBI-Invert: sorts the block in memory and groups identical termIDs into [postings](glossary:postings-list) lists
   - WriteBlockToDisk: writes that block's result to disk file f_n
   - MergeBlocks: merges f_1 \~ f_n into the final index f_merged

## 4.3 SPIMI algorithm

**A method that removes [BSBI](glossary:bsbi)'s [term](glossary:term)→termID [dictionary](glossary:dictionary) problem and doesn't sort either**

1. The problem with [BSBI](glossary:bsbi) (sort-based)
   - Assumption: **the [dictionary](glossary:dictionary) can stay in memory** → mapping [term](glossary:term) → termID needs the [dictionary](glossary:dictionary), but the [dictionary](glossary:dictionary) keeps growing
   - What if we use ([term](glossary:term), [docID](glossary:docid)) [postings](glossary:postings-list) instead of termIDs? → intermediate files become huge → it scales, but very slowly

2. [SPIMI](glossary:spimi) (Single-pass in-memory indexing)

   ![For the same token stream, BSBI builds (termID, docID) pairs and sorts them all, while SPIMI appends postings directly to a per-block hash dictionary and sorts only the terms](/static/images/information-retrieval-ch4-index-construction/spimi.svg)
   - **Key idea 1: build a separate [dictionary](glossary:dictionary) for each block** → no need to keep a term-termID mapping across blocks
   - **Key idea 2: don't sort**. Append each [token](glossary:token) to its [term](glossary:term)'s [postings list](glossary:postings-list) as it arrives
   - Together these produce one complete [inverted index](glossary:inverted-index) per block → merge them into one big index
   - In the figure: left [BSBI](glossary:bsbi) = sort all termID pairs + one [dictionary](glossary:dictionary) for all blocks / right [SPIMI](glossary:spimi) = append directly to a per-block [hash](glossary:hash-table) [dictionary](glossary:dictionary), sort only the [terms](glossary:term) when writing

3. Algorithm

   ```text
   SPIMI-Invert(token_stream)
   output_file = NewFile()
   dictionary = NewHash()
   while (free memory available)
     token = next(token_stream)
     if term(token) not in dictionary
       postings_list = AddToDictionary(dictionary, term(token))
     else
       postings_list = GetPostingsList(dictionary, term(token))
     if full(postings_list)
       postings_list = DoublePostingsList(dictionary, term(token))
     AddToPostingsList(postings_list, docID(token))
   sorted_terms = SortTerms(dictionary)
   WriteBlockToDisk(sorted_terms, dictionary, output_file)
   return output_file
   ```

   - Dictionary = a [hash](/en/blog/cs-fundamentals/information-retrieval/information-retrieval-ch3-dictionaries-tolerant-retrieval/#31-dictionaries). A new [term](glossary:term) is added to the [dictionary](glossary:dictionary); otherwise its existing [postings list](glossary:postings-list) is fetched
   - When a [postings list](glossary:postings-list) is full, double its size (DoublePostingsList)
   - Repeat while memory is left → when full, **sort only the [terms](glossary:term)** and write the block to disk
   - Why sort the [terms](glossary:term): so the blocks can be read in [term](glossary:term) order when merging
   - Merging the blocks is the same as in [BSBI](glossary:bsbi)

4. Compression
   - Compression makes [SPIMI](glossary:spimi) even more efficient: compress [terms](glossary:term), compress [postings](glossary:postings-list) → [ch5](/en/blog/cs-fundamentals/information-retrieval/information-retrieval-ch5-index-compression/#51-compression)

5. [BSBI](glossary:bsbi) vs [SPIMI](glossary:spimi)

   |              | [BSBI](glossary:bsbi)                                                            | [SPIMI](glossary:spimi)                                                              |
   | ------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
   | Dictionary   | keeps one [term](glossary:term) → termID [dictionary](glossary:dictionary) going | a new [dictionary](glossary:dictionary) ([hash](glossary:hash-table)) per block      |
   | Posting form | (termID, [docID](glossary:docid)) pairs                                          | appended directly to each [term](glossary:term)'s [postings](glossary:postings-list) |
   | Sorting      | sorts all pairs                                                                  | sorts only the [terms](glossary:term) (once, when writing)                           |
   | Block result | sorted pairs                                                                     | a complete [inverted index](glossary:inverted-index) for one block                   |
   | Merging      | merge blocks                                                                     | same as [BSBI](glossary:bsbi)                                                        |

## 4.4 Distributed indexing

**A web-scale index can't be built on one machine → how do we split the work across many failure-prone machines**

1. Why [distributed indexing](glossary:distributed-indexing) is needed
   - Web scale is impossible on one computer → we need a distributed computer [cluster](glossary:cluster)
   - Individual machines fail often: they slow down or die without warning
   - Problem: how do we make use of such an unreliable bunch of machines

2. Google data centers (2007 estimates)
   - Mostly [commodity](glossary:commodity-hardware) machines instead of expensive servers, spread around the world
   - 1 million servers, 3 million processors/cores, 100,000 machines added every quarter
   - 200–250 million dollars a year → 10% of the world's computing capacity

3. Failure calculations
   - **Probability that all 1000 machines are up** = 0.999^1000 ≈ **0.37 (37%)** → a system that stops when a single machine dies is unusable
   - **1 million servers, each failing once every 3 years** → 3 years = 3 × 365 × 24 × 60 = 1,576,800 minutes ÷ 1,000,000 = 1.6 minutes → **a machine fails in under 2 minutes**

4. The [master](glossary:master-node) and parallel tasks
   - **[master](glossary:master-node)**: the machine that directs the whole indexing job. Assumed to be "safe" (never dies)
   - Split indexing into many parallel tasks → the [master](glossary:master-node) assigns each one to an idle machine
   - Two kinds of tasks = two kinds of machines: **[parser](glossary:parser)**, **[inverter](glossary:inverter)**
   - **split**: a piece (subset of documents) of the document collection. Corresponds to a block in [BSBI](glossary:bsbi)/[SPIMI](glossary:spimi)

5. Parser and Inverter

   |          | [parser](glossary:parser)                                                                   | [inverter](glossary:inverter)                                                                                                       |
   | -------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
   | Receives | one split                                                                                   | one [term](glossary:term) range (e.g. a-f)                                                                                          |
   | Does     | reads documents one by one and emits ([term](glossary:term), [docID](glossary:docid)) pairs | collects all ([term](glossary:term), [docID](glossary:docid)) pairs (= [postings](glossary:postings-list)) for that range and sorts |
   | Result   | j files, one per [term](glossary:term) range                                                | the [postings](glossary:postings-list) lists for that range                                                                         |
   - **term-partition**: a range defined by the first letter of the [term](glossary:term). Example: a-f, g-p, q-z (j = 3)
   - **segment file**: a file a [parser](glossary:parser) writes for each range. j per [parser](glossary:parser)

6. [MapReduce](glossary:mapreduce) data flow

   ![The master assigns splits to parsers, parsers write a-f/g-p/q-z files, and each inverter collects one range to build postings](/static/images/information-retrieval-ch4-index-construction/mapreduce.svg)
   - **[map](glossary:mapreduce) = [parser](glossary:parser)**: split (group of documents) → ([term](glossary:term), [docID](glossary:docid)) pairs → segment files per first-letter range (a-f, g-p, q-z)
   - **[reduce](glossary:mapreduce) = [inverter](glossary:inverter)**: collects all segment files for one range and sorts → [postings](glossary:postings-list) lists
   - Order: splits → [map](glossary:mapreduce) phase (parsers) → segment files → [reduce](glossary:mapreduce) phase (inverters) → [postings](glossary:postings-list)
   - In the figure: grey lines = each [inverter](glossary:inverter) fetches only its own range's files from every [parser](glossary:parser)

7. [MapReduce](glossary:mapreduce)
   - The indexing method we just saw is one instance of **[MapReduce](glossary:mapreduce)**
   - **[MapReduce](glossary:mapreduce)**: a robust and simple framework for distributed computing, so you don't have to write the distribution code yourself
   - Google's indexing system (around 2002) = many phases, each implemented in [MapReduce](glossary:mapreduce). [Index construction](glossary:index-construction) is just one phase
   - Another phase, for example: converting a [term-partitioned](glossary:term-partitioned-index) index into a [document-partitioned](glossary:document-partitioned-index) index

   |                | [term-partitioned](glossary:term-partitioned-index)                                           | [document-partitioned](glossary:document-partitioned-index)            |
   | -------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
   | How it's split | by [term](glossary:term) range (a-f machine, g-p machine …)                                   | by document group (each machine has a full index of its own documents) |
   | Query handling | machines holding the query [terms](glossary:term) exchange [postings](glossary:postings-list) | send to all machines and just merge the results                        |
   - Exercise: why [document-partitioned](glossary:document-partitioned-index) can be better → even for multi-word queries, long [postings](glossary:postings-list) lists don't have to move between machines / load doesn't pile up on the machine holding popular [terms](glossary:term) / if one machine dies, only some documents are missing

8. Schema of the [map](glossary:mapreduce) and [reduce](glossary:mapreduce) functions

   |                                       | Input                                                                                   | Output                                                                                  |
   | ------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
   | [map](glossary:mapreduce)             | input                                                                                   | list(k, v)                                                                              |
   | [reduce](glossary:mapreduce)          | (k, list(v))                                                                            | output                                                                                  |
   | indexing [map](glossary:mapreduce)    | web collection                                                                          | list(termID, [docID](glossary:docid))                                                   |
   | indexing [reduce](glossary:mapreduce) | (⟨termID1, list([docID](glossary:docid))⟩, ⟨termID2, list([docID](glossary:docid))⟩, …) | ([postings](glossary:postings-list) list1, [postings](glossary:postings-list) list2, …) |
   - k = termID, v = [docID](glossary:docid). [reduce](glossary:mapreduce) receives the list of values grouped under the same key

9. [MapReduce](glossary:mapreduce) worked example
   - Input: `d1: C came, C c'ed.` / `d2: C died.`

   | Step                         | Result                                                           |
   | ---------------------------- | ---------------------------------------------------------------- |
   | [map](glossary:mapreduce)    | (C,d2) (died,d2) (C,d1) (came,d1) (C,d1) (c'ed,d1)               |
   | group                        | C → d2, d1, d1 / died → d2 / came → d1 / c'ed → d1               |
   | [reduce](glossary:mapreduce) | C → (d1:2, d2:1) / died → (d2:1) / came → (d1:1) / c'ed → (d1:1) |
   - [reduce](glossary:mapreduce) = gather docIDs for each [term](glossary:term) and **count how many times it occurs in each document**

## 4.5 Dynamic indexing

**How do we keep the index up to date when documents keep being added, deleted and modified**

1. Why it's needed
   - So far we assumed the collection is static
   - In reality documents are inserted, deleted and modified → the [dictionary](glossary:dictionary) and [postings](glossary:postings-list) lists must keep changing too

2. The simplest approach: [main + aux](glossary:auxiliary-index)
   - **main index**: the big index on disk / **[aux](glossary:auxiliary-index) (auxiliary) index**: a small in-memory index holding only new documents
   - Search: query both and merge the results
   - Periodically merge [aux](glossary:auxiliary-index) into main
   - Deletion: don't actually delete; mark a 1 in an **[invalidation bit-vector](glossary:invalidation-bit-vector)** → filter the results returned by the index with this vector

3. Problems with [main + aux](glossary:auxiliary-index)
   - Merges happen often
   - Search performance degrades during a merge

4. Cost of [main + aux](glossary:auxiliary-index)
   - Every time [aux](glossary:auxiliary-index) (size a) fills up, it's merged into main on disk → **all of main is rewritten**
   - Amount written: a + 2a + 3a + … + na = **a · n(n+1)/2 = O(n²)** → in [terms](glossary:term) of total [postings](glossary:postings-list) T, **[O(T²)](glossary:big-o-notation)** (each [posting](glossary:postings-list) is rewritten at every merge)
   - Example: a = 1, n = 4 → 1 + 2 + 3 + 4 = 10 = 4 × 5 / 2

5. Logarithmic merge = binary +1

   ![Each time Z0 fills up, the state of I3 I2 I1 I0 changes like the binary numbers 1, 10, 11, 100 ...](/static/images/information-retrieval-ch4-index-construction/log-merge.svg)
   - Spreads (amortizes) the merge cost over time → small impact on the response time users feel
   - Each size doubles: Z0 (memory, n) / I0 (n), I1 (2n), I2 (4n), I3 (8n) … (disk)
   - **When Z0 fills up to n**: if I0 is empty → store as I0 / if I0 exists → merge (2n) into I1; if I1 also exists, merge again (4n) into I2 … until an empty slot comes up
   - **State after the k-th fill = k written in binary** (from the right: I0, I1, I2 …). Example: 4th = 100 → only I2, 6th = 110 → I2, I1
   - In the figure: orange 1 = that index exists on disk, carry = merge

6. Algorithm

   ```text
   LMergeAddToken(indexes, Z0, token)
   Z0 = Merge(Z0, {token})
   if |Z0| = n
     for i = 0 to infinity
       if I_i in indexes
         Z_(i+1) = Merge(I_i, Z_i)
         indexes = indexes - {I_i}
       else
         I_i = Z_i
         indexes = indexes + {I_i}
         break
     Z0 = {}

   LogarithmicMerge()
   Z0 = {}
   indexes = {}
   while true
     LMergeAddToken(indexes, Z0, getNextToken())
   ```

   - Add [tokens](glossary:token) to Z0 one at a time; once Z0 holds n, climb up from i = 0
   - If I*i exists: merge into Z*(i+1) (a temporary index on disk) and remove I_i → go to the next i (carry)
   - If I_i doesn't exist: Z_i becomes I_i as is → stop
   - When done, empty Z0 and start receiving again

7. Cost of [logarithmic merge](glossary:logarithmic-merge)
   - Number of indexes = **O(log T)** → a query only merges O(log T) indexes
   - A [posting](glossary:postings-list) moves up one level each time it's merged → at most log T times → **[O(T log T)](glossary:big-o-notation)** overall

   |                                                        | [main + aux](glossary:auxiliary-index) | [logarithmic merge](glossary:logarithmic-merge) |
   | ------------------------------------------------------ | -------------------------------------- | ----------------------------------------------- |
   | [Index construction](glossary:index-construction) time | [O(T²)](glossary:big-o-notation)       | [O(T log T)](glossary:big-o-notation)           |
   | Indexes to merge at query time                         | 2                                      | O(log T)                                        |
   - An order of magnitude more efficient than the [aux](glossary:auxiliary-index) approach

8. What large search engines actually do
   - Usually a mix of approaches
   - Frequent incremental changes
   - Build big chunks of the index separately and swap them in whole (rotation, swap in)
   - Occasional complete rebuild. Harder the bigger the index; it's unclear whether Google can do a complete rebuild at all

9. Building [positional indexes](/en/blog/cs-fundamentals/information-retrieval/information-retrieval-ch2-term-vocabulary-postings/#24-phrase-queries)
   - Basically the same problem. The intermediate data structures are just much larger
