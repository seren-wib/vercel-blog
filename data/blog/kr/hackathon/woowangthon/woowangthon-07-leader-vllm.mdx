## 0. 들어가며

> 시리즈 7편. 구축 4단계의 남은 조각, 리더 [GPU](glossary:gpu)에 로컬 모델을 띄운 날이다. 클러스터 설치는 [6편](/kr/blog/hackathon/woowangthon/woowangthon-06-k3s-install/)에, 전체 그림은 [Woowangthon 0](/kr/blog/hackathon/woowangthon/woowangthon-00-overview/)에 있다.

리더 PC의 [GPU](glossary:gpu)가 놀고 있어서 로컬 모델을 그날 띄우기로 했다. 같은 날 팀 회의에서 배포 구조가 바뀌어, 그걸 문서로 옮기는 일부터 했다.

식당으로 비유하면 [GPU](glossary:gpu)는 주방 조리대이고, 모델 파일은 조리대에 펼쳐 둔 요리책이다. 손님 주문을 적어 두는 메모판도 조리대에 놓여야 하는데, 책이 6GB를 차지하고 나니 긴 주문 하나를 적을 메모판 자리가 모자랐다. 조리대는 [GPU](glossary:gpu), 요리책은 모델 파일, 메모판은 [KV cache](glossary:kv-cache), 긴 주문은 [16K](glossary:context-window) [Token](glossary:token) 요청이다.

RTX 3080(10GB)에 [Qwen3-8B-AWQ](glossary:qwen)를 [vLLM](glossary:vllm)으로 띄웠다. [16K](glossary:context-window) 요청 하나가 안 들어가 시작하자마자 멈췄고, [KV cache](glossary:kv-cache)를 [FP8](glossary:fp8)로 바꿔서 들어갔다.

## 1. 회의에서 바뀐 것

새벽에 디스코드로 팀 회의를 했다. 클러스터 쪽에 걸리는 결정이 다섯 개 나왔다.

| 결정                                                                                                                 | 클러스터 쪽에서 바뀌는 것                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 배포(매니페스트 만들기 · 적용 · 동작 확인)는 리더의 [GoCD](glossary:gocd) 실행기가 한다                              | 플랫폼 서버는 클러스터에 배포를 직접 쓰지 않는다. 실행기 계정이 따로 생긴다                                                                 |
| 접수부터 빌드 요청까지와 보안 검사는 플랫폼 서버([Nest](glossary:nestjs))가 한다                                     | 클러스터와는 상관없지만, AI 서버를 따로 둔 이유 하나가 뒤집힌다                                                                             |
| 학생 [Secret](glossary:kubernetes-secret)(.env)은 플랫폼 서버가 [Tailscale](glossary:tailscale)로 리더에 직접 넣는다 | [Secret](glossary:kubernetes-secret)은 배포 파이프라인과 빌드를 안 거친다. 서버 계정에는 [Secret](glossary:kubernetes-secret) 쓰기가 남는다 |
| 로그는 스파이크 순간에 잘라 둔 스냅샷만 남긴다                                                                       | 클러스터에 로그 수집기를 두지 않는다                                                                                                        |
| [Message queue](glossary:message-queue)([Kafka](glossary:apache-kafka))와 로컬 모델 설치는 후순위                    | 로컬 모델은 데모 경로 밖이다. 그래도 [GPU](glossary:gpu)가 놀고 있어서 나는 그날 띄우기로 했다(2~7절)                                       |

6편 무렵 배포 흐름 그림을 일부러 그대로 둔 이유가 "[ADR](glossary:adr)이 아직 없어서"였다. 이제 결정이 났으니 레포 규칙대로 [ADR](glossary:adr)부터 썼다.

- **[ADR-009](glossary:adr)**: 배포는 리더의 [GoCD](glossary:gocd) 실행기가 하고, [GoCD](glossary:gocd) 서버는 플랫폼 서버와 같은 [AWS EC2](glossary:amazon-ec2)에 둔다. 예전 [ADR-004](glossary:adr)(서버가 리더의 [Kubernetes](glossary:kubernetes) API를 직접 불러 배포한다)에서 "배포" 항목만 대체한다. [Secret](glossary:kubernetes-secret) 쓰기, 재시작 같은 조치, 상태 조회는 여전히 서버가 직접 한다.
- **[ADR-010](glossary:adr)**: 접수부터 빌드 요청까지와 보안 검사는 플랫폼 서버가 한다. 첫 [ADR](glossary:adr)은 AI 서버를 따로 둔 이유로 "학생 코드를 읽는 부분을 백엔드와 분리하고 싶다"를 들었는데, 이 결정이 그걸 되돌린다. 그래서 대가를 [ADR](glossary:adr)에 같이 적었다. 레포는 임시 폴더에 읽기 전용으로 받고 끝나면 지우며, 실행하지 않는다.

시스템 정의서, AI 범위 문서, 다이어그램 다섯 장도 같이 고쳤다. 클러스터 설계 문서에서는 권한 절을 다시 썼다. 지금까지는 플랫폼 서버 계정 하나에 배포 권한까지 다 줬는데, 이제 계정이 둘이다.

| 계정        | 받는 것                                                                                                                 | 못 하는 것                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 플랫폼 서버 | 학생 공간 만들기 · 지우기, 공간 상한과 차단 규칙 만들기, [Secret](glossary:kubernetes-secret) 쓰기, 재시작 · 중지, 읽기 | 배포 자원 만들기, [Secret](glossary:kubernetes-secret) 읽기                 |
| 배포 실행기 | 학생 공간 안의 배포 자원 만들기 · 고치기 · 지우기, 동작 확인용 읽기                                                     | 공간 · 상한 · 차단 규칙 건드리기, [Secret](glossary:kubernetes-secret) 읽기 |

실행기는 배포 전에 [Secret](glossary:kubernetes-secret)이 들어갔는지 확인해야 한다. 그런데 [Kubernetes](glossary:kubernetes)에서 [Secret](glossary:kubernetes-secret)을 "있는지만" 볼 수 있는 권한은 없다. 읽기를 주면 값까지 보인다. 그래서 실행기는 [Secret](glossary:kubernetes-secret)을 읽지 않고, 플랫폼 서버가 넣으면서 남긴 키 이름 목록으로 확인하게 했다.

## 2. GPU를 쿠버네티스에 보이게

리더에는 [GPU](glossary:gpu)를 컨테이너에 붙여 주는 도구가 [k3s 설치 때 이미 잡혀 있었다](/kr/blog/hackathon/woowangthon/woowangthon-06-k3s-install/#1-설치-전에-정한-것). 남은 건 [Kubernetes](glossary:kubernetes)가 "이 노드에 [GPU](glossary:gpu)가 하나 있다"를 아는 것이다. 그걸 알려 주는 게 [NVIDIA device plugin](glossary:nvidia-device-plugin)이다. 노드마다 하나씩 뜨는 프로그램인데, 리더에만 뜨게 고쳤다.

```yaml
spec:
  runtimeClassName: nvidia
  nodeSelector:
    kubernetes.io/hostname: k3s-leader
  tolerations:
    - key: node-role.kubernetes.io/control-plane
      operator: Exists
      effect: NoSchedule
```

`runtimeClassName: nvidia`가 빠지면 플러그인이 [GPU](glossary:gpu)를 못 본다. 붙이고 나니 리더의 할당 가능 자원에 `nvidia.com/gpu: 1`이 생겼다. [GPU](glossary:gpu) 한 장을 달라는 시험 Pod를 띄웠더니 리더에 떠서 RTX 3080, 10240MiB를 찍고 끝났다.

## 3. 모델 받기

모델은 [Hugging Face](glossary:hugging-face)에서 받는다. 받기 전에 학교망 속도부터 쟀다. 모델 파일 앞부분 300MB를 받아 보니 초당 약 47MB였다.

모델은 리더 디스크의 [PersistentVolume](glossary:persistentvolume)(30Gi)에 한 번만 받아 두고, [vLLM](glossary:vllm)은 그 폴더를 오프라인으로 읽게 했다. [vLLM](glossary:vllm)이 다시 뜰 때마다 인터넷에서 받지 않는다. 받을 때는 모델 저장소의 커밋을 고정했다. 같은 이름이라도 나중에 내용이 바뀔 수 있다. 6.1GB를 69초에 받았다.

## 4. 10GB에 16K가 안 들어갔다

[vLLM](glossary:vllm) 설정은 AI 담당(suda5936)의 설계에서 왔다. 한 번에 읽는 길이([Context window](glossary:context-window))는 [16K](glossary:context-window) [Token](glossary:token)이다. 띄웠더니 바로 죽었다.

![fp16 KV 캐시로 띄웠을 때 vLLM 로그. 모델을 올리는 데 5.71GiB, 남은 KV 캐시 자리 1.66GiB, 16384 길이 요청 하나에 2.25GiB가 필요하다는 오류](/static/images/woowangthon-07-leader-vllm/kv-fp16.svg)

_[fp16](glossary:fp16) [KV cache](glossary:kv-cache): 남은 자리 1.66GiB, [16K](glossary:context-window) 한 요청에 필요한 건 2.25GiB_

언어 모델은 글을 한 [Token](glossary:token)씩 만들면서, 앞에서 읽은 [Token](glossary:token)마다 계산해 둔 값을 메모리에 쌓아 둔다. 이게 [KV cache](glossary:kv-cache)다. [Qwen3-8B](glossary:qwen)는 [Token](glossary:token) 하나에 약 144KiB를 쓴다. [16K](glossary:context-window) [Token](glossary:token)이면 2.25GiB다. [vLLM](glossary:vllm)은 시작할 때 "최대 길이 요청 하나는 담을 수 있는지"를 먼저 따지고, 안 되면 아예 안 뜬다.

미리 계산해 둔 숫자로는 들어가야 했다. [GPU](glossary:gpu) 메모리의 90%(약 9GiB)를 쓰게 두고 가중치 5.7GiB를 빼면 3GiB쯤 남는다고 봤다. 실제로 남은 건 1.66GiB였다. [CUDA](glossary:cuda) 기본 메모리, 계산 중에 잠깐 쓰는 메모리, 미리 녹화해 두는 [CUDA graph](glossary:cuda-graph)가 합쳐서 1.6GiB쯤을 더 먹는데, 어림할 때 그걸 빼먹었다.

고를 수 있는 길이 셋이었다.

| 방법                                                           | 결과                                                                                                    |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| [GPU](glossary:gpu) 사용률을 0.95까지 올리기                   | 0.5GiB쯤 늘어도 2.2GiB 안팎이라 모자란다. 남는 여유도 없어진다                                          |
| [Context window](glossary:context-window)를 12K로 줄이기       | 들어가긴 하지만, [16K](glossary:context-window)는 AI 쪽 설계값이라 내가 혼자 바꿀 값이 아니다           |
| [KV cache](glossary:kv-cache)를 [FP8](glossary:fp8)로 저장하기 | [Token](glossary:token)당 약 72KiB로 반이 된다. 같은 1.67GiB에 24,352[Token](glossary:token)이 들어간다 |

[FP8](glossary:fp8)로 갔다. 숫자를 8비트로 줄여 저장하니 정확도가 조금 떨어질 수 있다. 그래서 시험에서 [Tool calling](glossary:tool-calling)과 긴 로그 요약이 제대로 나오는지를 같이 봤다(7절).

![KV 캐시를 FP8로 바꾼 뒤 vLLM 로그. KV 캐시 24,352토큰, 16,384 토큰 요청 기준 동시 1.49개, 시작 완료](/static/images/woowangthon-07-leader-vllm/kv-fp8.svg)

_[FP8](glossary:fp8) [KV cache](glossary:kv-cache): 24,352[Token](glossary:token), [16K](glossary:context-window) 요청 하나가 넉넉히 들어간다_

## 5. Service 이름이 vllm이면 vLLM이 안 뜬다

[FP8](glossary:fp8)로 바꿨더니 이번에는 다른 오류로 죽었다. `VLLM_PORT`라는 설정값이 `tcp://...:8000` 같은 주소로 들어와 있다는 것이다. 나는 그런 값을 넣은 적이 없다.

범인은 [Kubernetes](glossary:kubernetes)였다. [Kubernetes](glossary:kubernetes)는 같은 공간의 [Service](glossary:service)마다 `<이름>_PORT` 같은 [Environment variable](glossary:environment-variable)을 Pod에 자동으로 넣어 준다. 오래된 서비스 찾기 방식이다. [vLLM](glossary:vllm) 앞에 붙인 [Service](glossary:service) 이름이 `vllm`이라 `VLLM_PORT`가 생겼고, [vLLM](glossary:vllm)은 그걸 자기 설정으로 읽었다. Pod 설정에 `enableServiceLinks: false`를 넣어 자동 [Environment variable](glossary:environment-variable)을 껐다. 요즘은 이름으로 찾는 [DNS](glossary:dns)가 있어서 이 기능이 필요 없다.

## 6. 동시 요청 3은 어디서 나왔나

계획에는 "[Concurrency](glossary:concurrency) 3"이 적혀 있었다. 띄우고 나서 이 3이 어디서 나온 숫자인지 거슬러 올라가 봤다.

근거가 약했다. 11월 6일에 AI 담당에게 [Concurrency](glossary:concurrency)를 몇으로 할지 물었는데 답이 없었다. 그래서 에이전트가 "학생 슬롯 2개 + 분석 호출 1개"로 3을 잡아 두었다. AI 담당의 설계 문서([woowangthon/WOOWANGTHON_TEAM_18#32](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/32))에는 그런 숫자가 없다. 설계 문서는 한 배포 작업에 열린 문제 티켓이 하나라고만 한다.

정해진 값이 없으니 1로 바꿨다. 넘치는 요청은 실패하지 않고 줄을 서서 기다린다. [Concurrency](glossary:concurrency) 수를 줄여도 [FP8](glossary:fp8)은 그대로 필요하다. 시작할 때 따지는 건 "[16K](glossary:context-window) 요청 하나"라서다.

## 7. 확인

시험은 클러스터 안, [vLLM](glossary:vllm)과 같은 공간에 시험 Pod를 띄워서 했다. [API key](glossary:api-key)는 [Secret](glossary:kubernetes-secret)에서 바로 받아 써서 화면에 한 번도 안 찍혔다.

![클러스터 안 시험 Pod 결과. 키 없음과 틀린 키는 401, 요청 하나 0.38초, 도구 호출 29토큰, 셋을 한꺼번에 보내면 차례로 처리](/static/images/woowangthon-07-leader-vllm/vllm-test.svg)

_시험 Pod 결과. 넷째 줄은 300[Token](glossary:token) 요청 셋을 한꺼번에 보낸 것이다_

| 확인                                                    | 결과                                                                                              |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 키 없음 · 틀린 키                                       | [401](glossary:http-status-code)로 거부                                                           |
| 요청 하나                                               | 0.4초                                                                                             |
| 생각 모드를 끈 [Tool calling](glossary:tool-calling)    | 29[Token](glossary:token) 만에 `get_logs(proj-demo, 50)`을 정확히 부름                            |
| 300[Token](glossary:token) 요청 셋을 한꺼번에           | 2.6초, 5.2초, 7.8초에 차례로 끝남(동시 1)                                                         |
| 15.1K [Token](glossary:token)짜리 로그 요약             | 2.4초, 원인([OOMKilled](glossary:oom))을 맞게 짚음                                                |
| 16,385[Token](glossary:token)                           | [400](glossary:http-status-code)으로 거부(한도 16,384)                                            |
| [GPU](glossary:gpu) 메모리                              | 10GB 중 8.3~8.6GB                                                                                 |
| 시험 중 [Kubernetes](glossary:kubernetes) API 서버 응답 | 최대 91ms(평소 71ms). [Kubernetes control plane](glossary:kubernetes-control-plane)은 안 느려졌다 |
| [vLLM](glossary:vllm) 시작                              | 약 52초                                                                                           |

[vLLM](glossary:vllm)은 학생 앱보다 [Pod priority](glossary:pod-priority)를 낮게 뒀고(자리가 모자라면 먼저 밀려나고, 남을 밀어내지 않는다), CPU와 메모리 상한을 걸었다. 들어오는 통신은 같은 공간에서만 받는다. 바깥(AWS의 AI 서버)에서 부르는 길은 서버 연결 단계에서 연다. 공개 주소에는 절대 안 붙인다. 붙이면 인터넷의 아무나 [GPU](glossary:gpu)를 쓴다.

## 9. 느낀 점

구축 4단계가 끝났고, 남은 건 동아리방에서 전원을 통째로 뽑는 시험 하나다.
