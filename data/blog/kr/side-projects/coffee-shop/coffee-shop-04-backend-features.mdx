## 2. 주문 상태 전환

주문은 상태 일곱 개를 오간다. 기차표로 치면 발권, 탑승, 하차처럼 순서가 정해져 있어서 "이미 하차한 표를 취소"하는 요청은 역무원 선에서 거절된다.

![주문 상태 전환 다이어그램. PENDING에서 결제 성공이면 PAID, 회원 취소면 CANCELLED. PAID에서 관리자 준비면 PREPARING. PAID와 PREPARING에서 회원이 취소 요청하면 CANCEL_REQUESTED, 요청 전 상태를 status_before_cancel에 저장. CANCEL_REQUESTED에서 관리자 승인이면 PG 취소 뒤 CANCELLED, 반려면 요청 전 상태로. PREPARING에서 발송이면 SHIPPED, SHIPPED에서 배송 완료면 DELIVERED. 표에 없는 전환은 409 INVALID_STATE](/static/images/coffee-shop-04-backend-features/order-states.svg)

역무원이 하는 일이 조건부 UPDATE다. 이 비유는 여기까지만 쓴다.

```python:backend/orders/services.py
# 결제 대기 주문을 회원이 바로 취소할 때
updated = Order.objects.filter(
    pk=order.pk, order_status=OrderStatus.PENDING
).update(order_status=OrderStatus.CANCELLED)
if updated == 0:
    order.refresh_from_db()
    raise invalid_state(order.order_status, "취소할")
```

읽고 → 확인하고 → 쓰는 세 단계로 짜면 두 요청이 동시에 "확인"을 통과할 수 있다. 조건을 `WHERE`에 넣으면 확인과 쓰기가 한 문장이라 그 틈이 없다. 0행이면 다른 누가 먼저 바꾼 것이니 409로 돌려준다. 관리자 주문의 모든 전환은 헬퍼 하나를 거치고, `test_dr19_disallowed_transitions_raise_invalid_state`가 허용 표 밖의 (동작, 상태) 쌍을 전부 돌며 `INVALID_STATE`(API에선 409)인지 본다(#104).

취소 반려는 `status_before_cancel`을 `F()` 식으로 되돌린다. 이 칼럼이 비어 있는 `CANCEL_REQUESTED` 행은 CHECK 제약 `ck_orders_cancel_request_previous`가 아예 못 만들게 막는다. 리뷰에서 "요청 전 상태가 없는 취소 요청을 반려하면 500"이 나와서 붙인 제약이다.

## 3. 주문 생성: 장바구니 전체, 전부 아니면 전무

주문은 장바구니 전체로 만든다(#100). 한 트랜잭션 안에서 이렇게 간다.

1. IMMEDIATE 쓰기 잠금 아래에서 장바구니를 읽는다
2. 항목마다 판매 상태와 재고를 확인하고, 문제가 있는 `cart_item_ids`를 **전부** 모아 409(`NOT_AVAILABLE` 또는 `OUT_OF_STOCK`)로 돌려준다
3. 주문 번호 `ORD-YYYYMMDD-NNN`(서울 날짜 기준 일련번호)을 매긴다
4. 항목마다 `products.services.decrease_stock`으로 재고를 뺀다. 하나라도 실패하면 전체 롤백
5. 상품 이름과 가격을 주문 항목에 복사해 둔다(나중에 가격이 바뀌어도 주문은 그대로)

문제 항목을 하나씩이 아니라 전부 돌려주는 이유는 화면 때문이다. 하나만 알려 주면 손님이 고치고 다시 누를 때마다 다음 문제를 하나씩 만난다.

동시 주문은 3편의 스파이크 기대값을 그대로 테스트로 박았다. `test_nfr15_last_stock_concurrent_orders`가 파일 SQLite에서 스레드 10개로 돌고, 로컬 3회 모두 201 1건, 409 9건, 재고 0, 주문 1행이었다.

#100 리뷰(high)에서 8건이 나와 전부 고쳤다. 몇 개만 적으면 이렇다.

- 주문 번호 충돌만 409 `RETRY`로 바꾸고, 다른 제약 위반은 500으로 남긴다(전부 `RETRY`로 뭉개면 버그가 숨는다)
- 취소 409 메시지에 들어가는 상태를 다시 읽은 값으로 쓴다
- 배송지보다 장바구니를 먼저 확인한다

## 4. 결제: 먼저 재고, 그다음 코드

[결제창](/kr/blog/dev/payments/payments-00-basics/#결제창)은 브라우저가 열고, [결제 승인](/kr/blog/dev/payments/payments-00-basics/#결제-승인)은 서버가 토스 API로 한다. 승인 응답이 어떤 모양인지, 두 번 취소하면 어떤 오류가 오는지 모르고 짜면 추측으로 짜게 된다. 그래서 결제 코드 전에 스파이크를 돌렸다.

![결제 흐름 다이어그램. 브라우저가 POST /api/orders/id/payments/로 결제를 시작하면 서버가 READY 결제 행을 만든다. 브라우저가 토스 결제창을 열고 성공하면 successUrl로 paymentKey, orderId, amount를 받는다. 브라우저가 POST /api/payments/confirm/을 보내면 서버가 금액을 시작 금액과 비교하고, 같을 때만 트랜잭션 밖에서 토스 confirm API를 부른다. status가 DONE이면 결제 SUCCESS, 주문 PAID. 금액이 다르면 PG를 부르지 않고 CANCELLED, 409 PAYMENT_MISMATCH](/static/images/coffee-shop-04-backend-features/payment-flow.svg)

### 토스 스파이크 결과

테스트 결제 두 건(A, B, 각 1,000원)으로 쟀다. 원본 호출 9건은 `paymentKey`를 가려 `spikes/toss-confirm-cancel/results/calls.jsonl`에 있다(#92, #105).

| 단계 | 확인                                | 결과                                                                        |
| ---- | ----------------------------------- | --------------------------------------------------------------------------- |
| 2    | 승인                                | 200 `DONE`, `method: "간편결제"`, `approvedAt`에 +09:00(1,313 ms / 551 ms)  |
| 3    | 전액 취소, 다른 키로 두 번째 취소   | 200 `CANCELED`(585 ms), 두 번째는 400 `ALREADY_CANCELED_PAYMENT`(215 ms)    |
| 4    | 결제창과 다른 금액으로 승인         | 403 `FORBIDDEN_REQUEST`(211 ms). 결제는 남아 있어 맞는 금액으로 다시 승인됨 |
| 5    | 결제창을 X로 닫기                   | `failUrl`로 안 가고 `requestPayment()`가 `USER_CANCEL`로 실패(2회 모두)     |
| 6    | 10분 지난 결제 승인                 | 안 쟀다                                                                     |
| 7    | 같은 `Idempotency-Key`로 취소 두 번 | 둘 다 200, 같은 본문(616 ms / 89 ms). 취소는 1건                            |

설계가 바뀐 곳은 4단계다. 원래 설계는 "승인한 뒤 금액이 다르면 PG에서 취소"였다. 그런데 토스가 다른 금액의 승인 자체를 403으로 거절하니 그 경로에는 닿지 않는다. 그래서 확인 요청 금액이 결제 시작 때 금액과 다르면 **PG를 부르지 않고** 결제를 `CANCELLED`("결제 금액 불일치")로 닫고 409 `PAYMENT_MISMATCH`를 돌려주게 바꿨다(#105). 승인 뒤 취소 경로는 PG가 다른 `totalAmount`를 보고하는 경우를 위한 방어로 남겼다.

7단계는 관리자 취소 승인의 순서를 정했다. 같은 [멱등](/kr/blog/dev/payments/payments-00-basics/#멱등) 키(`cancel-<payment_id>`)로 다시 보내면 첫 결과가 그대로 오니, **PG 취소를 먼저 하고 DB를 나중에** 바꿔도 중간에 끊긴 요청을 안전하게 다시 보낼 수 있다. 5단계는 화면 쪽 규칙이 됐다. `failUrl`만 보면 창 닫기를 놓치니 `requestPayment()`의 오류를 직접 받아야 한다(5편).

6단계는 재지 않았다. 문서에는 "공개 문서 기준 10분 지나면 승인 실패" 가정으로 미결에 남겼다.

### 결제 코드의 규칙(#102)

- 토스를 부르는 코드는 `orders/pg.py`의 `TossPaymentsClient` 하나뿐이다. 테스트는 `FakePaymentsClient`를 쓴다.
- PG 호출은 DB 트랜잭션 밖에서 한다. 외부 호출이 10초(타임아웃)까지 걸릴 수 있는데 그동안 SQLite 쓰기 잠금을 잡고 있으면 다른 주문이 전부 멈춘다.
- 토스 `status == "DONE"`만 승인으로 본다. 타임아웃, 5xx, JSON이 아닌 응답, 끊긴 연결은 결제를 `READY`로 두고 502 `PG_ERROR`를 돌려준다.

#102 리뷰(high)에서 8건이 나왔고, 고칠 때마다 옛 코드에서 실패하는 회귀 테스트를 먼저 붙였다. 제일 무거운 건 이것이었다. 승인 중인 결제를 새 결제 시도가 대체하면, 성공 결제가 하나도 없는데 주문이 `PAID`가 될 수 있었다.

## 5. 상품 쪽과 시연 데이터

- **목록(#91):** 한 쪽 20개, 최신순, `STOPPED` 숨김, 검색·원산지·가격대·로스팅 필터를 AND로 묶는다. 목록과 상세가 같은 쿼리 함수 `customer_products()`를 써서 "중지 상품 숨김" 규칙이 둘 사이에서 갈라지지 않는다. 옵션 3개짜리 상세 응답은 쿼리 2번이다.
- **관리자 상품(#95):** 상태 변경은 `products.services`로만 한다. 원산지는 고정 목록 10개, 이미지 URL은 `https://`로 시작해야 한다.
- **`seed_demo`(#99):** 기본값으로 원두 100개, 회원 50명, 주문 500건을 고정 시드로 만든다. 주문은 상태 7개에 고르게 나눠 71~72건씩, 원두는 판매 95·중지 5였다. 파일 SQLite에서 1.71초(1회 측정). 데이터가 이미 있는 DB는 거부하고, `DEBUG=False`면 `--force`가 있어야 돈다.
