## 0. Introduction

`blog-post` is the [skill](/en/blog/side-projects/devblog/devblog-04-agent-environment/#3-pulling-out-what-is-needed) an AI agent opens when it writes or edits a post on this blog (kibotos.dev). Whether it is moving a lecture note, writing a project series or translating into English, it reads these rules first. The post you are reading was written by this skill too.

The skill is a single `SKILL.md` file with 7 sections. Its size and commit count are collected in the [By the numbers](#by-the-numbers) table at the end. This post walks through when the skill is read, where its rules came from, and what each rule asks of a post.

## 1. When the skill is read

Think of a style guide on a bookshelf. Most of the time you only see the title on its spine, and you take it down and open it only when you write.

![The order in which the blog-post skill is read: skill listing, Skill tool, SKILL.md body, publish_pipeline.md](/static/images/skills-01-blog-post/skill-loading.svg)

_The order in which the blog-post skill is read: skill listing → Skill tool → SKILL.md body → publish_pipeline.md_

In real terms, the spine is the frontmatter **description**, and taking the book down is a **Skill tool** call.

Claude Code puts a list of skills into the prompt every session. Each skill contributes only its `name` and its one-line `description`. The `blog-post` description lists its triggers as "uploading a note to the blog, writing or editing a post (KR or EN), preparing photos". When a task matches, the agent calls the skill through the Skill tool, and only then does the body enter the context. In a session that does no blog work, the 4.7 KB body is never read.

The repo has its own [publish pipeline](https://github.com/seren-wib/vercel-blog/blob/main/docs/agent/publish_pipeline.md) document. The two have different jobs.

| Document                         | Where                          | Covers                                                                        |
| -------------------------------- | ------------------------------ | ----------------------------------------------------------------------------- |
| `docs/agent/publish_pipeline.md` | Blog repo (public)             | Importing, file names, frontmatter, image paths, build, PR                    |
| `blog-post/SKILL.md`             | Personal config repo (private) | Voice, post structure, summary length, cross-links, masking people and photos |

The repo's `CLAUDE.md` pulls in the pipeline with `@docs/agent/publish_pipeline.md`, so it is always read when working in this repo. The skill's first line says "these rules sit on top of it". The pipeline sets the procedure, and the skill decides how to write on top of it. They clash in exactly one place today, the summary rule, and the skill says it wins ([section 5](#5-summary-and-heading-length)).

## 3. One voice

Think of an article, not an interview transcript. Nobody's lines are taken down word for word; one person sorts it out and writes it.

In real terms, the rule fixes the post to one **point of view**.

- The point of view is one of two: mine ("I decided to ~, because ~") or the agent's ("Claude Code proposed ~").
- The prompts I typed to the agent are never quoted, and the post never stages a back-and-forth like "I asked / the agent answered".
- Quoting documents, error messages, command output and teammates' chat is fine.

When this rule was added on 2026-11-10, every post already written that way was set to be fixed. In memory, the agent recorded its own reading of why: "quoted prompts read like a chat log, not a write-up".

The same section holds a series rule. A series has to be readable by someone who has never seen it, so the 00 post explains what, why and how, and every later post links back to 00 in its first line. The quote line at the top of this post is that link.

## 4. Writing in two layers

Think of a map that prints neighborhood names in large type and road numbers in small type. A first-time visitor reads only the names; someone who knows the area reads the numbers too.

![The structure of one section: analogy, SVG diagram, mapping line, real behavior, with a numbers table and glossary at the end of the post](/static/images/skills-01-blog-post/two-layers.svg)

_The structure of one section: ① analogy → ② SVG diagram → ③ mapping line → ④ real behavior_

In real terms, one text serves a **newcomer layer** and a **CS reader layer** at once. There is no separate easy version.

Commit `5c3b37a3` added this section on 2026-11-25. Each section follows a fixed order.

1. An analogy in one or two sentences
2. An SVG diagram, with the real terms as the main labels and the analogy words small beside them
3. One line stating which term the analogy pointed to, then terms only from there on
4. The real behavior: paths, commands, numbers, and why it was designed that way

Diagrams are files, not SVG code inlined into the post. They live at the same path as photos, `public/static/images/<slug>/<content>.svg`. The same masking rules apply, so labels must not contain real hostnames, IPs or account names.

Numbers that change (counts, sizes, versions) are not scattered through the text but gathered in one table stamped with its date. The prose points to that table. When a number changes, only the table needs fixing. Each post ends with a glossary table.

The skill commit has no body explaining why this rule came in; the direct trigger is not recorded. Earlier that month, on 2026-11-19, the agent instructions gained a rule that "an explanation may start with an analogy but must end in proper terms and real behavior", and this section has the same shape, applied to post structure.

## 5. Summary and heading length

Think of a book's belly band and its table of contents. Print the whole table of contents on the band and nobody reads it.

In real terms, these are length limits on the frontmatter **`summary`** (the list card subtitle and the meta/OG description) and on each **heading** (one line in the post's table of contents).

Commit `d6cb1c8a` added the rule on 2026-11-27.

| Field     | KR             | EN              | Reason                                            |
| --------- | -------------- | --------------- | ------------------------------------------------- |
| `summary` | about 80 chars | about 160 chars | Roughly where search result snippets get cut      |
| heading   | about 20 chars | about 40 chars  | Fits on one line in the desktop TOC and on mobile |

Listing terms in parentheses and chaining several topics with `·` are banned too. Those terms go to the section's first paragraph and the glossary.

The trigger was the summary of the [SSH overlay post](/en/blog/cs-fundamentals/network/network-ssh-overlay/). Its KR summary was 780 characters, one sentence strung together with term lists in parentheses and `·` chains. The skill's Bad example is a sentence cut from that summary. On the day the rule was added, 84 of 99 KR posts were over 80 characters.

The pipeline document still has the old line "list the core keywords of the body, separated by commas" for summary. The skill states that it overrides that line, and whether to fix the pipeline document and the existing posts has not been decided yet. The current figures are in [By the numbers](#by-the-numbers).

## 6. Cross-links

Think of replacing a footnote that says "details on page N" with a word you can click to jump straight to that page.

![How a cross-link is made: this post, origin/main posts, github-slugger, a link on the term itself](/static/images/skills-01-blog-post/cross-links.svg)

_How a cross-link is made: term → search posts on origin/main → github-slugger anchor_

In real terms, it is an **inline link** to the **anchor** of another post's heading.

- It happens only at the upload step. While writing lecture notes (`chN.md`), nobody hunts for links unless asked.
- Find a section in another post that covers the same thing in more depth, and put the link on the term itself. No separate "see: …" line.
- Compute the anchor with the repo's `github-slugger` and check it against the real heading. For example, `4.1.2 도메인 요구사항` becomes `#412-도메인-요구사항`.
- Read posts from `origin/main`. Pull first, so a post merged a moment ago counts as a candidate.
- The English copy links to `/en/blog/...` with the English post's anchors. English headings are worded differently, so their anchors differ too.

The "skill" link in section 0 of this post is an example. Section 3 of the agent environment post covers what a skill is in more depth, so the term links there.

## 7. People and photos

Think of a newspaper photo desk. The names of the people in the shot come out, and the name tag on the back wall gets pixelated.

In real terms, this is the **masking** rule for personal information in public posts.

- People appear as GitHub IDs only. I am "I" or seren-wib. No real names anywhere in the text or captions.
- Photos are cropped tight to the subject. Desks, walls, whiteboards and floors go.
- School asset stickers and barcodes, handwritten hostnames, IPs, MACs, account names, tailnet names and login URLs are masked. For terminals, a masked code block beats a photo.
- Personal photos showing people's faces never go in.
- The conversion is HEIC → PNG (ffmpeg) → pixelate and crop → `libwebp -quality 82`, at most 1600 px wide, saved to `public/static/images/<slug>/`. Each output is opened and zoomed into wherever something looks suspicious.

This rule came from posting the [Woowangthon series](/en/blog/hackathon/woowangthon/woowangthon-00-overview/) on 2026-11-05. The leader PC had a school asset label on it, and photos that included the background looked messy.

## 8. AI notes and mentions

Think of erasing the working notes in a manuscript's margins before it goes to print.

In real terms, these are **removing authorship tag lines** and the **PR mention rule for a public repo**.

AI-written UNIV lecture notes can be published and translated. The `AI 생성 문서.` ("AI-generated document.") and `AI 생성 부분 있음.` ("contains AI-generated parts.") lines left in older notes only marked authorship inside the UNIV folder, so they are removed from the blog copy. The blog marks this with `aiGenerated: true` in the frontmatter instead. This post has it too.

This blog repo is public. So PR bodies and commit messages never write another repo's PR as `owner/repo#N` or as a URL. If they did, GitHub would leave a mention on that repo's PR timeline. Repo names are written as plain text only. The full commit and PR rules are in the [pr-workflow post](/en/blog/side-projects/skills/skills-05-pr-workflow/).

## 9. Wrap-up

`blog-post` was not designed in one go. Four problems that came up while posting piled up in memory, were gathered into one skill, and then two-layer writing and length limits were added. Every rule has a post that prompted it. The next rule will probably appear the same way.
