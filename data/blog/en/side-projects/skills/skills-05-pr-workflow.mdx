## 0. Introduction

> Part 5 of the series. What a [skill](glossary:agent-skill) is and why these rules moved out of the instruction file is in [CH0. Skills overview](/en/blog/side-projects/skills/skills-00-overview/).

`pr-workflow` is the [skill](glossary:agent-skill) an AI coding [agent](glossary:ai-coding-agent) opens right before it creates an [issue](glossary:issue), cuts a [branch](glossary:branch), makes a [commit](glossary:commit) or [PR](glossary:pull-request), merges, or cleans up [branches](glossary:branch). Its rules were scattered across six global memory files. The [commit](glossary:commit) message gives one reason for the move: rules needed for only one kind of task should not sit in global memory all the time, but live in a [skill](glossary:agent-skill) that opens only when that task comes up.

In restaurant terms, you pin the order ticket first, cook at your own station, get the plate inspected before it goes to the floor, send plates to the pass one at a time, and clear the station when service ends. The recipe book that writes this order down is the [skill](glossary:agent-skill), one plate is one [PR](glossary:pull-request), and each cooking step inside it is one [commit](glossary:commit). The order ticket is the [issue](glossary:issue), the station is the [branch](glossary:branch), the inspection is [CI](glossary:ci), the pass is the [release branch](glossary:release-branch), and clearing the station is the [branch](glossary:branch) update.

On 2026-11-13 I gathered the six memory rules into one [skill](glossary:agent-skill). This post goes through the rules in it (order of work, one [PR](glossary:pull-request) at a time, splitting [commits](glossary:commit), rule docs first, [branch](glossary:branch) update, sorting bot reviews), where each came from, and how the [skill](glossary:agent-skill) changed afterwards.

## 1. Order of work

![Order of work: GitHub issue, branch, PR, merge after CI, branch update. A trivial change skips the issue](/static/images/skills-05-pr-workflow/order-of-work.svg)

_Order of work: [issue](glossary:issue) → [branch](glossary:branch) → [PR](glossary:pull-request) → merge → [branch](glossary:branch) update. Only trivial changes skip the issue_

1. Create a GitHub [issue](glossary:issue) in the main repo.
2. [Branch](glossary:branch) from [upstream](glossary:upstream) `main`: in my [fork](glossary:fork) for someone else's repo, inside the repo for my own.
3. Link the [issue](glossary:issue) in the [PR](glossary:pull-request) body. `Fixes #N` when this [PR](glossary:pull-request) finishes the [issue](glossary:issue) (merging closes it automatically), `Part of #N` when one [issue](glossary:issue) is handled by several PRs.
4. Right after the merge, run a [branch](glossary:branch) update so local `main` matches the [remote](glossary:remote). If the work was in a [worktree](glossary:git-worktree), update the main checkout too. Follow-ups (a docs mirror and so on) come after that.

**One task per [PR](glossary:pull-request).** Unrelated tasks never get folded into one [PR](glossary:pull-request).

This order was born on 2026-10-31 in the team repo of a hackathon (Woowangthon). The [agent](glossary:ai-coding-agent) opened a one-line README link [PR](glossary:pull-request) with no [issue](glossary:issue), and I said the [issue](glossary:issue) comes first. Then we looked at the usual practice together. [Issues](glossary:issue) track work that needs discussion or visibility; a one-line change is its own record in the [PR](glossary:pull-request). So one exception was added.

| Trivial ([PR](glossary:pull-request) without an [issue](glossary:issue)) | Not trivial ([issue](glossary:issue) first) |
| ------------------------------------------------------------------------ | ------------------------------------------- |
| A typo, a single link                                                    | Anything that needs a decision              |
| A one-line doc fix nobody else needs to know of                          | Anything that spans more than one sitting   |
|                                                                          | Anything someone else might pick up         |

The [agent](glossary:ai-coding-agent) judges the size. It never asks me "is this big enough for an [issue](glossary:issue)?"; it decides and says which path it took. The same day someone suggested folding that link fix into an unrelated diagram [PR](glossary:pull-request). One [PR](glossary:pull-request) has one purpose, so it was not folded in.

## 2. One PR at a time

![One PR at a time: a PR that triggers a deploy is merged and its deploy checked before the next PR opens. Docs-only PRs may be open together if they do not overlap, with the merge order written in the body](/static/images/skills-05-pr-workflow/one-pr-at-a-time.svg)

_PRs that [deploy](glossary:deployment) go in single file; docs-only PRs touching different files may be open together_

- Merge the current [PR](glossary:pull-request) after [CI](glossary:ci) passes and check its [deploy](glossary:deployment) before opening the next one.
- Queued tasks go in the order asked. If a new request arrives mid-task, the current one is finished first unless I say otherwise.
- While [CI](glossary:ci) runs, prepare the next work locally. Locally, run only the changed tests plus format, type and migration checks. The full suite is [CI](glossary:ci)'s job.

The reason is a single one. Each change should land and [deploy](glossary:deployment) on its own, so the history and the deploys stay easy to follow afterwards. Once the [agent](glossary:ai-coding-agent) read "merge the current [PR](glossary:pull-request) first" as "merge both together", so the rule now says it outright.

The exception came on 2026-11-02 at Woowangthon. Docs-only PRs with no [deploy](glossary:deployment) may be open at the same time when they touch different files or lines; the later [PR](glossary:pull-request)'s body states the merge order. The [skill](glossary:agent-skill) series this post belongs to is exactly that exception: one [PR](glossary:pull-request) per post, each creating different files, all open together and merged in number order.

[Git Flow](glossary:git-flow) repos follow their own `CONTRIBUTING.md`. Usually `main` is the release ([PR](glossary:pull-request) and [CI](glossary:ci) required, [merge commit](glossary:merge-commit), a merge deploys, tag `vX.Y.Z`) and `develop` is the default [branch](glossary:branch). `feature/*` goes into `develop` without waiting for [CI](glossary:ci). How Stairno switched to this is in [the Git Flow section of Stairno part 4](/en/blog/side-projects/stairno/stairno-04-payments/#4-why-i-moved-to-git-flow-midway).

There is one repo-specific line too. For Stairno, production writes and merges that [deploy](glossary:deployment) are done by me. PRs on this blog the [agent](glossary:ai-coding-agent) may merge.

## 3. Splitting commits

![Splitting commits: refactor, a failing test, then feat commits pile up on one branch and become one PR](/static/images/skills-05-pr-workflow/commit-slices.svg)

_Inside one [branch](glossary:branch), [refactor](glossary:refactoring) → test → feat slices pile up into one PR_

- **One [branch](glossary:branch) and [PR](glossary:pull-request) = one feature a user can use.** Its API, screen, tests and spec updates go in together. That is about 300 to 800 changed lines; past 1000, look for a place to split.
- An adapter or small fix that only serves that feature is a [commit](glossary:commit) on the same [branch](glossary:branch). No small [PR](glossary:pull-request) whose only job is to unblock the next one.
- Inside the [branch](glossary:branch), each slice is a failing `test` [commit](glossary:commit) followed by a `feat` [commit](glossary:commit) ([TDD](glossary:tdd)). Moves that keep behaviour the same are their own `refactor` [commit](glossary:commit) before the pair. Each [commit](glossary:commit) must be revertable on its own.
- [Stage](glossary:staging-area) explicit paths. Never `git add -A`. No record states the reason for this line.

The rule came after 14 small PRs, split finely by concern, did little but add [CI](glossary:ci) and [deploy](glossary:deployment) waits. 300 to 800 lines is the size that lets a whole feature be reviewed and reverted at once without a [CI](glossary:ci) and [deploy](glossary:deployment) wait for every piece.

## 4. Rule docs first

![Rule docs before a restructure: PR 1 changes CLAUDE.md and the rule docs and is merged, then PR 2 moves the files](/static/images/skills-05-pr-workflow/rule-docs-first.svg)

_The rule-docs [PR](glossary:pull-request) merges first; file moves come in the next PR_

When a convention changes (naming, folder layout, paths), `CLAUDE.md`, the docs it imports and other instruction files are changed first, in a [PR](glossary:pull-request) of their own. Only after that [PR](glossary:pull-request) passes [CI](glossary:ci) and merges does the move [branch](glossary:branch) start.

This blog still shows it. On 2026-10-10, [#44](https://github.com/seren-wib/vercel-blog/pull/44) changed one file only, `docs/agent/publish_pipeline.md` (13 lines added, 9 removed): post file names get a category prefix, and images are grouped in one folder per post. Later that day [#45](https://github.com/seren-wib/vercel-blog/pull/45) moved 119 files by that rule.

There is a counter-example too. On 2026-11-28, [#163](https://github.com/seren-wib/vercel-blog/pull/163), which added parent categories, carried the structure-doc [commit](glossary:commit) and the post-move [commit](glossary:commit) in the same [PR](glossary:pull-request). There is no record of why it was not split this time.

## 5. Branch update

![Branch update: fetch --prune, ff main, push fork main, delete merged, drop stashes, plus the rule for spotting squash merges](/static/images/skills-05-pr-workflow/branch-update.svg)

_The five steps of a [branch](glossary:branch) update. Squash merges don't show up in `git branch --merged`, so the [PR](glossary:pull-request) state decides_

When I say "브랜치 갱신" ([branch](glossary:branch) update), the [agent](glossary:ai-coding-agent) does all of the following in one go, without asking about deletions.

1. `git fetch --prune` on every [remote](glossary:remote).
2. [Fast-forward](glossary:fast-forward) local `main` to `upstream/main`. Uncommitted edits are stashed, not discarded, and then checked against [upstream](glossary:upstream).
3. Push the [fork](glossary:fork)'s `main` to match.
4. Delete merged [branches](glossary:branch) both locally and on the [remote](glossary:remote) (the [fork](glossary:fork), or `origin` in my own repos) with `git push origin --delete <b>`. Afterwards only `main` and [branches](glossary:branch) still in progress remain.
5. Drop [stashes](glossary:git-stash) whose content is already in `main`.

It then reports deleted and kept [branches](glossary:branch) in one short list, with a reason for each kept one.

Step 4 has two traps.

- **[Squash merge](glossary:squash-merge).** A [squash merge](glossary:squash-merge) puts a single new [commit](glossary:commit) on `main`; the [branch](glossary:branch)'s own [commits](glossary:commit) never land there. So `git branch --merged` can't find the merged [branch](glossary:branch), and the test is different: a [branch](glossary:branch) counts as merged when its [PR](glossary:pull-request) is `MERGED` and the [PR](glossary:pull-request)'s `headRefOid` (the last [PR](glossary:pull-request) [commit](glossary:commit) GitHub remembers) equals the [branch](glossary:branch) tip, or the tip is already in `upstream/main`. If the tip is past the [PR](glossary:pull-request) head, check whether those later [commits](glossary:commit) already landed through another [PR](glossary:pull-request) before deleting.
- **[Worktree](glossary:git-worktree).** git refuses `git branch -D` on a [branch](glossary:branch) checked out in a [worktree](glossary:git-worktree). So `git worktree remove` comes first, and `git worktree prune` at the end.

This section grew twice. On 2026-11-12 only local [branches](glossary:branch) were deleted and the [fork](glossary:fork)'s [remote](glossary:remote) [branches](glossary:branch) were left behind; I said an update obviously includes the [fork](glossary:fork) and asking before each deletion was unnecessary. So it became "the [fork](glossary:fork) too, without asking". On 2026-11-19 one of my private repos had 24 local and 22 [remote](glossary:remote) [branches](glossary:branch), 22 of them already merged. The rule only mentioned [forks](glossary:fork), so `origin` in my own repos was never cleaned. That day step 4 gained "or `origin` in my own repos", and step 4 of section 1, "[branch](glossary:branch) update right after the merge", came in the same day. How the session carries on after a merge is in [CH6. session-flow](/en/blog/side-projects/skills/skills-06-session-flow/).

## 6. Sorting bot reviews

![Bot reviews: bot comments sorted into right, half right and wrong, which are fixed, asked about and left out. Human reviews always get an answer](/static/images/skills-05-pr-workflow/bot-triage.svg)

_Bot comments go three ways; human reviews all get an answer_

The AI review bot is something like [CodeRabbit](glossary:coderabbit). Bot comments are advice, not a gate that blocks the merge.

- First sort them into right / half right / wrong and show me.
- Fix the right ones. Ask about the half-right ones. Leave the wrong ones out.
- Reply to the bot only when I ask.
- Human (teammate) reviews always get an answer, regardless of this sorting.

The rule comes from Woowangthon. Section 5 of the team repo's `AGENTS.md` said bot review is advice, not a gate, and the reason given was that following every comment bends the docs to the bot's taste and only adds [commits](glossary:commit). How the bot read proposal docs as implementation specs in the first week, kept asking for designs and got paused, is in [Woowangthon part 1](/en/blog/hackathon/woowangthon/woowangthon-01-docs-and-prs/#1-three-docs-i-posted-alone-on-day-one). On 2026-11-06 I also saw the bot review again on its own after a fix [commit](glossary:commit) was pushed. That is the record that "one bot review per [PR](glossary:pull-request)" was a wrong assumption.
