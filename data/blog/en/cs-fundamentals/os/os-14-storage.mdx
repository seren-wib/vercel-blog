# 1. Secondary Storage (this mainly covers HDDs)

- Definition: storage outside [primary memory](glossary:primary-memory). The CPU can't access it directly
  → can't execute instructions directly, can't read/write data directly (it must be loaded into memory to be used)
- 4 characteristics
  - Large: 4TB or more
  - Cheap: low cost per unit of capacity
  - [Persistent](glossary:non-volatile-storage): data is kept even when power is cut ([non-volatile](glossary:non-volatile-storage))
  - Slow: access takes ms (about a 10^6x difference from memory's ns)

# 2. HDD structure

![HDD-structure](/static/images/os-14-storage/hdd-structure.png)

## 1. Mechanical (the source of slowness = physically moving parts)

- Rotating [platters](glossary:platter) (disks)
- [arm assembly](glossary:disk-arm) (the [arm](glossary:disk-arm) carrying the [heads](glossary:readwrite-head))

## 2. Electronics

- [disk controller](glossary:disk-controller): handles requests
- [buffer](glossary:disk-buffer): cache memory
- host interface: connects to the host ([SATA](glossary:sata), etc.)

## 3. Physical units

### 1. track: one concentric circle on one platter surface

### 2. sector: the smallest read/write unit a track is divided into

### 3. cylinder: the set of tracks at the same radius on multiple surfaces, grouped vertically

(the [tracks](glossary:track) all [heads](glossary:readwrite-head) touch at once at one [arm](glossary:disk-arm) position)

### 4. platter / surface / spindle

- [platter](glossary:platter): the disk / surface: one side of the disk (top or bottom) / [spindle](glossary:spindle): the shaft the [platters](glossary:platter) are mounted on and rotated by

# 3. How the OS handles HDDs (Managing Disks)

- Premise: a disk is a messy physical device (errors, [bad blocks](glossary:bad-block), missed seeks)
  → the OS's job = hide this mess from higher-level SW

## 1. Access abstraction layers (top=abstract, bottom=physical)

- logical file (file name, byte#) ← user library (user level)
- disk [logical block](glossary:logical-block) (block#) ← [filesystem](glossary:file-system) (kernel level)
- [physical disk block](glossary:physical-block) (surface/[cylinder](glossary:cylinder)/[sector](glossary:sector)) ← [block layer](glossary:block-layer) (kernel level)
  e.g.: "a.txt" → block 1234 → S1, C3, S200. The app only needs to know "a.txt"

## 2. High-level interface (e.g. SCSI)

- In the past: the OS specified [cylinder](glossary:cylinder)/surface/[track](glossary:track)/[sector](glossary:sector) all by itself → the OS had to know all the disk parameters
- Today: the disk exposes its data as an array of [logical blocks](glossary:logical-block) [0..N-1]
  → the OS just passes a block number, and the disk maps it to a physical location on its own
  → the physical parameters are hidden from the OS (to cope with modern disks that got complicated, with varying [sector](glossary:sector) sizes, [remapping](glossary:remapping), etc.)

# 4. The 3 components of Disk Performance

## 1. Seek time

Move the [arm](glossary:disk-arm) to the target [cylinder](glossary:cylinder). The [arm](glossary:disk-arm) has to physically move — the slowest

## 2. Rotational latency

Wait for rotation until the target [sector](glossary:sector) comes under the [head](glossary:readwrite-head). Depends on [rpm](glossary:rpm) — slow

## 3. Transfer time

Data is transferred as the [sector](glossary:sector) passes under the [head](glossary:readwrite-head). Depends on recording density — fast

**→ Of the three, Seek ([arm](glossary:disk-arm) movement) is by far the bottleneck**

※ What if it's an [SSD](glossary:ssd)? No [arm](glossary:disk-arm) or rotation, so Seek and Rotation = 0 → these 3 components and the scheduling in section 5 below become entirely meaningless

**Breaking it down, we find that Seek ([arm](glossary:disk-arm) movement) is the overwhelmingly slow bottleneck**

# 5. Reducing the seek bottleneck (Disk Scheduling)

## 1. Purpose

- Seeks are expensive → if a request comes in while the disk is busy, the waiting requests pile up in the [disk queue](glossary:disk-queue)
- Rearrange the order the queue is processed in → fewer seeks and disk [bandwidth](glossary:bandwidth)↑

## 2. Algorithms

(Common example: queue = 98,183,37,122,14,124,65,67 / [head](glossary:readwrite-head) starts at = 53)

### 1. FCFS: in arrival order as is. Fine under low load, but as it grows it shuttles back and forth → long waiting times

### 2. SSTF: the request closest to the current head first. Minimal seek, request rate↑

Disadvantage: favors the middle blocks → requests at the edges can starve

### 3. SCAN (elevator): serve to the end in one direction, then reverse. Non-uniform waiting time

### 4. C-SCAN: serve in one direction only; on hitting the end, jump back to the start and go the same direction again

→ Uniform waiting time (goes all the way to the end even if there are no requests in that direction)

### 5. LOOK / C-LOOK: same as SCAN/C-SCAN, but move only as far as "the last request in that direction" instead of the disk end (0·199) → removes wasted travel

# 6. Applying it to real HDD use

## 1. Criteria for choosing an algorithm

These days it's best not to do scheduling at all

- [SSTF](glossary:sstf): common and intuitive → a safe default
- High-load systems → [SCAN](glossary:scan) / [C-SCAN](glossary:c-scan) do better
- [SSTF](glossary:sstf) or [LOOK](glossary:look) is reasonable as the default algorithm
- Performance depends on the number and type of requests, and on the file allocation method

## 2. What an I/O Scheduler has to do

- [throughput](glossary:throughput)↑: merge requests (reduce their number) + reorder/sort (reduce seeks)
- Prevent [starvation](glossary:starvation): submit requests before their deadline
- Guarantee [fairness](glossary:fairness) between processes
- Guarantee [QoS](glossary:qos) (quality-of-service) requirements

## 3. Disks today (Modern Disks)

- intelligent controller: a small CPU + tens of KB of memory, loaded with the manufacturer's program
- Features: [read-ahead](glossary:read-ahead) (prefetch the current [track](glossary:track)) / [caching](glossary:cache) (frequently used blocks) / [command queuing](glossary:command-queuing)
  / request reordering ([seek](glossary:seek-time) and rotation optimization) / retry / identifying and [remapping](glossary:remapping) [bad blocks](glossary:bad-block) and [tracks](glossary:track)
- → The disk does its own scheduling. It ignores and overrides the OS's scheduling (because it knows its own layout better than the OS)
