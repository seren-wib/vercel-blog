> 시리즈 13편. 구축 7단계(모니터링), 구축 11을 끝낸 11월 11일 밤부터 12일 새벽까지다. 무엇을 왜 만드는지는 [Woowangthon 0](/kr/blog/woowangthon/woowangthon-00-overview/)에 있다. 바로 앞 글은 [12편](/kr/blog/woowangthon/woowangthon-12-deploy-executor/)이다.

## 한 줄 요약

리더에 Prometheus와 Grafana를 깔고, 플랫폼 서버가 사설망으로 지표를 조회하게 했다. 처음엔 데모 경로 뒤로 미뤘다가 한 시간 남짓 만에 뒤집었다. 권한은 맞게 넣었는데 검사 규칙이 서버의 조회를 422로 거절했고, 리뷰 봇은 지표 공간이 클러스터 안에서 통째로 열려 있다는 걸 잡았다. 그래서 닫았다. 그리고 40분도 안 돼서, 운영자 화면에 넣으려고 Grafana를 공개 주소로 다시 열었다. 연 직후 돌린 셀프 리뷰가 로그인 없이 열린 길 하나와, 학생 앱이 Grafana를 자기 화면에 넣을 수 있는 길을 잡았다.

## 1. 미뤘다가 같은 날 깔았다

지표를 쓰는 곳은 셋이다. 학생이 자기 앱의 CPU · 메모리를 보는 화면, 운영자 화면의 사용량, 비용 추정. 배포 직후의 이상 판정(메모리 초과, 재시작 반복)은 플랫폼 서버가 Pod와 이벤트를 직접 지켜보며 하므로 Prometheus를 거치지 않는다.

그런데 이 셋이 전부 P1이다. 팀 규칙에 "P0가 끝까지 돌기 전엔 P1을 하지 않는다"가 있고, 배포 P0 경로는 플랫폼 서버를 올릴 EC2가 없어서 아직 한 번도 끝까지 돌지 않았다. 에이전트는 Prometheus · Grafana 설치를 데모 경로 뒤로 미루고, 그 전에 작은 것 하나만 하자고 권했다. 나는 그대로 받았다.

그 작은 것이 `metrics.k8s.io` 읽기 권한이다. k3s에는 metrics-server가 기본으로 들어 있어서(`kubectl top`이 되는 그것) 노드와 Pod의 지금 CPU · 메모리는 Prometheus 없이도 읽힌다. 운영자 API에는 이미 `usage` 칸이 있었고, 서버는 그 칸을 `not_collected`로 비워 두고 있었다. 서버 담당(TaeTaeJin)이 이슈에 "노드 · Pod 사용량 읽기 권한"을 달라고 적어 둔 상태였다. [플랫폼 서버 계정](/kr/blog/woowangthon/woowangthon-11-server-link/)에 노드 사용량 읽기를, 학생 공간 읽기 권한에 Pod 사용량 읽기를 하나씩 붙였다.

시험은 전부 통과했다(서버 계정 111개). 그다음 돌린 셀프 리뷰가 그 통과를 의심했다. 새 허용 검사는 요청이 받아들여졌는지만 봤다. metrics-server가 죽어서 빈 목록이 와도 PASS다. [9편에서 아무것도 재지 않고 통과하던 시험](/kr/blog/woowangthon/woowangthon-09-student-space/#7-시험하지-않고도-통과할-수-있었다)과 같은 모양이다. 노드 사용량은 값이 든 항목이 정확히 셋일 때만 통과하게 고쳤다. 이게 팀 레포 [#133](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/133)이다.

#133에는 "Prometheus · Grafana는 P0 뒤에 설치한다"는 문장이 들어 있었다. 머지하고 20분 남짓 뒤에 나는 그 순서를 뒤집었다. EC2는 서버 쪽 사정으로 기다려야 하고, 그동안 클러스터 쪽에서 끝낼 수 있는 일이다. 데모 경로를 밀어내는 일도 아니다. 설계 문서의 "P0 뒤"는 지우지 않고 "미뤘다가 같은 날 바꿨다"로 경위를 남겼다.

## 2. k3s가 Traefik을 넣는 방식으로

kube-prometheus-stack 차트(93.1.1, Prometheus Operator v0.95.1, Grafana 13.3.0)를 썼다. Prometheus, Grafana, 노드를 읽는 node-exporter, 쿠버네티스 객체 상태를 읽는 kube-state-metrics, 그리고 기본 대시보드가 한 묶음으로 온다.

넣는 방식은 k3s의 Helm 컨트롤러다. HelmChart 객체 하나를 적용하면 k3s가 설치 잡을 띄워 차트를 깐다. k3s가 [Traefik](/kr/blog/woowangthon/woowangthon-10-public-entry/#2-traefik을-워커-둘에-하나씩)을 넣는 방식이 이거다. 내 컴퓨터에 helm도, 릴리스 상태도 남지 않는다.

첫 설치는 실패했다. 잡이 3분 넘게 돌았는데 지표 공간에는 아무것도 안 떴다. 설치 잡 Pod는 워커 1에서 한 번 죽고 다시 돌고 있었고, 로그에는 GitHub 릴리스 자산 주소에서 차트 파일을 받다 실패한 줄이 있었다. 차트 저장소의 목록은 GitHub Pages에 있지만, 파일 자체는 GitHub 릴리스 CDN에서 내려온다. 그게 학교망에서 받아지지 않았다. 같은 차트를 GHCR의 OCI 주소에서 받게 바꾸자 잡이 30여 초 만에 끝났다. GHCR은 [이미지 캐시](/kr/blog/woowangthon/woowangthon-08-image-cache/#1-왜-캐시를-두나)가 이미지를 받아 오는 곳이라 학교망에서 길이 확인돼 있었다.

![설치 잡의 실패 로그(GitHub 릴리스 자산 주소에서 차트 받기 실패), 바꾼 뒤의 차트 주소 oci://ghcr.io/prometheus-community/charts/kube-prometheus-stack 93.1.1, 지표 공간 Pod 일곱 개가 모두 Running(node-exporter만 세 노드에 하나씩, 나머지는 리더), 보관 14d와 크기 상한 20GB](/static/images/woowangthon-13-metrics/install.svg)

_실패 로그는 설치하던 밤의 기록, 아래 셋은 글을 쓰며 다시 뜬 것이다_

k3s에서는 끈 것이 많다.

| 끈 것                                              | 이유                                                                                                   |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| etcd · scheduler · controller-manager · kube-proxy | k3s는 이것들을 자기 프로세스 하나 안에서 돌린다. 긁을 대상이 따로 없어 켜 두면 늘 "죽은 대상"으로 뜬다 |
| Alertmanager                                       | 클러스터에서는 알림을 보내지 않는다(6장)                                                               |
| Operator의 admission webhook                       | 인증서를 만드는 잡이 따로 필요한데, 하는 일은 적용 때 규칙 문법을 보는 것뿐이다                        |
| Prometheus 관리 API                                | 지표를 지우는 API다. 차트 기본값대로 꺼 두었다                                                         |

저장은 k3s의 local-path(노드의 폴더)에 Prometheus 30Gi, Grafana 2Gi를 요청했다. 보관은 2주다. 그런데 [8편에서 캐시 볼륨의 50Gi가 상한이 아니었던 것](/kr/blog/woowangthon/woowangthon-08-image-cache/#6-리뷰어-ai가-잡은-것-거절과-무응답)처럼, local-path는 볼륨 크기를 막지 않는다. 30Gi는 요청일 뿐이다. 리더 디스크에는 etcd와 모델 볼륨도 같이 있다. 그래서 Prometheus 자신에게 크기 상한 20GB를 같이 걸었다. 2주가 먼저 차든 20GB가 먼저 차든 오래된 것부터 지운다.

노드를 읽는 node-exporter는 호스트를 들여다봐야 해서 지표 공간의 보안 등급은 [학생 공간의 baseline](/kr/blog/woowangthon/woowangthon-09-student-space/#1-학생-공간-하나에-들어가는-것)이 아니라 privileged다. 나머지는 전부 리더에 뜬다. 긁는 대상은 세 노드의 node-exporter와 kubelet(Pod 사용량), kube-state-metrics, API 서버, CoreDNS, 워커 둘의 Traefik, 그리고 cloudflared다. cloudflared 공간에는 [10편에서 붙인 NetworkPolicy](/kr/blog/woowangthon/woowangthon-10-public-entry/#리더-방화벽은-cloudflared를-못-막는다)가 있어서, Prometheus만 지표 포트(2000)로 들어오게 한 줄을 더했다.

설치 직후 Grafana가 메모리를 450Mi쯤 쓰고 있었다. 처음 잡은 상한이 512Mi라 빠듯해서 1Gi로 올렸다.

## 3. 권한은 된다는데 422

플랫폼 서버는 AWS에 있고, 리더 API에는 사설망으로 붙는다. Prometheus를 조회하려고 포트를 하나 더 여는 대신, 리더 API의 서비스 프록시를 거친다. API 서버가 요청을 대신 Service로 넘겨 주는 기능이다.

```text
GET /api/v1/namespaces/monitoring/services/monitoring-prometheus:9090/proxy/api/v1/query?query=...
```

서버 계정에 준 권한(RBAC)은 이 Service 이름 하나에 대한 `services/proxy`의 `get`뿐이다. 같은 길로 `POST`는 403, Grafana도 403이다. 지표 공간의 Pod · Secret 읽기도 거절된다.

실제 서버 토큰으로 조회를 보냈더니 422가 왔다. 403(권한 없음)이 아니라 422다. 권한 검사는 통과하고 그 뒤의 검사 규칙(ValidatingAdmissionPolicy)에서 거절된 것이다. [플랫폼 서버 계정](/kr/blog/woowangthon/woowangthon-11-server-link/)에는 "서버는 `proj-` 공간 안에서만 쓴다"는 규칙이 걸려 있다. 그 규칙은 만들기 · 고치기 · 지우기, 그리고 CONNECT를 본다. Pod 안에서 명령을 실행하는 exec 같은 호출이 CONNECT다.

쿠버네티스 API 서버는 서비스 프록시 호출을 검사 규칙에 넘길 때, HTTP로는 `GET`이어도 CONNECT로 친다. 그래서 읽기만 하는 지표 조회가 "`proj-` 밖에 쓰기"로 걸렸다. 권한은 허락하고 규칙은 거절했다.

규칙에 이름을 콕 집은 예외 하나를 더했다.

```yaml
- name: isPrometheusQuery
  expression: >-
    request.operation == 'CONNECT' && request.resource.group == '' && request.resource.resource == 'services'
    && request.subResource == 'proxy' && request.namespace == 'monitoring' && request.name == 'monitoring-prometheus:9090'
```

에이전트가 이걸 리더에 적용하려 하자 자동 승인 검사가 "보안 규칙 완화"로 막았다. 틀린 판단이 아니다. 서버 토큰이 `proj-` 밖에 닿는 첫 길이다. 대가도 분명하다. 이 길로는 모든 공간의 지표 수치가 읽힌다(로컬 모델 공간, 시스템 공간까지). 로그 · Secret · 객체는 여전히 `proj-` 공간뿐이다. 쿼리를 공간별로 걸러 주는 프록시를 앞에 둘 수도 있었지만, 세우고 시험할 부품이 하나 는다. 새는 게 숫자뿐이면 그 대가를 문서에 적고 받기로 했다. 그걸 확인하고 내가 적용하라고 했다.

적용 뒤 시험 넷을 다 돌렸다. 지표 23, 서버 계정 111, 배포 실행기 63, 학생 공간 31, 모두 통과. 그 밤에 내 파트 안에서 끝나는 PR 몇 개는 팀원 승인 없이 머지했지만, 이 PR([#138](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/138))은 그러지 않았다. 검사 규칙에 예외를 넣는 변경은 서버 담당이 한 번은 봐야 한다.

## 4. 시험 스크립트가 먼저 틀렸다

422 말고도 시험이 처음엔 거의 다 실패했다. 대부분 시험 스크립트 쪽 잘못이었다.

![첫 실행은 수집 검사가 전부 got nothing, 서비스 프록시 조회는 bash 문법 오류, 실제 토큰 조회는 422. 두 번째 실행은 Traefik과 cloudflared만 got nothing, 서비스 프록시 조회는 ValidatingAdmissionPolicy wanggane-platform-server가 거절](/static/images/woowangthon-13-metrics/first-check.svg)

_시험 스크립트를 고치며 두 번 돌린 결과. `...`는 통과한 줄을 줄인 것이다_

**첫 실행은 쿼리가 깨졌다.** 시험 스크립트는 내 컴퓨터(Windows)에서 돌고, 쿼리는 SSH 너머 리더의 셸을 거쳐 API로 간다. PromQL에는 괄호, 따옴표, 중괄호가 잔뜩 있다. 그게 원격 셸과 Windows의 인자 전달을 지나며 깨졌다. bash 문법 오류도 그 때문이다. 쿼리를 명령줄 인자가 아니라 표준 입력으로 넘기고, 영문자와 숫자 말고는 전부 퍼센트 인코딩하게 바꿨다.

**두 번째 실행은 이름표가 틀렸다.** Traefik과 cloudflared만 "nothing"이었다. 둘은 차트가 아니라 내가 PodMonitor로 따로 붙인 대상인데, 시험은 `job="traefik"`을 찾았다. PodMonitor가 붙이는 job 이름은 `<공간>/<이름>`, 그러니까 `monitoring/traefik`이다. Prometheus에 job 이름 목록을 직접 물어보고 맞췄다.

남은 실패는 3장의 422 하나였다.

## 5. 리뷰 봇이 잡은 열린 지표 공간

[8편](/kr/blog/woowangthon/woowangthon-08-image-cache/#6-리뷰어-ai가-잡은-것-거절과-무응답)에서처럼 이 레포에는 리뷰 봇(CodeRabbit)이 저절로 오지 않는다. #138에 내가 불렀다. 지적이 셋 왔다.

가장 무거운 건 "지표 공간에 들어오는 쪽 NetworkPolicy가 없다"였다. 직접 확인했다. 로컬 모델 공간의 Pod 안에서 Prometheus와 Grafana를 불렀더니 둘 다 200이었다. Prometheus API에는 로그인이 없다. 서버 계정의 권한을 `get` 하나로 좁혀 둔 게, 서비스 프록시를 안 거치는 길 앞에서는 아무 의미가 없었다.

몇 시간 전 설계 문서의 "하지 않는 것"에 에이전트가 이렇게 적어 두었다. 지표 공간의 NetworkPolicy는 두지 않는다, 학생 공간은 [자기 차단 규칙](/kr/blog/woowangthon/woowangthon-09-student-space/#5-막혔다는-걸-어떻게-아나)으로 클러스터 안 대역에 나가지 못하니까. 학생 Pod만 생각한 설명이었다. 클러스터에는 학생 공간 말고도 로컬 모델, 터널, 이미지 캐시 같은 운영 도구 공간이 있다. 설명은 그쪽 Pod를 통째로 빼먹었다. 나도 그 문장을 읽고 넘겼다.

고친 건 NetworkPolicy 하나다. 지표 공간에는 같은 공간의 Pod에서 오는 것만 들어온다. Prometheus가 자기 부품을 긁고 Grafana가 Prometheus를 묻는 건 같은 공간 안이라 그대로 된다. 서버의 서비스 프록시와 운영자의 포트 포워딩도 그대로 된다. 둘 다 리더 자신에게서 Pod로 가는 통신이고, 차단 규칙 구현은 노드가 자기 Pod에 닿는 것을 늘 허용한다. node-exporter는 호스트 네트워크를 쓰니 이 규칙이 아니라 [호스트 방화벽](/kr/blog/woowangthon/woowangthon-05-node-prep/#들어오는-연결)이 막는다.

![정책 전에는 다른 공간에서 Prometheus와 Grafana가 200. 정책을 적용한 뒤에도 시험은 FAIL(command terminated with exit code 1). 직접 불러 보니 Connection refused. 시험을 고친 뒤 둘 다 out of reach로 PASS](/static/images/woowangthon-13-metrics/reach.svg)

_정책을 넣기 전, 넣은 뒤, 시험을 고친 뒤_

정책을 넣었는데도 시험이 실패했다. 이번에도 시험 쪽이었다. "막힘"을 연결 시간 초과로 판정하게 써 놨는데, 실제로는 바로 Connection refused가 왔다. k3s의 차단 규칙 구현(kube-router)은 막힌 연결을 버리지 않고 거절한다. [9편에서 이미 본 것](/kr/blog/woowangthon/woowangthon-09-student-space/#5-막혔다는-걸-어떻게-아나)이다. 그때 배운 걸 새 스크립트에서 또 놓쳤다. 처음엔 출력의 마지막 줄만 보느라 그 문구도 못 봤다. 두 번 고쳐서 맞췄다.

나머지 지적 둘. 하나는 시험이 Grafana나 Operator가 아예 없어도 통과한다는 것이었다. 구성요소 넷과 node-exporter 셋이 Ready인지 보는 검사를 더했다. 다른 하나는 "P0 전에 P1 작업"이었는데, 순서는 내가 정했고 경위를 문서에 적어 뒀다고 답했다. 지표 시험은 30개가 됐다.

이 PR을 그 밤에 승인 없이 머지했다면 열린 지표 공간이 그대로 main에 들어갔다.

## 6. 운영자 화면에 Grafana를 넣는다

그날 밤 팀 디스코드에서 방향이 바뀌었다. 운영자 대시보드는 TaeTaeJin이 플랫폼의 운영자 페이지(FE)에서 맡는다. Grafana 규칙으로 Discord에 보내려던 알림도 플랫폼 쪽으로 넘어갔다. 지표 이상으로 AI를 부를 때 같이 알리는 방안이고, 되면 한다. 그래서 클러스터는 알림을 보내지 않는다. 터널이 끊긴 건 리더 안에서는 알 수가 없으니 Cloudflare 쪽 터널 알림으로 보고, cloudflared의 연결 수 지표로는 보지 않는다. [10편의 인터넷 끊기 시험](/kr/blog/woowangthon/woowangthon-10-public-entry/#7-리더-인터넷-끊기-502-다음-530)에서 그 값이 0으로 안 떨어졌다.

운영자 페이지에 지표를 띄우는 길은 둘이었다. 서버가 Prometheus 값을 받아 FE가 차트를 직접 그리거나(조회 길은 이미 있다), Grafana 화면을 iframe으로 넣거나. 나는 Grafana를 넣기로 했다. 숫자만 받아서 그릴 거면 Grafana를 깔 이유가 없다. 화면을 쓰려고 까는 것이다.

대가는 Grafana가 바깥에 나와야 한다는 것이다. 방금 닫은 공간에 길을 하나 낸다.

- **주소**: `grafana.stairnoworks.com`. 길은 학생 주소와 같다(터널 → Traefik → Ingress). [와일드카드 레코드](/kr/blog/woowangthon/woowangthon-10-public-entry/#1-방문자가-들어오는-길)가 이미 터널을 가리켜서 DNS는 그대로고 Ingress 하나만 는다.
- **들어오는 길**: NetworkPolicy `grafana-from-traefik`. Traefik의 Pod가 Grafana의 3000번에만 닿는다. Prometheus에는 공개 주소가 없다(`prometheus.stairnoworks.com`은 404).
- **Grafana 설정**: `root_url`을 공개 주소로, `allow_embedding`을 켜서 iframe을 막는 머리글(`X-Frame-Options`)을 내지 않게.

로그인을 어떻게 할지가 남았다. 처음엔 JWT 로그인으로 가자고 했다. Grafana는 JWT를 검증할 공개 키 주소를 받는데, 플랫폼 서버가 로그인 토큰(Supabase)을 검증할 때 쓰는 그 주소를 그대로 주면 된다. 서버에 새 API가 필요 없다. 운영자의 로그인 토큰을 iframe 주소에 `?auth_token=`으로 붙이면 Grafana가 바로 열린다.

걸리는 게 그 "주소에 붙인다"였다. iframe은 요청 머리글을 붙일 수 없어서 토큰을 주소에 실어야 한다. 그 토큰은 Grafana 전용이 아니라 플랫폼 API에도 통하는 운영자 토큰이고, 만료(기본 1시간)까지 유효하다. 주소는 머리글보다 흔적이 많다. 접근 로그, 개발자 도구, 화면 공유. 그리고 JWT 없이도 운영자는 iframe 안에서 Grafana에 한 번만 로그인하면 된다. 브라우저가 세션을 기억한다. 그래서 JWT는 후순위로 미뤘다.

공개 주소 시험 6개를 더해 지표 시험은 36개가 됐다. 로그인 없이 대시보드 주소를 치면 로그인 화면으로 가고, API는 401이다. 설계 문서에 "로그인 없이는 아무것도 안 열린다"고 적었다.

## 7. 연 직후의 셀프 리뷰

공개 주소를 연 커밋에 바로 셀프 리뷰(에이전트의 코드 리뷰)를 돌렸다. 아홉 개가 나왔다. 셋이 무거웠다.

**Grafana 자신의 `/metrics`가 로그인 없이 열려 있었다.** 직접 쳐 보니 200에 868KB였다. 클러스터 지표가 아니라 Grafana 자기 지표지만, 정확한 빌드와 커밋, 플러그인과 버전, 사용자 · 대시보드 수, 로그인 횟수가 들어 있다. 문서의 "아무것도 안 열린다"가 틀렸다. Grafana의 지표 노출을 끄고, Prometheus가 그걸 긁던 것도 같이 껐다.

**학생 앱이 Grafana를 자기 화면에 넣을 수 있었다.** `allow_embedding`은 `X-Frame-Options`를 빼기만 하고, 누가 넣어도 되는지는 정하지 않는다. 그 자리를 채우는 머리글이 없으니 어느 사이트든 Grafana를 iframe으로 넣을 수 있었다. 문제는 학생 주소다. `<slug>.stairnoworks.com`과 `grafana.stairnoworks.com`은 출처(origin)는 달라도 브라우저 기준으로 같은 사이트(site)다. 같은 등록 도메인 아래니까. 그래서 운영자의 Grafana 로그인 쿠키(SameSite=Lax)가 학생 앱 안의 iframe에도 실려 간다. 학생 앱이 Grafana를 투명한 iframe으로 깔아 두면, 그 앱에 들어간 운영자의 클릭이 로그인된 Grafana 위에 떨어질 수 있다.

Traefik Middleware 하나로 막았다. Grafana 응답에 `Content-Security-Policy: frame-ancestors 'self' https://app.stairnoworks.com`을 붙인다. 이제 Grafana를 넣을 수 있는 건 Grafana 자신과 플랫폼 화면뿐이다.

**계정이 관리자 하나뿐이었다.** 운영자 화면에서 그걸로 들어가면 보는 화면에서 대시보드 삭제, 데이터 소스 변경, 계정 추가까지 된다. 보기 전용 계정 `viewer`를 만드는 스크립트(`make-viewer.sh`)를 더했다. 비밀번호는 리더에서 만들어 Secret에만 둔다. 운영자 화면은 이 계정으로 연다. 시험을 쓰면서 나도 하나 틀렸다. 보기 전용 계정은 데이터 소스 목록을 못 읽을 거라고 403을 기대했는데 200이 왔다. Grafana가 원래 보는 사람에게 허용하는 것이었다. 검사를 설정 읽기(403)로 바꿨다.

나머지는 작았다. 쿠키에 `Secure`, HSTS 머리글. 그리고 또 시험이었다. iframe 머리글 검사는 응답에 `X-Frame-Options`가 없으면 통과였는데, 터널이 끊겨 curl이 아무것도 못 받아도 "없음"이라 통과했다. 9편의 거짓 PASS가 여기서도 나왔다. Traefik → Grafana 3000번만 열렸는지 NetworkPolicy 모양을 보는 검사도 더했다. 아홉 중 둘은 고치지 않고 설계 문서의 알려진 한계에 적었다.

![공개 주소의 응답 머리글. content-security-policy frame-ancestors 'self' https://app.stairnoworks.com, strict-transport-security. /metrics는 로그인 화면으로 302](/static/images/woowangthon-13-metrics/headers.svg)

_글을 쓰며 데스크탑에서 다시 본 공개 주소_

![지표 시험 41개 전부 PASS. 배치, 다른 공간에서의 접근, 공개 주소(로그인 화면 200, 로그인 없는 대시보드 302, API 401, /metrics 302, frame-ancestors, 보기 전용 계정), 수집 대상, 서버 계정, 실제 토큰 조회 200](/static/images/woowangthon-13-metrics/check-all.svg)

## 8. 아직 확인 못 한 것

- **운영자 화면 안의 iframe.** FE가 아직 붙지 않았다. `app.`과 `grafana.`가 같은 사이트라 로그인 쿠키는 붙을 것으로 본다. FE를 `localhost`에서 띄우면 다른 사이트라 frame-ancestors 허용 목록에도 없고 쿠키도 안 붙는다. 로컬에서 먼저 붙여 봐야 하면 그때 개발 주소를 잠깐 넣는다.
- **2주 보관과 20GB 상한이 실제로 지우는지.** 설치한 지 하루도 안 됐다.
- **Cloudflare 터널 알림이 무료 플랜에서 되는지.** 설계 문서에 "설치 때 확인한다"고 적고 아직 안 봤다.
- 화면은 공개 주소로 한 번 로그인해 홈이 뜨는 것까지 봤다. 대시보드를 하나씩 열어 본 건 아니다.

#138은 이 글을 쓰는 지금 팀원 리뷰를 기다리고 있다. 리더에는 이미 적용돼 있어 기다려도 동작은 같다.
