## 한 줄 요약

처음엔 Google Docs가 원본이었다. 하루 만에 레포의 마크다운이 원본이 됐고, 한 달 뒤에는 절마다 파일 하나로 쪼개 커밋하고 `main`에 push할 때마다 GitHub Actions가 Google Docs를 덮어쓰는 구조가 됐다. 사람은 Google Docs에서 읽고 댓글만 단다. 고치는 건 언제나 레포다.

## 1. Google Docs 원본 시절

비유하면 처음엔 게시판에 직접 글을 쓰고, 공책에는 메모만 했다.

용어로는 2026-10-17 절차에서 **원본(source of truth)**이 Google Docs였다. 레포에는 README, CONTRIBUTING, 짧은 노트만 두고, 계획서·SRS·SDD 같은 산출물은 전부 Google Docs에 썼다.

다음 날인 10-18 이 순서를 뒤집었다. 원본은 로컬 마크다운이고, Google Docs는 단계가 끝날 때나 남에게 보여 주기 전에 한 번 맞춘다. 이유는 규칙 파일에 괄호로 남아 있다. account.stairno.com에서 PR마다 Google Docs를 맞추다 보니 너무 느렸다. 에이전트가 쓰는 Google Docs 커넥터는 문서 안 위치를 지정해서 고치는 방식뿐이라, 고칠 때마다 문서 하나에 수백 KB를 읽어야 했다.

이때 account.stairno.com은 문서 넷을 `docs/specs/`에 두되 `.gitignore`로 커밋하지 않았다. 왜 그렇게 했는지는 기록에 없다(기록 없음).

## 2. 절마다 파일 하나로

비유하면 두꺼운 공책 한 권을 장마다 낱장으로 뜯어 바인더에 꽂은 것이다. 한 장을 고치려고 공책 전체를 펼칠 필요가 없다.

용어로는 문서를 **절 단위 파일(per-section file)**로 나눠 커밋하는 **docs-as-code**다. 2026-11-16 새벽 두 가지 이유로 커밋하지 않던 단일 파일 넷을 커밋하는 절별 파일로 바꿨다.

- **두 컴퓨터**: 나는 윈도우 데스크톱과 맥북을 번갈아 쓴다. 문서가 커밋되지 않으면 한쪽에서 고친 걸 다른 쪽이 모른다. 커밋하면 [두 컴퓨터가 git으로 맞추는 구조](/kr/blog/side-projects/devblog/devblog-04-agent-environment/#7-두-컴퓨터-세-에이전트)를 문서도 그대로 탄다.
- **에이전트가 읽는 양**: 문서가 파일 하나면 에이전트는 한 절을 보려고 문서 전체를 읽는다. 절마다 파일이면 `docs/specs/README.md`에서 파일 이름을 보고 필요한 파일만 연다.

커밋하면 보안은 괜찮을까도 따져 봤다. private 레포는 계정이 나 하나라서 그대로 커밋한다. public 레포에서는 아직 안 고친 보안 구멍, 관리자 주소, 내부 호스트, 운영 절차, 의뢰인이 비공개를 요청한 내용을 빼고 그 자리에 `(Google Docs에만 있음)`이라고 적는다. 비밀값과 개인정보는 어느 레포에도 넣지 않는다.

## 3. 동기화 방향

비유하면 공책과 게시판 중 하나만 고치기로 하고, 나머지는 기계가 따라 쓰게 하는 것이다. 양쪽을 다 고치면 언젠가 내용이 갈린다.

![동기화 방향을 정한 이유: 버린 안은 Google Docs 먼저, 고른 안은 repo 원본에서 한 방향 자동](/static/images/project-docs-04-docs-sync/why-one-way.svg)

_동기화 방향을 정한 이유: 버린 안은 Google Docs 먼저, 고른 안은 repo 원본에서 한 방향 자동_

용어로는 **한 방향 동기화(one-way sync)**다. 같은 날 Google Docs를 먼저 쓰고 레포로 옮기는 안도 검토했다. 맥과 윈도우 사이 동기화만 보면 그쪽이 자연스러워 보였고, 문서가 늘수록 둘이 어긋날 거라는 걱정도 있었다. 하지만 Google Docs 먼저는 네 가지 이유로 버렸다.

| 버린 이유              | 내용                                                       |
| ---------------------- | ---------------------------------------------------------- |
| 통째로 읽어야 한다     | 에이전트가 Doc 하나를 다 읽어야 한 절을 본다               |
| 위치 계산 API          | Docs API는 문서 안 위치(index)로 고쳐서 느리고 쉽게 깨진다 |
| PR 규칙이 깨진다       | 코드와 그 코드의 설계 변경을 한 PR로 묶을 수 없다          |
| 어긋남이 방향만 바뀐다 | 사람이 옮기는 한, 어느 쪽이 먼저든 언젠가 어긋난다         |

대신 치른 대가도 셋이다. 인증 설정이 필요하고, 덮어쓸 때마다 Google Docs 댓글의 위치(anchor)가 풀리고, 표 서식은 단순해진다. 그래서 규칙이 하나 붙었다. 사람은 Google Docs를 고치지 않고 댓글만 단다. 댓글에는 레포를 고쳐서 답하고, 그 Doc을 다시 만드는 머지 전에 열린 댓글부터 처리한다.

## 4. push 한 번에 일어나는 일

비유하면 원본을 고쳐서 제출함에 넣으면, 복사 담당이 즉석 출입증을 받아 게시판의 같은 자리에 새 사본을 붙인다.

![repo에서 Google Docs로, 한 방향: push, GitHub Actions, OIDC와 WIF, Google Doc](/static/images/project-docs-04-docs-sync/sync-flow.svg)

_repo에서 Google Docs로, 한 방향: push, GitHub Actions, OIDC와 WIF, Google Doc_

용어로는 **GitHub Actions** 워크플로 `docs-sync.yml`이다. coffee-shop에 붙인 실제 모습은 커피샵 연재의 [워크플로가 하는 일](/kr/blog/side-projects/coffee-shop/coffee-shop-02-docs-sync/#2-워크플로가-하는-일)에 있다. `main`에 push되고 `docs/specs/`, `docs/images/`, `.github/google-docs.json` 중 하나라도 바뀌면 돈다.

1. Mermaid 코드 블록을 PNG로 렌더링한다. 한글이 깨지지 않게 `fonts-noto-cjk`를 먼저 설치한다.
2. 문서 폴더마다 `README.md`의 목록 순서대로 절 파일을 이어 붙여 HTML 하나로 만든다. 파일 목록 표만 빼고 나머지 표는 둔다.
3. 맨 위에 커밋 SHA를 찍는다. Doc을 열면 어느 커밋에서 만들어졌는지 보인다.
4. 그림 크기를 px로 적는다. Google Docs는 `%` 너비와 `max-width`를 무시해서, 비율을 지키면서 본문 폭(최대 624×864 px)에 맞춘다.
5. Drive API `files.update`로 같은 Doc ID에 덮어쓴다. 새 파일을 만들지 않으니 링크가 안 바뀐다.

다이어그램을 Mermaid로 그리는 것도 이 흐름 때문이다. GitHub가 Mermaid를 바로 렌더링하고, diff에 변경이 보이고, 워크플로가 그림으로 바꿀 수 있다. draw.io SVG는 diff로 무엇이 바뀌었는지 안 보여서 버렸다.

Doc 여섯 개는 내 계정으로 먼저 만들어 둔다. 워크플로가 쓰는 service account에는 Drive 저장 용량이 없어서 새 Doc을 만들 수 없기 때문이다. 문서 이름과 Doc ID의 짝은 `.github/google-docs.json`에 적는다.

## 5. 키 없는 인증

비유하면 사무실 열쇠를 복사해서 맡기는 대신, 출입할 때마다 신분을 확인하고 그 자리에서 한 번 쓰는 출입증을 받는 방식이다.

용어로는 **OIDC**와 **Workload Identity Federation(WIF)**이다. GitHub Actions가 실행마다 발급하는 OIDC 토큰을 Google Cloud가 확인하고, 조건이 맞으면 service account의 짧은 수명 토큰을 내준다. 조건은 레포 소유자가 `seren-wib`인지다. 그래서 내 레포라면 어느 레포든 같은 설정을 쓰고, 레포마다 비밀값을 넣을 필요가 없다.

첫 버전은 service account의 JSON 키를 레포 secret에 넣는 방식이었다. 2026-11-17 coffee-shop에 처음 붙이던 날 WIF로 바꿨고, 만들어 둔 키는 지웠다. 규칙에는 "JSON 키를 다시 만들지 않는다"는 결과만 남아 있고, 바꾼 이유를 적은 문장은 없다(기록 없음). 그날 작업은 맥 세션에서 한 것으로 보여서 윈도우 쪽 세션 기록에서는 찾지 못했다.

같은 날 coffee-shop에서 첫 실행이 Google Docs 여섯 개를 갱신했다. 그날 오후 65분 사이에 커밋 네 개로 빌드 스크립트의 다섯 가지를 고쳤다. SVG를 PNG로 바꾸기, 양식 링크 건너뛰기, Drive 폴더 위치와 그림 px 크기, 한글 폰트 설치, 그림 높이 상한 864 px다.

## 6. 정리

| 언제       | 원본                          | Google Docs                     |
| ---------- | ----------------------------- | ------------------------------- |
| 2026-10-17 | Google Docs                   | 원본                            |
| 2026-10-18 | 로컬 마크다운 (커밋 안 함)    | 단계 끝에 손으로 한 번 맞춤     |
| 2026-11-16 | 레포 `docs/specs/`, 절별 파일 | push마다 덮어쓰는 워크플로 작성 |
| 2026-11-17 | 같음                          | 첫 실행, 인증을 키 없는 WIF로   |

원본을 하나로 정하니 "어느 쪽이 맞냐"는 질문이 없어졌다. 레포가 맞고, Google Docs는 레포의 어느 커밋에서 만들어졌는지를 맨 위에 적고 있다.
