> 시리즈 6편. 구축 4단계, 클러스터 세우기다. 노드 준비는 [5편](/kr/blog/woowangthon/woowangthon-05-node-prep/)에, 전체 그림은 [Woowangthon 0](/kr/blog/woowangthon/woowangthon-00-overview/)에 있다.

## 한 줄 요약

k3s 설치 자체는 명령 한 줄이다. 오래 걸린 건 그다음이다. 우리 PC는 랜 카드 하나에 학교 주소와 노드 주소가 같이 붙어 있고, 학교 주소가 **먼저**다. 쿠버네티스 부품들은 별말이 없으면 첫 주소를 쓰고, 방화벽은 학교 주소에서 온 것을 버린다. 이번 단계에서 막힌 것 셋 중 둘이 여기서 나왔고, 나머지 하나는 방화벽과 쿠버네티스가 규칙을 까는 순서 문제였다.

## 1. 설치 전에 정한 것

k3s는 설치 스크립트에 옵션을 붙여서 깔 수도 있지만, 옵션을 설정 파일(`/etc/rancher/k3s/config.yaml`)에 모아 두고 설치 때는 버전만 고정했다. 같은 클러스터를 다시 세울 때 명령줄 기록을 뒤지지 않아도 되고, 파일을 고친 뒤 재시작만 하면 옵션이 바뀐다. 레포에도 같은 파일을 올렸다(`Infra/k3s/server.yaml`, `agent.yaml`).

```bash
curl -sfL https://get.k3s.io | INSTALL_K3S_VERSION=v1.37.2+k3s1 sh -s - server
```

| 옵션                              | 왜                                                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 버전 고정 `v1.37.2+k3s1`          | 다시 세울 때 같은 것이 나와야 한다                                                                      |
| 내장 etcd(`cluster-init`)         | 서버는 하나지만, 나중에 스냅샷으로 리더를 되살릴 여지를 남긴다. 설치 옵션 하나라 비용이 없다            |
| 노드 주소 지정(`node-ip`)         | 안 그러면 학교 주소를 잡는다                                                                            |
| 기본 CoreDNS 끄기                 | 복제본 1개라 리더에 뜰 수 있고, k3s가 켤 때마다 기본값으로 되돌려서 고쳐 쓸 수 없다. 직접 띄운다(5절)   |
| ServiceLB 끄기                    | 방화벽을 비켜 간다(3절)                                                                                 |
| Secret 암호화                     | 나중에 켜면 재시작과 기존 Secret 재암호화가 든다. 설치 때는 옵션 하나다                                 |
| 리더에 taint                      | 학생 앱이 리더에 못 올라가게. 설치 순간부터 걸린다                                                      |
| 노드가 죽은 뒤 기다리는 시간 30초 | 기본 5분이면 워커 하나가 꺼졌을 때 학생 앱이 5분 동안 안 열린다. Pod마다가 아니라 API 서버에 한 번 준다 |

리더 GPU에 컨테이너가 붙게 해 주는 도구(nvidia-container-toolkit)는 k3s보다 먼저 깔 계획이었다. 먼저 깔아 두면 k3s가 설치될 때 GPU 런타임을 알아서 잡는다. 확인해 보니 받은 PC에 이미 깔려 있었고, k3s가 그대로 잡았다.

작업마다 [5편의 되돌리기 예약](/kr/blog/woowangthon/woowangthon-05-node-prep/#3-끊기기-전에-되돌리기부터)을 이번에도 걸었다. 이번에는 300초 뒤 k3s를 통째로 멈추는 예약이다. k3s가 방화벽 규칙을 잔뜩 넣는데, 그게 원격 접속을 막으면 멈추는 것만으로 풀린다.

## 2. flannel이 학교 주소를 잡았다

5편 끝에서 [설계 문서 리뷰가 미리 짚은 것](/kr/blog/woowangthon/woowangthon-05-node-prep/#7-설계-문서-리뷰가-잡은-것)이 그대로 일어났다. flannel은 다른 노드에 있는 Pod끼리 통하게 길을 까는 k3s 부품이다. 리더를 깔고 보니 flannel이 기록한 이 노드의 주소가 학교 주소였다.

리뷰 때 세운 대책은 `--flannel-iface=enp4s0`, 즉 쓸 랜 카드를 지정하는 것이었다. 그런데 이건 **카드만 고른다**. 주소는 그 카드의 첫 주소를 쓴다. 우리 카드의 첫 주소가 학교 주소다.

다음으로 노드 주소를 "바깥 주소"로 따로 알려 주는 옵션(`node-external-ip`, `flannel-external-ip`)을 넣었다. 기록된 주소는 노드 주소로 바뀌었다. 그런데 실제로 패킷을 싸서 보내는 장치(`flannel.1`)를 열어 보니, 보내는 쪽 주소가 여전히 학교 주소였다.

```bash
ip -d link show flannel.1
```

flannel의 기본 방식은 VXLAN이다. Pod 패킷을 봉투에 한 번 더 넣어서 다른 노드로 보내는데, 봉투의 보낸 곳이 랜 카드의 첫 주소다. 받는 쪽 방화벽은 [5편에서 출발지로 거르게](/kr/blog/woowangthon/woowangthon-05-node-prep/#6-방화벽-들어오는-쪽은-출발지로-나가는-쪽은-포트로) 해 뒀으니 학교 주소에서 온 봉투를 버린다. 이 버전의 k3s에는 봉투의 보낸 곳을 고르는 옵션이 없었다.

그래서 봉투를 안 쓰기로 했다. host-gw 방식은 봉투 없이 각 노드에 "이 Pod 대역은 저 노드로" 하는 길만 깐다. 노드들이 한 스위치에 붙어 있을 때만 되는 방식인데, 우리가 딱 그렇다.

```yaml:/etc/rancher/k3s/config.yaml (리더, 일부)
node-ip: 192.168.77.11
flannel-iface: enp4s0
flannel-backend: host-gw
node-external-ip: 192.168.77.11
flannel-external-ip: true
```

바꾼 뒤 각 노드의 경로표에 `10.42.N.0/24 via 192.168.77.x`가 깔렸다. 다음 노드가 노드 주소라 방화벽을 통과한다. 봉투가 없으니 오히려 가볍다.

## 3. 방화벽을 비켜 가는 두 옆길

설치 전에 계획을 다시 보다가 걸린 게 있었다. k3s에는 ServiceLB라는 기능이 딸려 오는데, 모든 노드의 80/443 포트를 열어 Traefik(바깥 요청을 받아 학생 앱으로 나눠 주는 입구)으로 바로 넘긴다.

문제는 이렇게 열린 포트가 방화벽의 "들어오는 연결" 검사를 거치지 않는다는 점이다. 리눅스 방화벽은 패킷을 검사하는 자리가 셋이다. 이 PC로 들어오는 것(INPUT), 이 PC에서 나가는 것(OUTPUT), 이 PC를 거쳐 다른 데로 가는 것(FORWARD). ServiceLB는 들어온 패킷의 받는 곳을 Pod 주소로 바꿔 버리고(DNAT), 그러면 패킷은 INPUT이 아니라 FORWARD로 간다. 5편에서 막은 건 INPUT이었다. 그대로 두면 학교망 아무 PC에서나 우리 80/443에 닿는다.

ServiceLB는 껐다. 방문자는 [Cloudflare 터널](/kr/blog/woowangthon/woowangthon-05-node-prep/#1-남은-현장-값)로 클러스터 **안**에서 Traefik에 닿기 때문에 PC의 80/443이 필요 없다. 같은 옆길을 타는 NodePort(Service를 모든 노드의 30000번대 포트로 여는 기능)는 노드 대역으로 온 것만 받게 묶었다.

```yaml
disable:
  - coredns
  - servicelb
kube-proxy-arg:
  - nodeport-addresses=192.168.77.0/24
```

## 4. 새 Pod의 첫 패킷이 사라졌다

워커 둘을 붙이고 서로 다른 워커에 시험 Pod를 띄워 통신을 시켜 봤다. 되긴 하는데, 새 Pod가 뜬 직후 첫 연결이 1초쯤 늦게 붙었다. 방화벽 기록을 보니 Pod의 첫 패킷이 버려지고 있었다.

순서 문제였다. FORWARD를 지나는 패킷은 여러 규칙 묶음을 차례로 거친다. 맨 앞이 NetworkPolicy(Pod 사이 방화벽)를 지키는 kube-router, 그 뒤 쿠버네티스, Docker와 Tailscale, 그다음이 ufw다. kube-router는 새 Pod를 위한 통과 규칙을 까는 데 1초 남짓 걸린다. 그 사이 나간 첫 패킷은 kube-router에서 통과 판정을 못 받고 ufw까지 내려가서, ufw의 "거쳐 가는 건 기본 거부"에 걸린다. 1초 뒤 다시 보낸 패킷은 통과한다.

1초면 참을 만해 보이지만, 재부팅할 때마다 Pod 수십 개가 같은 손해를 본다. Pod 대역은 ufw를 지나가게 열었다.

```bash
sudo ufw route allow from 10.42.0.0/16
sudo ufw route allow to 10.42.0.0/16
```

이러면 Pod 사이가 다 열리는 것 아닌가 싶지만, NetworkPolicy는 ufw보다 **앞**에서 걸린다. 들어오는 걸 막는 정책을 하나 걸어 거절되는 걸 보고, 정책을 지우면 다시 되는 걸 봤다. 학생 공간끼리 막는 건 다음 단계에서 이 정책으로 한다.

이 규칙을 넣다가 한 번 더 걸렸다. 규칙 설명에 `in`과 `out`이 들어간 문장을 달았더니 ufw가 설명 안의 단어를 방향 지정으로 읽고 "인터페이스 지정이 틀렸다"며 거절했다. 설명에서 그 단어를 뺐다.

## 5. CoreDNS는 워커 둘에

CoreDNS는 클러스터 안의 전화번호부다. Pod가 이름을 부르면 주소로 바꿔 준다. k3s 기본 것은 하나만 뜨고 리더에 뜰 수도 있다. 리더가 꺼지면 워커에서 멀쩡히 돌던 학생 앱도 DB 주소를 이름으로 못 찾아서 같이 멈춘다. k3s 것을 끄고, 같은 버전의 매니페스트를 가져와 고쳐서 직접 띄웠다.

- 복제본 2
- 학생용 라벨이 붙은 워커에만
- 같은 노드에 둘이 못 뜨게(워커마다 하나)

띄웠더니 Pod가 `ContainerCreating`에서 안 넘어갔다. 설정 묶음(ConfigMap)에 `NodeHosts`라는 항목이 있어야 하는데 비어 있었다. 노드 이름과 주소 목록인데, k3s는 자기 CoreDNS를 켜 둘 때만 이걸 채워 준다. 세 노드를 직접 적어 넣었더니 떴다.

## 6. 워커 하나는 다운로드가 멈췄다

워커 2에서 k3s 바이너리 다운로드가 멈췄다. GitHub 배포 서버 주소 하나가 연결 시작 단계에서 응답을 안 줬고, 몇백 바이트짜리 파일 하나 받는 데 10초가 넘게 걸렸다. 학교망 사정이라 기다린다고 나아질지 알 수 없었다.

리더에는 같은 버전 바이너리가 이미 있었다. 집 데스크탑을 거쳐 SSH로 리더에서 워커 2로 파일을 흘려보내고, 공식 해시(sha256)와 같은지 맞춘 뒤 "다운로드는 건너뛰라"는 옵션으로 설치했다.

워커가 클러스터에 붙으려면 리더가 만든 가입 토큰이 필요하다. 이것도 SSH로 리더에서 워커 파일(`/etc/rancher/k3s/token`, 권한 600)로 바로 흘려보냈다. 화면에도, 레포에도, 채팅에도 찍히지 않는다.

## 7. 확인

| 확인                                           | 결과                                      |
| ---------------------------------------------- | ----------------------------------------- |
| 노드                                           | 3대 Ready, 내부 주소가 192.168.77.x       |
| Secret 암호화                                  | Enabled                                   |
| 서로 다른 워커의 Pod끼리                       | ping 약 0.66ms, HTTP 됨                   |
| 클러스터 DNS                                   | 서비스 이름, 노드 이름, 바깥 이름 모두 됨 |
| Pod에서 바깥 HTTPS                             | 됨                                        |
| 학교 주소로 6443 · 80 · 443 · 10250 · NodePort | 전부 닫힘                                 |
| 노드 주소로 6443 · NodePort                    | 열림                                      |

학교 주소 쪽 시험이 까다로웠다. 원래는 같은 학교망에 붙은 노트북에서 찔러 봐야 하는데, 나는 집에 있었다. 대신 워커 1의 학교 주소에서, 그리고 워커 1의 Pod에서(Pod가 밖으로 나갈 때 학교 주소로 바뀌어 나간다) 다른 노드를 찔렀다. 받는 쪽 방화벽 기록에 출발지가 학교 주소로 찍혀 있어서, 학교망 기기가 보낸 것과 같은 취급을 받았다는 걸 확인했다.

## 8. 재부팅 시험

다음 날 워커 1, 워커 2, 리더 순서로 한 대씩 원격으로 재부팅했다. 재부팅 명령을 2초 뒤로 예약해 두고 SSH를 먼저 빠져나오는 식이다.

세 대 모두 35~45초 만에 아무도 로그인하지 않은 채 돌아왔다. k3s, 방화벽(4절의 규칙 포함), 노드 주소, Pod 경로까지 그대로다. 리더를 재부팅한 뒤에도 세 노드가 한꺼번에 Ready로 돌아왔다.

### NotReady는 40초가 아니라 50초

그런데 재부팅만으로는 재고 싶은 숫자가 안 나왔다. 워커가 꺼졌을 때 학생 앱이 언제 다른 워커로 옮겨 가느냐다. 리더는 워커와 연락이 끊기고 얼마 뒤 그 노드를 NotReady로 판정하고, 거기서 1절의 30초를 더 기다렸다가 Pod를 옮긴다. 재부팅은 판정 시간보다 짧아서 리더가 워커를 한 번도 NotReady로 잡지 않았다. CoreDNS도 옮겨 가지 않고 같은 워커에서 다시 떴다.

그래서 워커 1의 k3s만 150초 멈췄다(물론 다시 켜는 예약을 걸고). 컨테이너는 그대로 돌고 리더와 연락만 끊긴다.

| 멈춘 뒤 | 일어난 일                                                              |
| ------- | ---------------------------------------------------------------------- |
| 약 50초 | 리더가 워커 1을 NotReady로 판정                                        |
| 약 80초 | 대체 CoreDNS Pod 생성 (워커마다 하나 규칙이라 워커 1이 올 때까지 대기) |

문서에는 40초로 적혀 있었다. 쿠버네티스 기본값을 보고 에이전트가 어림한 숫자였는데, 이 버전에서 재 보니 약 50초였다. 클러스터 설계 문서, 시스템 정의서, 도식 두 장의 "약 40초"를 다 "약 50초"로 고쳤다.

전원을 통째로 뽑았다 꽂는 시험만 남았다. [BIOS의 "정전 뒤 자동 켜짐"](/kr/blog/woowangthon/woowangthon-04-remote-access/#7-전원-정전-뒤에도-다시-켜지게)이 실제로 되는지는 동아리방에 가서 봐야 한다.

## 9. 정리

| 겪은 일                                               | 배운 것                                                                     |
| ----------------------------------------------------- | --------------------------------------------------------------------------- |
| `--flannel-iface`를 줬는데 학교 주소를 썼다           | 카드를 고르는 것과 주소를 고르는 건 다르다. 실제 장치(`flannel.1`)까지 본다 |
| VXLAN 봉투의 보낸 곳을 고를 수 없었다                 | 노드가 한 스위치면 host-gw로 봉투를 없앤다                                  |
| ServiceLB가 방화벽을 비켜 학교망에 80/443을 열 뻔했다 | DNAT된 포트는 INPUT이 아니라 FORWARD로 간다. 안 쓰는 입구는 끈다            |
| 새 Pod의 첫 패킷이 버려졌다                           | 방화벽 규칙이 깔리는 순서를 본다. NetworkPolicy가 앞에 있는지 시험한다      |
| 직접 띄운 CoreDNS가 안 떴다                           | 배포판에서 가져온 매니페스트는 배포판이 채워 주던 값까지 챙긴다             |
| 재부팅으로는 NotReady 시간이 안 나왔다                | 판정을 재려면 연락만 끊는다. 어림한 숫자는 잰 숫자로 바꾼다                 |

세 대가 하나의 클러스터가 됐다. 다음은 리더 GPU에 로컬 모델(Qwen3-8B-AWQ)을 띄우는 일이고, 그다음이 학생 앱을 받을 틀이다. 동아리방에 들르는 날 전원 뽑기 시험도 한다.
