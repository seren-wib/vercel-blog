## In one line

At first, Google Docs was the source. Within a day, Markdown in the repo became the source, and a month later the setup became one file per section, committed, with GitHub Actions overwriting Google Docs on every push to `main`. People read in Google Docs and only leave comments. Edits always happen in the repo.

## 1. When Google Docs was the source

As an analogy, at first I wrote directly on the bulletin board and only kept memos in my notebook.

In technical terms, in the 2026-10-17 process the **source of truth** was Google Docs. The repo held only a README, CONTRIBUTING and short notes, and deliverables like the plan, SRS and SDD were all written in Google Docs.

The next day, 10-18, I reversed that order. The source is local Markdown, and Google Docs is synced once at the end of a stage or before showing it to someone. The reason is left in parentheses in the rules file. On account.stairno.com, syncing Google Docs on every PR was too slow. The Google Docs connector the agent uses can only edit by specifying a position inside the document, so even changing one line meant reading hundreds of KB per document.

At that point account.stairno.com kept its four documents in `docs/specs/` but did not commit them, via `.gitignore`. Why I did that is not in the records (not recorded).

## 2. One file per section

As an analogy, I tore a thick notebook into loose pages, one per chapter, and put them in a binder. To fix one page, you don't have to open the whole notebook.

In technical terms, this is **docs-as-code** with the documents split into **per-section files** and committed. Early on 2026-11-16, for two reasons, I changed four uncommitted single files into committed per-section files.

- **Two computers**: I switch between a Windows desktop and a MacBook. If the documents aren't committed, one side doesn't know what was changed on the other. Once committed, the documents ride the same [setup where two computers sync through git](/en/blog/devblog/devblog-04-agent-environment/#7-two-computers-three-agents).
- **How much the agent reads**: if a document is one file, the agent reads the whole document to see one section. With one file per section, it looks up file names in `docs/specs/README.md` and opens only the files it needs.

I also checked whether committing is safe. In private repos I'm the only account, so I commit as is. In public repos I leave out unfixed security holes, admin addresses, internal hosts, operating procedures, and anything a client asked to keep private, and write `(Google Docs에만 있음)` ("only in Google Docs") in their place. Secrets and personal data go into no repo at all.

## 3. Sync direction

As an analogy, you decide to edit only one of the notebook and the bulletin board, and let a machine copy it to the other. If you edit both, the contents will split someday.

![Why the sync direction was chosen: the rejected option is Google Docs first, the chosen one is automatic one-way from the repo source](/static/images/project-docs-04-docs-sync/why-one-way.svg)

_Why the sync direction was chosen: the rejected option is Google Docs first, the chosen one is automatic one-way from the repo source_

In technical terms, this is **one-way sync**. The same day, I also considered writing in Google Docs first and moving it to the repo. Looking only at syncing between Mac and Windows, that seemed natural, and there was also the worry that the two would drift apart as documents grew. But I rejected Google Docs first for four reasons.

| Reason for rejecting      | Details                                                                          |
| ------------------------- | -------------------------------------------------------------------------------- |
| Must read the whole thing | The agent has to read an entire Doc to see one section                           |
| Position-based API        | The Docs API edits by position (index) in the document, so it's slow and brittle |
| Breaks the PR rule        | Code and the design change for that code can't be bundled in one PR              |
| Drift just flips sides    | As long as a person copies, whichever side is first, they drift apart someday    |

There are also three costs paid in exchange. It needs auth setup, every overwrite detaches Google Docs comments from their anchors, and table formatting gets simpler. So one rule was added. People don't edit Google Docs; they only leave comments. Comments are answered by fixing the repo, and open comments are handled first, before the merge that regenerates that Doc.

## 4. What one push does

As an analogy, when you fix the original and drop it in the submission box, the person in charge of copying gets an on-the-spot pass and pins a fresh copy in the same spot on the bulletin board.

![From the repo to Google Docs, one way: push, GitHub Actions, OIDC and WIF, Google Doc](/static/images/project-docs-04-docs-sync/sync-flow.svg)

_From the repo to Google Docs, one way: push, GitHub Actions, OIDC and WIF, Google Doc_

In technical terms, this is the **GitHub Actions** workflow `docs-sync.yml`. It runs on a push to `main` when any of `docs/specs/`, `docs/images/` or `.github/google-docs.json` changed.

1. Render Mermaid code blocks to PNG. Install `fonts-noto-cjk` first so Korean text doesn't break.
2. For each document folder, concatenate the section files in the order listed in its `README.md` into one HTML file. Only the file list table is dropped; other tables stay.
3. Stamp the commit SHA at the top. Open the Doc and you can see which commit it was built from.
4. Write image sizes in px. Google Docs ignores `%` widths and `max-width`, so images are fit to the body width (max 624×864 px) while keeping the aspect ratio.
5. Overwrite the same Doc ID with Drive API `files.update`. No new file is created, so the link doesn't change.

This flow is also why diagrams are drawn in Mermaid. GitHub renders Mermaid directly, changes show up in the diff, and the workflow can turn it into an image. I dropped draw.io SVG because a diff doesn't show what changed.

The six Docs are created first with my own account. The service account the workflow uses has no Drive storage quota, so it can't create new Docs. The pairs of document name and Doc ID are written in `.github/google-docs.json`.

## 5. Keyless auth

As an analogy, instead of copying the office key and handing it over, you verify your identity every time you enter and get a single-use pass on the spot.

In technical terms, this is **OIDC** and **Workload Identity Federation (WIF)**. Google Cloud checks the OIDC token that GitHub Actions issues for each run, and if the condition matches, it hands out a short-lived token for the service account. The condition is whether the repo owner is `seren-wib`. So any repo of mine uses the same setup, and there's no need to put secrets in each repo.

The first version put the service account's JSON key in a repo secret. On 2026-11-17, the day I first attached it to coffee-shop, I switched to WIF and deleted the key I had made. The rules keep only the result, "Don't create a JSON key again," and no sentence states why I switched (not recorded). That day's work seems to have been done in a Mac session, so I couldn't find it in the Windows session records.

The same day, the first run on coffee-shop updated six Google Docs. That afternoon, four commits fixed five things in the build script within 65 minutes: converting SVG to PNG, skipping template links, the Drive folder location and image px sizes, installing a Korean font, and an 864 px cap on image height.

## Glossary

| Term                                                                                                 | Meaning                                                                              |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| source of truth                                                                                      | The single original treated as correct when copies disagree                          |
| docs-as-code                                                                                         | Keeping documents in the repo like code and changing them through PRs and reviews    |
| one-way sync                                                                                         | Sync that copies only from source to copy and accepts no changes from the copy       |
| GitHub Actions                                                                                       | GitHub's CI service that runs workflows in response to repo events                   |
| Mermaid                                                                                              | A syntax for drawing diagrams from code block text                                   |
| service account                                                                                      | A Google Cloud account used by a program rather than a person                        |
| OIDC                                                                                                 | An auth standard that issues a token proving identity for each run                   |
| Workload Identity Federation                                                                         | A feature that exchanges an external OIDC token for a short-lived Google Cloud token |
