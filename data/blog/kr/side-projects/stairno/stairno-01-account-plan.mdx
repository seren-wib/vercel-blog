## 0. 들어가며

> 로드맵 2단계. 계정 센터 코드를 한 줄도 쓰기 전에 한 일이다. 전체 그림은 [Stairno 0. 전체 로드맵](/kr/blog/side-projects/stairno/stairno-00-roadmap/)에 있다.

로그인과 결제는 실수하면 남의 계정이 털리거나 남의 돈이 잘못 나가는 영역이고, 사이트마다 따로 만들면 같은 일을 네 번 하게 된다. 그리고 나는 의뢰인이자 개발자라서, 혼자 하면 "어디까지 만들기로 했더라"가 머릿속에만 남고 범위가 계속 늘어난다. 그래서 코드보다 설계를 먼저 정했다.

식당으로 비유하면, 지점마다 회원 카드를 따로 만들지 않고 본사에 회원 카드 발급 창구를 하나만 세우는 일이다. 가게 문을 열기 전에 도면과 운영 규칙 네 권을 쓰고, 한 지점에서 받은 카드가 다른 건물의 지점에서도 통하는지 시험 영업으로 확인했다. 지점 입구에서 찍어 준 도장은 다른 건물에서 인정받지 못했고, 본사가 발급한 회원 카드는 통했다. 여기서 본사 발급 창구는 계정 센터([OIDC](glossary:oidc) provider), 지점은 각 사이트(client), 지점 입구 도장은 [Cookie](glossary:cookie), 본사 회원 카드는 [Access token](glossary:access-token), 도면과 운영 규칙 네 권은 [Project plan](glossary:project-plan)·[SRS](glossary:srs)·[SDD](glossary:sdd)·테스트와 배포 문서, 시험 영업은 13단계 실험이다.

한 일은 두 가지다. 계정 센터가 무엇을 하고 무엇을 안 하고 어떻게 만들지를 문서 네 개로 정했고, 가장 불확실했던 질문인 "다른 [Domain](glossary:domain) 사이트끼리 로그인을 공유할 수 있나"를 작은 실험으로 확인했다.

## 1. 계정 센터를 별도 프로젝트로 분리

10월 17일, Labs(제품 스토어) [Project plan](glossary:project-plan)을 쓰다가 문제가 보였다. Labs는 로그인과 결제가 필요하다. Works(외주)도 선금 결제가 필요하다. 나중에 나올 제품들도 로그인이 필요하다. 이걸 각 사이트 [Project plan](glossary:project-plan)에 하나씩 넣으면, [Stairno 0](/kr/blog/side-projects/stairno/stairno-00-roadmap/#1-사이트는-넷-계정은-하나)에서 말한 "같은 일 네 번"이 그대로 일어난다.

그래서 Labs [Project plan](glossary:project-plan)의 [Decision record](glossary:decision-record)에 이렇게 적고, 계정과 결제를 **별도 프로젝트, 별도 레포**로 떼어 냈다.

- 계정 센터 `account.stairno.com`과 공용 [API](glossary:api) `api.stairno.com`을 하나의 프로젝트로 만든다
- 허브를 뺀 모든 Stairno 사이트와 제품은 자기 계정과 결제를 두지 않고 이 둘을 부른다
- 국내 결제는 [Toss Payments](glossary:toss-payments), 해외 결제는 [PayPal](glossary:paypal)

같은 날 밤 빈 레포 `seren-wib/account.stairno.com`을 만들었다. README 한 줄짜리였다.

### SRS의 번호 붙은 요구사항

[SRS](glossary:srs)는 요구사항 하나하나에 번호를 붙인다. 예를 들어 이런 식이다.

> **FR-3** 이메일과 비밀번호로 로그인한다. 실패 사유는 "이메일 또는 비밀번호가 맞지 않습니다" 하나로만 알린다.
> 확인 방법: 없는 이메일과 틀린 비밀번호의 응답 본문이 같다.

왜 실패 이유를 하나로 뭉치나? "그런 이메일은 없습니다"와 "비밀번호가 틀렸습니다"를 구분해서 알려 주면, 공격자가 아무 이메일이나 넣어 보면서 "이 사람이 Stairno에 가입했는지"를 알아낼 수 있다.

이 번호는 테스트 이름에도 그대로 들어간다(`FR-3 returns the same body for an unknown email and a wrong password`). 나중에 [Acceptance criteria](glossary:acceptance-criteria)에서 "FR-3 확인했나?"가 테스트 이름 검색 한 번이 된다.

## 3. Cookie로는 로그인 공유가 안 된다

계정 센터의 존재 이유는 "`account.stairno.com`에서 로그인하면 `stairnolabs.com`에서도 로그인 상태"다. 이게 안 되면 나머지 설계가 전부 의미가 없다. 그래서 문서를 쓰는 중간에 실험부터 했다.

로그인 상태는 보통 [Cookie](glossary:cookie)로 기억한다. 그런데 [Cookie](glossary:cookie)는 그걸 발급한 [Domain](glossary:domain)에만 보내진다.

- `account.stairno.com`과 `api.stairno.com`은 같은 `stairno.com` 아래의 [Subdomain](glossary:subdomain)이라, 설정하면 [Cookie](glossary:cookie)를 같이 쓸 수 있다
- `stairnolabs.com`은 다른 [Domain](glossary:domain)이다. `stairno.com`의 [Cookie](glossary:cookie)가 거기로 가지 않는다
- 다른 [Domain](glossary:domain)의 [Cookie](glossary:cookie)를 쓰는 [Third-party cookie](glossary:third-party-cookie)는 Safari 같은 브라우저가 막는다

그러니 [Cookie](glossary:cookie)를 공유하는 길은 처음부터 없다.

## 4. OIDC로 로그인 공유 실험

대안은 "구글로 로그인"과 같은 방식인 [OIDC](glossary:oidc)다. 계정 센터가 provider가 되고, 각 사이트는 provider가 발급한 신원을 받아 가는 client가 된다. 사이트는 사용자를 계정 센터로 [Redirect](glossary:redirect)했다가, [Authorization code](glossary:authorization-code)를 들고 돌아온 사용자를 받아 자기 [Cookie](glossary:cookie)로 자기 [Session](glossary:session)을 만든다. [Cookie](glossary:cookie)는 각 [Domain](glossary:domain)에 머물고, [Domain](glossary:domain)끼리는 [Redirect](glossary:redirect)로만 만난다.

문제는 내가 고른 인증 부품 [Better Auth](glossary:better-auth)가 **[OIDC](glossary:oidc) provider 역할까지** 제대로 해 주느냐였다. 그 기능(`@better-auth/oauth-provider`)은 비교적 새로 나온 부분이라 문서만 믿을 수 없었다.

### 실험 방법

1. 내 컴퓨터에 서버 둘을 띄운다. 하나는 계정 센터 대역(포트 4101), 하나는 Labs 대역(포트 4102). 둘 다 [Better Auth](glossary:better-auth)를 쓴다
2. 계정 센터 대역에는 [OIDC](glossary:oidc) provider 기능을 켜고, Labs 대역은 그 provider를 가리키는 client로 설정한다
3. 브라우저 대신 스크립트가 움직인다. 스크립트는 **[Origin](glossary:origin)마다 [Cookie](glossary:cookie) 저장소를 따로 들고**, 진짜 브라우저처럼 [Redirect](glossary:redirect)를 하나씩 따라간다. 그래야 "[Cookie](glossary:cookie)가 섞이지 않는 상태"에서 로그인이 되는지 볼 수 있다

### 실험 결과: 13단계 전부 통과

| 단계 | 한 일                                                                  | 결과                                                                                                     |
| ---- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 1    | 계정 센터에 가입                                                       | 계정 센터 [Cookie](glossary:cookie) 생김                                                                 |
| 2    | Labs를 계정 센터에 사이트로 등록                                       | 클라이언트 ID(`client_id`)와 시크릿(`client_secret`) 발급                                                |
| 3    | 계정 센터의 [Discovery document](glossary:discovery-document) 읽기     | 로그인 주소, 토큰 주소, 공개 키 주소가 다 있음                                                           |
| 4    | Labs에서 "Stairno로 로그인"                                            | 계정 센터 주소로 보내짐. [PKCE](glossary:pkce) 적용됨                                                    |
| 5    | 계정 센터에 로그인 안 한 상태로 도착                                   | 로그인 페이지로 감. 원래 요청 정보는 위조 방지 서명을 붙여 따라옴                                        |
| 6    | 로그인 페이지에서 비밀번호 입력                                        | 로그인 응답이 바로 "Labs로 돌아가라 + 코드"                                                              |
| 7    | 이미 로그인한 상태로 다시 요청                                         | [Consent screen](glossary:consent-screen) 없이 [Redirect](glossary:redirect) 한 번에 Labs로              |
| 8    | Labs가 코드를 토큰으로 바꿈                                            | 성공. Labs가 **자기 [Cookie](glossary:cookie)**로 자기 로그인을 만듦                                     |
| 9    | Labs에 "지금 누구야?"                                                  | 계정 센터와 같은 사람(이메일 같음)                                                                       |
| 10   | [Cookie](glossary:cookie) 바꿔 끼워 보기                               | 계정 센터 [Cookie](glossary:cookie)로 Labs 조회 → 아무도 아님. 반대도 마찬가지. 로그인은 사이트별로 따로 |
| 11   | Labs가 받은 [Access token](glossary:access-token) 검사                 | [JWT](glossary:jwt). 계정 센터의 [JWKS](glossary:jwks)로 서명 확인 통과, 유효기간 1시간                  |
| 12   | [ID token](glossary:id-token), [Refresh token](glossary:refresh-token) | 둘 다 있음                                                                                               |
| 13   | 계정 센터 로그인이 살아 있을 때 Labs에서 다시 로그인                   | 비밀번호 없이 [Redirect](glossary:redirect) 한 번                                                        |

**결론: 된다. [Cookie](glossary:cookie) 공유가 아니라 [OIDC](glossary:oidc)다.**

### 실험에서 배운 것

실험을 안 했으면 코드를 짜다가 하나씩 부딪혔을 것들이다. 전부 [SDD](glossary:sdd)에 옮겨 적었다.

- [Access token](glossary:access-token)은 기본으로 "아무 뜻 없는 문자열"로 나온다. 요청할 때 "이 토큰은 `api.stairno.com`용"이라고 밝혀야(`resource` 값) 내용을 확인할 수 있는 [JWT](glossary:jwt)로 나온다. [API](glossary:api)는 그 "누구용인지" 값을 검사한다
- 실제 운영용 사이트는 돌아올 주소가 [HTTPS](glossary:https)여야 한다. 실험은 로컬이라 예외 설정으로 했다
- 사이트끼리는 다 Stairno라서 "이 사이트가 내 정보를 받아도 됩니까?" [Consent screen](glossary:consent-screen)을 건너뛰게 등록한다. 이 설정은 서버 안쪽의 관리 명령으로만 할 수 있게 하고, 아무나 사이트를 등록하는 기능은 끈다
- 로그인 페이지는 따라온 요청 정보를 그대로 들고 있다가 비밀번호와 함께 보내야 한다. 그래야 로그인이 끝나자마자 원래 사이트로 돌아간다
- 실험에서 못 본 것: 진짜 [HTTPS](glossary:https) 환경, `stairno.com` [Subdomain](glossary:subdomain) 사이의 [Cookie](glossary:cookie) 공유, [Cloudflare Workers](glossary:cloudflare-workers)에서 돌아가는지. 이건 3단계 첫날 운영에서 확인하기로 했다

실험 코드는 레포의 `experiments/cross-domain-login`에 남겨 두고, [Better Auth](glossary:better-auth) 버전을 올릴 때마다 다시 돌려서 13개가 그대로 통과하는지 본다.

## 5. 구조: 레포 하나, 서버 둘

_1차(로그인) 기준 구조. 2차에서 API 뒤에 결제사와 파일 저장소가 더해진다_

- **`api.stairno.com`**(공용 [API](glossary:api)): 로그인, [Session](glossary:session), [OIDC](glossary:oidc) provider, 나중엔 주문과 결제까지. **DB를 만지는 건 여기뿐이다**
- **`account.stairno.com`**(계정 센터): 사람이 보는 화면. DB를 직접 열지 않고 [API](glossary:api)를 부른다. 서버에서 화면을 만들 때도 브라우저가 보낸 [Cookie](glossary:cookie)를 그대로 [API](glossary:api)에 넘겨 "이 사람 누구야?"를 묻는다
- **사이트들**: [OIDC](glossary:oidc)로 로그인하고, 토큰을 들고 [API](glossary:api)를 부른다

"DB는 [API](glossary:api)만 만진다"는 규칙 하나 덕분에, 데이터 규칙(누가 무엇을 볼 수 있나)이 [API](glossary:api) 한 곳에만 있다. 화면이 몇 개로 늘어나도 데이터 규칙은 한 벌이다.

## 6. 도구 선택

기준은 [Stairno 0](/kr/blog/side-projects/stairno/stairno-00-roadmap/#3-일하는-원칙과-도구)의 첫 원칙, **혼자 운영할 수 있는가**다.

| 영역     | 고른 것                                                                                    | 이유                                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 서버     | [Cloudflare Workers](glossary:cloudflare-workers)                                          | 허브와 같은 곳. 서버 컴퓨터 관리 없음, 무료로 시작, [Cron](glossary:cron)으로 구독 갱신 가능                                                          |
| API 뼈대 | [Hono](glossary:hono)                                                                      | 어느 서버 환경에서든 돈다. [Cloudflare Workers](glossary:cloudflare-workers)가 안 맞으면 다른 곳으로 옮겨도 코드 대부분이 그대로                      |
| 인증     | [Better Auth](glossary:better-auth) + [OIDC](glossary:oidc) provider + [JWT](glossary:jwt) | 가입, 로그인, [Session](glossary:session), [Rate limiting](glossary:rate-limiting)이 들어 있고, 실험으로 [OIDC](glossary:oidc) provider 역할을 확인함 |
| DB       | [Neon](glossary:neon)([PostgreSQL](glossary:postgresql)) + [Drizzle](glossary:drizzle)     | 남이 관리해 주는 DB, 무료 등급. [Cloudflare Workers](glossary:cloudflare-workers)에서 도는 연결 방식이 있음. 표 설계가 코드로 남음                    |
| 메일     | [Resend](glossary:resend)                                                                  | 보내는 방법이 단순하고 월 3,000통 무료. 도메인 인증으로 스팸함에 안 가게                                                                              |
| 화면     | [Astro](glossary:astro) + `@stairno/ui`                                                    | 허브와 같은 도구, 같은 모양. 로그인한 사람마다 화면이 달라서 [SSR](glossary:ssr)                                                                      |
| 테스트   | [Vitest](glossary:vitest)                                                                  | 부품 하나부터 실제 서버 엔진까지 같은 도구로                                                                                                          |

[Test mode](glossary:test-mode) 동안 고정비는 **0원**이다. 실제 결제가 시작되면 [Cloudflare Workers](glossary:cloudflare-workers) 유료 플랜(월 5달러)부터 든다.
