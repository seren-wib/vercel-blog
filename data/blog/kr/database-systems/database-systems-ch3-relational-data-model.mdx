# 3. 관계형 데이터 모델

## 3.1 관계형 모델 개념

**관계형 데이터 모델**: 데이터를 전부 relation(= 테이블)으로 나타내는 모델

- 장점: Simplicity(평평한 테이블이라 쉬움) / Data Integrity(유효·일관) / Easy Data Manipulation(SQL로 조건 걸어 조작) / Security(인증·권한·암호화)

### 3.1.1 도메인·속성·튜플·릴레이션

![STUDENT 테이블에 relation schema·instance·tuple·domain 기호 표시](/static/images/database-systems-ch3-relational-data-model/relation-schema-instance.svg)

| 기호                  | 뜻                                | 그림에서                                          |
| --------------------- | --------------------------------- | ------------------------------------------------- |
| R(A1, …, An)          | relation schema                   | STUDENT(Name, Ssn, Age, Gpa), 파란 머리줄         |
| Ai                    | i번째 attribute                   | A3 = Age                                          |
| n                     | degree (속성 개수)                | 4                                                 |
| r(R) = \{t1, …, tm\}  | relation instance(state)          | 머리줄 아래 행 3개, m = 3                         |
| t = &lt;v1, …, vn&gt; | tuple (행 하나), vi는 i번째 칸 값 | t1 = &lt;Dick Davidson, 422-11-2320, 25, 3.53&gt; |
| dom(Ai)               | Ai의 domain                       | dom(Age) = 15~80 정수                             |

**Relation**: 테이블 하나. relationship(ER 마름모)이랑 다름

**Tuple**: 행 하나. 실세계 entity나 관계 하나에 대응하는 사실

**Attribute**: 열 머리. 예: Name, Age

**Domain**: 그 열에 들어갈 수 있는 값의 집합 = 데이터 타입 + 제약조건. 예: Age는 15~80 정수

- 값은 atomic (더 못 쪼갬)

**Relation schema**: 테이블 머리. 이름 + 열 이름·타입만, 데이터 없음. 예: STUDENT(Name, Ssn, Age, Gpa)

- Degree: 속성 개수. 위 STUDENT는 4

**Relation instance(state)**: 지금 들어 있는 행들의 집합. 행 추가·삭제하면 바뀜, schema는 그대로

- 칸 값 vi는 dom(Ai) 안의 값이거나 NULL / 예: Age 칸에 25 O, 200 X

### 3.1.2 릴레이션의 특징, 관계형 DB 스키마와 상태

**튜플 순서 없음**: relation은 튜플의 집합(set)이라 행 순서 바꿔도 같은 relation

- 그래서 table 말고 relation이라고 부름

**튜플 안 값 순서도 안 중요**: 정의상 ordered list지만 (속성, 값) 쌍으로 보면 순서 바꿔도 같은 튜플

**값은 전부 atomic, NULL 허용**: composite·multivalued 속성은 못 넣음

- multivalued → 별도 relation (부서 위치들 → DEPT_LOCATIONS) / composite → simple 속성만 (Name → Fname, Minit, Lname)
- NULL: unknown·unavailable·undefined. 0이나 빈 문자열 아님

**Relational DB schema**: relation schema들의 집합 + 무결성 제약조건 IC. 예: COMPANY = \{EMPLOYEE, DEPARTMENT, DEPT_LOCATIONS, PROJECT, WORKS_ON, DEPENDENT\}

**Relational DB state**: 각 relation state의 집합 DB = \{r1, …, rm\}

- IC 전부 만족 → valid, 하나라도 어기면 not valid

|             | 틀               | 내용물         |
| ----------- | ---------------- | -------------- |
| 테이블 하나 | relation schema  | relation state |
| DB 전체     | DB schema (+ IC) | DB state       |

## 3.2 관계형 모델 제약조건

**제약조건**: 테이블끼리 엮여 있어서 값에 거는 제한. 요구사항 분석의 규칙에서 나옴

- 전부 지키면 valid state / 핵심 3개: Key, Entity integrity, Referential integrity

### 3.2.1 키 제약조건

![DEPARTMENT로 본 superkey·key·PK 포함 관계](/static/images/database-systems-ch3-relational-data-model/key-hierarchy.svg)

**출발점**: relation은 집합이라 같은 행 두 개 불가 → 행을 콕 집어 구분할 속성이 필요

|                          | 행마다 값 다름 | 군더더기 없음(minimal) | DEPARTMENT 예                                       |
| ------------------------ | -------------- | ---------------------- | --------------------------------------------------- |
| **Superkey**             | 필수           | 상관없음               | \{Dname, Dnumber\}, \{Dnumber, Mgr_ssn\}, 속성 전체 |
| **Key(= Candidate key)** | 필수           | 필수                   | \{Dname\}, \{Dnumber\}                              |
| **Primary key(PK)**      | 필수           | 필수                   | \{Dnumber\} (밑줄)                                  |

**Superkey**: 행마다 값 조합이 다른 속성 묶음. 군더더기 붙어 있어도 됨

- 모든 relation은 superkey 최소 하나 (속성 전체) / key 포함한 묶음은 전부 superkey

**Key(= Candidate key)**: minimal superkey. 하나라도 빼면 구분 안 됨. 예: \{Dnumber, Mgr_ssn\}에서 Mgr_ssn 빼도 구분됨 → key 아님, \{Dnumber\}가 key

- key 여러 개 가능, 그 각각이 candidate key / minimal은 key엔 필수, superkey엔 상관없음

**Primary key(PK)**: candidate key 중 하나 골라 지정한 것. 밑줄로 표시

- PK ⊂ Key ⊂ Superkey / 고르는 규칙은 없음

### 3.2.2 개체 무결성·참조 무결성 제약조건

![EMPLOYEE.Dno(FK)가 DEPARTMENT.Dnumber(PK)를 참조, NULL은 허용·없는 값은 위반](/static/images/database-systems-ch3-relational-data-model/referential-integrity.svg)

**Entity integrity**: PK 값은 NULL 불가. 비어 있으면 그 행이 누군지 모르니까

- PK가 여러 속성이면 한 칸이라도 NULL이면 위반

**Foreign key(FK)**: 다른 테이블의 PK를 가리키는 속성. 예: EMPLOYEE.Dno → DEPARTMENT.Dnumber

- 같은 테이블을 가리킬 수도 있음. 예: Super_ssn → EMPLOYEE.Ssn

**Referential integrity**: FK 값은 실제로 있는 PK 값이거나 NULL. 예: Dno=7인데 7번 부서 없으면 위반

- FK 도메인 = 참조하는 PK 도메인 / PK는 NULL 불가, FK는 NULL 가능 (부서 아직 없는 신입)

**FK는 가리키는 쪽에만 붙음**: EMPLOYEE.Dno가 FK, 가리켜지는 DEPARTMENT.Dnumber는 그냥 PK

- 남이 가리킨다고 FK 되는 거 아님

**PK이자 FK**: 자기 테이블 PK인데 그게 또 남을 가리킬 때. 예: ENROLL(<u>Ssn</u>, <u>Course#</u>, Grade)의 Ssn → STUDENT, Course# → COURSE

|           | 넣을 때 값이 이미 있으면   | 상대 쪽에 값이 없으면   |
| --------- | -------------------------- | ----------------------- |
| **PK**    | 거부 (Key 위반)            | 상관없음                |
| **FK**    | OK (5번 부서 직원 여러 명) | 거부 (Referential 위반) |
| 일반 속성 | OK (동명이인)              | 상관없음                |

**연습 1** (출장 하나는 계좌 여러 개에 청구됨): SALESPERSON(<u>Ssn</u>, Name, Start_year, Dept_no), TRIP(Ssn, From_city, To_city, Departure_date, Return_date, <u>Trip_id</u>), EXPENSE(<u>Trip_id</u>, <u>Account#</u>, Amount)

- FK: TRIP.Ssn → SALESPERSON.Ssn (출장마다 있는 영업사원) / EXPENSE.Trip_id → TRIP.Trip_id (비용마다 있는 출장)

**연습 2**: STUDENT(<u>Ssn</u>, Name, Major, Bdate), COURSE(<u>Course#</u>, Cname, Dept), ENROLL(<u>Ssn</u>, <u>Course#</u>, <u>Quarter</u>, Grade), BOOK_ADOPTION(<u>Course#</u>, <u>Quarter</u>, Book_isbn), TEXT(<u>Book_isbn</u>, Book_title, Publisher, Author)

- FK: ENROLL.Ssn → STUDENT.Ssn / ENROLL.Course# → COURSE.Course# / BOOK_ADOPTION.Course# → COURSE.Course# / BOOK_ADOPTION.Book_isbn → TEXT.Book_isbn

## 3.3 연산과 제약조건 위반

### 3.3.1 기본 연산: 삽입·삭제·갱신

**연산 두 종류**: Retrieval(조회, 상태 안 바뀜) / Update(변경, 위반은 전부 여기서)

| 연산               | 하는 일                | 지정할 것                         |
| ------------------ | ---------------------- | --------------------------------- |
| **Insert**         | 새 튜플 추가           | relation 이름 + 튜플 값 목록      |
| **Delete**         | 튜플 삭제              | relation 이름 + 지울 튜플의 PK 값 |
| **Update(Modify)** | 기존 튜플 속성 값 변경 | 바꿀 속성 + 새 값                 |

### 3.3.2 제약조건 위반

![지우는 튜플을 WORKS_ON이 FK로 가리키면 참조 무결성 위반, 아무도 안 가리키면 OK](/static/images/database-systems-ch3-relational-data-model/delete-violation.svg)

**Insert 검사**: 넣기 전에 질문 3개

- ① 새 PK가 이미 있는 값? → 거부 (Key) / ② 새 PK가 NULL? → 거부 (Entity) / ③ 새 FK 값이 상대 테이블에 없음? → 거부 (Referential)
- 예: &lt;111, Park, 5&gt; 111 이미 있음 → Key / &lt;NULL, Choi, 5&gt; → Entity / &lt;333, Jung, 7&gt; 7번 부서 없음 → Referential / &lt;444, Han, NULL&gt; FK NULL은 OK

**Delete 검사**: 지우는 행의 PK를 남이 FK로 가리키고 있음 → Referential. 이것만

- 예: EMPLOYEE 999887777 삭제 → WORKS_ON 2개가 가리킴, 위반 / WORKS_ON 행 삭제 → 아무도 안 가리킴, OK

**Update = 옛 값 Delete + 새 값 Insert**로 생각

| 뭘 바꿈 | 검사할 것                               |
| ------- | --------------------------------------- |
| PK      | 옛 값: Delete 검사 / 새 값: Insert 검사 |
| FK      | 새 값: 상대에 있나 (Referential)        |
| 나머지  | 없음                                    |

- 예: Ssn 999887777 → 987654321: 옛 값 WORKS_ON이 가리킴(Referential) + 새 값 이미 있음(Key), 위반 2개

**연습 3** (COMPANY DB 원래 상태에 각각 적용)

- b. Insert &lt;'ProductA', 4, 'Bellaire', 2&gt; into PROJECT: Referential 위반. Dnum 2인 부서 없음 (Pnumber 4는 처음 보는 값이라 Key는 OK)
- c. Insert &lt;'Production', 4, '943775543', '2007-10-01'&gt; into DEPARTMENT: Key 위반. Dnumber 4 이미 있음 (Mgr_ssn 943775543도 EMPLOYEE에 없어서 Referential도 걸림, 슬라이드는 Key만 표시)
- d. Insert &lt;'677678989', NULL, '40.0'&gt; into WORKS_ON: Entity + Referential 위반. PK 일부 Pno가 NULL, Essn 677678989 직원 없음
- e. Insert &lt;'453453453', 'John', 'M', '1990-12-12', 'spouse'&gt; into DEPENDENT: 위반 없음. 453453453(Joyce) 있고 (Essn, John) 조합은 처음
- g. Delete EMPLOYEE Ssn = '987654321': Referential 위반. WORKS_ON 2줄, DEPENDENT(Abner), DEPARTMENT 4번 Mgr_ssn, EMPLOYEE Super_ssn이 전부 가리킴

## 3.4 ER → 관계형 변환

**하는 일**: ER 그림 보고 테이블로 옮겨 그리기

- 순서: 사각형 → 이중 사각형 → 마름모(1:1, 1:N, M:N) → 이중 타원 → 셋 연결된 마름모

### 3.4.1 개체 타입 변환

![약한 개체 DEPENDENT: 주인 PK Essn을 FK로 가져오고 PK = Essn + 부분키](/static/images/database-systems-ch3-relational-data-model/weak-entity-mapping.svg)

**사각형 보이면**: 테이블 하나 만듦. 붙은 타원이 열, 밑줄 타원이 PK. 예: EMPLOYEE 사각형 → EMPLOYEE(<u>Ssn</u>, Fname, Lname, …)

- 타원이 가지 쳐 있으면(Name → Fname, Lname) 끝에 달린 것만 열로

**이중 사각형 보이면**: 혼자선 누군지 구분 안 되는 애. 테이블 만들고 연결된 사각형의 PK를 열로 하나 더 붙임. 예: DEPENDENT에 직원 Ssn을 Essn으로 붙임

- PK = 붙인 Essn + 점선 밑줄 속성(Dependent_name) / 이중 마름모는 테이블 안 만듦 (Essn이 이미 이어줌)

### 3.4.2 다중값 속성 변환

![다중값 속성 Locations를 DEPT_LOCATIONS 테이블로 분리](/static/images/database-systems-ch3-relational-data-model/multivalued-mapping.svg)

**이중 타원 보이면**: 원래 테이블엔 안 넣고 테이블 따로 만듦. 열은 원래 테이블 PK + 그 속성. 예: Locations → DEPT_LOCATIONS(<u>Dnumber</u>, <u>Dlocation</u>)

- 위치 하나당 한 줄이라 Dnumber 5가 여러 번 나옴 → PK는 두 열 합친 것

### 3.4.3 관계 타입 변환

![1:N은 N쪽에 FK, 1:1은 total 쪽에 FK, M:N은 새 테이블](/static/images/database-systems-ch3-relational-data-model/relationship-mapping.svg)

| 마름모 양쪽 숫자 | 할 일                                      | 예                                                               |
| ---------------- | ------------------------------------------ | ---------------------------------------------------------------- |
| **1:N**          | N 붙은 쪽 테이블에 상대 PK를 열로 추가     | EMPLOYEE에 Dno 추가                                              |
| **1:1**          | 선 두 줄인 쪽 테이블에 상대 PK를 열로 추가 | DEPARTMENT에 Mgr_ssn 추가                                        |
| **M:N**          | 마름모 이름으로 새 테이블, 양쪽 PK를 열로  | WORKS_ON(<u>Essn</u>, <u>Pno</u>, Hours)                         |
| 사각형 3개 연결  | 새 테이블, 셋 PK 전부 열로                 | SUPPLY(<u>Sname</u>, <u>Proj_name</u>, <u>Part_no</u>, Quantity) |

- 마름모에 타원 달려 있으면(Hours, Start_date) 열 추가한 테이블로 같이 감

**왜 N쪽에?**: 직원 한 명은 부서 하나 → 직원 줄마다 부서 번호 한 칸이면 끝

- 부서 쪽에 넣으면 한 칸에 직원 여러 명 들어가야 해서 안 됨

**왜 선 두 줄 쪽에?**: 부서는 다 관리자 있음 → 칸이 안 빔

- 직원 쪽에 넣으면 관리자 아닌 직원 칸이 다 NULL

**왜 M:N은 새 테이블?**: 어느 쪽에 칸 하나 넣어도 여러 개 못 담음

**연습 4** (UNIVERSITY ER, (min,max) 표기)

- HAS (DEPT (0,N) — STUDENT (0,1)): 학생은 학과 하나 → STUDENT에 Dept 열 추가 (→ DEPARTMENT.DName)
- CHAIR (DEPT (1,1) — INSTRUCTOR (0,1), CStartDate): 학과마다 학과장 꼭 있음 → DEPARTMENT에 ChairId(→ INSTRUCTOR.Id)와 CStartDate 추가
- TAKES (STUDENT (0,N) — SECTION (5,N), Grade): M:N → 새 테이블 TAKES(<u>Sid</u>, <u>SecId</u>, Grade)
