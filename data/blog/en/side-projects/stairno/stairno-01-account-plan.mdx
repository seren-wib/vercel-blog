## 0. Introduction

> Roadmap step 2: what was done before writing a single line of account center code. The big picture is in [Stairno 0. The whole roadmap](/en/blog/side-projects/stairno/stairno-00-roadmap/).

Sign-in and payments are an area where a mistake means someone's account gets taken over or someone's money goes the wrong way, and building them separately per site means doing the same work four times. I am also both the client and the developer, so working alone, "how far did I decide to go?" lives only in my head and the scope keeps growing. So I settled the design before the code.

In restaurant terms, it is setting up one member-card desk at headquarters instead of letting every branch make its own cards. Before opening, I wrote four books of blueprints and house rules, then ran a trial service to check whether a card issued at one branch is accepted at a branch in another building. The stamp given at a branch entrance was not accepted in the other building, but the headquarters-issued member card was. Here the headquarters desk is the account center (the [OIDC](glossary:oidc) provider), a branch is each site (a client), the entrance stamp is a [cookie](glossary:cookie), the headquarters member card is an [access token](glossary:access-token), the four books are the [project plan](glossary:project-plan), [SRS](glossary:srs), [SDD](glossary:sdd) and the test and deploy document, and the trial service is the 13-step experiment.

Two things were done. The four documents settled what the account center does, what it does not do and how it will be built, and the most uncertain question, "can sites on different [domains](glossary:domain) share a sign-in?", was answered with a small experiment.

## 1. Splitting the Account Center into Its Own Project

On 17 October, while writing the [project plan](glossary:project-plan) for Labs (the product store), a problem showed. Labs needs sign-in and payments. Works (freelance) needs deposit payments too. Products that come later will need sign-in. Putting this into each site's [project plan](glossary:project-plan) would cause exactly the "same work four times" described in [Stairno 0](/en/blog/side-projects/stairno/stairno-00-roadmap/#1-four-sites-one-account).

So I wrote this into the [decision log](glossary:decision-record) of the Labs plan and split accounts and payments into **their own project and their own repo**.

- The account center `account.stairno.com` and the shared [API](glossary:api) `api.stairno.com` are built as one project
- Every Stairno site and product except the hub has no accounts or payments of its own and calls these two
- Domestic payments go through [Toss Payments](glossary:toss-payments), international ones through [PayPal](glossary:paypal)

That evening I created the empty repo `seren-wib/account.stairno.com`. It had a one-line README.

## 2. Writing Four Documents Before Code

I used the deliverables from my university software engineering course as they are. The hub, an introduction site, got documents too, but the account center handles sign-in and payments, so it got the **full set, not a trimmed one**.

### The four documents

| Document                                         | Question                    | What is in it                                                                                                                                            |
| ------------------------------------------------ | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Project plan](glossary:project-plan)            | Why, how far, what is risky | Goals, scope (part 1 sign-in / part 2 payments / part 3 extensions / out of scope), risks and responses, costs, [decision log](glossary:decision-record) |
| [Requirements specification (SRS)](glossary:srs) | What to build               | 85 functional requirements, 21 non-functional, 9 domain, 12 use cases                                                                                    |
| [Design specification (SDD)](glossary:sdd)       | How to build it             | Structure, folders, DB tables, [API](glossary:api), payment sequence diagrams, screens, error codes, [decision log](glossary:decision-record)            |
| Test and deploy document                         | How to check it and ship it | Test layers, deploy procedure, rehearsal procedure, [acceptance checklist](glossary:acceptance-criteria), personal data breach response                  |

The originals are written in [Markdown](glossary:markdown) and copied into [Google Docs](glossary:google-docs) for sharing. The rule "if code and documents disagree, fix one of them in the same change" was set at this point too.

### Writing the out-of-scope list first

The most useful part of the [project plan](glossary:project-plan) was the **out of scope** list.

- [Social sign-in](glossary:social-login) (Google, Apple), [passkeys](glossary:passkey), [two-factor authentication](glossary:two-factor-authentication) → part 3. Part 1 is email and password only
- An admin screen → not built. At first, the DB and the providers' dashboards are used directly
- Product catalog and checkout screens → Labs' job
- Real payments → after business registration. Until then, everything is in [test mode](glossary:test-mode)

And the rule "a change that widens the scope only happens after the plan's scope and [decision log](glossary:decision-record) are changed **first**". Since a new "let's add this too" has to go through the documents first, the scope does not grow on a whim.

The risk table was written up front too. For example:

| Risk                                                                             | Response                                                                                                          |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Sign-in cannot be shared across [domains](glossary:domain)                       | Check with an experiment before designing (section 4 below)                                                       |
| The chosen tools do not run on [Cloudflare Workers](glossary:cloudflare-workers) | Actually deploy sign-up and sign-in on the first day of code. If it fails, change the [runtime](glossary:runtime) |
| Payment incidents (double charges, lost notices, amount mismatches)              | Draw the order state rules first. The server re-checks amounts                                                    |
| Handling card data                                                               | Never take or store card numbers. The provider's screen takes them                                                |
| Stalling halfway, being one person                                               | Finish part 1 so that site sign-in works on its own                                                               |

### Numbered requirements in the SRS

Every requirement in the [SRS](glossary:srs) gets a number. For example:

> **FR-3** Sign in with email and password. Report failure with a single message: "The email or password is incorrect."
> How to check: the response body is the same for an unknown email and a wrong password.

Why lump the failure reasons together? If the site says "no such email" and "wrong password" separately, an attacker can try arbitrary emails and learn "whether this person has a Stairno account".

The number goes straight into the test name (`FR-3 returns the same body for an unknown email and a wrong password`). Later, "did we check FR-3?" on the [acceptance checklist](glossary:acceptance-criteria) is one search over test names.

### Three repo documents

Three more documents live inside the code repo.

- `README.md`: what this repo is and how to run it. A public document, so written in English
- `CONTRIBUTING.md`: rules for branches, commits, PRs and deploys
- `CLAUDE.md`: the working rules the [AI coding agent](glossary:ai-coding-agent) reads. Things like "only the [API](glossary:api) touches the DB", "never write code that takes card numbers", "never put secrets in the repo"

## 3. Why Cookies Cannot Share Sign-in

The account center exists so that "signing in at `account.stairno.com` means being signed in at `stairnolabs.com` too". If that does not work, the rest of the design is meaningless. So I ran an experiment in the middle of writing the documents.

A signed-in state is usually remembered with a [cookie](glossary:cookie). But a cookie is only sent to the [domain](glossary:domain) that issued it.

- `account.stairno.com` and `api.stairno.com` are [subdomains](glossary:subdomain) under the same `stairno.com`, so they can share a [cookie](glossary:cookie) if configured to
- `stairnolabs.com` is a different [domain](glossary:domain). [Cookies](glossary:cookie) from `stairno.com` do not go there
- Browsers like Safari block [third-party cookies](glossary:third-party-cookie), which use another [domain](glossary:domain)'s [cookie](glossary:cookie)

So sharing [cookies](glossary:cookie) was never an option.

## 4. Testing Shared Sign-in with OIDC

The alternative is [OIDC](glossary:oidc), the same mechanism as "Sign in with Google". The account center becomes the provider, and each site becomes a client that accepts the identity the provider issues. A site [redirects](glossary:redirect) the user to the account center, then takes the user who comes back with an [authorization code](glossary:authorization-code) and creates its own [session](glossary:session) with its own [cookie](glossary:cookie). [Cookies](glossary:cookie) stay in their own [domains](glossary:domain), and [domains](glossary:domain) meet only through [redirects](glossary:redirect).

The question was whether [Better Auth](glossary:better-auth), the auth component I chose, properly does the **[OIDC](glossary:oidc) provider role** too. That feature (`@better-auth/oauth-provider`) is relatively new, so the documentation alone was not enough to trust.

### How the experiment worked

1. Run two servers on my computer: a stand-in for the account center (port 4101) and a stand-in for Labs (port 4102). Both use [Better Auth](glossary:better-auth)
2. Turn on the [OIDC](glossary:oidc) provider feature in the account center stand-in, and configure the Labs stand-in as a client pointing at that provider
3. A script moves instead of a browser. It **keeps a separate [cookie](glossary:cookie) jar per [origin](glossary:origin)** and follows [redirects](glossary:redirect) one by one, like a real browser. That way you see whether sign-in works "with [cookies](glossary:cookie) never mixing"

### The results: all 13 steps passed

| Step | What was done                                                                    | Result                                                                                                      |
| ---- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 1    | Sign up at the account center                                                    | An account center [cookie](glossary:cookie) appears                                                         |
| 2    | Register Labs as a site with the account center                                  | A client ID (`client_id`) and a secret (`client_secret`) issued                                             |
| 3    | Read the account center's [discovery document](glossary:discovery-document)      | The sign-in, token and public key addresses are all there                                                   |
| 4    | "Sign in with Stairno" on Labs                                                   | Sent to the account center's address. [PKCE](glossary:pkce) applied                                         |
| 5    | Arrive at the account center while signed out                                    | Taken to the sign-in page. The original request comes along with an anti-forgery signature                  |
| 6    | Enter the password on the sign-in page                                           | The sign-in response is directly "go back to Labs + code"                                                   |
| 7    | Ask again while already signed in                                                | Back to Labs in a single [redirect](glossary:redirect), no [consent screen](glossary:consent-screen)        |
| 8    | Labs exchanges the code for a token                                              | Success. Labs creates its own sign-in with **its own [cookie](glossary:cookie)**                            |
| 9    | Ask Labs "who is this?"                                                          | The same person as at the account center (same email)                                                       |
| 10   | Swap the [cookies](glossary:cookie) around                                       | Account center [cookie](glossary:cookie) on Labs → nobody. Same the other way. Sign-ins are per site        |
| 11   | Inspect the [access token](glossary:access-token) Labs received                  | A [JWT](glossary:jwt). Signature verified with the account center's [JWKS](glossary:jwks), valid for 1 hour |
| 12   | [ID token](glossary:id-token), [refresh token](glossary:refresh-token)           | Both present                                                                                                |
| 13   | Sign in again on Labs while the account center [session](glossary:session) lives | One [redirect](glossary:redirect), no password                                                              |

**Conclusion: it works. Not by sharing [cookies](glossary:cookie), but through [OIDC](glossary:oidc).**

### What the experiment taught

Without the experiment, each of these would have been hit one at a time while coding. All of them went into the [SDD](glossary:sdd).

- [Access tokens](glossary:access-token) come out as "a meaningless string" by default. The request has to say "this token is for `api.stairno.com`" (the `resource` value) to get a [JWT](glossary:jwt) whose content can be checked. The [API](glossary:api) checks that "who is it for" value
- Real production sites must use [HTTPS](glossary:https) return addresses. The experiment ran locally, so it used an exception setting
- All the sites are Stairno, so they are registered to skip the "may this site receive your information?" [consent screen](glossary:consent-screen). That setting can only be made through an internal admin command, and the feature that lets anyone register a site is turned off
- The sign-in page has to keep the request details that came along and send them together with the password. That way the user goes straight back to the original site once sign-in is done
- Not covered by the experiment: real [HTTPS](glossary:https), sharing [cookies](glossary:cookie) between `stairno.com` [subdomains](glossary:subdomain), and running on [Cloudflare Workers](glossary:cloudflare-workers). Those were to be checked in production on the first day of step 3

The experiment code stays in the repo at `experiments/cross-domain-login`, and it is rerun every time [Better Auth](glossary:better-auth) is upgraded to check that all 13 still pass.

## 5. Structure: One Repo, Two Servers

![Structure of the account center and API](/static/images/stairno-02-account-plan/architecture.svg)

_The structure for part 1 (sign-in). Part 2 adds payment providers and file storage behind the API_

- **`api.stairno.com`** (shared [API](glossary:api)): sign-in, [sessions](glossary:session), the [OIDC](glossary:oidc) provider, and later orders and payments. **It is the only thing that touches the DB**
- **`account.stairno.com`** (account center): the screens people see. It does not open the DB itself but calls the [API](glossary:api). Even when building a page on the server, it forwards the [cookie](glossary:cookie) the browser sent and asks the [API](glossary:api) "who is this?"
- **Sites**: sign in with [OIDC](glossary:oidc) and call the [API](glossary:api) with tokens

Thanks to the single rule "only the [API](glossary:api) touches the DB", the data rules (who may see what) live in the [API](glossary:api) alone. However many screens there are, there is one set of data rules.

## 6. Choosing the Tools

The yardstick is the first principle from [Stairno 0](/en/blog/side-projects/stairno/stairno-00-roadmap/#3-working-principles-and-tools): **can one person run it?**

| Area         | Chosen                                                                                     | Why                                                                                                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server       | [Cloudflare Workers](glossary:cloudflare-workers)                                          | Same place as the hub. No server machine to manage, starts free, subscriptions can renew with [cron](glossary:cron)                                                       |
| API skeleton | [Hono](glossary:hono)                                                                      | Runs on any server [runtime](glossary:runtime). If [Workers](glossary:cloudflare-workers) does not fit, most code stays the same elsewhere                                |
| Auth         | [Better Auth](glossary:better-auth) + [OIDC](glossary:oidc) provider + [JWT](glossary:jwt) | Sign-up, sign-in, [sessions](glossary:session) and [rate limiting](glossary:rate-limiting) built in, and the experiment confirmed the [OIDC](glossary:oidc) provider role |
| DB           | [Neon](glossary:neon) ([PostgreSQL](glossary:postgresql)) + [Drizzle](glossary:drizzle)    | A managed DB with a free tier. Has a connection mode that runs on [Workers](glossary:cloudflare-workers). Table design stays as code                                      |
| Mail         | [Resend](glossary:resend)                                                                  | Simple to send, 3,000 mails a month free. Domain authentication keeps mail out of spam                                                                                    |
| Screens      | [Astro](glossary:astro) + `@stairno/ui`                                                    | Same tool and look as the hub. Screens differ per signed-in person, so [SSR](glossary:ssr)                                                                                |
| Tests        | [Vitest](glossary:vitest)                                                                  | One tool from a single part up to the real server engine                                                                                                                  |

Fixed costs during [test mode](glossary:test-mode) are **zero**. Once real payments start, costs begin with the [Workers](glossary:cloudflare-workers) paid plan (5 dollars a month).
