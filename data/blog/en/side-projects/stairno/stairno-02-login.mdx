## 0. Introduction

> Roadmap step 3. Sign-in was actually built to the documents from [step 2](/en/blog/side-projects/stairno/stairno-01-account-plan/) and put live. The big picture is in [Stairno 0. The whole roadmap](/en/blog/side-projects/stairno/stairno-00-roadmap/).

Payments, the next step on the roadmap, needs an account to sit on, so sign-up and sign-in came first.

In restaurant terms, the kitchen is the API ([Hono](glossary:hono), [Better Auth](glossary:better-auth)), the floor is the account center screens ([Astro](glossary:astro)), the guest wristband is the [session](glossary:session), the coupon that partner shops accept is the [access token](glossary:access-token), and the reservation-confirmation call is the [verification mail](glossary:email-verification). The order in which this restaurant opens its doors is the deploy automation.

From the early hours to the late morning of 18 October, an empty repo got sign-up, sign-in, [verification mail](glossary:email-verification), device management and a sign-in gateway for other sites, and `api.stairno.com` and `account.stairno.com` went live. In the afternoon I attached the account menu shared with the hub and checked the [acceptance checklist](glossary:acceptance-criteria) on the production addresses, which closed step 3.

## 1. How the work was done

The rules came before the code.

- **One feature = one [issue](glossary:issue) + one [PR](glossary:pull-request).** A feature like "password reset mail" goes on a card, and a change containing only that feature is submitted
- **Commits come in `test` → `feat` pairs.** Following [TDD](glossary:tdd), the failing test is committed first, and the code that makes it pass is the next commit. The history alone shows "what was promised and how it was kept"
- **Requirement numbers in test names.** Like `FR-3 returns the same body for an unknown email and a wrong password`
- **Merging into `main` means deploying.** In this step, a [PR](glossary:pull-request) that passed [CI](glossary:ci) went into `main`, and `main` went to production automatically. This changes in step 4

The code was written by an [AI coding agent](glossary:ai-coding-agent) following these rules, and I reviewed the [PRs](glossary:pull-request) and made the decisions. More than 60 [PRs](glossary:pull-request) went into `main` during step 3.

## 2. Setting up the skeleton

One repo holds three pieces.

| Folder              | What                                                                             |
| ------------------- | -------------------------------------------------------------------------------- |
| `apps/api`          | The shared API. [Hono](glossary:hono) + [Better Auth](glossary:better-auth) + DB |
| `apps/account`      | The account center screens. [Astro](glossary:astro)                              |
| `packages/contract` | The agreements both share: input validation rules, the list of error codes       |

Why `packages/contract` exists: the sign-up form checks "the password must be at least so many characters", and the API must check exactly the same thing. Writing the rule in two places means they drift apart one day. So it is written once and both use it.

[CI](glossary:ci) runs these on every [PR](glossary:pull-request).

1. Code formatting check
2. [Type check](glossary:type-checking) (are the kinds of values right)
3. All tests
4. Whether the [DB blueprint](glossary:schema) and [migration](glossary:database-migration) files match each other
5. Actually building both servers
6. Sign-up → sign-in from start to finish on the real [Workers](glossary:cloudflare-workers) engine ([workerd](glossary:workerd))

## 3. The first-day Workers check

The second line of the step 2 risk table, "the chosen tools do not run on [Workers](glossary:cloudflare-workers)", was checked on day one. [Better Auth](glossary:better-auth), [Drizzle](glossary:drizzle) and the [Neon](glossary:neon) connection all say on paper that they support [Workers](glossary:cloudflare-workers), but you do not know until you run them.

The conclusion was "it works". But **one bug that never shows on [Node.js](glossary:nodejs)** came out.

> If the first request right after the server woke up ([cold start](glossary:cold-start)) was the health check (`/health`), **every sign-in request after it hung without an answer.**

Here is why. The first request starts getting [Better Auth](glossary:better-auth) ready, then finishes its own work and ends before the preparation is done. When a request ends, [workerd](glossary:workerd) throws away the work that request started. So the "preparing" state never finishes, and the following requests waiting on it hang with it. [Node.js](glossary:nodejs) does not throw that work away, so the problem does not show there.

The fix: the request that starts the preparation now waits until it is done before ending. Writing "actually try it on [Workers](glossary:cloudflare-workers) on day one" as a risk response was the right call.

## 4. One feature at a time

One by one, in order, test first every time.

### The API side

| Feature                                          | What it does                                                                                                                                                                                     |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Sign-up                                          | Email, password, accepting the terms. [Passwords that have leaked before](glossary:breached-password-check) are refused                                                                          |
| [Verification mail](glossary:email-verification) | Signing up sends a "confirm your email" message, in Korean or English, in the user's language                                                                                                    |
| Sign-in                                          | A single failure reason only (it does not say whether the email is unknown or the password is wrong)                                                                                             |
| Sign out, sign out everywhere                    | Delete one of my [sessions](glossary:session), or all of them                                                                                                                                    |
| Password reset                                   | A new password from a link in the mail                                                                                                                                                           |
| Profile                                          | Change name, language, email                                                                                                                                                                     |
| Device list                                      | See where you are signed in and sign out only the devices you choose                                                                                                                             |
| Account deletion                                 | Deleted after confirming the password once more                                                                                                                                                  |
| [Session](glossary:session) rules                | Kept 30 days, extended a day at a time with daily use. The [cookie](glossary:cookie) cannot be read by JavaScript and travels only over https                                                    |
| Sign-in gateway for sites                        | An [OIDC](glossary:oidc) provider. Sites are registered only by an operator command                                                                                                              |
| Tokens                                           | [Access tokens](glossary:access-token) 1 hour, [refresh tokens](glossary:refresh-token) 90 days                                                                                                  |
| Connected sites                                  | See which sites you signed into with Stairno and disconnect them                                                                                                                                 |
| Error format                                     | Every error in one shape, `{ error: { code, message } }`. Codes only from a fixed list                                                                                                           |
| Security                                         | Only registered sites may call the API ([CORS](glossary:cors)), [security headers](glossary:security-header), [rate limiting](glossary:rate-limiting) on sign-in, sign-up, reset and mail resend |
| Mail log                                         | Sent mail is recorded, and a failing mail service does not break the sign-up itself                                                                                                              |

### The screen side

Sign-in, sign-up, password reset, email confirmation, the consent screen, the account home, profile, signed-in devices, connected sites and account deletion. Visiting `/` sends you to `/ko` or `/en` based on the browser's language.

The screens also got a **[Content Security Policy](glossary:csp) ([CSP](glossary:csp))**: an allow-list saying "only scripts from these addresses run on this page". Even if someone sneaks a script into the page, the browser does not run it.

### Terms and privacy policy

Account data is collected here, so they live in the account center. I turned the required items from the relevant articles of Korea's Personal Information Protection Act and the Personal Information Protection Commission's drafting guide into a checklist and filled them in one by one. The data collected is the minimum (email, name, payment records), and the processors (Cloudflare, [Neon](glossary:neon), [Resend](glossary:resend)) and their countries are listed. Sign-up also confirms the user is at least 14.

At first the operator field had my name in it, but a personal name stamped on a public page bothered me, so it became "Stairno privacy desk" with a contact address. At step 9 (business registration), when real payments start, the representative's name goes back in as the law requires.

## 5. Going live

### Deploy automation

When something is merged into `main`, [GitHub Actions](glossary:github-actions) ships it to production in this order.

1. Tests
2. Apply [migrations](glossary:database-migration) to the production DB
3. Deploy the API
4. Deploy the account center

If the step that changes the DB structure fails, nothing after it runs. This prevents new code from running on an old DB structure.

### What a person had to do

Some things had to be done by a person once before the automation could take over.

- Create the DB on [Neon](glossary:neon) and run the first [migration](glossary:database-migration) by hand
- Store the two servers' [secrets](glossary:secret) at Cloudflare and the deploy keys at GitHub
- Connect the [subdomains](glossary:subdomain) `api` and `account` to the servers

Around 11 a.m. on 18 October, `api.stairno.com` and `account.stairno.com` went live.

### Keeping mail out of spam

If the [verification mail](glossary:email-verification) lands in spam, sign-up is blocked. So the `stairno.com` domain was authenticated with [Resend](glossary:resend). That means adding three records to the [DNS](glossary:dns) ([SPF](glossary:spf), [DKIM](glossary:dkim), [DMARC](glossary:dmarc)) that let the receiving side check "did stairno.com really send this mail?". Signing up for real and receiving it in Gmail, it arrived in the inbox with all three marked as passed.

### Measured in production

| Check                                                      | Result                                                                            |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Sign-up, sign-in, sign-out                                 | Passed                                                                            |
| [Cookie](glossary:cookie) settings                         | Not readable by JavaScript, https only, shared only among the `stairno.com` rooms |
| [Security headers](glossary:security-header)               | Passed                                                                            |
| Requests sneaked in from another [origin](glossary:origin) | Refused                                                                           |

And two problems turned up.

**1) It goes over the free plan CPU limit.** Password [hashing](glossary:hash-function) is deliberately heavy. Measured in production, one sign-up took 152 ms of CPU and a sign-in about 95 ms, far above the [Workers](glossary:cloudflare-workers) free plan's [10 ms per request](glossary:cpu-time-limit). The requests succeeded when measured, but running over the limit is not something to keep doing. For now the only users are me and test accounts, so the free plan stays, and the decision log says to switch to the paid plan (5 dollars a month) as soon as sign-ups or sign-ins start failing on CPU.

**2) Requests from Korea go through the US.** Requests sent from Korea entered Cloudflare's Los Angeles [data center](glossary:data-center) (LAX). The [round trip](glossary:latency) alone is about 0.2 seconds. That is decided by the plan and the internet provider, and I cannot change it. Instead I did what I could. The DB ([Neon](glossary:neon)) is in the [AWS](glossary:aws) Singapore [region](glossary:region), so I turned on [Smart Placement](glossary:smart-placement), which runs the API server next to the DB.

| Request (from Korea, [median](glossary:median)) | Before | After |
| ----------------------------------------------- | ------ | ----- |
| A request that does not use the DB              | 227ms  | 384ms |
| Health check (one DB call)                      | 391ms  | 371ms |
| Public key list (several DB calls)              | 816ms  | 418ms |
| Sign-in check (no [cookie](glossary:cookie))    | 211ms  | 399ms |

It is not a free win. Requests with several DB calls were halved, but requests that do not call the DB take one more trip to Singapore and got slower. It was still the right side to pick, because almost every real API request calls the DB at least once. [Session](glossary:session) checks look at the DB every time, and [rate limiting](glossary:rate-limiting) records are stored in the DB too. The only requests that skip the DB are "who is this?" from someone not signed in, and addresses that do not exist.

### Polishing the screens

Looking at the live screens myself showed things to fix.

- The "done" message showed even before sign-up was complete. Fixed so that hidden parts stay hidden
- The links on the sign-up screen stayed after sign-up was finished
- The sign-in and sign-up screens were put into a single card over the hub's night band and dot pattern so they connect with the hub

## 6. The account menu shared with the hub

In the afternoon, the account menu from [Stairno 0](/en/blog/side-projects/stairno/stairno-00-roadmap/#adding-the-account-menu) was attached. The order mattered, so it went one [PR](glossary:pull-request) at a time.

1. Build the account menu part in `@stairno/ui` and bump its version
2. Let the API accept "who is this?" and "sign out" requests coming from the hub (`stairno.com`)
3. If you came from the hub to sign in, send you back to the hub afterwards
4. The account center header uses the menu. Clicking the logo goes to the hub
5. The hub uses the menu (in the hub's repo)

Each step was checked in production by actually signing in. The signed-in state now shows at the top right of the hub's front page.

## 7. Tests ran under different conditions

The most unsettling find of this step. [Better Auth](glossary:better-auth) **turns off the [origin](glossary:origin) check automatically in a test environment.** So the test "refuse sign-in requests from another [origin](glossary:origin)" was actually passing with the check switched off.

Production had been closed from the start (sending from another [origin](glossary:origin) was in fact refused). But tests that run under different conditions from production cannot be trusted. A setting now keeps the check always on, so the tests run under the same conditions as production.
