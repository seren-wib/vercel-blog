> 시리즈 5편. 구축 3단계, 노드 준비다. 원격 접속을 만든 이야기는 [4편](/kr/blog/woowangthon/woowangthon-04-remote-access/)에, 전체 그림은 [Woowangthon 0](/kr/blog/woowangthon/woowangthon-00-overview/)에 있다.

## 한 줄 요약

이 단계의 일은 전부 원격이다. 그리고 전부 **잘못하면 원격 접속이 끊기는 일**이다. 네트워크 설정, SSH 설정, 방화벽. 하나라도 틀리면 동아리방까지 걸어가서 모니터를 꽂아야 한다. 그래서 바꾸기 전에 "2분 30초 뒤 저절로 원래대로"를 먼저 예약하고, 다시 붙는 걸 본 다음에 예약을 지우는 방식으로 했다. 한 번도 쓰지는 않았지만, 그 덕에 겁 없이 바꿀 수 있었다.

## 1. 남은 현장 값

2단계에서 못 본 것이 셋 남아 있었다.

| 확인할 것                                   | 결과                                                       |
| ------------------------------------------- | ---------------------------------------------------------- |
| 방화벽(ufw)이 켜져 있나                     | 세 대 모두 **아예 깔려 있지 않다**. 최소 설치판이라 그렇다 |
| Cloudflare 터널이 쓰는 7844 포트로 나가지나 | 세 대 모두 TCP로 나간다                                    |
| 학교망이 443만 열어 둔 건 아닌가            | 아니다. 80, 443, 7844, 8080 등 여러 포트가 나간다          |

7844가 걱정이었다. 방문자가 학생 앱에 들어오는 길로 Cloudflare 터널을 쓰기로 했는데, 터널 프로그램은 443이 아니라 7844로 Cloudflare에 연결을 건다. 학교망이 443만 열어 뒀을 수 있다는 이야기를 듣고(TaeTaeJin) 대안도 두 개 세워 뒀었다. 학교에 포트를 신청하거나, AWS 서버를 공개 입구로 두고 사설망으로 넘기는 것이다. 둘 다 필요 없어졌다.

시험 대상은 이번에도 조심했다. [4편](/kr/blog/woowangthon/woowangthon-04-remote-access/#3-인터넷이-막힌-줄-알았다)에서 학교가 막아 둔 `1.1.1.1`을 찔러서 인터넷이 안 되는 줄 알았던 일이 있었다. 이번에는 터널이 실제로 붙을 Cloudflare 터널 서버 주소에 직접 연결해 봤다.

```bash
timeout 6 bash -c '</dev/tcp/region1.v2.argotunnel.com/7844' && echo open
```

`ping`도 `nc`도 없는 최소 설치판이라, bash의 `/dev/tcp`로 TCP 연결만 맺어 보는 방법을 썼다.

방화벽이 없다는 건 반대로 생각하면 지금까지 **들어오는 연결이 다 열려 있었다**는 뜻이다. 유선에는 와이파이 같은 클라이언트 격리가 없어서, 같은 선에 붙은 학교망 기기가 우리 PC에 바로 닿는다. 이건 이 단계 안에서 바로 막았다(5절, 6절).

## 2. 이름과 시간대

노드 이름은 k3s가 노드 이름으로 그대로 쓴다. 학교가 붙여 둔 원래 이름 대신 `k3s-leader`, `k3s-w1`, `k3s-w2`로 바꿨다. 원래 이름은 반납 때 되돌리려고 기록해 뒀다.

```bash
sudo hostnamectl set-hostname k3s-w2
sudo sed -i 's/^127\.0\.1\.1[[:space:]].*/127.0.1.1 k3s-w2/' /etc/hosts
sudo timedatectl set-timezone Asia/Seoul
```

`/etc/hosts`의 `127.0.1.1` 줄도 같이 바꿔야 한다. 안 바꾸면 `sudo`를 칠 때마다 "호스트 이름을 찾을 수 없다"는 경고가 뜬다.

### cloud-init이 이름을 되돌린다

바꾸기 전에 에이전트가 설정 파일을 훑다가 하나를 찾았다. 이 PC들의 `/etc/cloud/cloud.cfg`에 이런 줄이 있었다.

```yaml
preserve_hostname: false
cloud_init_modules:
  - set_hostname
  - update_hostname
```

cloud-init은 처음 부팅할 때 기기를 설정해 주는 도구인데, 이 설정이면 재부팅할 때 호스트 이름을 자기가 가진 값으로 다시 써 버릴 수 있다. `hostnamectl`로 바꾼 이름이 재부팅 한 번에 원래대로 돌아가는 것이다. 이름을 유지하라는 파일 하나를 따로 넣었다.

```bash
echo 'preserve_hostname: true' | sudo tee /etc/cloud/cloud.cfg.d/99-wanggane-preserve-hostname.cfg
```

그다음 한 대씩 재부팅했다. 워커 2, 워커 1, 리더 순서다. 리더를 마지막에 둔 건, 리더가 안 돌아오면 가장 곤란하기 때문이다. 세 대 모두 아무도 로그인하지 않은 상태에서 1분 안쪽으로 인터넷, Tailscale, SSH가 돌아왔고, 이름도 새 이름 그대로였다.

## 3. 끊기기 전에 되돌리기부터

여기서부터가 위험한 일이다. 네트워크 설정을 잘못 적용하면 그 순간 PC가 인터넷에서 떨어지고, Tailscale도 같이 끊긴다. 원격으로는 고칠 방법이 없다.

그래서 바꾸기 전에 **되돌리는 명령을 미리 예약**했다. systemd의 `systemd-run`은 명령을 "몇 초 뒤에 실행"으로 걸어 둘 수 있다.

```bash
sudo systemd-run --unit=wanggane-revert --on-active=150 \
  /bin/sh -c 'rm -f /etc/netplan/60-wanggane-node.yaml; netplan apply'
sudo netplan apply
```

```bash
sudo systemctl stop wanggane-revert.timer
```

1. 150초 뒤에 새 설정 파일을 지우고 다시 적용하는 예약을 건다
2. 새 설정을 적용한다
3. 노트북에서 다시 접속해 본다
4. 붙으면 예약을 지운다. 안 붙으면 150초 뒤 저절로 원래대로 돌아오고, 그때 다시 접속한다

이걸 노드 주소, SSH 설정, 들어오는 방화벽, 나가는 방화벽에 전부 썼다. 매번 한 대씩, 워커 2부터. 예약이 실제로 터진 적은 없다. 그래도 이게 없었으면 방화벽을 켜는 순간마다 손이 떨렸을 것이다.

## 4. 노드 주소: 같은 랜 카드에 주소 하나 더

[2편](/kr/blog/woowangthon/woowangthon-02-network-design/#6-벽-포트가-바꾼-것)에서 정한 대로 세 대는 벽 랜 포트에 물린 스위치 하나로 인터넷과 노드끼리 연결을 같이 쓴다. 랜 카드 하나에 주소를 둘 둔다.

| 주소                         | 용도                            | 게이트웨이      |
| ---------------------------- | ------------------------------- | --------------- |
| 학교가 준 고정 주소          | 인터넷                          | 학교 게이트웨이 |
| 노드 주소 `192.168.77.11~13` | 노드끼리 (k3s는 이 주소만 쓴다) | 없음            |

학교 주소는 학교 사정으로 바뀔 수 있다. k3s가 그 주소에 묶여 있으면 바뀌는 날 노드끼리 끊긴다. 그래서 우리가 정한 주소를 따로 둔다.

원래 네트워크 설정 파일은 건드리지 않았다. cloud-init이 만든 파일이라 언제 다시 써질지 모르고, 되돌리기도 어렵다. 대신 노드 주소만 담은 파일을 하나 더 뒀다. netplan은 같은 랜 카드를 적은 파일 여러 개를 합쳐서 읽는다.

```yaml:/etc/netplan/60-wanggane-node.yaml
network:
  version: 2
  ethernets:
    enp4s0:
      addresses:
        - '192.168.77.13/24'
```

적용하기 전에 `netplan generate`로 합쳐진 결과부터 봤다. 주소 둘, 게이트웨이는 학교 쪽 하나. 게이트웨이를 노드 주소에도 넣으면 기본 경로가 엉뚱한 쪽으로 빠져 인터넷이 끊긴다.

세 대가 노드 주소로 서로 닿는지 보고, 속도도 쟀다.

```bash
iperf3 -c 192.168.77.12 -t 5
```

세 구간 모두 약 941Mbit/s, 재전송 0이었다. 기가비트 스위치가 낼 수 있는 거의 끝까지 나온다.

## 5. SSH는 키로만

4편에서 기기마다 SSH 키를 만들었지만, 비밀번호 로그인도 여전히 켜져 있었다. 방화벽이 없으니 학교망 어디서든 비밀번호만 맞히면 들어올 수 있었다는 뜻이다. 키 접속만 남겼다.

```text:/etc/ssh/sshd_config.d/10-wanggane-keys-only.conf
PasswordAuthentication no
KbdInteractiveAuthentication no
```

파일 이름 앞 번호가 중요하다. 같은 폴더에 cloud-init이 만든 `50-cloud-init.conf`가 있었고, 거기에 `PasswordAuthentication yes`가 들어 있었다. sshd는 같은 항목이면 **먼저 읽은 값**을 쓰고, 파일은 이름 순서로 읽는다. `10-`이 `50-`보다 먼저라 우리 값이 이긴다. 적용 뒤 `sshd -T`로 실제 값이 `no`인지 보고, 일부러 비밀번호로 접속해 봤다.

```text
Permission denied (publickey).
```

공개키만 받는다는 답이다. 이것도 되돌리기 예약을 걸고 했다. 키 접속이 안 되는 상태에서 비밀번호까지 끄면 그대로 갇힌다.

## 6. 방화벽: 들어오는 쪽은 출발지로, 나가는 쪽은 포트로

### 들어오는 연결

들어오는 연결은 기본 거부로 두고, 아래만 열었다.

| 허용                                  | 용도                                     |
| ------------------------------------- | ---------------------------------------- |
| Tailscale 인터페이스(`tailscale0`)    | 집에서 원격 접속, 나중에 서버 → 리더 API |
| 출발지 `192.168.77.0/24`              | 노드끼리 (k3s API, kubelet, flannel 등)  |
| 출발지 `10.42.0.0/16`, `10.43.0.0/16` | k3s Pod · 서비스 대역                    |

노드 대역을 **랜 카드가 아니라 출발지 주소로** 연 게 핵심이다. 노드 주소와 학교 주소가 같은 랜 카드에 있으니, "이 랜 카드로 들어오는 건 허용"으로 열면 같은 선의 학교망 기기도 전부 통과한다.

켠 뒤에 세 대가 서로를 두 주소로 찔러 봤다.

| 어디로                | 22번 포트 |
| --------------------- | --------- |
| 다른 노드의 노드 주소 | 열림      |
| 다른 노드의 학교 주소 | 막힘      |

학교 주소에서 출발한 연결은 학교망 기기와 같은 취급을 받으니, 학교망에서 들어오는 연결이 막혔다는 확인이 된다.

### 나가는 연결

나가는 쪽도 기본 거부로 바꿨다. 워커 PC가 뚫렸을 때 갈 수 있는 곳을 줄이려는 것이다. 처음에는 "GHCR(이미지 레지스트리)이랑 Ubuntu 패키지 서버만 허용"처럼 목적지로 묶고 싶었는데, ufw는 도메인을 모른다. IP로 묶자니 레지스트리도 패키지 서버도 Tailscale도 CDN 뒤에 있어서 IP가 계속 바뀐다. 그래서 **포트**로 묶었다.

| 허용                            | 용도                                      |
| ------------------------------- | ----------------------------------------- |
| 53, 123/udp                     | DNS, 시간 동기화                          |
| 80, 443/tcp                     | 패키지, 레지스트리, Tailscale 제어와 중계 |
| 41641/udp, 3478/udp             | Tailscale 직접 연결 시도                  |
| 노드 대역, k3s 대역, tailscale0 | 클러스터 안, 원격 접속                    |
| 7844 (리더만)                   | Cloudflare 터널                           |

바꾼 뒤 DNS, HTTPS, 레지스트리, `apt update`, 시간 동기화, Tailscale이 다 되는지, 그리고 8080 같은 다른 포트는 막히는지 봤다. 443을 열어 둔 이상 443으로는 어디든 나갈 수 있다는 한계는 남는다. 포트로 거르는 방식의 한계다.

## 7. 설계 문서 리뷰가 잡은 것

노드 준비가 끝나고, 다음 단계(k3s 설치)에 들어가기 전에 팀 레포 규칙대로 클러스터 설계 문서를 썼다([woowangthon/WOOWANGTHON_TEAM_18#31](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/31)). 초안은 에이전트가 썼고, 나는 "문제없는 것 같은데 리뷰 한 번만 하고 올리자"고 했다. 에이전트의 코드 리뷰를 문서에 돌렸더니 일곱 개가 나왔다. 그중 둘은 그대로 갔으면 다음 단계에서 실제로 터졌을 것이다.

- **방화벽이 Pod 통신에는 안 걸린다.** 6절의 나가는 규칙은 PC에서 직접 도는 프로그램(호스트 프로세스)에만 적용된다. 클러스터 안의 Pod가 밖으로 나가는 통신은 주소 변환을 거쳐 다른 길(FORWARD)로 나간다. 나중에 터널 프로그램과 이미지 캐시를 Pod로 띄우면, 이 규칙과 상관없이 통째로 막히거나 통째로 열린다. 문서에 그 구분을 적고, 운영 도구 Pod는 k3s 설치 때 따로 묶기로 했다.
- **flannel이 학교 주소를 잡을 수 있다.** k3s의 Pod 네트워크(flannel)는 노드끼리 터널을 맺을 때 랜 카드의 주소를 쓴다. 우리 랜 카드에는 학교 주소가 먼저 있다. flannel이 학교 주소로 터널을 맺으면, 6절의 방화벽이 그 출발지를 막아서 노드 사이 Pod 통신이 끊긴다. 설치할 때 랜 카드를 지정하고, 실제로 어느 주소를 잡았는지 확인하는 단계를 넣었다.
- 그 밖에, 워커가 꺼졌을 때 학생 DB가 넘어가게 하는 볼륨 설정이 앱만 옮기고 DB는 놓치는 값으로 적혀 있었다.

재미있는 건 이 문서를 쓴 것도 AI, 틀린 데를 잡은 것도 AI라는 점이다. 같은 에이전트가 쓸 때는 못 보고, 리뷰라는 다른 눈으로 다시 보게 하니 보였다. 다만 리뷰를 돌리자고 한 건 사람이었다. 시키지 않았으면 초안 그대로 올라갔다.

## 8. 정리

| 겪은 일                                          | 배운 것                                                        |
| ------------------------------------------------ | -------------------------------------------------------------- |
| 방화벽이 아예 없었다                             | 최소 설치판은 기본값을 믿지 말고 하나씩 본다                   |
| 7844가 막혔을까 걱정했다                         | 실제로 붙을 주소로 시험한다. 대안 두 개가 필요 없어졌다        |
| 바꾼 호스트 이름이 재부팅 때 되돌아갈 수 있었다  | cloud-init의 `preserve_hostname`을 먼저 본다                   |
| 원격 변경 하나하나가 접속을 끊을 수 있었다       | 되돌리는 명령부터 예약하고 바꾼다                              |
