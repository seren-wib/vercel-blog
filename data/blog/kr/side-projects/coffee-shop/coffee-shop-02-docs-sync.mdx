> 연재 2편. 프로젝트 전체 그림은 [Coffee Shop 0](/kr/blog/side-projects/coffee-shop/coffee-shop-00-overview/)에 있다. 이 글은 11월 17일 하루에 들어온 PR 네 개(#64, #65, #66, #69)를 다룬다.

## 한 줄 요약

문서 원본은 레포의 Markdown이고, 팀원과 교수님이 보는 건 Google Docs다. 둘을 손으로 맞추면 반드시 갈라진다. 그래서 `main`에 문서가 머지될 때마다 GitHub Actions가 Markdown을 HTML로 바꿔 **같은 Google Doc에 덮어쓰게** 했다. 링크가 안 바뀌니 공유한 주소가 계속 최신본을 보여 준다.

## 1. 왜 레포가 원본인가

[1편](/kr/blog/side-projects/coffee-shop/coffee-shop-01-requirements-design/)에서 문서를 `docs/specs/`로 옮긴 이유가 ID 추적이었다. 테스트와 PR이 문서를 가리키려면 문서가 코드와 같은 레포, 같은 커밋 기록 안에 있어야 한다. 그런데 Markdown 파일을 그대로 팀원에게 보내면 읽기 불편하고, 과제 제출도 Google Docs로 한다.

방송으로 치면 레포는 원본 테이프를 보관하는 편집실이고, Google Docs는 시청자가 보는 채널이다. 편집실에서 고친 테이프가 채널로 자동 송출되면, 채널에서 직접 고칠 일이 없어진다.

![docs-sync 흐름 다이어그램. docs/specs 아래 Markdown이 main에 머지되면 GitHub Actions의 docs-sync 작업이 Mermaid 블록과 SVG를 PNG로 바꾸고, 문서 폴더 여섯 개를 README 순서대로 이어 붙여 HTML 여섯 개를 만든다. GitHub OIDC 토큰을 Google Workload Identity Federation에서 서비스 계정 토큰으로 바꾼 뒤 Drive API로 같은 Doc ID에 덮어쓴다](/static/images/coffee-shop-02-docs-sync/docs-sync-flow.svg)

편집실은 `docs/specs/`, 송출은 `.github/workflows/docs-sync.yml`, 채널은 Drive 폴더 `projects-docs/coffee-shop`의 Doc 여섯 개다. 이 비유는 여기까지만 쓴다.

## 2. 워크플로가 하는 일

#64가 처음 들여온 구조다.

| 단계         | 하는 일                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- |
| 트리거       | `main` push 중 `docs/specs/**`, `docs/images/**`, `.github/google-docs.json`이 바뀐 것, 또는 수동 실행                    |
| Mermaid 렌더 | `mmdc`(mermaid-cli 11.4.2)로 Markdown 안 Mermaid 블록을 PNG로 바꾼다                                                      |
| SVG 렌더     | Google Docs는 SVG를 못 보여 준다. 그 커밋의 SVG를 `images.weserv.nl`로 PNG로 받는다(공개 레포라 가능)                     |
| 빌드         | `build-docs.mjs`가 문서 폴더마다 README 표 순서대로 파일을 이어 붙이고, 커밋 SHA를 맨 위에 찍고, 그림을 data URI로 넣는다 |
| 인증         | GitHub OIDC → Google Workload Identity Federation → 서비스 계정 `docs-sync`. 저장소 시크릿 0개                            |
| 업로드       | Drive API `PATCH /upload/drive/v3/files/<id>`에 HTML을 보내 기존 Doc을 덮어쓴다                                           |

마지막 단계가 핵심이다. 새 파일을 만들면 링크가 매번 바뀐다. `.github/google-docs.json`에 문서마다 Doc ID를 고정해 두고 그 파일의 내용만 바꾸니, 공유 링크가 그대로 남는다. Drive는 `text/html`로 올린 본문을 Google Docs 형식으로 변환해 준다.

인증에 키 파일이 없다는 점도 일부러 고른 것이다. 서비스 계정 키(JSON)를 저장소 시크릿에 넣으면 그 키가 새는 순간 Drive 쓰기 권한이 같이 샌다. OIDC는 GitHub이 실행마다 짧게 사는 토큰을 발급하고, Google 쪽이 "이 레포의 워크플로에서 온 토큰"인지 확인한 뒤 서비스 계정 토큰으로 바꿔 준다. 허용 범위는 `seren-wib`가 가진 레포로 묶었다.

## 3. 올리고 나서 고친 세 가지

첫 실행 뒤 Doc을 열어 보니 그림이 문제였다. 같은 날 PR 세 개로 고쳤다.

![그림 크기 맞추기 다이어그램. Google Docs 본문 영역은 가로 624px, 세로 864px이다. 1600px 폭 PNG는 #65 전에는 본문을 넘쳤다. #65는 폭만 624px로 줄였고, 세로로 긴 그림은 여전히 쪽을 넘었다. #69는 scale = min(624/w, 864/h, 1)로 두 방향을 다 맞춘다](/static/images/coffee-shop-02-docs-sync/image-fit.svg)

| PR  | 증상                                                             | 고친 것                                                                                      |
| --- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| #65 | 1600px 폭 PNG가 본문을 넘쳤다                                    | PNG 헤더(IHDR)에서 실제 크기를 읽어 `width=min(w, 624)`와 비율에 맞는 `height`를 px로 박는다 |
| #66 | 실행 44027929044에서 SDD의 Mermaid PNG 15장 한글이 전부 네모     | Mermaid 렌더 전에 `fonts-noto-cjk` 설치. draw.io SVG 15장은 원래 멀쩡했다                    |
| #69 | 세로로 긴 `create_order` 흐름도가 468×1168pt로 648pt 본문을 넘음 | 높이도 864px로 제한: `scale = min(624/w, 864/h, 1)`                                          |

#65에서 `%` 폭을 쓰지 않은 이유가 있다. Google Docs는 HTML을 가져올 때 `%` 폭과 `max-width`를 무시한다. px만 먹는다. 그래서 그림마다 실제 픽셀 크기를 알아야 했고, PNG 파일 앞 24바이트 안에 있는 IHDR 청크에서 가로·세로를 읽었다.

#69의 크기 계산은 스크립트 테스트 3개로 확인했다. 1248×400은 624×200, 600×2000은 259×864, 300×100은 그대로 300×100이다. 이 스크립트는 다른 프로젝트에서도 쓰려고 dotfiles의 project-docs 스킬에 원본을 두고, 레포에는 그 사본을 넣었다. #65, #66, #69 본문에 사본을 뜬 dotfiles 커밋이 적혀 있다.

### 워크플로 파일은 경로 필터 밖

#66은 워크플로 파일 자체를 고쳤는데, `docs-sync.yml`은 트리거 경로(`paths`)에 없다. #69가 바꾼 `.github/scripts/build-docs.mjs`도 마찬가지다. 그래서 두 PR 다 머지만으로는 다시 돌지 않았고, 머지 직후 한 번씩 수동 실행(`workflow_dispatch`)으로 돌렸다. 아래 표의 수동 실행 2회가 그것이다.

## 5. 이 구조로 안 되는 것

과제 제출본은 이 동기화 Doc과 따로 만들었다. 제출본에는 표지, 쪽 나누기, 그림 앞 제목을 다음 쪽으로 넘기지 않는 설정이 필요한데, HTML 업로드로는 쪽 나누기 CSS가 무시된다. 그래서 최종 제출본(SRS 86쪽, 설계 명세서 129쪽)은 같은 Markdown에서 따로 빌드하고 Docs API로 쪽 나누기를 넣었다. 동기화 Doc은 "지금 `main`이 무엇을 말하는가"를 보는 용도로 남겼다.

## 용어

| ------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| GitHub Actions                                         | GitHub 레포 이벤트(push, PR)에 맞춰 작업을 돌리는 CI 서비스                                |

| Workload Identity Federation                           | 외부 OIDC 토큰을 받아 Google 서비스 계정 토큰으로 바꿔 주는 Google Cloud 기능              |
| 서비스 계정                                            | 사람이 아니라 프로그램이 쓰는 Google 계정                                                  |
| [시크릿](/kr/blog/dev/devops/devops-00-basics/#시크릿) | 저장소에 넣어 두고 워크플로가 읽는 비밀 값. 이 워크플로는 하나도 쓰지 않는다               |
| Mermaid                                                | 텍스트로 다이어그램을 그리는 문법. `mmdc`가 이미지로 렌더한다                              |
| IHDR                                                   | PNG 파일의 첫 청크. 가로·세로 픽셀 수가 들어 있다                                          |
| `concurrency`                                          | 같은 그룹의 실행을 하나만 돌게 하는 워크플로 설정. `cancel-in-progress`면 앞 실행을 끊는다 |
