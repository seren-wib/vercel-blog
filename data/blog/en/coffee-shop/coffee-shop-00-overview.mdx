> This is the first post of a series on `coffee-shop`, the coffee bean shop built as the term project of a Software Engineering course. It is written so that someone new to the project gets the what, why and how from this post alone. The six posts after it follow the repository's commit history part by part. Claude Code wrote this series from the commits, pull requests and work notes.

## 1. What we built

A small online shop that sells coffee beans. Customers pick beans, choose a size and grind, put them in a cart, order, pay and track the delivery. Admins manage beans and stock and move orders through preparing, shipping and cancellation.

| Who      | What they can do                                                          |
| -------- | ------------------------------------------------------------------------- |
| Guest    | Bean list and detail, search and filters, sign-up, login                  |
| Member   | Cart, order, payment, order list and cancel, delivery tracking, addresses |
| Admin    | Create and edit beans, options and stock, stop sales, handle orders       |
| Operator | Install the server, deploy, create the admin account, check backups       |

Payments run in Toss Payments **test mode**. No real money moves. The repository is public: [seren-wib/coffee-shop](https://github.com/seren-wib/coffee-shop).

## 2. Why so much writing first

The course is Software Engineering, so the documents are graded more than the code. By the syllabus, the requirements specification (SRS) and the design description (SDD) are 10% each. That is why the first two months of the project were almost all documents.

In building terms, the first two months were drawing the blueprints and getting them reviewed, and the last ten days were construction.

![Project timeline diagram. Sep 15 repository created, Sep 22 to Oct 11 HW1 requirement documents, Nov 6 to 9 HW2 design documents, Nov 17 documents restructured and docs-sync, Nov 19 backend implementation, Nov 23 frontend, Nov 27 deployment and CD, Nov 28 SDD feedback applied](/static/images/coffee-shop-00-overview/timeline.svg)

The blueprints are the SRS and SDD, the reviews are the assignments (HW1, HW2) and the professor's feedback, and construction is the implementation pull requests. The analogy stops here.

## 3. How we built it

The structure is simple. The React screens in the browser call a Django REST API, and the data lives in one SQLite file. Production is one AWS EC2 instance with Cloudflare in front.

![System diagram. The React SPA in the browser goes through the Cloudflare proxy to nginx on EC2; nginx splits static files from /api/, which goes to gunicorn and Django. Django writes to a SQLite file and calls the Toss Payments API to confirm and cancel payments. The browser opens the payment window itself](/static/images/coffee-shop-00-overview/architecture.svg)

| Area       | Choice                                     | Reason                                                                                                      |
| ---------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| Backend    | Django 6.1, Django REST Framework          | ORM, migrations and auth come built in, which shrinks the work; the test runner is built in too             |
| DB         | SQLite (WAL, IMMEDIATE transactions)       | One server and only demo users, so no reason for a separate DB server. Concurrent orders checked by a spike |
| Frontend   | React 19, Vite 8, Tailwind CSS 4           | An SPA with 16 screens. The Vite dev server proxies `/api` to Django, so local setup is one line            |
| Payments   | Toss Payments window SDK 2.10.0, test keys | Korean test payments work with just a sign-up                                                               |
| Operations | EC2 t3.micro, nginx, gunicorn, systemd     | About $14.96 a month (estimate, SPMP 4.1). Only one server to look after                                    |
| Automation | GitHub Actions (ci, docs-sync, deploy)     | Reaches Google and AWS through OIDC with no secrets                                                         |
