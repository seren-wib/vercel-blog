## 1. 관례와 표준

비유하면 관례는 "다들 이 길로 다닌다"이고, 표준은 그 길을 지도에 공식으로 그려 넣은 것이다.

![관례와 표준: 널리 쓰이는 방식인 convention, 기관이 번호를 붙여 발행한 standard](/static/images/project-docs-03-standards/convention-vs-standard.svg)

_관례와 표준: 널리 쓰이는 방식인 convention, 기관이 번호를 붙여 발행한 standard_

용어로는 둘이 다르다.

- **convention(관례)**: 누가 공식으로 정하지 않아도 업계에서 널리 쓰는 방식. 요구사항에 `FR`·`NFR` 번호를 붙이는 것, ADR을 파일 하나씩 두는 것, 파일 이름을 kebab-case로 쓰는 것이 여기에 든다. 사실상 모두가 따르는 관례는 **de facto standard(사실상 표준)**라고도 부른다.
- **standard(표준)**: IEEE, ISO 같은 기관이 번호를 붙여 발행한 문서. 절 구성, 용어, 꼭 들어가야 할 항목이 정해져 있다. IEEE 1016, ISO/IEC/IEEE 29148이 그 예다.

내 기록에는 "관례"라는 말만 나온다. 문서 이름도, 결정 기록 자리도, 요구사항 번호도 관례대로 하자는 것이었다. 반면 문서의 절 구성은 처음부터 표준을 참고했다. 그래서 이 연재에서는 둘을 구분해서 쓴다. 이름과 표기는 관례, 문서의 절 구성은 표준이다.

## 2. 관례를 따르기로 한 날

비유하면 혼자 만든 서식을 쓰다가, 남들이 오래 다듬어 온 서식으로 갈아탄 것이다.

그 전까지 내 문서 이름은 내가 붙인 것이었다. 계획서는 `plan/`, 실험 코드는 `experiments/`, 테스트와 배포는 `test-deploy.md` 한 파일이었다. 2026-11-15 밤 스킬을 쓰기 시작할 때는 본보기 문서 넷과 IEEE 표준을 같이 참고해서, 첫 초안은 문서 넷에 표준 번호를 붙인 모양이었다. 몇 시간 뒤인 16일 새벽, 이런 이름에도 `FR`·`NFR`처럼 형식이 정해진 이름이 있는지 확인했고, 나는 전부 관례적인 표기로 바꾸기로 했다.

이유는 두 가지였다. 하나는 관례에는 그렇게 된 이유가 있을 거라는 것이다. 다른 하나는 관례대로 한 번 써 봐야 뭐가 좋은지 알 수 있다는 것이다. 즉 이건 확신이 아니라 실험이었다. 그래서 범위도 정했다. 앞으로 시작하는 문서만 관례를 따르고, 이미 작업한 프로젝트는 그대로 둔다. 스킬에는 "2026-11-16 이전에 시작한 프로젝트는 원래 구조와 이름을 유지한다"는 줄로 남아 있다.

| 전               | 후                        |
| ---------------- | ------------------------- |
| `plan/`          | `spmp/`                   |
| `experiments/`   | `spikes/`                 |
| `test-deploy.md` | `stp/`, `sip/`, `smp/` 셋 |

표준이 주는 구체적인 이점, 예를 들어 제출이나 협업에서 무엇이 나아지는지를 따져 본 기록은 없다(기록 없음). 남은 이유는 위의 두 가지뿐이다.

## 3. 문서마다 붙인 표준

비유하면 서류마다 공인된 서식 번호를 하나씩 찾아 붙인 것이다.

![문서마다 붙인 표준: SPMP는 IEEE 16326, SRS는 29148, SDD는 1016, STP는 29119-3, SIP는 MIL-STD-498, SMP는 14764](/static/images/project-docs-03-standards/standards-map.svg)

_문서마다 붙인 표준: SPMP는 IEEE 16326, SRS는 29148, SDD는 1016, STP는 29119-3, SIP는 MIL-STD-498, SMP는 14764_

용어로는 단계 문서마다 **참조 표준(reference standard)**을 하나씩 정했다.

| 문서 | 표준                 | 예전 번호 | 표준에서 가져온 것                                                         |
| ---- | -------------------- | --------- | -------------------------------------------------------------------------- |
| SPMP | IEEE 16326           | IEEE 1058 | 프로젝트 식별, 범위, 일정, 비용, 조직과 위험                               |
| SRS  | ISO/IEC/IEEE 29148   | IEEE 830  | 이해관계자, 1.4 가정·제약·의존성, 요구사항 하나에 기능 하나                |
| SDD  | IEEE 1016            |           | 절마다 viewpoint 표기(context, composition, interface …), design rationale |
| STP  | ISO/IEC/IEEE 29119-3 | IEEE 829  | 테스트 전략, 계층별 테스트, 인수 기준                                      |
| SIP  | MIL-STD-498 SIP      |           | 환경, 설치 절차, 설치 테스트                                               |
| SMP  | IEEE 14764           |           | 정기 작업, 변경 요청, 운영 절차                                            |

표준을 따라 실제로 새로 생긴 절도 있다. 본보기였던 account.stairno.com의 SRS에는 "가정, 제약, 의존성" 절이 없었는데, 29148에는 있다. 그래서 SRS 1.4절로 넣었다. 요구사항이 성립하려면 무엇이 참이어야 하는지(런타임, 외부 서비스, 법적 제한)를 적는 자리다.

2026-11-17에는 29148의 **singular** 원칙을 규칙으로 옮겼다. 기능 요구사항 하나에는 기능 하나만 담는다. 보기와 수정, 추가와 삭제, 시작과 멈춤은 각각 다른 FR이다. 비기능 요구사항도 하나에 측정 조건 하나다. 그래야 SRS의 검증 열이 기능 하나만 확인한다.

SIP에 MIL-STD-498을 고른 이유는 기록에 없다. 스킬을 만들 때 표로 제시된 안을 그대로 받았다.

## 4. 양식을 미리 정한 이유

비유하면 같은 서식을 매번 새로 그리지 않고, 빈 양식지를 한 묶음 인쇄해 둔 것이다.

용어로는 **템플릿(template)**이다. 표준이 절 구성을 정해 줘도, 절 안의 표 열이나 파일 이름까지 정해 주지는 않는다. 그 부분을 에이전트가 문서마다 새로 만들면 프로젝트마다 모양이 달라질 수 있다. 그래서 스킬을 만든 날 양식을 미리 정해 두기로 했고, `TEMPLATES.md`에 파일 54개 분량의 양식이 들어갔다.

양식은 파일 이름까지 정한다. 절 번호를 앞에 둔 영어 kebab-case다.

```text
docs/specs/srs/
├── README.md
├── 1-overview.md
├── 2-domain.md
├── 3-functional/
│   ├── README.md
│   └── 1-<area>.md
├── 4-nonfunctional.md
├── 5-use-cases.md
├── 6-interfaces.md
└── 7-decisions.md
```

새 파일은 반드시 양식에서 시작한다. 그래서 coffee-shop, design-system, open-calls 세 레포 모두 설계 근거가 같은 이름의 파일 `sdd/11-rationale.md`에 있다. 2026-11-28 양식에 절이 하나 늘어 지금 양식에서는 12절이지만, 이미 있던 SDD는 번호를 다시 매기지 않고 새 절을 뒤에 붙인다. 다른 프로젝트 문서를 열어도 같은 자리에 같은 것이 있다.

Drive [\_templates 폴더](https://drive.google.com/drive/folders/1IGzofOw3S0r05xmIvWutLiGDJcKNEoIG)의 Doc 여섯 개가 이 양식을 Google Docs로 옮긴 것이다. 각 절 아래 기울임 글씨 "안내:" 줄이 그 절에 무엇을 쓰는지 알려 주고, SDD 양식에는 IEEE 1016 viewpoint가 대괄호로 붙어 있다.

## 5. 정리

| 질문                      | 답                                                                   |
| ------------------------- | -------------------------------------------------------------------- |
| 왜 관례인가               | 관례에는 이유가 있을 것이고, 써 봐야 좋은지 안다. 앞으로의 문서만    |
| 관례와 표준은 뭐가 다른가 | 관례는 널리 쓰는 방식, 표준은 기관이 발행한 문서. 절 구성은 표준에서 |
| 표준에서 실제로 온 것     | SRS 1.4 가정·제약·의존성, singular 요구사항, SDD viewpoint 표기      |

| 기록에 없는 것            | 표준의 구체적 이점, SIP에 MIL-STD-498을 고른 이유                    |

## 용어 정리

| 용어                 | 뜻                                                                 |
| -------------------- | ------------------------------------------------------------------ |
| convention           | 공식으로 정하지 않아도 널리 따르는 방식. 관례                      |
| de facto standard    | 문서는 없지만 사실상 모두가 따르는 관례                            |
| standard             | 기관이 번호를 붙여 발행한 규격 문서. 표준                          |
| IEEE 16326           | 프로젝트 관리 계획서(SPMP) 표준. 예전 IEEE 1058                    |
| ISO/IEC/IEEE 29148   | 요구사항 공학 표준. 예전 IEEE 830                                  |
| ISO/IEC/IEEE 29119-3 | 테스트 문서 표준. 예전 IEEE 829                                    |
| MIL-STD-498          | 미 국방부의 소프트웨어 개발 문서 표준. SIP 양식이 들어 있다        |
| IEEE 14764           | 소프트웨어 유지보수 표준                                           |
| viewpoint            | IEEE 1016에서 설계를 보는 관점. context, composition, interface 등 |
| singular             | 요구사항 하나에 기능이나 조건 하나만 담는다는 29148의 품질 기준    |
