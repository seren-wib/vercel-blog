# 2. DB 시스템 소개와 ER 모델

## 2.1 DB 시스템 소개

### 2.1.1 데이터베이스 시스템이란?

**Database(DB)**: 서로 관련 있는 데이터를 논리적으로 일관되게 모아놓은 것

**DBMS**: DB를 정의·구축·조작·공유하는 소프트웨어

- 예: Oracle, MySQL, SQLite

**Database System**: DB + DBMS

### 2.1.2 데이터베이스 시스템을 왜 쓰나?

**예시**: 메시지 앱 데이터(친구, 메시지)를 텍스트 파일에 쉼표로 구분해 저장하면 생기는 문제

**Data Integrity(무결성)**: 메시지 길이 제한, 친구 중복 입력, 동명이인 구분이 안 됨

**Data Management(관리)**: 특정 메시지를 빨리 못 찾음, 여러 사용자가 동시에 읽고 쓰면 꼬임

**Data Durability(지속성)**: 쓰는 도중 장애 나면 파일이 깨지고 복구 방법이 없음

- 이 세 문제를 2.1.4 장점이 하나씩 해결

### 2.1.3 DB 시스템의 특징

**1) Self-describing nature(자기 서술성)**: DB 안에 데이터뿐 아니라 메타데이터(구조·제약조건 정의)도 같이 저장

- 메타데이터 저장 위치: DBMS 카탈로그

**2) Data abstraction(데이터 추상화)**: 프로그램은 논리적 표현만 보고 물리적 저장 구조는 모름

- 저장 구조가 바뀌어도 프로그램은 안 바뀜 → program-data independence

**3) Support of multiple views(다중 뷰 지원)**: 사용자마다 다른 모습으로 데이터를 보여줌

- **View**: DB에서 파생된 가상 데이터, 실제로 저장돼 있지 않음

**4) Sharing of data & multiuser transaction processing(공유·다중 사용자 처리)**: 여러 앱 데이터를 DB 하나에 통합, 여러 사용자가 동시 접근

- 동시 접근 보장: concurrency control
- **Transaction**: 하나의 논리적 기능을 수행하는 연산들의 모음

### 2.1.4 DB 시스템의 장점

**1) Controlling redundancy(중복 제어)**: 같은 데이터를 여러 곳에 여러 번 저장하는 걸 통제

- 중복의 문제: 갱신을 여러 번 해야 함, 저장 공간 낭비, 데이터 불일치(inconsistency)
- 중복이 항상 나쁜 건 아님 (성능 위해 일부러 두기도 함)

**2) Enforcing integrity constraints(무결성 제약조건 강제)**: 데이터가 지켜야 할 조건을 DBMS가 정의하고 강제

- 예: 열마다 데이터 타입 지정

**3) Storage structures & efficient searching(저장 구조·효율적 검색)**: 디스크는 느리니까 메모리에 올려 쓰고(buffering/caching), 빨리 찾는 구조 제공

- Indexing: 보조 파일, 보통 트리 구조(B-Tree, B+Tree)

**4) Backup and recovery(백업·복구)**: 하드웨어·소프트웨어 장애에서 복구하는 기능

- Backup: 평소에 DBMS 안에서 복사본 만들어 둠
- Recovery: 장애 직전 상태로 되돌림

**5) Restricting unauthorized access(권한 없는 접근 제한)**: 사용자별 접근 권한 제어

- 요약 슬라이드에만 있음

### 2.1.5 DBMS를 쓰지 않는 경우

**DBMS의 오버헤드**: 초기 투자(하드웨어·소프트웨어·교육), 범용성 자체의 비용, 보안·동시성 제어·복구·무결성 기능의 비용

**맞춤 저장소가 나은 경우**

- 단순하고 잘 정의돼 있고 바뀔 일 없는 앱
- 엄격한 실시간(real-time) 요구를 DBMS로 못 맞출 때
- 저장 공간이 부족한 임베디드 시스템
- 다중 사용자 접근이 없을 때

## 2.2 DB 시스템 아키텍처

**추상화를 어떻게 하는지**

### 2.2.1 데이터 모델

**데이터 추상화**: 데이터 이해에 필요한 특징은 드러내고, 저장·구성 세부는 감추는 것

- 사용자마다 원하는 수준으로 데이터를 볼 수 있음

**데이터 모델**: DB 구조를 설명하는 개념들의 집합 (추상화를 위한 도구)

- 포함: 데이터 타입·관계·제약조건, 조회·갱신 기본 연산

| 모델                 | 수준       | 눈높이                                 | 쓰는 개념                                                 |
| -------------------- | ---------- | -------------------------------------- | --------------------------------------------------------- |
| **Conceptual**       | high-level | 사용자가 데이터를 인식하는 방식        | Entity, Attribute, Relationship                           |
| **Representational** | 중간       | 사용자도 이해하고 저장 방식과도 가까움 | relation schema, relation state, attribute, tuple, domain |
| **Physical**         | low-level  | 컴퓨터 전문가용                        | record format, ordering, access path                      |

- Conceptual 설계 전에 요구사항 분석 필요
- Representational 모델을 상용 DBMS 대부분이 사용

**예시 (학생 DB)**

- Conceptual: Entity = 학생, 수업 / Attribute = 학번, 이름 / Relationship = 학생이 수업을 수강
- Representational: 아래 그림
- Physical: STUDENT 레코드를 학번 순으로 디스크에 저장, 학번 인덱스로 접근

![Representational 모델 개념을 STUDENT 테이블에 표시](/static/images/database-systems-ch2-db-systems-er-model/representational-model.svg)

### 2.2.2 3단계 스키마 구조

**목표**: 사용자 프로그램을 물리적 DB에서 분리 (프로그램과 데이터의 독립)

| 단계                | 스키마가 기술하는 것                                              | 쓰는 데이터 모델 |
| ------------------- | ----------------------------------------------------------------- | ---------------- |
| **External (View)** | 특정 사용자 그룹이 관심 있는 부분만, 나머지는 숨김                |                  |
| **Conceptual**      | DB 전체의 논리적 구조 (entity, 데이터 타입, 관계, 연산, 제약조건) | Representational |
| **Internal**        | 물리적 저장 구조, 접근 경로                                       | Physical         |

- 주의: Conceptual **level**은 Conceptual 모델이 아니라 **Representational** 모델로 기술
- External 스키마는 여러 개, Conceptual·Internal 스키마는 하나씩

**Mapping**: 단계 사이에서 요청과 결과를 변환하는 것

- 실제 데이터는 물리 단계에만 저장
- 상위 스키마로 들어온 요청을 DBMS가 하위 스키마 요청으로 변환

### 2.2.3 데이터 독립성

**데이터 독립성**: 한 단계의 스키마를 바꿔도 바로 위 단계의 스키마는 안 바꿔도 되는 능력

- 2.2.2에서 3층으로 쌓은 이유. 층 사이 mapping만 고치면 위층은 그대로

|              | 바꾸는 층         | 안 바뀌는 층                   | 예                            |
| ------------ | ----------------- | ------------------------------ | ----------------------------- |
| **Logical**  | Conceptual 스키마 | External 스키마, 응용 프로그램 | 테이블에 열 추가, 테이블 분리 |
| **Physical** | Internal 스키마   | Conceptual (+ External)        | 인덱스 교체, 파일 구조 변경   |

- 둘 다 결과는 같음: 외부 스키마를 쓰는 기존 응용 프로그램을 다시 안 짜도 됨
- 이름은 "바꾸는 층" 기준. 테이블 건드리면 Logical, 디스크 건드리면 Physical

**중요한 이유**: DBMS의 가장 중요한 특징 중 하나, 기존 응용 프로그램의 유지보수 오버헤드를 크게 줄임

![3단계 스키마 구조와 데이터 모델·mapping·데이터 독립성의 관계](/static/images/database-systems-ch2-db-systems-er-model/three-schema-architecture.svg)

## 2.3 개체-관계(ER) 모델

### 2.3.1 데이터베이스 설계 과정

**1단계 요구사항 수집·분석**: DB를 쓸 사용자들의 데이터 요구를 모으고 분석

- 결과물: 사용자 요구사항 상세 목록

**2단계 개념적 설계**: 데이터 모델을 고르고 요구사항을 개념 스키마로 변환

- ER 다이어그램 그리는 단계 (**2강 전체가 여기**)

**3단계 구현**: 개념 스키마를 바탕으로 DB 구축

- 논리적 설계: DB 스키마(테이블) / 물리적 설계: 물리적 배치

![DB 설계 과정 4단계와 각 단계의 데이터 모델·결과물](/static/images/database-systems-ch2-db-systems-er-model/db-design-process.svg)

**COMPANY 요구사항** (이 PDF 끝까지 쓰는 예제)

- Department: 고유한 이름, 고유한 번호, 위치(여러 개), 관리자, 관리자 시작일
- Project: 고유한 이름, 고유한 번호, 위치 하나, 관리하는 부서
- Employee: 이름, SSN, 주소, 급여, 성별, 생년월일, 참여 프로젝트들
- Dependent: 직원의 부양가족. 이름, 성별, 생년월일, 직원과의 관계
- "고유한" → key, "여러 개" → multivalued, "하나" → cardinality로 바뀜

**ER 모델**: 데이터를 entity와 relationship의 모음으로 기술, ER 다이어그램으로 그림

- Entity: 다른 것과 구별되는 사물이나 객체 / Relationship: 여러 entity 사이의 연관

**좋은 설계 기준**: Redundancy(정보 반복) 없음, Incompleteness(표현 못 하는 데이터) 없음

### 2.3.2 개체와 속성

**Entity(개체)**: 실세계에서 독립적으로 존재하는 사물이나 객체

- 물리적 존재: 사람, 차, 학생 / 개념적 존재: 회사, 부서, 프로젝트

**Attribute(속성)**: entity를 설명하는 특정 성질

- 예: 학생의 이름, 나이, 주소, 성별, 전화번호, 생년월일

| 축  | 종류               | 뜻                              | 예                                    |
| --- | ------------------ | ------------------------------- | ------------------------------------- |
| 1   | **Composite**      | 더 작은 부분으로 쪼개짐 (계층)  | Address = 도로명 + 시 + 주 + 우편번호 |
|     | **Simple(atomic)** | 더 못 쪼갬                      | 시, 우편번호                          |
| 2   | **Single-valued**  | entity 하나에 값 하나           | 나이, 성별, SSN                       |
|     | **Multivalued**    | entity 하나에 값 여러 개        | 전화번호들, 학위들                    |
| 3   | **Stored**         | 실제로 저장                     | 생년월일                              |
|     | **Derived**        | 저장 안 하고 다른 속성에서 계산 | 나이 (생년월일에서)                   |

- 세 축은 독립. 한 속성이 composite + single-valued + stored일 수 있음

**Entity Type**: 이름과 속성으로 기술되는 틀 / **Entity Set**: 같은 속성 집합을 가진 entity들의 집합

- relation schema(틀) : relation state(내용물) 관계와 같음

**Key Attribute**: 값이 entity마다 다른 속성. entity를 유일하게 식별

- 예: STUDENT의 학번, PERSON의 SSN
- 속성 여러 개를 합쳐 키가 될 수 있음 (조합 값이 entity마다 달라야 함)
- 한 entity type에 키가 둘 이상 있을 수 있음

| 기호                    | 뜻                    | 설명                                                                  |
| ----------------------- | --------------------- | --------------------------------------------------------------------- |
| 직사각형                | Entity                | 개체. 안에 이름을 대문자로 (EMPLOYEE)                                 |
| 타원                    | Attribute             | 보통 속성. 선으로 entity에 연결                                       |
| 타원 + 글자 밑줄        | Key attribute         | 키 속성. 값이 entity마다 달라서 식별에 씀 (Ssn)                       |
| 이중 타원 (타원 두 겹)  | Multivalued attribute | 값이 여러 개인 속성 (전화번호 여러 개)                                |
| 타원에서 가지 친 타원들 | Composite attribute   | 쪼개지는 속성. 위 타원이 전체(Name), 아래 타원들이 부분(Fname, Lname) |
| 점선 타원               | Derived attribute     | 저장 안 하고 계산하는 속성 (생년월일로 구한 Age)                      |

![ER 표기법: EMPLOYEE의 속성 종류별 기호](/static/images/database-systems-ch2-db-systems-er-model/er-attributes.svg)

**COMPANY 초기 설계** (entity 4개)

- DEPARTMENT: Name, Number, Locations, Manager, Manager_start_date. Name·Number 각각 키, Locations는 multivalued
- PROJECT: Name, Number, Location, Controlling_department. Name·Number 키
- EMPLOYEE: Name, SSN, Address, Salary, Birth_date, Sex, Department, Supervisor, Works_on. SSN 키, Name은 composite(Fname, Minit, Lname). 프로젝트별 주당 근무시간도 관리
- DEPENDENT: Employee, Dependent_name, Sex, Birth_date, Relationship
- 문제: Manager, Controlling_department, Department, Supervisor, Works_on, Employee는 다른 entity를 가리킴 → 속성이 아니라 관계로 빼야 함 (2.3.3)

### 2.3.3 관계 타입과 제약조건

![WORKS_FOR 관계: 위는 ER 다이어그램, 아래는 실제 내용물](/static/images/database-systems-ch2-db-systems-er-model/er-relationship-set.svg)

| 기호             | 뜻                                                            |
| ---------------- | ------------------------------------------------------------- |
| 사각형           | entity type                                                   |
| 마름모           | 관계 (relationship type)                                      |
| 선 두 줄         | total participation. 그쪽 entity는 전부 관계에 들어감         |
| 선 한 줄         | partial participation. 안 들어가는 entity 있어도 됨           |
| 선 위 1, N, M    | cardinality ratio. 그쪽 entity 하나가 상대편 몇 개와 묶이는지 |
| 선 위 (min, max) | 최소·최대 참여 수. 두 줄 = min 1, 한 줄 = min 0               |

**Relationship Type**: entity type 사이의 관계 하나. "직원은 부서에서 일한다" = WORKS_FOR (마름모)

**Relationship Instance**: 그 관계의 실제 사실 하나. "Kim은 Research에서 일한다" (타원 안 점 하나)

**Relationship Set**: 사실 전부의 집합 (타원 전체)

**Degree**: 관계에 끼는 entity type 수. WORKS_FOR는 2 (binary). 마름모는 안 셈

**Role Name**: 관계에서 맡는 역할 이름. worker / employer. recursive일 때만 필수

**Recursive Relationship**: 같은 entity type이 양쪽에 다 들어감. SUPERVISION (EMPLOYEE–EMPLOYEE), supervisor / supervisee로 구분

**Cardinality Ratio**: entity 하나가 상대편 최대 몇 개와 묶이는지

- 1:1 MANAGES (부서 하나에 관리자 하나) / 1:N WORKS_FOR (부서 하나에 직원 여럿) / M:N WORKS_ON (직원 여럿 ↔ 프로젝트 여럿)
- 인스턴스 그림에서 선이 여러 개 들어오는 쪽이 1

**Participation Constraint**: 관계에 꼭 들어가야 하는지

- Total: 모든 직원은 부서 소속 → EMPLOYEE–WORKS_FOR / Partial: 부서 안 맡는 직원 있음 → EMPLOYEE–MANAGES

**(min, max)**: EMPLOYEE–MANAGES (0,1) 안 맡아도 되고 맡으면 하나 / DEPARTMENT–MANAGES (1,1) 반드시 하나

**관계의 속성**: 관계에도 속성 가능 (MANAGES의 Start_date, WORKS_ON의 Hours)

- 1:1 → 아무 entity로 / 1:N → N쪽 entity로 / M:N → 못 옮김, 관계에 남김

### 2.3.4 약한 개체 타입

![약한 개체 DEPENDENT와 식별 관계 DEPENDENTS_OF](/static/images/database-systems-ch2-db-systems-er-model/er-weak-entity.svg)

**위 그림 읽는 법**

- 사각형 두 겹 = 약한 개체, 마름모 두 겹 = 식별 관계
- 약한 개체 쪽 선 두 줄 = 부양가족은 전부 주인 직원이 있음 (total)
- Dependent_name 점선 밑줄 = partial key (실선 밑줄 Ssn은 일반 키)

**Weak Entity Type(약한 개체 타입)**: 자기 속성만으로는 누가 누군지 구분 못 하는 entity type. 키 속성이 없음

- 그림에서: DEPENDENT. Kim의 딸 Minji와 Lee의 딸 Minji는 이름·생년월일이 같을 수 있음
- 주인(owner, identifying entity)에 기대서 식별 → "Kim의 Minji"
- 약한 개체는 반드시 주인 하나와 연결돼 있어야 함 (주인 없는 부양가족 없음)

**Identifying Relationship(식별 관계)**: 약한 개체와 주인을 잇는 관계

- 그림에서: DEPENDENTS_OF
- 약한 개체 쪽은 항상 total participation (두 줄)

**Partial Key(부분 키)**: 같은 주인에 딸린 약한 개체들끼리만 구분하는 속성

- 그림에서: Dependent_name. 한 직원의 부양가족 중에는 같은 이름 없음
- 예 2: COURSE–SECTION의 Section_num. 한 과목 안에서만 분반 번호가 유일
- partial key 혼자서는 식별 못 함 → 진짜 키 = 주인의 키 + partial key = (Ssn, Dependent_name)
