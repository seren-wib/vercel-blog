> 연재 3편. 프로젝트 전체 그림은 [Coffee Shop 0](/kr/blog/side-projects/coffee-shop/coffee-shop-00-overview/)에 있다. 이 글은 11월 19일 백엔드 기반 PR 여섯 개(#73, #77, #80, #83, #85, #87)를 다룬다.

## 한 줄 요약

구현 첫 코드는 기능이 아니라 실험이었다. "SQLite로 동시 주문을 버틸 수 있나"를 먼저 재서 답이 "트랜잭션 모드만 바꾸면 된다"로 나왔고, 그 값을 설정에 박았다. 그다음 CI와 브랜치 보호를 걸고, 그 위에 모델 → 인증 → 재고 → 배송지 순서로 쌓았다.

## 1. 스파이크: SQLite가 동시 주문을 버티나

설계 단계에서 제일 큰 위험은 DB였다. 서버 한 대에 SQLite 파일 하나로 가기로 했는데, SQLite는 파일 전체에 쓰기 잠금을 하나만 둔다. 재고가 1개 남은 원두에 주문 10건이 동시에 들어오면 어떻게 되는지 모르고 주문 코드를 짤 수는 없었다.

화장실이 하나뿐인 집으로 치면, DEFERRED는 일단 들어가서 문을 잠그려다 다른 사람이 먼저 잠갔으면 그대로 쫓겨나는 방식이고, IMMEDIATE는 들어가기 전에 문 앞에서 줄을 서는 방식이다.

![SQLite 트랜잭션 모드 비교 다이어그램. DEFERRED는 BEGIN 뒤 읽기로 시작했다가 쓰기 잠금으로 올라가려는 순간 다른 연결이 먼저 커밋했으면 대기 없이 SQLITE_BUSY를 받아 500이 된다. IMMEDIATE는 BEGIN 때 바로 쓰기 잠금을 요청하고, 잠금이 풀릴 때까지 timeout 20초 안에서 기다린 뒤 조건부 UPDATE로 재고를 확인해 진 쪽은 409를 받는다](/static/images/coffee-shop-03-backend-foundation/sqlite-modes.svg)

쫓겨나는 게 `SQLITE_BUSY`(`database is locked`), 줄 서기가 `BEGIN IMMEDIATE`의 쓰기 잠금 대기다. 이 비유는 여기까지만 쓴다.

스파이크 코드는 `spikes/sqlite-concurrent-order/`에 커밋했다(#73). 설계 문서의 `create_order`를 그대로 쓰고, gunicorn sync 워커 3개 앞에서 스레드 10개가 동시에 `POST /api/orders/`를 보낸다. 조건마다 10건씩 30라운드, 라운드마다 데이터를 다시 넣었다.

| 조건                    | 201 | 409 | 500                          | 재고가 틀린 라운드 | p95(로컬) |
| ----------------------- | --- | --- | ---------------------------- | ------------------ | --------- |
| IMMEDIATE, 300건        | 30  | 270 | 0                            | 0                  | 41.96 ms  |
| DEFERRED(기본값), 300건 | -   | -   | 68(30라운드 중 29라운드에서) | 0                  | 안 비교함 |

실행 환경은 WSL2 Ubuntu(논리 CPU 16개), Python 3.14.4, Django 6.1.1, gunicorn 27.0.1, SQLite 3.46.1이다. 운영 서버(t3.micro)에서는 재지 않아서 응답 시간은 로컬 값일 뿐이다.

결과에서 두 가지를 읽었다.

- **재고는 두 모드 다 맞았다.** 재고를 지키는 건 트랜잭션 모드가 아니라 `WHERE stock_quantity >= n` 조건부 UPDATE와 롤백이다. 이 설계는 그대로 간다.
- **DEFERRED의 500은 `timeout`으로 못 막는다.** 잠금 오류가 20초를 기다리지 않고 바로 왔다(서버 처리 최대 16.86 ms). 읽기로 시작한 트랜잭션이 쓰기로 올라갈 때 그 사이 다른 연결이 커밋했으면, SQLite는 기다려도 소용없다고 보고 즉시 `SQLITE_BUSY`를 돌려준다. 그래서 `transaction_mode="IMMEDIATE"`가 필수 설정이 됐다.

## 2. CI와 브랜치 보호를 먼저

기능 코드가 하나도 없을 때 CI부터 넣었다(#77). 테스트가 0개여도 형식 검사와 마이그레이션 검사는 첫 모델 PR부터 의미가 있다.

| 작업       | 단계                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------ |
| `backend`  | `black --check`, `makemigrations --check`, 메모리 SQLite 테스트, 파일 SQLite 동시성 테스트 |
| `frontend` | `prettier --check`, `oxlint`, `vitest`, `vite build`                                       |

동시성 테스트만 따로 도는 이유는 메모리 SQLite에서는 연결끼리 같은 DB를 못 보기 때문이다. 그래서 `test_settings_file.py`로 파일 DB를 쓰는 설정을 따로 뒀다. 이걸 만들다 하나 걸렸다. 테스트 러너는 탐색하면서 `test*.py` 모듈을 전부 import하는데, 이 설정 파일이 공유 `DATABASES` 딕셔너리를 그 자리에서 고쳐서 메모리 실행이 `KeyError: 'MIRROR'`로 깨졌다. `deepcopy`로 고쳤다.

CI에는 저장소 시크릿이 하나도 없다. 테스트는 `config/test_settings.py`의 가짜 값으로 돈다. 그날 바로 `main`에 브랜치 보호를 걸었다(#109에 기록).

| 설정                     | 값                      |
| ------------------------ | ----------------------- |
| 필수 검사                | `backend`, `frontend`   |
| PR 필수, 승인 수         | 필수, 0                 |
| enforce admins           | 켬(관리자도 우회 못 함) |
| force push, 삭제         | 막음                    |
| strict(최신 main 맞추기) | 꺼짐                    |

승인 0인 이유는 사람이 혼자 머지하는 구조라서다. 대신 CI 통과 없이는 아무도 못 넣는다.

## 3. 설정과 모델(#80)

모델은 HW1의 `backend/schema.sql`을 버리고 SDD 5절에서 새로 짰다(+1,623 / -590줄). SQL 파일과 Django 모델이 따로 있으면 둘 중 하나가 거짓말을 하게 된다. 제약은 전부 모델의 `Meta.constraints`로 옮겨 마이그레이션이 만들게 했다.

| 설정               | 값                                                        |
| ------------------ | --------------------------------------------------------- |
| DB                 | SQLite, `transaction_mode="IMMEDIATE"`, WAL, `timeout=20` |
| 기본 권한          | `IsAuthenticated`(공개 API만 명시적으로 연다)             |
| 응답 형식          | JSON 렌더러만                                             |
| 요청 제한          | 로그인 10회/분, 가입 20회/시간                            |
| JWT                | 액세스 30분, 리프레시 7일                                 |
| 시간대·언어        | `Asia/Seoul`, `ko-kr`                                     |
| Django 관리 사이트 | `DEBUG`일 때만 붙인다                                     |

제약 이름 몇 개만 봐도 규칙이 보인다. `uq_user_addresses_one_default`(기본 배송지는 하나), `uq_payments_order_success`(주문 하나에 성공 결제는 하나), `ck_orders_shipped_fields`(발송 상태면 송장 필드 필수). 이 PR 브랜치에서 테스트 34개가 0.87초에 통과했다.

## 4. 회원과 인증(#83)

로그인은 [JWT](/kr/blog/dev/auth/auth-00-basics/#jwt)다. 액세스 토큰 클레임에는 `user_id`와 `role`만 넣었다. 화면이 관리자 메뉴를 보여 줄지 정하는 데 그 둘이면 충분하고, 토큰에 넣은 정보는 누구나 디코드해서 볼 수 있다.

- **로그인 실패는 응답이 하나다.** 없는 이메일이든 틀린 비밀번호든 같은 401 `INVALID_CREDENTIALS` 본문을 돌려준다(NFR-7). 응답이 다르면 그 차이로 가입된 이메일을 알아낼 수 있다.
- **가입에는 개인정보 동의가 필요하다.** `privacy_agreed`가 없으면 거절하고, 동의 시각을 `privacy_agreed_at`에 남긴다(FR-58).
- **요청 제한 테스트의 함정.** `override_settings`로 제한값을 바꿔도 안 먹었다. DRF가 `THROTTLE_RATES`를 import 시점에 읽어 두기 때문이다. 테스트는 `ScopedRateThrottle.THROTTLE_RATES`를 직접 패치한다.
- **운영자 명령 `create_admin`.** 관리자 계정은 가입 API로 못 만든다. 서버에서 `manage.py create_admin --email ...`으로만 만든다.

## 5. 재고와 배송지(#85, #87)

재고 서비스는 함수 다섯 개다. `decrease_stock`, `increase_stock`, `set_stock`, `stop_sales`, `resume_sales`. 전부 조건부 UPDATE 한 문장이고, 바뀐 행이 0이면 `DomainError`를 낸다. 판매 중지(`STOPPED`) 원두는 재고가 바뀌어도 스스로 판매 중으로 돌아가지 않는다.

배송지 서비스는 "주소가 있는 회원은 기본 배송지가 정확히 하나"를 지킨다. 지키는 장치가 둘이다. 서비스가 새 기본값을 세우기 전에 옛 기본값을 먼저 지우고, 그래도 둘이 되면 부분 유니크 인덱스(`is_default`가 참인 행만 대상)가 막는다. 앞이 실수해도 DB가 막는 구조다.
