# Concepts on One Page (2.1–2.2, 3.1)

For the "explain this" questions that are neither drawing nor [SQL](glossary:sql). What to memorize is the words in the tables and the counts.

## 1. What a DB is

| Term                                            | Meaning                                                                                                                       |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **[Database](glossary:database)**               | A collection of related data                                                                                                  |
| **[DBMS](glossary:dbms)**                       | The software that creates, fills, manipulates and shares that DB. [Oracle](glossary:oracle-database), [MySQL](glossary:mysql) |
| **[Database system](glossary:database-system)** | DB + [DBMS](glossary:dbms)                                                                                                    |

**3 problems with just storing data in files** (why we use a DB)

| Problem                              | What goes wrong                                                                     |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| [Integrity](glossary:data-integrity) | No length limits, duplicate entries, can't tell apart people with the same name     |
| Management                           | Can't find specific data quickly, things get tangled when many people write at once |
| [Durability](glossary:durability)    | A failure mid-write corrupts the file and it can't be recovered                     |

## 2. 4 characteristics of a DB system

| Characteristic                                              | In one line                                                                                   | [Key](glossary:key) word                                                                 |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **[Self-describing](glossary:self-describing)**             | Stores not only the data but also its structure ([metadata](glossary:metadata)) inside the DB | [catalog](glossary:catalog)                                                              |
| **[Data abstraction](glossary:data-abstraction)**           | Programs see only the logical structure, not how it's stored on disk                          | [program-data independence](glossary:program-data-independence)                          |
| **[Multiple views](glossary:view)**                         | Shows the data differently to each user                                                       | [view](glossary:view) = virtual table that isn't stored                                  |
| **Sharing & multiuser [transaction](glossary:transaction)** | Many users use one DB at the same time                                                        | [concurrency control](glossary:concurrency-control), [transaction](glossary:transaction) |

## 3. 5 advantages of a DB system

| Advantage                                                            | In one line                                                                                                                       |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Controlling [redundancy](glossary:redundancy)**                    | Don't keep the same data in several places → update once, save space, no inconsistency. Sometimes kept on purpose for performance |
| **Enforcing [integrity constraints](glossary:integrity-constraint)** | The [DBMS](glossary:dbms) enforces the conditions data must satisfy (type, key, [FK](glossary:foreign-key))                       |
| **Storage structures & efficient searching**                         | Disks are slow, so buffers and caches; indexes ([B-tree](glossary:b-tree), [B+tree](glossary:b-tree)) to find things fast         |
| **[Backup and recovery](glossary:backup)**                           | Keep copies normally, restore to the state just before a failure                                                                  |
| **Restricting unauthorized access**                                  | Per-user privileges                                                                                                               |

**When not using a [DBMS](glossary:dbms) is better**: simple apps that don't change / strict real-time requirements / embedded systems short on space / a single user

## 4. 3 levels of data models

**Data model**: the set of concepts that describe a DB's structure. Data types, relationships, [constraints](glossary:integrity-constraint), down to basic operations

| Model                                                                 | Whose eye level                                               | Concepts used                                                                                                      | Example                           |
| --------------------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------- |
| **[Conceptual](glossary:conceptual-data-model)** (high-level)         | Users                                                         | [entity](glossary:entity), [attribute](glossary:attribute), [relationship](glossary:relationship-type)             | [ER diagram](glossary:er-diagram) |
| **[Representational](glossary:representational-data-model)** (middle) | Users can understand it, and it's close to how data is stored | [relation](glossary:relation), [tuple](glossary:tuple), [attribute](glossary:attribute), [domain](glossary:domain) | Tables. Most commercial DBMSs     |
| **[Physical](glossary:physical-data-model)** (low-level)              | Computer specialists                                          | record format, ordering, [access path](glossary:access-path)                                                       | Disk layout, indexes              |

## 5. Three-schema architecture

**Goal**: separate application programs from the physical DB

| Level                                                            | What it describes                                                                                                | How many | Model used                                               |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------- | -------------------------------------------------------- |
| **[External](glossary:external-schema) ([view](glossary:view))** | Only the part that user group sees                                                                               | Many     |                                                          |
| **[Conceptual](glossary:conceptual-schema)**                     | Logical structure of the whole DB (entities, types, relationships, [constraints](glossary:integrity-constraint)) | One      | [Representational](glossary:representational-data-model) |
| **[Internal](glossary:internal-schema)**                         | Physical storage structure, access paths                                                                         | One      | [Physical](glossary:physical-data-model)                 |

- Trap: the [Conceptual](glossary:conceptual-schema) **level** is written with the **[Representational](glossary:representational-data-model)** model, not the [Conceptual](glossary:conceptual-data-model) model
- **[Mapping](glossary:schema-mapping)**: converts requests and results between levels. Data exists only at the [Internal](glossary:internal-schema) level; the [DBMS](glossary:dbms) turns requests coming in from above into requests for the level below

## 6. 2 kinds of data independence

**[Data independence](glossary:data-independence)**: changing one level's schema doesn't require changing the level right above it. The reason for stacking 3 levels. Only the [mapping](glossary:schema-mapping) is fixed

|                                                     | Level changed                            | Level unaffected                                           | Example                                                          |
| --------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------- |
| **[Logical](glossary:logical-data-independence)**   | [Conceptual](glossary:conceptual-schema) | [External](glossary:external-schema), application programs | Adding a column, splitting a table                               |
| **[Physical](glossary:physical-data-independence)** | [Internal](glossary:internal-schema)     | [Conceptual](glossary:conceptual-schema)                   | Swapping an [index](glossary:index), changing the file structure |

- Named after the level that changes. Touch tables → [Logical](glossary:logical-data-independence), touch the disk → [Physical](glossary:physical-data-independence) / both end with "existing programs don't need changes"

## 7. DB design process

| Step                                              | What you do                                       | Output                            |
| ------------------------------------------------- | ------------------------------------------------- | --------------------------------- |
| 1 Requirements collection & analysis              | Gather users' data requirements                   | Requirements list                 |
| 2 [Conceptual design](glossary:conceptual-design) | Pick a model and turn it into a conceptual schema | [ER diagram](glossary:er-diagram) |
| 3 [Logical design](glossary:logical-design)       | Conceptual schema → DB schema                     | Tables                            |
| 4 [Physical design](glossary:physical-design)     | Decide the storage structure                      | Files, indexes                    |

- Requirement wording → ER: "unique" = key, "several" = [multivalued](glossary:multivalued-attribute), "one" = [cardinality](glossary:cardinality)
- Good design: no Redundancy (the same information repeated), no Incompleteness (data that can't be represented)

## 8. 4 advantages of the relational model

| Advantage                                 | In one line                                       |
| ----------------------------------------- | ------------------------------------------------- |
| Simplicity                                | Flat tables are easy to understand                |
| [Data integrity](glossary:data-integrity) | Constraints keep data valid and consistent        |
| Easy data manipulation                    | Manipulate with conditions in [SQL](glossary:sql) |
| Security                                  | Authentication, privileges, encryption            |
