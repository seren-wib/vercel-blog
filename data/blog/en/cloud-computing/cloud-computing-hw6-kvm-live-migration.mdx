This homework follows the KVM labs in chapters 11 and 12 of the textbook. The first half is the basic lab: install KVM, create a Rocky Linux VM, manage it with `virsh`, and clone it. The second half is live migration: build two Rocky VMs that act as KVM hosts, then move a CirrOS VM running inside one of them to the other without stopping it.

# 0. Lab Environment

I used the same Ubuntu host as since HW2 (Ubuntu 24.04 aarch64 on UTM on an Apple M3 Mac). Because the host is aarch64, I used the aarch64 builds of the Rocky Linux ISO and the CirrOS image, and I noted under each figure where commands differ from the slides.

For live migration, instead of two VirtualBox VMs as in the slides, I created two Rocky VMs on the Ubuntu host's KVM. Each of them becomes a KVM host, and CirrOS is a VM nested one level further inside.

```text
Ubuntu host (KVM)
├─ servera Rocky 10.2   192.168.56.101   ── CirrOS ──┐   virsh migrate --live
└─ serverb Rocky 10.2   192.168.56.102   ◀───────────┘
```

To let a regular user use the bridge network, I put `allow all` in `/etc/qemu/bridge.conf` and set the setuid bit on `qemu-bridge-helper`. The libvirt connection URI was set to the user session (`qemu:///session`).

```bash
sudo mkdir -p /etc/qemu; echo "allow all" | sudo tee /etc/qemu/bridge.conf
sudo chmod u+s /usr/lib/qemu/qemu-bridge-helper
export LIBVIRT_DEFAULT_URI=qemu:///session
sudo systemctl restart libvirtd
```

## Installing a Rocky VM on KVM

```bash
virt-install --name rocky10-1 --ram 3072 --disk path=VM/instances/rocky10-1.img,size=20 \
  --vcpus 2 --cpu host-passthrough --network bridge=virbr0 --graphics none \
  --console pty,target_type=serial --location Rocky-10.2-aarch64-minimal.iso \
  --extra-args "inst.text console=ttyAMA0,115200 pci=nomsi" \
  --boot loader=/usr/share/AAVMF/AAVMF_CODE.no-secboot.fd,\
loader.readonly=yes,loader.type=pflash,loader.secure=no,\
nvram.template=/usr/share/AAVMF/AAVMF_VARS.fd \
  --osinfo detect=on,require=off
```

Compared with the command on slide 8, four things changed because of aarch64.

- The ISO is the aarch64 build.
- The serial console is `ttyAMA0` instead of `ttyS0`.
- MSI interrupts are not delivered under nested virtualization, so I added `pci=nomsi`.
- The default UEFI firmware (Secure Boot) won't run the installed GRUB, so I specified firmware without Secure Boot with `--boot`.

The last two are settings I found in HW2 while fixing the [Rocky boot hang under nested virtualization](/en/blog/cloud-computing/cloud-computing-hw2-kvm-vm-cluster/#appendix-rocky-boot-hang-under-nested-virtualization). I split the `--boot` value over three lines with `\` so the paths don't break in the middle. The continuation lines are not indented, because the shell would otherwise split the option value at the spaces.

## Cloning with KVM

Cloning is done while the original is shut off. `virt-clone` copies the disk image and the UEFI variable file (`_VARS.fd`) and creates a new definition.

```bash

virsh undefine rocky10-2 --nvram
```

## Ch11-5. hellocloud.c and the Virtual Memory Layout

> Write and run hellocloud.c, and use pmap and similar tools to draw the layout of its virtual memory.

I made one variable for each memory region: an initialized global, an uninitialized global, a string constant, a local variable and a malloc block. The program prints their addresses and waits for Enter, and while it waits I checked the layout from another terminal with `pmap` and `/proc/<pid>/maps`.

```c:hellocloud.c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int g_init = 2026;          /* .data : initialized global */
int g_uninit;               /* .bss  : uninitialized global */
const char *msg = "Hello, Cloud!";   /* string literal goes in .rodata */

int main(void)
{
    int local = 1;                          /* stack */
    char *heap = malloc(4096);              /* heap (4 KiB, brk area) */

    printf("%s  pid=%d\n", msg, getpid());
    printf("text   (main)     : %p\n", (void *)main);
    printf("rodata (msg)      : %p\n", (void *)msg);
    printf("data   (g_init)   : %p\n", (void *)&g_init);
    printf("bss    (g_uninit) : %p\n", (void *)&g_uninit);
    printf("heap   (malloc)   : %p\n", (void *)heap);
    printf("libc   (printf)   : %p\n", (void *)printf);
    printf("stack  (local)    : %p\n", (void *)&local);
    printf("press Enter to exit...\n");
    getchar();
    free(heap);
    return 0;
}
```

![Virtual memory layout](/static/images/cloud-computing-hw6-kvm-live-migration/38.webp)

_Virtual memory layout of hellocloud (higher addresses at the top)_

- `main` (0x…909d8) and the string `msg` (0x…90b38) sit in the executable's first mapping (r-x). Code and read-only data landed on the same page.
- `g_init` (.data) and `g_uninit` (.bss) sit next to each other on one page of the executable's writable mapping (rw-). The r-- page below it is the region made read-only after relocation (RELRO).
- `malloc(4096)` came from the [heap] (132K) right above the executable. The heap grows toward higher addresses with brk. A request of 128 KiB or more gets its own mapping in the mmap area instead of the heap.
- `printf` is in the libc.so.6 code in the mmap area, and the dynamic linker ld-linux-aarch64.so.1 and the kernel-provided [vvar]·[vdso] are in this area too.
- The local variable `local` is in the [stack] (132K) at the top of the user address space, and the stack grows toward lower addresses.
- ASLR changes the addresses on every run, but the order and permissions of the regions stay the same.

## Ch11-9. Memory Ballooning

> Research the memory ballooning technique and explain it.

Memory ballooning is a technique that lets the hypervisor reclaim memory from a running virtual machine or give it back. A balloon driver lives inside the guest OS (`virtio_balloon` on KVM). The hypervisor tells the driver a target size, and the driver inflates or deflates a balloon inside the guest's memory.

- **Why it is needed**: the hypervisor cannot tell which of the guest's pages are actually in use (the semantic gap). If the hypervisor picks guest pages and swaps them out itself when host memory runs low, it may evict pages the guest kernel uses often, and performance can drop sharply. Ballooning lets the guest OS choose which pages to give up.
- **Reclaim (inflate)**: when the hypervisor lowers the target size, the balloon driver allocates pages from the guest kernel, holds on to them and reports their physical page numbers to the hypervisor. From the guest's point of view the driver is using that memory, so no other process touches those pages. The hypervisor can then hand the pages to another virtual machine. If the guest has no free memory, the guest OS drops caches or pages out to its own swap by itself.
- **Return (deflate)**: when the target size goes back up, the driver releases the pages it held back to the guest kernel, and the guest uses that memory again.
- **Effect**: memory size can change without stopping the virtual machine, so memory overcommit (the memory given to all virtual machines adds up to more than the physical memory) can be run safely. On KVM, changing the current memory (`currentMemory`) with `virsh setmem <vm> <size>` within the configured maximum (`memory`) drives the balloon driver.
- **Limits**: the guest needs the balloon driver installed and the guest OS has to cooperate. Reclaim is tied to the guest's page reclaim speed, so it is not instant, and inflating too far can cause swapping or OOM inside the guest. Memory cannot grow past the maximum. That is why real systems use ballooning together with KSM (sharing pages with identical content) and hypervisor swapping.
