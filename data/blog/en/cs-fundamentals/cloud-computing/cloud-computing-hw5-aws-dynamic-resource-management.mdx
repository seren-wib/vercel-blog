## Setting credentials

Slides 67–70 create an [access key](glossary:access-key) for the root user. A root key has every permission on the account, down to billing and closing the account, and can't be limited by policies, so AWS itself shows a "not recommended" warning on the creation screen (checkbox 4 on slide 69). Instead I created an [IAM](glossary:iam) user cloud-hw with no console login and only the AmazonEC2FullAccess policy, and issued an [access key](glossary:access-key) for that user (use case: CLI). This key can only touch [EC2](glossary:amazon-ec2).

Entering the key, [region](glossary:region) (ap-northeast-2) and output format (json) in `aws configure` saves them to `~/.aws/credentials` and `~/.aws/config`, and both the [AWS CLI](glossary:aws-cli) and [boto3](glossary:boto3) read these files. `aws sts get-caller-identity` confirmed that the key authenticates as `user/cloud-hw`. The keys are printed masked, showing only the last four characters.

```bash
aws configure
aws configure list; aws sts get-caller-identity
```

## Security group

As on Chapter 8 slides 18–21, I created a [security group](glossary:security-group) named [HTCondor](glossary:htcondor) with two [inbound rules](glossary:inbound-rule). [SSH](glossary:ssh) (22) is open to Anywhere (0.0.0.0/0) because I connect from the [Ubuntu](glossary:ubuntu) host. The [HTCondor](glossary:htcondor) [port](glossary:port) (9618) is Anywhere on the slides, but the nodes talk to each other over private [VPC](glossary:vpc) addresses and the config has `ALLOW_WRITE = *`, so opening it to the whole internet would let anyone attach a node to the [pool](glossary:condor-pool). So I only allowed the default [VPC](glossary:vpc) range (172.31.0.0/16).

```bash
SG=$(aws ec2 create-security-group --group-name HTCondor --description "HTCondor pool (SSH + 9618)" --query GroupId --output text); echo $SG
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 22   --cidr 0.0.0.0/0     --query Return
aws ec2 authorize-security-group-ingress --group-id $SG --protocol tcp --port 9618 --cidr 172.31.0.0/16 --query Return
aws ec2 describe-security-groups --group-ids $SG --query "SecurityGroups[0].IpPermissions[].[IpProtocol,FromPort,ToPort,IpRanges[0].CidrIp]" --output table
```

## Installing and configuring HTCondor on main

I installed the [HTCondor](glossary:htcondor) 25.0 repository package ([EPEL](glossary:epel) comes along with it) and then condor (slides 16–19). `condor_config.local` is the same six lines as on the slides, with main's own private [DNS](glossary:dns) name in `CONDOR_HOST`. main is the [pool](glossary:condor-pool)'s central manager, so COLLECTOR and [NEGOTIATOR](glossary:htcondor-negotiator) run; it accepts job submissions, so [SCHEDD](glossary:htcondor-schedd) runs; and it also runs jobs, so [STARTD](glossary:htcondor-startd) runs too. Once the service started, `condor_status` showed one main slot, and I enabled the service so it comes up after reboots.

```bash
sudo su -
dnf install -y https://research.cs.wisc.edu/htcondor/repo/25.0/htcondor-release-current.el10.noarch.rpm
dnf install -y condor
cd /etc/condor/config.d
printf "%s\n" "ALLOW_WRITE = *" "CONDOR_HOST = $(hostname)" "DAEMON_LIST = MASTER, SCHEDD, STARTD, COLLECTOR, NEGOTIATOR" \
  "SEC_PASSWORD_FILE = /etc/condor/passwords.d/POOL" "SEC_DEFAULT_AUTHENTICATION_METHODS = PASSWORD,FS" \
  "SEC_DAEMON_AUTHENTICATION_METHODS = PASSWORD,FS" > condor_config.local
systemctl start condor; condor_status
systemctl enable condor; systemctl status condor
```

## SSH key from main to worker

To copy the [pool](glossary:condor-pool) password file from main to [worker](glossary:worker-node), I let main's rocky account log in to [worker](glossary:worker-node) with a key (slides 29–31). I generated [ed25519](glossary:ed25519) keys on both nodes (empty passphrase) and appended main's [public key](glossary:public-key) to `~/.ssh/authorized_keys` on [worker](glossary:worker-node). The first line of that file is the cloud-test key AWS put there when the instance was created. I confirmed that main can connect to [worker](glossary:worker-node) by its private [DNS](glossary:dns). The [port](glossary:port) 22 rule in the [security group](glossary:security-group) also allows connections from inside the [VPC](glossary:vpc).

```bash
ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519          # on main and worker
cat ~/.ssh/id_ed25519.pub                                   # main
echo "ssh-ed25519 AAAA... rocky@ip-172-31-12-47..." >> ~/.ssh/authorized_keys   # worker
ssh rocky@ip-172-31-11-85.ap-northeast-2.compute.internal   # main → worker
```

## Sharing the pool password and checking 2 nodes

Both nodes are configured to authenticate daemons with PASSWORD, so they only trust each other if they hold the same [pool](glossary:condor-pool) password file (slides 32–35). Running `condor_store_cred add -c` on main creates the [pool](glossary:condor-pool) password at `/etc/condor/passwords.d/POOL` (readable by root only). I typed a random string as the password and didn't record it. I copied the file as rocky-owned, sent it to `/tmp` on [worker](glossary:worker-node) with [scp](glossary:scp), moved it to the same location on [worker](glossary:worker-node) and set permissions back to 600 and root. After confirming both nodes had the same [md5](glossary:md5) and restarting condor, `condor_status` showed 2 nodes (the problem I hit along the way is Problem 1 below).

```bash
condor_store_cred add -c                                   # main, root
cp /etc/condor/passwords.d/POOL /home/rocky/POOL; chown rocky:rocky /home/rocky/POOL; exit
scp /home/rocky/POOL rocky@ip-172-31-11-85.ap-northeast-2.compute.internal:/tmp/ && rm /home/rocky/POOL
mkdir -p /etc/condor/passwords.d && mv /tmp/POOL /etc/condor/passwords.d/          # worker, root
chmod 600 /etc/condor/passwords.d/POOL; chown root:root /etc/condor/passwords.d/POOL
md5sum /etc/condor/passwords.d/POOL; systemctl restart condor                    # both
condor_status                                                                    # main
```

# 3. The dynamic management program

## Written with Python boto3

Instead of [Java](glossary:java), I wrote it with [boto3](glossary:boto3), the AWS [SDK](glossary:sdk) for [Python](glossary:python) (`~/cloud_project/aws_control.py`, 156 lines). The textbook's [Java](glossary:java) [SDK](glossary:sdk) v1 (1.11.x) reached end of support at the end of 2025, and [boto3](glossary:boto3) installs as an [Ubuntu](glossary:ubuntu) package (`python3-boto3`), so there's no [JDK](glossary:jdk) or library bundle to download. The menu and output format match the screens on slides 42–63. The program creates one `boto3.client("ec2")` at startup and reads [credentials](glossary:credential) and [region](glossary:region) from the `~/.aws` files set up earlier. The [EC2](glossary:amazon-ec2) API each menu calls:

| Menu                                    | [boto3](glossary:boto3) call ([EC2](glossary:amazon-ec2) API) | What it does                                                                                                                                                 |
| --------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. list instance                        | `describe_instances` ([paginator](glossary:pagination))       | ID, Name tag, type, state and [private IP](glossary:private-ip-address) of every instance                                                                    |
| 2. available zones                      | `describe_availability_zones`                                 | [Availability zone](glossary:availability-zone) IDs and names in the current [region](glossary:region), and the count                                        |
| 3. start instance                       | `start_instances`                                             | Start the instance with the given ID                                                                                                                         |
| 4. available [regions](glossary:region) | `describe_regions`                                            | [Regions](glossary:region) the account can use and their [EC2](glossary:amazon-ec2) endpoints                                                                |
| 5. stop instance                        | `stop_instances`                                              | Stop the instance with the given ID                                                                                                                          |
| 6. create instance                      | `run_instances`                                               | Create one t3.small, cloud-test, [HTCondor](glossary:htcondor) instance from the given [AMI](glossary:ami), Name tag htcondor-[worker](glossary:worker-node) |
| 7. reboot instance                      | `reboot_instances`                                            | Reboot the instance with the given ID                                                                                                                        |
| 8. list images                          | `describe_images(Owners=["self"])`                            | [AMIs](glossary:ami) created by my account                                                                                                                   |
| 99. quit                                | —                                                             | Exit                                                                                                                                                         |

API errors (no permission, bad ID and so on) are caught as `ClientError`, which prints just the message and goes back to the menu, and non-numeric input prints `concentration!` and is ignored. The [key pair](glossary:key-pair), [security group](glossary:security-group) and type for create can be changed with [environment variables](glossary:environment-variable). The full source:

```python:aws_control.py
#!/usr/bin/env python3
"""Amazon AWS Control Panel using SDK (boto3).

HW5 / Ch9 "AWS dynamic resource management" tool. Same menu as the
textbook's Java version (awsTest.java), written with the AWS SDK for Python.

Credentials and default region come from ~/.aws (set with `aws configure`).
Settings for "create instance" can be overridden with environment variables:
  AWS_KEY_NAME        key pair name           (default: cloud-test)
  AWS_SECURITY_GROUP  security group name     (default: HTCondor)
  AWS_INSTANCE_TYPE   instance type           (default: t3.small)
"""
import os
import sys

import boto3
from botocore.exceptions import BotoCoreError, ClientError

KEY_NAME = os.environ.get("AWS_KEY_NAME", "cloud-test")
SECURITY_GROUP = os.environ.get("AWS_SECURITY_GROUP", "HTCondor")
```

## Compared with the Java SDK

[boto3](glossary:boto3) exposes the same [EC2](glossary:amazon-ec2) API as the [Java](glossary:java) [SDK](glossary:sdk) under the same names (in snake_case), so the structure maps 1:1 to the [Java](glossary:java) program on the slides. The [Java](glossary:java) version builds a client with `AmazonEC2ClientBuilder` and passes a `DescribeInstancesRequest` object, while [boto3](glossary:boto3) is called with keyword arguments like `client.describe_instances()` and returns dictionaries. There's no compiling or classpath setup (slide 75), so running it is simpler.

## How it relates to the REST API

I didn't call the [REST API](glossary:rest-api) directly. But [boto3](glossary:boto3) and the [AWS CLI](glossary:aws-cli) send requests to [EC2](glossary:amazon-ec2)'s [HTTPS](glossary:https) API under the hood (requests like `Action=DescribeInstances` to `https://ec2.ap-northeast-2.amazonaws.com/`), and sign every request with the [access key](glossary:access-key) ([Signature Version 4](glossary:aws-signature-version-4)). That signature includes the request time, which is why requests were rejected when the [Ubuntu](glossary:ubuntu) host's clock fell behind during the lab (Problem 2 below). The endpoint list from menu 4 is the list of these API addresses.

# 5. Problems during the lab

## Problem 1. Worker missing even after matching the pool password

**Symptom**: Both nodes had the same POOL [md5](glossary:md5), but `condor_status` on main only showed main. The [worker](glossary:worker-node)'s `/var/log/condor/StartLog` had `attempt to connect to <172.31.12.47:9618> failed: Connection refused` and `TCP connection to collector ... failed`.

**Cause**: I restarted the [worker](glossary:worker-node) (with the POOL file installed) before main, so when the [worker](glossary:worker-node) first tried to register, main's collector was in the middle of restarting and refused the connection. [startd](glossary:htcondor-startd) sends again at its periodic update (every 5 minutes by default), so waiting would have worked, but until then it's not in the [pool](glossary:condor-pool).

**Fix**: Restarting main and then the [worker](glossary:worker-node) once more gave 2 nodes right away. Following the order on slide 34 (main → [worker](glossary:worker-node)) avoids this.

## Problem 2. AWS requests suddenly failing authentication

**Symptom**: Partway through the lab, aws commands on the [Ubuntu](glossary:ubuntu) host failed with `AuthFailure`, `SignatureDoesNotMatch: Signature expired: 20261027T111114Z is now earlier than 20261027T114023Z`.

**Cause**: The [Ubuntu](glossary:ubuntu) [VM](glossary:vm)'s clock was 44 minutes behind. It looks like the [VM](glossary:vm) clock stopped while the Mac was asleep. AWS rejects a request as a possible [replay attack](glossary:replay-attack) if the request time in the signature differs from server time by more than 15 minutes.

**Fix**: Re-syncing [NTP](glossary:ntp) with `sudo systemctl restart systemd-timesyncd` fixed the clock, and authentication worked right away.

## Ch8-9. The Various AMIs AWS Offers

> Research the various [AMIs](glossary:ami) offered by Amazon AWS and describe their characteristics.

An [AMI](glossary:ami) (Amazon Machine Image) is the template used to launch an instance. It consists of a [snapshot](glossary:snapshot) of the [root volume](glossary:root-volume) (the OS and installed software), launch permissions (who can use the [AMI](glossary:ami)) and the block device mapping for volumes attached to the instance. Every instance launched from the same [AMI](glossary:ami) starts in the same state, which is why in this lab I could save the [worker](glossary:worker-node) with [HTCondor](glossary:htcondor) installed as an [AMI](glossary:ami) and launch an identical [worker](glossary:worker-node) with menu 6 (create instance). [AMIs](glossary:ami) fall into four groups depending on who made them and where they're published.

| Type                                                            | What / examples                                                                                                                                                                                                                | Characteristics                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Quick Start [AMI](glossary:ami) (provided by AWS)               | [Amazon Linux](glossary:amazon-linux) 2023, [Ubuntu](glossary:ubuntu), Red Hat Enterprise Linux, SUSE, Debian, Windows Server, macOS and so on. The first tab of the console's launch screen                                   | Verified by AWS or the OS vendor, with security-patched versions published regularly. [Amazon Linux](glossary:amazon-linux) comes with the [AWS CLI](glossary:aws-cli) and SSM agent preinstalled at no extra cost. For commercial OSes like Windows and RHEL, the license fee is included in the hourly price                                                                                                               |
| AWS [Marketplace](glossary:aws-marketplace) [AMI](glossary:ami) | [AMIs](glossary:ami) sold by software companies with their product (firewall, DB, security solution and so on) installed and configured on an OS. [Rocky Linux](glossary:rocky-linux) and CIS hardened images are here too     | Requires a subscription (accepting terms) before use, and paid products add a software fee to the instance price. The product is ready to use with no installation or setup                                                                                                                                                                                                                                                  |
| Community [AMI](glossary:ami) (public [AMI](glossary:ami))      | [AMIs](glossary:ami) anyone has published publicly. The `Rocky-10-EC2-Base-10.2-20260525.0.x86_64` (ami-0e86f920feb0e6b17) used in this lab was published by the official [Rocky](glossary:rocky-linux) account (792107900819) | Usable right away by specifying the ID, with no subscription. But since anyone can publish one, you must check that the owner account is the official publisher ([AMIs](glossary:ami) with malware planted in them can be mixed in)                                                                                                                                                                                          |
| My [AMI](glossary:ami) (self-made)                              | [AMIs](glossary:ami) made from my own running or stopped instances. aws-htcondor-[worker](glossary:worker-node) (ami-055e133532793acd2) in this lab                                                                            | Private by default, and can be shared with specific accounts or made public. It clones a fully configured state, so it's used to scale out identical nodes quickly ([auto scaling](glossary:auto-scaling), or create instance here). The [EBS](glossary:ebs) [snapshot](glossary:snapshot) the [AMI](glossary:ami) references keeps costing storage, so deregister it and delete the [snapshot](glossary:snapshot) when done |

There are also [AMIs](glossary:ami) prepared for specific purposes: the [Deep Learning AMI](glossary:deep-learning-ami) with deep learning frameworks and [GPU](glossary:gpu) drivers, [ECS](glossary:amazon-ecs)/[EKS](glossary:amazon-eks) optimized [AMIs](glossary:ami) with Docker and agents for container services, and [Bottlerocket](glossary:bottlerocket), a minimal OS just for running containers.

When choosing an [AMI](glossary:ami), check these attributes as well.

- **Architecture**: [x86_64](glossary:x86-64) (Intel, AMD) or [arm64](glossary:arm64) (AWS [Graviton](glossary:aws-graviton)). It has to match the [instance type](glossary:instance-type). This time I picked the [x86_64](glossary:x86-64) [Rocky](glossary:rocky-linux) [AMI](glossary:ami) to use t3.small (unrelated to the [Ubuntu](glossary:ubuntu) host being [aarch64](glossary:arm64)).
- **Root device type**: [EBS](glossary:ebs)-backed [AMIs](glossary:ami) can be stopped and started and keep their disk contents. [Instance store](glossary:instance-store)-backed ones can't be stopped and lose their data on termination. Almost all are [EBS](glossary:ebs)-backed now.
- **[Virtualization](glossary:virtualization) type and boot mode**: Current-generation instances only support [HVM](glossary:hvm), and the boot mode (Legacy [BIOS](glossary:bios) or [UEFI](glossary:uefi)) has to be one the [instance type](glossary:instance-type) supports.
- **[Region](glossary:region)**: [AMIs](glossary:ami) exist per [region](glossary:region) with different IDs. Even for the same [Rocky](glossary:rocky-linux) 10.2 you need the Seoul [region](glossary:region)'s ID, and to use it in another [region](glossary:region) you have to copy the [AMI](glossary:ami) (copy-image).

## Ch8-13. AWS Instance Types and Their Characteristics

> What [instance types](glossary:instance-type) does AWS offer (e.g. t3.nano), and what are their characteristics?

An [instance type](glossary:instance-type) is the combination of [vCPU](glossary:vcpu) count, memory, storage and network performance assigned to an instance. The name follows the format `family + generation + (extra attributes) . size`. For example, t3.nano is the nano size of the 3rd generation of the T family ([burstable](glossary:burstable-instance) general purpose), and c7gn.xlarge is the xlarge size of the 7th generation of the C family (compute optimized) with g ([Graviton](glossary:aws-graviton) processor) and n (enhanced networking). A higher number means a newer generation with better performance for the same price.

| Category                      | Main families             | Characteristics and uses                                                                                                                                                                                                                                                                                               |
| ----------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| General purpose               | T, M, Mac                 | Balanced CPU and memory (about 4 GiB per [vCPU](glossary:vcpu)). M for general work like web servers and small to mid-size DBs. T is the [burstable](glossary:burstable-instance) type that normally runs below a baseline and briefly boosts CPU when needed; the cheapest. Mac is a dedicated host for running macOS |
| Compute optimized             | C                         | Less memory per [vCPU](glossary:vcpu) (about 2 GiB). For work that uses a lot of CPU for a long time, like batch processing, scientific computing, video encoding and game servers. Good for [HTCondor](glossary:htcondor) execute nodes                                                                               |
| Memory optimized              | R, X, z, u- (High Memory) | More memory per [vCPU](glossary:vcpu) (R about 8 GiB, X about 16 GiB or more). In-memory DBs ([Redis](glossary:redis), SAP HANA), large-scale analytics. z has a high clock frequency                                                                                                                                  |
| Accelerated computing         | P, G, Inf, Trn, F         | [GPUs](glossary:gpu) (P: ML training and [HPC](glossary:hpc), G: graphics and inference), AWS's own chips ([Inferentia](glossary:aws-inferentia): inference, [Trainium](glossary:aws-trainium): training), [FPGAs](glossary:fpga) (F). The most expensive                                                              |
| Storage optimized             | I, D, H                   | Local [NVMe](glossary:nvme) SSDs or HDDs attached directly to the instance, so disk I/O is very fast. [NoSQL](glossary:nosql) DBs, [data warehouses](glossary:data-warehouse), distributed file systems                                                                                                                |
| [HPC](glossary:hpc) optimized | Hpc                       | For high performance computing. Low-latency networking between nodes ([EFA](glossary:efa)) suits large-scale parallel computation                                                                                                                                                                                      |

The extra attributes in the middle of the name are: g AWS [Graviton](glossary:aws-graviton) (Arm) processor, a AMD processor, i Intel processor, d includes local [NVMe](glossary:nvme) storage, n enhanced network bandwidth, e extra memory or storage, flex a cheaper flexible variant. Sizes grow in the order nano &lt; micro &lt; small &lt; medium &lt; large &lt; xlarge &lt; 2xlarge …, and each step up roughly doubles the resources and price. metal is [bare metal](glossary:bare-metal), using the whole physical server without [virtualization](glossary:virtualization).

The T3 family from the question, by size:

| Type                   | [vCPU](glossary:vcpu) | Memory      | Baseline per [vCPU](glossary:vcpu) |
| ---------------------- | --------------------- | ----------- | ---------------------------------- |
| t3.nano                | 2                     | 0.5 GiB     | 5%                                 |
| t3.micro               | 2                     | 1 GiB       | 10%                                |
| t3.small               | 2                     | 2 GiB       | 20%                                |
| t3.medium              | 2                     | 4 GiB       | 20%                                |
| t3.large               | 2                     | 8 GiB       | 30%                                |
| t3.xlarge / t3.2xlarge | 4 / 8                 | 16 / 32 GiB | 40%                                |

The T family earns [CPU credits](glossary:cpu-credit) while it uses less than its baseline, and spends them to go up to 100% when it briefly needs a lot of CPU. T3 defaults to Unlimited mode, so performance holds even when credits run out, but usage above the baseline is billed extra. That makes it cheap and fine for development and test servers that are usually idle, but for computation that keeps the CPU at 100%, the C or M family is more economical. In this lab, 1 GiB was tight for running several [HTCondor](glossary:htcondor) daemons, so I used t3.small (2 [vCPU](glossary:vcpu), 2 GiB), and `condor_status` showed 1711 MB of slot memory (what's left after the OS and kernel take their share).

## Ch9-3. Running condor_status Directly from the Tool

> Modify the program tool so that it can run the condor_status command directly.

In the lab, after start, stop or create in the tool, I switched to the [SSH](glossary:ssh) window on the main instance and typed `condor_status` separately to see whether the [pool](glossary:condor-pool) had changed. To do this inside the tool, I added the menu `9. condor status` (`aws_control.py`).

`condor_status` has to run on the main node where the [Collector](glossary:htcondor-collector) runs. The [Ubuntu](glossary:ubuntu) host running the tool has no [HTCondor](glossary:htcondor), and the [security group](glossary:security-group) only opens [port](glossary:port) 9618 inside the [VPC](glossary:vpc) (172.31.0.0/16), so the [Collector](glossary:htcondor-collector) can't be queried directly from outside either. So the tool connects to main over [SSH](glossary:ssh), runs the command and prints the result.

1. **Look up the address**: Use the [EC2](glossary:amazon-ec2) API `describe_instances` to find the instance whose Name tag is htcondor-main and whose state is running. main's public [DNS](glossary:dns) name changes on every stop and start, so it's looked up each time instead of hard-coded.
2. **Run remotely**: Run `ssh -i cloud-test.pem rocky@<public DNS> condor_status` against that address ([Python](glossary:python) `subprocess`). So it doesn't hang when the address changes, unknown host keys are accepted automatically (`StrictHostKeyChecking=accept-new`), with a 10-second connect limit and a 60-second overall limit.
3. **Print the result**: Show stdout as is, and print [SSH](glossary:ssh)'s error message on failure. If main is off, print `htcondor-main is not running.`.

```python:aws_control.py
MAIN_NAME = os.environ.get("AWS_MAIN_NAME", "htcondor-main")
KEY_FILE = os.path.expanduser(os.environ.get("AWS_KEY_FILE", "~/Downloads/cloud-test.pem"))
SSH_USER = os.environ.get("AWS_SSH_USER", "rocky")

def condor_status():
    # The public DNS name changes on every stop/start, so look it up each time.
    res = ec2.describe_instances(Filters=[
        {"Name": "tag:Name", "Values": [MAIN_NAME]},
        {"Name": "instance-state-name", "Values": ["running"]},
    ])
    insts = [i for r in res["Reservations"] for i in r["Instances"]]
    if not insts:
        print(f"{MAIN_NAME} is not running.")
        return
    host = insts[0].get("PublicDnsName") or insts[0].get("PublicIpAddress")
    print(f"Running condor_status on {MAIN_NAME} ({insts[0]['InstanceId']}) ....")
    try:
        r = subprocess.run(
            ["ssh", "-i", KEY_FILE,
             "-o", "StrictHostKeyChecking=accept-new",
             "-o", "ConnectTimeout=10",
             f"{SSH_USER}@{host}", "condor_status"],
            capture_output=True, text=True, timeout=60,
        )
    except subprocess.TimeoutExpired:
        print("Error: condor_status timed out")
        return
    print(r.stdout, end="")
    if r.returncode != 0:
        print(f"Error: {r.stderr.strip()}")

ACTIONS = {
    ...
    8: (list_images, None),
    9: (condor_status, None),   # added
}
```

I also added the `9. condor status` line to the menu. Now instance operations and [pool](glossary:condor-pool) changes can be checked in a row on one screen, like "5 stop instance → 9 condor status → 3 start instance → 9 condor status". The key file location, [SSH](glossary:ssh) user and main name can be changed with [environment variables](glossary:environment-variable) (`AWS_KEY_FILE`, `AWS_SSH_USER`, `AWS_MAIN_NAME`), so it works as is for other accounts or [clusters](glossary:cluster).

Another option is sending the command without [SSH](glossary:ssh) through AWS [Systems Manager](glossary:aws-systems-manager) Run Command (`ssm.send_command`). There's no key file to carry around and [port](glossary:port) 22 can be closed, but each instance needs the SSM agent and an [IAM](glossary:iam) role attached separately (this [Rocky](glossary:rocky-linux) [AMI](glossary:ami) has no agent), and the result has to be fetched in a second call, so for this environment, which already runs on [SSH](glossary:ssh), the [SSH](glossary:ssh) approach is simpler.

## Ch9-12. Korean Cloud Providers with VM APIs

> Research Korean cloud service providers that offer APIs for controlling [virtual machines](glossary:vm) and summarize them.

Major Korean cloud providers, like AWS, let you create, start and stop [virtual machines](glossary:vm) through APIs, CLIs and [SDKs](glossary:sdk) besides the console. Authentication and API design differ by provider, but they roughly split into signing each request with an [access key](glossary:access-key) like AWS (Naver Cloud) and getting a [token](glossary:access-token) first and putting it in the request header like [OpenStack](glossary:openstack) (NHN Cloud, Kakao Cloud).

| Provider                   | [VM](glossary:vm) API                                                                                                                                                                                                                                                                                                                                     | Authentication and characteristics                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Naver Cloud Platform (NCP) | Server API (REST). For [VPC](glossary:vpc), `createServerInstances`, `startServerInstances`, `stopServerInstances`, `rebootServerInstances`, `getServerInstanceList` and so on under `/vserver/v2/`. Provides a CLI, [SDKs](glossary:sdk) for [Java](glossary:java), [Python](glossary:python) and others, and a [Terraform](glossary:terraform) provider | Requests are signed with [HmacSHA256](glossary:hmac) using the [Access Key](glossary:access-key) and Secret Key issued in the console, put in the `x-ncp-apigw-signature-v2` header and sent along with timestamp and [access key](glossary:access-key) headers. Rejected if more than 5 minutes off from server time (similar to AWS's signing). The API naming maps almost one-to-one to the [boto3](glossary:boto3) functions in this lab |
| NHN Cloud                  | [OpenStack](glossary:openstack) based. The Compute (Instance) API is compatible with [OpenStack](glossary:openstack) Nova, with a different endpoint per [region](glossary:region) (Pangyo kr1, Pyeongchon kr2 and so on)                                                                                                                                 | Set an API password separate from the account password, send the tenant ID, user and API password to the Identity API (`POST /v2.0/tokens`) to get a [token](glossary:access-token), then call with the `X-Auth-Token` header. Being [OpenStack](glossary:openstack) compatible, [OpenStack](glossary:openstack) CLI, [SDK](glossary:sdk) and [Terraform](glossary:terraform) tooling work as is                                             |
| Kakao Cloud                | [OpenStack](glossary:openstack)-based [Virtual Machine](glossary:vm) service. Provides a [REST API](glossary:rest-api), CLI and [Terraform](glossary:terraform)                                                                                                                                                                                           | Issue a per-project [access key](glossary:access-key) from the console profile (permissions set by [IAM](glossary:iam) role; the secret key can only be viewed at creation). Get a [token](glossary:access-token) from `https://iam.kakaocloud.com/identity/v3/auth/tokens` and use the value of the `X-Subject-Token` response header; it expires after 12 hours                                                                            |
| KT Cloud                   | Open API to create, start, stop and delete servers (e.g. `deployVirtualMachine`). [Python](glossary:python) [SDK](glossary:sdk) examples provided                                                                                                                                                                                                         | Requests are signed with an API key and secret key. A [CloudStack](glossary:cloudstack)-style design where creating a server specifies a template ID (OS), service offering ID (spec) and zone                                                                                                                                                                                                                                               |

In short, Korean providers also offer [VM](glossary:vm) create, start, stop, reboot and list through APIs, so the same menu can be built by swapping only the [boto3](glossary:boto3) calls in this assignment's dynamic resource management tool for each provider's API. In particular, NHN Cloud and Kakao Cloud follow the standard [OpenStack](glossary:openstack) API, so one [OpenStack](glossary:openstack) [SDK](glossary:sdk) can handle both, and Naver Cloud uses key signing similar to AWS, which makes the AWS tool's structure easy to port. For the public sector, Naver Cloud, NHN Cloud and KT Cloud all run separate public [regions](glossary:region) (CSAP certified) with the same kind of API.
