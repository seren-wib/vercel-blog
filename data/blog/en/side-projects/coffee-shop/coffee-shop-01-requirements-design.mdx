> Post 1 of the series. The whole project is in [Coffee Shop 0](/en/blog/side-projects/coffee-shop/coffee-shop-00-overview/). This post follows only the documentation pull requests from September to the end of November.

## In one paragraph

The two assignments (HW1 requirements, HW2 design) were written by three people in separate folders. On November 17, right before implementation, the scattered documents were rewritten as six stage documents and every requirement got an ID. From then on test names and pull request bodies cited those IDs, and whenever code changed the documents were fixed in the same pull request or the next one.

### Two places where documents disagreed

When several people write at once, the same fact ends up different in different documents. The two "needs confirmation" items I left in the #36 body are examples.

- **State after a rejected cancel.** The requirement said "a rejected cancel request goes back to the state before the request (`PAID` or `PREPARING`)", but the schema had no column to store that earlier state.
- **When stock goes down.** The requirements and the `create_order` algorithm took stock at order creation; the table specification took it at payment (`PAID`).

Both were decided at the October 11 meeting and applied in #41. The first went into the table specification as a `status_before_cancel` column holding the earlier state; the second became a single conditional UPDATE at order creation. In the final code the column also got the CHECK constraint `ck_orders_cancel_request_previous` (#104), and the second stayed as `decrease_stock` inside the order-creation transaction (#100). [Post 4](/en/blog/side-projects/coffee-shop/coffee-shop-04-backend-features/) has the details.

## 3. November 17: rewriting as stage documents

In library terms, the HW1 and HW2 documents were books piled on each person's desk. The rewrite put them on one shelf with catalog numbers. With a number, other documents and code can point at "that book, that page".

![Document restructure diagram. Left, the old layout: HW1 and HW2 documents spread over docs/backend, docs/frontend and docs/architecture.md. Right, the new layout: six folders spmp, srs, sdd, stp, sip, smp under docs/specs. The SRS defines DR, FR, NFR and UC IDs, and the SDD, STP, test names and pull request bodies cite them](/static/images/coffee-shop-01-requirements-design/docs-layout.svg)

The shelf is `docs/specs/`, and the catalog numbers are the requirement IDs (`DR-`, `FR-`, `NFR-`, `UC-`). The analogy stops here.

The move took four pull requests on the same day.

| PR  | Lines changed | Content                                                                                                      |
| --- | ------------- | ------------------------------------------------------------------------------------------------------------ |
| #59 | +557 / -10    | Old documents moved to `docs/old/`; SPMP, SRS, SDD, STP, SIP, SMP skeletons                                  |
| #60 | +554 / -35    | SRS sections 1~7 rewritten. DR 24, FR 57, NFR 35, UC 14. Runtime changed from "local PC" to EC2 + Cloudflare |
| #62 | +2,292 / -51  | SDD sections 1~10 rewritten. 9 components, 8 tables, 15 screens. 17 open questions in 11.2                   |
| #68 | +49 / -2,345  | `docs/old/` deleted (git history keeps it). Only the 14 wireframes moved to `docs/images/`                   |

#60 and #62 wrote their checks in the body: the SRS had 0 references to IDs outside the defined ranges, and in the SDD every FR, NFR, DR and UC was cited at least once, with 0 missing IDs.

Three reasons for the rewrite:

- **No IDs, no tracing.** To say which test checks "the order cancel requirement", the requirement needs a number.
- **The runtime changed.** HW1 said "runs on a local PC only, no external server". Deciding to demo on a production server brought new deployment and security requirements.
- **Stage documents let each implementation session read only what it needs.** Several Claude Code sessions did the implementation. Each one read `docs/specs/README.md` first and opened only its own sections.

## 4. How IDs reach the code

Once the SRS defines an ID, everything else cites it. Test function names are the firmest link.

| Requirement | Test function                                          | What it checks                                                                      |
| ----------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| NFR-8       | `test_nfr8_token_lifetimes`                            | Access token 1,800 s, refresh token 604,800 s                                       |
| NFR-9       | `test_nfr9_every_private_route_needs_token`            | Walks the whole URL conf and checks a request without a token gets 401              |
| NFR-15      | `test_nfr15_last_stock_concurrent_orders`              | Ten concurrent orders for stock 1: one success, nine 409                            |
| DR-19       | `test_dr19_disallowed_transitions_raise_invalid_state` | Every (action, state) pair outside the table gives `INVALID_STATE` (409 in the API) |

The NFR-9 test walks the URL conf itself, so routes added later are covered without editing the test (#83). Because of that, every new route from the address API (#87) and the admin APIs (#95, #104) was checked automatically.

#121 came late because of HW1's "local PC only". The SRS written on that premise had no CI/CD requirement, while CI had been running since November 19. The code went first and the requirements followed, so they were raised to requirements with IDs before the final version.

### Professor feedback: part IDs and class specification

The SDD feedback had two points: number every UI part of each screen, and keep the class and method specification separate.

- Section 6 got a `6.x.0 Whole screen` subsection and 72 part subsections (`6.1.1 SCR-01-01 search box`) across 16 screens. The 14 wireframes got 62 matching ID badges, added to the draw.io source and exported again.
- A new section 12 lists 55 public backend functions, 29 internal functions and 92 classes. A script compared it with every `def` and `class` in `backend/`: 0 missing names, 0 signature mismatches (#129).
- Sections 1~11 kept their numbers, because many other documents point at them by section number.

## 6. What I would do differently

- **IDs from the first document.** Had HW1 used IDs, the November 17 rewrite would have been a move, not a rewrite.
- **Question the runtime assumption early.** One line, "local only", left the CI/CD requirements empty until three days before the deadline.
- **Each fact in one place only.** When two documents hold the same fact, like when stock goes down, they drift apart sooner or later. After the rewrite each fact sits in one place and the others point at it by ID.

## Glossary

| Term                                                                                                                                                       | Meaning                                                                                              |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| [Domain requirement](/en/blog/cs-fundamentals/software-engineering/software-engineering-ch4-requirements-analysis/#412-domain-requirements)                | A requirement that comes from business rules. Here: option prices, shipping fee, order state changes |
| [Non-functional requirement](/en/blog/cs-fundamentals/software-engineering/software-engineering-ch4-requirements-analysis/#42-non-functional-requirements) | A requirement on quality (response time, security, concurrency) rather than a feature                |
| Use case                                                                                                                                                   | One goal a user reaches with the system, and its flow                                                |
| Wireframe                                                                                                                                                  | A drawing of a screen's layout without colors or fonts                                               |
| Sequence diagram                                                                                                                                           | Messages between objects or systems drawn along a time axis                                          |
| Traceability                                                                                                                                               | Being able to follow one requirement to its design section, code and test                            |
| CHECK constraint                                                                                                                                           | A condition the DB checks before a row is stored                                                     |
