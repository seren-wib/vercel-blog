# 2. Introduction to DB Systems and the ER Model

## 2.1 Introduction to DB Systems

### 2.1.1 What Is a Database System?

**Database (DB)**: a logically coherent collection of related data

**DBMS**: software that defines, constructs, manipulates and shares a DB

- e.g. Oracle, MySQL, SQLite

**Database System**: DB + DBMS

### 2.1.2 Why Use a Database System?

**Example**: problems that appear when a messaging app stores its data (friends, messages) in comma-separated text files

**Data Integrity**: no message length limit, duplicate friend entries, no way to tell apart friends with the same name

**Data Management**: a given message can't be found quickly, concurrent reads and writes by several users get tangled

**Data Durability**: a crash in the middle of a write corrupts the file and there is no way to recover

- Each advantage in 2.1.4 solves one of these three problems

### 2.1.3 Characteristics of DB Systems

**1) Self-describing nature**: the DB stores metadata (definitions of structure and constraints) along with the data

- Where metadata is stored: the DBMS catalog

**2) Data abstraction**: programs see only the logical representation, not the physical storage structure

- Changing the storage structure doesn't change the programs → program-data independence

**3) Support of multiple views**: different users see the data in different ways

- **View**: virtual data derived from the DB, not actually stored

**4) Sharing of data & multiuser transaction processing**: data of many applications integrated into one DB, accessed by many users at once

- Guaranteeing concurrent access: concurrency control
- **Transaction**: a collection of operations that performs one logical function

### 2.1.4 Advantages of DB Systems

**1) Controlling redundancy**: keeping the same data from being stored many times in many places

- Problems of redundancy: one update has to be done many times, wasted storage, inconsistent data (inconsistency)
- Redundancy is not always bad (sometimes added on purpose for performance)

**2) Enforcing integrity constraints**: the DBMS defines and enforces the conditions the data must satisfy

- e.g. a data type for each column

**3) Storage structures & efficient searching**: disks are slow, so data is loaded into memory (buffering/caching) and structures for fast lookup are provided

- Indexing: an auxiliary file, usually a tree structure (B-Tree, B+Tree)

**4) Backup and recovery**: the ability to recover from hardware and software failures

- Backup: keeping a copy inside the DBMS during normal operation
- Recovery: bringing the DB back to the state just before the failure

**5) Restricting unauthorized access**: per-user access control

- Only on the summary slide

### 2.1.5 When Not to Use a DBMS

**Overhead of a DBMS**: initial investment (hardware, software, training), the cost of generality itself, the cost of security, concurrency control, recovery and integrity functions

**When a custom store is better**

- Simple, well-defined applications that won't change
- Strict real-time requirements a DBMS can't meet
- Embedded systems with little storage
- No multiuser access

## 2.2 DB System Architecture

**How abstraction is done**

### 2.2.1 Data Models

**Data abstraction**: showing the features needed to understand the data and hiding the details of storage and organization

- Each user can see the data at the level they want

**Data model**: a collection of concepts that describe the structure of a DB (the tool for abstraction)

- Includes: data types, relationships, constraints, and basic operations for retrieval and update

| Model                | Level      | Point of view                                         | Concepts used                                             |
| -------------------- | ---------- | ----------------------------------------------------- | --------------------------------------------------------- |
| **Conceptual**       | high-level | How users perceive the data                           | Entity, Attribute, Relationship                           |
| **Representational** | middle     | Understandable to users and close to how data is kept | relation schema, relation state, attribute, tuple, domain |
| **Physical**         | low-level  | For computer specialists                              | record format, ordering, access path                      |

- Requirements analysis comes before conceptual design
- Most commercial DBMSs use the representational model

**Example (student DB)**

- Conceptual: Entity = student, course / Attribute = student ID, name / Relationship = a student takes a course
- Representational: see the figure below
- Physical: STUDENT records stored on disk in student ID order, accessed through a student ID index

![Representational model concepts marked on a STUDENT table](/static/images/database-systems-ch2-db-systems-er-model/representational-model.svg)

### 2.2.2 Three-Schema Architecture

**Goal**: separate user programs from the physical DB (independence between programs and data)

| Level               | What the schema describes                                                                            | Data model used  |
| ------------------- | ---------------------------------------------------------------------------------------------------- | ---------------- |
| **External (View)** | Only the part a user group cares about, the rest hidden                                              |                  |
| **Conceptual**      | The logical structure of the whole DB (entities, data types, relationships, operations, constraints) | Representational |
| **Internal**        | Physical storage structure, access paths                                                             | Physical         |

- Watch out: the conceptual **level** is described with the **representational** model, not the conceptual model
- Many external schemas, one conceptual schema and one internal schema

**Mapping**: transforming requests and results between levels

- Actual data is stored only at the physical level
- The DBMS turns a request on a higher schema into a request on the lower schema

### 2.2.3 Data Independence

**Data independence**: the ability to change the schema at one level without changing the schema at the level just above

- The reason for stacking three levels in 2.2.2. Fix only the mapping between levels and the upper level stays the same

|              | Level changed     | Level unchanged                        | Example                                  |
| ------------ | ----------------- | -------------------------------------- | ---------------------------------------- |
| **Logical**  | Conceptual schema | External schemas, application programs | Adding a column, splitting a table       |
| **Physical** | Internal schema   | Conceptual (+ external)                | Replacing an index, changing file layout |

- Same result for both: existing application programs that use the external schema don't have to be rewritten
- The name follows the level that changes. Touch tables → logical, touch the disk → physical

**Why it matters**: one of the most important features of a DBMS, greatly reduces maintenance overhead of existing application programs

## 2.3 Entity-Relationship (ER) Model

### 2.3.1 Database Design Process

**Phase 1 requirements collection and analysis**: gather and analyze the data needs of the DB's users

- Output: a detailed list of user requirements

**Phase 2 conceptual design**: choose a data model and turn the requirements into a conceptual schema

- The phase where the ER diagram is drawn (**all of lecture 2 is here**)

**Phase 3 implementation**: build the DB from the conceptual schema

- Logical design: DB schema (tables) / Physical design: physical layout

![The four steps of DB design with the data model and output of each](/static/images/database-systems-ch2-db-systems-er-model/db-design-process.svg)

**COMPANY requirements** (the example used to the end of this lecture)

- Department: unique name, unique number, locations (several), manager, manager start date
- Project: unique name, unique number, one location, controlling department
- Employee: name, SSN, address, salary, sex, birth date, projects worked on
- Dependent: an employee's dependents. Name, sex, birth date, relationship to the employee
- "unique" → key, "several" → multivalued, "one" → cardinality

**ER model**: describes data as a collection of entities and relationships, drawn as an ER diagram

- Entity: a thing or object distinguishable from others / Relationship: an association among entities

**Criteria for a good design**: no redundancy (repeated information), no incompleteness (data that can't be represented)

### 2.3.2 Entities and Attributes

**Entity**: a thing or object that exists independently in the real world

- Physical existence: person, car, student / conceptual existence: company, department, project

**Attribute**: a particular property that describes an entity

- e.g. a student's name, age, address, sex, phone number, birth date

| Axis | Kind               | Meaning                                     | Example                               |
| ---- | ------------------ | ------------------------------------------- | ------------------------------------- |
| 1    | **Composite**      | Splits into smaller parts (hierarchy)       | Address = street + city + state + zip |
|      | **Simple(atomic)** | Can't be split                              | city, zip                             |
| 2    | **Single-valued**  | One value per entity                        | age, sex, SSN                         |
|      | **Multivalued**    | Several values per entity                   | phone numbers, degrees                |
| 3    | **Stored**         | Actually stored                             | birth date                            |
|      | **Derived**        | Not stored, computed from another attribute | age (from birth date)                 |

- The three axes are independent. One attribute can be composite + single-valued + stored

**Entity Type**: the template described by a name and attributes / **Entity Set**: the set of entities that share the same attributes

- Same relationship as relation schema (template) : relation state (contents)

**Key Attribute**: an attribute whose value differs for each entity, used to identify an entity uniquely

- e.g. student ID of STUDENT, SSN of PERSON
- Several attributes can form a key together (the combined value must differ for each entity)
- An entity type can have more than one key

| Symbol                       | Meaning               | Description                                                                                    |
| ---------------------------- | --------------------- | ---------------------------------------------------------------------------------------------- |
| Rectangle                    | Entity                | An entity. Name inside in capitals (EMPLOYEE)                                                  |
| Oval                         | Attribute             | A plain attribute, connected to the entity by a line                                           |
| Oval + underlined text       | Key attribute         | Key attribute. Its value differs for each entity, so it identifies one (Ssn)                   |
| Double oval                  | Multivalued attribute | An attribute with several values (several phone numbers)                                       |
| Ovals branching from an oval | Composite attribute   | An attribute that splits. Upper oval is the whole (Name), lower ovals the parts (Fname, Lname) |
| Dashed oval                  | Derived attribute     | Computed rather than stored (Age from the birth date)                                          |

![ER notation: symbols for each kind of EMPLOYEE attribute](/static/images/database-systems-ch2-db-systems-er-model/er-attributes.svg)

**COMPANY initial design** (four entities)

- DEPARTMENT: Name, Number, Locations, Manager, Manager_start_date. Name and Number are each keys, Locations is multivalued
- PROJECT: Name, Number, Location, Controlling_department. Name and Number are keys
- EMPLOYEE: Name, SSN, Address, Salary, Birth_date, Sex, Department, Supervisor, Works_on. SSN is the key, Name is composite (Fname, Minit, Lname). Weekly hours per project are also kept
- DEPENDENT: Employee, Dependent_name, Sex, Birth_date, Relationship
- Problem: Manager, Controlling_department, Department, Supervisor, Works_on and Employee point to other entities → they should be relationships, not attributes (2.3.3)

### 2.3.3 Relationship Types and Constraints

![The WORKS_FOR relationship: ER diagram on top, actual contents below](/static/images/database-systems-ch2-db-systems-er-model/er-relationship-set.svg)

| Symbol             | Meaning                                                                          |
| ------------------ | -------------------------------------------------------------------------------- |
| Rectangle          | entity type                                                                      |
| Diamond            | relationship (relationship type)                                                 |
| Double line        | total participation. Every entity on that side takes part in the relationship    |
| Single line        | partial participation. Some entities may not take part                           |
| 1, N, M on line    | cardinality ratio. How many entities on the other side one entity can be tied to |
| (min, max) on line | Minimum and maximum participation. Double line = min 1, single line = min 0      |

**Relationship Type**: one relationship between entity types. "Employees work for departments" = WORKS_FOR (the diamond)

**Relationship Instance**: one actual fact in that relationship. "Kim works for Research" (one dot inside the oval)

**Relationship Set**: the set of all those facts (the whole oval)

**Degree**: the number of entity types in a relationship. WORKS_FOR is 2 (binary). The diamond isn't counted

**Role Name**: the name of the role played in a relationship. worker / employer. Required only for recursive relationships

**Recursive Relationship**: the same entity type appears on both sides. SUPERVISION (EMPLOYEE–EMPLOYEE), told apart by supervisor / supervisee

**Cardinality Ratio**: the maximum number of entities on the other side one entity can be tied to

- 1:1 MANAGES (one manager per department) / 1:N WORKS_FOR (many employees per department) / M:N WORKS_ON (many employees ↔ many projects)
- In the instance diagram, the side many lines come into is the 1 side

**Participation Constraint**: whether an entity must take part in the relationship

- Total: every employee belongs to a department → EMPLOYEE–WORKS_FOR / Partial: some employees manage no department → EMPLOYEE–MANAGES

**(min, max)**: EMPLOYEE–MANAGES (0,1) may manage none, at most one / DEPARTMENT–MANAGES (1,1) exactly one

**Attributes of relationships**: relationships can have attributes (Start_date of MANAGES, Hours of WORKS_ON)

- 1:1 → may move to either entity / 1:N → only to the N-side entity / M:N → can't move, stays on the relationship

![Line styles and attribute placement for 1:N, 1:1 and M:N, and a recursive relationship](/static/images/database-systems-ch2-db-systems-er-model/er-relationship-constraints.svg)

**Exercise 1**: STUDENT 1:1 SSC / STUDENT M:N TEACHER / COUNTRY 1:1 PRESIDENT / COURSE M:N TEXTBOOK / ITEM M:N ORDER / STUDENT M:N CLASS / CLASS N:1 INSTRUCTOR

### 2.3.4 Weak Entity Types

![Weak entity DEPENDENT and identifying relationship DEPENDENTS_OF](/static/images/database-systems-ch2-db-systems-er-model/er-weak-entity.svg)

**How to read the figure**

- Double rectangle = weak entity, double diamond = identifying relationship
- Double line on the weak entity side = every dependent has an owner employee (total)
- Dashed underline on Dependent_name = partial key (solid underline on Ssn = ordinary key)

**Weak Entity Type**: an entity type whose own attributes can't tell its entities apart. It has no key attribute

- In the figure: DEPENDENT. Kim's daughter Minji and Lee's daughter Minji can have the same name and birth date
- Identified through its owner (identifying entity) → "Kim's Minji"
- A weak entity must always be tied to one owner (no dependent without an employee)

**Identifying Relationship**: the relationship that ties a weak entity to its owner

- In the figure: DEPENDENTS_OF
- The weak entity side is always total participation (double line)

**Partial Key**: an attribute that tells apart only the weak entities of the same owner

- In the figure: Dependent_name. No two dependents of one employee share a name
- Example 2: Section_num in COURSE–SECTION. Section numbers are unique only within one course
- A partial key alone can't identify an entity → the real key = owner's key + partial key = (Ssn, Dependent_name)
