> 시리즈 14편. 구축 6단계(바깥이랑 잇기) 중 구축 09의 마무리, 플랫폼 서버가 올라갈 EC2가 생긴 11월 12일이다. 무엇을 왜 만드는지는 [Woowangthon 0](/kr/blog/woowangthon/woowangthon-00-overview/)에 있다. 클러스터 쪽 준비는 [11편](/kr/blog/woowangthon/woowangthon-11-server-link/)에서 끝났고, 이 글은 그 글의 [마지막 목록](/kr/blog/woowangthon/woowangthon-11-server-link/#9-ec2가-없어서-못-본-것)을 지우는 날이다. 같은 날 오후의 GoCD 서버와 리더 실행기 등록은 [15편](/kr/blog/woowangthon/woowangthon-15-gocd-registration/)에 따로 썼다.

## 한 줄 요약

EC2가 키 없이 관리자 승인으로 사설망에 들어왔다. 리더에서 EC2의 GoCD 포트로는 연결 거부가, 막아 둔 길로는 시간 초과가 났다. 사설망에서는 거부가 "열려 있다"는 뜻이다. EC2에서 서버 계정으로 리더 API를 직접 부른 시험 18개가 통과했고, 응답은 평균 0.1초였다. 저녁에는 서버 자기 코드로 리더를 불렀는데, 첫 시도는 인증서 오류로 실패했다. 틀린 건 서버가 아니라 시험이었다.

## 1. 계획과 다르게 생긴 EC2

EC2는 EC2 담당인 팀장 TaeTaeJin이 만들었다. 11월 11일 회의에서 정한 것과 실제로 생긴 것은 한 군데가 다르다.

| 항목                | 정한 것                        | 실제                                           |
| ------------------- | ------------------------------ | ---------------------------------------------- |
| 인스턴스 타입       | t3.large                       | m7i-flex.large (메모리 8GB로 같다)             |
| OS · 지역           | Amazon Linux 2023, 서울        | 같음                                           |
| 들어오는 규칙       | 없음                           | 없음 (보안 그룹에 들어오는 규칙이 하나도 없다) |
| 인스턴스 메타데이터 | IMDSv2, hop 제한 1             | 같음                                           |
| 권한                | 서버 설정을 읽는 인스턴스 역할 | 같음 (Parameter Store의 서버 설정 · 터널 토큰) |
| 운영자 접속         | SSM Session Manager            | 같음. SSH는 없다                               |

t3.large가 안 된 이유는 AWS 계정이었다. 이 계정은 프리 티어 대상 타입만 띄울 수 있었고, t3.large 요청은 거절됐다. 프리 티어 목록 안에서 메모리가 같은 m7i-flex.large로 갔다. 서버 · AI 서버 · GoCD 서버가 한 대에 올라가는 계획이라 메모리가 줄면 문제였는데, 8GB는 그대로다.

SSH가 없다는 건 이 글 내내 따라다니는 조건이다. EC2에 들어가는 길은 AWS의 SSM뿐이다. 사람은 콘솔의 Session Manager 창으로 들어가고, 에이전트는 같은 SSM의 Run Command(`aws ssm send-command`)로 명령을 보낸다. 들어오는 포트가 하나도 없으니 SSH 키를 관리할 일도, 22번을 누가 두드릴 일도 없다.

## 2. 키 없이 사설망에 들어오기

11편에서는 "가입용 일회용 키는 쓸 기기가 생기는 날 만들어 바로 쓴다"고 적었다. 실제로는 키를 아예 만들지 않았다.

Run Command로 EC2에 보낸 명령은 이것이다.

```bash
tailscale up --hostname wcp-platform --advertise-tags=tag:platform-server
```

키를 안 주면 Tailscale은 로그인 주소를 하나 찍고 기다린다. 사설망 관리자인 내가 그 주소를 브라우저에서 열어 승인하자 EC2가 `tag:platform-server`를 달고 들어왔다. 태그를 달 수 있는 사람은 [접근 규칙 파일](/kr/blog/woowangthon/woowangthon-11-server-link/#8-사설망-접근-규칙)의 `tagOwners`가 정한다. 여기서는 관리자뿐이라, 승인 한 번이 "이 기기는 서버다"라는 선언까지 같이 한다.

키를 안 만든 게 이 단계에서 제일 깔끔한 선택이었다. 일회용 키라도 만들면 어딘가에 한 번은 적히고, 다 쓴 뒤에 폐기됐는지 확인해야 한다. 승인은 그 자리에서 끝나고 남는 비밀이 없다. 나중에 지울 것도 없다.

들어오는 규칙이 하나도 없는데도 경로는 금방 직접 연결이 됐다. 보안 그룹은 나간 패킷의 답을 들여보내고, Tailscale은 양쪽이 먼저 UDP를 내보내 길을 뚫는다. EC2가 공인 주소를 가진 덕도 있을 것이다. 학교 PC와 내 기기 사이가 [아직도 도쿄 중계](/kr/blog/woowangthon/woowangthon-04-remote-access/#직접-연결이-아니라-중계)를 거치는 것과 대조적이다.

## 3. 연결 거부가 반가운 이유

리더 → EC2 `:8153` 규칙은 11월 11일에 파일에만 넣어 두었다([12편](/kr/blog/woowangthon/woowangthon-12-deploy-executor/)의 배포 실행기가 GoCD 서버에서 일감을 받아 오는 길이다). EC2가 들어온 날 관리 화면에 붙여 넣고, 시험 둘을 더해 저장했다.

```text
{
	"src": "k3s-leader",
	"accept": ["tag:platform-server:8153"],
	"deny": ["tag:platform-server:22", "operator-desktop:22"],
},
{
	"src": "k3s-w1",
	"deny": ["operator-desktop:22", "operator-laptop:22", "k3s-leader:22", "tag:platform-server:8153"],
},
```

정책 안 시험은 규칙을 글자로 검사할 뿐이다. 그래서 저장한 뒤에 실제로 찔러 봤다.

| 출발 → 도착                            | 결과      |
| -------------------------------------- | --------- |
| 리더 → EC2 `:8153`                     | 연결 거부 |
| EC2 → 리더 `:6443`                     | `401`     |
| EC2 → 리더 `:22`, w1 `:22`, w2 `:6443` | 시간 초과 |
| 리더 → EC2 `:22`, w1 → EC2 `:8153`     | 시간 초과 |

첫 줄이 이 글의 제목이다. 리더에서 EC2의 8153으로 연결이 **거부**됐다. 그 시각 EC2에는 GoCD가 아직 없었다. 거부는 패킷이 EC2까지 가서, 그 포트에 받는 프로그램이 없다는 답을 받아 왔다는 뜻이다. 길은 열려 있다. 반대로 막아 둔 길은 전부 **시간 초과**였다. Tailscale의 접근 규칙은 허용하지 않은 패킷을 말없이 버린다.

[8편](/kr/blog/woowangthon/woowangthon-08-image-cache/#6-리뷰어-ai가-잡은-것-거절과-무응답)에서 배운 "거절당하는 것과 대답이 없는 것"이 여기서 다시 나왔는데, 이번엔 뜻이 뒤집혔다. [9편](/kr/blog/woowangthon/woowangthon-09-student-space/#5-막혔다는-걸-어떻게-아나)의 학생 공간에서는 차단 규칙(kube-router)이 거절을 돌려줬다. 거기서는 거절이 "막혔다"였다. 사설망에서는 거절이 "열렸다"이고, 막힌 건 무응답이다. 같은 거절이라도 누가 막는지를 알아야 읽을 수 있다. 시험 결과를 "닿는다 / 안 닿는다" 두 칸으로만 적었으면 첫 줄은 실패로 읽혔을 것이다.

이 글을 쓰는 저녁에 같은 길을 다시 찔렀다. 그사이 GoCD 서버가 떠서 8153은 이제 답을 한다.

![리더에서 EC2의 8153은 health OK, 22는 5초 시간 초과, w1에서 EC2의 8153도 시간 초과, tailscale ping은 EC2의 공인 주소로 직접 5ms](/static/images/woowangthon-14-ec2-joins/reach.svg)

_`$EC2`는 EC2의 사설망 주소다. 주소는 가렸다_

## 4. 컨테이너에서 본 401

반대 방향, EC2에서 리더 API로 가는 길은 `401`이었다. 토큰 없이 불렀으니 쿠버네티스가 "누구냐"고 돌려보낸 것이다. 401은 TLS까지 맺고 API 서버가 직접 답했다는 뜻이라, 길 확인으로는 이게 제일 좋은 답이다.

이건 EC2 호스트가 아니라 **도커 컨테이너 안에서** 봤다. 서버는 컨테이너로 뜬다. 호스트에서 닿는다고 컨테이너에서도 닿는다는 보장은 없다. 컨테이너의 패킷은 도커 네트워크를 한 번 거쳐 호스트의 Tailscale로 나간다.

여기서 두 번 걸렸다. Session Manager로 들어가면 셸 사용자가 `ssm-user`라 도커를 부르려면 `sudo`가 필요했다. 그리고 에이전트가 Run Command로 도커 명령을 보내려던 건 세션의 안전 분류기가 막았다. 원격 기기에 셸 쓰기를 보내는 것으로 분류됐다. 이 확인은 내가 콘솔의 Session Manager 창에 직접 쳤다.

## 5. EC2에서 돌린 서버 계정 시험

11편의 서버 계정 시험은 내 데스크탑에서 실제 토큰으로 리더를 부른 것이었다. 권한은 같아도 출발지가 다르다. 그래서 EC2에서 한 번 더 돌렸다.

스크립트는 EC2 안에서 인스턴스 역할로 Parameter Store의 서버 설정(`/wcp/be/K8S_*`, 11월 11일에 미리 넣어 둔 리더 주소 · CA · 토큰)을 꺼내, 리더의 사설망 주소를 직접 부른다. 서버가 실제로 쓸 값 그대로다. 토큰은 셸 변수에만 두고 curl에 표준 입력으로 넘긴다. 쓰기는 전부 server dry run이라 클러스터에는 아무것도 안 남는다.

```bash
api() { # api <token> <method> <path> [body] [content type] -> HTTP status
  printf 'header = "Authorization: Bearer %s"\n' "$1" | curl -s -K - -o /dev/null -m 10 -w '%{http_code}' --cacert "$CA" -H "Content-Type: ${5:-application/json}" -X "$2" ${4:+-d "$4"} "$URL$3"
}
```

이것도 Run Command로 보냈고, 18개가 전부 기대한 답을 받았다.

| 된다 (7)                                     | 거절된다 (11)                                  |
| -------------------------------------------- | ---------------------------------------------- |
| 노드 읽기 `200`                              | `proj-` 아닌 이름의 공간, 라벨 없는 공간 `422` |
| `proj-` 공간 만들기 `201`                    | `proj-demo`의 Secret 읽기 `403`                |
| 이름이 `-secrets`로 끝나는 Secret 쓰기 `201` | `proj-` 밖(`vllm`) Secret 쓰기 `422`           |
| `proj-demo`의 Pod 읽기 `200`                 | `vllm`의 Pod 읽기 · 중지 `403`                 |
| `proj-demo`의 Deployment 읽기 `200`          | 모든 공간 목록 `403`                           |
| `proj-demo` 중지(레플리카 0) `200`           | 레플리카 2 `422`                               |
| 노드 사용량 읽기 `200`                       | `vllm` 삭제 `422`, 틀린 토큰 `401`             |

눈여겨볼 줄은 `proj-` 밖 Secret 쓰기다. 답이 `403`이 아니라 `422`다. 서버 계정은 Secret 만들기 권한을 클러스터 전체로 갖고 있어서([11편](/kr/blog/woowangthon/woowangthon-11-server-link/#2-rbac는-이름으로-거르지-못한다)) 권한으로는 통과하고, 검사 규칙이 막는다. 그러니 이 줄은 "검사 규칙이 지금 켜져 있다"의 증거이기도 하다. 규칙이 꺼진 날 이 시험을 돌리면 dry run이 `201`로 통과하고 시험이 실패한다. 무언가 지워지지는 않는다.

응답 시간도 쟀다. 노드 읽기 열 번이 평균 약 0.1초, 가장 느린 게 0.29초였다. 재는 사이에 경로가 도쿄 중계(DERP)에서 직접 연결로 바뀌었다. 설계 문서의 알려진 한계에 "중계라 서버 → 리더 API가 느리다"고 적어 둔 걱정은, 적어도 이날은 해당이 없었다.

## 6. 머지한 PR에 빠진 커밋

결과는 팀 레포에 적었다. 사설망 규칙과 길 확인은 [woowangthon/WOOWANGTHON_TEAM_18#154](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/154)로 올렸고, EC2 시험 결과는 같은 브랜치에 커밋 하나를 더 올렸다.

그런데 #154는 그 커밋이 올라가기 전에 머지돼 있었다. 머지는 그 순간의 브랜치 머리까지만 가져간다. 뒤에 올린 커밋은 브랜치에만 남고 `main`에는 들어가지 않았다. PR 화면은 이미 "Merged"라 겉으로는 다 끝난 것처럼 보였다. 같은 커밋을 [woowangthon/WOOWANGTHON_TEAM_18#155](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/155)로 따로 올렸고, #154 머지 17분 뒤에 들어갔다.

머지 전에 올릴 커밋을 다 올린다. 머지 뒤에는 `main`에 그 줄이 있는지 본다. 당연한 얘기인데, 리뷰를 기다리는 동안 작업이 이어지면 쉽게 어긋난다.

## 7. api. 주소가 530에서 200으로

[10편](/kr/blog/woowangthon/woowangthon-10-public-entry/#9-서버-주소도-이-도메인으로)에서 서버 주소를 `api.stairnoworks.com`으로 정하고, 터널은 EC2가 생기기 전에 미리 만들어 두었다. 그동안 이 주소는 `530`이었다. Cloudflare가 터널에 붙은 커넥터가 없다고 돌려주는 답으로, [리더 인터넷을 끊었을 때](/kr/blog/woowangthon/woowangthon-10-public-entry/#7-리더-인터넷-끊기-502-다음-530) 본 그 숫자다.

EC2에 커넥터가 뜨고 서버가 올라오자 `/api/health`가 `200`이 됐다. 이 주소의 터널은 학생 앱의 터널과 따로다. 리더의 터널은 방문자를 학교로, EC2의 터널은 플랫폼 사용자를 서버로 보낸다. 둘 다 들어오는 포트를 열지 않는다.

## 8. 서버 자기 코드로 부른 리더, 틀렸던 첫 시험

5절의 시험은 curl이다. 서버가 실제로 리더를 부르는 건 서버 코드의 클러스터 호출 모듈이다. 저녁에 마지막으로 이걸 봤다. 서버 컨테이너(`wcp-be`) 안에서, 빌드된 서버 코드의 순서 그대로 불렀다. 환경 변수 검사(`validateEnv`)가 설정을 읽고, 클라이언트(`K8sClient`)를 만들고, 읽기 모듈(`ClusterReader`)로 부른다. 설정은 컨테이너가 받은 환경 변수 그대로다.

| 부른 것                  | 결과                 |
| ------------------------ | -------------------- |
| 노드 목록                | 세 대 Ready, 약 80ms |
| `proj-demo`의 Deployment | `web` 하나, 약 20ms  |
| 서버가 만들지 않은 공간  | `403`                |

마지막 줄은 [11편의 좁힌 읽기](/kr/blog/woowangthon/woowangthon-11-server-link/#4-읽기는-검사-규칙이-못-본다) 그대로다. 연결이 없는 공간은 `404`가 아니라 `403`이다.

이 결과는 두 번째 시도에서 나왔다. 첫 시도는 이렇게 실패했다.

```text
SELF_SIGNED_CERT_IN_CHAIN
```

서버가 리더의 인증서를 믿지 못했다는 뜻이다. 이대로 보고했으면 "서버의 클러스터 연결에 인증서 버그가 있다"가 됐을 것이다. 원인은 시험 쪽이었다. 에이전트는 첫 시도에서 `validateEnv`를 건너뛰고 환경 변수 값을 클라이언트에 바로 넣었다. 리더의 CA는 환경 변수에 base64 한 줄로 들어 있고, 그걸 PEM으로 푸는 게 `validateEnv`의 일이다. base64 그대로 받은 클라이언트는 CA를 못 알아보고, 리더의 자체 서명 인증서 체인을 거부했다. 앱의 설정 해석을 거쳐서 부르자 바로 통과했다.

서버를 시험할 때는 서버가 설정을 읽는 길까지 시험에 넣는다. 그 길을 건너뛴 시험은 서버가 아니라 시험을 잰다.

이것도 Run Command로 도커 안에 보내려다 4절처럼 분류기에 막혀, 내 브라우저의 콘솔 Session Manager 창에서 돌렸다.

이 대회의 주제는 "AI는 동료가 될 수 있을까?"다. 이날 에이전트는 둘 다 했다. 연결 거부를 "열렸다"로 맞게 읽어 냈고, 자기 시험의 지름길 때문에 멀쩡한 서버를 의심하게 만들 뻔했다. 둘을 가른 건 결과를 읽을 때 그 결과가 어떤 길로 나왔는지를 같이 본 것이다. 거부가 누구에게서 왔는지, 실패가 서버 코드의 어느 줄에서 났는지. 동료의 결과는 그 결과가 지나온 길만큼만 믿을 수 있다. 사람의 결과도 마찬가지다.

## 9. 11편의 목록, 이제

[11편 9절](/kr/blog/woowangthon/woowangthon-11-server-link/#9-ec2가-없어서-못-본-것)에 "EC2가 없어서 못 본 것"을 적어 두었다. 하루 만에 대부분 지웠다.

| 11편에 남긴 것                                    | 11월 12일                                             |
| ------------------------------------------------- | ----------------------------------------------------- |
| EC2가 서버 태그를 달고 사설망에 들어오는가        | 들어왔다. 키 없이 관리자 승인으로 (2절)               |
| 서버 태그가 리더 `:6443`만 여는가                 | `6443`은 `401`, 리더 SSH와 워커는 시간 초과 (3절)     |
| 보안 그룹이 Tailscale의 나가는 연결을 막지 않는가 | 막지 않는다. 직접 연결까지 됐다 (2절)                 |
| 서버가 리더 인증서를 클러스터 CA로 검증하는가     | curl도, 서버 코드도 검증했다 (5절, 8절)               |
| 토큰을 EC2의 비밀 설정에 넣는 것                  | EC2보다 하루 먼저 Parameter Store에 넣어 두었다 (5절) |
| 리더에서 EC2 `:8153`으로 나가는 길                | 열렸다. 그날은 거부, 저녁에는 GoCD가 답한다 (3절)     |
| 서버 코드의 실제 끄기 · 켜기 · 재시작 호출        | 아직. 서버 코드로는 읽기만 봤다                       |

마지막 줄과, 플랫폼에서 배포를 눌러 리더 실행기가 학생 공간에 앱을 올리는 끝까지 배포 시험은 EC2 담당에게 넘겼다. AI 담당의 작업이 끝난 뒤 돌리기로 했다.

## 10. 정리

| 겪은 일                                   | 배운 것                                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------------------------- |
| 계획한 인스턴스 타입이 계정에서 거절됐다  | 계획에는 타입보다 조건(메모리 8GB)을 적는다. 조건이 같으면 다른 타입으로 간다               |
| 일회용 키를 쓸 생각이었다                 | 관리자가 승인하면 키가 필요 없다. 남는 비밀이 없는 쪽을 먼저 고른다                         |
| 열어 둔 길이 연결 거부였다                | 사설망에서 거부는 "열림"이고 무응답이 "막힘"이다. 누가 막는지 알아야 결과를 읽는다          |
| 호스트가 아니라 컨테이너에서 길을 봤다    | 서버가 도는 자리에서 확인한다. 호스트에서 닿는 것과 컨테이너에서 닿는 것은 다르다           |
| `proj-` 밖 Secret 쓰기가 403이 아니라 422 | 권한과 검사 규칙 중 누가 막았는지까지 맞아야 통과다. 그 줄이 규칙이 켜져 있다는 증거가 된다 |
| 머지된 PR에 뒤에 올린 커밋이 빠졌다       | 머지 전에 다 올리고, 머지 뒤에 `main`에서 확인한다                                          |
| 서버 코드 시험이 인증서 오류로 실패했다   | 시험은 앱의 설정 해석부터 탄다. 지름길로 부른 시험은 시험 자신을 잰다                       |

이걸로 구축 09가 끝났다. 서버 계정은 11편에서 만들었고, 그 계정이 진짜 서버 자리에서 진짜 서버 코드로 쓰이는 것까지 이날 봤다. 같은 날 오후에는 EC2에 GoCD 서버가 뜨고 리더의 배포 실행기가 거기에 등록됐다. 그 이야기가 다음 글이다.
