## 0. 들어가며

> 시리즈 14편. 구축 6단계(바깥이랑 잇기) 중 구축 09의 마무리, 플랫폼 서버가 올라갈 [EC2](glossary:ec2)가 생긴 11월 12일이다. 무엇을 왜 만드는지는 [Woowangthon 0](/kr/blog/hackathon/woowangthon/woowangthon-00-overview/)에 있다. 클러스터 쪽 준비는 [11편](/kr/blog/hackathon/woowangthon/woowangthon-11-server-link/)에서 끝났고, 이 글은 그 글의 [마지막 목록](/kr/blog/hackathon/woowangthon/woowangthon-11-server-link/#9-ec2가-없어서-못-본-것)을 지우는 날이다. 같은 날 오후의 [GoCD](glossary:gocd) 서버와 리더 실행기 등록은 [15편](/kr/blog/hackathon/woowangthon/woowangthon-15-gocd-registration/)에 따로 썼다.

구축 09를 마무리하려면 플랫폼 서버가 올라갈 [EC2](glossary:ec2)가 필요했고, 11편에서 남긴 "[EC2](glossary:ec2)가 없어서 못 본 것"을 이날 지워야 했다.

식당으로 비유하면 본점(학교 클러스터) 옆에 지점 건물이 새로 지어진 날이다. 지점에는 손님용 정문이 없고 직원 통로만 있다. 통로 끝 문을 두드려 "문 앞에서 거절한다"는 답이 오면 통로가 열려 있다는 뜻이고, 아무 대답이 없으면 통로가 막힌 것이다. 지점 건물은 [EC2](glossary:ec2), 직원 통로는 [Tailscale](glossary:tailscale) 사설망, 문 앞의 거절은 [Connection refused](glossary:connection-refused), 무응답은 [Timeout](glossary:timeout)이다.

이날 한 일은 이렇다. [EC2](glossary:ec2)를 키 없이 관리자 승인으로 사설망에 넣고, [ACL](glossary:acl)을 실제로 찔러 읽고, [EC2](glossary:ec2)에서 서버 계정 시험 18개를 돌리고, 저녁에는 서버 코드로 리더를 불러 봤다.

## 1. 계획과 다르게 생긴 EC2

[EC2](glossary:ec2)는 [EC2](glossary:ec2) 담당인 팀장 TaeTaeJin이 만들었다. 11월 11일 회의에서 정한 것과 실제로 생긴 것은 한 군데가 다르다.

| 항목                                    | 정한 것                                                                         | 실제                                                                                                                                      |
| --------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| [Instance type](glossary:instance-type) | t3.large                                                                        | m7i-flex.large (메모리 8GB로 같다)                                                                                                        |
| OS · 지역                               | [Amazon Linux](glossary:amazon-linux) 2023, 서울                                | 같음                                                                                                                                      |
| 들어오는 규칙                           | 없음                                                                            | 없음 ([Security group](glossary:security-group)에 들어오는 규칙이 하나도 없다)                                                            |
| 인스턴스 메타데이터                     | [IMDSv2](glossary:imdsv2), hop 제한 1                                           | 같음                                                                                                                                      |
| 권한                                    | 서버 설정을 읽는 [IAM role](glossary:iam-role)                                  | 같음 ([Parameter Store](glossary:aws-systems-manager-parameter-store)의 서버 설정 · [Cloudflare Tunnel](glossary:cloudflare-tunnel) 토큰) |
| 운영자 접속                             | [SSM](glossary:aws-systems-manager) [Session Manager](glossary:session-manager) | 같음. [SSH](glossary:ssh)는 없다                                                                                                          |

t3.large가 안 된 이유는 AWS 계정이었다. 이 계정은 프리 티어 대상 타입만 띄울 수 있었고, t3.large 요청은 거절됐다. 프리 티어 목록 안에서 메모리가 같은 m7i-flex.large로 갔다. 서버 · AI 서버 · [GoCD](glossary:gocd) 서버가 한 대에 올라가는 계획이라 메모리가 줄면 문제였는데, 8GB는 그대로다.

[SSH](glossary:ssh)가 없다는 건 이 글 내내 따라다니는 조건이다. [EC2](glossary:ec2)에 들어가는 길은 AWS의 [SSM](glossary:aws-systems-manager)뿐이다. 사람은 콘솔의 [Session Manager](glossary:session-manager) 창으로 들어가고, 에이전트는 같은 [SSM](glossary:aws-systems-manager)의 [Run Command](glossary:run-command)(`aws ssm send-command`)로 명령을 보낸다. 들어오는 포트가 하나도 없으니 [SSH](glossary:ssh) 키를 관리할 일도, 22번을 누가 두드릴 일도 없다.

## 2. 키 없이 사설망에 들어오기

11편에서는 "가입용 일회용 키는 쓸 기기가 생기는 날 만들어 바로 쓴다"고 적었다. 실제로는 키를 아예 만들지 않았다.

[Run Command](glossary:run-command)로 [EC2](glossary:ec2)에 보낸 명령은 이것이다.

```bash
tailscale up --hostname wcp-platform --advertise-tags=tag:platform-server
```

키를 안 주면 [Tailscale](glossary:tailscale)은 로그인 주소를 하나 찍고 기다린다. 사설망 관리자인 내가 그 주소를 브라우저에서 열어 승인하자 [EC2](glossary:ec2)가 `tag:platform-server`를 달고 들어왔다. 태그를 달 수 있는 사람은 [접근 규칙 파일](/kr/blog/hackathon/woowangthon/woowangthon-11-server-link/#8-사설망-접근-규칙)의 `tagOwners`가 정한다. 여기서는 관리자뿐이라, 승인 한 번이 "이 기기는 서버다"라는 선언까지 같이 한다.

키를 안 만든 게 이 단계에서 제일 깔끔한 선택이었다. 일회용 키라도 만들면 어딘가에 한 번은 적히고, 다 쓴 뒤에 폐기됐는지 확인해야 한다. 승인은 그 자리에서 끝나고 남는 비밀이 없다. 나중에 지울 것도 없다.

들어오는 규칙이 하나도 없는데도 경로는 금방 직접 연결이 됐다. [Security group](glossary:security-group)은 나간 패킷의 답을 들여보내고, [Tailscale](glossary:tailscale)은 양쪽이 먼저 UDP를 내보내 길을 뚫는다. [EC2](glossary:ec2)가 공인 주소를 가진 덕도 있을 것이다. 학교 PC와 내 기기 사이가 [아직도 도쿄 중계](/kr/blog/hackathon/woowangthon/woowangthon-04-remote-access/#직접-연결이-아니라-중계)를 거치는 것과 대조적이다.

## 3. 연결 거부가 반가운 이유

리더 → [EC2](glossary:ec2) `:8153` 규칙은 11월 11일에 파일에만 넣어 두었다([12편](/kr/blog/hackathon/woowangthon/woowangthon-12-deploy-executor/)의 배포 실행기가 [GoCD](glossary:gocd) 서버에서 일감을 받아 오는 길이다). [EC2](glossary:ec2)가 들어온 날 관리 화면에 붙여 넣고, 시험 둘을 더해 저장했다.

```text
{
	"src": "k3s-leader",
	"accept": ["tag:platform-server:8153"],
	"deny": ["tag:platform-server:22", "operator-desktop:22"],
},
{
	"src": "k3s-w1",
	"deny": ["operator-desktop:22", "operator-laptop:22", "k3s-leader:22", "tag:platform-server:8153"],
},
```

정책 안 시험은 규칙을 글자로 검사할 뿐이다. 그래서 저장한 뒤에 실제로 찔러 봤다.

| 출발 → 도착                                                        | 결과                                              |
| ------------------------------------------------------------------ | ------------------------------------------------- |
| 리더 → [EC2](glossary:ec2) `:8153`                                 | [Connection refused](glossary:connection-refused) |
| [EC2](glossary:ec2) → 리더 `:6443`                                 | `401`                                             |
| [EC2](glossary:ec2) → 리더 `:22`, w1 `:22`, w2 `:6443`             | [Timeout](glossary:timeout)                       |
| 리더 → [EC2](glossary:ec2) `:22`, w1 → [EC2](glossary:ec2) `:8153` | [Timeout](glossary:timeout)                       |

첫 줄이 이 글의 제목이다. 리더에서 [EC2](glossary:ec2)의 8153으로 연결이 **거부**됐다. 그 시각 [EC2](glossary:ec2)에는 [GoCD](glossary:gocd)가 아직 없었다. 거부는 패킷이 [EC2](glossary:ec2)까지 가서, 그 포트에 받는 프로그램이 없다는 답을 받아 왔다는 뜻이다. 길은 열려 있다. 반대로 막아 둔 길은 전부 **[Timeout](glossary:timeout)**였다. [Tailscale](glossary:tailscale)의 [ACL](glossary:acl)은 허용하지 않은 패킷을 말없이 버린다.

[8편](/kr/blog/hackathon/woowangthon/woowangthon-08-image-cache/#6-리뷰어-ai가-잡은-것-거절과-무응답)에서 배운 "거절당하는 것과 대답이 없는 것"이 여기서 다시 나왔는데, 이번엔 뜻이 뒤집혔다. [9편](/kr/blog/hackathon/woowangthon/woowangthon-09-student-space/#5-막혔다는-걸-어떻게-아나)의 학생 공간에서는 차단 규칙([kube-router](glossary:kube-router))이 거절을 돌려줬다. 거기서는 거절이 "막혔다"였다. 사설망에서는 거절이 "열렸다"이고, 막힌 건 무응답이다. 같은 거절이라도 누가 막는지를 알아야 읽을 수 있다. 시험 결과를 "닿는다 / 안 닿는다" 두 칸으로만 적었으면 첫 줄은 실패로 읽혔을 것이다.

이 글을 쓰는 저녁에 같은 길을 다시 찔렀다. 그사이 [GoCD](glossary:gocd) 서버가 떠서 8153은 이제 답을 한다.

![리더에서 EC2의 8153은 health OK, 22는 5초 시간 초과, w1에서 EC2의 8153도 시간 초과, tailscale ping은 EC2의 공인 주소로 직접 5ms](/static/images/woowangthon-14-ec2-joins/reach.svg)

_`$EC2`는 [EC2](glossary:ec2)의 사설망 주소다. 주소는 가렸다_

## 4. 컨테이너에서 본 401

반대 방향, [EC2](glossary:ec2)에서 리더 API로 가는 길은 `401`이었다. [Bearer token](glossary:bearer-token) 없이 불렀으니 [Kubernetes](glossary:kubernetes)가 "누구냐"고 돌려보낸 것이다. [401](glossary:http-status-code)은 [TLS](glossary:tls)까지 맺고 API 서버가 직접 답했다는 뜻이라, 길 확인으로는 이게 제일 좋은 답이다.

이건 [EC2](glossary:ec2) 호스트가 아니라 **[Docker](glossary:docker) [Container](glossary:container) 안에서** 봤다. 서버는 [Container](glossary:container)로 뜬다. 호스트에서 닿는다고 [Container](glossary:container)에서도 닿는다는 보장은 없다. [Container](glossary:container)의 패킷은 [Docker](glossary:docker) 네트워크를 한 번 거쳐 호스트의 [Tailscale](glossary:tailscale)로 나간다.

여기서 두 번 걸렸다. [Session Manager](glossary:session-manager)로 들어가면 셸 사용자가 `ssm-user`라 [Docker](glossary:docker)를 부르려면 `sudo`가 필요했다. 그리고 에이전트가 [Run Command](glossary:run-command)로 [Docker](glossary:docker) 명령을 보내려던 건 세션의 안전 분류기가 막았다. 원격 기기에 셸 쓰기를 보내는 것으로 분류됐다. 이 확인은 내가 콘솔의 [Session Manager](glossary:session-manager) 창에 직접 쳤다.

## 5. EC2에서 돌린 서버 계정 시험

11편의 서버 계정 시험은 내 데스크탑에서 실제 [Bearer token](glossary:bearer-token)으로 리더를 부른 것이었다. 권한은 같아도 출발지가 다르다. 그래서 [EC2](glossary:ec2)에서 한 번 더 돌렸다.

스크립트는 [EC2](glossary:ec2) 안에서 [IAM role](glossary:iam-role)로 [Parameter Store](glossary:aws-systems-manager-parameter-store)의 서버 설정(`/wcp/be/K8S_*`, 11월 11일에 미리 넣어 둔 리더 주소 · CA · [Bearer token](glossary:bearer-token))을 꺼내, 리더의 사설망 주소를 직접 부른다. 서버가 실제로 쓸 값 그대로다. [Bearer token](glossary:bearer-token)은 셸 변수에만 두고 [curl](glossary:curl)에 표준 입력으로 넘긴다. 쓰기는 전부 server [dry run](glossary:dry-run)이라 클러스터에는 아무것도 안 남는다.

```bash
api() { # api <token> <method> <path> [body] [content type] -> HTTP status
  printf 'header = "Authorization: Bearer %s"\n' "$1" | curl -s -K - -o /dev/null -m 10 -w '%{http_code}' --cacert "$CA" -H "Content-Type: ${5:-application/json}" -X "$2" ${4:+-d "$4"} "$URL$3"
}
```

이것도 [Run Command](glossary:run-command)로 보냈고, 18개가 전부 기대한 답을 받았다.

| 된다 (7)                                                                   | 거절된다 (11)                                                       |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| [Node](glossary:node) 읽기 `200`                                           | `proj-` 아닌 이름의 공간, 라벨 없는 공간 `422`                      |
| `proj-` 공간 만들기 `201`                                                  | `proj-demo`의 [Secret](glossary:kubernetes-secret) 읽기 `403`       |
| 이름이 `-secrets`로 끝나는 [Secret](glossary:kubernetes-secret) 쓰기 `201` | `proj-` 밖(`vllm`) [Secret](glossary:kubernetes-secret) 쓰기 `422`  |
| `proj-demo`의 [Pod](glossary:pod) 읽기 `200`                               | `vllm`의 [Pod](glossary:pod) 읽기 · 중지 `403`                      |
| `proj-demo`의 [Deployment](glossary:deployment) 읽기 `200`                 | 모든 공간 목록 `403`                                                |
| `proj-demo` 중지([Replica](glossary:replica) 0) `200`                      | [Replica](glossary:replica) 2 `422`                                 |
| [Node](glossary:node) 사용량 읽기 `200`                                    | `vllm` 삭제 `422`, 틀린 [Bearer token](glossary:bearer-token) `401` |

눈여겨볼 줄은 `proj-` 밖 [Secret](glossary:kubernetes-secret) 쓰기다. 답이 `403`이 아니라 `422`다. 서버 계정은 [Secret](glossary:kubernetes-secret) 만들기 권한을 클러스터 전체로 갖고 있어서([11편](/kr/blog/hackathon/woowangthon/woowangthon-11-server-link/#2-rbac는-이름으로-거르지-못한다)) 권한으로는 통과하고, [Admission control](glossary:admission-control)이 막는다. 그러니 이 줄은 "[Admission control](glossary:admission-control)이 지금 켜져 있다"의 증거이기도 하다. 규칙이 꺼진 날 이 시험을 돌리면 [dry run](glossary:dry-run)이 `201`로 통과하고 시험이 실패한다. 무언가 지워지지는 않는다.

응답 시간도 쟀다. [Node](glossary:node) 읽기 열 번이 평균 약 0.1초, 가장 느린 게 0.29초였다. 재는 사이에 경로가 도쿄 중계([DERP](glossary:derp))에서 직접 연결로 바뀌었다. 설계 문서의 알려진 한계에 "중계라 서버 → 리더 API가 느리다"고 적어 둔 걱정은, 적어도 이날은 해당이 없었다.

## 6. 머지한 PR에 빠진 커밋

결과는 팀 레포에 적었다. 사설망 규칙과 길 확인은 [woowangthon/WOOWANGTHON_TEAM_18#154](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/154)로 올렸고, [EC2](glossary:ec2) 시험 결과는 같은 [Branch](glossary:branch)에 [Commit](glossary:commit) 하나를 더 올렸다.

그런데 #154는 그 [Commit](glossary:commit)이 올라가기 전에 [Merge](glossary:merge)돼 있었다. [Merge](glossary:merge)는 그 순간의 [Branch](glossary:branch) 머리까지만 가져간다. 뒤에 올린 [Commit](glossary:commit)은 [Branch](glossary:branch)에만 남고 `main`에는 들어가지 않았다. [PR](glossary:pull-request) 화면은 이미 "Merged"라 겉으로는 다 끝난 것처럼 보였다. 같은 [Commit](glossary:commit)을 [woowangthon/WOOWANGTHON_TEAM_18#155](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/155)로 따로 올렸고, #154 [Merge](glossary:merge) 17분 뒤에 들어갔다.

[Merge](glossary:merge) 전에 올릴 [Commit](glossary:commit)을 다 올린다. [Merge](glossary:merge) 뒤에는 `main`에 그 줄이 있는지 본다. 당연한 얘기인데, 리뷰를 기다리는 동안 작업이 이어지면 쉽게 어긋난다.

## 7. api. 주소가 530에서 200으로

[10편](/kr/blog/hackathon/woowangthon/woowangthon-10-public-entry/#9-서버-주소도-이-도메인으로)에서 서버 주소를 `api.stairnoworks.com`으로 정하고, [Cloudflare Tunnel](glossary:cloudflare-tunnel)은 [EC2](glossary:ec2)가 생기기 전에 미리 만들어 두었다. 그동안 이 주소는 `530`이었다. Cloudflare가 [Cloudflare Tunnel](glossary:cloudflare-tunnel)에 붙은 커넥터가 없다고 돌려주는 답으로, [리더 인터넷을 끊었을 때](/kr/blog/hackathon/woowangthon/woowangthon-10-public-entry/#7-리더-인터넷-끊기-502-다음-530) 본 그 숫자다.

[EC2](glossary:ec2)에 커넥터가 뜨고 서버가 올라오자 `/api/health`가 `200`이 됐다. 이 주소의 [Cloudflare Tunnel](glossary:cloudflare-tunnel)은 학생 앱의 [Cloudflare Tunnel](glossary:cloudflare-tunnel)과 따로다. 리더의 [Cloudflare Tunnel](glossary:cloudflare-tunnel)은 방문자를 학교로, [EC2](glossary:ec2)의 [Cloudflare Tunnel](glossary:cloudflare-tunnel)은 플랫폼 사용자를 서버로 보낸다. 둘 다 들어오는 포트를 열지 않는다.

## 8. 서버 코드로 리더를 불러 본 시험

5절의 시험은 [curl](glossary:curl)이다. 서버가 실제로 리더를 부르는 건 서버 코드의 클러스터 호출 모듈이다. 저녁에 마지막으로 이걸 봤다. 서버 [Container](glossary:container)(`wcp-be`) 안에서, 빌드된 서버 코드의 순서 그대로 불렀다. [Environment variable](glossary:environment-variable) 검사(`validateEnv`)가 설정을 읽고, 클라이언트(`K8sClient`)를 만들고, 읽기 모듈(`ClusterReader`)로 부른다. 설정은 [Container](glossary:container)가 받은 [Environment variable](glossary:environment-variable) 그대로다.

| 부른 것                                         | 결과                 |
| ----------------------------------------------- | -------------------- |
| [Node](glossary:node) 목록                      | 세 대 Ready, 약 80ms |
| `proj-demo`의 [Deployment](glossary:deployment) | `web` 하나, 약 20ms  |
| 서버가 만들지 않은 공간                         | `403`                |

마지막 줄은 [11편의 좁힌 읽기](/kr/blog/hackathon/woowangthon/woowangthon-11-server-link/#4-읽기는-검사-규칙이-못-본다) 그대로다. 연결이 없는 공간은 `404`가 아니라 `403`이다.

이 결과는 두 번째 시도에서 나왔다. 첫 시도는 이렇게 실패했다.

```text
SELF_SIGNED_CERT_IN_CHAIN
```

서버가 리더의 인증서를 믿지 못했다는 뜻이다. 이대로 보고했으면 "서버의 클러스터 연결에 인증서 버그가 있다"가 됐을 것이다. 원인은 시험 쪽이었다. 에이전트는 첫 시도에서 `validateEnv`를 건너뛰고 [Environment variable](glossary:environment-variable) 값을 클라이언트에 바로 넣었다. 리더의 CA는 [Environment variable](glossary:environment-variable)에 [base64](glossary:base64) 한 줄로 들어 있고, 그걸 [PEM](glossary:pem)으로 푸는 게 `validateEnv`의 일이다. [base64](glossary:base64) 그대로 받은 클라이언트는 CA를 못 알아보고, 리더의 [Self-signed certificate](glossary:self-signed-certificate) 체인을 거부했다. 앱의 설정 해석을 거쳐서 부르자 바로 통과했다.

서버를 시험할 때는 서버가 설정을 읽는 길까지 시험에 넣는다. 그 길을 건너뛴 시험은 서버가 아니라 시험을 잰다.

이것도 [Run Command](glossary:run-command)로 [Docker](glossary:docker) 안에 보내려다 4절처럼 분류기에 막혀, 내 브라우저의 콘솔 [Session Manager](glossary:session-manager) 창에서 돌렸다.

서버 코드의 실제 끄기·켜기·재시작 호출은 아직 읽기만 봤다. 이 호출과, 플랫폼에서 배포를 눌러 리더 실행기가 학생 공간에 앱을 올리는 끝까지 배포 시험은 [EC2](glossary:ec2) 담당에게 넘겼다. AI 담당의 작업이 끝난 뒤 돌리기로 했다.
