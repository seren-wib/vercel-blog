# 5. Index compression

## 5.1 Compression

**Why compress the [index](glossary:inverted-index) → it saves space and also makes things faster**

1. Why compress (in general)
   - Saves disk space (saves money)
   - Fits more into memory (faster)
   - Disk → memory transfer also gets faster: **reading compressed data and decompressing it in memory is faster than reading it uncompressed**
   - Assumption: the [decompression](glossary:decompression) algorithm is fast. Everything used in this chapter is fast

2. Why compress in IR

   | Target                             | Goal                                    |
   | ---------------------------------- | --------------------------------------- |
   | [Dictionary](glossary:dictionary)  | Small enough to keep entirely in memory |
   | [Postings](glossary:postings-list) | Less disk space, less time reading disk |
   - Large search engines keep a large part of the [postings](glossary:postings-list) in memory too

3. [lossy](glossary:lossy-compression) vs [lossless](glossary:lossless-compression)
   - **[lossy](glossary:lossy-compression)**: [compression](glossary:index-compression) that throws away some information. E.g. [case folding](glossary:case-folding), [stop word](glossary:stop-word) removal, [Porter](glossary:porter-stemmer) [stemming](glossary:stemming), number elimination ([ch2 preprocessing](/en/blog/cs-fundamentals/information-retrieval/information-retrieval-ch2-term-vocabulary-postings/#22-terms) is effectively [lossy](glossary:lossy-compression) [compression](glossary:index-compression))
   - **[lossless](glossary:lossless-compression)**: [compression](glossary:index-compression) that throws away nothing. **[Index compression](glossary:index-compression) is mostly this**

3. [Heaps' law](glossary:heaps-law): estimating vocabulary size
   - Is there an upper bound on the vocabulary? No. Words of length 20 alone allow 70²⁰ ≈ 10³⁷ possibilities → **as the collection grows, the vocabulary keeps growing**
   - **[Heaps' law](glossary:heaps-law)**: an empirical law that predicts the number of [terms](glossary:term) from the number of [tokens](glossary:token) in the collection
   - **M = k · T^b** (M = number of [terms](glossary:term), T = number of [tokens](glossary:token)), typically 30 ≤ k ≤ 100, b ≈ 0.5
   - A straight line on a log-log plot: log M = b · log T + log k (the simplest relation between collection size and vocabulary size)
   - [Reuters](glossary:reuters-rcv1): log₁₀M = 0.49 · log₁₀T + 1.64 → k = 10^1.64 ≈ 44, b = 0.49
   - Example: T = 1,000,020 → 44 × 1,000,020^0.49 ≈ 38,323 (actual 38,365) → a good fit

4. [Heaps' law](glossary:heaps-law) exercise: find k, b and compute M
   - 3,000 [terms](glossary:term) in the first 10,000 [tokens](glossary:token), 30,000 [terms](glossary:term) in 1,000,000 [tokens](glossary:token)
   - Divide: 30,000 / 3,000 = (1,000,000 / 10,000)^b → 10 = 100^b → **b = 0.5**
   - Substitute: 3,000 = k × 10,000^0.5 = k × 100 → **k = 30**
   - 2 × 10¹⁰ pages × 200 [tokens](glossary:token) = T = 4 × 10¹² → M = 30 × √(4 × 10¹²) = 30 × 2 × 10⁶ = **60,000,000**
   - Exercise 1 (keeping typos vs auto-correcting): keeping typos keeps creating new [terms](glossary:term), so M gets larger (k or b grows)

5. [Zipf's law](glossary:zipfs-law): computing frequencies
   - [Heaps](glossary:heaps-law) = how big the vocabulary gets / [Zipf](glossary:zipfs-law) = how many frequent vs rare [terms](glossary:term) there are
   - **[Zipf's law](glossary:zipfs-law)**: the frequency of the i-th most frequent [term](glossary:term) is proportional to 1/i. **cf_i ∝ 1/i** ([cf](glossary:collection-frequency) = total occurrences in the collection)
   - [cf](glossary:collection-frequency)₂ = [cf](glossary:collection-frequency)₁ / 2, [cf](glossary:collection-frequency)₃ = [cf](glossary:collection-frequency)₁ / 3 … e.g. if the is [cf](glossary:collection-frequency)₁, of is half of that and and is 1/3
   - cf_i = c · i^k (k = −1) → log cf_i = log c − log i → a straight line with slope −1 on a log-log plot ([power law](glossary:power-law))
   - On [Reuters](glossary:reuters-rcv1) it doesn't fit the line exactly. What matters is the conclusion: **a few frequent [terms](glossary:term), a huge number of rare [terms](glossary:term)**

## 5.3 Dictionary compression

**To fit the [dictionary](glossary:dictionary) in memory, first get rid of the waste in fixed-width slots**

1. Why compress the [dictionary](glossary:dictionary)
   - The [dictionary](glossary:dictionary) is much smaller than the [postings](glossary:postings-list). But it **has to stay in memory**
   - It competes with other programs for memory, devices with little memory such as phones and onboard computers, fast startup time

2. Fixed-width array ([ch3 3.1](/en/blog/cs-fundamentals/information-retrieval/information-retrieval-ch3-dictionaries-tolerant-retrieval/#31-dictionaries))
   - One row = [term](glossary:term) 20 + frequency 4 + [postings](glossary:postings-list) pointer 4 = 28 bytes → (20 + 4 + 4) × 400,000 = **11.2 MB**
   - Problems
     - Most of the [term](glossary:term) slot is wasted: a 1-letter [term](glossary:term) also takes 20 bytes
     - Words longer than 20 letters don't fit (hydrochlorofluorocarbons, supercalifragilisticexpialidocious)
     - Average English [term](glossary:term) length is about 8 letters → **how do we use only about 8 characters per [term](glossary:term) on average?**

3. [Dictionary as a string](glossary:dictionary-as-a-string)
   - **One long string with all [terms](glossary:term) concatenated + a pointer to each [term](glossary:term)'s start in each row**
   - Example: `...systilesyzygeticsyzygialsyzygyszaibelyiteszecin...` / the next [term](glossary:term)'s pointer position = the end of the current [term](glossary:term)
   - One row = frequency 4 + [postings](glossary:postings-list) pointer 4 + **[term](glossary:term) pointer 3** + [term](glossary:term) average 8 bytes (in the string)
   - Why the [term](glossary:term) pointer is 3 bytes: string length 8 × 400,000 = 3,200,000 → log₂(3,200,000) ≈ 21.6 &lt; 24 bits = 3 bytes
   - 400,000 × (4 + 4 + 3 + 8) = **7.6 MB** (smaller than the fixed-width 11.2 MB)

4. [blocking](glossary:blocking) (k = 4)
   - Keep only 1 pointer per 4 [terms](glossary:term), and instead prefix each [term](glossary:term) with a 1-byte length. Example: `7systile9syzygetic8syzygial6syzygy11szaibelyite6szecin`
   - Per block: before, 4 pointers × 3 = 12 bytes → now pointer 3 + lengths 4 × 1 = 7 bytes → **5 bytes saved per block**
   - Total: 400,000 / 4 blocks × 5 = 0.5 MB → 7.6 → 7.1 MB
   - Cost: lookup gets a bit slower

   |                                | No [blocking](glossary:blocking)                                  | [Blocking](glossary:blocking) (k = 4)                                           |
   | ------------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------------------- |
   | How to look up                 | [Binary search](glossary:binary-search) per [term](glossary:term) | [Binary search](glossary:binary-search) to the block → linear scan inside block |
   | Ex. (8 [terms](glossary:term)) | aid, box, ... all tree nodes                                      | [aid box den ex] [job ox pit win], 2 blocks                                     |
   | Speed                          | Fast                                                              | A bit slower                                                                    |
   - A larger k saves more space but takes longer to scan inside a block

5. [front coding](glossary:front-coding)
   - **[front coding](glossary:front-coding)**: when [terms](glossary:term) in a block share a prefix, write the prefix only once (they're sorted, so neighbors often share a prefix)
   - `8automata8automate9automatic10automation` → `8automat*a1◇e2◇ic3◇ion`
   - How to read it: `8automat*a` = length 8, the prefix automat ends at `*` → automata / `1◇e` = 1 letter e after the prefix → automate / `2◇ic` → automatic / `3◇ion` → automation
   - Exercise: which prefix should be used, and what's the trade-off?
     - A long prefix saves more letters per [term](glossary:term), but fewer [terms](glossary:term) share it
     - A short prefix is shared by many [terms](glossary:term), but saves fewer letters

6. [Dictionary](glossary:dictionary) size summary ([Reuters](glossary:reuters-rcv1), M = 400,000)

   | Method                                                                  | Computation                             | Size    |
   | ----------------------------------------------------------------------- | --------------------------------------- | ------- |
   | Fixed-width array                                                       | (20 + 4 + 4) × 400,000                  | 11.2 MB |
   | String + [term](glossary:term) pointers                                 | 400,000 × (4 + 4 + 3 + 8)               | 7.6 MB  |
   | + [blocking](glossary:blocking) (k = 4)                                 | 7.6 − 400,000 / 4 × 5 bytes = 7.6 − 0.5 | 7.1 MB  |
   | + [blocking](glossary:blocking) + [front coding](glossary:front-coding) |                                         | 5.9 MB  |

## 5.4 Postings compression

**Store [gaps](glossary:gap-encoding) instead of [docIDs](glossary:docid), and use a [variable length](glossary:variable-length-encoding) code that spends fewer bits on small [gaps](glossary:gap-encoding)**

1. Why compress [postings](glossary:postings-list) / how many bits per [docID](glossary:docid)
   - The [postings](glossary:postings-list) file is at least 10 times bigger than the [dictionary](glossary:dictionary) → storing each [posting](glossary:postings-list) (= one [docID](glossary:docid)) compactly is the key
   - 4-byte integer = 32 bits / only as many as needed: log₂ 800,000 ≈ 19.6 → **20 bits**
   - Goal: far fewer than 20 bits

2. Storing [gaps](glossary:gap-encoding)
   - [Postings](glossary:postings-list) are in ascending [docID](glossary:docid) order → store only **the first [docID](glossary:docid) + the difference ([gap](glossary:gap-encoding)) from the previous one**
   - Example: computer 283154, 283159, 283202 → 283154, 5, 43

   | [term](glossary:term) | [docID](glossary:docid)        | [gap](glossary:gap-encoding) |
   | --------------------- | ------------------------------ | ---------------------------- |
   | the                   | 283042, 283043, 283044, 283045 | 1, 1, 1                      |
   | computer              | 283047, 283154, 283159, 283202 | 107, 5, 43                   |
   | arachnocentric        | 252000, 500100                 | 252000, 248100               |
   - A frequent [term](glossary:term) (the) has small [gaps](glossary:gap-encoding) / a rare [term](glossary:term) (arachnocentric) has large ones

3. [Variable length encoding](glossary:variable-length-encoding)
   - An encoding that uses **few bits for small [gaps](glossary:gap-encoding) and many for large [gaps](glossary:gap-encoding)**
   - Goal: about 20 bits per [gap](glossary:gap-encoding) for rare [terms](glossary:term) like arachnocentric, only a few bits per [gap](glossary:gap-encoding) for common [terms](glossary:term) like the
   - Two methods: byte-level [VB code](glossary:variable-byte-code) / bit-level [γ code](glossary:gamma-code)

4. [VB code](glossary:variable-byte-code) ([variable byte](glossary:variable-byte-code))

   ![VB code: split into 7 bits each, only the last byte has c=1 / gamma code: 13 → 1101 → offset 101, length 3 → 1110 → 1110101](/static/images/information-retrieval-ch5-index-compression/vb-gamma.svg)
   - Widely used in commercial and research systems. [Variable length](glossary:variable-length-encoding), yet [aligned](glossary:alignment) to byte boundaries
   - One byte = **1 [continuation bit](glossary:continuation-bit) c (first) + 7 bits of number**
   - Encoding: keep dividing by 128 and fill in the remainders from the back (7 bits each) → **only the last byte has c = 1**, the rest have c = 0
   - Examples: 824 = 6 × 128 + 56 → `00000110 10111000` / 5 → `10000101` / 214577 = 13·128² + 12·128 + 49 → `00001101 00001100 10110001`
   - Decoding: n = 128 × n + (7-bit value); when a byte with c = 1 arrives, one number is done → start again with n = 0
   - Exercise: 130 = 1 × 128 + 2 → `00000001 10000010`
   - In the figure: top = [VB](glossary:variable-byte-code) (orange c = 1 = last byte)

   ```text
   VBEncodeNumber(n)
   1 bytes <- < >
   2 while true
   3 do Prepend(bytes, n mod 128)
   4    if n < 128
   5      then Break
   6    n <- n div 128
   7 bytes[Length(bytes)] += 128
   8 return bytes

   VBDecode(bytestream)
   1 numbers <- < >
   2 n <- 0
   3 for i <- 1 to Length(bytestream)
   4 do if bytestream[i] < 128
   5      then n <- 128 * n + bytestream[i]
   6      else n <- 128 * n + (bytestream[i] - 128)
   7           Append(numbers, n)
   8           n <- 0
   9 return numbers
   ```

   - VBEncodeNumber: repeatedly prepend the remainder mod 128 → add 128 to the last byte (= c bit 1)
   - VBEncode: run VBEncodeNumber on each number and concatenate
   - VBDecode: if below 128 (c = 0), keep accumulating; if 128 or more (c = 1), subtract 128 and accumulate → one number complete

5. Other variable codes
   - Units ([alignment](glossary:alignment)) other than bytes are possible: 32 bits (word), 16 bits, 4 bits ([nibble](glossary:nibble))
   - With many small [gaps](glossary:gap-encoding), bytes are wasteful → [nibbles](glossary:nibble) are better
   - There are also [word-aligned](glossary:word-aligned-code) codes that pack several [gaps](glossary:gap-encoding) into one word

6. Gamma ([γ](glossary:gamma-code)) code
   - **Bitlevel code**: compresses better than [VB](glossary:variable-byte-code). The best known is [γ](glossary:gamma-code)
   - **[unary](glossary:unary-code)**: n → n ones + 0. E.g. 3 → `1110`, 40 → 40 ones + 0
   - **[γ](glossary:gamma-code) = length ([unary](glossary:unary-code)) + offset**
     - offset = the binary number with the leading 1 removed: 13 → `1101` → `101`
     - length = the number of offset bits in [unary](glossary:unary-code): 3 → `1110`
     - [γ](glossary:gamma-code)(13) = `1110,101`
   - Examples: 1 → `0` (no offset) / 2 → `10,0` / 3 → `10,1` / 4 → `110,00` / 9 → `1110,001` / 24 → `11110,1000` / 511 → `111111110,11111111` / 1025 → `11111111110,0000000001`
   - 0 has no [γ code](glossary:gamma-code) ([gaps](glossary:gap-encoding) are at least 1, so it doesn't matter)
   - Exercise: 130 = `10000010` → offset `0000010` (7 bits) → length 7 → `11111110` → [γ](glossary:gamma-code)(130) = `11111110,0000010`
   - Decoding: count 1s until a 0 (= number of offset bits) → read that many bits → prepend a 1 to get the binary → decimal
   - In the figure: bottom = 13 → 1101 → drop the leading 1 → length 3 in [unary](glossary:unary-code) → concatenate

7. [γ code](glossary:gamma-code) length
   - offset = ⌊log₂G⌋ bits, length = ⌊log₂G⌋ + 1 bits
   - **Total = 2⌊log₂G⌋ + 1 bits** → always odd. E.g. 13 → 2 × 3 + 1 = 7 bits
   - Within **a factor of 2** of the optimal length log₂G (when the assumption about the [gap](glossary:gap-encoding) distribution roughly holds)

8. Properties of [γ codes](glossary:gamma-code)
   - **[prefix-free](glossary:prefix-free-code)**: no code is the beginning of another → can be concatenated without separators and still decoded (same for [VB](glossary:variable-byte-code))
   - Within a factor of 3 of optimal (2 with more assumptions). **Holds regardless of the [gap](glossary:gap-encoding) distribution**
   - **[universal](glossary:universal-code)**: usable for any distribution
   - **[parameter-free](glossary:parameter-free-code)**: no parameters to fit

9. [γ](glossary:gamma-code) vs [VB](glossary:variable-byte-code): [alignment](glossary:alignment)
   - Computers work on 8, 16, 32-bit boundaries → compressing and manipulating at the [bit level](glossary:bit-level-code) can be slow
   - [VB](glossary:variable-byte-code) is [aligned](glossary:alignment) to byte boundaries, so it can be faster

   |                | [VB](glossary:variable-byte-code)         | [γ](glossary:gamma-code) |
   | -------------- | ----------------------------------------- | ------------------------ |
   | Unit           | Byte                                      | Bit                      |
   | Size           | 116 MB ([Reuters](glossary:reuters-rcv1)) | 101 MB (smaller)         |
   | Speed          | Fast ([aligned](glossary:alignment))      | Can be slow              |
   | Implementation | Simple                                    | Complex                  |
   - [VB](glossary:variable-byte-code) uses a bit more space but is conceptually simpler
