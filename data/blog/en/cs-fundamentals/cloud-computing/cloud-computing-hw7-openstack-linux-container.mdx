This homework covers the labs in chapters 13 to 15 of the textbook. The first half deploys [OpenStack](glossary:openstack) on a single node with [Kolla-Ansible](glossary:kolla-ansible) and creates [instances](glossary:instance) from the [dashboard](glossary:horizon) and the command-line tools. The second half builds a [container](glossary:container) network (the setup on slide p67) by hand with Linux network namespaces. I first installed [OpenStack](glossary:openstack) inside a [Rocky](glossary:rocky-linux) [VM](glossary:vm) as the slides do, but gave up after running the deployment 8 times over more than 6 hours. That process is written up separately in [section 5](#5-problems-during-the-lab).

# 0. Lab Environment

I used the same [Ubuntu](glossary:ubuntu) host as since HW2 ([Ubuntu](glossary:ubuntu) 24.04 [aarch64](glossary:arm64) on [UTM](glossary:utm) on an Apple M3 Mac, 9.7GiB of memory, 6 [vCPUs](glossary:vcpu)). Because the host is [aarch64](glossary:arm64), I used [aarch64](glossary:arm64) builds of every image, and I noted under each figure where commands differ from the slides.

- **[OpenStack](glossary:openstack)**: Installed directly on the [Ubuntu](glossary:ubuntu) host instead of adding one more [VM](glossary:vm) level. Installing it inside a [Rocky](glossary:rocky-linux) [VM](glossary:vm) makes a three-level [nesting](glossary:nested-virtualization) of Mac → [UTM](glossary:utm) → [Ubuntu](glossary:ubuntu) → [KVM](glossary:kvm) → [Rocky](glossary:rocky-linux), and the deployment never finished because of [timeouts](glossary:timeout).
- **Linux [containers](glossary:container)**: Done in a [Rocky Linux](glossary:rocky-linux) 10.2 [aarch64](glossary:arm64) [VM](glossary:vm), `lxc.cloud.org`, created on the host's [KVM](glossary:kvm).

```text
Ubuntu host yoosung-vm (enp0s1 192.168.64.4 = internal VIP, dashboard http://192.168.64.4)
├─ Docker containers: keystone, glance, nova, neutron, placement, heat, horizon, mariadb, rabbitmq ...
├─ veth1 (neutron_external_interface) ⇄ veth0
├─ Instances (KVM): stackvm-1, stackvm-2, stackvm-3 ── demo-net 10.0.0.0/24
└─ KVM ─ lxc.cloud.org (Rocky 10.2)  ← network namespace lab
```

# 1. Preparing the OpenStack Installation

## Interface for the External Network

The slides hand enp0s8, one of two NICs, entirely over to the [neutron](glossary:neutron) external network. This host has only one NIC, enp0s1, and handing it over would cut off access to the host, so I created a [veth](glossary:veth) pair with [NetworkManager](glossary:networkmanager) and used one end (veth1) as the external interface.

```bash
ip -br addr | grep -v vnet
sudo nmcli con add type veth con-name veth0 ifname veth0 veth.peer veth1 ipv4.method disabled ipv6.method disabled
sudo nmcli con add type veth con-name veth1 ifname veth1 veth.peer veth0 ipv4.method disabled ipv6.method disabled
ip -br link show type veth
```

## Preparing the Host

[Kolla](glossary:kolla-ansible) runs [libvirt](glossary:libvirt) in the `nova_libvirt` [container](glossary:container), and if the [libvirt](glossary:libvirt) installed on the host in HW6 is still running, prechecks stops. I turned off every [libvirt](glossary:libvirt) unit on the host and checked the firewall and time synchronization. Units given as a glob are not disabled, so I listed them one by one.

```bash
sudo systemctl disable --now libvirt-guests.service libvirtd.service virtlockd.service virtlogd.service \
  libvirtd-admin.socket libvirtd-ro.socket libvirtd.socket virtlockd-admin.socket virtlockd.socket \
  virtlogd-admin.socket virtlogd.socket
systemctl is-active libvirtd libvirtd.socket virtlogd
sudo ufw status
timedatectl | grep -E 'synchronized|NTP'
```

## globals.yml

Five values changed compared with the slides.

- `kolla_base_distro: "ubuntu"`: The host is [Ubuntu](glossary:ubuntu), so I used the [Ubuntu](glossary:ubuntu) builds of the [container images](glossary:container-image) too.
- `network_interface: "enp0s1"`, `neutron_external_interface: "veth1"`
- `enable_haproxy: "no"`, `kolla_internal_vip_address: "192.168.64.4"`: With a single node, I turned off the load balancer ([haproxy](glossary:haproxy)·[keepalived](glossary:keepalived)) and set the [VIP](glossary:virtual-ip) to the host IP.
- `openstack_tag_suffix: "-aarch64"`: With the default `""`, it pulls the `2026.2-ubuntu-noble` tag, which has no [arm64](glossary:arm64) manifest.

```bash
sed -i -e 's/^#kolla_base_distro:.*/kolla_base_distro: "ubuntu"/' \
  -e 's/^#network_interface:.*/network_interface: "enp0s1"/' \
  -e 's/^#neutron_external_interface:.*/neutron_external_interface: "veth1"/' \
  -e 's/^#\?kolla_internal_vip_address:.*/kolla_internal_vip_address: "192.168.64.4"/' \
  -e 's/^#enable_haproxy:.*/enable_haproxy: "no"/' globals.yml
echo 'openstack_tag_suffix: "-aarch64"' >> globals.yml
```

To upload images from the [dashboard](glossary:horizon), [glance](glossary:glance) has to allow the [dashboard](glossary:horizon) address through [CORS](glossary:cors).

[cors]
allowed_origin = http://192.168.64.4,http://localhost:8080
allow_headers = Content-Type,X-Auth-Token,X-CSRFToken,X-Image-Meta-Checksum,Content-MD5,X-OpenStack-Request-ID

# 5. Problems During the Lab

## Problem 1. Deployment Inside the Rocky VM Never Finished

At first I created a [Rocky](glossary:rocky-linux) [VM](glossary:vm) (`openstack`, 8GiB, 4 [vCPUs](glossary:vcpu)) as in the slides and installed all-in-one inside it. The slides have two levels, x86 PC → VirtualBox → [Rocky](glossary:rocky-linux), but in this environment it becomes three levels of [nesting](glossary:nested-virtualization): Mac → [UTM](glossary:utm) → [Ubuntu](glossary:ubuntu) → [KVM](glossary:kvm) → [Rocky](glossary:rocky-linux). On top of that, [Kolla](glossary:kolla-ansible) starts dozens of [containers](glossary:container).

bootstrap-servers and prechecks passed. These were the measurements 37 minutes after deploy started.

| Measurement                                                                                    | Value                                 |
| ---------------------------------------------------------------------------------------------- | ------------------------------------- |
| [Rocky](glossary:rocky-linux) [load average](glossary:load-average) (4 [vCPUs](glossary:vcpu)) | 28–33, [I/O wait](glossary:io-wait) 0 |
| [Ubuntu](glossary:ubuntu) host [CPU steal](glossary:cpu-steal)                                 | 55–59%                                |
| CPU of the [VM](glossary:vm) process on the Mac                                                | 285%                                  |
| 50 runs of `/bin/true` ([Ubuntu](glossary:ubuntu) / [Rocky](glossary:rocky-linux))             | 0.013 s / 0.908 s (about 70×)         |
| `python3 -c pass` ([Rocky](glossary:rocky-linux))                                              | 2.9 s                                 |

The bottleneck was neither disk nor network but the cost of going through three layers of virtualization every time a process is created. From then on, [Kolla](glossary:kolla-ansible)'s [timeout](glossary:timeout) defaults broke one by one.

| Run | Time        | Result                                                | What broke and the fix                                                                                                                                                                                                                                                        |
| --- | ----------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 12:29–13:20 | Stuck at [rabbitmq](glossary:rabbitmq) for 25 minutes | The [healthcheck](glossary:health-check) `rabbitmq-diagnostics ping`, run every 30 seconds, never finished and 22 piled up → `enable_container_healthchecks: "no"`                                                                                                            |
| 2   | 13:28–13:55 | Failed (ok=33)                                        | [Containers](glossary:container) created in run 1 kept their [healthcheck](glossary:health-check) settings and piled up again, `docker ps` 40 seconds → `kolla-ansible destroy` (3 min 26 s)                                                                                  |
| 3   | 14:00–14:37 | Failed (ok=204)                                       | [keystone](glossary:keystone) bootstrap rc=1 after 4 min 59.8 s. The same command run by hand succeeded in 37 seconds                                                                                                                                                         |
| 4   | 14:37–15:43 | Failed (ok=232)                                       | `ovs-vsctl -t 5` didn't finish within 5 seconds, SIGALRM → `timeout: 60` on the [openvswitch](glossary:open-vswitch)·ovn-controller roles                                                                                                                                     |
| 5   | 15:46–16:25 | Failed (ok=287)                                       | [nova](glossary:nova) API 503. The [keepalived](glossary:keepalived) check (2-second interval, FAULT after 2 failures) didn't finish in time, 49 FAULTs, each dropping the [VIP](glossary:virtual-ip) for 20–40 seconds → interval 10, [timeout](glossary:timeout) 60, fall 6 |
| 6   | 16:28–16:52 | Failed (ok=281)                                       | Same 503 with 0 FAULTs. The nova_api [uwsgi](glossary:uwsgi) started while the [VIP](glossary:virtual-ip) was missing in run 5 stayed in a `no python application found` state → `docker restart nova_api nova_metadata`                                                      |
| 7   | 16:56–17:49 | Failed (ok=343)                                       | [Docker API](glossary:docker) ReadTimeout (default 120 seconds) in the [neutron](glossary:neutron) restart handler. [Load average](glossary:load-average) 128–144, 3 min 41 s for one `docker ps -q` → `docker_client_timeout: 600`, worker count 1                           |
| 8   | 17:56–18:46 | Stopped                                               | Most [containers](glossary:container) restarting because of changed settings, [load average](glossary:load-average) 113                                                                                                                                                       |

Run 7 reached ok=343, so a few more runs might have finished the deployment itself. I stopped there anyway for two reasons.

- There is no `/dev/kvm` inside [Rocky](glossary:rocky-linux), so [nova](glossary:nova) has to start [instances](glossary:instance) with [TCG](glossary:tcg) (software emulation). With emulation on top of a place where process creation is 70 times slower, there was no telling whether the [instance](glossary:instance) labs would work.
- What the homework asks for is "the result of building [OpenStack](glossary:openstack)", and the [Rocky](glossary:rocky-linux) [VM](glossary:vm) in the slides is a means of building it.

So I deleted the [Rocky](glossary:rocky-linux) [VM](glossary:vm), removed one level, and installed directly on the [Ubuntu](glossary:ubuntu) host. [Ubuntu](glossary:ubuntu) has `/dev/kvm`, so [nova](glossary:nova) uses [KVM](glossary:kvm) directly. With the same [Kolla](glossary:kolla-ansible) version, the first deployment finished with failed=0 in 13 minutes 22 seconds.

Three lessons remain.

- Each added level of [nesting](glossary:nested-virtualization) breaks, in turn, [timeout](glossary:timeout) defaults that were assumed to be "long enough". The order was [healthcheck](glossary:health-check) 30 seconds → `ovs-vsctl` 5 seconds → [keepalived](glossary:keepalived) 2 seconds → [Docker API](glossary:docker) 120 seconds.
- [Kolla](glossary:kolla-ansible) deploy does not restart [containers](glossary:container) whose settings haven't changed. A service that failed at startup ([uwsgi](glossary:uwsgi) that couldn't load the app) stays that way even if the deployment is run again, so it has to be restarted by hand.

## Problem 2. cirros Hangs at virtio_blk

The first [instance](glossary:instance) created on the [Ubuntu](glossary:ubuntu) host hung during boot right after the `virtio_blk` message. CPU was at 100% and the guest clock didn't go past 9 seconds. [cirros](glossary:cirros) 0.6.3 was the same.

## Connecting Through a Bridge

A [veth](glossary:veth) pair only connects two ends. When there are more namespaces, a [bridge](glossary:linux-bridge) goes in the root and the opposite end (brif) of each [namespace](glossary:network-namespace)'s [veth](glossary:veth) is plugged into the [bridge](glossary:linux-bridge).

ip link set veth1 netns netns1
ip link set veth2 netns netns2

ip netns exec netns2 ip a add 10.0.100.102/24 dev veth2

## External Access with NAT

Going outside needs three more things: a [default route](glossary:default-gateway) in the namespaces pointing to br0, [IP forwarding](glossary:ip-forwarding) in the root, and [masquerade](glossary:masquerade) that rewrites the 10.0.100.0/24 source to the enp1s0 address.

```bash
ip netns exec netns1 ip route add default via 10.0.100.1
ip netns exec netns2 ip route add default via 10.0.100.1
sysctl -w net.ipv4.ip_forward=1
firewall-cmd --permanent --zone=public --add-masquerade
firewall-cmd --permanent --zone=public --add-rich-rule='rule family="ipv4" source address="10.0.100.0/24" masquerade'
firewall-cmd --reload
ip netns exec netns1 ping -c 2 8.8.8.8
```

## Ch14-3. A Case Where a Container-Based Service Is More Efficient

I chose Spotify's move to [Kubernetes](glossary:kubernetes) as the case. Spotify ran its [containers](glossary:container) with Helios, an [orchestration](glossary:container-orchestration) tool it built in-house, and then moved to [Kubernetes](glossary:kubernetes). According to the CNCF case study, after the move [Kubernetes](glossary:kubernetes)' [bin-packing](glossary:bin-packing) and [multi-tenancy](glossary:multi-tenancy) raised CPU utilization 2–3 times on average, and the time to create a new service and get capacity ready for deployment dropped from nearly an hour to seconds or minutes. Doing the same thing with [VMs](glossary:vm) would mean starting a full OS for every service, which would not reach this density and speed.

There are four reasons container-based services are better.

- **Density (resource efficiency)**: [Containers](glossary:container) share the host kernel and only isolate (namespaces) and limit ([cgroups](glossary:cgroup)) at the process level, so unlike [VMs](glossary:vm) they don't keep a separate guest OS kernel, memory and boot disk per service. More services can therefore be packed tightly onto one node ([bin-packing](glossary:bin-packing)), and Spotify's 2–3× CPU utilization improvement is this effect.
- **Performance overhead**: Felter et al. (2015) at IBM Research compared [KVM](glossary:kvm) [VMs](glossary:vm) and [Docker](glossary:docker) [containers](glossary:container) on the same hardware and reported that [containers](glossary:container) performed equal to or better than [VMs](glossary:vm) in almost every measurement. This is because [VM](glossary:vm) I/O goes through the [hypervisor](glossary:hypervisor) one more time, and they added that both need tuning for I/O-intensive workloads.
- **Startup time and deployment speed**: [Containers](glossary:container) start processes without booting an OS, so they start in seconds. Services with hundreds of [microservices](glossary:microservices) deploy, scale and roll back often, and this speed led to Spotify's shorter service creation time.
- **Portability and consistency**: The application and its libraries are bundled into one [image](glossary:container-image), and the same [image](glossary:container-image) is used in development, testing and production. [Images](glossary:container-image) are smaller than [VM](glossary:vm) images, so they are easier to pull from a [registry](glossary:container-registry) and to version.

However, [containers](glossary:container) share the kernel, so their isolation is weaker than [VMs](glossary:vm). When mutually untrusted users share one host or a different OS kernel is needed, [VMs](glossary:vm) are better, which is why running [containers](glossary:container) on top of [VMs](glossary:vm) is common in practice.

References

- CNCF, "Spotify Case Study," 2019. https://www.cncf.io/case-studies/spotify/
- W. Felter, A. Ferreira, R. Rajamony, J. Rubio, "An Updated Performance Comparison of Virtual Machines and Linux Containers," IEEE ISPASS 2015, pp. 171–172.
