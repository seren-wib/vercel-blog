> 시리즈 12편. 구축 6단계(바깥이랑 잇기) 중 리더의 배포 실행기, 구축 09′을 한 11월 11일 이야기다. 같은 단계의 플랫폼 서버 쪽은 [11편](/kr/blog/woowangthon/woowangthon-11-server-link/)에, 전체 그림은 [Woowangthon 0](/kr/blog/woowangthon/woowangthon-00-overview/)에 있다.

## 한 줄 요약

학생 앱 배포는 리더에서 도는 GoCD 실행기가 한다. 그 실행기가 쓸 계정을 만들었는데, 클러스터 전체 권한은 하나도 없고 학생 공간마다 붙는 권한 연결 하나로만 일한다. 권한이 못 막는 것은 검사 규칙 넷이 막는다. 그중 하나는 셀프 리뷰가 찾았다. 학생 Service가 이미지 캐시 주소를 자기 것이라고 적을 수 있었다. 실행기 Pod 매니페스트도 만들었지만 GoCD 서버가 아직 없어서 리더에 올리지 않았고, 같은 모양의 임시 Pod로만 확인했다. 서버 등록과 사설망 길은 아직 아무도 안 봤다.

## 1. 실행기를 리더에 두는 이유

배포를 누가 하느냐는 [7편의 회의](/kr/blog/woowangthon/woowangthon-07-leader-vllm/#1-회의에서-바뀐-것)에서 정했다(ADR-009). GoCD 서버는 플랫폼 서버와 같은 AWS EC2에 두고, 일을 실제로 하는 실행기(GoCD Agent)는 리더에서 돌린다.

배포 한 번은 이렇게 나뉜다.

| 단계             | 어디서      | 하는 일                                                           |
| ---------------- | ----------- | ----------------------------------------------------------------- |
| Build            | AWS         | 학생 레포로 이미지를 만들어 올린다                                |
| Prepare · Render | 리더 실행기 | 대상 슬롯을 비우고, 매니페스트를 만들어 서버 쪽 dry run에 넣는다  |
| Apply            | 리더 실행기 | 적용하고 Pod가 Ready가 될 때까지 기다린다                         |
| Verify · Switch  | 리더 실행기 | Traefik을 거쳐 새 슬롯에 요청해 보고, 통과하면 공개 주소를 옮긴다 |

서버가 실행기를 부르는 게 아니라, 실행기가 서버로 일을 받으러 간다. 리더가 사설망(Tailscale)으로 EC2의 GoCD 서버에 먼저 붙어서 할 일을 받아 간다. [학교로 들어오는 포트는 여전히 0개](/kr/blog/woowangthon/woowangthon-00-overview/#5-전체-구조)다.

리더에 두는 이유는 둘이다. 학생 공간에 쓰는 권한이 클러스터 밖으로 안 나가고, 동작 확인이 클러스터 안의 Traefik에 바로 닿는다. 다른 길도 ADR에 남겼다.

| 대안                                    | 버린 이유                                                                             |
| --------------------------------------- | ------------------------------------------------------------------------------------- |
| 플랫폼 서버가 직접 배포                 | 적용 · 대기 · 동작 확인 · 되돌리기를 서버 코드로 다 짜야 하고, 쓰기 권한이 AWS에 있다 |
| EC2의 실행기가 사설망 너머로 배포       | 쓰기 권한이 클러스터 밖에 남고, 동작 확인을 사설망 너머에서 해야 한다                 |
| ArgoCD(클러스터 안에서 git을 당겨 온다) | 회의 때 검토하지 않았다. AI 담당이 따로 보는 중이고, 팀이 바꾸면 이 단계가 바뀐다     |

## 2. 계정을 둘로

[7편에서 권한 절을 다시 쓸 때](/kr/blog/woowangthon/woowangthon-07-leader-vllm/#1-회의에서-바뀐-것) 계정을 둘로 나눴다. 플랫폼 서버 계정은 공간을 만들고 비밀값을 넣고 상태를 읽는다. 그 계정은 하루 먼저 구축 09에서 들어갔다([11편](/kr/blog/woowangthon/woowangthon-11-server-link/)). 이번 글은 나머지 하나, 배포 실행기 계정 `deploy/deploy-executor`다.

나눈 이유는 털렸을 때의 범위다. 실행기는 GoCD 서버가 시키는 명령을 그대로 돌린다. GoCD 서버는 인터넷에 붙은 EC2에 있다. 그쪽이 털리면 실행기 계정으로 할 수 있는 일은 전부 공격자 손에 간다. 그래서 이 계정이 할 수 있는 일을 "학생 공간 안의 배포"로 좁히는 게 이번 단계의 거의 전부였다.

토큰은 따로 만들지 않았다. 실행기 Pod가 `deploy` 공간에서 뜨면 쿠버네티스가 기한 있는 토큰을 파일로 넣어 준다. 리더 밖으로 나가는 토큰이 없고, 손으로 폐기할 것도 없다.

## 3. 클러스터 전체 권한이 0

실행기 계정에는 클러스터 전체에 걸리는 권한 연결(ClusterRoleBinding)이 하나도 없다. 할 수 있는 일은 역할 `proj-deployer`에 모아 두고, 그 역할은 권한 연결 `deploy-executor`가 있는 공간에서만 생긴다. 이 연결은 플랫폼 서버가 학생 공간을 만들 때 같이 만든다. [9편의 학생 공간 양식](/kr/blog/woowangthon/woowangthon-09-student-space/#1-학생-공간-하나에-들어가는-것)이 다섯 객체에서 여섯 객체가 됐다.

공간마다 연결을 두는 이유는 읽기 때문이다. 실행기는 롤아웃을 기다리고 동작을 확인하느라 Pod, 이벤트, Endpoints를 읽어야 한다. 그런데 다음 절의 검사 규칙은 쓰기만 걸러서, 읽기는 공간 이름으로 좁힐 수 없다. 읽기를 클러스터 전체에 주지 않으려면 어차피 공간마다 연결이 있어야 한다. 그럼 쓰기도 그 연결에 같이 담으면 된다. 연결이 없는 공간에서는 아무것도 못 한다.

설계 문서에는 이 이유가 "`kubectl apply`는 쓰기 전에 대상을 읽는다"로 적혀 있다. 그런데 같은 날 머지된 파이프라인 코드(suda5936의 Render 단계)는 kubectl을 안 쓰고 k3s API를 직접 부른다(server-side apply). 그 문장의 전제는 틀렸다. 결론은 그대로다. 롤아웃 대기와 동작 확인에 읽기가 필요하기 때문이다.

![실행기 계정의 권한. ClusterRoleBinding은 0개, RoleBinding은 proj-demo와 student-template 둘. proj-demo에서는 Deployment · Middleware 만들기와 Pod 읽기만 yes이고 Secret · 로그 · exec는 no. kube-system에서는 전부 no, 노드 읽기도 no](/static/images/woowangthon-12-deploy-executor/rights.svg)

_리더에서 실행기 계정으로(impersonation) 물어본 결과. 아래 표는 `kubectl auth can-i`를 공간과 항목마다 돌린 것이다_

없는 것도 일부러 고른 것이다.

| 없는 권한                                         | 이유                                                                                 |
| ------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Secret 읽기 · 쓰기                                | 학생 비밀값은 플랫폼 서버가 넣는다. 실행기는 서버가 남긴 키 이름 목록으로만 확인한다 |
| Pod 로그 · Pod 안 명령 실행                       | 로그는 플랫폼 서버가 읽는다. 명령 실행은 공간 안 Secret을 꺼내는 길이 된다           |
| Pod 직접 만들기                                   | 배포는 Deployment로만 한다                                                           |
| 네임스페이스 · 상한 · 차단 규칙 · 권한 연결       | 털렸을 때 자기 제한부터 풀 수 있으면 안 된다                                         |
| IngressRoute 같은 Traefik 리소스(Middleware 빼고) | Ingress 하나로 충분하다                                                              |

`student-template`에 연결이 하나 더 보이는 건 비교용이다. [9편](/kr/blog/woowangthon/woowangthon-09-student-space/#1-학생-공간-하나에-들어가는-것)의 양식을 그대로 적용해 둔 기준 공간인데, 플랫폼 서버가 만드는 연결이 양식과 같은지 검사 규칙이 여기 있는 것과 비교한다. 대신 RBAC만 보면 실행기가 이 공간에 쓸 수 있다. 그걸 막는 게 다음 절의 첫 규칙이다.

## 4. 권한이 못 막는 것은 검사 규칙이

RBAC는 "이 종류의 객체를 만들 수 있나"까지만 본다. 내용은 안 본다. Deployment를 만들 수 있으면 리더에 뜨는 Deployment도 만들 수 있다. 그래서 검사 규칙(ValidatingAdmissionPolicy)으로 내용을 거른다. 이번에 더하거나 넓힌 건 넷이다.

| 규칙                           | 통과 조건                                                           | 걸리는 계정 |
| ------------------------------ | ------------------------------------------------------------------- | ----------- |
| `wanggane-deploy-executor`     | 실행기 계정의 쓰기 · 삭제는 `proj-`로 시작하는 공간에서만           | 실행기      |
| `wanggane-student-middlewares` | `proj-` 공간의 Middleware는 `spec`에 `stripPrefix` 하나만           | 모두        |
| `wanggane-student-services`    | `proj-` 공간의 Service는 ClusterIP 타입이고 `externalIPs`가 없다    | 모두        |
| `wanggane-student-pods`        | `NET_RAW` 빼기 · API 토큰 끄기에 더해, toleration과 `nodeName` 금지 | 모두        |

"모두"는 운영자인 나도 포함이다. 실수로 내가 만들어도 거절된다.

첫 규칙은 3절의 기준 공간 같은 경우를 막는 둘째 겹이다. 권한 연결이 어디에 잘못 생겨도 실행기는 `proj-` 밖에 못 쓴다.

Middleware는 suda5936이 올린 이슈([woowangthon/WOOWANGTHON_TEAM_18#72](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/issues/72))에서 시작했다. 배포 입력에 `stripPrefix`가 있다. 공개 경로가 `/api`면 방문자의 `/api/users`를 학생 백엔드에는 `/users`로 넘기는 기능이다. Ingress만으로는 안 되고 Traefik의 Middleware가 필요한데, 실행기 권한에 Middleware가 없었다. 이슈는 둘 중 하나를 골라 달라고 했다. 권한을 주는 것과, `stripPrefix`를 막고 학생 앱이 `/api`까지 받게 하는 것이다.

권한을 주기로 했다. 학생 백엔드는 받는 경로가 제각각이고(`/api/usr`인 곳도, `/usr`인 곳도 있다), 프로젝트마다 주소가 하나라 백엔드를 다른 이름으로 뺄 수도 없다. 대신 Middleware는 `stripPrefix` 하나만 통과시킨다. Middleware는 요청이 앱에 닿기 전에 요청을 바꾸는 물건이다. 리다이렉트는 방문자를 다른 곳으로 보내고, `forwardAuth`는 요청 머리글을 다른 서버로 보낸다. 학생 공간에서 그런 걸 만들 이유가 없다.

`NET_RAW`와 API 토큰은 [9편](/kr/blog/woowangthon/woowangthon-09-student-space/#1-학생-공간-하나에-들어가는-것)에서 이미 걸어 둔 규칙이다. 남은 둘, Service와 toleration · `nodeName`은 이야기가 따로 있다.

## 5. 학생 Service가 이미지 캐시 주소를 적으면

PR([woowangthon/WOOWANGTHON_TEAM_18#114](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/114))을 열고 셀프 리뷰(에이전트의 코드 리뷰)를 돌렸다. 아홉 개가 나왔고, 그중 하나가 이번 단계에서 가장 컸다.

실행기 계정은 Service를 만들 수 있다. Service에는 `externalIPs`라는 필드가 있다. 여기 주소를 적으면 kube-proxy가 클러스터 안에서 그 주소와 포트로 가는 통신을 이 Service의 Pod로 돌린다. 그 주소가 누구 것인지는 안 따진다. 학생 Service가 `192.168.77.11:5000`, [리더의 이미지 캐시](/kr/blog/woowangthon/woowangthon-08-image-cache/#2-캐시를-어디에-묶나) 주소를 적으면 노드들이 이미지를 받으러 가는 요청을 학생 Pod가 받게 된다.

리뷰가 이걸 짚고, 실행기 계정으로 server dry run을 보내 보니 통과했다. [9편의 자원 상한](/kr/blog/woowangthon/woowangthon-09-student-space/#1-학생-공간-하나에-들어가는-것)은 NodePort와 LoadBalancer 개수만 세서 이 필드를 못 본다. 그래서 규칙을 하나 더 만들었다. 학생 공간의 Service는 ClusterIP여야 하고 `externalIPs`가 없어야 한다. `ExternalName`(아무 이름의 별칭이 되는 Service)도 같이 막았다.

![두 거절. 실행기 계정이 externalIPs 192.168.77.11, 포트 5000인 Service를 dry run으로 만들려 하자 wanggane-student-services가 거절한다. 운영자가 nodeName이 k3s-leader인 Pod를 만들려 하자 wanggane-student-pods가 거절한다](/static/images/woowangthon-12-deploy-executor/refusals.svg)

_글을 쓰며 리더에서 다시 보낸 server dry run. 둘 다 아무것도 만들지 않는다_

쿠버네티스도 경고를 띄운다. `externalIPs`는 사라질 예정(deprecated)이고 "어떤 클러스터에서는 동작하지 않을 수 있다"고 적혀 있다. 사라질 예정인 것과 지금 없는 것은 다르다. 규칙을 넣기 전에는 경고만 찍고 받아 줬다.

규칙을 넣자 다른 시험 하나가 바뀌었다. 학생 공간 시험의 NodePort 거절이, 상한보다 이 규칙에 먼저 걸리게 됐다. 거절되는 건 같지만 이유가 달라져서 그 시험의 기대값도 고쳤다.

이번 구축을 같이 한 에이전트가 쓴 PR이고, 같은 에이전트의 리뷰가 찾은 구멍이다. 혼자 쓰고 혼자 검토하는 구조인데도 리뷰를 따로 돌리면 쓰는 동안 못 본 게 나온다. 사람도 그렇다.

## 6. taint는 이름을 찍은 Pod를 못 막는다

리더에는 [설치 때부터 taint가 걸려 있다](/kr/blog/woowangthon/woowangthon-06-k3s-install/#1-설치-전에-정한-것). 학생 앱이 리더에 못 올라가게 하려는 것이다. 그런데 taint `NoSchedule`이 막는 건 스케줄러가 Pod를 그 노드에 놓는 것이다. 두 길이 남는다.

- **toleration**: Pod에 "이 taint는 견딘다"고 적으면 스케줄러가 리더에도 놓는다.
- **`nodeName`**: Pod에 노드 이름을 처음부터 적으면 스케줄러를 아예 거치지 않는다. 리더의 kubelet이 그냥 띄운다.

리더에는 k3s API, 이미지 캐시, 로컬 모델, 그리고 이 실행기가 있다. 그래서 학생 Pod 규칙이 둘 다 거절하게 했다. 위 그림의 두 번째가 `nodeName: k3s-leader`를 적은 Pod다. 운영자 계정으로 보냈는데도 거절된다.

예외가 둘 있다. 쿠버네티스는 모든 Pod에 toleration 두 개(`not-ready`, `unreachable`, 둘 다 `NoExecute`)를 스스로 넣는다. 노드가 끊겼을 때 Pod를 얼마나 기다렸다 옮길지 정하는 값이다. 이 둘까지 막으면 모든 Pod가 거절되니 통과시킨다.

Pod만이 아니라 Deployment도 같은 규칙으로 본다. Pod만 보면 실행기가 Deployment를 적용할 때는 통과하고, 그 아래 Pod를 만드는 ReplicaSet 이벤트에만 거절이 남는다. 실행기는 적용한 순간 거절을 받아야 실패를 빨리 안다.

## 7. 동작 확인은 Traefik을 거쳐서

Verify 단계는 새 슬롯의 앱이 실제로 응답하는지 본다. 학생 공간은 [같은 공간과 Traefik에서 오는 연결만 받는다](/kr/blog/woowangthon/woowangthon-09-student-space/#1-학생-공간-하나에-들어가는-것). 실행기가 학생 Service로 바로 갈 수 없다. 그래서 실행기는 대상 슬롯의 시험용 주소를 Host 머리글에 적어 워커의 Traefik에 요청한다. 방문자와 같은 길이다. `stripPrefix`도 이 길에서 확인된다.

시험 스크립트(`Infra/executor/check.sh`)는 시험 공간을 하나 만들고, 실행기 계정으로 예시 앱을 실제로 배포한 다음, Traefik을 거쳐 요청한다.

![check.sh의 첫 부분. 실행기 계정으로 dry run, 적용, 롤아웃 대기, 읽기가 통과한다. Traefik을 거친 /readyz 200, stripPrefix가 걸린 /svc/readyz 200, 로그와 exec 거절, Middleware를 떼면 /svc/readyz 404, 0개로 줄이기와 지우기 통과](/static/images/woowangthon-12-deploy-executor/check-deploy.svg)

_예시 앱은 `/readyz`를 받는다. `/svc/readyz`가 200이면 앞부분이 떼인 것이다. Middleware를 떼면 같은 경로가 404가 된다_

시험 공간 이름에서 한 번 걸렸다. [10편에서 배운 대로](/kr/blog/woowangthon/woowangthon-10-public-entry/#시험-공간-proj-check) 학생 이름으로는 못 만드는 `proj--exec`로 지었다. 학생 이름은 하이픈으로 시작할 수 없기 때문이다. 그런데 Ingress가 Middleware를 가리킬 때는 `<공간>-<Middleware 이름>@kubernetescrd`로 적는데, Traefik(3.7.15)은 이 이름에서 연달은 하이픈을 하나로 줄인다. `proj--exec`의 `web-strip`은 Traefik 안에서 `proj-exec-web-strip`이다. 공간 이름을 그대로 적은 주석은 아무것도 가리키지 않고, 그 Ingress 전체가 404가 된다.

시험 공간은 학생 이름의 최대 길이(40자)보다 긴 이름으로 바꿨다. `proj-check-of-the-deploy-executor-not-a-student-space`. 하이픈을 겹치지 않고도 학생 이름과 안 겹친다. 차트는 이제 하이픈을 줄인 이름으로 주석을 적는다.

## 8. 실행기 Pod: 우리 이미지를 만들지 않는다

계정이 생긴 뒤 같은 날 밤에 실행기 Pod 매니페스트(`Infra/executor/agent.yaml`)를 만들었다. 정한 것은 이렇다.

| 정한 것                                                    | 이유                                                                                                          |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| GoCD 공식 실행기 이미지 `gocd-agent-debian-12:v26.1.0`     | GoCD 서버와 같은 버전이어야 붙는다. 서버 버전(26.1.0)과 포트(8153)는 답이 안 와서 내가 정했다                 |
| `node` 24.15.0 · `helm` 3.22.1은 init 컨테이너가 꺼내 온다 | 각 공식 이미지에서 공유 볼륨으로 복사한다. 우리 이미지를 빌드 · 보관하지 않으니 리더에 레지스트리 토큰이 없다 |
| `kubectl` · `aws` 없음                                     | 파이프라인은 k3s API를 직접 부른다. Build는 AWS 실행기 몫이라 학교 PC에 AWS 자격 증명을 둘 이유가 없다        |
| 토큰은 파일 경로로만 넘긴다                                | `KUBE_TOKEN_FILE` 같은 경로만 env에 둔다. 토큰 값이 env나 작업 로그에 안 남는다                               |
| 교체 방식 `Recreate`                                       | 실행기 하나에 이름 하나. 새 Pod가 등록하기 전에 옛 Pod를 내린다                                               |
| 서버 주소 · 등록 키는 리더 Secret `gocd-agent`             | 레포와 채팅에 안 남긴다. Secret이 없으면 Pod가 안 뜬다(`CreateContainerConfigError`). 그게 의도한 실패다      |

`aws`는 원래 계획에 있었다. 계획 문서에는 "node · helm · aws가 든 이미지"라고 적혀 있었는데, 에이전트가 매니페스트를 쓰다가 Build 단계는 AWS에서 돈다는 배포 설계와 어긋난다고 보고 뺐다. 그리고 계획과 다르게 한 것으로 나한테 따로 알렸다. 맞는 판단이라 그대로 갔다.

나가는 길은 NetworkPolicy로 묶었다. 클러스터 DNS, 리더 API(6443), Traefik Pod(8000, Verify), 사설망 대역의 GoCD 포트(8153), 사설 대역을 뺀 인터넷의 443(파이프라인이 git을 받는다)뿐이다. Pod의 통신은 [리더 방화벽이 못 막는다는 걸](/kr/blog/woowangthon/woowangthon-10-public-entry/#리더-방화벽은-cloudflared를-못-막는다) cloudflared 때 배웠으니, 이번엔 처음부터 Pod 쪽 규칙으로 했다. 작업이 털려도 kubelet, 이미지 캐시, 로컬 모델, 노드 대역, 학교망에는 못 닿는다.

## 9. 서버 없이 시험하기

GoCD 서버가 없으니 실행기를 띄워 봐야 등록할 곳이 없다. 대신 확인용 스크립트(`Infra/executor/agent-check.sh`)를 따로 만들었다. 매니페스트의 Pod 틀을 그대로 가져와(같은 노드, 계정, 보안 설정, 도구, env) 실행기 대신 시험 명령을 넣은 임시 Pod를 같은 NetworkPolicy 아래 띄우고, 끝나면 지운다.

처음엔 돌지도 못했다. 에이전트 쪽 자동 승인 검사가 리더에 임시 Pod를 띄우는 명령을 막았다. 에이전트는 우회하지 않고 멈춰서, 무엇을 왜 하려는지 적고 나한테 물었다. 진행하라고 했다.

두 번째는 스크립트가 터졌다.

스크립트는 매니페스트 파일을 `kubectl create --dry-run=client -o json`에 넣어 JSON으로 받은 다음, 그걸 읽어 시험 Pod를 만든다. 파일에는 객체가 둘(NetworkPolicy, Deployment) 있다. 에이전트는 kubectl이 둘을 목록(List) 하나로 감싸 줄 거라고 짐작하고 `.items`를 읽었다. 실제로는 객체 두 개를 그냥 이어서 찍는다. 첫 객체가 끝난 118번째 줄에서 두 번째 `{`가 나오니 JSON 파서가 멈췄다. 이어 붙은 걸 객체 단위로 잘라서 읽게 고쳤고, 다시 돌리니 15개가 다 통과했다.

통과한 것과 거절된 것이 둘 다 의미가 있다. 도구는 init 컨테이너로 제대로 왔고, 실행기 토큰으로 학생 공간이 읽히고, Traefik과 바깥 HTTPS에 닿는다. 그리고 Secret과 `kube-system`은 403, 이미지 캐시와 로컬 모델과 워커 kubelet과 평문 HTTP에는 연결 자체가 안 된다.

계정 쪽 시험(`check.sh`)은 63개다. 이 글을 쓰면서 다시 돌렸더니 처음엔 SSH 연결이 한 번 끊겨 하나가 FAIL로 찍혔고, 다시 돌려 63개가 다 통과했다. 끝부분이 4~6절의 규칙들이다.

## 10. 아직 아무도 못 본 것

실행기 Pod는 머지했지만 리더에 올리지 않았다. GoCD 서버가 들어갈 EC2가 아직 없다. 그래서 이건 하나도 확인되지 않았다.

- GoCD 실행기 프로세스가 이 설정(env, 사용자, 볼륨)으로 실제로 뜨는지
- 자동 등록 키로 서버에 등록되는지, 이름표 `leader`를 단 배포 작업이 이 실행기로만 가는지
- Pod에서 사설망의 GoCD 포트(8153)로 나가는 길. NetworkPolicy는 사설망 대역의 8153을 열어 두었지만, 그 통신이 리더의 Tailscale을 타고 EC2까지 가는지는 안 봤다. 사설망 접근 규칙(리더 → EC2의 8153)도 설계 문서 기준으로 레포 파일에만 있고 관리 화면에는 아직 안 들어갔다
- 시험 파이프라인이 `proj-demo`에 배포하고 Verify까지 통과하는지

계정 쪽은 실제 클러스터에서 실행기 계정으로(impersonation) 시험했고, Pod 틀은 같은 모양의 임시 Pod로 시험했다. 둘을 합친 진짜 실행기는 EC2가 생긴 날 Secret 하나 넣고 적용하면서 처음 본다.

## 11. 정리

| 겪은 일                                                    | 배운 것                                                                                           |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 실행기에 클러스터 전체 권한을 줄 뻔했다                    | 읽기를 공간마다 줘야 한다면 쓰기도 그 연결에 담는다. 연결 없는 공간에서는 아무것도 못 하게 된다   |
| 이유 문장이 `kubectl apply` 전제였는데 코드는 API를 불렀다 | 결정의 이유를 적을 때 그 전제가 바뀌면 문장도 같이 고친다. 결론이 맞아도 이유는 틀릴 수 있다      |
| 학생 Service가 이미지 캐시 주소를 적을 수 있었다           | 남의 공간에 Service를 만들 수 있으면 `externalIPs`부터 막는다. 자원 상한은 이 필드를 안 본다      |
| 리더 taint가 있으니 학생 Pod는 못 올라간다고 봤다          | `NoSchedule` taint는 toleration도, 스케줄러를 건너뛰는 `nodeName`도 못 막는다                     |
| 하이픈 둘로 지은 시험 공간에서 Ingress 전체가 404였다      | Traefik은 Middleware 이름의 연달은 하이픈을 하나로 줄인다. 시험용 이름은 길이로 피했다            |
| 실행기 이미지를 우리가 만들 줄 알았다                      | 공식 이미지에 공식 이미지의 도구를 init 컨테이너로 얹으면, 보관할 이미지도 레지스트리 토큰도 없다 |
| kubectl이 JSON을 목록으로 줄 줄 알았다                     | `--dry-run=client -o json`은 여러 객체를 이어서 찍는다. 읽기 전에 자른다                          |
| 계획에 있던 `aws`를 에이전트가 뺐다                        | 계획과 다르게 할 때는 하고 나서 따로 알린다. 그래야 맞는지 사람이 본다                            |
| 서버가 없어 실행기를 못 띄웠다                             | 같은 Pod 틀의 임시 Pod로 도구 · 권한 · 길을 먼저 본다. 남은 건 등록과 사설망 길 둘로 좁혀졌다     |

계정 PR은 팀장(TaeTaeJin)의 승인을 받아 머지됐고, Pod 매니페스트 PR([woowangthon/WOOWANGTHON_TEAM_18#132](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/132))은 같은 날 밤 머지했다. 6단계에서 클러스터 쪽은 이걸로 할 수 있는 만큼 했다. 나머지는 EC2가 생겨야 움직인다. 그 사이에 7단계, 모니터링으로 넘어갔다([13편](/kr/blog/woowangthon/woowangthon-13-metrics/)).
