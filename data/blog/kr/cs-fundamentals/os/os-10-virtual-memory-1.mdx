# 0. HEX

- `0x`: 이건 [Hexadecimal](glossary:hexadecimal)이다 라는 표시
- 예시
  - `0x4AFE = 4×4096(16^3) + 10×256(16^2) + 15×16(16^1) + 14×1(16^0) = 19198`
- 한자리가 4bit이다([Hexadecimal](glossary:hexadecimal)이기 때문에)

# 1. Paging

## 1. 개념

**[virtual memory](glossary:virtual-memory) → [page table](glossary:page-table) → [physical memory](glossary:physical-memory)**

- 프로세스가 사용하는 메모리를 [Physical memory](glossary:physical-memory) 상의 비연속적인([noncontiguous](glossary:noncontiguous-allocation)) 위치에 나누어 배치할 수 있게 한다.
- [virtual-mem](glossary:virtual-memory)과 [physical-mem](glossary:physical-memory)을 동일한 크기로 자른다(4kb가 대중적)
- 운영체제는 모든 빈 [Frame](glossary:frame)을 추적한다.
- [Virtual address](glossary:virtual-address)를 [Physical address](glossary:physical-address)로 변환하기 위한 [Page table](glossary:page-table)을 설정한다.
- 프로그램을 한 번 종료했다가 재시작하면 [vm](glossary:virtual-memory)은 같은 값이 나오지만 실제 [Physical memory](glossary:physical-memory)는 다른 값이다.

### 유저관점에서 추가 개념

- 유저는 연속적인 메모리만 본다.
  - [Virtual address space](glossary:address-space)
- 실제로 [Page](glossary:page)들은 [Physical memory](glossary:physical-memory) 전체에 흩어져([scattered](glossary:noncontiguous-allocation)) 저장된다.
  - [Virtual address](glossary:virtual-address)를 [Physical address](glossary:physical-address)로 변환하는 매핑이 존재한다.
  - 이 매핑 과정은 프로그램에게 보이지 않는다.
- process A가 process B에 엑세스 못해서 자연스럽게 protection도 해결된다.
- Process A는 Process B의 메모리 구조나 [Page](glossary:page) 매핑 정보를 알 수 없어야 한다.
  - 왜냐:
    - 다른 프로세스의 데이터를 읽을 수 있고
    - 다른 프로세스의 데이터를 수정할 수 있고
    - 시스템 전체의 보안과 안정성이 깨질 수 있으니까
- 그래서 절대 유저레벨에게 보여주지 않는다.

### 장점

1. [Physical memory](glossary:physical-memory) 할당이 쉽다.
2. [External fragmentation](glossary:external-fragmentation)이 없다.
3. [page out](glossary:page-out)(메모리 꽉차면 디스크로 내려보내는거)이 쉽다.
4. [Page](glossary:page) 보호가 쉽다([protection bit](glossary:protection-bit) + [valid bit](glossary:valid-bit)을 사용하기 때문에).
5. [Page](glossary:page) 공유가 쉽다(OS가 [Page table](glossary:page-table)에서 같은 [PFN](glossary:pfn)을 가리키게 하면 되기 때문에).

### 단점

1. [Internal fragmentation](glossary:internal-fragmentation) 발생 가능(4kb여서 크게 문제는 안됨) + 뒤에 [segmentation](glossary:segmentation) 기법이랑 같이 사용해서 잘 발생 안함
2. 모든 메모리 access를 2번이나 해야해서 2배씩 느려짐
   - 해결법: [TLB](glossary:tlb) 사용
3. [Page table](glossary:page-table)이 너무 큼 → 해결책 [multi-level](glossary:multi-level-page-table) / [inverted page table](glossary:inverted-page-table)

## 2. virtual address

**[virtual address](glossary:virtual-address)란 프로세스가 생성하는 [Virtual address](glossary:virtual-address) 공간 상의 한 위치**

### 구성요소

- [VPN](glossary:vpn)과 [offset](glossary:offset)으로 구성된다.
- 총 32비트로 구성된다.
- 그 중 [offset](glossary:offset)은 [Page](glossary:page)의 크기와 관련이 있다.
  - [Page](glossary:page) 크기 2^n이라면 [offset](glossary:offset)은 n비트만큼 할당된다.
- [VPN](glossary:vpn)은 32-n 비트이다.
  - 만약 [Page](glossary:page)의 크기가 4kb라면 2^12=4kb이기 때문에 [VPN](glossary:vpn) = 20bit, [offset](glossary:offset) = 12bit이다.

## 3. page table

- OS가 관리한다.
- 각 프로레스는 자신만의 [Page table](glossary:page-table)을 가지고 있다(프로세스마다 주소 공간이 독립이고 보호돼야 해서).
- [VPN](glossary:vpn)이 [Page table](glossary:page-table)에 의해 [PFN](glossary:pfn)으로 매핑된다.
- [VPN](glossary:vpn)과 [PTE](glossary:pte)([page table](glossary:page-table) entry = [Page table](glossary:page-table)의 한 칸)은 일대일 대응된다.

## 4. PTE(Page Table Entries)의 구성요소

| V    | R    | M    | [Prot](glossary:protection-bit) | [PFN](glossary:pfn)(Page Frame Number) |
| ---- | ---- | ---- | ------------------------------- | -------------------------------------- |
| 1bit | 1bit | 1bit | 2bit                            | 20bit                                  |

- V([Valid bit](glossary:valid-bit)):
  - 1이면 [PFN](glossary:pfn)꺼내서 [VPN](glossary:vpn)에서 변환, 0이면 문제있어서 OS한테 넘김([trap](glossary:trap))
    - 1이면 [valid](glossary:valid-bit), 이 [Page](glossary:page)가 프로세스의 주소 공간 안에 있는, 합법적인 [Page](glossary:page)라는 뜻
    - 0이면 invalid, 주소 공간 밖 2가지 경우가 있다
      - 애초에 할당된 적 없음 (Never allocated) — 엉뚱한 주소, [Null pointer](glossary:null-pointer) 같은 거. 건드리면 불법 접근
      - 디스크로 쫓겨남 ([page out](glossary:page-out) to disk) — 합법인데 자리 없어서 디스크에 내려간 상태. 건드리면 [page fault](glossary:page-fault) → 다시 끌어올림
- [R(Reference)](glossary:reference-bit): 그 [Page](glossary:page)에 접근된 적있는지
- M([Modify](glossary:dirty-bit)/[dirty](glossary:dirty-bit)): 이 [Page](glossary:page)에 뭘 썼나 - [dirty](glossary:dirty-bit)일 때만 디스크에 다시 씀
- [Prot](glossary:protection-bit): R/W/X 권한
  - 각 [Page](glossary:page)마다 보호 비트가 있어서, 합법 [Page](glossary:page)라도 "무슨 동작까지 허용할지(read-only, read-write, execute-only)"를 세밀하게 정한다.
- [PFN](glossary:pfn): 물리 [Frame](glossary:frame) 번호

### valid bit 이 0(invalid)일 때

1. [Page table](glossary:page-table)에서 처음으로 피지컬 메모리 접근
2. 메모리에 없다
3. 디스크에 있다
4. 디스크에서 메모리로 올린다 ([page fault](glossary:page-fault))

## 6. 페이징 전체 흐름

```text
ex:
page = 4096byte

0   0 ~ 4095
1   4096 ~ 8191
2   8192 ~ 12287
3   12288 ~ 16383
4   16384 ~ 20479

virtual address = 0x4AFE = 19198
19198//4096 = 4 = 0x00004(20bit)
따라서 VPN = 0x00004(20bit)

따라서 들어가는 페이지 = 페이지 4번

19198 % 4096 = 2814= 0xAFE
따라서 offset = 0xAFE

page table이 아래와 같이 생겼다면

0   2|7
1   D|0
2   3|1
3   F|E
4   B|6 여기에 들어감
5   A|4

이 virtual address는 페이지 테이블의 [4]번 칸을 조회한다.
그 후 VPN 0X00004는 PFN 0xB6로 매핑된다

그래서 나오는 physical address B6AFE가 된다(offset은 유지되기 때문에)
```

# 2. demanding paging

**프로그램을 통째로 메모리에 안 올리고, 실제로 건드리는 [Page](glossary:page)만 그때그때(demand) 올린다.**

- I/O 줄이고, 메모리 적게 쓰고, 유저 더 수용하고, 반응성이 좋아진다.

[Page](glossary:page)가 메모리에 없으면 → [PTE](glossary:pte)의 [valid](glossary:valid-bit)=0, 그리고 [PTE](glossary:pte)에 OS가 **"이 [Page](glossary:page)가 디스크 어디에 있는지([swap](glossary:swap-space) 위치)"**를 적어둔다.

그 [Page](glossary:page)를 건드리면 → [page fault](glossary:page-fault)([trap](glossary:trap))

**이건 [segfault](glossary:segmentation-fault) 같은 에러가 아니라 회복 가능한 정상 동작.**

OS가 처리하고 터진 명령을 다시 실행한다. 앱은 이게 일어난 줄도 모른다. (transparent)

## 1. page fault 처리 단계

1. 주소 참조(cpu가 [Page](glossary:page) 접근)
2. [Trap](glossary:trap)([Page fault](glossary:page-fault))([valid](glossary:valid-bit) = 0 → OS로 넘김)
3. 디스크에서 찾기 [swap](glossary:swap-space) file 위치 확인
4. 디스크에서 [Frame](glossary:frame)으로 이동 -- 여기서 근데 빈 [Frame](glossary:frame)이 없으면? 누군가를 내쫓아야함([page replacement algorithm](glossary:page-replacement))
5. [PTE](glossary:pte) 갱신 [valid](glossary:valid-bit)=1, [Frame](glossary:frame) 연결
6. 명령 재시작

## 2. 이게 잘 굴러가는 이유 -- Locality

- 필요할 때만 올린다는게 [page fault](glossary:page-fault)를 계속 유발하지 않나?
  - 안그렇다. [Locality of reference](glossary:locality-of-reference) 때문에
    1. 시간 [Locality of reference](glossary:locality-of-reference)(Temporal): 방금 쓴 데이터는 또 쓸 가능성이 높다.
    2. 공간 [Locality of reference](glossary:locality-of-reference)(Spatial): 방금 쓴 곳 근처를 다시 쓸 가능성이 높다.

## 3. Cold start

프로세스 처음 시작하면 [Page table](glossary:page-table) 전부 [valid](glossary:valid-bit)=0인 상태

처음 시작할 때 [cold page fault](glossary:cold-start) 생으로 맞고 가야함

demand인 이유: 미리 다 올리는 게 아니라, 요구가 들어와야(폴트가 나야) 올리니까

# 3. Segmentation

[paging](glossary:paging)은 메모리를 의미 무시하고 똑같은 칸으로 자르는데 반해 [segmentation](glossary:segmentation)은 **메모리를 논리적 의미 단위로 자른다.**

[virtual address](glossary:virtual-address) = [ Segment# | [Offset](glossary:offset) ] // 세그먼트 번호 + [offset](glossary:offset)

- Segment# = [base](glossary:base-register), [limit](glossary:base-register)으로 구성되어있음
  - [base](glossary:base-register): 이 세그먼트가 [Physical memory](glossary:physical-memory) 어디서 시작하는지
  - [limit](glossary:base-register): 이 세그먼트가 얼마나 긴지 ← 이게 새로 등장
    - [limit](glossary:base-register)이 필요한 이유: 세그먼트마다 크기가 달라서
- [variable partition](glossary:variable-partition)의 확장판이다.

### 장점

1. 논리 단위라 늘리고 줄이기 편하다.
2. 보호가 자연스럽다(세그먼트 단위로 R/W/X권한).
3. 공유가 깔끔하다.

### 단점

1. [External fragmentation](glossary:external-fragmentation) 발생 - 세그먼트 크기가 제각각이라서. 근데 세그먼트가 워낙 큰 문제는 안됨
2. [Segment table](glossary:segment-table)이 크다(메인 메모리에 두고 하드웨어 캐시로 속도 보완)(근데 일반적으로 [Page table](glossary:page-table)보다는 크기가 작다)

## 1. 변환과정

**logical address → space [segment table](glossary:segment-table) → [physical memory](glossary:physical-memory)**

1. [Virtual address](glossary:virtual-address)[segment#|[Offset](glossary:offset)]
2. [Segment table](glossary:segment-table) [Seg#](limit, base)
3. [offset](glossary:offset)이 [limit](glossary:base-register)보다 작은지 조사
4. **[offset](glossary:offset)이 [limit](glossary:base-register)보다 크면 [protection fault](glossary:protection-fault)**
   - [offset](glossary:offset)이 [limit](glossary:base-register)보다 크면 안되는 이유: [limit](glossary:base-register)는 그 [Virtual address](glossary:virtual-address)가 할당받은 전체 메모리 크기여서
5. 물리주소 = [base](glossary:base-register) + [offset](glossary:offset)

# 4. Paging vs Segmentation 차이점 상세

## 1. 구조, 성능 차이

| 항목                                                  | [Paging](glossary:paging)                             | [Segmentation](glossary:segmentation) |
| ----------------------------------------------------- | ----------------------------------------------------- | ------------------------------------- |
| 블록 크기                                             | 고정 (4KB~64KB)                                       | 가변                                  |
| 주소 지정                                             | [Page](glossary:page)번호 + [offset](glossary:offset) | 세그먼트# + [offset](glossary:offset) |
| 교체 (replacement)                                    | 쉬움 (다 같은 크기)                                   | 어려움 (맞는 빈자리 찾기)             |
| 단편화                                                | 내부                                                  | 외부                                  |
| 디스크 전송                                           | 효율적 ([Page](glossary:page) 크기에 최적화)          | 비효율 (전송 크기 들쭉날쭉)           |
| [Linear address space](glossary:linear-address-space) | 1개                                                   | 여러 개                               |
| 프로그래머에게 투명?                                  | Yes (안 보임)                                         | No (보임)                             |

## 2. 능력, 목적 차이

| 질문                                                              | [Paging](glossary:paging)                                | [Segmentation](glossary:segmentation) |
| ----------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------- |
| 전체 주소공간 > [Physical memory](glossary:physical-memory) 가능? | Yes                                                      | Yes (단, 비효율적일 수 있음)          |
| 코드/데이터 구분해 따로 보호?                                     | No                                                       | Yes                                   |
| 크기 변하는 자료구조 수용 쉬움?                                   | No                                                       | Yes                                   |
| 코드 공유 쉬움?                                                   | No                                                       | Yes                                   |
| 왜 발명됨?                                                        | 큰 [Linear address space](glossary:linear-address-space) | 논리적 독립 공간 (공유·보호)          |

# 5. 결론 Segmentation with Paging (하이브리드)

- **[Paged Segments](glossary:paged-segments): [Segmentation](glossary:segmentation) + [Paging](glossary:paging). 세그먼트를 [Page](glossary:page) 크기의 배수로 잡음**
- 세그먼트가 **"pageable"**해짐 — 세그먼트 통째로 옮기는 게 아니라 [Page](glossary:page) 조각 단위로 올리고 내림
- 그 결과 [External fragmentation](glossary:external-fragmentation) 제거 ([Segmentation](glossary:segmentation)의 치명적 약점을 [Paging](glossary:paging)으로 해결)
  - [Internal fragmentation](glossary:internal-fragmentation)은 있을 수 있다.
