## 0. 들어가며

로드맵 4단계다. 공용 API에 결제를 붙이고, 그게 운영에서 진짜 되는지 확인해 단계를 닫았다. 전체 그림은 [Stairno 0. 전체 로드맵](/kr/blog/side-projects/stairno/stairno-00-roadmap/)에 있다. 결제는 실수가 곧 돈 사고라서 코드보다 규칙을 먼저 정했고, 테스트가 통과해도 운영 주소와 알림까지는 보장하지 않아서 운영에서 시나리오를 돌리는 리허설을 따로 했다.

식당으로 비유하면 사이트는 홀, API는 주방이고 계산대가 결제 회사다. 손님이 주문을 넣고 계산하면 주방은 계산대와만 이야기하고, 계산이 끝나면 입장권을 끊어 준다. 단골 카드를 한 번 등록해 두면 매달 알아서 계산되고, 개점 전에는 직원끼리 손님 역할로 하루를 미리 돌려 본다. 계산대는 [Payment gateway](glossary:payment-gateway)(여기서는 [Toss Payments](glossary:toss-payments)와 [PayPal](glossary:paypal)), 입장권은 [Entitlement](glossary:entitlement), 단골 카드는 [Billing key](glossary:billing-key), 매달 자동 계산은 [Subscription](glossary:subscription) 갱신, 계산대와 통역하는 창구는 [Adapter](glossary:adapter-pattern), 개점 전 예행연습은 리허설이다.

10월 18일 오후부터 밤까지 결제를 [Sandbox](glossary:sandbox)로 만들어 `v0.4.0`과 `v0.4.1`을 냈고, 10월 20일 새벽 운영에서 시나리오 10개를 돌렸다. 시작하자마자 공개 첫날부터 다른 사이트의 로그인이 막혀 있었다는 걸 알았고, 첫날 8개와 다음 날 나머지 둘을 통과시켜 10월 22일 `v0.4.3`으로 4단계를 닫았다. 실제 돈은 한 푼도 오가지 않았다.

## 1. 무엇을 만들고 어떤 규칙으로 만들까

| [Payment gateway](glossary:payment-gateway) | 통화      | 만든 것                                                                                                                                     |
| ------------------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| [Toss Payments](glossary:toss-payments)     | 원화(KRW) | 1회 결제, 카드 등록([Billing key](glossary:billing-key)), [Subscription](glossary:subscription) 자동결제, 취소, [Webhook](glossary:webhook) |
| [PayPal](glossary:paypal)                   | 달러(USD) | 1회 결제, [Refund](glossary:refund), [Webhook](glossary:webhook)                                                                            |

계정 센터에는 카드 등록·삭제·기본 카드 바꾸기, 주문 내역, [Subscription](glossary:subscription) 해지와 재개, 구매한 프로그램 다시 받기를 넣고, 영수증·갱신 실패·[Refund](glossary:refund) 결과 메일을 보낸다. 실제 결제로 바꿀 때는 테스트 열쇠를 진짜 열쇠로 바꾸고 사업자 정보를 적는 것만으로 끝나게 설계한다. 그 전환은 사업자등록 뒤인 9단계다. 규칙은 전부 레포의 작업 규칙 문서에 있고 AI 에이전트도 따른다.

1. **[Payment gateway](glossary:payment-gateway)는 [Adapter](glossary:adapter-pattern) 뒤에만 둔다.** 주문 처리 코드는 "승인", "취소" 같은 공통 기능만 알고 [Toss Payments](glossary:toss-payments)인지 [PayPal](glossary:paypal)인지 모른다. 테스트는 진짜 대신 [Test double](glossary:test-double)로 돌려서 "다음 결제는 거절해", "응답 없는 척해" 같은 상황을 마음대로 만든다
2. **금액은 정수 + 통화.** 1,000원은 `1000 KRW`, 1달러는 `100 USD`(센트). 소수로 계산하지 않고 원과 달러를 섞어 더하지 않는다
3. **카드 번호를 받는 코드는 없다.** [Payment gateway](glossary:payment-gateway) 화면이 받는다. 우리는 암호화한 [Billing key](glossary:billing-key)와 카드사, 끝 4자리만 갖는다
4. **서버가 금액을 다시 확인한다.** 브라우저가 보낸 금액이 주문 금액과 다르면 거절하고 승인 요청을 보내지 않는다
5. **[Webhook](glossary:webhook)은 [Idempotency](glossary:idempotency)를 지킨다.** 같은 알림이 두 번 와도 한 번만 처리한다
6. **주문은 [State machine](glossary:state-machine)을 따른다.** 허용된 이동만 일어난다
7. **결제만 끄는 [Kill switch](glossary:kill-switch)를 둔다.** 장애 때 로그인은 살리고 결제만 멈춘다
8. **로그에 개인정보를 남기지 않는다.** 이메일, [Token](glossary:token), 카드 정보 대신 주문 번호와 [Payment gateway](glossary:payment-gateway) 번호만 남긴다

## 2. 만든 순서와 결제 한 번의 길

PR 하나에 기능 하나, 테스트 먼저 쓰고 아래 순서로 넣었다.

| 순서  | 만든 것                                                                                                           | 내용                                                                                                                                                        |
| ----- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | 결제 DB 설계                                                                                                      | 상품, 가격, 주문, 결제, 카드, [Subscription](glossary:subscription), [Entitlement](glossary:entitlement), 환불 요청, [Webhook](glossary:webhook) 기록 표    |
| 2     | [Adapter](glossary:adapter-pattern), [Test double](glossary:test-double), [State machine](glossary:state-machine) | [Payment gateway](glossary:payment-gateway)와 대화하는 틀, 주문이 움직이는 규칙                                                                             |
| 3     | 상품 등록 명령, [Kill switch](glossary:kill-switch)                                                               | 운영자가 명령어로 상품을 등록한다. 관리자 화면은 안 만든다                                                                                                  |
| 4     | 사이트 신분, 주문 API                                                                                             | 사이트가 "등록된 Stairno 사이트"임을 밝히고 주문을 만든다                                                                                                   |
| 5~7   | [Toss Payments](glossary:toss-payments) 승인, [Webhook](glossary:webhook), [PayPal](glossary:paypal) 결제         | 돌아온 결제를 확인해 확정한다. [PayPal](glossary:paypal)은 승인 화면에 다녀온 뒤 캡처한다                                                                   |
| 8~10  | 카드 등록·삭제, 계정 삭제 연동, 결제 수단 화면                                                                    | 등록창에서 [Billing key](glossary:billing-key)를 발급받아 암호화해 저장한다. 계정을 지우면 [Payment gateway](glossary:payment-gateway)에 저장된 키도 지운다 |
| 11~13 | [Billing key](glossary:billing-key) 결제, [Subscription](glossary:subscription) 시작, 기본 카드 변경 반영         | 기본 카드로 바로 결제하고 [Subscription](glossary:subscription)을 연다. 기본 카드를 바꿔도 옛 카드에 묶여 있던 걸 따로 고쳤다                               |
| 14~15 | 매일 자동 갱신, 해지와 재개                                                                                       | 하루 한 번 [Cron](glossary:cron)이 기간 끝난 [Subscription](glossary:subscription)을 결제한다. 해지는 계정 센터에서만                                       |
| 16~17 | [Entitlement](glossary:entitlement) 조회, 다운로드 링크                                                           | 사이트가 "이 사람 이 제품 써도 돼?"를 묻는다. 산 사람에게 10분짜리 다운로드 주소를 준다                                                                     |
| 18~20 | 환불 요청과 운영자 환불 명령, 결제 메일, 주문 내역                                                                | 환불은 운영자가 확인하고 명령어로 처리한다. 메일은 주문마다 종류별로 한 번만                                                                                |

1,000원짜리 프로그램을 사는 한 번의 흐름은 이렇다. (Labs가 아직 없어서 6절의 리허설 사이트가 그 자리를 대신한다.)

1. 사이트가 사이트 [Token](glossary:token)과 구매자 [Token](glossary:token)을 같이 보내 주문을 만든다. API는 가격을 DB에서 읽어 주문을 `pending`으로 만든다. 가격은 사이트가 정하지 않고, 30분 안에 결제하지 않으면 만료된다
2. [Toss Payments](glossary:toss-payments) 결제창에서 카드를 넣고 인증한다. 아직 돈은 안 나갔다
3. 사이트가 API에 "확정해 줘"를 보낸다. API는 이 사이트의 주문인지, 이미 처리한 결제 번호인지(그렇다면 처음 결과를 그대로 돌려준다), 주문이 아직 `pending`인지, **금액이 주문과 같은지**를 순서대로 본다. 다르면 주문을 `failed`로 두고 [Toss Payments](glossary:toss-payments)에는 승인 요청을 보내지 않는다
4. API가 [Toss Payments](glossary:toss-payments)에 승인을 요청한다. 여기서 돈이 나가고, 승인 금액을 한 번 더 비교한다
5. 결제 완료, 주문 `fulfilled`, [Entitlement](glossary:entitlement) 생성을 한 번에 기록하고 사용자 언어로 영수증 메일을 보낸다
6. 나중에 [Webhook](glossary:webhook)이 오면 이미 처리한 결제라 아무것도 바꾸지 않는다. 사용자가 2번 뒤에 창을 닫았다면 이 [Webhook](glossary:webhook)이 3~5번을 대신한다

## 3. 만들면서 부딪힌 것

### 대화형 Database transaction이 없다

보통은 결제 기록, 주문 상태, [Entitlement](glossary:entitlement) 생성을 [Database transaction](glossary:database-transaction) 하나로 묶는다. 그런데 [Cloudflare Workers](glossary:cloudflare-workers)에서 [Neon](glossary:neon)에 붙는 HTTP 연결은 요청마다 따로라서 여러 요청에 걸친 [Database transaction](glossary:database-transaction)을 열 수 없다. 그래서 상태를 바꾸는 일은 [SQL](glossary:sql) 한 문장으로 쓰고, 그 문장에 "주문이 이 상태들일 때만 바꿔라"는 조건을 붙였다. 허용 상태 목록은 [State machine](glossary:state-machine) 표에서 자동으로 만든다. 두 요청이 동시에 같은 주문을 바꾸려 해도 먼저 바꾼 쪽만 성공한다.

### Webhook은 저장보다 확인이 먼저

"받았음"을 먼저 저장하면 위조된 알림이 진짜 알림의 이벤트 번호를 먼저 차지하고, 진짜가 나중에 오면 "이미 받은 번호"로 버려진다. 그래서 순서를 확인, 저장, 처리로 했다. [Toss Payments](glossary:toss-payments)의 결제 알림에는 서명이 없어서, 받으면 [Toss Payments](glossary:toss-payments)에 그 결제를 직접 다시 물어보고 답한 상태만 믿는다.

### 다운로드 링크를 직접 서명한다

파일은 [Cloudflare R2](glossary:cloudflare-r2)에 둔다. [Cloudflare R2](glossary:cloudflare-r2)에서 10분짜리 다운로드 주소를 만들려면 별도 열쇠가 하나 더 필요한데 비밀 값이 늘어나는 게 싫었다. 그래서 주소를 API 자신의 것으로 만들고 "이 파일, 이 시각까지"를 API가 직접 서명한다. 사용자가 오면 서명과 시간을 확인하고 파일을 흘려보낸다.

### 거절과 장애를 구분한다

"카드 한도 초과"는 거절이라 주문을 `failed`로 닫고 사용자에게 알리면 된다. "[Payment gateway](glossary:payment-gateway) 서버 응답 없음"은 장애라 주문을 그대로 두고 다시 시도할 수 있어야 한다. 오류 코드를 문서에서 하나씩 확인해서 [Adapter](glossary:adapter-pattern)가 코드로 둘을 나누게 했다.

## 4. 중간에 Git Flow로 바꾼 이유

3단계까지는 PR이 [CI](glossary:ci)를 통과하면 바로 `main`에 넣었고 `main`은 바로 운영에 올라갔다. 결제 기능이 반쯤 들어간 상태로 운영에 올라가는 건 로그인 화면 글자 하나 바뀌는 것과 무게가 달라서, 10월 18일 저녁 결제 PR이 20개를 넘은 시점에 [Git Flow](glossary:git-flow)로 바꿨다.

- 평소 작업은 `develop`에 모으고, `develop`에 들어간다고 운영에 올라가지 않는다
- 로드맵 단계 하나가 끝나면 `release` 브랜치를 만들어 `main`으로 보내고 그때 한 번 배포한다
- 운영의 급한 버그는 [Hotfix](glossary:hotfix)로 운영 버전만 고친다
- [Semantic versioning](glossary:semantic-versioning)의 가운데 숫자가 로드맵 단계 번호다. 4단계 첫 출시가 `v0.4.0`

확인은 층으로 나눴다. 커밋마다 바꾼 테스트만, `develop`에 올릴 때 [CI](glossary:ci) 전체, `main`으로 갈 때 [CI](glossary:ci) 필수, 배포 직전 테스트 한 번 더, 운영에서 리허설. 마지막 층이 6절부터다. [Payment gateway](glossary:payment-gateway)가 우리 서버로 돌아오는 주소와 [Webhook](glossary:webhook)은 운영에서만 진짜로 확인되기 때문이다.

## 5. v0.4.0과 v0.4.1

밤 10시쯤 결제 메일, 주문 내역, 다시 받기 화면까지 넣어 `v0.4.0`을 운영에 올렸다. 그리고 계정 센터가 프로필, 기기, 연결된 사이트, 결제 수단, [Subscription](glossary:subscription), 주문, 다운로드, 삭제로 흩어져 찾기 어렵다는 걸 보고, 구글·마이크로소프트·애플·GitHub·카카오의 계정 화면을 비교해 바꿨다.

- 한 페이지에 계정 관리, 결제, 내 제품, 보안 네 덩어리. 왼쪽 목차를 누르면 그 자리로 스크롤하고 지금 보는 덩어리가 표시된다
- 계정 삭제는 맨 아래, 실수로 누르기 어려운 자리
- 빠져 있던 비밀번호 변경 추가. 바꾸면 다른 기기 로그인을 전부 끊고 "비밀번호가 바뀌었습니다" 메일을 보낸다
- 국가·지역과 시간대(주문 날짜를 그 시간대로 표시), 프로필 사진

생일, 성별, 전화번호, 주소는 받지 않기로 했다. 쓸 기능이 없는 개인정보는 받지 않는 게 개인정보보호법의 원칙인 [Data minimization](glossary:data-minimization)이고, 털릴 것도 줄어든다. 자정 직후 `v0.4.1`로 올렸고 여기까지가 구현이다. 남은 건 운영에서 진짜 되는지 확인하는 일이었다.

## 6. 리허설 전용 사이트

테스트는 가짜 [Payment gateway](glossary:payment-gateway), 가짜 DB, 가짜 서버에서 돈다. 그런데 결제를 마친 사용자가 진짜 사이트 주소로 돌아오는지, [Webhook](glossary:webhook)이 진짜 서버에 도착하는지, 메일이 진짜 메일함에 오는지는 운영에서만 확인된다. 그래서 4단계는 시나리오를 하나씩 돌리고 [Acceptance criteria](glossary:acceptance-criteria)를 채워야 닫힌다.

문제는 주문을 만들려면 API에 붙은 사이트가 있어야 한다는 점이었다. 주문 요청에는 사이트 [Token](glossary:token)과 구매자 [Token](glossary:token)이 모두 필요하고, 돌아올 주소는 그 사이트의 https 주소여야 하고, 결제창은 사이트 페이지에서 열린다. 첫 사이트 Labs는 5단계에서 만든다. 3단계에서는 비슷한 상황을 "사이트가 생기면 확인"으로 미뤘지만 이번엔 그러지 않았다. Labs에 결제를 붙이다 문제가 나면 결제 API의 버그인지 Labs의 버그인지 가릴 수 없기 때문이다.

그래서 레포의 `experiments/payment-rehearsal`에 리허설만 하는 한 페이지짜리 [Worker](glossary:cloudflare-workers)를 만들었다.

- 진짜 Stairno 사이트와 똑같이 [OIDC](glossary:oidc)([PKCE](glossary:pkce) 포함)로 로그인하고 사이트 [Token](glossary:token)을 받는다
- 버튼은 로그인, 1회 상품 주문(원화는 [Toss Payments](glossary:toss-payments), 달러는 [PayPal](glossary:paypal)), 결제 확인, 금액을 반으로 바꾼 결제 확인, [Subscription](glossary:subscription) 시작, 주문·[Entitlement](glossary:entitlement) 조회. 카드 번호 입력칸은 없다
- 사이트 비밀번호(`client_secret`)는 이 [Worker](glossary:cloudflare-workers)의 [Secret](glossary:secret)으로만 둔다
- **API 쪽에 리허설용 예외나 뒷문은 하나도 없다.** 진짜 사이트와 같은 길을 타야 의미가 있다. 이 도구는 레포에 남기고 결제 경로를 바꾸는 출시마다 다시 돌린다

준비는 도구를 Cloudflare에 올리고, 계정 센터에 [OIDC](glossary:oidc) 사이트로 등록해 받은 이름표와 비밀번호를 [Secret](glossary:secret)에 넣고, 1회 상품 둘(1,000원, 1달러)과 월 [Subscription](glossary:subscription) 상품(1,000원)을 등록하고, [Toss Payments](glossary:toss-payments)와 [PayPal](glossary:paypal) 대시보드의 [Webhook](glossary:webhook) 주소를 확인하고, 리허설용 계정을 만드는 순서였다. 운영 DB를 읽는 확인 스크립트도 만들었다. 역할은 카드 입력, 비밀번호 입력, 대시보드 설정 변경은 내가 하고 버튼 누르기와 결과 확인(응답, DB 기록, 메일)은 AI 에이전트가 맡는 것으로 나눴다.

두 가지가 걸렸다. 처음 등록했을 때 발급된 사이트 비밀번호가 작업 대화 기록에 그대로 찍혀서, 그 등록을 지우고 새로 등록했다. 지운 쪽 비밀번호로 로그인하면 거절(`invalid_client`)되는 것까지 확인했다. 또 [Neon](glossary:neon) 콘솔에서 만든 DB 계정은 자동으로 관리자 그룹에 들어가 "읽기 권한만"이 먹지 않아서, 스크립트가 여는 [Database transaction](glossary:database-transaction) 자체를 [Read-only transaction](glossary:read-only-transaction)으로 열어 쓰기를 원천 차단했다. 이메일·[Token](glossary:token)·카드 키는 출력하지 않는다.

## 7. 첫 버튼에서 404

리허설 도구에서 로그인을 눌렀더니 계정 센터의 `/sign-in`이 [404](glossary:http-status-code)였다. 이 페이지는 다른 사이트가 "Stairno로 로그인"을 누르면 도착하는 곳이다. 10월 18일 공개 첫날부터 어떤 사이트도 Stairno로 로그인할 수 없었는데, 붙은 사이트가 없어서 아무도 몰랐다. 3단계에서 "5단계에서 확인"으로 미뤘던 바로 그 확인이다.

원인은 이렇다. 계정 센터는 주소 앞에 언어를 붙이고([i18n](glossary:i18n)) [Astro](glossary:astro)의 설정이 "모든 페이지에 언어를 붙인다"였는데, 이 설정은 언어 없는 페이지를 다 그린 뒤 [404](glossary:http-status-code)로 바꾼다. [OIDC](glossary:oidc) 로그인 주소는 다른 사이트가 사용자 언어를 모르고 보내는 언어 없는 `/sign-in`이다. 화면 테스트는 페이지를 따로 떼어 그려서 언어 설정에 따른 주소 처리가 끼지 않으니, "`/sign-in`이 폼을 그린다"는 통과해도 "운영 빌드에서 이 주소가 살아 있다"는 아무도 확인하지 않았다.

[Astro](glossary:astro)에서 언어 접두사 밖에서 답할 수 있는 건 확장 기능(integration)이 따로 끼운 주소뿐이다. 그래서 `/sign-in`을 그 방식으로 넣고 요청을 사용자 언어의 로그인 페이지(`/ko/sign-in` 등)로 [302](glossary:http-status-code)로 보냈다. 언어 없이 답해야 하는 주소는 목록으로 묶어 테스트하고, 실제 빌드를 띄워 `/sign-in`이 [302](glossary:http-status-code)인지, 다른 주소는 여전히 [404](glossary:http-status-code)인지 확인했다.

## 8. 지운 주소를 가리키던 메일과 v0.4.2

"갱신이 실패하면 오는 메일의 버튼을 눌러 본다"를 준비하다가 버튼이 `/billing`을 가리키는 걸 봤다. 5절의 `v0.4.1`에서 계정 센터를 한 페이지로 바꾸며 내가 지운 주소다. 화면 구조를 바꾸면서 메일 속 링크는 같이 보지 않았다. 새 구조의 결제 덩어리(`/ko/#payment-methods`)로 바꿨다.

이 둘을 운영 중인 `v0.4.1`에 얹어 [Hotfix](glossary:hotfix) `v0.4.2`로 묶었다. `develop`에 쌓인 다른 변경은 섞지 않는다. 평소 몇 분인 [CI](glossary:ci)가 이날은 [GitHub Actions](glossary:github-actions) 쪽이 느려져 40분 가까이 걸려서, 올리고 머지까지 한 시간이었다. 새벽 1시 반쯤 `v0.4.2`가 운영에 올라갔고 `/sign-in`을 확인한 뒤 리허설을 다시 시작했다.

## 9. 아무도 갖고 있지 않던 Secret

운영 서버의 `BETTER_AUTH_SECRET` 원래 값이 어디에도 없었다. [Password manager](glossary:password-manager)에도, 내 컴퓨터에도 없었고 [Cloudflare Workers](glossary:cloudflare-workers)는 넣은 [Secret](glossary:secret)을 다시 보여 주지 않는다. 이 값으로 로그인 [Token](glossary:token)에 서명하는 [JWKS](glossary:jwks)의 비밀 열쇠가 DB에 암호화돼 있어서, 갖고 있는 어떤 값으로도 풀리지 않았다.

공개 전이라 사용자가 나와 테스트 계정뿐이어서 새 값으로 바꿨다.

1. 새 값을 먼저 [Password manager](glossary:password-manager)에 저장
2. [Wrangler](glossary:wrangler)로 Cloudflare에 넣는다(`wrangler secret put`)
3. 옛 값으로 암호화된 서명 열쇠를 DB에서 지운다
4. 공개 열쇠 주소를 한 번 불러 새 서명 열쇠를 만들게 하고, 새 값으로 풀리는지 확인

이 값을 바꾸면 모든 로그인이 끊기고 나가 있던 다운로드 링크도 전부 무효가 된다. 사용자가 있었다면 공지부터 해야 한다. 어디에도 적어 두지 않은 [Secret](glossary:secret)은 잃어버린 [Secret](glossary:secret)이라서, 이 절차는 운영 문서에 옮겼다.

### 환불 요청을 계정 센터로 옮긴 결정

3번에서 설계의 빈틈이 나왔다. 절차서에는 "계정 센터에서 환불 요청"이라고 적혀 있었는데 계정 센터에 환불 버튼이 없었다. [SRS](glossary:srs)는 환불 요청을 사이트가 넣도록 정했고 계정 센터는 상태만 보여 주게 되어 있어서, 코드는 명세서대로이고 절차서가 틀렸다. 리허설은 도구에 "환불 요청" 버튼을 더해 통과시켰다.

그런데 사용자 입장에서는 어느 사이트에서 샀든 주문 내역이 있는 계정 센터에서 요청하는 게 자연스럽고, 사이트마다 환불 화면을 만드는 건 [Stairno 0](/kr/blog/side-projects/stairno/stairno-00-roadmap/#1-사이트는-넷-계정은-하나)에서 피하려던 "같은 일 여러 번"이다. 그 자리에서 결정을 바꿔 계획서에 적었다.

- 환불 요청은 계정 센터의 주문 상세에서 받는다. 사유를 적어 보내면 요청이 되고 바로 환불되지는 않는다
- 운영자가 승인하거나 거절하고 결과는 메일로 간다. 사이트에서 요청을 넣는 길은 입구로 남긴다
- 환불 정책 본문은 파는 사이트에 두고 계정 센터는 링크를 건다
- 명세서를 먼저 고친 뒤 구현한다. 다음 출시에 넣는다

## 11. 나머지 둘 (10월 21일)

**10번.** 계정 언어를 영어로 바꾸고 1번과 3번을 간편결제로 다시 했다. 주문이 `fulfilled`가 되고 영어 영수증이 왔고, 환불을 요청해 운영자 명령으로 승인하니 `refunded`, [Entitlement](glossary:entitlement) 회수, 영어 환불 메일이 왔다. 메일 언어는 보내는 순간의 계정 언어를 따라서, 첫날의 한국어 결과로는 영어 쪽을 증명할 수 없었다.

**6번.** [Toss Payments](glossary:toss-payments) 테스트 환경은 카드와 상관없이 결제를 다 승인해서 실패를 만들어야 했다. 공식 방법인 요청의 테스트용 표시는 API를 고쳐야 해서 "리허설용 예외 없음" 원칙에 어긋난다. 그래서 운영 DB의 리허설 데이터만 바꿔 저장된 [Billing key](glossary:billing-key)와 고객 번호가 맞지 않게 했고, [Toss Payments](glossary:toss-payments)가 진짜로 "고객 정보가 맞지 않음"(`NOT_MATCHES_CUSTOMER_KEY`)으로 거절하게 했다. 하루 한 번 도는 갱신 [Cron](glossary:cron)은 잠깐 매분으로 바꿨고, 재시도는 원래 마지막 시도 사흘 뒤라 재시도마다 "마지막 시도 날짜"를 사흘 전으로 돌렸다. 우리 쪽은 이걸 장애가 아니라 결제 거절로 받아 실패 주문과 영어 메일로 처리했고, 메일 버튼은 8절에서 고친 계정 센터 결제 섹션으로 갔다.

| 시도     | [Subscription](glossary:subscription) 상태 | 실패 횟수 |
| -------- | ------------------------------------------ | --------- |
| 첫 갱신  | `past_due`                                 | 1         |
| 재시도 1 | `past_due`                                 | 2         |
| 재시도 2 | `past_due`                                 | 3         |
| 재시도 3 | `expired`                                  | 4         |

`expired`가 된 뒤에도 [Subscription](glossary:subscription) [Entitlement](glossary:entitlement)가 원래 만료 시각(한 달 뒤)으로 남아 보였다. 리허설이 기간 끝만 당기고 [Entitlement](glossary:entitlement) 만료 시각은 건드리지 않아서 생긴 어긋남이고, 실제로는 갱신이 실패할 때쯤 그 시각도 이미 지나 있다.

대시보드에서 매분 [Cron Triggers](glossary:cron-triggers)를 더하고 15분을 기다렸는데 아무 일도 없었고, 그렇게 30분을 날린 뒤에야 로그를 열었다. [Cron](glossary:cron)이 돌면 API는 갱신할 게 없어도 `renewal run` 한 줄을 남기는데, 매분 [Cron](glossary:cron)을 더한 뒤로 그 줄이 하나도 없었다. 그날 아침 9시(자정 UTC)에는 있었으니 원래 [Cron](glossary:cron)은 멀쩡했다. 원인은 추가 창에서 "Add"만 누르고 "Save"를 안 누른 것이었다. Save 약 8분 뒤 첫 실행이 돌았다. 절차서에는 "Add 뒤 Save, 새로고침해서 남았는지 본다"를 적었다.

## 12. 4단계를 닫으며 (10월 22일)

리허설이 다 통과해도 뒷정리와 출시가 남아 있었다.

- **뒷정리.** 운영 DB를 읽던 확인 스크립트, 접속 정보 파일, 묻지 않고 돌리게 해 둔 허용 규칙을 지우고 임시 DB 계정은 [Neon](glossary:neon) 콘솔에서 지웠다. 리허설 도구는 남긴다
- **공유 문서.** 원본은 레포의 마크다운이고 Google Docs는 단계가 끝날 때 한 번 맞춘다. 링크를 지키려고 새로 올리지 않고 같은 문서에서 바뀐 곳만 고쳤다. [SDD](glossary:sdd)는 세 줄, 계획서는 표 몇 줄과 결정 셋, 테스트와 배포 문서는 리허설 절차 한 절과 [Acceptance criteria](glossary:acceptance-criteria) 결과 전부였고 [SRS](glossary:srs)는 이미 맞아 있었다. 단계가 사흘이라 괜찮았지, 길면 중간에 한 번 더 맞춰야 한다
- **환불 절차.** 열린 환불 요청을 DB에서 보고 사이트의 환불 정책으로 판단해 운영자 명령으로 승인·거절한다. 코드로 확인해 보니 [Payment gateway](glossary:payment-gateway) 대시보드에서 손으로 환불하면 [Webhook](glossary:webhook)이 주문은 환불로 맞추지만 열린 환불 요청은 닫지 않는다. 그래서 절차서에 "대시보드에서 손으로 환불하지 않는다"를 적었다
- **[Webhook](glossary:webhook) 재처리.** 처리하다 실패한 [Webhook](glossary:webhook)은 DB에 실패로 남고 오류를 답하면 [Payment gateway](glossary:payment-gateway)가 다시 보낸다([Toss Payments](glossary:toss-payments)는 3일 19시간 동안 최대 일곱 번). 원인을 고쳐 배포한 뒤 대시보드에서 다시 보내면 끝이고, 8번에서 중복 없이 처리되는 걸 이미 봤다
- **v0.4.3.** `develop`에 쌓인 것을 냈다. 주문 목록 링크 밑줄 제거, 리허설 도구의 환불 요청 버튼, 그리고 [Flaky test](glossary:flaky-test) 하나. [Billing key](glossary:billing-key) 위조 거절을 보는 테스트가 [Ciphertext](glossary:ciphertext)의 끝에서 두 번째 글자를 `A`로 바꾸는데(이미 `A`면 `B`), "이미 `A`인가"를 옆 글자를 보고 판단했다. 바꿀 자리가 원래 `A`이면 아무것도 안 바뀌어 복호화가 성공하고 테스트가 실패한다. 64번에 한 번쯤이다. 바꿀 그 자리를 보게 고쳤다
- **열려 있던 이슈 둘.** `v0.4.2`의 PR 본문에 "Closes #209, closes #211"을 썼는데 [GitHub Issues](glossary:github-issues)의 이슈 둘이 그대로 열려 있었다. GitHub은 PR이 [Default branch](glossary:default-branch)에 머지될 때만 이 키워드로 이슈를 닫는다. 이 레포의 [Default branch](glossary:default-branch)는 `develop`이고 출시 PR은 `main`으로 가서 키워드가 아무 일도 하지 않는다. 운영에서 고쳐진 걸 확인하고 손으로 닫았다

남은 것은 계정 센터의 환불 요청과 로그인 유지(둘 다 명세서부터)이고, 리허설 중에 찾은 버그 셋(허브 계정 메뉴의 "로그인" 링크가 없는 주소를 가리킴, [OIDC](glossary:oidc) 로그인 뒤에도 "연결된 사이트"가 비어 있음, 환불된 주문 목록에 환불 표시가 두 번 뜸)이다. 그다음이 5단계 stairnolabs.com이고, 3단계에서 미뤄 둔 운영 실험 13단계와 "계정 삭제 뒤 [Token](glossary:token) 갱신 실패" 확인도 거기서 한다. 실제 결제는 사업자등록과 계약 뒤이고, 그 전에 [Cloudflare Workers](glossary:cloudflare-workers) 유료 플랜 전환과 약관의 사업자 정보 표기를 다시 본다.

## 13. 느낀 점

테스트가 통과한다고 주소가 살아 있는 건 아니어서, 붙일 사이트가 없다고 미룬 확인이 이틀 가까이 로그인을 막고 있었고 진짜 사이트를 운영에 붙여 봐야 나왔다.
