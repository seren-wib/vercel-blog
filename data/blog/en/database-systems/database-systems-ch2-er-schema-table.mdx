# ER, Schema and Tables Through One COMPANY

The same COMPANY drawn as three layers. ① ER (ch2) → ② the converted schema (ch3 3.4) → ③ tables filled with data (ch3 3.1). The tables below only point to where each concept is in the three figures. The exam's "draw the RDB" = look at ① and draw ②

## 1. ER diagram

![COMPANY ER: 4 entities, 6 relationships, with (min,max)](/static/images/database-systems-ch2-er-schema-table/company-1-er.svg)

| Symbol                                      | Meaning                                                                                                                                  |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Rectangle / double rectangle                | entity type / weak entity type                                                                                                           |
| Oval / underline / dashed underline         | attribute / key / partial key                                                                                                            |
| Double oval / dashed oval / branching ovals | multivalued / derived / composite                                                                                                        |
| Diamond / double diamond                    | relationship / identifying relationship                                                                                                  |
| Single line / double line                   | partial / total participation                                                                                                            |
| 1, N, M                                     | cardinality ratio (at most how many on the other side)                                                                                   |
| Purple (min,max)                            | How many times, at least and at most, one entity of this type takes part in the relationship. min 0 = single line, min ≥ 1 = double line |

## 2. Relational schema

![COMPANY relational schema: 6 tables, PKs underlined, FK arrows](/static/images/database-systems-ch2-er-schema-table/company-2-schema.svg)

- 6 tables = 4 rectangles + 1 M:N diamond (WORKS_ON) + 1 double oval (DEPT_LOCATIONS)
- Every arrow is FK → PK. 7 arrows = 2 1:N diamonds (Dno, Dnum) + 1 1:1 diamond (Mgr_ssn) + 1 recursive (Super_ssn) + 2 from M:N (Essn, Pno) + 1 weak entity (Essn) + 1 double oval (Dnumber)
- Watch the renamed columns: Number → Dnumber/Pnumber, Name → Dname/Pname, EMPLOYEE.Ssn taken elsewhere becomes Essn, Mgr_ssn, Super_ssn

## 3. Tables (relation state)

![The 6 COMPANY tables filled with tuples](/static/images/database-systems-ch2-er-schema-table/company-3-tables.svg)

- Header row = schema, the rows under it = state. Adding or deleting rows leaves the header unchanged
- A value in an FK cell must be a value that exists in the other table's PK, or NULL. The five lines at the bottom right of the figure judge insert and delete violations

## 5. Relationships

| Concept                    | Meaning                                                                                                                                                                                                                                                                                | ① ER                                                                             | ② Schema                                                                      | ③ Table                                                                          |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Relationship type**      | How two entity types are tied together. An employee works for a department = WORKS_FOR. A diamond between rectangles. Becomes an FK column or a new table                                                                                                                              | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-relationship.svg) | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-1n.svg)        | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-1n.svg)           |
| **Relationship instance**  | One actual fact of that relationship. Smith works for department 5. Not drawn in ER. One FK cell value in a table                                                                                                                                                                      | Not drawn                                                                        | —                                                                             | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-rel-instance.svg) |
| **Degree**                 | How many entity types take part in one relationship. Employee–department is 2 (binary); supplier–project–part tied together at once is 3 (ternary). Count the rectangles connected to the diamond                                                                                      | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-ternary.svg)      | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-ternary.svg)   | 3 FKs per row                                                                    |
| **Cardinality 1:N**        | One entity on one side is tied to many on the other, and one on the other side is tied to only one on this side. One department has many employees, an employee has one department. 1 and N on the lines. The FK goes on the N side                                                    | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-1n.svg)           | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-1n.svg)        | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-1n.svg)           |
| **Cardinality 1:1**        | On both sides one entity is tied to only one on the other. One department has one manager, and that employee manages only one department. 1 and 1 on the lines. The FK goes on the double-line side                                                                                    | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-11.svg)           | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-11.svg)        | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-11.svg)           |
| **Cardinality M:N**        | On both sides one is tied to many. One employee on many projects, one project with many employees. M and N on the lines. One FK cell can't hold it, so a new table                                                                                                                     | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-mn.svg)           | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-mn.svg)        | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-mn.svg)           |
| **Total participation**    | Every entity on that side, without exception, is in the relationship. No employee without a department. Double line between rectangle and diamond. That FK cell is never empty                                                                                                         | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-total.svg)        | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-total.svg)     | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-total.svg)        |
| **Partial participation**  | Some entities may not be in the relationship. Some employees aren't managers. Single line. That cell can be NULL                                                                                                                                                                       | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-partial.svg)      | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-partial.svg)   | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-partial.svg)      |
| **(min, max)**             | At least and at most how many times one entity takes part in the relationship. An employee manages a department 0 or 1 times = (0,1); a department has exactly 1 manager = (1,1). min 0 means a single line, min 1 or more a double line, and whether max is 1 or N is the ratio above | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-minmax.svg)       | min ≥ 1 → NOT NULL / max 1 → one FK column, max N → new table                 | —                                                                                |
| **Relationship attribute** | A value attached to the relationship, not an entity. Hours belong to neither the employee nor the project but to "the employee on that project". An oval hung off the diamond. In tables it follows the FK into the table it went to                                                   | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-rel-attr.svg)     | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-rel-attr.svg)  | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-rel-attr.svg)     |
| **Recursive relationship** | A relationship an entity type has with itself. An employee supervises an employee. Both lines of the diamond go into the same rectangle. In a table, an FK pointing at its own PK                                                                                                      | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-recursive.svg)    | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-recursive.svg) | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-recursive.svg)    |
| **Role name**              | The name of the role each side plays in a relationship. The supervising side is supervisor, the other supervisee. Text beside the line. In a recursive relationship both rectangles are the same, so without it you can't tell which line is which                                     | ![](/static/images/database-systems-ch2-er-schema-table/sym/er-recursive.svg)    | Stays as the FK column name (Super_ssn)                                       | —                                                                                |

## 7. Relational model, keys and integrity

| Concept                   | Meaning                                                                                                                                                             | ① ER                                                                       | ② Schema                                                                      | ③ Table                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **Relation**              | One table. One ER rectangle, one M:N diamond and one double oval each become one table. Sounds like relationship (diamond) but is a different word                  | 1 rectangle / 1 M:N diamond / 1 double oval → one relation each            | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-entity.svg)    | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-relation.svg)         |
| **Relation schema**       | The table's template. Name + column names. EMPLOYEE(Fname, …, Dno). This is the schema figure; in the table figure, the header row                                  | —                                                                          | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-entity.svg)    | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-schema.svg)           |
| **Relation state**        | The rows currently in that template. Changes as rows are inserted and deleted, but the schema stays. Everything below the header in the table figure                | —                                                                          | —                                                                             | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-state.svg)            |
| **Tuple**                 | One row. One employee = one entity, or one WORKS_ON row = one relationship fact                                                                                     | One entity / one relationship instance                                     | —                                                                             | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-tuple.svg)            |
| **Domain**                | The range of values allowed in that column. Salary is a positive integer. Values outside the range can't go in                                                      | Not drawn                                                                  | As the type in DDL                                                            | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-domain.svg)           |
| **NULL**                  | No value in the cell. Unknown, or not applicable. Not 0 or an empty string. Borg's Super_ssn, who has no supervisor                                                 | Comes from the partial side                                                | —                                                                             | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-null.svg)             |
| **Degree**                | In the relational model, the number of columns in a table. Count the header boxes. Same name as ER's degree (number of rectangles) but a different thing            | Leaf ovals + FKs brought in                                                | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-degree.svg)    | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-degree.svg)           |
| **Superkey**              | A set of columns where no two rows can have the same values. \{Dnumber\} works, and so does \{Dnumber, Dname\} with extras added                                    | —                                                                          | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-superkey.svg)  | —                                                                                    |
| **Key**                   | A superkey that stops being a superkey if you remove even one column. \{Dname\} and \{Dnumber\} each. If there are several, all are candidates                      | Underlined ovals (both Name and Number)                                    | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-candidate.svg) | —                                                                                    |
| **Primary key**           | The one candidate picked to represent the table. Dnumber. Underlined. A column with no duplicates and no NULLs in the table                                         | —                                                                          | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-pk.svg)        | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-key.svg)              |
| **Foreign key**           | A column holding another table's (or its own table's) PK values to point at that row. EMPLOYEE.Dno = 5 is row 5 of DEPARTMENT. An arrow in the schema               | 1:N and 1:1 diamonds, double rectangles, double ovals, recursive → all FKs | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-1n.svg)        | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-1n.svg)               |
| **Both PK and FK**        | A column brought in from someone else's PK that is also part of its own PK. WORKS_ON's Essn, Pno. Half yellow, half blue                                            | M:N diamond, double oval, double rectangle                                 | ![](/static/images/database-systems-ch2-er-schema-table/sym/sc-pkfk.svg)      | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-mn.svg)               |
| **Key constraint**        | No two rows with the same PK value. You can't insert two employees with Ssn 123456789                                                                               | Underlined oval                                                            | Underline                                                                     | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-key-constraint.svg)   |
| **Entity integrity**      | PK cells can't be NULL. An employee with an empty Ssn can't be identified                                                                                           | —                                                                          | Underlined column                                                             | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-entity-integrity.svg) |
| **Referential integrity** | An FK cell's value must actually exist in the other table's PK, or be NULL. Dno = 7 with no department 7 is a violation                                             | —                                                                          | That value must exist at the arrow's end                                      | ![](/static/images/database-systems-ch2-er-schema-table/sym/tb-referential.svg)      |
| **Violation checks**      | Insert checks all three: Key, Entity and Referential. Delete only checks whether other rows point at the deleted row through an FK. Treat update as delete + insert | —                                                                          | —                                                                             | Bottom right of figure ③                                                             |
