## 0. Introduction

During the semester, lecture files, assignment attachments and notices keep appearing on the school LMS for every course. I collect these files in iCloud under `UNIV/<semester>/<course>/` and write my notes there. The problem was that a person had to check by eye, every time, what had not been downloaded yet. Assignment deadlines were also often on the LMS only, not on my calendar.

`lms-sync` is the skill that hands this job to the agent. When I say "get the LMS files", it runs three steps per course: download missing files, convert PPT to PDF, and add deadlines to the calendar. The skill is one `SKILL.md` and one helper script, `pagecount.mjs`. Sizes and run records are in the [By the numbers](#by-the-numbers) table.

The sources are the 3 commits to this skill in my dotfiles repo, the worklog for school work, and the memory change log. Where a reason is not written down anywhere, the post says "no record". Values that must not be public, such as course numbers, the school account and the login steps, are left out.

## 1. The shape of one run

As an analogy, it is like walking past each course's notice board once, picking up only the handouts you have not taken yet, binding the slides into a book, and copying the due dates onto a wall calendar.

![One lms-sync run: LMS course page, Files, Convert, Calendar](/static/images/skills-09-lms-sync/sync-flow.svg)

_One lms-sync run: LMS course page, Files, Convert, Calendar_

The notice board is the course page of a Moodle-based LMS, the handouts are its modules (`ubfile` lecture files, `assign` assignment attachments, `ubboard` notice attachments), and the wall calendar is Google Calendar.

The agent does not use an LMS API. On top of the session I am already logged into in Chrome, it opens a new tab through the Claude in Chrome extension and runs JavaScript `fetch` inside the page. The limits that come with this approach are written at the top of the skill.

- **School notice (2026-11-09)**: abnormal heavy access can get an account restricted. So the skill goes one course at a time, pauses between requests, never runs `fetch` in parallel, and fetches only what is missing.
- **Extension limits**: a JavaScript call is cut off after about 45 seconds (the script keeps running), and results are truncated at about 1000 characters. One course per call; results are stored on `window` and read back in pieces.
- **Query string masking**: if a result contains a URL query string, the extension replaces it with `[BLOCKED: Cookie/query string data]`. So only file names are returned.
- **Approval scope**: the request to fetch is itself the approval to download the missing files. The agent does not ask per file; it lists what it saved in the report.

At first this was not a skill but a memory file (notes on collecting LMS files). On 2026-11-17, when task-specific rules were moved from memory into skills, `lms-sync` was born at 46 lines. Why a skill rather than memory is the same story as in [CH0](/en/blog/side-projects/skills/skills-00-overview/): this is not needed in every session, only when looking at the LMS.

## 2. Recognizing files already downloaded

As an analogy, it checks whether two sheets of paper are the same by fingerprint, not by the name tag stuck on them. I often rename the files I download, so comparing names alone would fetch the same file again.

![Deciding whether one LMS item is already there: manifest, name match, SHA-1](/static/images/skills-09-lms-sync/match-flow.svg)

_Deciding whether one LMS item is already there: manifest, name match, SHA-1_

The name tag is the file name, the fingerprint is a **SHA-1 hash**, and the list of what was taken is the course folder's **manifest** file, `.lms-sync.json`.

The first version (2026-11-17) compared by file name only (or by title when the name could not be read). Two days later, the 2026-11-19 commit turned this into three steps.

1. **Manifest**: each course folder keeps `.lms-sync.json`, one entry per LMS module id: `{"title", "name", "sha1", "size", "path"}`. An item in the manifest counts as already there whatever its local name is now. It is fetched again only when its `path` is gone and no local file has the same `sha1`.
2. **Name comparison**: items not in the manifest are matched by name against the whole course folder, recursively and across every file type, including `jpg`s attached to notices.
3. **Hash comparison**: if no name matches, the page `fetch`es the file without saving it and hashes it with `crypto.subtle.digest("SHA-1", ...)`. Local files of the same extension are hashed with `crypto.createHash("sha1")` in `node -e`. A match means the file was only renamed, so it is recorded in the manifest and not saved.

Why SHA-1 and not MD5 is in the worklog: the browser's Web Crypto `crypto.subtle` has no MD5. The browser and the local side have to use the same algorithm, so it became SHA-1. The local side uses `node` because the command is the same on macOS and Windows.

The hash comparison also catches duplicate posts. In one course, the file posted under "Chapter 15" was actually the same file as the Chapter 14 pptx. The skill keeps this as one line: when a fetched file looks like one already there, compare SHA-1 and drop the duplicate.

Only files that are truly missing get saved. The fetched blob is clicked through `<a download>`, lands in `~/Downloads`, and is moved with `mv` into the course folder. For lecture files, `GET /mod/ubfile/view.php` redirects to the file, but `HEAD` returns 404, so the file name is taken from the last path segment of `r.url` after `fetch`. If the redirect goes to another host, `fetch` throws a TypeError, and the item is matched by title instead. Items that only have an `열기` (Open) button go to a viewer and cannot be downloaded; the report counts them as viewer-only.

The same commit also fixed where files go. The folder's existing layout comes first; these defaults apply only when it has none.

| Kind                              | Place                                                    |
| --------------------------------- | -------------------------------------------------------- |
| Lecture files (`ubfile`)          | `pdf/`, with the original pptx next to its pdf           |
| Assignment attachments (`assign`) | `hw/hw<N>/`, or `hw/<assignment title>/` when unnumbered |
| Notice attachments (`ubboard`)    | `공고문/` (notices folder)                               |
| Syllabus                          | Course folder root, as `<course name>-강의계획서.pdf`    |
| Anything else                     | Course folder root, and the report says where it went    |

## 3. PDF conversion and page count check

As an analogy, it binds a stack of slides into a book, then checks that the "n pages in total" line at the front matches the original number of slides.

![Two ways to count PDF pages: /Count of the root Pages and the number of /Type /Page objects](/static/images/skills-09-lms-sync/page-count.svg)

_Two ways to count PDF pages: /Count of the root Pages and the number of /Type /Page objects_

Binding is `soffice --headless --convert-to pdf`, the "n pages in total" line is the `/Count` at the root of the PDF page tree, and counting loose sheets is counting `/Type /Page` objects.

`ppt`, `pptx`, `doc` and `docx` are converted with LibreOffice's `soffice --headless --convert-to pdf --outdir <same folder> <file>`, and the original stays next to the pdf. The Mac has LibreOffice from Homebrew. Windows has none (checked 2026-11-19), so the agent converts with the installed PowerPoint, or asks me before installing LibreOffice with `winget`. `hwp` files are left alone and only listed, because LibreOffice cannot read current HWP.

After conversion, the page count must match the slide count. The slide count is the number of `ppt/slides/slide*.xml` files inside the pptx zip. Counting pages turned out to be the tricky part. The first version said to use mupdf's `mutool info` or count `/Type /Page` objects, but Windows has no `mutool`, and `mdls` on the Mac returned null for the page count.

So on 2026-11-19 a dependency-free Node script, `pagecount.mjs`, was added. It does two things.

- It reads the PDF as `latin1` and collects the `N 0 obj` objects. Compressed object streams (`/Type /ObjStm`) are decompressed with `zlib.inflateSync` so the objects inside are collected too. When an object number appears again, the later definition wins (incremental update).
- The first column is the largest `/Count` among `/Type /Pages` objects, the page count the root page tree states. The second column is the number of `/Type /Page` objects, marked `OBJ+` when it differs from the first.

Why the first column is trusted is recorded with numbers in the script comment and the worklog. Checked against the Windows PDF API page count on 110 course PDFs, the root `/Count` matched on all 110. The object count was higher on 2 of the 110. Those PDFs keep orphan pages that are not linked into the page tree, so `OBJ+` is only a flag, not an error. If LibreOffice breaks the layout, the agent converts again with PowerPoint and says so in the report.

There were few actual conversions. The first run on 2026-11-17 converted one pptx, and its 48 slides matched 48 PDF pages. The 2026-11-20 run re-counted one existing PDF (35 pages, 35 slides).

## 4. Adding deadlines to the calendar

As an analogy, it reads the assignment notice and writes the due date on the calendar, but skips it when that day already has an entry for the same course.

![Deciding whether one deadline goes on the calendar: submitted, past, same date + course](/static/images/skills-09-lms-sync/calendar-dedupe.svg)

_Deciding whether one deadline goes on the calendar: submitted, past, same date + course_

The notice is the assignment page's `.submissionstatustable` (end time, submission status) plus notice board posts, the calendar is the school-schedule calendar in Google Calendar, and checking the day is `list_events`.

- **Submitted assignments are skipped.** Past dates are skipped too.
- **Duplicates are matched by date and course, not by title.** Some existing events were added by hand, so title formats vary. The same deadline can be there as "assignment due" or "[Submit] …".
- **Exam dates come from notices only.** This semester's syllabi list exams by week ("week 15") with no date. So the agent does not guess; it reports "no date yet".
- **Search scope**: the calendar connector's `search_events` only searches the primary calendar. So the agent finds the school calendar's id with `list_calendars` and runs `list_events` on that calendar around the date.
- A new event gets the title `[course short name] <assignment> due`, the LMS end time, and the LMS item title as its description. The list (title, date, reminder) is shown before writing, unless the request already said to add them.

The reminder time once caused a rule conflict. My general calendar rule was "always ask for the reminder time first". On the first run, 2026-11-17, it collided with the LMS deadline default (9 a.m. the day before; 900 minutes before for all-day events as a popup). That day a line saying "LMS assignment deadlines are the exception" went into the memory change log, and the skill now says this default is my standing answer for LMS deadlines, so the general rule does not apply.

## 5. Reporting and closing to-dos

As an analogy, after one round it writes a line of numbers in the ledger, then crosses finished assignments off the to-do column of every other logbook.

![What a run leaves behind: report, worklog/univ/WORK.md, worklog/*/WORK.md](/static/images/skills-09-lms-sync/report-record.svg)

_What a run leaves behind: report, worklog/univ/WORK.md, worklog/\*/WORK.md_

The ledger is the report, my logbook is `worklog/univ/WORK.md`, and the other logbooks are every worklog key (`worklog/*/WORK.md`). The worklog structure is covered in [CH6. session-flow](/en/blog/side-projects/skills/skills-06-session-flow/).

The report is in numbers per course: downloaded, already there, viewer-only, failed (with the reason), converted, events added, skipped as duplicates. The same numbers go as one dated line under `## 한 일` (done) in `worklog/univ/WORK.md`. New LMS facts, such as a new course or a changed page structure, go into the school file in memory.

The last rule was added on 2026-11-27. That day the LMS sync session confirmed two assignments as submitted and closed only the to-dos in `worklog/univ/WORK.md`. The same assignments were also open to-dos under the worklog key for the virtual machine labs, and the session did not look there. So the skill gained a line: for each assignment confirmed as submitted, grep every key's `WORK.md` for the course short name and the assignment number (like `HW7`) and close its to-dos. The shared instructions and the `session-flow` skill got the same kind of rule that day.
