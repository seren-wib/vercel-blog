> Post 6 of the series, the last one. The whole project is in [Coffee Shop 0](/en/blog/side-projects/coffee-shop/coffee-shop-00-overview/). This post covers the four deploy pull requests (#108, #109, #125, #127) and the first production deploy on November 27.

## In one paragraph

The deploy script takes one tag, builds it in a new folder, and only moves the `current` link once the health check passes. On failure it points the link back at the previous folder. The script was rehearsed in a container, which caught three bugs, then went to production for the first time (29 s, health 200). After that came continuous deployment, where GitHub Actions runs the same script on the server once CI passes. It is still switched off because the AWS side is not set up yet.

## 1. The server starts even without a key (#108)

One thing blocked deployment: there was no Toss test key for this project yet. If the server could not start without a key, the whole shop would be held hostage by one payment feature.

So an empty `TOSS_SECRET_KEY` makes `PAYMENTS_ENABLED` false. Payment start, payment confirm and admin cancel approval stop with 503 `PAYMENTS_DISABLED` before touching the PG or the DB, and everything else (list, cart, orders, admin) keeps working. The [payment switch](/en/blog/dev/payments/payments-00-basics/#payment-switch) is decided by whether a key exists, not by a code path.

The other way around, dangerous settings keep the server from starting at all (`config/checks.py`):

- `DEBUG` off with an empty `ALLOWED_HOSTS`: refuse to start
- `TOSS_SECRET_KEY` not starting with `test_`: refuse to start. A live key put in by mistake, and real money moving, is stopped at startup

This pull request added 6 tests, and all 6 were confirmed to fail on the code before the change. 230 backend tests plus 1 concurrency test passed.

## 2. A deploy script that can roll back

In moving terms: instead of carrying things out of the old house while carrying them into the new one, you furnish the new house completely and then just move the nameplate. If the new house is wrong, you put the nameplate back on the old one.

![Deploy script diagram. Under /srv/coffee-shop/releases there is one folder per tag. deploy.sh clones the new tag into a new folder and checks it is an ancestor of main, builds the venv with pip install, builds the frontend with version.txt, backs up the DB before deploying and runs migrate, then switches the current symbolic link to the new folder. If the health check and version.txt match, it is done; if not, current goes back to the previous folder. The DB and .env live outside the release folders](/static/images/coffee-shop-06-deploy/release-switch.svg)

The new house is `releases/<tag>/`, and the nameplate is the `current` symbolic link. The analogy stops here.

What `deploy/deploy.sh release-YYYYMMDD-N` does, in order:

1. Check the tag format (exit code 2 if wrong); stop if `.env` is missing
2. Clone the tag into `releases/<tag>/` and check the commit is an ancestor of `main` (if not, delete and stop)
3. Backend venv and `pip install`, frontend `npm ci` and build. The build output gets a `version.txt` holding the commit hash
4. Back up the DB before deploying, run `migrate`
5. Create `current.new` and swap it over `current` with `mv -T` (the link changes in one step)
6. Check the health endpoint (`/api/health/`) and that the `version.txt` nginx serves is this commit. On failure, point `current` back at the previous release and, if the DB needs restoring, print the pre-deploy backup path
7. Keep only the last 3 releases

The DB file and `.env` live outside the release folders (`/srv/coffee-shop/data/`, `/srv/coffee-shop/.env`), so switching the link leaves them alone. The same pull request added the nginx config template, security headers, a log format that drops query strings, a script that trusts `CF-Connecting-IP` only from Cloudflare address ranges, systemd units (the app, and a daily 04:00 backup timer), a journald size limit and `install.sh` for the first setup.

## 3. What the rehearsal caught (#125)

The shell scripts in #108 had only been through `bash -n` (syntax check). Before the first run on the production server they were [rehearsed](/en/blog/dev/devops/devops-00-basics/#rehearsal) in an Ubuntu 24.04 container with only `systemctl` faked.

| Case                         | Result                                     |
| ---------------------------- | ------------------------------------------ |
| First deploy                 | 54 s, health 200                           |
| Tag whose health check fails | Rolled back to the previous release (rc 1) |
| Tag whose `migrate` fails    | `current` unchanged (rc 1)                 |
| Tag not on `main`            | `current` unchanged (rc 1)                 |
| Malformed tag                | Exit code 2                                |
| `shellcheck -S warning`      | 0 warnings                                 |

Three bugs from the rehearsal were fixed:

- **Executable bit.** Four scripts in `deploy/` were committed as `100644`. They got the executable bit.
- **A link pointing at itself after a failed first deploy.** On the first deploy there is no `current`. Reading the previous release with `readlink` returned the link path itself, so a failed first deploy left `current` pointing at itself. `readlink -e` returns nothing when the target does not exist.
- **gunicorn control socket.** gunicorn 27 opens a control socket in `$HOME`. The app account is a system account that cannot log in and has no home folder. `control_socket_disable = True` turned it off.

## 5. Continuous deployment (#127)

A manual deploy means the operator logs in over SSH and types `deploy.sh`. After #127, merging to `main` is the only human step.

![Continuous deployment diagram. A push to main runs the ci workflow; on success, the deploy workflow starts through workflow_run, but only when DEPLOY_ENABLED is true. It picks the next release-YYYYMMDD-N tag, takes an IAM role through GitHub OIDC, then pushes the tag. SSM Run Command (AWS-RunShellScript) runs deploy.sh with the tag on EC2 and prints the result. Finally it reads version.txt through Cloudflare and checks it equals the commit. Port 22 is not opened to GitHub; the SSM agent uses outbound 443](/static/images/coffee-shop-06-deploy/cd-flow.svg)

The rules in `.github/workflows/deploy.yml`:

- **When it runs.** When `ci` succeeds on a push to `main` (`workflow_run`), or by hand. An automatic run skips a commit that is no longer the tip of `main`, a commit that already has a release tag (a `ci` re-run), and changes that are docs-only since the last tag.
- **Credentials first, tag second.** If the IAM role is refused, no tag is left behind.
- **SSM, not SSH.** Port 22 is not opened to GitHub Actions runners. The SSM agent on the server opens outbound 443 and picks the command up. The role may only `ssm:SendCommand` with `AWS-RunShellScript` to that one instance and read the result, and only for requests from `main` of this repository.
- **One deploy at a time.** `concurrency: deploy-production`, `cancel-in-progress: false`. A deploy must not be cut off halfway, so the next run waits.
- **No long-lived secrets.** The three Actions secrets (role ARN, instance ID, production URL) are identifiers, not secrets; they are stored as secrets only so the public logs mask them.
- **Off by default.** It runs only while the repository variable `DEPLOY_ENABLED` is `true`. Merging it before the AWS setup does nothing.

The tag-picking shell was run in a scratch repository for five cases: first deploy, `ci` re-run, docs-only change, the number after `-10`, and a manual run on an already tagged commit. The AWS part runs only once the setup is done.

## Glossary

| Term                                                         | Meaning                                                                                |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| [Deploy](/en/blog/dev/devops/devops-00-basics/#deploy)       | Putting new code on the production server for users                                    |
| Release tag                                                  | A git tag on the commit to deploy. Here, `release-YYYYMMDD-N`                          |
| Symbolic link                                                | A file that points at another path. `current` points at the release folder in use      |
| Rollback                                                     | Returning a failed deploy to the previous release                                      |
| Health check                                                 | A light API that shows whether the server can handle requests. Here, `/api/health/`    |
| systemd                                                      | Linux's service manager. It runs the app and the backup timer                          |
| SSM Run Command                                              | An AWS Systems Manager feature that sends a command to the agent on an instance to run |
| IAM role                                                     | A bundle of AWS permissions, borrowed briefly with an OIDC token                       |
| `workflow_run`                                               | A trigger that starts this workflow when another workflow finishes                     |
| [Rehearsal](/en/blog/dev/devops/devops-00-basics/#rehearsal) | Running the production procedure outside production beforehand                         |
