# 5. Software Design Principles

## 5.1 Divide and Conquer

**[Divide and conquer](glossary:divide-and-conquer)**: split a big problem into pieces small enough to solve directly, solve them, then combine the results (e.g. [merge sort](glossary:merge-sort))

- Steps
  1. **Divide**: recursively split into subproblems until they can't be split further
  2. **Conquer**: solve each subproblem recursively
  3. **Combine**: merge the subproblem answers into the answer for the original problem

## 5.2 Modularity

**[Modularity](glossary:modularity)**: split a problem into independent [modules](glossary:module) with standard [interfaces](glossary:interface), then combine reusable [modules](glossary:module) to solve the whole (e.g. hardware built by assembling parts)

- A [module](glossary:module) with one function is built once and reused
- **[Module](glossary:module)**: a piece of code that can be built and maintained independently, so other systems can reuse it
- **[Modular programming](glossary:modularity)**: a design technique that separates program functions into independent, interchangeable [modules](glossary:module)
- Difference from [divide and conquer](glossary:divide-and-conquer): both split the problem; [modularity](glossary:modularity) adds **[interfaces](glossary:interface), independence and reuse** to the pieces
- What a [module](glossary:module) means
  1. As independent of other [modules](glossary:module) as possible
  2. Reusable in other systems, interchangeable within the system
  3. A part of the system's code and a function (a structural unit)
- Basic principles
  - Good [modularity](glossary:modularity): changing one part barely affects the rest
  - **High [cohesion](glossary:cohesion), loose [coupling](glossary:coupling)**
  - Closely related to [structured](glossary:structured-programming) (procedural) and [object-oriented](glossary:object-oriented-programming) programming; started around the 1960s
- Benefits
  1. The system is easier to understand
  2. The system is easier to maintain
  3. Reuse: a finished [module](glossary:module) never has to be rewritten

## 5.3 Abstraction

**[Abstraction](glossary:abstraction) (computer science)**: pulling only the core concepts or functions out of complex data, [modules](glossary:module) or systems and expressing them simply (e.g. aerial photo → map with only roads and buildings)

- How to [abstract](glossary:abstraction)
  1. **[Generalization](glossary:generalization)**: keep what things have in common, drop the differences (undergrad, grad student → student)
  2. **Removing detail**: keep only what matters, delete unneeded detail
- **Data**: values that represent real-world things as characters, numbers, sound, images, video or text
- Types of data
  - **[Quantitative](glossary:quantitative-data) (numerical) data**: physical values measured directly (temperature, price, sales)
  - **[Qualitative](glossary:qualitative-data) (categorical) data**: logical values that aren't physical even when written as numbers; nominal and ordinal (gender, blood type, letter grade)
- What to [abstract](glossary:abstraction)
  - **Operational data**: data the organization needs to run and manage itself; only this gets abstracted
  - **[Abstraction](glossary:abstraction) target**: the set of data needed to solve the problem
  - **Non-operational data**: everything else, can be ignored
  - Operational vs non-operational depends on the system's purpose (student records → students, grades; facility management → roads, buildings)
- Operational data becomes a [class](glossary:class): student → `Student { id, name, address, mobile, major }`, unneeded attributes are dropped

## 5.4 Stepwise Refinement

**[Stepwise refinement](glossary:stepwise-refinement)**: a **[top-down](glossary:top-down-design)** design method that starts at a high level of [abstraction](glossary:abstraction) and adds detail at each step on the way down (e.g. "print the average" → input, sum, divide, output → [pseudocode](glossary:pseudocode) → [Java](glossary:java))

- Tasks are broken into subtasks, data into data structures
- Start from a big [abstract](glossary:abstraction) step and split it into smaller tasks, repeating until [pseudocode](glossary:pseudocode) comes out
- Difference from [divide and conquer](glossary:divide-and-conquer): both split the problem; [divide and conquer](glossary:divide-and-conquer) **combines** the subanswers again, [stepwise refinement](glossary:stepwise-refinement) **concretizes** by lowering the level of [abstraction](glossary:abstraction) until it reaches code

## 5.5 Information Hiding

> [Abstraction](glossary:abstraction) (what to keep) → [encapsulation](glossary:encapsulation) (bundle it) → [information hiding](glossary:information-hiding) (hide with private, open only through public methods)

**[Information hiding](glossary:information-hiding)**: hiding a [class](glossary:class)'s internals and allowing access only through defined methods; it starts from [abstraction](glossary:abstraction) (e.g. `private name` + `public getName()`)

- Process
  1. Use [abstraction](glossary:abstraction) to find what the requirements have in common
  2. Remove whatever is unrelated to the goal
  3. [Encapsulate](glossary:encapsulation) the common part
  4. Give the [encapsulated](glossary:encapsulation) target a data type and hide it
- Basic idea
  - Access to a [class](glossary:class)'s internal attributes is restricted; access only through its [interface](glossary:interface) (methods)
  - Good [information hiding](glossary:information-hiding) comes from good [class](glossary:class) [abstraction](glossary:abstraction)
- Relation to object orientation
  - [Object-oriented](glossary:object-oriented-programming) programming starts from [information hiding](glossary:information-hiding)
  - The goal of [OO](glossary:object-oriented-programming) is flexibility (extending, replacing, changing functions); [information hiding](glossary:information-hiding) is the strategy that makes it possible
- [Java](glossary:java) example

```java
class Student {
    private int id;
    private String name;

    public String getName(int id);
    public void setName(int newId, String iname);
}
```

- `private` attributes are blocked from outside access, reachable only through `public` methods

## 5.6 Increasing Module Cohesion

![Cohesion and coupling: on the left each module has one purpose, so links inside are strong and links between modules are few; on the right purposes are mixed, so there are many links between modules](/static/images/software-engineering-ch5-design-principles/cohesion-coupling.svg)

**How to read the figure**

- Box = [module](glossary:module), circle = element inside a [module](glossary:module), color = purpose
- Black line = link inside a [module](glossary:module) ([cohesion](glossary:cohesion)), red line = link between [modules](glossary:module) ([coupling](glossary:coupling))
- Left (good): elements with the same purpose sit in one [module](glossary:module) → strong inside links, few outside links
- Right (bad): elements with the same purpose are scattered across [modules](glossary:module) → many red lines to reach each other

**[Cohesion](glossary:cohesion)**: how tightly the elements inside one [module](glossary:module) ([class](glossary:class)) hold together around one purpose; higher is better (e.g. a grade [module](glossary:module) contains only grade code)

- High: elements closely related, one purpose / Low: loosely related, several purposes
- High [cohesion](glossary:cohesion) → packages, [modules](glossary:module) and [classes](glossary:class) are designed consistently
- Having only functional [cohesion](glossary:cohesion) is best
- Types (high → low)

| Rank | Type                                                 | Meaning                                                                                                                        | Example                                           |
| ---- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| 1    | [Functional](glossary:functional-cohesion)           | Contains exactly the elements one function needs; the ideal                                                                    |                                                   |
| 2    | [Sequential](glossary:sequential-cohesion)           | One element's output is the next one's input; data flow                                                                        | Function calls                                    |
| 3    | [Communicational](glossary:communicational-cohesion) | Groups functions that use the same input or produce the same output data; also called "exchange" [cohesion](glossary:cohesion) | Update and save a record + send it to the printer |
| 4    | [Procedural](glossary:procedural-cohesion)           | Grouped by order of instruction execution; weakly connected, hard to reuse                                                     | Read grades → sum → GPA → save → print            |
| 5    | [Temporal](glossary:temporal-cohesion)               | Groups tasks that run at the same time                                                                                         | Initializing the whole system                     |
| 6    | [Logical](glossary:logical-cohesion)                 | Groups things that are logically similar but functionally unrelated                                                            | Input from tape, disk and network                 |
| 7    | [Coincidental](glossary:coincidental-cohesion)       | Unrelated things grouped with no purpose; the worst                                                                            |                                                   |

## 5.7 Reducing Coupling Between Modules

**[Coupling](glossary:coupling)**: the degree of interdependence between [modules](glossary:module); lower is better (e.g. if A calls B, A and B are coupled)

- High: changing one [module](glossary:module) affects others / Low: independent, almost no effect
- High [coupling](glossary:coupling) looks easier to implement at first, but debugging and fixing get much harder when something fails
- Exchanging only the data that's needed is best
- Types (low [coupling](glossary:coupling) → high [coupling](glossary:coupling))

| Rank | Type                                   | Meaning                                                                                              | Example                                                                  |
| ---- | -------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1    | [Data](glossary:data-coupling)         | Exchange only the data that's needed                                                                 | `add(a, b)`                                                              |
| 2    | [Stamp](glossary:stamp-coupling)       | Pass a whole data structure                                                                          | Passing the whole `Student` object when only the name is needed          |
| 3    | [Control](glossary:control-coupling)   | Pass control information to change the other [module](glossary:module)'s behavior                    | A sort function that takes a compare function                            |
| 4    | [External](glossary:external-coupling) | Depends on [modules](glossary:module) or hardware outside the software                               | Protocols, external files, device formats                                |
| 5    | [Common](glossary:common-coupling)     | Share global data; hard to reuse, control access and maintain                                        | Shared [global variables](glossary:global-variable)                      |
| 6    | [Content](glossary:content-coupling)   | Directly modifies another [module](glossary:module)'s data or passes control flow into it; the worst | Directly modifying another [module](glossary:module)'s internal variable |

- 5 extra types (no rank)
  - **Temporal**: depends on execution timing or order (A must run before B)
  - **Sequential**: one [module](glossary:module)'s output is another's input; a chain of dependencies
  - **Communicational**: share a communication mechanism such as shared messages or a DB
  - **Functional**: depend on each other's functions, e.g. calling another [module](glossary:module)'s functions
  - **Data-structured**: share a common data structure such as a DB table or data file; integrity is hard to keep
- Benefits of low [coupling](glossary:coupling): better [maintainability](glossary:maintainability), better [modularity](glossary:modularity) (independent development and testing, reuse), better [scalability](glossary:scalability) (easy to add and remove [modules](glossary:module))
- Drawbacks of high [coupling](glossary:coupling): more complexity, less flexibility, less [modularity](glossary:modularity)
