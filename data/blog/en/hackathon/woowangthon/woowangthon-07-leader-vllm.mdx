## 0. Introduction

> Part 7 of the series. The last piece of build stage 4: the day a local model went up on the leader's [GPU](glossary:gpu). The cluster install is in [part 6](/en/blog/hackathon/woowangthon/woowangthon-06-k3s-install/), and the big picture is in [Woowangthon 0](/en/blog/hackathon/woowangthon/woowangthon-00-overview/).

The leader PC's [GPU](glossary:gpu) was sitting idle, so I decided to bring up a local model that day. A team meeting the same day changed the deploy design, so moving that into the docs came first.

In restaurant terms, the [GPU](glossary:gpu) is a kitchen counter and the model file is a cookbook lying open on it. A notepad for the guests' orders has to sit on the same counter, but the book took 6 GB and there was no room left to write one long order. The counter is the [GPU](glossary:gpu), the cookbook is the model file, the notepad is the [KV cache](glossary:kv-cache), and the long order is a [16K](glossary:context-window)-[token](glossary:token) request.

I ran [Qwen3-8B-AWQ](glossary:qwen) with [vLLM](glossary:vllm) on an RTX 3080 (10 GB). One [16K](glossary:context-window) request did not fit and it stopped at start-up, so I switched the [KV cache](glossary:kv-cache) to [FP8](glossary:fp8) and it fit.

## 1. What changed in the meeting

We held a team meeting on Discord in the early hours. Five decisions touched the cluster.

| Decision                                                                                                                                                                                 | What changes on the cluster side                                                                                                            |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Deploys (building manifests, applying them, checking they work) are run by a [GoCD](glossary:gocd) executor on the leader                                                                | The platform server no longer writes deploys to the cluster. The executor gets its own account                                              |
| Everything from intake to the build request, plus the security scan, runs in the platform server ([Nest](glossary:nestjs))                                                               | Nothing on the cluster, but one reason for keeping a separate AI server is reversed                                                         |
| Student [secrets](glossary:kubernetes-secret) (.env) go from the platform server straight to the leader over the [private network](glossary:tailscale) ([Tailscale](glossary:tailscale)) | Secrets skip the deploy pipeline and the build. The server account keeps write access to [secrets](glossary:kubernetes-secret)              |
| Logs are kept only as snapshots cut at the moment of a spike                                                                                                                             | No log collector on the cluster                                                                                                             |
| The [message queue](glossary:message-queue) ([Kafka](glossary:apache-kafka)) and the local model install move down the list                                                              | The local model is off the demo path. The [GPU](glossary:gpu) was sitting idle, though, so I decided to bring it up that day (sections 2–7) |

Around part 6 I left the deploy flow drawing alone on purpose because there was no [decision record](glossary:adr) ([ADR](glossary:adr)) yet. Now that the decision was made, I wrote the [ADRs](glossary:adr) first, as the repo rules say.

- **[ADR-009](glossary:adr)**: deploys run on a [GoCD](glossary:gocd) executor on the leader, and the [GoCD](glossary:gocd) server sits on the same [AWS EC2](glossary:amazon-ec2) instance as the platform server. It replaces only the "deploy" item of the older [ADR-004](glossary:adr) (the server calls the leader's [Kubernetes](glossary:kubernetes) API directly to deploy). Writing [secrets](glossary:kubernetes-secret), actions like restart, and reading status still go straight from the server.
- **[ADR-010](glossary:adr)**: everything from intake to the build request, plus the security scan, runs in the platform server. The first [ADR](glossary:adr) gave "keep the part that reads student code apart from the backend" as one reason for a separate AI server, and this decision undoes it. So the cost went into the [ADR](glossary:adr) too: the repo is fetched read-only into a temporary folder, deleted afterwards, and never run.

The system definition, the AI scope doc and five diagrams changed along with them. In the cluster design doc I rewrote the permissions section. Until now one platform server account held everything, deploy rights included. Now there are two accounts.

| Account         | Gets                                                                                                                                       | Can't                                                                           |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| Platform server | Create and delete student spaces, create their limits and block rules, write [secrets](glossary:kubernetes-secret), restart and stop, read | Create deploy resources, read [secrets](glossary:kubernetes-secret)             |
| Deploy executor | Create, change and delete deploy resources inside a student space, read what it needs to check a deploy                                    | Touch spaces, limits or block rules, read [secrets](glossary:kubernetes-secret) |

Before a deploy, the executor has to check that the [secrets](glossary:kubernetes-secret) are in place. But [Kubernetes](glossary:kubernetes) has no permission that lets you see only whether a Secret exists. Grant read and you see the values too. So the executor never reads Secrets. It checks against the list of key names the platform server left when it wrote them.

## 2. Making the GPU visible to Kubernetes

The tool that attaches the [GPU](glossary:gpu) to containers was [already picked up when k3s was installed](/en/blog/hackathon/woowangthon/woowangthon-06-k3s-install/#1-what-i-fixed-before-installing). What was left was for [Kubernetes](glossary:kubernetes) to know "this node has one [GPU](glossary:gpu)". The [NVIDIA device plugin](glossary:nvidia-device-plugin) tells it that. It runs once per node, and I changed it to run on the leader only.

```yaml
spec:
  runtimeClassName: nvidia
  nodeSelector:
    kubernetes.io/hostname: k3s-leader
  tolerations:
    - key: node-role.kubernetes.io/control-plane
      operator: Exists
      effect: NoSchedule
```

Without `runtimeClassName: nvidia` the plugin can't see the [GPU](glossary:gpu). With it, the leader's allocatable resources gained `nvidia.com/gpu: 1`. A test Pod asking for one [GPU](glossary:gpu) landed on the leader, printed RTX 3080, 10240 MiB, and exited.

## 3. Downloading the model

The model comes from [Hugging Face](glossary:hugging-face). Before downloading I measured the school network. Fetching the first 300 MB of the model file ran at about 47 MB per second.

The model is downloaded once into a [volume](glossary:persistentvolume) on the leader's disk (30Gi), and [vLLM](glossary:vllm) reads that folder offline. It doesn't fetch from the internet every time it restarts. I pinned the model repo's commit for the download, since the same name can point at different content later. 6.1 GB took 69 seconds.

## 4. 16K didn't fit in 10 GB

The [vLLM](glossary:vllm) settings come from the AI lead's (suda5936) design. The length it reads at once (the [context](glossary:context-window)) is [16K](glossary:context-window) [tokens](glossary:token). I brought it up and it died straight away.

![vLLM log with an fp16 KV cache. Loading the model took 5.71 GiB, 1.66 GiB left for the KV cache, and an error saying one request of length 16384 needs 2.25 GiB](/static/images/woowangthon-07-leader-vllm/kv-fp16.svg)

_[fp16](glossary:fp16) [KV cache](glossary:kv-cache): 1.66 GiB left, while one [16K](glossary:context-window) request needs 2.25 GiB_

A language model writes one [token](glossary:token) at a time and keeps the values it computed for every [token](glossary:token) it has read so far in memory. That's the [KV cache](glossary:kv-cache). [Qwen3-8B](glossary:qwen) uses about 144 KiB per [token](glossary:token). At [16K](glossary:context-window) [tokens](glossary:token) that's 2.25 GiB. When [vLLM](glossary:vllm) starts, it first checks whether it can hold one request of the maximum length, and if it can't, it doesn't start at all.

By the numbers I had worked out beforehand, it should have fit. With 90% of [GPU](glossary:gpu) memory (about 9 GiB) available and 5.7 GiB of weights taken out, I expected around 3 GiB left. What was actually left was 1.66 GiB. [CUDA](glossary:cuda)'s base memory, the memory used briefly during computation, and the pre-recorded [computation graphs](glossary:cuda-graph) take about 1.6 GiB between them, and the estimate had left that out.

There were three ways out.

| Option                                                         | Result                                                                                                         |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Raise [GPU](glossary:gpu) memory use to 0.95                   | Gains about 0.5 GiB, still around 2.2 GiB and short. And there's no slack left                                 |
| Cut the [context](glossary:context-window) to 12K              | It fits, but [16K](glossary:context-window) is the AI side's design value, not mine to change alone            |
| Store the [KV cache](glossary:kv-cache) in [FP8](glossary:fp8) | Halves it to about 72 KiB per [token](glossary:token). The same 1.67 GiB holds 24,352 [tokens](glossary:token) |

I went with [FP8](glossary:fp8). Storing the numbers in 8 bits can cost a little accuracy, so the tests also checked that [tool calls](glossary:tool-calling) and a long log summary still came out right (section 7).

![vLLM log after switching the KV cache to FP8. KV cache 24,352 tokens, 1.49 concurrent requests at 16,384 tokens each, start-up complete](/static/images/woowangthon-07-leader-vllm/kv-fp8.svg)

_[FP8](glossary:fp8) [KV cache](glossary:kv-cache): 24,352 [tokens](glossary:token), room for one [16K](glossary:context-window) request with space to spare_

## 5. If the Service is called vllm, vLLM won't start

After the switch to [FP8](glossary:fp8) it died with a different error. A setting called `VLLM_PORT` held an address like `tcp://...:8000`. I had never set anything like that.

[Kubernetes](glossary:kubernetes) did. For every [Service](glossary:service) in the same space, it injects [environment variables](glossary:environment-variable) like `<NAME>_PORT` into Pods. It's an old way of finding services. The [Service](glossary:service) in front of [vLLM](glossary:vllm) was named `vllm`, so `VLLM_PORT` appeared, and [vLLM](glossary:vllm) read it as its own setting. Adding `enableServiceLinks: false` to the Pod turned the automatic variables off. These days [DNS](glossary:dns) finds services by name, so the feature isn't needed.

## 6. Where did a concurrency of 3 come from

The plan said "3 [concurrent requests](glossary:concurrency)". After it was up, I traced where this 3 had come from.

The source was thin. On November 6 we asked the AI lead how many [concurrent requests](glossary:concurrency) to allow and got no answer. So the agent had set 3 as "2 student slots + 1 analysis call". The AI lead's design doc ([woowangthon/WOOWANGTHON_TEAM_18#32](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/32)) has no such number. It only says one deploy job has one open problem ticket.

With no decided value, I changed it to 1. Extra requests don't fail. They wait in line. [FP8](glossary:fp8) is still needed with fewer [concurrent requests](glossary:concurrency), because the start-up check is about "one [16K](glossary:context-window) request".

## 7. Checks

The tests ran from a test Pod inside the cluster, in the same space as [vLLM](glossary:vllm). The [API key](glossary:api-key) came straight from the Secret and was never printed.

![Results from the test Pod in the cluster. No key and a wrong key get 401, one request in 0.38 seconds, a tool call in 29 tokens, and three requests sent at once are handled in turn](/static/images/woowangthon-07-leader-vllm/vllm-test.svg)

_Test Pod results. The fourth line is three 300-[token](glossary:token) requests sent at once_

| Check                                                              | Result                                                                                              |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| No key, wrong key                                                  | Rejected with [401](glossary:http-status-code)                                                      |
| One request                                                        | 0.4 seconds                                                                                         |
| Tool call with thinking mode off                                   | Called `get_logs(proj-demo, 50)` correctly in 29 [tokens](glossary:token)                           |
| Three 300-[token](glossary:token) requests at once                 | Finished in turn at 2.6, 5.2 and 7.8 seconds (one at a time)                                        |
| Summary of a 15.1K-[token](glossary:token) log                     | 2.4 seconds, named the cause ([OOMKilled](glossary:oom)) correctly                                  |
| 16,385 [tokens](glossary:token)                                    | Rejected with [400](glossary:http-status-code) (the limit is 16,384)                                |
| [GPU](glossary:gpu) memory                                         | 8.3–8.6 of 10 GB                                                                                    |
| [Kubernetes](glossary:kubernetes) API server response during tests | 91 ms at most (71 ms idle). The [control plane](glossary:kubernetes-control-plane) didn't slow down |
| [vLLM](glossary:vllm) start-up                                     | About 52 seconds                                                                                    |

[vLLM](glossary:vllm) has a lower [priority](glossary:pod-priority) than student apps (it goes first when room runs out, and never pushes anything else out), with CPU and memory limits. It only accepts traffic from its own space. The path from outside (the AI server on AWS) opens in the server connection stage. It never goes on a public address. Put it there and anyone on the internet gets our [GPU](glossary:gpu).
