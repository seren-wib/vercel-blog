## In one paragraph

My public profile lives in three places: the GitHub profile README, this blog's About and Projects pages, and LinkedIn. `profile-edit` is the skill the agent opens when it changes any of them. Its rules come down to one idea. A person edits only two source files, the README and the blog are generated, and LinkedIn gets only the gap between the generated target and the live page, edited in a browser. The skill is 42 lines and 5,528 bytes, and 11 of its 28 bullets are LinkedIn editor traps.

## 1. One manuscript

As an analogy, keep a single manuscript and print it three times in different formats. Correct each edition separately and sooner or later the three disagree.

![One source, three profiles: profile-sync data/ → lib/render.mjs → GitHub README, blog, LinkedIn](/static/images/skills-04-profile-edit/pipeline-en.svg)

_One source, three profiles_

In real terms this is a **single source of truth** plus **code generation**. The manuscript is `data/profile.mjs` (intro, experience, education, certificates, awards, open source contributions) and `data/projects.mjs` (14 projects) in the private profile-sync repo, and the press is `lib/render.mjs`. The repo was created on 2026-10-25 and has 22 commits as of 2026-11-28.

The skill's first rules pin this down.

- Edit only `data/profile.mjs` and `data/projects.mjs`. The GitHub README, the blog's `data/authors/*.mdx` and `data/projectsData.ts` are generated output.
- Never edit the README by hand. Its format also comes from `lib/render.mjs`.
- Before generating, `git pull` all three repos: profile-sync, the profile README repo and vercel-blog.

The last rule has a record behind it. On 2026-10-28 a run generated from a stale `data/` and wiped entries another session had added, and the rule was written that day. The generator prints its source as is, so a stale source overwrites newer output with older content.

Generation runs after the tests. The documented command only reaches `scripts/build.mjs` if `npm test` passes, and on 2026-11-28 all 10 tests in `test/render.test.mjs` passed (94 ms). Each output ships differently. The README is committed straight to `main` of the profile repo, and the blog goes through a branch and a PR that is merged after CI passes. The blog PR process belongs to [CH5. pr-workflow](/en/blog/side-projects/skills/skills-05-pr-workflow/).

As of 2026-11-28, 2 of the 14 projects are not `hidden`. So the README shows all 14, and the blog and LinkedIn show those 2 plus the open source item, 3 in total. That number is the result of a cut on 2026-11-26, when 6 projects and 20 skills were removed from LinkedIn, leaving 4 skills.

The other rules are about content.

- The intro is one text in all three places. The Stairno Account paragraph sits second so it lands in the part LinkedIn's About shows before "see more". Other projects stay out of the intro.
- Lists put Building before Shipped. A project that is released and works is Shipped right away, even with updates still coming. The blog `status` field and LinkedIn end dates follow the same rule.
- The GitHub README keeps its format: the stars badges and the Contributing to section stay.
- Updates happen only when I ask. At first a cloud routine ran every Monday, but I decided to pick what goes up myself and turned it off on 2026-10-25. Now the candidates are gathered into a table and only the ones I pick go in.

## 3. LinkedIn gets only the gap

As an analogy, put the sign that is up next to the draft of the new sign, and swap only the panels whose letters differ. There is no machine that hangs the whole sign at once.

![LinkedIn: edit only the gap between live and target. Diff live.md against target.md, edit with Playwright, then copy target over live](/static/images/skills-04-profile-edit/linkedin-diff-en.svg)

_LinkedIn: edit only the gap between live and target_

In real terms this is a diff between **desired state** and **current state**. The generator never writes to LinkedIn. It stops at `linkedin/target.md`, and the live page is recorded in `linkedin/live.md`. Changes go in this order.

1. `git diff --no-index linkedin/live.md linkedin/target.md` lists the fields that would change.
2. On my go-ahead, Playwright edits them. I sign in myself. There are 8 seconds between saves.
3. When done, target is copied over live and committed.

There is no guarantee `live.md` still matches the page, though. I edit LinkedIn directly too, so the skill says to re-read the live page before editing. Cloud runs never touch LinkedIn.

There are a few policy lines as well. The positioning is backend plus AI, without leading on React or Next.js. English is the primary profile language and Korean the secondary one, and each is written natively rather than translated. Projects have no per-language version, so each project holds an English block, then a Korean block, then the repo URL. Class team projects go under Projects, never Experience. Feed posts are written only when I ask, and never deleted.

## 4. Editor traps

As an analogy, it is moving furniture in a house you don't know. You learn which floorboard gives way by stepping through it once.

In real terms these are **UI automation gotchas**. LinkedIn's edit screens are built for human hands, so under automation some of them do something other than what they show. All 11 lines of the skill's last section are traps like that. The ones with a record come first.

| Trap                                                                                                 | What happened (record)                                          | What the skill does                                                                                     |
| ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| In the About editor (tiptap), clicking a paragraph does not move the caret and overwrites other text | 2026-10-21 the About was overwritten twice                      | Set a DOM Range on the target `<p>` text node, `keyboard.insertText`, read every `<p>` back before Save |
| Adding skills in the Korean UI picks Korean-named entities                                           | 2026-10-11 six Korean-named skills replaced by English entities | Add them in the English UI and click only an exactly matching option                                    |
| Deleting a skill can't be undone                                                                     | 2026-10-11 a skill was deleted before confirmation              | Only recommend a deletion and wait for a clear yes                                                      |
| Removing and re-adding project media can lose it                                                     | 2026-10-25 project images were lost                             | One image at a time, and check the project name after saving                                            |

The rest have no record of when they were hit. Here is what they say.

- Adding an Experience entry overwrites the headline with the job title, so the headline gets re-checked after any position change.
- Projects can't be reordered. Ongoing ones come first, then by end date, newest first.
- The add-image button often needs a second click, and it has to be clicked with the MCP click tool to catch the file chooser. Once, chained steps wrote a media title into the project name.
- Typing a Featured link with `fill()` breaks the preview. Type it one key at a time and wait about 10 seconds.
- Escape in an edit form opens a discard-changes confirm. The education form's notify-your-network switch defaults on and gets turned off before saving.
- LinkedIn's "share this update" prompts are declined, because accepting posts to the feed.

The human-like mouse and typing helper used for Playwright clicks and input lives in the global instructions, not in this skill. A similar pointer and typing effect for screen recordings is in [CH10. demo-recording](/en/blog/side-projects/skills/skills-10-demo-recording/).

## 5. What stays private

As an analogy, some papers never get attached to a résumé.

In real terms these are **disclosure rules**. Every profile is a public page, so the skill lists what can't go on one.

- Student ID number, health and finances go nowhere.
- Vane, the game in progress, gets one neutral line (Unity 2D top-down story adventure, prototype). No story details.
- In vercel-blog PR bodies and commit messages, upstream PRs are never written as `owner/repo#N` or URLs. Repo name in plain text only.

The last rule dates from 2026-10-28. vercel-blog is a public repo, so a PR body that names another repo's PR number shows up on that upstream PR's timeline as "mentioned". That happened on two of this blog's PRs. The same rule is in [CH1. blog-post](/en/blog/side-projects/skills/skills-01-blog-post/), which covers blog posts.

## 7. Wrap-up

`profile-edit` comes down to three things. Edit only the one source. Generate whatever can be generated, and for LinkedIn, which can't be, touch only the gap between target and current.
