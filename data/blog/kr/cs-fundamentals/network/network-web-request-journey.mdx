> 집 노트북([Wi-Fi](glossary:wi-fi))에서 `https://www.example.com/video`를 열 때 [Packet](glossary:ip) 하나가 웹 서버까지 갔다 오는 과정을 0~13단계로 끝까지 따라간다. 끝에 [VPN](glossary:vpn)을 켰을 때와 [SSH](glossary:ssh)로 접속할 때 무엇이 달라지는지 붙였다. 컴퓨터시스템개론 5강(네트워크)을 공부하면서 슬라이드 범위 밖까지 정리한 노트다. 같은 내용을 계층(응용·전송·네트워크·링크·물리)별로 묶은 글은 [계층으로 본 네트워크](/kr/blog/cs-fundamentals/network/network-tcp-ip-layers/)다. 같은 내용을 계층(응용·전송·네트워크·링크·물리)별로 묶은 글은 [계층으로 본 네트워크](/kr/blog/cs-fundamentals/network/network-tcp-ip-layers/)다.

# 전체 그림

택배 상자를 생각하면 쉽다. 보내는 사람은 물건을 상자에 넣고, 그 상자를 더 큰 상자에 넣고, 겉에 송장을 붙인다. 물류센터를 지날 때마다 겉 송장은 "다음 센터"로 새로 붙지만, 안쪽 상자에 적힌 최종 주소는 끝까지 그대로다.

![노트북에서 웹 서버까지 패킷이 가는 과정, 구간마다 바뀌는 헤더](/static/images/network-web-request-journey/packet-journey.svg)

_노트북 → 집 공유기 → [ISP](glossary:isp) [Router](glossary:router) → [Router](glossary:router) B → 웹 서버. 아래 상자는 지금 구간을 지나는 [Frame](glossary:frame)이고, 빨간 글씨가 구간이 바뀔 때 바뀌는 값이다._

비유로 겹겹이 싼 상자는 **[Encapsulation](glossary:encapsulation)**, 겉 송장은 링크 계층 헤더([MAC address](glossary:mac-address)), 안쪽 최종 주소는 IP 헤더의 목적지 IP, 물류센터는 [Router](glossary:router)다.

**그림 읽는 법**

- 위: 노트북 → 집 공유기 → [ISP](glossary:isp) [Router](glossary:router) → [Router](glossary:router) B → 웹 서버. 링크 1~4는 장비 사이 한 구간이다.
- 아래 상자: 지금 구간에서 날아가는 [Frame](glossary:frame). 바깥부터 링크 헤더([MAC](glossary:mac-address)) ⊃ IP 헤더 ⊃ [TCP](glossary:tcp) 헤더 ⊃ [TLS](glossary:tls)로 암호화된 [HTTP](glossary:http) 순서다.
- 빨간 글씨: 구간이 바뀔 때 바뀌는 값. 목적지 IP와 목적지 [Port](glossary:port)는 끝까지 그대로다.

**전체 흐름 한 줄**: 송신 측이 4계층을 내려가며 [캡슐화](/kr/blog/cs-fundamentals/network/network-ch1-2-overview/#캡슐화)하고 → [Router](glossary:router)마다 IP 헤더만 보고 다음 구간으로 넘기고 → 수신 측이 4계층을 올라가며 [Decapsulation](glossary:decapsulation)한다.

**예시 주소** (전부 문서용으로 예약된 주소)

| 장비                            | 주소                                                      |
| ------------------------------- | --------------------------------------------------------- |
| 노트북 (사설)                   | 192.168.1.20                                              |
| 공유기 ([LAN](glossary:lan) 쪽) | 192.168.1.1 ([Default gateway](glossary:default-gateway)) |
| 공유기 (공인)                   | 203.0.113.5                                               |
| 웹 서버                         | 192.0.2.10                                                |

# 0. 준비: 네트워크에 붙고 주소 받기

이사 온 첫날을 떠올리면 된다. 아파트 출입증을 받고(무선 연결), 관리사무소에서 내 호수와 가까운 우체국 위치를 받아야(IP와 게이트웨이) 편지를 보낼 수 있다. 여기서 출입증은 [Wi-Fi](glossary:wi-fi) 결합, 관리사무소는 [DHCP](glossary:dhcp) 서버다.

## Wi-Fi 연결

1. 스캔: [AP](glossary:access-point)가 뿌리는 [beacon](glossary:beacon)에서 [SSID](glossary:ssid)를 찾는다.
2. 인증·결합(association).
3. [WPA2/3 4-way handshake](glossary:wpa2-4-way-handshake)로 무선 구간 암호화 키를 만든다.

여기까지는 노트북 ↔ [AP](glossary:access-point) 연결만 된 상태다. 인터넷에 닿는지는 아직 모른다. [ISP](glossary:isp)와 서버 구간은 따로다.

## 공유기 ↔ ISP

공유기 WAN [Port](glossary:port)는 모뎀이나 [ONT](glossary:ont)(광 단말)를 거쳐 [ISP](glossary:isp) 망에 붙어 있다. [Public IP](glossary:public-ip-address) 203.0.113.5는 [ISP](glossary:isp)가 공유기에 준 주소다.

## DHCP

공유기가 IP를 자동으로 나눠 준다. 4단계라서 앞 글자를 따 **[DORA](glossary:dhcp)**라고 부른다.

1. **Discover**: "IP 줄 사람?" [Broadcast](glossary:broadcast). 아직 내 IP가 없어서 0.0.0.0 → 255.255.255.255, [UDP](glossary:udp) 68 → 67로 보낸다.
2. **Offer**: 공유기가 192.168.1.20을 제안한다.
3. **Request**: "그거 쓸게."
4. **Ack**: 확정.

받는 것: 내 IP, [Subnet mask](glossary:subnet-mask)(/24), **[Default gateway](glossary:default-gateway)**(= 공유기 192.168.1.1), [DNS](glossary:dns) 서버 주소, 임대 시간.

**[Default gateway](glossary:default-gateway)** 는 다른 네트워크로 나가는 출구다. 보통 같은 [LAN](glossary:lan)에 붙은 [Router](glossary:router) 인터페이스의 IP다.

# 1. URL 해석

브라우저가 [URL](glossary:url)을 쪼갠다.

- 스킴 `https` → 기본 [Port](glossary:port) 443
- 호스트 `www.example.com`
- 경로 `/video`

브라우저 캐시에 아직 유효한 응답이 있으면 네트워크에 나가지 않고 여기서 끝난다([Web cache](glossary:web-cache)).

# 2. DNS: 이름 → IP

전화번호부와 같다. 사람은 이름(`www.example.com`)을 알지만 전화를 걸려면 번호(IP)가 필요하다. 동네 안내원([Resolver](glossary:recursive-resolver))에게 물으면 안내원이 본사 → 지역 지사 → 담당 부서 순으로 대신 물어 번호를 알려 준다. 여기서 동네 안내원은 [Recursive DNS resolver](glossary:recursive-resolver), 본사·지사·부서는 루트·[TLD](glossary:tld)·[Authoritative DNS server](glossary:authoritative-dns-server)다.

**캐시부터 확인**: 브라우저 [DNS](glossary:dns) 캐시 → OS [DNS](glossary:dns) 캐시 → `hosts` 파일. 있으면 여기서 끝이다.

없으면 내 기기가 **[Recursive DNS resolver](glossary:recursive-resolver)**([DHCP](glossary:dhcp)로 받은 [DNS](glossary:dns) 서버, 보통 [ISP](glossary:isp)나 공유기)에 묻는다. 질의는 보통 [UDP](glossary:udp) 53이다. 이 [DNS](glossary:dns) 질의 [Packet](glossary:ip)도 아래 3·6~9단계와 똑같이 [ARP](glossary:arp) → 게이트웨이 → [NAT](glossary:nat) → [Router](glossary:router) [Hop](glossary:hop)을 거쳐 갔다 온다.

[Resolver](glossary:recursive-resolver)는 차례로 대신 묻는다. 각 서버는 "다음은 저기 물어봐"만 알려 준다.

1. **[Root DNS server](glossary:root-dns-server)**: `.com` 담당([TLD](glossary:tld) 서버) 위치
2. **[TLD](glossary:tld) [DNS](glossary:dns) 서버**: `example.com` 담당([Authoritative server](glossary:authoritative-dns-server)) 위치
3. **[Authoritative DNS server](glossary:authoritative-dns-server)**: `www.example.com`의 공식 레코드 → [DNS record](glossary:dns-record) 192.0.2.10

[Resolver](glossary:recursive-resolver)는 결과를 레코드 [TTL](glossary:ttl) 동안 캐시한다. 다음에 같은 이름을 묻는 사람은 바로 받는다. 대형 서비스면 [Authoritative server](glossary:authoritative-dns-server)가 가까운 **[CDN](glossary:cdn)** 서버 IP를 줄 수도 있다. 도메인을 사서 [DNS](glossary:dns) 레코드를 직접 거는 쪽 이야기는 [DNS와 Registrar](glossary:domain-registrar)에 있다.

# 3. 같은 네트워크인지 판별 + ARP

편지를 같은 아파트 이웃에게 보내면 직접 문 앞에 두면 되고, 다른 동네로 보내면 우체국에 맡겨야 한다. 우체국에 맡기려면 우체국 창구가 어디인지([MAC](glossary:mac-address)) 알아야 하는데, 그걸 단지 방송으로 묻는 게 [ARP](glossary:arp)다.

## 서브넷 판별

내 IP와 서버 IP를 각각 [Subnet mask](glossary:subnet-mask)와 AND해서 네트워크 주소를 비교한다. 192.168.1.0 ≠ 192.0.2.0 → 다른 네트워크다. 계산 방법은 [임의의 IP가 어느 서브넷 소속인지 찾는 방법](/kr/blog/cs-fundamentals/network/network-ch1-2-overview/#7-임의의-ip가-어느-서브넷-소속인지-찾는-방법)에 있다.

- 같으면: 상대 [MAC](glossary:mac-address)으로 [LAN](glossary:lan) 안에서 바로 보낸다.
- 다르면: [Default gateway](glossary:default-gateway)로 보낸다.

## ARP

게이트웨이 IP(192.168.1.1)는 알지만 [MAC](glossary:mac-address)은 모른다.

1. [ARP](glossary:arp) 캐시를 먼저 확인한다.
2. 없으면 [ARP](glossary:arp) 요청을 [Broadcast](glossary:broadcast)한다: "192.168.1.1 누구야?" (목적지 [MAC](glossary:mac-address) `FF:FF:FF:FF:FF:FF`)
3. 공유기가 자기 [MAC](glossary:mac-address)으로 [ARP](glossary:arp) 응답을 보낸다([Unicast](glossary:unicast)).
4. [ARP](glossary:arp) 캐시에 저장한다. 다음부터는 안 묻는다.

그래서 첫 [Frame](glossary:frame)은 목적지 [MAC](glossary:mac-address) = 공유기, 목적지 IP = 서버다. 둘이 가리키는 대상이 다르다. 왜 주소가 두 개 필요한지는 [IP와 MAC은 상호 보완적이다](/kr/blog/cs-fundamentals/network/network-ch1-2-overview/#ip와-mac은-상호-보완적이다)에 있다.

# 4. TCP 연결 (3-way handshake)

전화를 걸면 "여보세요?" → "네, 들려요. 제 말도 들려요?" → "네" 하고 나서야 본론을 꺼낸다. 이 세 마디가 SYN → SYN+ACK → ACK다.

- 브라우저가 [Socket](glossary:socket)을 만든다. 출발지 [Port](glossary:port)는 OS가 임시로 고르고([ephemeral port](glossary:ephemeral-port), 예: 51000), 목적지 [Port](glossary:port)는 443이다.
- SYN (seq = x, [MSS](glossary:mss) 같은 옵션) → SYN+ACK (seq = y, ack = x+1) → ACK (ack = y+1)
- 선을 잇는 게 아니라 양쪽에 통신 상태(순서 번호 시작값 등)를 만드는 것이다.
- [Segment](glossary:tcp-segment) 3개가 각각 6~9단계를 거쳐 왕복한다. 여기서 1 [RTT](glossary:rtt)를 쓴다.

필드 단위 설명은 [Three-Way Handshake 과정](/kr/blog/cs-fundamentals/network/network-ch1-2-overview/#three-way-handshake-과정)에 있다.

# 5. TLS 설정 (HTTPS니까)

둘만 아는 암호표를 만드는 단계다. 상대가 진짜 그 가게인지 사업자등록증([Digital certificate](glossary:digital-certificate))부터 확인하고, 둘이 숫자를 주고받아 같은 열쇠를 각자 만들어 낸다. 열쇠 자체는 한 번도 오가지 않는다. 여기서 사업자등록증은 서버 [Digital certificate](glossary:digital-certificate), 둘이 각자 만든 열쇠는 [Session key](glossary:session-key)다.

[TLS](glossary:tls) 1.3 기준:

1. **ClientHello**: 쓸 수 있는 암호 방식, 키 교환 값, 접속할 이름([SNI](glossary:sni) = `www.example.com`)
2. **ServerHello**: 고른 방식, 서버 키 교환 값 + **[Digital certificate](glossary:digital-certificate)** + 서명 + Finished
3. 브라우저가 [Digital certificate](glossary:digital-certificate)를 검증한다: [CA](glossary:ca) 서명 체인, [Digital certificate](glossary:digital-certificate) 도메인 = 접속한 도메인인지, 유효기간.
4. Finished → 양쪽이 같은 **[Session key](glossary:session-key)**를 계산한다([ECDHE](glossary:ecdhe) 키 교환, 키 자체는 안 보냄).

이후 [HTTP](glossary:http) 데이터는 [Session key](glossary:session-key)로 암호화한다([Symmetric key](glossary:symmetric-encryption)).

지켜 주는 것은 기밀성(못 읽음), 무결성(바뀌면 앎), 서버 인증이다. 사이트 내용이 진짜인지는 보장하지 않는다. [Phishing](glossary:phishing) 사이트도 [HTTPS](glossary:https)를 쓴다.

# 6. HTTP 요청 + 캡슐화 (송신 측, 위 → 아래)

맨 앞의 택배 상자 비유가 여기서 실제로 일어난다. 계층마다 자기 상자와 송장을 하나씩 더한다.

[HTTP](glossary:http) 요청: `GET /video HTTP/1.1`, `Host: www.example.com`, [Cookie](glossary:cookie), 브라우저 정보 등.

**[Encapsulation](glossary:encapsulation)**: 계층마다 자기 일에 필요한 헤더를 붙여서 위 계층 데이터를 감싼다.

| 계층     | 단위                                | 붙이는 것                                                                     | 이 예에서                                                               |
| -------- | ----------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 응용     | 메시지                              | [HTTP](glossary:http) 요청 → [TLS](glossary:tls) 레코드로 암호화              | `GET /video`                                                            |
| 전송     | [TCP segment](glossary:tcp-segment) | 출발지·목적지 [Port](glossary:port), 순서 번호, ACK 번호, 체크섬              | 51000 → 443                                                             |
| 네트워크 | [IP packet](glossary:ip)            | 출발지·목적지 IP, [TTL](glossary:ttl), 프로토콜 번호([TCP](glossary:tcp) = 6) | 192.168.1.20 → 192.0.2.10, [TTL](glossary:ttl) 64                       |
| 링크     | [Frame](glossary:frame)             | 출발지·목적지 [MAC](glossary:mac-address), 오류 검출([FCS](glossary:fcs))     | 노트북 [MAC](glossary:mac-address) → 공유기 [MAC](glossary:mac-address) |

- **크기 제한**: [Frame](glossary:frame) 하나는 최대 1500 B([MTU](glossary:mtu))다. 그래서 [TCP](glossary:tcp)가 데이터를 [MSS](glossary:mss)(보통 1460 B) 이하로 쪼갠다. 큰 데이터는 [Packet](glossary:ip) 여러 개가 되고, 각자 다른 길로 갈 수도 있다.
- **[Physical layer](glossary:physical-layer)**: [Frame](glossary:frame)의 비트를 신호로 바꿔 내보낸다. [Wi-Fi](glossary:wi-fi)는 전파, 이더넷 구리선은 전기, 광섬유는 빛이다.

# 7. 링크 1: 노트북 → 공유기 (Wi-Fi)

여러 사람이 한 방에서 무전기 하나로 말하는 상황이다. 아무도 말 안 하는지 먼저 듣고, 조용해도 바로 말하지 않고 잠깐 숫자를 센 다음 말한다. 동시에 말을 꺼내 겹치는 걸 줄이려는 것이다. 이 규칙이 [CSMA/CA](glossary:csmaca)다.

무선 채널은 공유 매체라서 **[CSMA/CA](glossary:csmaca)**를 쓴다.

- 채널이 비었는지 듣는다 → 비어도 무작위 [Backoff](glossary:backoff)만큼 기다린다 → 전송 → [AP](glossary:access-point)가 ACK를 보낸다(못 받으면 재전송).
- [Hidden terminal problem](glossary:hidden-terminal-problem)이 있으면 [RTS/CTS](glossary:rtscts)로 먼저 자리를 잡는다.

공유기는 [AP](glossary:access-point) + [Switch](glossary:switch) + [Router](glossary:router) + [DHCP](glossary:dhcp) 서버 + [Firewall](glossary:firewall)을 한 제품에 묶은 것이다.

- [AP](glossary:access-point)가 받은 무선 [Frame](glossary:frame)은 공유기 안에서 [Router](glossary:router) 기능으로 넘어간다(무선 [Frame](glossary:frame) → 이더넷 [Frame](glossary:frame) 변환).
- 유선 PC였다면 [Switch](glossary:switch)가 [MAC address](glossary:mac-address) 테이블을 보고 해당 [Port](glossary:port)로만 넘긴다. 모르는 [MAC](glossary:mac-address)이면 전체 [Port](glossary:port)로 보낸다.

# 8. 공유기: 방화벽 + 라우팅 + NAT

회사 대표번호를 생각하면 된다. 밖에서 보면 전화번호는 하나지만, 교환원이 "내선 20번이 건 전화"를 장부에 적어 두었다가 답 전화가 오면 그 내선으로 돌려 준다. 대표번호는 [Public IP](glossary:public-ip-address), 내선은 [Private IP](glossary:private-ip-address)와 [Port](glossary:port), 교환원의 장부는 [NAT](glossary:nat) 변환표다.

1. [Frame](glossary:frame) [FCS](glossary:fcs)를 확인하고 → [Frame](glossary:frame)을 벗겨서 [IP packet](glossary:ip)을 꺼낸다.
2. [Firewall](glossary:firewall) 규칙을 확인한다(나가는 건 보통 허용).
3. [Routing](glossary:routing): 목적지 192.0.2.10은 집 [LAN](glossary:lan) 밖 → 기본 경로 = [ISP](glossary:isp) 쪽.
4. **[NAT](glossary:nat)**(정확히는 [Port](glossary:port)까지 바꾸는 [NAPT](glossary:napt))
   - (192.168.1.20 : 51000) → (203.0.113.5 : 40001)로 바꾸고 **[NAT](glossary:nat) 변환표**에 기록한다.
   - 집 안 장치 여러 대가 [Public IP](glossary:public-ip-address) 하나를 같이 쓰니까 [Port](glossary:port)로 구분한다.
   - IP·[TCP](glossary:tcp) 체크섬을 다시 계산한다.
5. [TTL](glossary:ttl) 64 → 63.
6. 나가는 링크용 새 [Frame](glossary:frame)을 만든다. 목적지 [MAC](glossary:mac-address) = [ISP](glossary:isp) 쪽 다음 장비(이것도 [ARP](glossary:arp) 등으로 안다).

# 9. 링크 2~: ISP → 인터넷 → 서버 쪽 (라우터 홉마다 반복)

물류센터에 도착한 상자는 겉 송장을 뜯고 안쪽 최종 주소만 본 뒤, "그 지역이면 저 트럭"이라는 배차표를 보고 다음 센터로 가는 새 송장을 붙인다. 배차표는 [Forwarding table](glossary:forwarding-table), 센터 하나를 지나는 것은 [Hop](glossary:hop)이다.

[Router](glossary:router) 하나를 지날 때마다:

1. [Frame](glossary:frame) [FCS](glossary:fcs)를 확인한다. 깨졌으면 버린다(복구는 나중에 [TCP](glossary:tcp) 재전송이 한다).
2. [Frame](glossary:frame)을 벗기고 [IP packet](glossary:ip)을 꺼낸다.
3. 목적지 IP → [Forwarding table](glossary:forwarding-table)에서 가장 길게 맞는 접두사([longest prefix match](glossary:longest-prefix-match))를 찾는다 → 다음 [Router](glossary:router).
4. [TTL](glossary:ttl)을 1 줄인다. 0이 되면 버리고 출발지에 [ICMP](glossary:icmp) Time Exceeded를 보낸다([Packet](glossary:ip)이 빙빙 도는 걸 막는다).
5. 나가는 링크에 맞는 새 [Frame](glossary:frame)을 만든다(목적지 [MAC](glossary:mac-address) = 다음 장비).

**[Routing](glossary:routing) vs [Forwarding](glossary:packet-forwarding)**

- [Routing](glossary:routing): 경로 정보를 정하고 관리하는 일. 결과가 [라우팅 테이블](/kr/blog/cs-fundamentals/network/network-ch1-2-overview/#3-라우팅-테이블)이다.
- [Forwarding](glossary:packet-forwarding): 그 표를 보고 [Packet](glossary:ip)을 다음 장치로 실제로 넘기는 일.
- 표는 [Routing](glossary:routing) 프로토콜이 만든다. [ISP](glossary:isp) 안은 [OSPF](glossary:ospf) 같은 것, [ISP](glossary:isp)끼리는 [BGP](glossary:bgp).

그 밖에:

- 중간 [Router](glossary:router)는 응용 데이터를 안 본다(링크·네트워크 계층까지만). [TLS](glossary:tls)라서 봐도 못 읽는다.
- [ISP](glossary:isp) 사이는 직접 연결, 상위 사업자 경유, [IXP](glossary:ixp)에서 교환 중 하나로 이어진다. 해외면 백본과 해저 케이블을 탄다.
- [Router](glossary:router) 큐가 꽉 차면 [Packet](glossary:ip)을 버린다 → [Congestion](glossary:congestion). 큐에서 기다린 시간이 지연에 더해진다.
- 중간에 [MTU](glossary:mtu)가 더 작은 구간이 있으면 [IP fragmentation](glossary:ip-fragmentation)하거나, [Path MTU](glossary:pmtud)를 찾아서 처음부터 작게 보낸다.
- **[Packet switching](glossary:packet-switching)**: 링크를 여러 사람의 [Packet](glossary:ip)이 나눠 쓴다. 그래서 같은 서버라도 그때그때 지연과 처리량이 다르다.

# 10. 서버 쪽: 도착 + 역캡슐화 + 처리

택배를 받은 쪽은 상자를 바깥부터 하나씩 연다. 겉 송장이 우리 집 맞는지, 그다음 상자의 받는 사람이 나 맞는지, 그다음 어느 방([Port](glossary:port))으로 갈 물건인지 차례로 보고 마지막에 물건을 꺼낸다. 이게 [Decapsulation](glossary:decapsulation)이다.

데이터센터 [Router](glossary:router) → [Firewall](glossary:firewall) → **[Load balancer](glossary:load-balancer)**가 서버 여러 대 중 하나에 넘긴다.

**[Decapsulation](glossary:decapsulation)**: [Frame](glossary:frame) → [IP packet](glossary:ip) → [TCP segment](glossary:tcp-segment) → 응용

- 링크: 목적지 [MAC](glossary:mac-address)이 나인지, [FCS](glossary:fcs)를 확인 → [IP packet](glossary:ip)을 꺼낸다.
- 네트워크: 목적지 IP가 나인지 확인 → 프로토콜 번호를 보고 [TCP](glossary:tcp)로 넘긴다.
- 전송: (출발지 IP·[Port](glossary:port), 목적지 IP·[Port](glossary:port))로 해당 [Socket](glossary:socket)을 찾는다 → 순서를 맞추고 ACK를 보낸다 → 443번 웹 서버 프로그램에 바이트로 준다.
- [TLS](glossary:tls) 복호화 → 응용: [HTTP](glossary:http) 요청을 해석한다.

웹 서버 프로그램이 처리하고(DB 조회 등) [HTTP](glossary:http) 응답을 만든다: `200 OK`, `Content-Type`, 본문(영상 데이터).

# 11. 응답: 같은 길 반대로

답장도 같은 방식으로 포장되어 온다. 다만 돌아오는 트럭 노선은 갈 때와 다를 수 있다.

- 응답도 4~9단계처럼 [Encapsulation](glossary:encapsulation) → [Hop](glossary:hop)을 거쳐 공유기 [Public IP](glossary:public-ip-address) 203.0.113.5 : 40001로 도착한다. 가는 길과 오는 길은 다를 수 있다.
- 공유기가 [NAT](glossary:nat) 변환표를 보고 목적지를 192.168.1.20 : 51000으로 되돌려서 노트북에 전달한다.
- 노트북 [Decapsulation](glossary:decapsulation): [Frame](glossary:frame) → [Packet](glossary:ip) → [TCP](glossary:tcp)
  - 순서를 맞춰 재조립하고, 받은 만큼 ACK를 보내고, 빠진 건 재전송받는다.
  - **[Flow control](glossary:flow-control)**: 받는 쪽 버퍼(수신 창)가 넘치지 않게 보내는 양을 조절한다. 자세히는 [흐름제어](/kr/blog/cs-fundamentals/network/network-ch1-2-overview/#2-흐름제어수신자가-속도를-정한다).
  - **[Congestion control](glossary:congestion-control)**: 손실과 지연을 보고 네트워크가 막힌다 싶으면 보내는 속도를 줄인다. 자세히는 [혼잡제어](/kr/blog/cs-fundamentals/network/network-ch1-2-overview/#3-혼잡제어네트워크가-속도를-정한다).
- [TLS](glossary:tls) 복호화 → 브라우저에 [HTTP](glossary:http) 응답이 올라간다.

# 12. 브라우저: 받은 걸 화면으로

[HTTP 상태 코드](glossary:http-status-code)부터 확인한다: 200 성공, 404 없음, 403 권한 없음, 500 서버 오류.

HTML을 분석하고 → CSS·JavaScript·이미지를 추가로 요청하고 → 렌더링해서 화면에 표시한다.

- 추가 요청은 같은 [TCP](glossary:tcp)·[TLS](glossary:tls) 연결을 재사용한다([keep-alive](glossary:http-keep-alive), [HTTP/2](glossary:http2)는 한 연결에 여러 요청을 동시에). 그래서 1~5단계를 다시 하지 않는다.
- 받은 자원은 [Web cache](glossary:web-cache)에 저장한다.

영상은 **[Streaming](glossary:streaming)**이다. 다 받고 재생하지 않고, 받으면서 재생한다(버퍼에 조금 쌓아 두고).

- **[Adaptive streaming](glossary:adaptive-streaming)**: 1080p/720p/480p 구간을 미리 준비해 두고, 플레이어가 최근 다운로드 속도와 버퍼 양을 보고 다음 구간 화질을 고른다. 느려지면 화질을 낮춰서 안 끊기게 한다.

# 13. 연결 종료

전화를 끊을 때도 "이제 끊을게" → "응" → "나도 끊을게" → "응"으로 양쪽이 각자 끝을 알린다. 이게 FIN과 ACK를 두 번 주고받는 4-way 종료다.

- 한동안 안 쓰거나 탭을 닫으면 [TCP](glossary:tcp)를 종료한다: FIN → ACK, FIN → ACK (4-way). 순서는 [접속해제](/kr/blog/cs-fundamentals/network/network-ch1-2-overview/#3-접속해제).
- 먼저 끊은 쪽은 [TIME_WAIT](glossary:time_wait)로 잠깐 기다린다(늦게 온 [Packet](glossary:ip) 정리).
- 공유기 [NAT](glossary:nat) 변환표 항목도 일정 시간이 지나면 지운다.

# 14. VPN 쓸 때

편지를 봉투째 다른 봉투에 넣어 "대리 발송 사무소"로 보내는 것과 같다. 우체부는 겉봉에 적힌 사무소 주소만 보고, 사무소가 겉봉을 뜯어 안쪽 편지를 진짜 받는 사람에게 다시 부친다. 받는 사람에게는 보낸 곳이 사무소로 보인다. 겉봉은 바깥 IP·[UDP](glossary:udp) 헤더, 사무소는 [VPN](glossary:vpn) 서버, 봉투 안 편지는 암호화된 원래 [Packet](glossary:ip)이다.

![VPN: 터널 안에 원래 패킷을 암호화해서 한 겹 더 감싼 모습](/static/images/network-web-request-journey/vpn-journey.svg)

_노트북 ~ [VPN](glossary:vpn) 서버 사이 보라 띠가 [Tunnel](glossary:tunnel)이다. 회색은 중간 장비가 못 읽는 부분이다._

**그림 읽는 법**

- 위: 노트북 → 공유기 → [ISP](glossary:isp) [Router](glossary:router) → [VPN](glossary:vpn) 서버 → 웹 서버. 노트북 ~ [VPN](glossary:vpn) 서버 사이 보라 띠가 **[Tunnel](glossary:tunnel)**이다.
- 아래 상자: [Tunnel](glossary:tunnel) 구간에서는 바깥 IP·[UDP](glossary:udp) 헤더 안에 **원래 [Packet](glossary:ip) 전체가 암호화돼서** 들어 있다(회색 = 중간 장비가 못 읽는 부분).
- [VPN](glossary:vpn) 서버를 지나면 바깥 껍데기가 사라지고 원래 [Packet](glossary:ip)만 간다.

**[VPN](glossary:vpn)(Virtual Private Network)**: 내 [Packet](glossary:ip)을 통째로 암호화해서 다른 [Packet](glossary:ip) 안에 넣고([Encapsulation](glossary:encapsulation) 한 겹 더) [VPN](glossary:vpn) 서버까지 보내는 것. 이 통로가 **[Tunnel](glossary:tunnel)**이다.

## 연결 준비

- [VPN](glossary:vpn) 클라이언트가 [VPN](glossary:vpn) 서버(198.51.100.7)와 키를 교환한다 → [Virtual network interface](glossary:virtual-network-interface)(`utun`, `tun0`)가 생기고 가상 IP 10.8.0.2를 받는다.
- [Routing table](glossary:routing-table)이 바뀐다: 기본 경로가 [Tunnel](glossary:tunnel)로 간다(**[full tunnel](glossary:full-tunnel)**). 회사 대역만 [Tunnel](glossary:tunnel)로 보내면 **[split tunnel](glossary:split-tunnel)**이다.
- [DNS](glossary:dns)도 [VPN](glossary:vpn) 쪽 [DNS](glossary:dns) 서버로 바뀐다. 안 바뀌면 [DNS](glossary:dns) 질의가 [Tunnel](glossary:tunnel) 밖으로 새는데, 이걸 **[DNS leak](glossary:dns-leak)**이라고 한다.

## 보낼 때

1. 원래 [Packet](glossary:ip): 10.8.0.2 → 192.0.2.10 : 443 (안에 [TLS](glossary:tls)로 암호화된 [HTTP](glossary:http))
2. [Routing table](glossary:routing-table)이 [Tunnel](glossary:tunnel) 인터페이스로 보낸다 → [VPN](glossary:vpn) 클라이언트가 이 [Packet](glossary:ip) 전체를 암호화한다.
3. 바깥에 새 헤더를 붙인다: [UDP](glossary:udp) (→ 51820, [WireGuard](glossary:wireguard) 예) + IP (192.168.1.20 → 198.51.100.7)
4. 그다음은 평소와 같다: [ARP](glossary:arp) → 공유기 → [NAT](glossary:nat)(바깥 출발지만 바뀜) → [ISP](glossary:isp) [Router](glossary:router) [Hop](glossary:hop).

## 누가 무엇을 보나

- **중간 장비**: 바깥 헤더뿐이다. 공유기와 [ISP](glossary:isp)는 "[VPN](glossary:vpn) 서버와 통신 중"까지만 알고, 진짜 목적지(192.0.2.10)와 내용은 못 본다.
- **[VPN](glossary:vpn) 서버**: 바깥 헤더를 벗기고 복호화해서 원래 [Packet](glossary:ip)을 꺼낸다 → [NAT](glossary:nat)로 출발지를 10.8.0.2 → 198.51.100.7로 바꾼다 → 일반 인터넷으로 웹 서버에 보낸다.
- **웹 서버**: 출발지 = [VPN](glossary:vpn) 서버 IP. 내 진짜 IP와 위치는 안 보인다.

## 주의

- [VPN](glossary:vpn) 서버 → 웹 서버 구간에는 [VPN](glossary:vpn) 암호화가 없다. [HTTPS](glossary:https)면 [TLS](glossary:tls)는 여전히 있다([Tunnel](glossary:tunnel) 안에서는 [VPN](glossary:vpn) + [TLS](glossary:tls) 이중 암호화).
- [VPN](glossary:vpn) 회사는 내 목적지를 다 본다. 믿어야 하는 대상이 [ISP](glossary:isp)에서 [VPN](glossary:vpn) 회사로 옮겨 갈 뿐이다.
- 헤더가 늘어서 한 [Packet](glossary:ip)에 실을 데이터가 줄고([MTU](glossary:mtu)), 우회 경로라 지연이 늘어난다.
- 회사 [VPN](glossary:vpn)은 목적이 다르다. [VPN](glossary:vpn) 서버 뒤 사내 사설망(10.x 서버)에 들어가려고 쓴다.

# 15. SSH 접속

원격 컴퓨터 앞에 앉아 있는 것처럼 키보드를 치는데, 그 사이 전화선이 도청당해도 내용이 안 새게 하는 것이다. 처음 걸 때 상대 목소리([SSH host key](glossary:ssh-host-key))를 확인하고, 내가 누군지는 열쇠([Private key](glossary:private-key))로 서명해서 증명한다. 목소리는 서버 [SSH host key](glossary:ssh-host-key)의 [fingerprint](glossary:fingerprint), 열쇠는 내 [Private key](glossary:private-key)다.

![SSH: 연결 단계와 키 입력 한 번이 서버까지 가는 모습](/static/images/network-web-request-journey/ssh-journey.svg)

_위는 노트북([ssh](glossary:ssh)) ↔ 서버(sshd) 메시지 순서, 아래는 키 하나를 누를 때의 [Packet](glossary:ip) 모양이다._

**그림 읽는 법**

- 위 시퀀스: 노트북([ssh](glossary:ssh)) ↔ 서버(sshd) 사이 메시지 순서. 번호 순으로 하나씩 나타난다. ④부터 자물쇠 = 암호화.
- 아래: 연결이 끝난 뒤 키 하나를 누를 때 [Packet](glossary:ip) 모양. 경로와 [Hop](glossary:hop)은 웹 접속과 똑같고 목적지 [Port](glossary:port)만 22다.

**[SSH](glossary:ssh)(Secure Shell)**: 원격 컴퓨터에 암호화해서 접속하고 명령을 실행하는 프로토콜. 기본 [Port](glossary:port) 22.

**[Telnet](glossary:telnet)**: 같은 원격 접속인데 암호화가 없다(23번). 비밀번호와 명령이 평문으로 가서 인터넷 원격 접속에는 부적절하다.

## `ssh user@server.example.com`을 치면

1. [DNS](glossary:dns)로 server.example.com → IP (2단계와 같음)
2. [ARP](glossary:arp)·게이트웨이·[NAT](glossary:nat)·[Hop](glossary:hop) (3, 7~9단계와 같음). 목적지 [Port](glossary:port) 22.
3. [TCP](glossary:tcp) [3-way handshake](glossary:three-way-handshake) (→ 22)
4. **버전 교환**: 양쪽이 `SSH-2.0-OpenSSH_…` 한 줄씩 평문으로 보낸다.
5. **알고리즘 협상**: 키 교환·암호·[MAC](glossary:mac-address) 방식 목록을 주고받고 고른다.
6. **키 교환**: ECDH([curve25519](glossary:curve25519) 등)로 양쪽이 같은 [Session key](glossary:session-key)를 계산한다. 서버는 자기 **[SSH host key](glossary:ssh-host-key)**로 서명해서 보낸다 → 여기부터 전부 암호화.
7. **[SSH host key](glossary:ssh-host-key) 확인**: 노트북이 `~/.ssh/known_hosts`의 [fingerprint](glossary:fingerprint)와 비교한다.
   - 처음이면 "Are you sure you want to continue connecting?"을 묻고, yes면 저장한다.
   - 저장된 것과 다르면 경고한다([Man-in-the-middle attack](glossary:man-in-the-middle-attack) 의심, 서버 재설치 등).
8. **사용자 인증**
   - [Public key](glossary:public-key-authentication) 방식: 서버 `~/.ssh/authorized_keys`에 내 [Public key](glossary:public-key-authentication)가 있고, 노트북이 [Private key](glossary:private-key)로 서명해서 증명한다. [Private key](glossary:private-key)는 밖으로 안 나간다. 실습은 [SSH 키 인증](/kr/blog/cs-fundamentals/cloud-computing/cloud-computing-hw2-kvm-vm-cluster/#2-ssh-키-인증-ch04-extra).
   - 비밀번호 방식: 이미 암호화된 채널 안이라 평문으로 새지 않는다.
9. **채널 열기 + 셸 시작**: 세션 채널 → 가상 터미널([pty](glossary:pty)) → 서버에 로그인 셸이 뜬다.
10. **키 하나 누를 때마다**: 키 입력 → [SSH](glossary:ssh)가 암호화 → [TCP](glossary:tcp) 22 → [Hop](glossary:hop) → 서버 sshd가 복호화 → 셸에 전달 → 화면 출력(입력한 글자 에코 포함)이 다시 암호화돼서 돌아온다.

4~8단계를 서버·클라이언트 쪽 파일 기준으로 본 정리는 [SSH 서버와 클라이언트의 연결 과정](/kr/blog/cs-fundamentals/cloud-computing/cloud-computing-hw3-htcondor-cluster/#ch4-2-ssh-서버와-클라이언트의-연결-과정)에 있다.

## NAT 뒤의 PC에 접속할 때

밖에서 집 공유기 뒤 PC로 [ssh](glossary:ssh) 하려면 공유기에 **[Port forwarding](glossary:port-forwarding)**([Public IP](glossary:public-ip-address):22 → 192.168.1.20:22)이 필요하다. 안에서 밖으로 나가는 연결은 [NAT](glossary:nat) 변환표가 알아서 항목을 만들지만, 밖에서 먼저 들어오는 [Packet](glossary:ip)은 표에 항목이 없어서 버려진다. [Port](glossary:port)를 열지 않고 [Tailscale](glossary:tailscale) 같은 [overlay network](/kr/blog/cs-fundamentals/network/network-ssh-overlay/#3-계층마다-필요한-것) 위에서 [SSH](glossary:ssh)를 하는 방법도 있다.

## SSH 터널

[SSH](glossary:ssh) 연결 안에 다른 [TCP](glossary:tcp) 연결을 실어 보내는 것이다(`ssh -L 8080:localhost:80 서버`). 원리는 [VPN](glossary:vpn)처럼 [Encapsulation](glossary:encapsulation)을 한 겹 더 하는 것이다.
