> 연재 6편, 마지막 글이다. 프로젝트 전체 그림은 [Coffee Shop 0](/kr/blog/coffee-shop/coffee-shop-00-overview/)에 있다. 이 글은 배포 PR 네 개(#108, #109, #125, #127)와 11월 27일 첫 운영 배포를 다룬다.

## 한 줄 요약

배포 스크립트는 태그 하나를 받아 새 폴더에 빌드하고, 헬스 체크가 통과해야만 `current` 링크를 넘긴다. 실패하면 직전 폴더로 링크를 되돌린다. 이 스크립트를 컨테이너에서 리허설해 버그 세 개를 잡은 뒤 운영에 처음 올렸고(29초, health 200), 그다음 CI 통과 뒤 GitHub Actions가 같은 스크립트를 서버에서 돌리는 자동 배포를 붙였다. 자동 배포는 AWS 쪽 설정이 남아서 아직 꺼져 있다.

## 1. 키가 없어도 서버는 뜨게(#108)

배포를 막던 게 하나 있었다. 이 프로젝트 전용 토스 테스트 키가 아직 없었다. 키가 없으면 서버를 못 띄우는 구조면 쇼핑몰 전체가 결제 하나에 묶인다.

그래서 `TOSS_SECRET_KEY`가 비어 있으면 `PAYMENTS_ENABLED`가 거짓이 되게 했다. 결제 시작, 결제 확인, 관리자 취소 승인은 PG와 DB에 닿기 전에 503 `PAYMENTS_DISABLED`로 멈추고, 나머지(목록, 장바구니, 주문, 관리자)는 그대로 돈다. [결제 스위치](/kr/blog/payments/payments-00-basics/#결제-스위치)를 코드 경로가 아니라 키 유무 하나로 정한 셈이다.

반대로 위험한 설정에는 서버가 아예 안 뜨게 했다(`config/checks.py`).

- `DEBUG`가 꺼져 있는데 `ALLOWED_HOSTS`가 비어 있으면 시작 거부
- `TOSS_SECRET_KEY`가 `test_`로 시작하지 않으면 시작 거부. 라이브 키가 잘못 들어가 진짜 돈이 오가는 일을 시작 단계에서 막는다

이 PR에 새 테스트 6개가 붙었고, 6개 모두 바꾸기 전 코드에서 실패하는 걸 확인했다. 백엔드 230개 + 동시성 1개가 통과했다.

## 2. 되돌릴 수 있는 배포 스크립트

이사로 치면, 짐을 옛집에서 빼면서 새집에 넣는 게 아니라 새집을 다 꾸며 놓고 문패만 바꿔 다는 방식이다. 새집이 이상하면 문패를 옛집으로 다시 단다.

![배포 스크립트 다이어그램. /srv/coffee-shop/releases 아래에 태그마다 폴더가 있다. deploy.sh는 새 태그를 새 폴더에 clone하고 main 조상인지 확인, venv와 pip install, 프론트엔드 빌드와 version.txt, 배포 전 DB 백업, migrate를 한 뒤 current 심볼릭 링크를 새 폴더로 바꾼다. 헬스 체크와 version.txt가 맞으면 끝, 아니면 current를 직전 폴더로 되돌린다. DB와 .env는 릴리스 폴더 밖에 있다](/static/images/coffee-shop-06-deploy/release-switch.svg)

새집은 `releases/<태그>/`, 문패는 `current` 심볼릭 링크다. 이 비유는 여기까지만 쓴다.

`deploy/deploy.sh release-YYYYMMDD-N`이 하는 순서다.

1. 태그 형식 확인(틀리면 종료 코드 2), `.env`가 없으면 멈춤
2. 그 태그를 `releases/<태그>/`에 clone하고, 커밋이 `main`의 조상인지 확인(아니면 지우고 멈춤)
3. 백엔드 venv와 `pip install`, 프론트엔드 `npm ci`와 빌드. 빌드 결과에 커밋 해시를 담은 `version.txt`를 넣는다
4. 배포 전 DB 백업, `migrate`
5. `current.new`를 만들고 `mv -T`로 `current`와 바꾼다(링크 교체가 한 번에 일어난다)
6. 헬스 체크(`/api/health/`)와 nginx가 내주는 `version.txt`가 이 커밋인지 확인. 실패하면 `current`를 직전 릴리스로 되돌리고, DB를 되돌려야 하면 배포 전 백업 경로를 알려 준다
7. 릴리스는 최근 3개만 남긴다

DB 파일과 `.env`는 릴리스 폴더 밖(`/srv/coffee-shop/data/`, `/srv/coffee-shop/.env`)에 있어서 링크를 바꿔도 그대로다. 같은 PR에 nginx 설정 틀, 보안 헤더, 쿼리 문자열을 빼고 남기는 로그 형식, Cloudflare 주소 대역에서 온 요청만 `CF-Connecting-IP`를 믿게 하는 스크립트, systemd 유닛(앱, 매일 04:00 백업 타이머), journald 크기 제한, 처음 설치용 `install.sh`가 들어갔다.

## 3. 리허설에서 잡은 것(#125)

#108의 셸 스크립트는 `bash -n`(문법 검사)만 거쳤다. 운영 서버에 처음 돌리기 전에, Ubuntu 24.04 컨테이너에서 `systemctl`만 가짜로 바꿔 [리허설](/kr/blog/devops/devops-00-basics/#리허설)했다.

| 경우                      | 결과                       |
| ------------------------- | -------------------------- |
| 첫 배포                   | 54초, health 200           |
| 헬스 체크가 실패하는 태그 | 직전 릴리스로 되돌림(rc 1) |
| `migrate`가 실패하는 태그 | `current` 그대로(rc 1)     |
| `main`에 없는 태그        | `current` 그대로(rc 1)     |
| 형식이 틀린 태그          | 종료 코드 2                |
| `shellcheck -S warning`   | 경고 0                     |

리허설에서 나온 버그 세 개를 고쳤다.

- **실행 권한.** `deploy/`의 스크립트 네 개가 `100644`로 커밋돼 있었다. 실행 비트를 붙였다.
- **첫 배포 실패 때 자기 자신을 가리키는 링크.** 첫 배포에는 `current`가 없다. 직전 릴리스를 `readlink`로 읽으면 링크 경로 자체가 나와서, 첫 배포가 실패하면 `current`가 자기 자신을 가리키게 됐다. `readlink -e`는 대상이 없으면 빈 값을 돌려준다.
- **gunicorn 제어 소켓.** gunicorn 27은 `$HOME`에 제어 소켓을 연다. 앱 실행 계정은 로그인할 수 없는 시스템 계정이라 홈 폴더가 없다. `control_socket_disable = True`로 껐다.

## 5. 자동 배포(#127)

수동 배포는 운영자가 SSH로 들어가 `deploy.sh`를 치는 일이다. #127 뒤로는 `main`에 머지하는 것이 사람이 하는 유일한 단계가 된다.

![자동 배포 다이어그램. main에 push되면 ci 워크플로가 돌고, 성공하면 deploy 워크플로가 workflow_run으로 시작한다. DEPLOY_ENABLED가 true일 때만 진행한다. 다음 release-YYYYMMDD-N 태그를 고르고, GitHub OIDC로 IAM 역할을 받은 뒤 태그를 push한다. SSM Run Command(AWS-RunShellScript)로 EC2에서 deploy.sh 태그를 돌리고 결과를 출력한다. 마지막으로 Cloudflare를 거쳐 version.txt를 읽어 커밋과 같은지 본다. 22번 포트는 GitHub에 열지 않고, SSM 에이전트가 밖으로 443을 쓴다](/static/images/coffee-shop-06-deploy/cd-flow.svg)

`.github/workflows/deploy.yml`의 규칙은 이렇다.

- **언제 도나.** `ci`가 `main` push에서 성공했을 때(`workflow_run`), 또는 수동 실행. 자동 실행은 그 커밋이 더는 `main` 끝이 아니거나, 이미 릴리스 태그가 있거나(`ci` 재실행), 지난 태그 뒤로 문서만 바뀌었으면 건너뛴다.
- **자격 증명이 먼저, 태그가 나중.** IAM 역할을 못 받으면 태그도 안 남는다.
- **SSH가 아니라 SSM.** GitHub Actions 러너에 22번 포트를 열지 않는다. 서버의 SSM 에이전트가 밖으로 443을 열어 명령을 받아 간다. 역할 권한은 이 레포 `main`에서 온 요청만, 그 인스턴스 하나에 `AWS-RunShellScript`로 `ssm:SendCommand`하는 것과 결과 읽기뿐이다.
- **배포는 한 번에 하나.** `concurrency: deploy-production`, `cancel-in-progress: false`. 배포 중간에 끊기면 안 되니 다음 실행은 기다린다.
- **오래 사는 비밀이 없다.** Actions 시크릿 세 개(역할 ARN, 인스턴스 ID, 운영 URL)는 비밀이 아니라 식별자인데, 공개 레포의 로그에서 가려지게 시크릿에 넣었을 뿐이다.
- **기본은 꺼짐.** 저장소 변수 `DEPLOY_ENABLED`가 `true`일 때만 돈다. AWS 설정 전에 머지해도 아무 일도 안 일어난다.

태그 고르는 셸은 임시 레포에서 다섯 경우로 돌려 봤다. 첫 배포, `ci` 재실행, 문서만 바뀜, `-10` 다음 번호, 이미 태그 있는 커밋의 수동 실행. AWS 쪽은 설정이 끝나야 돈다.
