## 0. 들어가며

> 시리즈 4편. [skill](glossary:skill)이 무엇이고 왜 따로 뺐는지는 [CH0. 스킬 개요](/kr/blog/side-projects/skills/skills-00-overview/)에 있다.

내 공개 프로필은 [GitHub](glossary:github) 프로필 [README](glossary:readme), 이 블로그의 About·Projects, LinkedIn 세 곳에 있다. 셋을 따로 고치면 언젠가 서로 다른 말을 하게 돼서, 고치는 자리를 하나로 모으기로 했다.

식당으로 비유하면 레시피 한 장을 두고 주방이 접시 세 개를 찍어 내는 구조다. 다만 LinkedIn 접시는 주방이 직접 내지 못해서, 이미 나간 접시와 새 접시의 다른 부분만 홀 직원이 손으로 고친다. 레시피는 [single source of truth](glossary:single-source-of-truth), 주방은 [code generation](glossary:code-generation), 이미 나간 접시와 새 접시의 차이는 [desired state](glossary:desired-state)와 current state의 [diff](glossary:diff)다.

그 규칙을 담은 게 `profile-edit` [skill](glossary:skill)이다. 사람은 원본 파일 두 개만 고치고, [README](glossary:readme)와 블로그는 생성하고, LinkedIn은 생성된 목표와 지금 화면의 차이만 브라우저로 손댄다. [skill](glossary:skill) 본문은 42줄, 5,528바이트이고 불릿 28개(규칙 9, LinkedIn 방침 8, 함정 11) 중 11개가 LinkedIn 편집기 함정이다.

## 1. 원본 하나에서 세 곳 생성

![원본 하나에서 프로필 세 곳으로: profile-sync data/ → lib/render.mjs → GitHub README, 블로그, LinkedIn](/static/images/skills-04-profile-edit/pipeline.svg)

_원본 하나에서 프로필 세 곳으로_

원본은 private 레포 profile-sync의 `data/profile.mjs`(소개, 경력, 학력, 자격증, 수상, 오픈소스 기여)와 `data/projects.mjs`(프로젝트 14개)이고, 생성기가 `lib/render.mjs`다. 이 레포는 2026-10-25에 만들었고 2026-11-28 기준 커밋은 22개다.

[skill](glossary:skill)의 첫 규칙이 이걸 못 박는다.

- 고치는 파일은 `data/profile.mjs`와 `data/projects.mjs`뿐이다. [GitHub](glossary:github) [README](glossary:readme), 블로그 `data/authors/*.mdx`, `data/projectsData.ts`는 생성 결과물이다.
- [README](glossary:readme)를 손으로 고치지 않는다. 형식의 원본도 `lib/render.mjs`다.
- 생성 전에 profile-sync, 프로필 [README](glossary:readme) 레포, vercel-blog 세 레포를 전부 `git pull`한다.

마지막 줄에는 기록이 있다. 2026-10-28 뒤처진 `data/`로 생성을 돌려서 다른 세션이 넣은 항목을 지운 일이 있었고, 그날 이 규칙이 생겼다. 생성기는 원본을 그대로 찍기 때문에, 원본이 낡았으면 낡은 내용이 최신 결과물을 덮는다.

생성은 테스트 뒤에 돈다. 절차 문서의 명령은 `npm test`가 통과해야 `scripts/build.mjs`로 넘어가게 돼 있고, 2026-11-28에 돌렸을 때 `test/render.test.mjs` 10개가 전부 통과했다(94 ms). 결과물마다 반영 경로가 다르다. [README](glossary:readme)는 프로필 레포 `main`에 바로 커밋하고, 블로그는 브랜치와 [PR](glossary:pull-request)을 거쳐 [CI](glossary:ci) 통과 뒤 머지한다. 블로그 [PR](glossary:pull-request) 절차는 [CH5. pr-workflow](/kr/blog/side-projects/skills/skills-05-pr-workflow/)가 맡는다.

## 2. 출력마다 싣는 항목 정하기

[skill](glossary:skill)은 출력마다 무엇이 들어가는지 정해 둔다.

| 항목                  | [GitHub](glossary:github) [README](glossary:readme) | 블로그 About·Projects      | LinkedIn                                |
| --------------------- | --------------------------------------------------- | -------------------------- | --------------------------------------- |
| 소개 문단             | 있음                                                | 있음                       | 있음                                    |
| 프로젝트              | 전부                                                | `hidden` 아닌 것만         | `hidden` 아닌 것만                      |
| 오픈소스 기여         | Contributing to 절                                  | About의 Contributing to 절 | Open Source Contributions 프로젝트 하나 |
| 경력·학력·자격증·수상 | 없음                                                | 있음                       | 있음                                    |

2026-11-28 기준 프로젝트 14개 중 `hidden`이 아닌 건 2개다. 그래서 [README](glossary:readme)엔 14개가 다 보이고, 블로그와 LinkedIn엔 2개에 오픈소스 기여 항목을 더한 3개가 보인다. 이 숫자는 2026-11-26에 줄인 결과다. 그날 LinkedIn에서 프로젝트 6개와 보유 기술 20개를 지우고 기술을 4개로 남겼다.

그 밖의 규칙은 내용에 관한 것이다.

- 소개는 세 곳에서 같은 글이다. Stairno Account 문단은 두 번째에 둔다. LinkedIn About이 "더 보기" 전에 보여주는 부분에 들어가게 하려는 배치다. 다른 프로젝트는 소개에 넣지 않는다.
- 목록은 Building을 Shipped보다 먼저 둔다. 출시해서 돌아가는 프로젝트는 업데이트가 남아 있어도 바로 Shipped다. 블로그 `status` 필드와 LinkedIn 종료일도 같은 기준을 쓴다.
- [GitHub](glossary:github) [README](glossary:readme)는 형식을 바꾸지 않는다. stars 배지와 Contributing to 절을 유지한다.
- 갱신은 내가 시킬 때만 한다. 처음엔 매주 월요일 도는 클라우드 루틴이 있었는데, 무엇을 올릴지는 내가 고르기로 하고 2026-10-25에 껐다. 지금은 후보를 표로 모아 보여주고 내가 고른 것만 넣는다.

## 3. LinkedIn은 차이만 수정

![LinkedIn은 live와 target의 차이만 손댄다: live.md와 target.md를 diff해서 Playwright로 편집하고, 끝나면 target을 live로 복사](/static/images/skills-04-profile-edit/linkedin-diff.svg)

_LinkedIn은 live와 target의 차이만 손댄다_

바뀔 곳은 [desired state](glossary:desired-state)(`linkedin/target.md`)와 current state(`linkedin/live.md`)의 [diff](glossary:diff)로 정한다. 생성기는 LinkedIn에 직접 쓰지 않는다. 생성은 `linkedin/target.md`까지만 하고, 지금 화면은 `linkedin/live.md`에 적어 둔다. 반영은 이 순서다.

1. `git diff --no-index linkedin/live.md linkedin/target.md`로 바뀔 칸을 뽑아 보여준다.
2. 반영하라고 하면 [Playwright](glossary:playwright)로 편집한다. 로그인은 내가 직접 한다. 저장 사이에 8초를 둔다.
3. 끝나면 target을 live로 복사해서 커밋한다.

다만 `live.md`가 화면과 늘 같다는 보장은 없다. 나도 LinkedIn을 직접 고치기 때문에 [skill](glossary:skill)은 편집 전에 라이브 페이지를 다시 읽으라고 한다. 클라우드에서 도는 실행은 LinkedIn을 건드리지 않는다.

방침도 몇 줄 있다. 포지셔닝은 백엔드와 AI이고 [React](glossary:react)·[Next.js](glossary:nextjs)를 앞세우지 않는다. 영어가 기본 프로필 언어이고 한국어는 보조인데, 두 언어 모두 번역이 아니라 그 언어로 쓴다. 프로젝트 항목은 언어별 버전이 없어서 한 항목 안에 영어 블록, 한국어 블록, 레포 URL 순서로 쓴다. 수업 팀 프로젝트는 Experience가 아니라 Projects에 둔다. 피드 게시물은 시킬 때만 쓰고, 지우지 않는다.

## 4. 편집기 함정 기록

LinkedIn 편집 화면은 사람 손을 기준으로 만들어져서, [UI automation](glossary:ui-automation)으로 고치면 화면과 실제 동작이 어긋나는 곳이 있다. [skill](glossary:skill)의 마지막 절 11줄이 전부 이런 함정이다. 기록이 남아 있는 것부터 적는다.

| 함정                                                                                            | 겪은 일 (기록)                                                          | [skill](glossary:skill)의 대응                                                                                          |
| ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| About 편집기([tiptap](glossary:tiptap))에서 문단을 클릭해도 캐럿이 안 옮겨지고 다른 글을 덮어씀 | 2026-10-21 About을 두 번 덮어씀                                         | 대상 `<p>`의 text node에 [DOM Range](glossary:dom-range)를 잡고 `keyboard.insertText`, 저장 전에 모든 `<p>`를 다시 읽기 |
| 한국어 화면에서 기술을 추가하면 한국어 이름 [entity](glossary:entity)가 잡힘                    | 2026-10-11 한국어 이름 기술 6개를 영어 [entity](glossary:entity)로 교체 | 영어 화면에서 추가, 이름이 정확히 같은 옵션만 클릭                                                                      |
| 기술 삭제는 되돌릴 수 없음                                                                      | 2026-10-11 확인 전에 기술 하나가 지워짐                                 | 삭제는 추천만 하고 분명한 "응"을 기다림                                                                                 |
| 프로젝트 미디어를 지웠다 다시 넣으면 사라질 수 있음                                             | 2026-10-25 프로젝트 이미지 유실                                         | 이미지는 한 장씩, 저장 뒤 프로젝트 이름까지 확인                                                                        |

나머지 함정은 기록에 언제 겪었는지가 없다. 내용만 옮긴다.

- 경력 항목을 추가하면 헤드라인이 직함으로 바뀐다. 경력을 고친 뒤엔 헤드라인을 다시 본다.
- 프로젝트는 순서를 바꿀 수 없다. 진행 중인 것이 먼저, 그다음 종료일 최신순으로 정렬된다.
- 이미지 추가 버튼은 두 번 눌러야 할 때가 많고, 파일 선택 창을 잡으려면 MCP 클릭 도구로 눌러야 한다. 연속 동작으로 저장했다가 미디어 제목이 프로젝트 이름에 들어간 적이 있다.
- Featured 링크는 URL을 `fill()`로 넣으면 미리보기가 깨진다. 한 글자씩 입력하고 10초쯤 기다린다.
- 편집 폼에서 Escape를 누르면 변경 삭제 확인이 뜬다. 학력 폼의 "인맥에게 알리기" 스위치는 기본이 켜짐이라 저장 전에 끈다.
- "이 업데이트를 공유할까요" 제안은 받지 않는다. 받으면 피드에 게시된다.

[Playwright](glossary:playwright)로 클릭·입력할 때 쓰는 사람 같은 마우스·타이핑 도우미는 이 [skill](glossary:skill)이 아니라 전역 지침에 있다. 비슷한 포인터·타이핑 연출을 화면 녹화에 쓰는 건 [CH10. demo-recording](/kr/blog/side-projects/skills/skills-10-demo-recording/)이다.

## 5. 공개하지 않는 것

프로필은 전부 공개 페이지라서 [skill](glossary:skill)이 못 싣는 걸 정해 둔다.

- 학번, 건강, 재정은 어디에도 싣지 않는다.
- 만들고 있는 게임 Vane은 중립적인 한 줄([Unity](glossary:unity) 2D 탑다운 스토리 어드벤처, 프로토타입)만 쓴다. 이야기 내용은 싣지 않는다.
- vercel-blog [PR](glossary:pull-request) 본문과 커밋 메시지에는 업스트림 [PR](glossary:pull-request)을 `owner/repo#N`이나 URL로 쓰지 않는다. 레포 이름만 평문으로 쓴다.

마지막 규칙은 2026-10-28에 생겼다. vercel-blog는 public 레포라서, [PR](glossary:pull-request) 본문에 다른 레포의 [PR](glossary:pull-request) 번호를 쓰면 그 업스트림 [PR](glossary:pull-request) 타임라인에 "mentioned"로 공개된다. 이 블로그 [PR](glossary:pull-request) 두 개에서 실제로 그렇게 찍혔다. 같은 규칙은 블로그 글을 다루는 [CH1. blog-post](/kr/blog/side-projects/skills/skills-01-blog-post/)에도 있다.

## 6. 메모리에서 스킬로 이전

2026-11-13 커밋 메시지는 이유를 이렇게 적었다. 한 가지 작업에만 필요한 규칙과 함정을 전역 [memory file](glossary:memory-file)에 두지 않고, 그 작업이 나올 때만 읽히게 한다. 프로필을 안 고치는 세션에는 LinkedIn 함정 11줄이 들어갈 자리가 없다. 그 뒤로 [skill](glossary:skill) 파일은 2026-11-28까지 한 번도 바뀌지 않았다. [skill](glossary:skill)과 지침, [memory file](glossary:memory-file)을 어떻게 나눴는지는 [CH0. 스킬 개요](/kr/blog/side-projects/skills/skills-00-overview/)에 있다.
