# 1. Introduction: data link control protocols

**A set of rules that lets two directly connected devices exchange data [frame](glossary:frame) by [frame](glossary:frame), safely and in an orderly way**

## 1. Frame synchronization

**Aligning [frame](glossary:frame) boundaries**

Given data like 010100/101101/001001, cutting it to say "this much is one [frame](glossary:frame)"

## 2. Flow control

**Keeping the sender from sending more data than the receiver can handle**

Because if the sender just blasts data out fast, a [buffer overflow](glossary:buffer-overflow) can occur

## 3. Error control

**Rules for what to do when a [frame](glossary:frame) is damaged**

Raises reliability by detecting errors, getting responses like [ACK](glossary:ack) or [NAK](glossary:nak), and retransmitting when needed. **[ARQ](glossary:arq)**, covered later, belongs here

## 4. Addressing

**Indicating who sent it and who will receive it**

It may look less important on [point-to-point](glossary:point-to-point-link) links, but it matters on links shared by many devices

## 5. Control and data

**Distinguishing control information from actual data**

Because when data is transmitted, the actual data and control information are sent together

Control information: address, sequence numbers, [FCS](glossary:fcs) for error checking, [ACK](glossary:ack) information, etc.

Actual data: the actual data the user sends

## 6. Link management

**Procedures for setting up, maintaining and releasing the link**

Checking that nothing is getting in the way of communication. More of a preparation step than something directly tied to the communication itself.

# 2. Flow Control

**A technique that keeps the sender from sending data beyond the receiver's processing capacity**

### Cause

- [buffer](glossary:buffer): space that temporarily stores received data. The receiver checks whether the [frame](glossary:frame) arrived intact, checks the order, interprets the necessary control information, and then passes it to the upper layer

The sending side can push [frames](glossary:frame) in quickly, but the receiving side has to store them in the [buffer](glossary:buffer), check them and pass them up to the upper layer, so it takes time

And this [buffer](glossary:buffer) is limited.

If the [buffer](glossary:buffer) is full and the sender keeps pushing data in, an [overflow](glossary:buffer-overflow) occurs.

The overflowing data is lost.

### Why split data into frames instead of sending the whole data block?

1. The receiver's [buffer](glossary:buffer) size
2. The cost of errors and [retransmission](glossary:retransmission)
   - The longer the [frame](glossary:frame), the higher the chance that any single bit in it gets corrupted. And since error checking is done per [frame](glossary:frame), if one long [frame](glossary:frame) is corrupted, that entire long [frame](glossary:frame) has to be resent. Conversely, if it's split into several small [frames](glossary:frame), only the [frames](glossary:frame) with errors need to be resent.
3. Fairness on a shared medium
   - When several devices share the same medium, if one device keeps holding on and sending a huge data block, the other devices have to wait. So it's better to cut it into small [frames](glossary:frame) so that one station can't occupy the medium too long. That way the other senders also get transmission opportunities in between.

## 1. Stop-and-Wait Flow Control

**Send one [frame](glossary:frame) and wait until the [ACK](glossary:ack) arrives**

- Drawback
  - After sending one [frame](glossary:frame), the link can sit idle until the [ACK](glossary:ack) comes back. Especially when the distance is long and the [propagation delay](glossary:propagation-delay) is large, the waiting time can exceed the actual data transmission time. That's where the [link utilization](glossary:link-utilization) problem comes from.

![link utilization](/static/images/network-ch7-data-link/stop-and-wait-flow-control.png)

- T: sender
- R: receiver
- a: [propagation delay](glossary:propagation-delay)
- 1: [Transmission time](glossary:transmission-delay)
- Blue bar: [Frame](glossary:frame)
- Gray bar: [ACK](glossary:ack)

* In [Stop-and-Wait](glossary:stop-and-wait-arq) [Flow Control](glossary:flow-control), total time = t0 (reference time) + 1 ([Transmission time](glossary:transmission-delay)) + 2a ([propagation delay](glossary:propagation-delay)).

* So [link utilization](glossary:link-utilization) drops.
* a = propagation time / transmission time
* U = 1 / (1 + 2a)
  - The smaller a, the better, because utilization goes up as it gets smaller
* If a is less than 1, efficiency is good; if it's greater than 1, efficiency is poor

## 2. Sliding Windows Flow Control

**Lets multiple [frames](glossary:frame) be sent in a row even while waiting for [ACKs](glossary:ack)**

- The receiver has a [buffer](glossary:buffer) that can store up to about W [frames](glossary:frame)
- The sender can send up to W [frames](glossary:frame) in a row even before receiving an [ACK](glossary:ack)
  - W: the size of the receiver's [buffer](glossary:buffer). Up to W [frames](glossary:frame) of data can be sent without an [ACK](glossary:ack)
- The [ACK](glossary:ack) carries the number of the [frame](glossary:frame) it wants next
- The field for the [frame](glossary:frame) number is limited to k bits
  - With k bits there are 2^k possible numbers. (ex: k=3, possible [frame](glossary:frame) numbers: 0,1,2,3,4,5,6,7,0,1,2,3,4,5,6,7...)
- The window size is limited to 2^k-1.
  - There are two windows: the send window and the receive window
  - If the window were 2^k or more, [frame](glossary:frame) numbers of the previous and next windows would overlap, so when an [ACK](glossary:ack) is lost, a retransmitted [frame](glossary:frame) couldn't be told apart from a new [frame](glossary:frame)
- When its [buffer](glossary:buffer) is nearly full or it needs processing time, the receiver can acknowledge what has been sent so far but ask the sender not to send any more data.
  - Once ready, it has to respond asking for data to continue.
- If the link supports [full-duplex](glossary:full-duplex), [ACK](glossary:ack) information can be carried inside the data [frame](glossary:frame) sent to the other side. This is called a [piggyback](glossary:piggybacking) [ACK](glossary:ack).

### Sliding Window operation example

A [sliding window](glossary:sliding-window) flow that works normally without errors.

- **A** = sender (TX), **B** = receiver (RX)
- [Frame](glossary:frame) numbers: cycle 0~7 (k=3, modulo 8)
- Window size: 7 (blue cells = current window)

![sliding Windows Flow Control](/static/images/network-ch7-data-link/sliding-window-flow-control.png)

#### ① Initial state

```
A: [0 1 2 3 4 5 6] 7 ...   ← can send 0~6
B: [0 1 2 3 4 5 6] 7 ...   ← can receive 0~6
```

#### ② A sends F0, F1, F2

Three were sent, so the window's **trailing edge (back) shrinks**. Sent [frames](glossary:frame) are kept in the [buffer](glossary:buffer) until the [ACK](glossary:ack) arrives.

```
A: 0 1 2 [3 4 5 6] ...   ← window shrinks to 3~6
```

#### ③ B receives F0, F1, F2 and sends RR3

The window shrinks by the amount received, and the **leading edge (front) expands** as the [ACK](glossary:ack) is sent.
RR3 = "got 0,1,2 fine, expecting 3 next" (cumulative acknowledgment)

```
B: 0 1 2 [3 4 5 6 7 0 1] ...
        → sends RR3 to A
```

#### ④ A receives RR3

[ACK](glossary:ack) arrives → A's window **expands forward** and fills 7 slots again.

```
A: 0 1 2 [3 4 5 6 7 0 1] ...
```

#### ⑤ A sends F3~F6 → B receives → RR reply (repeat)

```
final A: 0 1 2 3 4 5 6 [7 0 1 2] ...
final B: 0 1 2 3 4 5 6 [7 0 1 2] ...
```

# 4. ARQ(Automatic Repeat Request)

**An error control method that ensures reliability by automatically retransmitting a [frame](glossary:frame) when an error occurs or an [ACK](glossary:ack) doesn't arrive**

The purpose of [ARQ](glossary:arq) is to make an unreliable data link look like a reliable data link.  
That is, errors don't disappear from the link itself; when an error occurs it is detected and the [frame](glossary:frame) is resent, so delivery ends up correct.

## 1. Stop-and-Wait ARQ

### Case 1. Normal operation

1. The sender sends one [frame](glossary:frame) and waits until the [ACK](glossary:ack) arrives.
2. When the [ACK](glossary:ack) arrives normally, it sends the next [frame](glossary:frame).

### Case 2. The received frame is a damaged frame

1. If the [frame](glossary:frame) the receiver got is a [damaged frame](glossary:damaged-frame), the receiver discards it.
2. Then the sender doesn't receive an [ACK](glossary:ack).
3. The sender doesn't wait forever; it sets a [timeout](glossary:timeout).
4. If no [ACK](glossary:ack) arrives within the [timeout](glossary:timeout), it assumes "something went wrong" and sends the same [frame](glossary:frame) again.

### Case 3. The frame arrived fine but the ACK was damaged or lost

1. The [frame](glossary:frame) arrived fine, but the [ACK](glossary:ack) was damaged or disappeared.
2. Then, from the sender's point of view, it can't recognize an [ACK](glossary:ack), so it sends the same [frame](glossary:frame) again after the [timeout](glossary:timeout).
3. The problem is that the receiver has already received that [frame](glossary:frame) once. A duplication problem, with the same [frame](glossary:frame) arriving twice, should occur, so why doesn't it?
   - It doesn't, because [frames](glossary:frame) are numbered with [alternate numbering](glossary:alternate-numbering)

```
Example
The sender sent Frame 0, and the receiver received it fine and sent an ACK.
But the ACK got corrupted on the way.
The sender didn't get the ACK, so it resends Frame 0 after the timeout.
The receiver looks at the frame's number, decides "ah, this is frame 0, which I already received", and instead of passing the data up to the upper layer again, it just resends the ACK.
```

### Stop-and-Wait ARQ operation example

The flow for recovering when a [frame](glossary:frame)/[ACK](glossary:ack) is lost.

- **A** = sender, **B** = receiver
- Time flows top → bottom
- [ACK](glossary:ack) numbers are used **[alternating](glossary:alternate-numbering) between 0/1**

#### Meaning of ACK numbers

| [ACK](glossary:ack) | Meaning                             |
| ------------------- | ----------------------------------- |
| **ACK1**            | "expecting 1 next" = **got 0 fine** |
| **ACK0**            | "expecting 0 next" = **got 1 fine** |

![stop-and-wait ARQ](/static/images/network-ch7-data-link/stop-and-wait-arq.png)

#### Step-by-step flow

##### ① Normal operation

```
A --- frame 0 ---> B    (frame transmission time + propagation time)
A <--- ACK1 ------ B    (got 0, expecting 1 next)
A --- frame 1 ---> B
A <--- ACK0 ------ B    (got 1, expecting 0 next)
```

One [frame](glossary:frame) → receive [ACK](glossary:ack) → next [frame](glossary:frame). The basic stop-and-wait operation.

##### ② Frame loss

```
A --- frame 0 --✕       (lost on the way)
   ⋮ Time-out interval   (A doesn't receive an ACK)
   "Frame 0 lost; A retransmits"
A --- frame 0 ---> B     (retransmitted after timeout)
A <--- ACK1 ------ B
```

If the [ACK](glossary:ack) doesn't arrive, A **waits until the [timeout](glossary:timeout) and [retransmits](glossary:retransmission) the same [frame](glossary:frame)**.
It doesn't detect [frame](glossary:frame) loss directly; it infers it indirectly from "the [ACK](glossary:ack) isn't coming".

##### ③ ACK loss (key point)

```
A --- frame 1 ---> B     (B receives it fine)
A      ✕--- ACK0 -- B    (ACK0 is lost on the way)
   ⋮ Time-out interval
   "ACK0 lost; A retransmits"
A --- frame 1 ---> B     (A retransmits frame 1)
                   B     "B discards duplicate frame" → retransmits ACK0
```

If the [ACK](glossary:ack) disappears, A thinks it failed and sends [frame](glossary:frame) 1 **again** → from B's point of view it's a **duplicate**.
B looks at the number, thinks "this is the 1 I got earlier", and **discards** it.

---

#### Key summary

1. **Loss is detected only through [timeout](glossary:timeout)**
   - Whether the [frame](glossary:frame) dies or the [ACK](glossary:ack) dies, to A it's the same: "the [ACK](glossary:ack) isn't coming"
   - → once the [timeout](glossary:timeout) passes, it always [retransmits](glossary:retransmission)

2. **[ACK](glossary:ack) loss creates duplicate [frames](glossary:frame)**
   - This is solved with **[alternating](glossary:alternate-numbering) ACK0 / ACK1 numbers**
   - The receiver uses the number to tell "new [frame](glossary:frame) vs retransmitted duplicate" → duplicates are discarded

> One-line summary: both [frame](glossary:frame) loss and [ACK](glossary:ack) loss are recovered through [timeout](glossary:timeout), and the duplicates created by [ACK](glossary:ack) loss are filtered out with the 0/1 numbers.

## 2. Go-Back-N ARQ

**A [Sliding Window](glossary:sliding-window)-based [ARQ](glossary:arq). Multiple [frames](glossary:frame) are sent in a row, and when an error occurs, the erroneous [frame](glossary:frame) and all [frames](glossary:frame) after it are retransmitted**

- The most commonly used.
- More efficient than [Stop-and-Wait ARQ](glossary:stop-and-wait-arq).
  - Because multiple [frames](glossary:frame) can be sent even while waiting for an [ACK](glossary:ack).
- The receiver sends [RR](glossary:rr) ([Receive Ready](glossary:rr)) for [frames](glossary:frame) received correctly.
  - [RR](glossary:rr) n: means it expects [frame](glossary:frame) n.
- When the receiver finds an erroneous [frame](glossary:frame), it sends [REJ](glossary:rej) ([Reject](glossary:rej)).
  - [REJ](glossary:rej) n: means resend starting from [frame](glossary:frame) n.
- [Frames](glossary:frame) arriving after the erroneous [frame](glossary:frame) are discarded.
  - Because the order is broken.
- The sender [retransmits](glossary:retransmission) the erroneous [frame](glossary:frame) and the [frames](glossary:frame) after it.

```
Example:
The sender sent Frames 0,1,2,3,4,5.
The receiver received 0,1,2 fine but found an error in 3.
The receiver sends REJ 3.
4 and 5, which arrive afterwards, are discarded.
The sender resends starting from Frame 3.
```

![Sliding-Window-ARQ](/static/images/network-ch7-data-link/sliding-window-arq.png)

## 3. Selective-Reject ARQ

**An [ARQ](glossary:arq) method that selectively [retransmits](glossary:retransmission) only the erroneous [frame](glossary:frame)**

- Unlike [Go-Back-N](glossary:go-back-n-arq), correct [frames](glossary:frame) arriving after the erroneous [frame](glossary:frame) are not discarded but stored in the [buffer](glossary:buffer).
- The sender [retransmits](glossary:retransmission) only the erroneous [frame](glossary:frame).
- Less [retransmission](glossary:retransmission) waste.
- The receiver must store [out-of-order frames](glossary:out-of-order-frame), so it needs enough [buffer](glossary:buffer).
- The sender has to resend only specific [frames](glossary:frame), so the logic is more complex.
- Useful on [satellite links](glossary:satellite-communication) with long [propagation delay](glossary:propagation-delay).

```
Example:
If Frame 4 has an error and Frames 5,6 arrive fine,
Go-Back-N discards 5,6 and receives again from 4.
Selective-Reject stores 5,6 in the buffer and receives only 4 again.
```

# 5. HDLC(High Level Data Link Control)

**"A bit-oriented standard protocol that implements all the data link layer requirements (framing, flow, error, addressing), and the prototype of later protocols**

Station/link are the premises that define "in what environment, and who to whom" [HDLC](glossary:hdlc) operates

## 1. Station: a device (node) participating in communication

Classified by: who has control in this communication.

- [Primary](glossary:primary-station): the side that leads the communication
- [Secondary](glossary:secondary-station): the side that responds as the [Primary](glossary:primary-station) directs
- [Combined](glossary:combined-station): both leads and responds (peers)

## 2. Link: the connection (line) joining those stations

[Unbalanced](glossary:unbalanced-configuration): 1 [primary](glossary:primary-station) + several secondaries (a master-slave structure where one directs many)

[Balanced](glossary:balanced-configuration): 2 combined stations (the two as equals)

## 3. HDLC frame structure

```
frame format

| Flag | Address | Control | Information | FCS | Flag |
   8      8/16     8/16      variable     16/32   8     (bit)
```

- Flag: always 01111110, a boundary marker signaling the start and end of a [frame](glossary:frame)
- Address: identifies the receiving/sending [secondary](glossary:secondary-station)
- Control: holds control information (differs for I [frame](glossary:frame), S [frame](glossary:frame), U [frame](glossary:frame))
- Information: the actual data
- [FCS](glossary:fcs): error detection code

**[I-frame](glossary:i-frame), [S-frame](glossary:s-frame) and [U-frame](glossary:u-frame) are the types of [HDLC](glossary:hdlc) [frames](glossary:frame) as a whole**

Which [frame](glossary:frame) it is can be determined by looking at the control field

## 4. HDLC-2

- N(S): send sequence number (the number of the [frame](glossary:frame) I'm sending)
- N(R): receive sequence number (the number expected next = cumulative [ACK](glossary:ack))
- P/F: Poll/Final bit (requests a response / marks the last one)
- The type is determined by the first bit(s) — 0 means I, 10 means S, 11 means U

### Bit Stuffing

Problem: the Flag is 01111110 (six 1s), so if six 1s happen to appear in a row in the data, the receiver mistakes it for "oh, the [frame](glossary:frame) ended?"

Solution: whenever five consecutive 1s appear in the data, the sender always forcibly inserts a 0

### Address field

- Identifies the [secondary](glossary:secondary-station) station
- Usually 8 bits; if that's not enough, it can be extended in multiples of 7 bits
- When extended, the leftmost bit of each octet indicates "is this the last octet" — 1 means last, 0 means more follow
- 11111111 is the [broadcast](glossary:broadcast-address) address — used when the [primary](glossary:primary-station) sends to all secondaries at once

### FCS(Frame Check Sequence)

- An error detection code computed over all bits except the Flags
- The default is 16-bit [CRC-CCITT](glossary:crc)
- If [frames](glossary:frame) are long or the line is unstable, there is a 32-bit [CRC-32](glossary:crc) option
