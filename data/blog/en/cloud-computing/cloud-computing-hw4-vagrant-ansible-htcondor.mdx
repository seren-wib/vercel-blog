## Automation Flow

The work I did by hand in Chapter 5 is split between two tools. Vagrant creates the three VMs from one Vagrantfile (provisioning) and sets up hostnames, IPs and SSH keys. Ansible installs HTCondor on those three VMs and deploys the per-role configuration files from one playbook (`htcondor.yaml`). Both handle the VMs over SSH from the Ubuntu host.

| Step                | Tool                      | Input files                                     | Result                                                                       |
| ------------------- | ------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------- |
| 1. VM provisioning  | Vagrant + vagrant-libvirt | `~/vrepo/Vagrantfile`                           | main, work1, work2 created, hostnames, 192.168.56.101–103, per-node SSH keys |
| 2. VM configuration | Ansible                   | `/etc/ansible/hosts`, `~/Ansible/htcondor.yaml` | SELinux, firewall, hosts, packages, HTCondor config, service restart         |

## SSH Access Layout

The assignment requires every step to be done by connecting to the VMs over SSH, so I wrote down the access paths. There are three layers.

- **Mac → Ubuntu host**: SSH key login, same as HW3.
- **Ubuntu host → VMs**: I used `vagrant ssh <node>`. It runs ssh with the per-node private key that `vagrant up` created and the management IP; `vagrant ssh-config` (shown later) prints that configuration. The `[vagrant@main ~]$` prompt in the screenshots is this connection.
- **Ansible**: Ansible also works over SSH. It connects to each node with `ansible_user=vagrant` and `ansible_ssh_private_key_file` from the inventory and runs modules there.

Apart from one look through `virsh console` while diagnosing problem 4, I didn't use the VM consoles.

### Problem 1. No arm64 Vagrant in the Repository

`apt install vagrant` tried to fetch `vagrant:amd64` and failed with `package architecture (amd64) does not match system (arm64)`.

![apt install failure](/static/images/cloud-computing-hw4-vagrant-ansible-htcondor/03.webp)

_apt only offers the amd64 package, so the install fails on an arm64 system_

Looking into it, the repository's package index only has vagrant for amd64 and i686, and releases.hashicorp.com only has a linux_amd64 zip. Ubuntu's own archive last shipped vagrant in 23.10 (mantic); 24.04 (noble) doesn't have it at all. HashiCorp does, however, publish the same version on RubyGems. That works because Vagrant is written in Ruby.

### Installing from RubyGems

I installed Ruby and build tools, then installed vagrant as a gem. `libarchive-tools` provides bsdtar, which vagrant uses to unpack boxes, and `libvirt-dev` is needed to compile the plugin in the next step. Since this isn't an official install path, it warns "outside of the official installers", but it works fine. The installed version is 2.4.9, same as the slides.

```bash
sudo rm /etc/apt/sources.list.d/hashicorp.list && sudo apt clean
sudo apt install -y ruby-full ruby-dev build-essential libarchive-dev libarchive-tools zlib1g-dev libssl-dev pkg-config libvirt-dev
ruby --version; gem --version; bsdtar --version
sudo gem install vagrant --no-document
vagrant --version
```

## Adding pci=nomsi to the Box Image

As I found in HW2, in this nested virtualization setup the Rocky guest kernel hangs during boot without `pci=nomsi`, because it can't receive virtio interrupts. So I wrote a script that attaches the box image with `qemu-nbd` and appends the argument to the `options` line of the boot entries (`/boot/loader/entries/*.conf`). It only needs to run once before the first `vagrant up`; every VM disk created afterwards uses this image as its backing file.

```bash:box-nomsi.sh
#!/bin/bash
# box-nomsi.sh <box.img>
# Add "pci=nomsi" to the kernel command line inside a qcow2 box image (offline, via qemu-nbd).
set -e
IMG="$1"; [ -f "$IMG" ] || { echo "usage: $0 <box.img>"; exit 1; }
sudo modprobe nbd max_part=16
sudo qemu-nbd --disconnect /dev/nbd0 >/dev/null 2>&1 || true
sudo qemu-nbd --connect=/dev/nbd0 "$IMG"
sleep 2; sudo partprobe /dev/nbd0 2>/dev/null || true; sleep 1
lsblk -o NAME,SIZE,FSTYPE,LABEL /dev/nbd0
M=$(mktemp -d)
cleanup() { sudo umount "$M/boot" 2>/dev/null; sudo umount "$M" 2>/dev/null; rmdir "$M" 2>/dev/null; sudo qemu-nbd --disconnect /dev/nbd0 >/dev/null 2>&1; }
trap cleanup EXIT
ROOT=""; BOOT=""
for p in /dev/nbd0p*; do
  fs=$(lsblk -no FSTYPE "$p"); [ -z "$fs" ] && continue
  [ "$fs" = vfat ] && continue
  sudo mount -o ro "$p" "$M"
  if [ -d "$M/etc" ] && [ -d "$M/boot" ]; then ROOT="$p"; fi
  if [ -d "$M/loader/entries" ]; then BOOT="$p"; fi
  sudo umount "$M"
done
echo "root=$ROOT boot=$BOOT"
sudo mount "$ROOT" "$M"
[ -n "$BOOT" ] && sudo mount "$BOOT" "$M/boot"
# /boot/loader/entries is root-only (0700): expand the glob inside sudo
show() { sudo bash -c "grep -h '^options' '$M'/boot/loader/entries/*.conf; cat '$M/etc/kernel/cmdline' 2>/dev/null; grep '^GRUB_CMDLINE_LINUX=' '$M/etc/default/grub'; true"; }
echo "--- before"; show
sudo bash -c "sed -i '/^options/{/pci=nomsi/!s/\$/ pci=nomsi/}' '$M'/boot/loader/entries/*.conf"
sudo bash -c "[ -f '$M/etc/kernel/cmdline' ] && sed -i '/pci=nomsi/!s/\$/ pci=nomsi/' '$M/etc/kernel/cmdline' || true"
sudo sed -i '/^GRUB_CMDLINE_LINUX=/{/pci=nomsi/!s/"$/ pci=nomsi"/}' "$M/etc/default/grub" 2>/dev/null || true
echo "--- after"; show
sync; cleanup; trap - EXIT
echo "done: pci=nomsi added to $IMG"
```

```bash
~/bin/box-nomsi.sh ~/.vagrant.d/boxes/rockylinux-VAGRANTSLASH-10/0/arm64/libvirt/box.img
```

## Writing the Vagrantfile

I kept the structure from slide 18 (`NODE_COUNT`, the main definition, a `times` loop defining work1 and work2) and only replaced the VirtualBox-specific parts with libvirt ones.

- **Box and provider**: `config.vm.box = "rockylinux/10"`, provider `"libvirt"`. `cpus` and `memory` instead of `modifyvm`, and `title` for the VM name.
- **Options that fix problems**: `storage_pool_name = "images"` fixes the conflict with the existing pool (problem 2), and `machine_virtual_size = 10` corrects the box metadata error (problem 4).
- **aarch64 UEFI boot**: `machine_type`/`machine_arch`, the AAVMF `loader` without secure boot, and per-node `nvram`. The VirtualBox defaults, cirrus video and a PS/2 mouse, don't work on aarch64, so `graphics_type = "none"` plus a virtio keyboard.
- **Network**: `private_network` reuses the 192.168.56.0/24 network from Chapter 4 via `libvirt__network_name: "cloud56"`. I SSH directly to the management IP, so I removed `forwarded_port`, and I disabled the rsync shared folder built into the box since I don't use it.
- **Typo**: the slide's last line `End` is a Ruby syntax error, so I wrote `end`.

```ruby:Vagrantfile
NODE_COUNT=2

Vagrant.configure("2") do |config|
  config.vm.box = "rockylinux/10"
  config.vm.synced_folder ".", "/vagrant", disabled: true

  config.vm.provider "libvirt" do |v|
    v.storage_pool_name = "images"
    v.machine_virtual_size = 10
    v.machine_type = "virt"
    v.machine_arch = "aarch64"
    v.cpu_mode = "host-passthrough"
    v.loader = "/usr/share/AAVMF/AAVMF_CODE.no-secboot.fd"
    v.graphics_type = "none"
    v.input type: "keyboard", bus: "virtio"
    v.cpus = 1
    v.memory = 1024
  end

  config.vm.define "main" do |main|
    main.vm.hostname = "main.cloud.org"
    main.vm.network "private_network", ip: "192.168.56.101", libvirt__network_name: "cloud56"
    main.vm.provider "libvirt" do |v|
      v.title = "Main(vagrant)"
      v.nvram = "/var/lib/libvirt/qemu/nvram/vrepo_main_VARS.fd"
    end
  end

  NODE_COUNT.times do |i|
    node_id = "work#{i+1}"
    ip_address = "192.168.56.10#{i+2}"
    config.vm.define node_id do |node|
      node.vm.hostname = "#{node_id}.cloud.org"
      node.vm.network "private_network", ip: ip_address, libvirt__network_name: "cloud56"
      node.vm.provider "libvirt" do |v|
        v.title = "Work#{i+1}(vagrant)"
        v.nvram = "/var/lib/libvirt/qemu/nvram/vrepo_#{node_id}_VARS.fd"
      end
    end
  end
end
```

## vagrant up

### Problem 4. All Three VMs Drop to the dracut Emergency Shell

On the first `vagrant up`, all three VMs got stuck at `Waiting for domain to get an IP address...`. The kernel was running (CPU idle) but there were no DHCP requests, so I went in with `virsh console` and found an `sh-5.2#` emergency shell. `/run/initramfs/rdsosreport.txt` showed a timeout waiting for the root UUID device and `Could not boot.`, and `blkid` showed only `/dev/vda: PTTYPE="PMBR"`, with no partitions at all.

![dracut emergency shell](/static/images/cloud-computing-hw4-vagrant-ansible-htcondor/13.webp)

_Console of the 1st up: dracut timeout, no partitions in blkid_

The cause was the box metadata. The box's `metadata.json` says `virtual_size: 5` (GB), but the actual `box.img` is 10 GiB. vagrant-libvirt created a 5 GiB VM disk from the metadata value, and the kernel dropped the GPT partitions that ran past the end of the disk, so it couldn't find the root filesystem. It's a bug on the Rocky box side, so I added `machine_virtual_size = 10` to the Vagrantfile and brought the VMs up again.

```bash
vagrant up                      # 1st: emergency shell
virsh -c qemu:///system console vrepo_main
vagrant destroy -f
grep -n machine_virtual_size Vagrantfile
vagrant up                      # 2nd: success
```

![destroy and disk size fix](/static/images/cloud-computing-hw4-vagrant-ansible-htcondor/14.webp)

_vagrant destroy -f and adding the disk size option_

With 10 GiB disks, all three VMs booted in about 40 seconds. You can see it replacing the per-node SSH keys and setting up hostnames and networking, as on slide 19.

![2nd vagrant up](/static/images/cloud-computing-hw4-vagrant-ansible-htcondor/15.webp)

_2nd vagrant up: per-node SSH key replacement, "Machine booted and ready!", hostname and network setup_

## Writing the Playbook

I copied the three plays from slides 34–38 (common install on cluster, main setup, worker setup) and changed only two things. `NETWORK_INTERFACE` is now `enp4s0`, this environment's cluster interface, and I added a task that turns off firewalld to the cluster play (it's the fix for problem 5, so it wasn't there on the first run). Indentation is two spaces, no tabs.

```yaml:htcondor.yaml
---
- name: HTCondor Installation
  hosts: cluster
  become: yes
  become_user: root

  tasks:
    - name: Disable SELinux
      ansible.posix.selinux:
        state: permissive
        policy: targeted

    - name: Stop and disable firewalld
      ansible.builtin.service:
        name: firewalld
        state: stopped
        enabled: no

    - name: Modify /etc/hosts file
      ansible.builtin.blockinfile:
        path: /etc/hosts
        block: |
          192.168.56.101 main.cloud.org     main
          192.168.56.102 work1.cloud.org    work1
          192.168.56.103 work2.cloud.org    work2

    - name: Ensure OpenSSH fully update
      ansible.builtin.dnf:
        name:
          - openssh-server
          - openssh-clients
          - openssl
          - openssl-libs
        state: latest

    - name: Install wget package
      ansible.builtin.dnf:
        name: wget
        state: present

    - name: Install EPEL
      ansible.builtin.dnf:
        name: epel-release
        state: present

    - name: Install HTCondor Repository for EL10
      ansible.builtin.dnf:
        name: https://research.cs.wisc.edu/htcondor/repo/25.0/htcondor-release-current.el10.noarch.rpm
        state: present
        disable_gpg_check: yes

    - name: Install condor
      ansible.builtin.dnf:
        name: condor
        state: present

- name: HTCondor Main Node Setup
  hosts: main
  become: yes
  become_user: root

  tasks:
    - name: Remove old configuration file
      ansible.builtin.file:
        path: /etc/condor/config.d/condor_config.local
        state: absent

    - name: Creating a configuration file
      ansible.builtin.copy:
        dest: /etc/condor/config.d/condor_config.local
        content: |
          UID_DOMAIN = cloud.org
          ALLOW_READ = *
          ALLOW_WRITE = 192.168.56.*
          CONDOR_ADMIN = root@$(FULL_HOSTNAME)
          CONDOR_HOST = main.cloud.org
          IN_HIGHPORT = 9999
          IN_LOWPORT = 9000
          REQUIRE_LOCAL_CONFIG_FILE = False
```

## Ch7-3. Other Automation Tools for the Data Center

Automation tools fall into two groups by what they do. **Provisioning tools** create resources like servers, networks and storage (Vagrant in this lab), and **configuration management tools** bring the packages, settings and services inside existing servers to a desired state (Ansible). I researched them based on the IaC tool list on slides 8–9.

| --------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Terraform (HashiCorp) | Provisioning, declarative, immutable infrastructure. HCL language. Agentless                                     | Many providers (AWS, Azure, GCP, OpenStack, vSphere…) so multiple clouds in one codebase. Preview changes with plan, then apply. State file matches real resources to code. Largest community | Can't configure inside servers, so it needs a configuration management tool. Losing the state file or concurrent use causes accidents. License changed to BSL in 2023, which led to the OpenTofu fork |

AWS only (Closed)                                     | Fastest and deepest support for AWS services, no extra cost. Create, change and delete by stack, automatic rollback on failure. IAM integration                                               | Unusable outside AWS. Templates are long and verbose. Slow deploys, unfriendly error messages. Small community                                                                                        |
| OpenStack Heat        | Provisioning, declarative, immutable. HOT (YAML) templates. OpenStack only                                       | Built into private clouds (OpenStack), no extra install. Accepts CloudFormation-compatible templates                                                                                          | Unusable outside OpenStack. Few users and resources (Small community), less mature                                                                                                                    |
| Pulumi                | Provisioning, declarative model written in general languages (Python, TypeScript, Go…)                           | No separate DSL to learn; loops, functions and tests from the language. Reuses Terraform providers                                                                                            | State storage defaults to the paid Pulumi Cloud service (Must-have). | Chef                  | Configuration management, procedural, mutable infrastructure. Ruby DSL. Server–agent                             | Old and stable with plenty of resources (Large community). | Puppet                | Configuration management, declarative, mutable. Own DSL. Master–agent                                            | You only write "what state it should be in". Good node state reporting and auditing, strong for compliance. Large community                                                                   | Need to learn its own DSL and master server. Agents pull periodically, so weak at ad-hoc runs. Heavy for small environments                                                                           |
| SaltStack (Salt)      | Configuration management + remote execution, declarative (YAML). Master–minion (ZeroMQ), agentless with salt-ssh | Message bus sends commands to thousands of machines quickly and simultaneously. State application and remote execution in one tool. In short, for creating resources, Terraform is more general than CloudFormation or Heat, which are tied to a specific cloud, since it handles many environments in one codebase; Pulumi is the alternative if you want a familiar programming language. For configuring the inside of servers, Chef, Puppet and Salt all use agents and a central server, which makes them strong for large, long-running operations but costly to adopt. Ansible works over plain SSH without agents, which suits quickly configuring a small cluster like this lab.

Real data centers usually don't do everything with one tool; they pair a provisioning tool with a configuration management tool, as in "create with Terraform (or Vagrant), configure with Ansible (or Puppet)". The Vagrant + Ansible combination in this assignment is a miniature of that.

## Ch7-8. Idempotence in Ansible and Why It Matters

Idempotence is the property that applying the same operation once or many times gives the same result (slide 27). In Ansible it means the system stays in the same state no matter how many times you run the playbook.

This works because Ansible modules don't "run commands"; they take a "desired state", check the current state first, and change things only when they differ. For example, `dnf: name: condor, state: present` installs condor if it's missing and does nothing if it's already there. `blockinfile` finds the block it inserted by its marker comments and never adds it twice. That's why results are split into changed (I changed it) and ok (already in that state, left alone).

This lab is a direct example. The first run installed and configured everything with `ok=12 changed=9` on all three nodes, and after adding one firewalld task the second run gave `ok=13 changed=4`. The four changes were only the new firewalld stop, the config file removal and creation, and the condor restart; the rest, like SELinux, hosts and package installs, were already in the desired state and passed through. Without idempotence, the second run would have appended the same three lines to `/etc/hosts` again and re-downloaded packages, messing up the state.

Why idempotence matters:

- **Safe re-runs**: if a run fails midway, say from a dropped network, you just run it again from the start. Nobody has to work out how far it got, which cuts the human errors of manual work (like the KT outage case on slides 3 and 5, where a single command was missed).
- **Many machines in the same state**: running the same playbook on 100 machines puts them all in the same state regardless of when they were set up or what state they were in. Configuration drift, where servers' settings diverge over time, can be reversed by running it regularly.
- **Infrastructure as code**: the playbook becomes a record of "what state the system should be in" rather than a procedure, so it can be version-controlled, reviewed and reused in other environments (the IaC features on slide 7).
- **Change tracking**: looking at changed alone tells you what a run actually changed, so any change on a server that shouldn't change shows up immediately. `--check` mode lets you check without applying.

Not every task is idempotent on its own, though. The `shell` and `command` modules run every time, and this playbook's `service: state: restarted` restarts on every run, so it's deliberately not idempotent. Such tasks need a `creates:` condition, or a handler (`notify`) that restarts only when the config file changed, for the whole playbook to be idempotent.
