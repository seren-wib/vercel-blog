## 0. Introduction

> Part 4 of the series. What a skill is and why these rules moved into one is in [CH0. Skills overview](/en/blog/side-projects/skills/skills-00-overview/).

My public profile lives in three places: the [GitHub](glossary:github) profile [README](glossary:readme), this blog's About and Projects pages, and LinkedIn. Edit the three separately and sooner or later they disagree, so I decided to gather the editing into one place.

In restaurant terms, one recipe card sits on the wall and the kitchen stamps out three plates from it. The kitchen can't plate LinkedIn directly, so a waiter fixes by hand only the parts that differ between the plate already served and the new one. The recipe is the [single source of truth](glossary:single-source-of-truth), the kitchen is [code generation](glossary:code-generation), and the difference between the served plate and the new plate is the [diff](glossary:diff) between [desired state](glossary:desired-state) and current state.

The result is the `profile-edit` skill. A person edits only two source files, the [README](glossary:readme) and the blog are generated, and LinkedIn gets only the gap between the generated target and the live page, edited in a browser. The skill is 42 lines and 5,528 bytes, and 11 of its 28 bullets (9 rules, 8 LinkedIn policy lines, 11 traps) are LinkedIn editor traps.

## 1. Generating three outputs from one source

![One source, three profiles: profile-sync data/ → lib/render.mjs → GitHub README, blog, LinkedIn](/static/images/skills-04-profile-edit/pipeline-en.svg)

_One source, three profiles_

The source is `data/profile.mjs` (intro, experience, education, certificates, awards, open source contributions) and `data/projects.mjs` (14 projects) in the private profile-sync repo, and the generator is `lib/render.mjs`. The repo was created on 2026-10-25 and has 22 commits as of 2026-11-28.

The skill's first rules pin this down.

- Edit only `data/profile.mjs` and `data/projects.mjs`. The [GitHub](glossary:github) [README](glossary:readme), the blog's `data/authors/*.mdx` and `data/projectsData.ts` are generated output.
- Never edit the [README](glossary:readme) by hand. Its format also comes from `lib/render.mjs`.
- Before generating, `git pull` all three repos: profile-sync, the profile [README](glossary:readme) repo and vercel-blog.

The last rule has a record behind it. On 2026-10-28 a run generated from a stale `data/` and wiped entries another session had added, and the rule was written that day. The generator prints its source as is, so a stale source overwrites newer output with older content.

Generation runs after the tests. The documented command only reaches `scripts/build.mjs` if `npm test` passes, and on 2026-11-28 all 10 tests in `test/render.test.mjs` passed (94 ms). Each output ships differently. The [README](glossary:readme) is committed straight to `main` of the profile repo, and the blog goes through a branch and a [PR](glossary:pull-request) that is merged after [CI](glossary:ci) passes. The blog [PR](glossary:pull-request) process belongs to [CH5. pr-workflow](/en/blog/side-projects/skills/skills-05-pr-workflow/).

As of 2026-11-28, 2 of the 14 projects are not `hidden`. So the [README](glossary:readme) shows all 14, and the blog and LinkedIn show those 2 plus the open source item, 3 in total. That number is the result of a cut on 2026-11-26, when 6 projects and 20 skills were removed from LinkedIn, leaving 4 skills.

The other rules are about content.

- The intro is one text in all three places. The Stairno Account paragraph sits second so it lands in the part LinkedIn's About shows before "see more". Other projects stay out of the intro.
- Lists put Building before Shipped. A project that is released and works is Shipped right away, even with updates still coming. The blog `status` field and LinkedIn end dates follow the same rule.
- The [GitHub](glossary:github) [README](glossary:readme) keeps its format: the stars badges and the Contributing to section stay.
- Updates happen only when I ask. At first a cloud routine ran every Monday, but I decided to pick what goes up myself and turned it off on 2026-10-25. Now the candidates are gathered into a table and only the ones I pick go in.

## 3. Editing only the LinkedIn gap

![LinkedIn: edit only the gap between live and target. Diff live.md against target.md, edit with Playwright, then copy target over live](/static/images/skills-04-profile-edit/linkedin-diff-en.svg)

_LinkedIn: edit only the gap between live and target_

What to change is decided by the [diff](glossary:diff) between [desired state](glossary:desired-state) (`linkedin/target.md`) and current state (`linkedin/live.md`). The generator never writes to LinkedIn. It stops at `linkedin/target.md`, and the live page is recorded in `linkedin/live.md`. Changes go in this order.

1. `git diff --no-index linkedin/live.md linkedin/target.md` lists the fields that would change.
2. On my go-ahead, [Playwright](glossary:playwright) edits them. I sign in myself. There are 8 seconds between saves.
3. When done, target is copied over live and committed.

There is no guarantee `live.md` still matches the page, though. I edit LinkedIn directly too, so the skill says to re-read the live page before editing. Cloud runs never touch LinkedIn.

There are a few policy lines as well. The positioning is backend plus AI, without leading on [React](glossary:react) or [Next.js](glossary:nextjs). English is the primary profile language and Korean the secondary one, and each is written natively rather than translated. Projects have no per-language version, so each project holds an English block, then a Korean block, then the repo URL. Class team projects go under Projects, never Experience. Feed posts are written only when I ask, and never deleted.

## 4. Recording the editor traps

LinkedIn's edit screens are built for human hands, so under [UI automation](glossary:ui-automation) some of them do something other than what they show. All 11 lines of the skill's last section are traps like that. The ones with a record come first.

| Trap                                                                                                                    | What happened (record)                                                             | What the skill does                                                                                                           |
| ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| In the About editor ([tiptap](glossary:tiptap)), clicking a paragraph does not move the caret and overwrites other text | 2026-10-21 the About was overwritten twice                                         | Set a [DOM Range](glossary:dom-range) on the target `<p>` text node, `keyboard.insertText`, read every `<p>` back before Save |
| Adding skills in the Korean UI picks Korean-named [entities](glossary:entity)                                           | 2026-10-11 six Korean-named skills replaced by English [entities](glossary:entity) | Add them in the English UI and click only an exactly matching option                                                          |
| Deleting a skill can't be undone                                                                                        | 2026-10-11 a skill was deleted before confirmation                                 | Only recommend a deletion and wait for a clear yes                                                                            |
| Removing and re-adding project media can lose it                                                                        | 2026-10-25 project images were lost                                                | One image at a time, and check the project name after saving                                                                  |

The rest have no record of when they were hit. Here is what they say.

- Adding an Experience entry overwrites the headline with the job title, so the headline gets re-checked after any position change.
- Projects can't be reordered. Ongoing ones come first, then by end date, newest first.
- The add-image button often needs a second click, and it has to be clicked with the MCP click tool to catch the file chooser. Once, chained steps wrote a media title into the project name.
- Typing a Featured link with `fill()` breaks the preview. Type it one key at a time and wait about 10 seconds.
- Escape in an edit form opens a discard-changes confirm. The education form's notify-your-network switch defaults on and gets turned off before saving.
- LinkedIn's "share this update" prompts are declined, because accepting posts to the feed.

The human-like mouse and typing helper used for [Playwright](glossary:playwright) clicks and input lives in the global instructions, not in this skill. A similar pointer and typing effect for screen recordings is in [CH10. demo-recording](/en/blog/side-projects/skills/skills-10-demo-recording/).

## 5. What stays private

Every profile is a public page, so the skill lists what can't go on one.

- Student ID number, health and finances go nowhere.
- Vane, the game in progress, gets one neutral line ([Unity](glossary:unity) 2D top-down story adventure, prototype). No story details.
- In vercel-blog [PR](glossary:pull-request) bodies and commit messages, upstream PRs are never written as `owner/repo#N` or URLs. Repo name in plain text only.

The last rule dates from 2026-10-28. vercel-blog is a public repo, so a [PR](glossary:pull-request) body that names another repo's [PR](glossary:pull-request) number shows up on that upstream [PR](glossary:pull-request)'s timeline as "mentioned". That happened on two of this blog's PRs. The same rule is in [CH1. blog-post](/en/blog/side-projects/skills/skills-01-blog-post/), which covers blog posts.

## 6. Moving from memory to a skill

The rules started out spread across three global memory files: the profile [README](glossary:readme) format, the LinkedIn profile, and profile-sync. They moved from memory, which every session reads, into a skill, which loads only when needed. That is [lazy loading](glossary:lazy-loading).

The 2026-11-13 commit message gives the reason: rules and gotchas that matter for one kind of task load when that task comes up, instead of sitting in global memory. A session that never touches a profile has no use for 11 lines of LinkedIn traps. The skill file has not changed since, as of 2026-11-28. How skills, instructions and memory were split is in [CH0.
