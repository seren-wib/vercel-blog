# 1. Purpose of CPU scheduling

- Pick which of the runnable [processes](glossary:process) to put on the CPU next
- It happens often, so it has to be fast.

# 2. Goals of scheduling

**Don't play favorites with jobs, keep working without rest, get a lot done, meet schedules, and [process](glossary:process) things fast.**

## 1. There should be no starvation.

1. [fairness](glossary:fairness): every [process](glossary:process) should get equal access to the CPU
2. Balance: not just the CPU, every device should be kept busy.

### starvation: a process is ready to run, but the scheduler never gives it a chance, so it never runs and just sits ready

- Caused by a bad [scheduler](glossary:scheduler) or by [synchronization](glossary:synchronization).

## 2. batch system

- Submit jobs all at once and let the system [process](glossary:process) them in order

1. [throughput](glossary:throughput): do as many jobs as possible per hour
2. [Turn around time](glossary:turnaround-time): reduce the time from when a job is submitted until it's completely done
3. [CPU utilaization](glossary:cpu-utilization): keep the CPU working all the time.

## 3. Interactive system

- A system where the user types input directly and waits for a response
- [response time](glossary:response-time): must respond as quickly as possible

## 4. Real-time system

- Must not go past the deadline
- Job execution time must be predictable.

# 3. Basic concepts

## 1. non-preemptive vs preemptive

1. [non-preemptive](glossary:non-preemptive-scheduling): call [yield](glossary:yield) and give up the CPU voluntarily
   - Here, even if a higher-priority one arrives later, this [process](glossary:process) finishes completely first and then the next [process](glossary:process) is taken
2. [preemptive](glossary:preemptive-scheduling): give up the CPU on an [interrupt](glossary:interrupt)
   - Problem: what if an [interrupt](glossary:interrupt) arrives while modifying shared data? While in a [system call](glossary:system-call)?
   - [Synchronization](glossary:synchronization) problems come along with it (shared data and kernel state can be corrupted)
   - Here, if a higher-priority one arrives, [context switch](glossary:context-switch) immediately

## 2. cpu-bound vs I/O-bound

[cpu bound](glossary:cpu-bound): long [CPU bursts](glossary:cpu-burst) (holds the CPU for long stretches)
[I/O bound](glossary:io-bound): short [CPU bursts](glossary:cpu-burst) + frequent I/O waits (uses the CPU briefly, then drops out for I/O)
**[I/O-bound](glossary:io-bound) is more responsive**

- In practice, the time [processes](glossary:process) actually hold the CPU is short.

# 4. State queue flow

```
From the Running state
├─ time slice expired
│  └─ used the CPU too long, forced off
│     → moves to the Ready Queue
│
├─ I/O request
│  └─ disk read, network request, etc.
│     → moves to the Waiting Queue until the I/O finishes
│     → I/O completion interrupt
│     → back to the Ready Queue
│
├─ wait()
│  └─ waits for an event like a child process exiting
│     → moves to the Waiting Queue
│     → child exits
│     → back to the Ready Queue
│
└─ exit
   └─ execution finished
      → Terminated
```

# 5. Four scheduling algorithms

## 1. FCFS/FIFO

- Run in the order of arrival in the [ready queue](glossary:ready-queue).
- Mostly [non-preemptive](glossary:non-preemptive-scheduling) (if P2 arrives while P1 is running, it waits until P1's work is done)
- Pros: simple to implement
- Cons: [waiting time](glossary:waiting-time) can get long (if a [process](glossary:process) with a long [CPU burst](glossary:cpu-burst) arrives first, it runs first no matter how short the [processes](glossary:process) that arrive later are), it's a problem when the CPU does long I/O in the middle
  ![FCFS diagram](/static/images/os-08-scheduling/sched-fcfs.png)

## 2. SJF(Shortest Job First)

**Run first the [process](glossary:process) expected to have the shortest [CPU burst](glossary:cpu-burst)**

- Goal: reduce average [waiting time](glossary:waiting-time)
- Condition: when all jobs are available at once (all [processes](glossary:process) are already in the [ready queue](glossary:ready-queue) and their burst times are known)
- Mostly runs non-preemptively
- Problems: future [CPU burst](glossary:cpu-burst) times can't be known (so they're predicted from past patterns), [starvation](glossary:starvation) can occur
  ![SJF diagram](/static/images/os-08-scheduling/sched-sjf.png)

## 3. SRTF(Shortest Remaining Time First)

- The [preemptive](glossary:preemptive-scheduling) version of [SJF](glossary:sjf)
- How is it different? In [SJF](glossary:sjf) with T1(arrival = 0, burst time = 5), T2(arrival = 2, burst time = 2),
- T1 runs to completion even after T2 arrives, then it moves on to T2
- In [SRTF](glossary:srtf), when T2 arrives it compares the two burst times (T1:3, T2:2): T2 is shorter? It can switch to T2. Why: because it's [preemptive](glossary:preemptive-scheduling).
  ![SRTF diagram](/static/images/os-08-scheduling/sched-srtf.png)

## 4. RR(Round Robin)

**Hand out the CPU in turns, one [time quantum](glossary:time-slice) at a time**
An improved version of [FIFO](glossary:fcfs) that treats the [ready queue](glossary:ready-queue) as a circular queue.

- [Preemptive](glossary:preemptive-scheduling)
  ![RR diagram](/static/images/os-08-scheduling/sched-rr.png)

# 6. Priority Scheduling

**Pick and run the [process](glossary:process) with the highest priority among the [processes](glossary:process) in the [ready queue](glossary:ready-queue)**

- [SJF](glossary:sjf) and [SRTF](glossary:srtf) are kinds of this too (shorter burst = higher priority)
- If prority is equal, [FIFO](glossary:fcfs) or [RR](glossary:round-robin) can be applied
- Both [non-preemptive](glossary:non-preemptive-scheduling) and [preemptive](glossary:preemptive-scheduling) are possible
- Priority can change dynamically (e.g. raise the priority of [processes](glossary:process) that waited long, lower the priority of [processes](glossary:process) that used a lot of CPU)
  - This leads to [MLFQ](glossary:mlfq) ([Multilevel Feedback Queue](glossary:mlfq)).

## Problems with Priority Scheduling

### 1. Starvation

- Solution: [Aging](glossary:aging): raise the priority of old [processes](glossary:process), lower the priority of CPU hogs

### 2. Priority inversion

1. Priority: P1 > P2 > P3
2. P1 and P3 both need to enter the same [critical section](glossary:critical-section)
3. But P3 enters the [critical section](glossary:critical-section) first and grabs the lock
4. Then P2 shows up
5. P2 has higher priority than P3, so P2 runs first
6. P3 can't release the lock, the lock stays held, so P1 can't run

#### Solutions

1. [PIP](glossary:priority-inheritance-protocol)

- Raise the priority of the low-priority job
- In the example above, raise P3's priority so P3 finishes quickly, then run P1 next

2. [PCP](glossary:priority-ceiling-protocol)

- Each resource has a [priority ceiling](glossary:priority-ceiling-protocol) value set in advance
- When a thread locks that resource
- it is immediately raised to that ceiling priority

# 7. Multilevel Queue Scheduling

**Assign [processes](glossary:process) permanently to a queue by type, and apply a different algorithm per ueue**

- Why separate them? Because different jobs want different goals

## foreground

- interective jobs
  - [response time](glossary:response-time) matters, must respond quickly
  - ex: terminal, editor, gui, handling user input
  - Algorithm: [RR](glossary:round-robin)

## background

- batch jobs
  - [throughput](glossary:throughput) and [turnaround time](glossary:turnaround-time) matter, what counts is processing a lot and finishing
  - ex: large computations, log processing, long-running jobs
  - Algorithm: [FCFS](glossary:fcfs)

## Scheduling between queues

- [Fixed priority scheduling](glossary:fixed-priority-scheduling): [process](glossary:process) all of [foreground](glossary:foreground-process) first, then [background](glossary:background-process)
  - Problem: [starvation](glossary:starvation)

- A figure showing "a structure that stacks several queues in priority order and gives the CPU starting from the top queue"
- So if the queues are separated outright, there's less overhead in figuring out who has higher priority

# 8. MLFQ(Multilevel Feedback Queue)

**The [multilevel queue](glossary:multilevel-queue-scheduling) with the [aging](glossary:aging) technique applied at the queue level**

## Difference from the multilevel queue

- [Multilevel Queue](glossary:multilevel-queue-scheduling): a [process](glossary:process) is fixed to one queue

- [Multilevel Feedback Queue](glossary:mlfq): a [process](glossary:process) moves between queues depending on its execution pattern

## Flow

```
→ start by running at high priority
→ if it uses the CPU for long, move it down
→ if it uses it briefly and does I/O, keep it up

And raise the priority of queues that haven't run for a long time
the aging technique
```

# 9. UNIX scheduler

**[preemptive](glossary:preemptive-scheduling) + priority-based + round-robin + dynamic priority + [MLFQ](glossary:mlfq)**

- [Preemptive](glossary:preemptive-scheduling): if a higher-priority [process](glossary:process) arrives, it can cut off the current [process](glossary:process)
- Priority-based: run high-priority [processes](glossary:process) first
- Round-robin: within the same priority, take turns by [time slice](glossary:time-slice)
- Dynamic priority
  - Using a lot of CPU lowers priority
  - [I/O-bound](glossary:io-bound) or interactive [processes](glossary:process) get favored priority
- Similar to [MLFQ](glossary:mlfq): priority changes based on [process](glossary:process) behavior
- [Aging](glossary:aging): prevents [starvation](glossary:starvation) of [processes](glossary:process) that waited long

# 10. Scheduling on multiprocessors

**So far we've only covered the single-CPU case; how should we schedule when there are several CPUs?**

```
P1, P2, P3, P4
CPU0, CPU1, CPU2, CPU3

→ P1 on CPU0?
→ P2 on CPU1?
→ Or give each CPU its own queue?
→ What if work piles up on one CPU?
```

- **[load balance](glossary:load-balancer)**: split the workload among CPUs appropriately so that no CPU sits idle while another is busy
- **[process affinity](glossary:processor-affinity)**: when possible, the same [process](glossary:process) should run on the same CPU. Because of the [cache](glossary:cache)

# 11. NUMA(Non-Uniform Memory Access)

**Memory access time is not uniform**

- Where is the physical memory located? The design has to take even this into account

* Multithreaded [multicore](glossary:multicore) is a structure that puts several [hardware threads](glossary:hardware-thread) on one core to use it more efficiently, and the [scheduler](glossary:scheduler) has to account for the fact that a [logical CPU](glossary:logical-cpu) isn't truly an independent CPU.
