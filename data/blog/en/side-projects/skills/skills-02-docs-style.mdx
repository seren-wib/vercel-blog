## In one line

`docs-style` is the skill opened right before writing a document. It holds six groups of rules: plan pages and checklists, option comparisons, the language of public repo docs, file formats, building school reports, and Google Docs gotchas. It started as rules gathered from global memory, and over two weeks and seven commits it moved the source of school reports from Google Docs to local files. The size history is in the "By the numbers" table below.

## 2. Plan pages and checklists

Think of a to-do note on the fridge. You don't tear it into one strip per person; you keep one sheet and tick lines off as they are done.

![One TODO list ticked off in place instead of lists split by person](/static/images/skills-02-docs-style/todo-list.svg)

_One TODO list ticked off in place instead of lists split by person_

The sheet is one **TODO list**, and the tick is the Markdown task list `- [x]`. There are three rules.

- No person's name anywhere, mine included. Lines like "owner: ○○○" or "for ○○ to do" are out.
- One list. No "done / who does what" split; finished items are checked where they are. Groups are by phase or place only ("prep", "at school (per PC)", "check"). When the device matters, prefix it ("desktop:").
- Role tables a team defines in its own repo docs are outside this rule. If unsure, ask.

The **team documents** rule added the same day sits here too. Before changing a document a teammate owns, report whose it is, where it is and what would change, then wait for an answer. This line came from tidying a team assignment's combined document, where teammates' sections had to be shortened to fit the page limit (old memory record).

## 3. Option comparisons

Think of a balance scale. If several heavy weights go on one pan as a single "slightly inconvenient," the scale lies.

For an **option comparison** table or list there are two rules.

- Every drawback that matters gets its own bullet, with the concrete consequence. Several costs are never shrunk into one soft phrase.
- Before finishing, check that every cost of an option mentioned in chat is also in the document.

The second rule follows from comparisons happening in conversation first. If a cost said in chat drops out on the way into the document, anyone reading only the document later never learns about it. The specific incident behind this rule is not recorded. The format for keeping rejected options and their reasons in decision records is in [the entry shape in Project Docs 2](/en/blog/side-projects/project-docs/project-docs-02-decision-records/#4-the-shape-of-one-entry).

## 4. Language and file formats

Think of a guest notice and an envelope standard. A notice a first-time guest reads is in a language everyone reads, and papers go out in the agreed envelope.

**Language** rules:

- Public documents a visitor reads first (README, CONTRIBUTING, SECURITY, CHANGELOG, PR templates) are in English, and the repo docs say so.
- Planning documents (`docs/specs/`), their Google Docs copies, CLAUDE.md, and commit and PR language follow the repo's own rule.

The **file format** rules came in on 2026-11-27.

- A document is a docx and a sheet is an xlsx, built locally. I open them in Google Docs and Sheets through Drive.
- Deliverables are not made as new native Google Docs or Sheets. Existing ones stay as they are.
- Exceptions: Markdown in a repo, the repo → Google Docs sync in `project-docs` ([Project Docs 4](/en/blog/side-projects/project-docs/project-docs-04-docs-sync/)), and documents teammates edit together.
- On the Mac, the iCloud Drive `UNIV/` folder shows in Drive under "Computers → mac → UNIV". It was the only folder Google Drive for desktop had added on that Mac (checked 2026-11-27), and the Drive API reports those copies as `canEdit: false`. The Windows side has not been checked.

## 5. Building school reports

Think of keeping the manuscript and the typesetter on your own desk and binding a fresh copy each time. To fix something, you don't write on the bound book; you fix the manuscript and print again.

![A build pipeline from an HTML source and a build script to docx and PDF, with Google Docs dropped as the source](/static/images/skills-02-docs-style/report-pipeline.svg)

_A build pipeline from an HTML source and a build script to docx and PDF, with Google Docs dropped as the source_

The manuscript is the **HTML body**, the typesetter is the **build script**, and the binding is the **docx** and the **PDF** converted from it.

- The source stays local: one HTML body and one build script (`hwN-body.html` + `hwN-docx-build.js`). The script builds the docx with the npm packages `docx` and `node-html-parser`. Figures are referenced by file path.
- For the PDF, a copy with fonts swapped is converted through `soffice` (바탕 → AppleMyungjo, Consolas → Menlo, 맑은 고딕 → Apple SD Gothic Neo). Why the fonts are swapped is not written in the skill (not recorded).
- If the course folder has its own `CLAUDE.md`, it wins over this section.

### Why Google Docs stopped being the source

The first rule (2026-11-13) was to build reports in Google Docs and export them to PDF. On 2026-11-25 the default moved to a local source, and the skill keeps three reasons measured on a cloud computing assignment.

- A Doc with screenshots returns over 400k characters per `read_doc`. The local HTML source is about 30k characters.
- Every fix repeats read, write and re-check.
- Conversion drops the TOC heading ids, and the API can't restore them.

The same conclusion showed up earlier in that course folder's memory. On 2026-10-04 there is a record of trying to edit HW3 in Google Docs and going back to docx, and from then on cloud computing reports were local docx as an exception in the course `CLAUDE.md`. The 11-25 commit promoted that exception to the default and deleted the exception sentence. Text-only reports are built locally too. Only documents teammates edit together stay in Google Docs.

### Page rules

- Page 1 cover: the CBNU (Chungbuk National University) logo, title, course, submission date and authors. Authors are GitHub handles or roles, never real names. The logo line came in on 2026-11-17, when 13 document instructions from that day were checked against the skill and it was one of the 5 found missing.
- Page 2 table of contents: indented headings, no page numbers.
- A big block (a diagram section, a schema or table spec, each algorithm) starts with a page break. To keep a heading from sitting alone at the bottom of a page, headings get keep-with-next.
- Heading levels follow weight. A major component like a Class Diagram or the DB schema is never at the same level as a small subtopic. Sub-sections are numbered like 2-2-1.
- Figures are embedded images in the docx. No links or paths where a figure should be. SVG diagrams are rendered to PNG locally before embedding.
- Section names use the assignment's own wording ("사용자 인터페이스 명세 및 설계", user interface specification and design, not just "wireframe").
- A report built from stage documents has its own source. Docs that the `project-docs` sync overwrites are never edited.
- After building, every page of the PDF is rendered and looked at before reporting.

## 6. Google Docs gotchas

Think of a note taped to the copier. The original won't take on just any paper; you copy it once to the right format and then put it in.

![Converting an SVG from a public repo to PNG through weserv and inserting it with insertInlineImage](/static/images/skills-02-docs-style/svg-to-docs.svg)

_Converting an SVG from a public repo to PNG through weserv and inserting it with insertInlineImage_

The copier is the image proxy **images.weserv.nl**, and the format is what the Google Docs API `insertInlineImage` accepts. Even after report sources moved local, these gotchas still show up in Docs shared with teammates and in synced Docs.

- `insertInlineImage` takes only PNG, JPEG or GIF from a public URL. An SVG in a public GitHub repo goes in as `https://images.weserv.nl/?url=raw.githubusercontent.com/<owner>/<repo>/<sha>/<path>.svg&output=png&w=1600`. The path uses a commit SHA instead of `main`, because weserv caches by URL and a `main` path can return an old picture. Fetch it with curl and look at it before inserting. drawio SVGs with Korean text render fine.
- Mermaid source is not sent to mermaid.ink without asking. That counts as uploading data, so it is rendered locally.
- To resize an inline image, delete it and insert again with a new `objectSize`. About 420-440 pt wide × 300 pt high fits two landscape diagrams on one page.
- `read_file_content` shows bold text inside tables as `\*\*text\*\*`. Those are not literal asterisks.
- A `read_doc` result over 1 MB is saved to a file. Extract it with node and find the body after the first HEADING_1 (the TOC lines repeat the headings). The final check is exporting to PDF and rendering every page.

## 7. Summary

| Group          | Core rule                                              |
| -------------- | ------------------------------------------------------ |
| Plan pages     | No names, one TODO list, finish by checking            |
| Team documents | Before editing, report whose, where and what           |
| Option compare | One bullet per drawback, checked against the chat      |
| Language       | Public docs in English, the rest by repo rule          |
| File formats   | Documents docx, sheets xlsx, no new Google Docs        |
| School reports | Local HTML → docx → PDF, render every page to check    |
| Google Docs    | SVG as weserv PNG, SHA paths, Mermaid rendered locally |

The skill itself has changed by these rules. The reasons for switching the source (400k vs 30k characters, lost heading ids) are kept as measured values, and if those values change again, the rule gets reopened.
