## 1. What is Woowangthon

It's a three-week hackathon run by LIKELION Chungbuk National University and the Chungbuk National University AI Bootcamp program. There is one theme.

> **Can AI be a coworker?**

The organizers gave three examples. A coworker that keeps track of your graduation requirements, a coworker that checks in on elderly people, a coworker that catches defective products first. All three have the same shape: **AI filters and suggests first, but a person makes the final call**. They also ask "how is this different from what already exists?"

| November 16~20    | Preliminary judging, 10 teams picked for the finals                  |

Two of the rules come up a lot in this series. One is **don't dress up results**. You can't show fake data or pre-made screens as if they were real, and if you have to use them, you mark them in code and list them in a doc. The other is **say where you used AI**. ## 2. The problem we are solving

The users are students. When you build a web service in a project course, you deploy it yourself. You put it on a commercial cloud like Vercel, AWS or Cloudflare, and when you go over the free tier, you pay out of your own pocket. When the course ends, the service usually goes down with it.

| Problem                     | Details                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------ |
| Cloud costs are a burden    | The moment you pass the free tier, money comes out of the student's own card         |
| School computers sit unused | Lab PCs are off or idle outside class hours                                          |
| Courses stop at deployment  | You learn to deploy, but running it afterward (outages, monitoring) is never covered |

## 3. What we are building

**A deploy platform where students run their own GitHub repos on a server made by tying school PCs together.** A student only submits a repo URL and pays nothing. Before a deploy, AI checks the code for security risks first, and if a service starts acting strange while it runs, AI explains the cause in plain words.

From the student's side, one deploy goes like this.

1. The student logs in with a GitHub account, enters a public repo URL, picks a type (static web / server / web+server) and, if they use a DB, the connection details for their own DB, and submits
2. **AI reviews it.** It pulls the repo read-only and looks for risks like exposed secret keys or overly broad public permissions, with evidence. If something needs fixing, a bot account opens a PR with a suggested fix
3. **The operator decides.** They read the review summary and pick one of approve, request changes, or block
4. Only approved code gets built into a container image, on an isolated build server outside the school
5. The school PC cluster pulls that image and runs it. The app connects to the student's own DB with those details
6. Visitors come in through a `name.stairnoworks.com` address
7. If something goes wrong while it runs, like running out of memory or restarting over and over, rules stop or restart it first, and AI sends an alert explaining the cause and what to do next

## 4. What AI does, what people decide

This is our answer to the contest theme. We don't hand decisions over to AI.

| Situation                    | What AI does                                                                       | What people decide                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Pre-deploy review            | Finds security risks in code and config and reports them with evidence             | The student fixes or pushes back, the operator decides on approval |
| Metric anomaly in production | Guesses the cause of the anomaly, explains it in plain words, suggests a next step | Picks the action: restart, stop, or roll back                      |

How we differ from what already exists also comes out of this table. On commercial clouds the student pays, and commercial AI deploy helpers (Vercel Agent, AWS's security and ops agents, that kind of thing) are paid and aimed at companies. We run on school PCs so students pay nothing, and every deploy gets a review and anomaly analysis without any extra setup.

There is one more AI coworker in this series. It's the [AI coding agent](/en/blog/devops/devops-00-basics/#ai-coding-agent) (Claude Code) that typed commands and edited the plan next to me while I set up the cluster. It got some things right, and once it threw the design off course because of an assumption it made on its own. I write that down too and don't hide it.

## 5. Overall structure

The platform lives in the cloud (AWS), and only student services run on the school PCs.

| Zone             | Component             | Tech                                | What it does                                                                  |
| ---------------- | --------------------- | ----------------------------------- | ----------------------------------------------------------------------------- |
| Cloud (AWS)      | User Page, Admin Page | React + TypeScript, S3 + CloudFront | Deploy screen for students, approval screen for operators                     |
|                  | Platform server       | Nest.js, EC2                        | Takes requests, asks for builds, tells the school cluster to deploy           |
|                  | AI server             | FastAPI, EC2                        | Pre-deploy review, anomaly analysis                                           |
|                  | Build                 | AWS CodeBuild                       | Turns student code into images. The only outside step where student code runs |
|                  | DB · login            | Supabase                            | GitHub login, stores review results and deploy status                         |
|                  | Message queue         | Kafka                               | Keeps deploy records from getting lost                                        |
| External         | Container registry    | GHCR                                | Stores built images                                                           |
| School           | Cluster               | k3s, 3 school PCs                   | Runs student services                                                         |
| School ↔ outside | Private network       | Tailscale                           | How the platform server and operators reach the school PCs                    |
|                  | Public tunnel         | Cloudflare Tunnel                   | How visitors reach student services                                           |
| School           | Monitoring            | Prometheus, Grafana                 | Node and service metrics                                                      |

There is one important assumption on the school PC side. **We don't open a single inbound port into the school.** The PCs sit behind the school firewall, so nothing outside can start a connection to them. That means every connection to the outside is started by the school PCs, going out. Operators and the platform server come in over the Tailscale private network, and visitors come in through the Cloudflare tunnel.

The cluster looks like this.

| PC   | Role   | What it does                                                                               |
| ---- | ------ | ------------------------------------------------------------------------------------------ |
| PC 1 | Leader | Cluster control, public tunnel, image cache, metrics collection. Takes no student services |
| PC 2 | Worker | One student project                                                                        |
| PC 3 | Worker | One student project                                                                        |

The three are wired with LAN cables to one switch we bought. If a worker goes down, the leader brings that project back up on the remaining worker. The DB is the student's own and lives outside the cluster, so there is no data to move with it. There is only one leader, so if the leader goes down, new deploys stop. With only three PCs, we accept that.

## 6. New terms

| Term                                       | Meaning                                                                                                              |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| Container image                            | A bundle of a program plus the environment it runs in. It runs the same way anywhere                                 |
| Kubernetes                                 | A program that spreads containers across many computers and restarts them when they die                              |
| k3s                                        | A slimmed-down Kubernetes distribution. Used to build a cluster from a few small computers                           |
| Cluster, node                              | A group of computers tied together to act as one is a cluster, and one computer in it is a node                      |
| Leader, worker                             | The leader is the node that decides what runs where, workers are the nodes that actually run services                |
| Pod                                        | The smallest unit Kubernetes runs. One container or a few                                                            |
| Namespace                                  | A compartment inside the cluster. Each student project gets one (`proj-<id>`)                                        |
| Tailscale                                  | A service that ties devices together into one private network. Lets you reach devices behind a firewall from outside |
| Cloudflare Tunnel                          | The inside server opens a connection to Cloudflare first, and visitor requests come in over that connection          |
| ADR                                        | A short doc that records one technical decision and its reasons (Architecture Decision Record)                       |
| [PR](/en/blog/devops/devops-00-basics/#pr) | A request on GitHub saying "please merge this change" (Pull Request). A teammate reviews and merges it               |
