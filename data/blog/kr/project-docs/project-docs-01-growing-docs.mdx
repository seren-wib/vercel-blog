## 2. 과제마다 붙은 문서

비유하면 숙제가 나올 때마다 공책을 한 권씩 새로 산 셈이다. 공책마다 칸이 다르고, 같은 내용이 여러 권에 나뉘어 적혔다.

용어로는 문서가 **평면 구조(flat structure)**로 쌓였다. coffee-shop은 2026-09-15에 시작한 소프트웨어공학 팀 과제다. 커밋 제목을 날짜순으로 보면 문서가 과제 단위로 붙었다.

## 3. 수업 순서를 내 절차로

비유하면 수업에서 배운 공정표를 내 작업대 옆에 붙인 것이다.

용어로는 **SDLC 단계**를 개인 작업 규칙으로 옮겼다. 2026-10-17 에이전트 메모리에 "프로젝트 절차" 파일이 생겼다. 파일에는 stairno.com 허브 문서를 시작하며 정했다는 것과, 기준이 소프트웨어공학 3~6장이라는 것이 적혀 있다. 단계는 계획, 요구사항, 설계, 구현, 배포, 유지보수였고 단계마다 산출물이 하나씩 붙었다. 계획서는 [3장 프로젝트 계획](/kr/blog/software-engineering/software-engineering-ch3-project-planning/), SRS는 [4장 요구사항 명세](/kr/blog/software-engineering/software-engineering-ch4-requirements-analysis/#433-3단계-요구사항-명세software-requirements-specification-srs)에서 온 것이다.

다음 날인 10-18, 이 절차대로 account.stairno.com의 문서 넷을 썼다. `plan.md` 179줄, `srs.md` 382줄, `sdd.md` 534줄, `test-deploy.md` 507줄, 합쳐 1,602줄이다. 이 넷이 나중에 양식의 본보기가 됐다. 이 시점엔 Google Docs가 원본이었는데, 그날 바로 레포의 마크다운이 원본으로 바뀌었다. 그 경위는 [4편](/kr/blog/project-docs/project-docs-04-docs-sync/)에 있다.

## 4. 넷에서 여섯으로

비유하면 한 공책에 섞어 쓰던 시험 계획과 이사 계획을 각자 다른 공책으로 나눈 것이다.

용어로는 SDLC 단계마다 문서 하나라는 규칙을 테스트, 배포, 유지보수까지 지킨 것이다. 2026-11-16 새벽, 이 절차를 에이전트 스킬로 만들면서 문서는 넷에서 여섯이 됐다. 계획서는 SPMP라는 이름을 얻었고, 테스트와 배포가 한데 섞여 있던 `test-deploy.md`는 테스트 계획서(STP), 설치 계획서(SIP), 유지보수 계획서(SMP) 셋으로 나뉘었다.

나누자고 한 이유는 내가 관례를 따르기로 했기 때문이다. 관례에는 이유가 있을 테고, 관례대로 한 번 써 봐야 뭐가 좋은지도 알 수 있다고 봤다. 이 결정과 각 문서가 따르는 표준은 [3편](/kr/blog/project-docs/project-docs-03-standards/)에 따로 정리했다.

SRS를 먼저 쓰는 건 규칙이다. 요구사항 번호가 나머지 문서를 잇는 키라서다. 다시 쓴 SRS에는 도메인 요구사항 24개, 기능 요구사항 57개, 비기능 요구사항 35개, 사용사례 14개가 들어갔다. SDD는 이 번호를 붙여서 썼다.

옛 문서를 지우는 #68 본문에는 이유를 한 줄로 적었다. 단계 문서가 옛 파일을 대신하고, 옛 파일은 git 이력이 갖고 있다는 것이다. 그래서 새 문서에는 "초안 몇 번 참고" 같은 줄을 남기지 않았고, `docs/old/`를 가리키는 곳도 두지 않았다. 그래야 옛 폴더를 지워도 끊기는 링크가 없다. 같은 날 이 순서가 스킬의 이전 규칙이 됐다. 옛 문서를 `docs/old/`로 옮기고, 양식을 복사하고, SRS부터 채우고, `docs/old/`를 지운다.

## 6. 지금도 늘어나는 중

비유하면 공책 양식을 정했다고 끝난 게 아니라, 선생님이 빈칸을 지적할 때마다 칸이 하나씩 생긴다.

용어로는 양식의 개정(revision)이다. 2026-11-28 새벽 SDD 양식에 절 하나와 규칙 하나가 늘었다. 계기는 coffee-shop SDD에 대한 [교수님 피드백](/kr/blog/coffee-shop/coffee-shop-01-requirements-design/#교수님-피드백-부품-id와-클래스-명세) 두 개였다. 와이어프레임의 부품에 번호가 없다는 것, 그리고 클래스와 메서드 명세가 컴포넌트 설계와 섞여 있다는 것이다.

- **화면 부품 ID**: 화면 설계의 UI 부품마다 `SCR-01-01` 같은 ID를 붙이고, 와이어프레임에도 같은 ID를 표시한다. 절 번호는 밀릴 수 있지만 ID는 안 밀린다.
- **클래스·모듈 명세 절**: 코드 구조대로 모듈마다 파일 하나를 두고 공개 함수의 시그니처, 반환과 예외, 요구사항 ID를 적는다. 다 쓰고 나면 코드의 `def`·`class` 목록과 스크립트로 대조한다.

coffee-shop에는 [#129](https://github.com/seren-wib/coffee-shop/pull/129)(+1,059 / −50)와 [#130](https://github.com/seren-wib/coffee-shop/pull/130)으로 들어갔다. 이미 SDD가 있던 레포는 절 번호를 다시 매기지 않고 새 절을 맨 뒤에 붙였다. 그래서 coffee-shop에서는 클래스 명세가 12절이고, 설계 근거는 11절에 그대로 있다.
