## 0. Introduction

> Part 14 of the series. Build stage 6 (connecting to the outside), the end of build 09: November 12, the day the [EC2](glossary:ec2) for the platform server appeared. What we are building and why is in [Woowangthon 0](/en/blog/hackathon/woowangthon/woowangthon-00-overview/). The cluster side was ready in [part 11](/en/blog/hackathon/woowangthon/woowangthon-11-server-link/), and this post crosses off that post's [last list](/en/blog/hackathon/woowangthon/woowangthon-11-server-link/#9-what-stays-unchecked-without-the-ec2). The [GoCD](glossary:gocd) server and the leader executor's registration that afternoon get their own post, [part 15](/en/blog/hackathon/woowangthon/woowangthon-15-gocd-registration/).

To finish build 09 we needed the [EC2](glossary:ec2) that the platform server will run on, and that day we had to cross off the "what stays unchecked without the [EC2](glossary:ec2)" list left in part 11.

In restaurant terms, it is the day a second location opened next to the flagship (the school cluster). The second location has no front door for guests, only a staff passage. Knock on the door at the end of the passage: if the answer is "no one is serving here yet", the passage is open, and if nobody answers at all, the passage is blocked. The second location is the [EC2](glossary:ec2), the staff passage is the [Tailscale](glossary:tailscale) tailnet, the "no one is serving here yet" answer is [connection refused](glossary:connection-refused), and no answer is a [timeout](glossary:timeout).

What I did that day: put the [EC2](glossary:ec2) on the tailnet by admin approval with no key, probe the [access rules](glossary:acl) for real and read the results, run 18 server-account checks from the [EC2](glossary:ec2), and in the evening call the leader through the server code.

## 1. An EC2 that differs from the plan

The [EC2](glossary:ec2) was made by our team lead TaeTaeJin, who owns it. One thing differs from what the November 11 meeting settled.

| Item                                    | Settled                                                                         | Actual                                                                                                                                       |
| --------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| [Instance type](glossary:instance-type) | t3.large                                                                        | m7i-flex.large (same 8 GB of memory)                                                                                                         |
| OS · region                             | [Amazon Linux](glossary:amazon-linux) 2023, Seoul                               | Same                                                                                                                                         |
| Inbound rules                           | None                                                                            | None (the [security group](glossary:security-group) has no inbound rule at all)                                                              |
| Instance metadata                       | [IMDSv2](glossary:imdsv2), hop limit 1                                          | Same                                                                                                                                         |
| Permissions                             | An [instance role](glossary:iam-role) that reads the server's settings          | Same (the server settings and [tunnel](glossary:cloudflare-tunnel) token in [Parameter Store](glossary:aws-systems-manager-parameter-store)) |
| Operator access                         | [SSM](glossary:aws-systems-manager) [Session Manager](glossary:session-manager) | Same. No [SSH](glossary:ssh)                                                                                                                 |

t3.large failed because of the AWS account. It could only launch free-tier [instance types](glossary:instance-type), and the t3.large request was [refused](glossary:connection-refused). We took m7i-flex.large from the free-tier list because it has the same memory. The plan puts the server, the AI server and the [GoCD](glossary:gocd) server on this one machine, so less memory would have hurt. It is still 8 GB.

No [SSH](glossary:ssh) is a condition that follows this whole post. The only way into the [EC2](glossary:ec2) is AWS [SSM](glossary:aws-systems-manager). People come in through the [Session Manager](glossary:session-manager) window in the console, and the agent sends commands through [SSM](glossary:aws-systems-manager)'s [Run Command](glossary:run-command) (`aws ssm send-command`). With no inbound port at all, there are no [SSH](glossary:ssh) keys to manage and nobody knocking on port 22.

## 2. Joining the tailnet with no key

In part 11 I wrote that "the one-time join key will be made on the day there is a device to use it, and used right away." In the end we made no key at all.

This is the command [Run Command](glossary:run-command) sent to the [EC2](glossary:ec2).

```bash
tailscale up --hostname wcp-platform --advertise-tags=tag:platform-server
```

Without a key, [Tailscale](glossary:tailscale) prints a login URL and waits. I am the tailnet admin, so I opened that URL in the browser and approved it, and the [EC2](glossary:ec2) came in carrying `tag:platform-server`. Who may apply a tag is set by `tagOwners` in the [access rule file](/en/blog/hackathon/woowangthon/woowangthon-11-server-link/#8-private-network-access-rules). Here that is admins only, so one approval also declares "this device is the server".

Making no key was the cleanest choice of this step. Even a one-time key gets written down somewhere at least once, and afterwards someone has to check that it was revoked. An approval ends on the spot and leaves no [secret](glossary:kubernetes-secret) behind. There is nothing to delete later.

With no inbound rule at all, the path still turned direct quickly. The [security group](glossary:security-group) lets in the replies to packets that went out, and [Tailscale](glossary:tailscale) opens a path by having both sides send UDP first. The [EC2](glossary:ec2) having a public address probably helps too. Compare the path between the school PCs and my devices, which [still goes through the Tokyo relay](/en/blog/hackathon/woowangthon/woowangthon-04-remote-access/#a-relay-not-a-direct-connection).

## 3. Why "connection refused" was good news

The leader → [EC2](glossary:ec2) `:8153` rule had been in the file since November 11 (it is how [part 12](/en/blog/hackathon/woowangthon/woowangthon-12-deploy-executor/)'s deploy executor fetches work from the [GoCD](glossary:gocd) server). On the day the [EC2](glossary:ec2) joined, it went into the admin console, with two more tests, and was saved.

```text
{
	"src": "k3s-leader",
	"accept": ["tag:platform-server:8153"],
	"deny": ["tag:platform-server:22", "operator-desktop:22"],
},
{
	"src": "k3s-w1",
	"deny": ["operator-desktop:22", "operator-laptop:22", "k3s-leader:22", "tag:platform-server:8153"],
},
```

The tests inside the policy only check the rules as text. So after saving, we probed the real paths.

| From → to                                                            | Result                                            |
| -------------------------------------------------------------------- | ------------------------------------------------- |
| leader → [EC2](glossary:ec2) `:8153`                                 | [Connection refused](glossary:connection-refused) |
| [EC2](glossary:ec2) → leader `:6443`                                 | `401`                                             |
| [EC2](glossary:ec2) → leader `:22`, w1 `:22`, w2 `:6443`             | [Timed out](glossary:timeout)                     |
| leader → [EC2](glossary:ec2) `:22`, w1 → [EC2](glossary:ec2) `:8153` | [Timed out](glossary:timeout)                     |

The first row is the title of this post. From the leader, the connection to the [EC2](glossary:ec2)'s 8153 was **[refused](glossary:connection-refused)**. At that moment there was no [GoCD](glossary:gocd) on the [EC2](glossary:ec2) yet. [Refused](glossary:connection-refused) means the packet reached the [EC2](glossary:ec2) and came back with "nothing is listening on that port". The path is open. Every path we had closed, on the other hand, **[timed out](glossary:timeout)**. [Tailscale](glossary:tailscale)'s [access rules](glossary:acl) silently drop what they do not allow.

[Part 8](/en/blog/hackathon/woowangthon/woowangthon-08-image-cache/#6-what-the-reviewer-ai-caught-refused-vs-no-answer)'s lesson, "[refused](glossary:connection-refused) is not the same as no answer", came back here, but with the meaning flipped. In [part 9](/en/blog/hackathon/woowangthon/woowangthon-09-student-space/#5-how-do-you-know-its-blocked)'s student spaces, the network policy ([kube-router](glossary:kube-router)) sent a refusal back. There, [refused](glossary:connection-refused) meant "blocked". On the tailnet, [refused](glossary:connection-refused) means "open", and blocked is no answer. The same refusal can only be read once you know who is doing the blocking. Had the results been written down in two columns, "reaches / doesn't", the first row would have read as a failure.

While writing this post in the evening I probed the same paths again. The [GoCD](glossary:gocd) server came up in between, so 8153 now answers.

## 4. A 401 seen from inside a container

The other way, from the [EC2](glossary:ec2) to the leader API, gave `401`. We called it with no [token](glossary:bearer-token), so [Kubernetes](glossary:kubernetes) sent us back with "who are you". A [401](glossary:http-status-code) means [TLS](glossary:tls) was set up and the API server itself answered, which makes it the best possible answer for a path check.

We saw this **from inside a [Docker](glossary:docker) [container](glossary:container)**, not from the [EC2](glossary:ec2) host. The server runs as a [container](glossary:container). Reaching the leader from the host does not promise the same from a [container](glossary:container). A [container](glossary:container)'s packets pass through [Docker](glossary:docker)'s network once before they leave through the host's [Tailscale](glossary:tailscale).

Two things got in the way. Through [Session Manager](glossary:session-manager) the shell user is `ssm-user`, so [Docker](glossary:docker) needed `sudo`. And when the agent tried to send the [Docker](glossary:docker) command through [Run Command](glossary:run-command), the session's safety classifier blocked it: it counted as sending shell writes to a remote machine. I typed this check into the console's [Session Manager](glossary:session-manager) window myself.

## 5. The server-account checks from the EC2

Part 11's server-account checks called the leader from my desktop with the real [token](glossary:bearer-token). The rights are the same, but the starting point is not. So we ran them once more from the [EC2](glossary:ec2).

The script runs on the [EC2](glossary:ec2). It uses the [instance role](glossary:iam-role) to read the server's settings from [Parameter Store](glossary:aws-systems-manager-parameter-store) (`/wcp/be/K8S_*`: the leader address, CA and [token](glossary:bearer-token), put there in advance on November 11) and calls the leader's tailnet address directly. These are exactly the values the server will use. The [token](glossary:bearer-token) stays in a shell variable and goes to [curl](glossary:curl) on standard input. Every write is a server [dry run](glossary:dry-run), so nothing is left in the cluster.

```bash
api() { # api <token> <method> <path> [body] [content type] -> HTTP status
  printf 'header = "Authorization: Bearer %s"\n' "$1" | curl -s -K - -o /dev/null -m 10 -w '%{http_code}' --cacert "$CA" -H "Content-Type: ${5:-application/json}" -X "$2" ${4:+-d "$4"} "$URL$3"
}
```

This also went through [Run Command](glossary:run-command), and all 18 got the answer we expected.

| Allowed (7)                                                                      | [Refused](glossary:connection-refused) (11)                                 |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Read nodes `200`                                                                 | A space not named `proj-`, a space without labels `422`                     |
| Create a `proj-` space `201`                                                     | Read [Secrets](glossary:kubernetes-secret) in `proj-demo` `403`             |
| Write a [Secret](glossary:kubernetes-secret) whose name ends in `-secrets` `201` | Write a [Secret](glossary:kubernetes-secret) outside `proj-` (`vllm`) `422` |
| Read Pods in `proj-demo` `200`                                                   | Read · stop Pods in `vllm` `403`                                            |
| Read Deployments in `proj-demo` `200`                                            | List all namespaces `403`                                                   |
| Stop `proj-demo` (replicas 0) `200`                                              | Replicas 2 `422`                                                            |
| Read node usage `200`                                                            | Delete `vllm` `422`, wrong [token](glossary:bearer-token) `401`             |

The row to look at is the [Secret](glossary:kubernetes-secret) write outside `proj-`. The answer is `422`, not `403`. The server account holds [Secret](glossary:kubernetes-secret) create rights across the whole cluster ([part 11](/en/blog/hackathon/woowangthon/woowangthon-11-server-link/#2-rbac-cannot-filter-by-name)), so the rights let it through and the [admission](glossary:admission-control) policy stops it. That makes this row proof that the policy is on right now. Run the check on a day the policy is off, and the [dry run](glossary:dry-run) passes with `201` and the check fails. Nothing gets deleted.

We timed it too. Ten node reads averaged about 0.1 s, the slowest 0.29 s. During the measurement the path switched from the Tokyo relay ([DERP](glossary:derp)) to a direct connection. The design doc lists "the relay makes server → leader API calls slow" as a known limit. At least on this day, that worry did not apply.

## 6. A commit missing from a merged PR

The results went into the team repo. The tailnet rule and the path checks went up as [woowangthon/WOOWANGTHON_TEAM_18#154](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/154), and the [EC2](glossary:ec2) check results as one more [commit](glossary:commit) on the same [branch](glossary:branch).

But #154 had already been merged before that [commit](glossary:commit) went up. A [merge](glossary:merge) takes the [branch](glossary:branch) only up to its head at that moment. The later [commit](glossary:commit) stayed on the [branch](glossary:branch) and never reached `main`. The [PR](glossary:pull-request) page already said "Merged", so from the outside everything looked done. The same [commit](glossary:commit) went up separately as [woowangthon/WOOWANGTHON_TEAM_18#155](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/155) and went in 17 minutes after #154's [merge](glossary:merge).

Push every [commit](glossary:commit) before the [merge](glossary:merge). After the [merge](glossary:merge), check that the line is on `main`. Obvious, and still easy to get wrong when work keeps going while a [PR](glossary:pull-request) waits for review.

## 7. The api. address went from 530 to 200

In [part 10](/en/blog/hackathon/woowangthon/woowangthon-10-public-entry/#9-server-addresses-on-the-same-domain) we set the server's address to `api.stairnoworks.com` and made its [tunnel](glossary:cloudflare-tunnel) before the [EC2](glossary:ec2) existed. Until now the address returned `530`. That is Cloudflare saying no connector is attached to the [tunnel](glossary:cloudflare-tunnel), the same number we saw [when we cut the leader's internet](/en/blog/hackathon/woowangthon/woowangthon-10-public-entry/#7-cutting-the-leaders-internet-502-then-530).

Once the connector was up on the [EC2](glossary:ec2) and the server came up, `/api/health` turned `200`. This address's [tunnel](glossary:cloudflare-tunnel) is separate from the one for student apps. The leader's [tunnel](glossary:cloudflare-tunnel) sends visitors to the school, and the [EC2](glossary:ec2)'s [tunnel](glossary:cloudflare-tunnel) sends platform users to the server. Neither opens an inbound port.

## 8. Calling the leader through the server code

Section 5's checks are [curl](glossary:curl). What actually calls the leader is the server code's cluster client module. In the evening we looked at that last. Inside the server [container](glossary:container) (`wcp-be`), we called it in the same order the built server code does. The environment check (`validateEnv`) reads the settings, the client (`K8sClient`) is built, and the read module (`ClusterReader`) makes the calls. The settings are the [container](glossary:container)'s own environment variables.

| Called                            | Result                   |
| --------------------------------- | ------------------------ |
| Node list                         | Three Ready, about 80 ms |
| Deployments in `proj-demo`        | One, `web`, about 20 ms  |
| A space the server did not create | `403`                    |

The last row is [part 11's narrowed reads](/en/blog/hackathon/woowangthon/woowangthon-11-server-link/#4-admission-policies-dont-see-reads) as written. A space without the binding gives `403`, not `404`.

These results came from the second try. The first one failed like this.

```text
SELF_SIGNED_CERT_IN_CHAIN
```

It means the server did not trust the leader's certificate. Reported as is, this would have become "the server's cluster connection has a certificate bug". The cause was on the test side. On the first try the agent skipped `validateEnv` and handed the environment values to the client directly. The leader's CA sits in the environment as one line of [base64](glossary:base64), and decoding it into [PEM](glossary:pem) is `validateEnv`'s job. Given raw [base64](glossary:base64), the client did not recognize the CA and rejected the leader's [self-signed](glossary:self-signed-certificate) certificate chain. Called through the app's own config parsing, it passed right away.

When you test the server, put the way the server reads its settings into the test. A test that skips it measures the test, not the server.

This one, too, was meant to go into [Docker](glossary:docker) through [Run Command](glossary:run-command), was blocked by the classifier as in section 4, and was run in the console's [Session Manager](glossary:session-manager) window in my browser.

Through the server code we have only seen reads, not the real stop, resume and restart calls. Those calls, and the end-to-end deploy test (pressing deploy on the platform and having the leader executor put an app into a student space), went to the [EC2](glossary:ec2) owner. It runs after the AI owner's work is done.
