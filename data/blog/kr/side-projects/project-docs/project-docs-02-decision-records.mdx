## 한 줄 요약

2026년 10월 해커톤(우왕톤) 팀 레포에서 처음으로 ADR을 썼다. 돌아보면 결정마다 이유와 버린 안이 남는 게 괜찮았다. 그런데 내 프로젝트에서는 ADR 폴더를 따로 두지 않고, 결정을 SDD 맨 끝 "설계 근거"에 날짜 붙은 목록으로 넣기로 했다. 범위나 일정 같은 프로젝트 결정은 SPMP에, 요구사항 정책은 SRS에 같은 형식으로 넣는다.

## 1. 우왕톤에서 처음 쓴 ADR

비유하면 회의에서 뭔가를 정할 때마다 쪽지 한 장에 "이렇게 정했다, 이유는 이렇다"를 적어 상자에 넣는 방식이다.

용어로는 **ADR(Architecture Decision Record)**이다. Michael Nygard가 2011년에 제안한 형식으로, 결정 하나를 짧은 파일 하나로 남긴다. 우왕톤 팀 레포에는 2026-10-26 팀원 TaeTaeJin의 첫 PR([#1](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/1))로 `docs/adr/` 폴더가 생겼다. 규칙은 `docs/adr/README.md`에 있었다.

- 되돌리기 비싼 결정만 ADR로 쓴다.
- 한 페이지에 결정 하나.
- 상태는 셋이다: `유효`, `유효 (일부 대체 …)`, `대체됨 (→ NNN)`.
- 색인 표는 따로 없다. 디렉터리 목록이 곧 색인이다.

나도 같은 날 기술 스택 ADR의 "이유" 열을 채우면서 처음 ADR을 써 봤다. 11-03에는 머지된 ADR은 고치지 않고 상태 줄로 일부 대체를 표시하는 규칙([#20](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/20))과 클러스터 ADR 넷([#21](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/21))을 올렸다. 상태 줄만 읽으면 어느 결정이 아직 유효한지 바로 알 수 있다. 이 규칙들은 [Woowangthon 1편의 ADR 규칙](/kr/blog/hackathon/woowangthon/woowangthon-01-docs-and-prs/#4-adr-규칙)에 자세히 있다.

지금 돌아보면 써 본 경험은 괜찮았다. 무엇을 골랐는지만이 아니라 무엇을 버렸는지, 왜 버렸는지가 남는다. 2026-11-28 기준 레포에는 ADR이 18개 있고, 결정이 바뀔 때마다 새 ADR이 옛 ADR을 대체했다.

## 2. 그래도 따로 빼지 않기로

비유하면 쪽지 상자 대신 설계 공책 맨 뒤에 결정 일지 페이지를 두는 것이다. 적는 내용은 같고, 놓는 자리만 다르다.

![결정을 남기는 두 관례: 결정마다 파일 하나인 ADR, SDD 안의 날짜 붙은 설계 근거 목록](/static/images/project-docs-02-decision-records/adr-vs-rationale.svg)

_결정을 남기는 두 관례: 결정마다 파일 하나인 ADR, SDD 안의 날짜 붙은 설계 근거 목록_

용어로는 **design rationale(설계 근거)**이다. IEEE 1016(소프트웨어 설계 기술 표준)은 설계 결정과 그 이유를 SDD 안에 함께 적는다.

내 규칙에는 2026-10-27 정오에 "ADR 폴더나 페이지는 두지 않는다"는 줄이 먼저 들어갔다. 결정과 버린 대안은 SDD 끝 "결정 기록"에 날짜를 붙여 목록으로 쓰고, 본보기는 account.stairno.com의 SDD로 삼았다. 같은 커밋에서 우왕톤용으로 Notion 개인 페이지에 만들었던 ADR 001·002 페이지를 휴지통으로 보내고 그 내용을 결정 기록 목록으로 옮겼다. 그날 내가 왜 그렇게 정했는지 직접 적은 문장은 남아 있지 않다(기록 없음). 기록에 남은 근거는 본보기 SDD가 이미 그 형식이었다는 것뿐이다.

3주 뒤인 2026-11-16 새벽, 이 규칙을 스킬로 옮기면서 결정 기록을 SDD에 넣는 게 관례에 맞는지 확인했다. 확인해 보니 관례가 둘이었다.

| 관례                       | 어디에                    | 단위                  |
| -------------------------- | ------------------------- | --------------------- |
| ADR (Nygard 2011, MADR 등) | `docs/adr/NNNN-<제목>.md` | 결정 하나에 파일 하나 |
| IEEE 1016 design rationale | SDD 안의 절               | 결정 하나에 항목 하나 |

나는 IEEE 쪽을 골랐다. 이유는 하나다. 내 레포에서는 문서가 어차피 절마다 파일 하나로 나뉜다([4편](/kr/blog/side-projects/project-docs/project-docs-04-docs-sync/)). 그러면 설계 근거도 `sdd/11-rationale.md` 한 파일이고(2026-11-28 양식에 절이 하나 늘어 지금 양식에서는 `sdd/12-rationale.md`지만, 그 전에 만든 SDD는 번호를 다시 매기지 않는다), 결정을 찾을 때 파일 하나만 열면 된다. 스킬 첫 커밋에는 이 이유가 한 줄로 적혀 있었는데, 11-20 스킬을 줄이면서 경위 문장을 지울 때 같이 빠졌다. 지금은 규칙만 남아 있다.

ADR 파일 방식을 버린 이유로 우왕톤 경험을 적은 기록은 없다. 2026-11-15 밤부터 16일 새벽까지 이어진 스킬 대화에서 우왕톤과 ADR이 한 문장에 같이 나온 곳은 0곳이다. 다만 바뀐 결정은 고치지 않고 새로 쓴다는 규칙은 우왕톤 ADR README의 규칙과 같은 생각이다.

## 3. 결정이 들어가는 세 자리

비유하면 회의록을 운영 회의, 규칙 회의, 설계 회의로 나눠 각자의 공책 뒤에 붙인 것이다.

![결정이 들어가는 세 자리: SPMP 8 프로젝트 결정, SRS 7 요구사항 정책, SDD 설계 근거](/static/images/project-docs-02-decision-records/decision-homes.svg)

_결정이 들어가는 세 자리: SPMP 8 프로젝트 결정, SRS 7 요구사항 정책, SDD 설계 근거_

용어로는 결정의 **범위(scope)**에 따라 자리가 갈린다. ADR은 이름부터 "아키텍처" 결정이라서, 범위·일정·비용 같은 프로젝트 결정은 원래 ADR이 다루는 대상이 아니다. 그래서 그런 결정은 SPMP로 보냈다.

| 자리                    | 담는 결정                               | coffee-shop 항목 수 |
| ----------------------- | --------------------------------------- | ------------------- |
| SPMP 8 확정 사항과 미결 | 범위, 일정, 비용, 제품, 사업, 진행 방식 | 13                  |
| SRS 7 확정과 미결       | 요구사항 수준 정책, 한도, 뺀 기능       | 따로 안 셈          |
| SDD 설계 근거           | 기술 선택                               | 32                  |

## 4. 항목 하나의 모양

비유하면 결정 일지 한 줄에 날짜, 고른 것, 버린 것, 이유, 누가 정했는지를 빠짐없이 적는 칸이 정해져 있다.

용어로는 항목마다 같은 **스키마**를 쓴다.

```text
- YYYY-MM-DD: <정한 것>. 버린 것: <안> (<진 이유>), <안> (<진 이유>). 이유: <확장성, 유지보수성, 종속성, 테스트 용이성, 비용>. (<누가 정했나>)
```

coffee-shop SDD 설계 근거의 실제 항목 하나다.

```text
- 2026-11-17: 운영 DB는 SQLite를 그대로 쓴다. WAL 모드를 켜고, 하루 한 번 `sqlite3 .backup`으로 백업 파일을 만들어 7개를 남긴다(NFR-25). 버린 것: RDS(비용과 설정이 늘고, 시연 규모에선 동시 쓰기 부하가 작음). 이유: 비용, 종속성. NFR-15 동시 주문 테스트에서 잠금 오류가 나면 다시 정한다. (커피샵 Lead 결정, 팀장 위임)
```

규칙은 다섯 개다.

1. 진지하게 검토한 안은 전부 "버린 것"에 이유와 함께 적는다. 채팅에서 안을 비교했다면 그 비교는 이 항목으로 끝난다.
2. 결정이 바뀌면 옛 항목을 고치지 않는다. 날짜가 붙은 새 항목을 달고, 무엇을 대체하는지 적는다. 우왕톤 ADR의 "머지된 ADR은 고치지 않는다"와 같은 생각이다.
3. 미결 항목에는 무엇이 열려 있는지, 왜 지금 안 정하는지, 언제 다시 볼지를 적는다. 위 항목의 "잠금 오류가 나면 다시 정한다"처럼 다시 열 신호를 쓴다.
4. 이유는 확장성, 유지보수성, 종속성, 테스트 용이성, 비용 같은 말로 쓴다. "익숙해서"는 이유가 아니다.
5. 결정을 내린 그 턴에 쓴다. 나중에 몰아서 쓰지 않는다.

## 5. 정리

| 우왕톤 ADR             | 내 프로젝트                          |
| ---------------------- | ------------------------------------ |
| `docs/adr/` 폴더, 18개 | SDD 설계 근거 한 파일                |
| 결정 하나에 파일 하나  | 결정 하나에 날짜 붙은 항목 하나      |
| 상태 줄로 대체 표시    | 새 항목이 옛 항목을 대체한다고 적음  |
| 아키텍처 결정만        | 프로젝트 결정은 SPMP, 정책은 SRS에도 |

ADR에서 괜찮았던 점, 즉 버린 안과 이유가 남는다는 건 같은 형식으로 남는다. 바꾼 건 자리다. 문서가 이미 절마다 파일로 나뉘어 있으니, 결정만 따로 빼서 폴더를 하나 더 만들 이유가 없었다.
