교재 13~15장 실습이다. 앞부분은 [Kolla-Ansible](glossary:kolla-ansible)로 [OpenStack](glossary:openstack)을 한 노드에 배포하고 [Horizon](glossary:horizon)과 명령행 도구로 [Instance](glossary:instance)를 만드는 실습이고, 뒷부분은 리눅스 [Network namespace](glossary:network-namespace)로 [Container](glossary:container) 네트워크(슬라이드 p67 구성)를 손으로 짜는 실습이다. [OpenStack](glossary:openstack)은 처음에 슬라이드처럼 [Rocky](glossary:rocky-linux) [VM](glossary:vm) 안에 설치하다가 배포를 8번, 6시간 넘게 돌리고 접었다. 그 과정은 [5장](#5-실습-중-생긴-문제)에 따로 정리했다.

# 0. 실습 환경

HW2부터 쓰던 [Ubuntu](glossary:ubuntu) 호스트(Apple M3 맥의 [UTM](glossary:utm) 위 [Ubuntu](glossary:ubuntu) 24.04 [aarch64](glossary:arm64), 메모리 9.7GiB, 6 [vCPU](glossary:vcpu))에서 했다. 호스트가 [aarch64](glossary:arm64)라서 이미지는 전부 [aarch64](glossary:arm64)판을 썼고, 슬라이드와 명령이 달라진 곳은 해당 그림 아래에 적었다.

- **[OpenStack](glossary:openstack)**: [VM](glossary:vm)을 한 단 더 만들지 않고 [Ubuntu](glossary:ubuntu) 호스트에 바로 설치했다. [Rocky](glossary:rocky-linux) [VM](glossary:vm) 안에 설치하면 맥 → [UTM](glossary:utm) → [Ubuntu](glossary:ubuntu) → [KVM](glossary:kvm) → [Rocky](glossary:rocky-linux)의 3단 [Nested virtualization](glossary:nested-virtualization)이 되어 배포가 시간 초과로 끝나지 않았기 때문이다.
- **리눅스 [Container](glossary:container)**: 호스트의 [KVM](glossary:kvm) 위에 [Rocky Linux](glossary:rocky-linux) 10.2 [aarch64](glossary:arm64) [VM](glossary:vm) `lxc.cloud.org`를 만들어 했다.

```text
Ubuntu 호스트 yoosung-vm (enp0s1 192.168.64.4 = 내부 VIP, 대시보드 http://192.168.64.4)
├─ Docker 컨테이너: keystone, glance, nova, neutron, placement, heat, horizon, mariadb, rabbitmq ...
├─ veth1 (neutron_external_interface) ⇄ veth0
├─ 인스턴스(KVM): stackvm-1, stackvm-2, stackvm-3 ── demo-net 10.0.0.0/24
└─ KVM ─ lxc.cloud.org (Rocky 10.2)  ← 네트워크 네임스페이스 실습
```

| 슬라이드                                                                 | 이 환경                                                                                                            |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| x86 PC → VirtualBox → [Rocky Linux](glossary:rocky-linux) (2단)          | M3 맥 → [UTM](glossary:utm) → [Ubuntu](glossary:ubuntu) 호스트에 바로 설치 (2단)                                   |
| 랜카드 2개 enp0s3·enp0s8                                                 | 랜카드 enp0s1 하나 + 외부 네트워크용 [veth](glossary:veth) 쌍 veth0↔veth1                                          |
| [firewalld](glossary:firewalld)·[SELinux](glossary:selinux)·chronyd 설정 | 호스트 [libvirt](glossary:libvirt) 중지, [ufw](glossary:ufw)·timedatectl 확인                                      |
| `dnf install`                                                            | `apt-get install` (같은 패키지의 [Ubuntu](glossary:ubuntu) 이름)                                                   |
| kolla-ansible `stable/2026.1`, rocky 이미지                              | `stable/2026.2`, ubuntu 이미지 + 태그 접미사 `-aarch64`                                                            |
| 내부 [VIP](glossary:virtual-ip) 별도 주소 + [haproxy](glossary:haproxy)  | `enable_haproxy: "no"`, [VIP](glossary:virtual-ip) = 호스트 IP                                                     |
| cirros-0.5.1-x86_64                                                      | cirros-0.5.1-aarch64, [Instance](glossary:instance)용은 커널 인자에 `pci=nomsi`를 넣은 사본                        |
| [Horizon](glossary:horizon) [VNC](glossary:vnc) 콘솔                     | "로그" 탭 ([aarch64](glossary:arm64) [cirros](glossary:cirros)는 [Serial console](glossary:serial-console)로 출력) |
| [Container](glossary:container) 실습 외부 인터페이스 enp0s3 10.0.2.15    | enp1s0 192.168.122.16 ([libvirt](glossary:libvirt) [NAT](glossary:nat))                                            |

# 1. 오픈스택 설치 준비

## 외부 네트워크용 인터페이스

슬라이드는 랜카드 두 개 중 enp0s8을 [neutron](glossary:neutron) 외부 네트워크에 통째로 넘긴다. 이 호스트는 랜카드가 enp0s1 하나뿐이고 이걸 넘기면 호스트 접속이 끊기므로, [NetworkManager](glossary:networkmanager)로 [veth](glossary:veth) 쌍을 만들어 한쪽(veth1)을 외부 인터페이스로 썼다.

```bash
ip -br addr | grep -v vnet
sudo nmcli con add type veth con-name veth0 ifname veth0 veth.peer veth1 ipv4.method disabled ipv6.method disabled
sudo nmcli con add type veth con-name veth1 ifname veth1 veth.peer veth0 ipv4.method disabled ipv6.method disabled
ip -br link show type veth
```

![veth 쌍 생성](/static/images/cloud-computing-hw7-openstack-linux-container/01.webp)

_호스트 인터페이스와 외부 네트워크용 [veth](glossary:veth) 쌍 생성. 슬라이드의 enp0s8 자리를 veth1이 대신함_

## 호스트 준비

[Kolla](glossary:kolla-ansible)는 [libvirt](glossary:libvirt)를 `nova_libvirt` [Container](glossary:container)로 띄우는데, HW6 때 호스트에 깐 [libvirt](glossary:libvirt)가 살아 있으면 prechecks에서 막힌다. 호스트의 [libvirt](glossary:libvirt) 유닛을 전부 끄고, 방화벽과 시간 동기화를 확인했다. 유닛 이름은 glob으로 주면 disable이 안 돼서 하나씩 적었다.

```bash
sudo systemctl disable --now libvirt-guests.service libvirtd.service virtlockd.service virtlogd.service \
  libvirtd-admin.socket libvirtd-ro.socket libvirtd.socket virtlockd-admin.socket virtlockd.socket \
  virtlogd-admin.socket virtlogd.socket
systemctl is-active libvirtd libvirtd.socket virtlogd
sudo ufw status
timedatectl | grep -E 'synchronized|NTP'
```

_호스트의 [libvirt](glossary:libvirt) 서비스 중지, 방화벽 비활성 확인, 시간 동기화 확인. 슬라이드 16~17쪽에 해당_

## globals.yml

슬라이드 대비 바뀐 값은 다섯 개다.

- `kolla_base_distro: "ubuntu"`: 호스트가 [Ubuntu](glossary:ubuntu)라 [Container image](glossary:container-image)도 [Ubuntu](glossary:ubuntu)판을 썼다.
- `network_interface: "enp0s1"`, `neutron_external_interface: "veth1"`
- `enable_haproxy: "no"`, `kolla_internal_vip_address: "192.168.64.4"`: 노드가 하나라 로드밸런서([haproxy](glossary:haproxy)·[keepalived](glossary:keepalived))를 끄고 [VIP](glossary:virtual-ip)를 호스트 IP로 뒀다.
- `openstack_tag_suffix: "-aarch64"`: 기본값 `""`이면 `2026.2-ubuntu-noble` 태그를 받는데, 이 태그에는 [arm64](glossary:arm64) 매니페스트가 없다.

```bash
sed -i -e 's/^#kolla_base_distro:.*/kolla_base_distro: "ubuntu"/' \
  -e 's/^#network_interface:.*/network_interface: "enp0s1"/' \
  -e 's/^#neutron_external_interface:.*/neutron_external_interface: "veth1"/' \
  -e 's/^#\?kolla_internal_vip_address:.*/kolla_internal_vip_address: "192.168.64.4"/' \
  -e 's/^#enable_haproxy:.*/enable_haproxy: "no"/' globals.yml
echo 'openstack_tag_suffix: "-aarch64"' >> globals.yml
```

[Horizon](glossary:horizon)에서 이미지를 업로드하려면 [glance](glossary:glance)가 [Horizon](glossary:horizon) 주소를 [CORS](glossary:cors)로 허용해야 한다.

```ini:/etc/kolla/config/glance.conf
[cors]
allowed_origin = http://192.168.64.4,http://localhost:8080
allow_headers = Content-Type,X-Auth-Token,X-CSRFToken,X-Image-Meta-Checksum,Content-MD5,X-OpenStack-Request-ID
```

![globals.yml](/static/images/cloud-computing-hw7-openstack-linux-container/08.webp)

_globals.yml 설정과 [glance](glossary:glance) [CORS](glossary:cors) 설정. `http://localhost:8080`은 [Horizon](glossary:horizon) 접속 뒤에 추가했다([문제 4](#문제-4-대시보드-이미지-업로드가-cors로-막힘))_

# 5. 실습 중 생긴 문제

## 문제 1. Rocky 가상머신 안 배포가 끝나지 않음

처음에는 슬라이드대로 [Rocky](glossary:rocky-linux) [VM](glossary:vm)(`openstack`, 8GiB, 4 [vCPU](glossary:vcpu))을 만들어 그 안에 all-in-one으로 설치했다. 슬라이드는 x86 PC → VirtualBox → [Rocky](glossary:rocky-linux)의 2단인데, 이 환경에서는 맥 → [UTM](glossary:utm) → [Ubuntu](glossary:ubuntu) → [KVM](glossary:kvm) → [Rocky](glossary:rocky-linux)의 3단 [Nested virtualization](glossary:nested-virtualization)이 된다. 그 위에서 [Kolla](glossary:kolla-ansible)가 [Container](glossary:container) 수십 개를 띄운다.

bootstrap-servers와 prechecks까지는 통과했다. deploy를 시작한 지 37분 뒤 측정값은 이랬다.

| 측정                                                                                          | 값                                    |
| --------------------------------------------------------------------------------------------- | ------------------------------------- |
| [Rocky](glossary:rocky-linux) [load average](glossary:load-average) ([vCPU](glossary:vcpu) 4) | 28~33, [I/O wait](glossary:io-wait) 0 |
| [Ubuntu](glossary:ubuntu) 호스트 [CPU steal](glossary:cpu-steal)                              | 55~59%                                |
| 맥의 [VM](glossary:vm) 프로세스 CPU                                                           | 285%                                  |
| `/bin/true` 50회 실행 ([Ubuntu](glossary:ubuntu) / [Rocky](glossary:rocky-linux))             | 0.013초 / 0.908초 (약 70배)           |
| `python3 -c pass` ([Rocky](glossary:rocky-linux))                                             | 2.9초                                 |

디스크도 네트워크도 아니고, 프로세스를 하나 만들 때마다 세 겹의 가상화를 거치는 비용이 병목이었다. 그다음부터는 [Kolla](glossary:kolla-ansible)의 [timeout](glossary:timeout) 기본값이 하나씩 깨졌다.

| 회차 | 시간        | 결과                                        | 깨진 곳과 조치                                                                                                                                                                                                                               |
| ---- | ----------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 12:29~13:20 | [rabbitmq](glossary:rabbitmq)에서 25분 정지 | 30초마다 도는 [healthcheck](glossary:health-check) `rabbitmq-diagnostics ping`이 끝나지 않고 22개 누적 → `enable_container_healthchecks: "no"`                                                                                               |
| 2    | 13:28~13:55 | 실패(ok=33)                                 | 1차 때 만든 [Container](glossary:container)는 [healthcheck](glossary:health-check) 설정 그대로라 다시 누적, `docker ps` 40초 → `kolla-ansible destroy`(3분 26초)                                                                             |
| 3    | 14:00~14:37 | 실패(ok=204)                                | [keystone](glossary:keystone) bootstrap이 4분 59.8초 만에 rc=1. 같은 명령을 손으로 돌리면 37초에 성공                                                                                                                                        |
| 4    | 14:37~15:43 | 실패(ok=232)                                | `ovs-vsctl -t 5`가 5초 안에 못 끝나 SIGALRM → [openvswitch](glossary:open-vswitch)·ovn-controller 역할에 `timeout: 60`                                                                                                                       |
| 5    | 15:46~16:25 | 실패(ok=287)                                | [nova](glossary:nova) API 503. [keepalived](glossary:keepalived) 상태 검사(2초 간격, 2번 실패면 FAULT)가 제때 안 끝나 49번 FAULT, 그때마다 [VIP](glossary:virtual-ip)가 20~40초씩 빠짐 → interval 10, [timeout](glossary:timeout) 60, fall 6 |

| 7    | 16:56~17:49 | 실패(ok=343)                                | [neutron](glossary:neutron) 재시작 핸들러에서 [Docker API](glossary:docker) ReadTimeout(기본 120초). [load average](glossary:load-average) 128~144, `docker ps -q` 하나에 3분 41초 → `docker_client_timeout: 600`, worker 수 1               |
| 8    | 17:56~18:46 | 중단                                        | 설정이 바뀌어 [Container](glossary:container) 대부분이 재시작 중, [load average](glossary:load-average) 113                                                                                                                                  |

7차에서 ok=343까지 갔으니 몇 번 더 돌리면 배포 자체는 끝났을지도 모른다. 그래도 거기서 멈춘 이유는 두 가지다.

- [Rocky](glossary:rocky-linux) 안에는 `/dev/kvm`이 없어서 [nova](glossary:nova)가 [Instance](glossary:instance)를 [TCG](glossary:tcg)(소프트웨어 에뮬레이션)로 띄워야 한다. 프로세스 생성이 70배 느린 곳에서 그 위에 또 에뮬레이션이면 [Instance](glossary:instance) 실습이 될지 알 수 없었다.
- 과제가 요구하는 건 "[OpenStack](glossary:openstack) 구축 결과"이고, 슬라이드의 [Rocky](glossary:rocky-linux) [VM](glossary:vm)은 구축 수단이다.

그래서 [Rocky](glossary:rocky-linux) [VM](glossary:vm)을 지우고 한 단을 걷어내, [Ubuntu](glossary:ubuntu) 호스트에 바로 설치했다. [Ubuntu](glossary:ubuntu)에는 `/dev/kvm`이 있어서 [nova](glossary:nova)가 [KVM](glossary:kvm)을 그대로 쓴다. 같은 [Kolla](glossary:kolla-ansible) 버전으로 첫 배포가 13분 22초 만에 failed=0으로 끝났다.

남은 교훈은 셋이다.

- [Nested virtualization](glossary:nested-virtualization)이 한 단 늘 때마다 "이 정도면 충분하다"는 [timeout](glossary:timeout) 기본값이 차례로 깨진다. [healthcheck](glossary:health-check) 30초 → `ovs-vsctl` 5초 → [keepalived](glossary:keepalived) 2초 → [Docker API](glossary:docker) 120초 순이었다.
- [Kolla](glossary:kolla-ansible) deploy는 설정이 바뀌지 않은 [Container](glossary:container)를 재시작하지 않는다. 기동 순간에 실패한 서비스(앱을 못 올린 [uwsgi](glossary:uwsgi))는 배포를 다시 돌려도 그대로라 손으로 재시작해야 한다.
- 실패 메시지에는 명령줄이 그대로 찍히고, 그 명령줄에 서비스 비밀번호가 평문으로 들어 있다. 로그는 파일로 받고 화면에는 PLAY RECAP만 띄웠다.

## 문제 2. cirros가 virtio_blk에서 멈춤

[Ubuntu](glossary:ubuntu) 호스트에서 만든 첫 [Instance](glossary:instance)가 부팅 중 `virtio_blk` 메시지 직후 멈췄다. CPU는 100%였고 게스트 시계는 9초에서 더 가지 않았다. [cirros](glossary:cirros) 0.6.3도 같았다.

[HW6](/kr/blog/cs-fundamentals/cloud-computing/cloud-computing-hw6-kvm-live-migration/#kvm에-rocky-가상머신-설치)에서 [Rocky](glossary:rocky-linux) [aarch64](glossary:arm64)를 [KVM](glossary:kvm)에 설치할 때 겪은 [Nested virtualization](glossary:nested-virtualization)의 [MSI](glossary:msi) 인터럽트 문제와 같은 증상이다. 그때처럼 커널 인자에 `pci=nomsi`를 넣으면 [MSI](glossary:msi) 대신 기존 인터럽트 방식을 쓴다. [cirros](glossary:cirros) [aarch64](glossary:arm64)는 [EFI system partition](glossary:efi-system-partition)의 [GRUB](glossary:grub)으로 부팅하므로, 이미지를 복사해 `qemu-nbd`로 블록 장치에 연결하고 [EFI system partition](glossary:efi-system-partition)을 마운트해 `EFI/ubuntu/grub.cfg`의 커널 줄 끝에 `pci=nomsi`를 붙였다.

```bash
modprobe nbd max_part=16
cp /root/cirros-0.5.1-aarch64-disk.img /root/cirros-nomsi.img
qemu-nbd --connect /dev/nbd0 /root/cirros-nomsi.img
lsblk -o NAME,SIZE,FSTYPE,LABEL /dev/nbd0
```

[EFI system partition](glossary:efi-system-partition)(vfat)을 마운트해 `grub.cfg`를 고친 뒤 연결을 끊고, 이미지를 다시 등록했다.

```bash
qemu-nbd --disconnect /dev/nbd0
openstack image delete cirros
openstack image create --disk-format qcow2 --container-format bare --public --file /root/cirros-nomsi.img cirros
```

이 이미지로 바꾸니 60초 안에 로그인 프롬프트가 떴다. [Horizon](glossary:horizon)에서 올린 mycirros도 같은 파일이다.

## 문제 3. prechecks에서 docker·dbus 모듈이 없음

prechecks가 `import docker`, `import dbus` 확인에서 실패했다. [Kolla-Ansible](glossary:kolla-ansible)이 [Python virtual environment](glossary:python-virtual-environment)의 파이썬으로 [Docker](glossary:docker)와 systemd를 다루는데, [Python virtual environment](glossary:python-virtual-environment)에 두 패키지가 없었다. `dbus-python`은 빌드가 필요해서 헤더 패키지를 먼저 깔았다.

```bash
apt-get install -y libdbus-1-dev libglib2.0-dev pkg-config
pip install docker dbus-python
```

## 문제 4. 대시보드 이미지 업로드가 CORS로 막힘

[Horizon](glossary:horizon)에서 mycirros를 올리면 브라우저가 [glance](glossary:glance)로 파일을 직접 보내는데, 그 요청이 [CORS](glossary:cors)로 막혔다. 맥에서 [SSH tunnel](glossary:ssh-tunnel)로 접속해 [origin](glossary:origin)이 `http://localhost:8080`이었고, [glance](glossary:glance)가 허용한 [origin](glossary:origin)은 `http://192.168.64.4`뿐이었다. `glance.conf`의 `allowed_origin`에 터널 주소를 더하고 [glance](glossary:glance)만 다시 설정했다(34초).

```bash
kolla-ansible reconfigure -i ./all-in-one -t glance
```

## 문제 5. VNC 콘솔이 비어 있음

[Horizon](glossary:horizon) "콘솔" 탭에는 "Display output is not active"만 떴다. [aarch64](glossary:arm64) [cirros](glossary:cirros)는 화면([VGA](glossary:vga))이 아니라 시리얼 포트로 출력하기 때문이다. [Horizon](glossary:horizon)에서는 "로그" 탭으로 [Serial console](glossary:serial-console) 출력을 봤고, 콘솔 입력은 `virsh console`로 했다.

# 6. 리눅스 컨테이너 네트워크

[Rocky Linux](glossary:rocky-linux) 10 [VM](glossary:vm)을 복제해 `lxc.cloud.org`를 만들고, 슬라이드 Ch15 [Network namespace](glossary:network-namespace) 실습(29~75쪽)을 따라 p67 그림의 구성을 만들었다. 루트 [Network namespace](glossary:network-namespace)에 [Linux bridge](glossary:linux-bridge) br0(10.0.100.1)를 두고, [Network namespace](glossary:network-namespace) netns1·netns2를 [veth](glossary:veth)로 붙인 뒤, [NAT](glossary:nat)로 외부에 내보내는 구성이다.

```text
루트 네트워크 네임스페이스 (lxc.cloud.org)
 enp1s0 192.168.122.16 ── NAT(masquerade) ── 외부
 br0 10.0.100.1 ─┬─ brif1 ⇄ veth1 10.0.100.101 [netns1]
                 └─ brif2 ⇄ veth2 10.0.100.102 [netns2]
```

## 브리지로 연결

[veth](glossary:veth) 쌍은 두 끝만 잇는다. [Network namespace](glossary:network-namespace)가 늘어나면 루트에 [Linux bridge](glossary:linux-bridge)를 두고 각 [Network namespace](glossary:network-namespace)의 [veth](glossary:veth) 반대편 끝(brif)을 [Linux bridge](glossary:linux-bridge)에 꽂는다.

```bash
ip netns exec netns1 ip link delete veth1
ip link add br0 type bridge
ip link set br0 up
ip link add brif1 type veth peer name veth1
ip link add brif2 type veth peer name veth2
ip link set veth1 netns netns1
ip link set veth2 netns netns2
ip netns exec netns1 ip a add 10.0.100.101/24 dev veth1
ip netns exec netns2 ip a add 10.0.100.102/24 dev veth2
ip netns exec netns1 ip link set dev veth1 up
ip netns exec netns2 ip link set dev veth2 up
```

![br0 생성](/static/images/cloud-computing-hw7-openstack-linux-container/47.webp)

_기존 [veth](glossary:veth) 삭제, [Linux bridge](glossary:linux-bridge) br0 생성·활성화, [veth](glossary:veth) 쌍 brif1–veth1, brif2–veth2 생성_

![LOWERLAYERDOWN](/static/images/cloud-computing-hw7-openstack-linux-container/48.webp)

_veth1·veth2를 각 [Network namespace](glossary:network-namespace)로 옮겨 10.0.100.101/102 할당. 반대편 brif가 꺼져 있어 LOWERLAYERDOWN_

```bash
ip link set brif1 master br0
ip link set brif2 master br0
ip link set dev brif1 up
ip link set dev brif2 up
ip netns exec netns1 ping -c 2 10.0.100.102
```

![brif master](/static/images/cloud-computing-hw7-openstack-linux-container/49.webp)

_br0를 거쳐 netns1 ↔ netns2 [ping](glossary:ping) 성공_

## 루트 네트워크 네임스페이스와 연결

이 상태에서는 [Network namespace](glossary:network-namespace)끼리만 통한다. 루트와 외부로는 경로가 없다.

## NAT로 외부 통신

외부로 나가려면 세 가지가 더 필요하다. [Network namespace](glossary:network-namespace)의 [Default gateway](glossary:default-gateway)를 br0로, 루트의 [IP forwarding](glossary:ip-forwarding), 그리고 10.0.100.0/24 출발지를 enp1s0 주소로 바꾸는 [masquerade](glossary:masquerade)다.

```bash
ip netns exec netns1 ip route add default via 10.0.100.1
ip netns exec netns2 ip route add default via 10.0.100.1
sysctl -w net.ipv4.ip_forward=1
firewall-cmd --permanent --zone=public --add-masquerade
firewall-cmd --permanent --zone=public --add-rich-rule='rule family="ipv4" source address="10.0.100.0/24" masquerade'
firewall-cmd --reload
ip netns exec netns1 ping -c 2 8.8.8.8
```

_루트의 [default gateway](glossary:default-gateway)(192.168.122.1, enp1s0) 확인, netns1·netns2에는 [Default gateway](glossary:default-gateway)가 없음_

![default via br0](/static/images/cloud-computing-hw7-openstack-linux-container/59.webp)

_netns1·netns2에 [default via](glossary:default-gateway) 10.0.100.1(br0) 추가_

_[IP forwarding](glossary:ip-forwarding) 활성화, [firewalld](glossary:firewalld)에 [masquerade](glossary:masquerade)와 10.0.100.0/24 출발지 [masquerade](glossary:masquerade) 규칙 추가 후 reload_

IP로는 나가는데 [DNS](glossary:dns)가 안 된다. `ip netns exec`는 `/etc/netns/<이름>/`에 있는 파일을 그 [Network namespace](glossary:network-namespace)의 `/etc` 위에 겹쳐 보여 주므로, 거기에 `resolv.conf`를 두면 된다.

```bash

echo 'nameserver 8.8.8.8' > /etc/netns/netns2/resolv.conf

```

## Ch14-3. 컨테이너 기반 서비스가 더 효율적인 사례

사례로 Spotify의 [Kubernetes](glossary:kubernetes) 전환을 골랐다. Spotify는 [Container](glossary:container)를 자체 개발한 [Container orchestration](glossary:container-orchestration) 도구 Helios로 운영하다가 [Kubernetes](glossary:kubernetes)로 옮겼다. CNCF 사례 보고서에 따르면 전환 후 [Kubernetes](glossary:kubernetes)의 [bin-packing](glossary:bin-packing)과 [Multi-tenancy](glossary:multi-tenancy) 덕분에 CPU 사용률이 평균 2~3배 높아졌고, 새 서비스를 만들어 배포 가능한 용량을 잡는 데 걸리던 시간이 거의 한 시간에서 몇 초~몇 분으로 줄었다. 같은 일을 [VM](glossary:vm) 단위로 했다면 서비스마다 OS 한 벌을 띄워야 해서 이 정도 밀도와 속도가 나오지 않는다.

[Container](glossary:container) 기반이 더 좋은 이유는 네 가지다.

- **밀도(자원 효율)**: [Container](glossary:container)는 호스트 커널을 공유하고 프로세스 단위로 격리([Network namespace](glossary:network-namespace))·제한([cgroup](glossary:cgroup))만 하므로, [VM](glossary:vm)처럼 게스트 OS의 커널·메모리·부팅 디스크를 서비스마다 따로 두지 않는다. 그래서 한 노드에 더 많은 서비스를 빽빽하게 배치([bin-packing](glossary:bin-packing))할 수 있고, Spotify의 CPU 사용률 2~3배 향상이 이 효과다.
- **성능 오버헤드**: IBM Research의 Felter 등(2015)은 같은 하드웨어에서 [KVM](glossary:kvm) [VM](glossary:vm)과 [Docker](glossary:docker) [Container](glossary:container)를 비교해, [Container](glossary:container)가 거의 모든 측정에서 [VM](glossary:vm)과 같거나 더 나은 성능을 냈다고 보고했다. [VM](glossary:vm)은 I/O가 [Hypervisor](glossary:hypervisor)를 한 번 더 거치기 때문이며, I/O 집약적인 작업에서는 둘 다 튜닝이 필요하다고 덧붙였다.
- **시작 시간과 배포 속도**: [Container](glossary:container)는 OS 부팅 없이 프로세스를 띄우므로 초 단위로 시작된다. [Microservices](glossary:microservices)가 수백 개인 서비스에서는 배포·확장·롤백이 잦은데, 이 속도가 Spotify의 서비스 생성 시간 단축으로 이어졌다.
- **이식성과 일관성**: 애플리케이션과 라이브러리를 [Container image](glossary:container-image)[Container image](glossary:container-image) 하나로 묶어 개발·테스트·운영 환경에서 같은 [Container image](glossary:container-image)를 쓴다. [VM](glossary:vm) 이미지보다 작아 [Container registry](glossary:container-registry)에서 내려받고 버전을 관리하기 쉽다.

다만 [Container](glossary:container)는 커널을 공유하므로 격리 수준이 [VM](glossary:vm)보다 낮다. 서로 신뢰할 수 없는 사용자를 한 호스트에 올리거나 다른 OS 커널이 필요한 경우에는 [VM](glossary:vm)이 낫고, 그래서 실제로는 [VM](glossary:vm) 위에 [Container](glossary:container)를 올리는 구성이 흔하다.

- CNCF, "Spotify Case Study," 2019. https://www.cncf.io/case-studies/spotify/
- W. Felter, A. Ferreira, R. Rajamony, J. Rubio, "An Updated Performance Comparison of Virtual Machines and Linux Containers," IEEE ISPASS 2015, pp. 171–172.

## Ch15-9. 그림 15.12와 같은 네트워크 환경 구성

6장에서 만든 구성(br0 + netns1·netns2 + [NAT](glossary:nat))에 세 번째 [Network namespace](glossary:network-namespace) netns3를 같은 방식으로 붙였다.

```bash
ip netns add netns3
ip link add brif3 type veth peer name veth3
ip link set veth3 netns netns3
ip netns exec netns3 ip a add 10.0.100.103/24 dev veth3
ip netns exec netns3 ip link set dev veth3 up
ip link set brif3 master br0
ip link set dev brif3 up
ip netns exec netns3 ip route add 192.168.122.0/24 dev veth3
ip netns exec netns3 ip route add default via 10.0.100.1
mkdir -p /etc/netns/netns3; echo 'nameserver 8.8.8.8' > /etc/netns/netns3/resolv.conf
```

_[Network namespace](glossary:network-namespace) netns1·netns2·netns3와 br0에 연결된 brif1·brif2·brif3_

