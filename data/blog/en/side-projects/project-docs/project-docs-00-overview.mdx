## 0. Introduction

When I start a new project, I write six documents in the same format. Half a year ago, when I built this blog, I only had a [DB schema](glossary:database-schema), an [API spec](glossary:api-specification), and a page structure document, and I thought that was enough. But as assignments and projects piled up, I kept needing a place for requirements, decision reasons, tests, and deployment procedures, and the section layout and names changed every time I wrote a document. This post traces how the template reached its current shape, using [git](glossary:git) [commits](glossary:commit) of the rule files, the worklog kept for each project, the memory change log, and the session logs from the days decisions were made. Decisions whose reasons are written down nowhere are marked "not recorded".

In restaurant terms, a shop that ran on a few menu cards ended up with one form per step as customers and staff grew: a business plan, an order slip, a recipe, an inspection sheet, an opening procedure, and a maintenance log, where each step needs a stamp from the previous one before work moves on. The business plan is the [SPMP](glossary:spmp), the order slip is the [SRS](glossary:srs), the recipe is the [SDD](glossary:sdd), the inspection sheet is the [STP](glossary:stp), the opening procedure is the [SIP](glossary:sip), the maintenance log is the [SMP](glossary:smp), and the stamp rule is the [stage gate](glossary:stage-gate). Below I cover how twelve documents became six templates, why I attached standards and chose a place for [decision records](glossary:decision-record), and the one-day migration of coffee-shop.

## 1. The first twelve documents

The first docs [commit](glossary:commit) in this repo on 2026-05-08 (`a156d2a`) added 12 files, 724 lines: page definitions (56 lines), [DB schema](glossary:database-schema) (67; the first line is "a [static site](glossary:static-site) with no DB"), [API spec](glossary:api-specification) (45), component structure (193), architecture (87), export function names (79), design (16), and the agent-facing [runbook](glossary:runbook), done conditions, and `CLAUDE.md`. All of them are [design artifacts](glossary:design-artifact) that cover only "what to build and how". There was nothing on what the system must do (requirements), why it was built that way (decision reasons), or how to check it (test plan). For one static blog, this was enough.

## 3. Fitting conventions and standards

![A standard for each document: SPMP is IEEE 16326, SRS is 29148, SDD is 1016, STP is 29119-3, SIP is MIL-STD-498, SMP is 14764](/static/images/project-docs-03-standards/standards-map.svg)

_A standard for each document: SPMP is IEEE 16326, SRS is 29148, SDD is 1016, STP is 29119-3, SIP is MIL-STD-498, SMP is 14764_

Until then, my document names were ones I had made up (`plan/`, `experiments/`, `test-deploy.md`). When I started writing the [skill](glossary:skill) on the night of 2026-11-15, I drew on the four model documents and the [IEEE](glossary:ieee) standards together. A few hours later, early on 11-16, I decided to switch names and notation to convention. A convention is a practice the industry widely uses without an official document (a [de facto standard](glossary:de-facto-standard)); a standard is a document an organization such as [IEEE](glossary:ieee) or [ISO](glossary:iso) published under a number. Names and notation are convention; the section layout of a document comes from the standard.

There were two reasons. A convention probably exists for a reason, and I would only find out what is good about it by writing by convention once. So this was an experiment, not a conviction: only documents started from now on follow it, and projects I had already worked on stay as they are (the [skill](glossary:skill) says "Projects started before 2026-11-16 keep their original structure and names"). There is no record of weighing the concrete benefits of standards for submission or collaboration (not recorded).

One section exists because of a standard. The model [SRS](glossary:srs) had no "assumptions, constraints, dependencies" section, but 29148 does, so it became [SRS](glossary:srs) section 1.4. On 2026-11-17 I turned 29148's [singular](glossary:singular-requirement) principle into a rule: one [functional requirement](glossary:functional-requirement) carries one function (view and edit, add and delete are separate [FRs](glossary:functional-requirement)), and one [non-functional requirement](glossary:non-functional-requirement) carries one measurable condition, so the [SRS](glossary:srs) verification column checks one thing. The reason for choosing [MIL-STD-498](glossary:mil-std-498) for the [SIP](glossary:sip) is not recorded; I accepted the option as it was proposed in a table when making the [skill](glossary:skill).

## 4. Fixing the template up front

A standard fixes the section layout but not the table columns or file names. If the [agent](glossary:ai-coding-agent) invented those for each document, projects would drift apart. So the day I made the [skill](glossary:skill), I put a 54-file set of templates into `TEMPLATES.md`. File names are English [kebab-case](glossary:kebab-case) with the section number first. New files always start from the template, so any project has the same thing in the same place.

```text
docs/specs/srs/
├── README.md
├── 1-overview.md
├── 2-domain.md
├── 3-functional/
│   └── 1-<area>.md
├── 4-nonfunctional.md
├── 5-use-cases.md
├── 6-interfaces.md
└── 7-decisions.md
```

The source of the templates is the `project-docs` [skill](glossary:skill) in my personal settings repo (private). A [skill](glossary:skill) is an instruction file an [AI coding agent](glossary:ai-coding-agent) opens only for a specific task; [how skills are loaded](/en/blog/side-projects/devblog/devblog-04-agent-environment/#3-pulling-out-what-is-needed) is covered in DevBlog part 4. `TEMPLATES.md` in the [skill](glossary:skill) is the file-level template, and the six Docs in the [Google Drive](glossary:google-drive) [\_templates folder](https://drive.google.com/drive/folders/1IGzofOw3S0r05xmIvWutLiGDJcKNEoIG) are that template moved into [Google Docs](glossary:google-docs) (written in Korean; anyone with the link can view). ## 5. Decision records inside the SDD

![Two conventions for recording decisions: ADRs with one file per decision, and a dated design rationale list inside the SDD](/static/images/project-docs-02-decision-records/adr-vs-rationale.svg)

_Two conventions for recording decisions: ADRs with one file per decision, and a dated design rationale list inside the SDD_

On 2026-10-26, the Woowangthon team repo got a `docs/adr/` folder from teammate TaeTaeJin's first [PR](glossary:pull-request) ([#1](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/1)). An [ADR](glossary:adr) (Michael Nygard, 2011) keeps one decision as one short file. The rules: only decisions that are expensive to reverse, one decision per page, and three statuses (`유효` valid, `유효 (일부 대체 …)` valid but partly superseded, `대체됨 (→ NNN)` superseded). That same day I filled in the "reason" column of the tech stack [ADR](glossary:adr), and on 11-03 I posted a rule that merged [ADRs](glossary:adr) are not edited and supersession is marked with a status line ([#20](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/20)), plus four cluster [ADRs](glossary:adr) ([#21](https://github.com/woowangthon/WOOWANGTHON_TEAM_18/pull/21)). The details are in [the ADR rules in Woowangthon part 1](/en/blog/hackathon/woowangthon/woowangthon-01-docs-and-prs/#4-adr-rules). What stayed with me was that not only the choice but also the rejected options and their reasons remain; as of 2026-11-28 there are 18 [ADRs](glossary:adr).

Still, I decided not to keep an [ADR](glossary:adr) folder in my own projects. On 2026-10-27 at noon, the line "no [ADR](glossary:adr) folder or page" went into my rules first, with decisions and rejected alternatives written as a dated list at the end of the [SDD](glossary:sdd). In the same [commit](glossary:commit) I moved the [ADR](glossary:adr) 001 and 002 pages I had made in [Notion](glossary:notion) for Woowangthon to the trash and moved their content into that list. No sentence explaining why I decided this survives (not recorded); the only trace is that the model [SDD](glossary:sdd) was already in that format.

Three weeks later, early on 2026-11-16, when moving this rule into the [skill](glossary:skill), I found there are two conventions. An [ADR](glossary:adr) (including [MADR](glossary:madr)) is one file per decision at `docs/adr/NNNN-<title>.md`; [IEEE 1016](glossary:ieee-1016) [design rationale](glossary:design-rationale) is one entry per decision in a section inside the [SDD](glossary:sdd). I chose the [IEEE](glossary:ieee) side. In my repos, documents are split into one file per section anyway ([Project Docs 4](/en/blog/side-projects/project-docs/project-docs-04-docs-sync/)), so [design rationale](glossary:design-rationale) is also a single file, `sdd/11-rationale.md`, and finding a decision means opening one file (a section was added on 2026-11-28, so the current template has `sdd/12-rationale.md`, but SDDs made earlier are not renumbered). That reason was one line in the [skill](glossary:skill)'s first [commit](glossary:commit) and was dropped on 11-20 when I trimmed the [skill](glossary:skill). There is no record naming the Woowangthon experience as a reason for dropping [ADR](glossary:adr) files. Still, the rule that a changed decision is written anew rather than edited is the same idea as in the Woowangthon [ADR](glossary:adr) README.

Decisions go to three places by scope. [ADR](glossary:adr) is by name about architecture decisions, so project decisions such as scope, schedule, and cost went to the [SPMP](glossary:spmp).

| Place                                                             | Decisions it holds                                       | coffee-shop entries |
| ----------------------------------------------------------------- | -------------------------------------------------------- | ------------------- |
| [SPMP](glossary:spmp) 8 Decided and open items                    | Scope, schedule, cost, product, business, way of working | 13                  |
| [SRS](glossary:srs) 7 Decided and open                            | Requirement-level policies, limits, dropped features     | Not counted         |
| [SDD](glossary:sdd) [design rationale](glossary:design-rationale) | Technology choices                                       | 32                  |

Every entry has the same shape.

```text
- YYYY-MM-DD: <what was decided>. Rejected: <option> (<why it lost>), <option> (<why it lost>). Reason: <scalability, maintainability, dependencies, testability, cost>. (<who decided>)
```

A real entry from the coffee-shop [SDD](glossary:sdd):

```text
- 2026-11-17: Keep SQLite as the production DB. Turn on WAL mode and make a backup file once a day with `sqlite3 .backup`, keeping 7 (NFR-25). Rejected: RDS (more cost and setup, and concurrent write load is small at demo scale). Reason: cost, dependencies. Revisit if the NFR-15 concurrent order test hits a lock error. (decided by the coffee-shop lead session, delegated by the team leader)
```

Its terms: [SQLite](glossary:sqlite), [WAL](glossary:wal), [backup](glossary:backup), [RDS](glossary:amazon-rds), [NFR](glossary:non-functional-requirement). There are five rules.

1. Every option seriously considered goes under "Rejected" with its reason. If options were compared in chat, that comparison ends in this entry.
2. When a decision changes, the old entry is not edited. A new dated entry states what it supersedes.
3. Open items record what is open, why it is not decided now, and the signal or date to look again.
4. Reasons are written as scalability, maintainability, dependencies, testability, and cost. "Because I'm used to it" is not a reason.
5. Write it in the turn the decision is made. Don't batch them up later.

Writing the [SRS](glossary:srs) first is a rule, because the [requirement IDs](glossary:requirement-id) are the keys that connect the other documents. The rewritten [SRS](glossary:srs) held 24 [domain requirements](glossary:domain-requirement), 57 [functional requirements](glossary:functional-requirement), 35 [non-functional requirements](glossary:non-functional-requirement), and 14 [use cases](glossary:use-case), and the [SDD](glossary:sdd) was written with these numbers attached. The reason for deleting the old documents, given in one line in #68: the stage documents replace the old files, and [git](glossary:git) history keeps them. So the new documents have no lines like "see draft no. N" and nothing points to `docs/old/`, and deleting it breaks no links. The same day this order became the [skill](glossary:skill)'s migration rule.

Early on 2026-11-28 the template was revised after two pieces of [feedback from the professor](/en/blog/side-projects/coffee-shop/coffee-shop-00-overview/#professor-feedback-129-130) on the coffee-shop [SDD](glossary:sdd): the parts in the [wireframes](glossary:wireframe) had no numbers, and the class and method specs were mixed in with the [component design](glossary:component-design).

- **Screen part IDs**: every UI part gets an ID like `SCR-01-01`, and the [wireframes](glossary:wireframe) show the same ID. Section numbers can shift, but IDs don't.
- **Class and module spec section**: one file per module records each public function's [signature](glossary:function-signature), return values and exceptions, and [requirement IDs](glossary:requirement-id), and once written it is checked by script against the list of `def` and `class` in the code.

In coffee-shop this went in through [#129](https://github.com/seren-wib/coffee-shop/pull/129) (+1,059 / −50) and [#130](https://github.com/seren-wib/coffee-shop/pull/130). A repo that already has an [SDD](glossary:sdd) gets the new section at the end, so the class spec is section 12 and [design rationale](glossary:design-rationale) stays at section 11.

## 7. How I use it now

Documents work as a [stage gate](glossary:stage-gate): the next stage starts only after each stage document is finalized, and code is written only after the [SRS](glossary:srs) and [SDD](glossary:sdd) are finalized. Implementation follows [TDD](glossary:tdd).

1. Pick which documents to write. For a small tool or a [static site](glossary:static-site), the plan and [SRS](glossary:srs) are merged into one document and the API and DB sections say "not applicable". With login, payment, or a DB, all six are written.
2. Requirements come from an interview. Even in a personal project, I play the client and the [agent](glossary:ai-coding-agent) asks the questions.
3. After copying the template, I write the first word. The repo's `docs/specs/<document>/` is the source, and [Google Docs](glossary:google-docs) is a one-way copy.

Requirement numbers (`FR-12`) are the keys that test names, [PR](glossary:pull-request) descriptions, and the [SDD](glossary:sdd)'s feature subsections use to point at each other. To find one, I open just that line with `grep -rn "FR-12" docs/specs`; the [grep](glossary:grep) result is the trace from requirement to design to test.

This template is used for projects started or migrated on or after 2026-11-16. coffee-shop ([coffee-shop series](/en/blog/side-projects/coffee-shop/coffee-shop-00-overview/)) was the first one moved, and design-system and open-calls (private repos) use it since 11-19. account.stairno.com was the model, but its documents predate the template, so it still has the old structure.

## 8. Reflection

My first idea wasn't wrong: a [schema](glossary:schema) and an [API spec](glossary:api-specification) were enough for one static blog, but once people grew, decisions piled up, and deployment and operations came in, documents that only said "what to build" could not answer "why was it built this way" or "how do we check it".
