## 0. Introduction

> Part 6 of the series. Build stage 4: bringing up the [cluster](glossary:kubernetes-cluster). [Node](glossary:kubernetes-node) prep is in [part 5](/en/blog/hackathon/woowangthon/woowangthon-05-node-prep/), and the big picture is in [Woowangthon 0](/en/blog/hackathon/woowangthon/woowangthon-00-overview/).

Build stage 4 is about tying three PCs into one [cluster](glossary:kubernetes-cluster). Installing [k3s](glossary:k3s) is one command, and what took time came after. Our PCs carry both the school address and the [node](glossary:kubernetes-node) address on one [LAN card](glossary:nic), and the school address comes **first**. [Kubernetes](glossary:kubernetes) parts use the first address unless told otherwise, and the [firewall](glossary:firewall) drops anything that comes from a school address. Two of the three things that got stuck in this stage came from that. The third was about the order in which the [firewall](glossary:firewall) and [Kubernetes](glossary:kubernetes) lay down their rules.

In restaurant terms, three kitchens exchange order slips to run as one restaurant, but each kitchen has two street numbers and the slip always carries the one written first as the sender. The bouncer at the door turns back any slip from that number. The kitchens are [nodes](glossary:kubernetes-node), the order slips are [packets](glossary:packet), the number written first is the [LAN card](glossary:nic)'s first address (the school address), and the bouncer is the [firewall](glossary:firewall).

In this post I put the [k3s](glossary:k3s) options in a config file and installed, moved [flannel](glossary:flannel) to host-gw, turned off [ServiceLB](glossary:servicelb), started [CoreDNS](glossary:coredns) myself on both [workers](glossary:worker-node), and then measured the reboot and the [NotReady](glossary:node) judgment time.

## 1. What I fixed before installing

You can install [k3s](glossary:k3s) with options on the install script, but I put the options in a config file (`/etc/rancher/k3s/config.yaml`) and pinned only the version at install time. Rebuilding the same [cluster](glossary:kubernetes-cluster) then doesn't mean digging through shell history, and changing an option is just editing the file and restarting. The same files are in the repo (`Infra/k3s/server.yaml`, `agent.yaml`).

```bash
curl -sfL https://get.k3s.io | INSTALL_K3S_VERSION=v1.37.2+k3s1 sh -s - server
```

| Option                                                       | Why                                                                                                                                                                                                     |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pinned version `v1.37.2+k3s1`                                | A rebuild has to produce the same thing                                                                                                                                                                 |
| Embedded [etcd](glossary:etcd) (`cluster-init`)              | There is one server, but this keeps the option to restore the leader from a [snapshot](glossary:snapshot) later. One install option, no cost                                                            |
| [Node](glossary:kubernetes-node) address (`node-ip`)         | Otherwise it grabs the school address                                                                                                                                                                   |
| Packaged [CoreDNS](glossary:coredns) off                     | It runs one [replica](glossary:replica) that can land on the leader, and [k3s](glossary:k3s) resets it on every start so it can't be edited. We run our own (section 5)                                 |
| [ServiceLB](glossary:servicelb) off                          | It goes around the [firewall](glossary:firewall) (section 3)                                                                                                                                            |
| [Secret](glossary:kubernetes-secret) encryption              | Turning it on later means a restart and re-encrypting existing [Secrets](glossary:kubernetes-secret). At install it is one option                                                                       |
| [Taint](glossary:taint) on the leader                        | Keeps student apps off the leader, from the moment of install                                                                                                                                           |
| 30-second wait after a [node](glossary:kubernetes-node) dies | With the default 5 minutes, a dead [worker](glossary:worker-node) means student apps stay down for 5 minutes. Set once on the [API server](glossary:kubernetes-api-server), not per [Pod](glossary:pod) |

The tool that lets [containers](glossary:container) use the leader's [GPU](glossary:gpu) ([nvidia-container-toolkit](glossary:nvidia-container-toolkit)) was planned to go in before [k3s](glossary:k3s). Installed first, [k3s](glossary:k3s) picks up the [GPU](glossary:gpu) runtime by itself. It turned out to be on the PC already as we received it, and [k3s](glossary:k3s) picked it up.

Every change again ran under [the revert from part 5](/en/blog/hackathon/woowangthon/woowangthon-05-node-prep/#3-put-the-undo-in-place-before-it-breaks). This time it was "stop [k3s](glossary:k3s) entirely in 300 seconds". [k3s](glossary:k3s) adds a lot of [firewall](glossary:firewall) rules, and if they block remote access, stopping [k3s](glossary:k3s) is enough to clear them.

## 2. flannel grabbed the school address

What [the design doc review flagged](/en/blog/hackathon/woowangthon/woowangthon-05-node-prep/#7-what-the-design-doc-review-caught) at the end of part 5 happened exactly. [flannel](glossary:flannel) is the [k3s](glossary:k3s) part that lays down paths so [Pods](glossary:pod) on different [nodes](glossary:kubernetes-node) can talk. After installing the leader, the address [flannel](glossary:flannel) had recorded for this [node](glossary:kubernetes-node) was the school address.

The fix from the review was `--flannel-iface=enp4s0`, which names the [LAN card](glossary:nic) to use. But that **only picks the card**. The address is the card's first address, and our card's first address is the school one.

Next I added the options that announce the [node](glossary:kubernetes-node) address separately as an "external address" (`node-external-ip`, `flannel-external-ip`). The recorded address changed to the [node](glossary:kubernetes-node) address. But when I opened the device that actually wraps and sends the [packets](glossary:packet) (`flannel.1`), its sending address was still the school address.

```bash
ip -d link show flannel.1
```

[flannel](glossary:flannel)'s default mode is [VXLAN](glossary:vxlan). It wraps each [Pod](glossary:pod) [packet](glossary:packet) in an outer [packet](glossary:packet) and sends it to the other [node](glossary:kubernetes-node), and the outer [packet](glossary:packet)'s source is the card's first address. The receiving [firewall](glossary:firewall) [filters by source since part 5](/en/blog/hackathon/woowangthon/woowangthon-05-node-prep/#6-firewall-inbound-by-source-outbound-by-port), so it drops [packets](glossary:packet) from a school address. This version of [k3s](glossary:k3s) had no option to choose the outer [packet](glossary:packet)'s source.

So I dropped the wrapping. host-gw mode wraps nothing and only lays a route on each [node](glossary:kubernetes-node): "this [Pod](glossary:pod) range goes to that [node](glossary:kubernetes-node)". It only works when the [nodes](glossary:kubernetes-node) share one [switch](glossary:switch), which is exactly our setup.

```yaml:/etc/rancher/k3s/config.yaml (leader, excerpt)
node-ip: 192.168.77.11
flannel-iface: enp4s0
flannel-backend: host-gw
node-external-ip: 192.168.77.11
flannel-external-ip: true
```

After the change, each [node](glossary:kubernetes-node)'s [routing table](glossary:routing-table) had `10.42.N.0/24 via 192.168.77.x`. The next hop is a [node](glossary:kubernetes-node) address, so it passes the [firewall](glossary:firewall). Without the wrapping step it is lighter, if anything.

## 3. Closing ServiceLB and NodePort

Going over the plan again before installing, one thing stood out. [k3s](glossary:k3s) ships with a feature called [ServiceLB](glossary:servicelb) that opens [ports](glossary:port) 80/443 on every [node](glossary:kubernetes-node) and hands them straight to [Traefik](glossary:traefik) (the entrance that takes outside requests and routes them to student apps).

The problem is that [ports](glossary:port) opened this way never go through the [firewall](glossary:firewall)'s "inbound" check. The Linux [firewall](glossary:firewall) checks [packets](glossary:packet) in three places: what comes into this PC ([INPUT](glossary:iptables)), what leaves this PC ([OUTPUT](glossary:iptables)), and what passes through this PC to somewhere else ([FORWARD](glossary:iptables)). [ServiceLB](glossary:servicelb) rewrites an incoming [packet](glossary:packet)'s destination to a [Pod](glossary:pod) address ([DNAT](glossary:dnat)), and then the [packet](glossary:packet) goes through [FORWARD](glossary:iptables), not [INPUT](glossary:iptables). What part 5 blocked was [INPUT](glossary:iptables). Left as is, any PC on the school network could reach our 80/443.

I turned [ServiceLB](glossary:servicelb) off. Visitors reach [Traefik](glossary:traefik) from **inside** the [cluster](glossary:kubernetes-cluster) through the [Cloudflare tunnel](/en/blog/hackathon/woowangthon/woowangthon-05-node-prep/#1-the-last-site-checks), so the PCs don't need 80/443. [NodePort](glossary:nodeport) (which opens a [Service](glossary:kubernetes-service) on a 30000-range [port](glossary:port) on every [node](glossary:kubernetes-node)) takes the same path, so I bound it to the [node](glossary:kubernetes-node) network only.

```yaml
disable:
  - coredns
  - servicelb
kube-proxy-arg:
  - nodeport-addresses=192.168.77.0/24
```

## 4. A new Pod's first packet went missing

With both [workers](glossary:worker-node) joined, I put test [Pods](glossary:pod) on different [workers](glossary:worker-node) and had them talk. It worked, but right after a new [Pod](glossary:pod) started, the first connection came up about a second late. The [firewall](glossary:firewall) log showed the [Pod](glossary:pod)'s first [packet](glossary:packet) being dropped.

It was about order. A [packet](glossary:packet) going through [FORWARD](glossary:iptables) passes several rule sets in turn. First is [kube-router](glossary:kube-router), which enforces [NetworkPolicy](glossary:networkpolicy) (the [firewall](glossary:firewall) between [Pods](glossary:pod)), then [Kubernetes](glossary:kubernetes), [Docker](glossary:docker) and [Tailscale](glossary:tailscale), and then [ufw](glossary:ufw). [kube-router](glossary:kube-router) takes a little over a second to lay down the pass rule for a new [Pod](glossary:pod). A first [packet](glossary:packet) sent in that window gets no verdict from [kube-router](glossary:kube-router), falls through to [ufw](glossary:ufw), and hits [ufw](glossary:ufw)'s "default deny for routed traffic". The [packet](glossary:packet) resent a second later gets through.

A second sounds tolerable, but every reboot costs dozens of [Pods](glossary:pod) the same delay. I let the [Pod](glossary:pod) range through [ufw](glossary:ufw).

```bash
sudo ufw route allow from 10.42.0.0/16
sudo ufw route allow to 10.42.0.0/16
```

Doesn't that open everything between [Pods](glossary:pod)? No, because [NetworkPolicy](glossary:networkpolicy) runs **before** [ufw](glossary:ufw). I applied a policy that blocks inbound traffic and saw it refused, then removed the policy and saw it work again. Walling student spaces off from each other is done with these policies in the next stage.

Adding these rules tripped me once more. I gave a rule a comment with the words `in` and `out` in it, and [ufw](glossary:ufw) read those words inside the comment as direction keywords and rejected the rule as a bad interface clause. I took the words out of the comment.

## 5. CoreDNS on both workers

[CoreDNS](glossary:coredns) is the [DNS](glossary:dns) server inside the [cluster](glossary:kubernetes-cluster): a [Pod](glossary:pod) asks for a name and gets an address. The packaged one runs a single copy, and it can land on the leader. If the leader goes down, student apps running fine on the [workers](glossary:worker-node) can't look up their DB by name and stop too. I turned off the [k3s](glossary:k3s) one, took the [manifest](glossary:manifest) of the same version, edited it and ran it myself.

- 2 [replicas](glossary:replica)
- Only on [workers](glossary:worker-node) with the student [label](glossary:kubernetes-label)
- Never two on one [node](glossary:kubernetes-node) (one per [worker](glossary:worker-node))

The [Pods](glossary:pod) then sat in `ContainerCreating`. The config bundle ([ConfigMap](glossary:configmap)) needed an entry called `NodeHosts`, and it was empty. It is the list of [node](glossary:kubernetes-node) names and addresses, and [k3s](glossary:k3s) fills it only while its own [CoreDNS](glossary:coredns) is on. I wrote the three [nodes](glossary:kubernetes-node) into it and the [Pods](glossary:pod) came up.

## 6. One worker's download stalled

On [worker](glossary:worker-node) 2, the [k3s](glossary:k3s) binary download stalled. One GitHub release server address never answered the start of the connection, and a file of a few hundred bytes took more than 10 seconds. It was the school network, so there was no telling whether waiting would help.

The leader already had the same binary. I streamed it from the leader to [worker](glossary:worker-node) 2 over [SSH](glossary:ssh) by way of my home desktop, matched it against the official hash ([sha256](glossary:sha-256)), and installed with the option that skips the download.

To join the [cluster](glossary:kubernetes-cluster), a [worker](glossary:worker-node) needs the [join token](glossary:join-token) the leader created. That too went straight over [SSH](glossary:ssh) from the leader into a file on the [worker](glossary:worker-node) (`/etc/rancher/k3s/token`, mode 600). It never shows up on screen, in the repo, or in chat.

## 8. Reboot test

The next day I rebooted [worker](glossary:worker-node) 1, [worker](glossary:worker-node) 2 and the leader remotely, one at a time. I scheduled the reboot 2 seconds out so the [SSH](glossary:ssh) call could return first.

All three came back in 35–45 seconds with nobody logged in, with [k3s](glossary:k3s), the [firewall](glossary:firewall) (including the rules from section 4), [node](glossary:kubernetes-node) addresses and [Pod](glossary:pod) routes intact. After the leader reboot, all three [nodes](glossary:kubernetes-node) were Ready together.

### NotReady takes 50 seconds, not 40

But rebooting didn't give me the number I wanted: when student apps move to another [worker](glossary:worker-node) after one goes down. A while after the leader loses contact with a [worker](glossary:worker-node), it marks that [node](glossary:kubernetes-node) [NotReady](glossary:node), then waits the 30 seconds from section 1 before moving its [Pods](glossary:pod). A reboot is shorter than that judgment, so the leader never marked a [worker](glossary:worker-node) [NotReady](glossary:node). [CoreDNS](glossary:coredns) didn't move either. It restarted on the same [worker](glossary:worker-node).

So I stopped only [worker](glossary:worker-node) 1's [k3s](glossary:k3s) for 150 seconds (with a restart scheduled, of course). The [containers](glossary:container) keep running and only the contact with the leader is cut.

| After stopping | What happened                                                                                                                                                         |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ~50 s          | The leader marks [worker](glossary:worker-node) 1 [NotReady](glossary:node)                                                                                           |
| ~80 s          | Replacement [CoreDNS](glossary:coredns) [Pod](glossary:pod) created (waits for [worker](glossary:worker-node) 1 to come back, one per [worker](glossary:worker-node)) |

The docs said 40 seconds. That was the agent's estimate from [Kubernetes](glossary:kubernetes) defaults. Measured on this version, it was about 50. I changed "about 40 seconds" to "about 50 seconds" in the [cluster](glossary:kubernetes-cluster) design doc, the system definition and two diagrams.

Only the full power cut test is left. Whether [the BIOS "power on after an outage" setting](/en/blog/hackathon/woowangthon/woowangthon-04-remote-access/#7-power-coming-back-on-after-an-outage) really works has to be seen in the club room.

## 9. Reflection

Picking the card is not picking the address, and estimated numbers have to be replaced with measured ones.
