## 2. Device Controller (host adapter)

### 1. Two components of a device

- Mechanical component
- Electronic component (= contains the [controller](glossary:device-controller))

### 2. What the controller does

- Converts a serial bit stream → a block of bytes
- Delivers it to main memory
- [Error correction](glossary:error-correction) when needed
- Can handle multiple devices at once

## 3. Device Registers

- Types: data-in / data-out / status / control (1~4 byte or [FIFO](glossary:fifo))
- Usually 1~4 bytes, or a [FIFO](glossary:fifo) buffer

### 2. Two ways to read or write registers ← ※ same concept as #2.2 (duplicate)

- [Direct I/O](glossary:port-mapped-io) / [Memory-mapped](glossary:memory-mapped-io)

### 3. Example: Simple Printer

- [status register](glossary:status-register): done bit (output complete) / error bit (paper jam, out of paper)
- data register: the data to print
- CPU behavior: wait until the done bit is set + always check the error bit

# 2. I/O Device (classifying behavior from 5 angles)

## 1. In what units is data exchanged?

### 1. Block (fixed blocks)

- Definition: stores information in fixed-size blocks, each block has its own address
- Characteristics: block size 512B~32KB / each block can be read and written independently / has a unique address, so → seek is possible ([random access](glossary:random-access) (the opposite of sequential access; it doesn't mean accessing at random, it means you can skip ahead and land exactly on the location you want.))
- Examples: disks, tapes

### 2. Character (character stream)

- Definition: exchanges a character stream one character at a time
- Characteristics: no address (not addressable) / no seek (sequential)
- Examples: printers, modems, mice, keyboards

## 2. How does the CPU access device registers?

### 1. Direct I/O (dedicated instructions)

From the CPU's point of view there are two address spaces — one is the memory address space (where RAM is read and written), the other is the I/O port address space (where the [device registers](glossary:device-register) are).

The two are completely separate, so memory access instructions can't reach the devices, and dedicated instructions like in/out have to be used instead

### 2. Memory-mapped (memory addresses)

- Definition: map the [device control registers](glossary:device-register) into the processor's memory address space → treat the [registers](glossary:device-register) just like memory addresses
- Characteristics: accessed with standard data transfer instructions (load/store) with no separate I/O instructions
- Advantages:
  - [Drivers](glossary:device-driver) can be written in pure C (no assembly in/out needed)
  - No separate protection mechanism needed → protected by the existing [page tables](glossary:page-table) ([PTE](glossary:pte)); by putting the desired pages in a [page table](glossary:page-table), you can even give a specific user control of a specific device
  - Reading a [register](glossary:device-register) and testing its value is handled in a single instruction

## 3. How does the CPU know the I/O has been handled?

### 1. Polling (keep checking)

- Definition: the CPU repeatedly asks the device itself, "do you need attention?" (poll)
  - Checks whether it's ready to accept a command / what the command status is, etc.
- Advantages:
  - Simple (just run a loop checking the [status register](glossary:status-register))
  - Software holds control (the CPU decides when to check)
  - Actually efficient if the device becomes ready right away
- Disadvantages:
  - Inefficient in complex systems → only drives up CPU usage ([busy-wait](glossary:busy-waiting))
  - Low-priority devices might never get serviced

### 2. Interrupt (receive a signal)

- Definition: when a device needs attention it requests an [interrupt](glossary:interrupt) from the CPU → wait until the CPU is notified
- Characteristics:
  - A dedicated [ISR](glossary:interrupt-handler) per device is called
  - Several devices can share an [interrupt](glossary:interrupt)
- Advantages:
  - The CPU steps in to the device only when really needed (does other work the rest of the time)
  - Generally more efficient than [polling](glossary:polling)
- Disadvantages:
  - Too many [interrupts](glossary:interrupt) slow down or block execution of the main program
  - Overhead (might need 1 [interrupt](glossary:interrupt) per byte transferred) ← the reason 1.4 [DMA](glossary:dma) came along
- Handling flow (7 steps):
  1. The [driver](glossary:device-driver) starts the I/O
  2. The [controller](glossary:device-controller) performs the I/O
  3. On completion/error, an [interrupt](glossary:interrupt) signal is raised (when going [wait queue](glossary:wait-queue) -> [ready queue](glossary:ready-queue) )
  4. The CPU receives the [interrupt](glossary:interrupt) and hands control to the [handler](glossary:interrupt-handler)
  5. The [handler](glossary:interrupt-handler) processes the data and returns
  6. The CPU resumes its original work (the CPU checks whether an [interrupt](glossary:interrupt) came in between every instruction)

## 4. Who actually moves the data?

### 1. Programmed I/O (the CPU moves it)

- Definition: the CPU is directly involved in moving data device ↔ memory (each word passes through the CPU's hands)
- Characteristics: moved with dedicated I/O instructions or [memory-mapped](glossary:memory-mapped-io)
- Disadvantage: on large transfers the CPU has to hang on every byte → wastes the CPU

### 2. DMA (the controller moves it)

- Definition: the [DMA](glossary:dma) controller transfers directly device ↔ memory without going through the CPU
- Characteristics:
  - For high-speed devices that pour out data close to memory speed
  - Transfers block by block directly from buffer → main memory (no CPU involvement)
  - Only 1 [interrupt](glossary:interrupt) per block ← solves the "[interrupt](glossary:interrupt) per byte" disadvantage of 1.3.2
- Handling flow (4 steps):
  1. The CPU sets up the [DMA](glossary:dma) controller (Address/Count/Control registers)
  2. [DMA](glossary:dma) requests a transfer to memory → 3. data is transferred directly → 4. on completion, Ack + [interrupt](glossary:interrupt)

## 5. How does the calling process wait? (process/system call level)

### 1. Blocking (wait)

- Definition: the process is suspended (sleeps) until the I/O finishes
- Characteristics: easy to write and easy to understand (the code flows in order from top → bottom)
- Examples: read(), write()
- ※ The cause of the run→wait transition in the [process state](glossary:process-state) diagram = exactly this [blocking I/O](glossary:blocking-io)

### 2. Non-blocking (return immediately)

- Definition: the I/O call returns immediately, and the return value tells how many bytes have been transferred so far
- Characteristics:
  - Even if there's no data, it doesn't wait and moves right on to the next thing
  - Implemented with [multithreading](glossary:multithreading)
  - [select()](glossary:select) checks whether data is ready
- Example: [select()](glossary:select)

# 3. I/O Software (how the kernel abstracts it)

## 1. Goals

[Device independence](glossary:device-independence), uniform naming, error handling, synchronous/asynchronous, [buffering](glossary:buffer), shared/dedicated

## 2. Layer

### 1. User-level I/O Software

- Mostly provided as libraries (run outside the [kernel](glossary:kernel), in user space)
  - C standard I/O library: [fopen()](glossary:fopen), fgets(), fscanf(), etc. / you can also write your own (myopen)
- Key distinction [fopen()](glossary:fopen) vs [open()](glossary:open):
  - [open()](glossary:open) = [system call](glossary:system-call) (enters the [kernel](glossary:kernel) directly)
  - [fopen()](glossary:fopen) = a library function wrapping [open()](glossary:open) (adds [buffering](glossary:buffer), etc.)
- What it does: I/O calls / formatting (printf's %d) / [spooling](glossary:spooling)

### 2. Device-independent I/O Software

- Role: a layer that sits on top of all [drivers](glossary:device-driver) in common. Where the 3.1 goals (uniform naming, protection, [buffering](glossary:buffer), allocation, error handling) are actually implemented
- (1) Uniform interfacing:
  - File protection rules apply to devices as is
- (2) Error reporting:
  - Many errors are device-specific → handled by that [driver](glossary:device-driver); distinguish programming errors vs actual I/O errors
  - 5 ways to handle them: return an error code / retry / ignore / kill the calling process / shut down the system

### 3. Device Drivers

- Definition: device-specific code that controls each I/O device
- Role/position:
  - Talks upward with the device-independent I/O software + [interrupt handlers](glossary:interrupt-handler), and controls the actual hardware downward
  - Connects to the rest of the OS through a well-defined model and standard interface → responsible for actually implementing [device independence](glossary:device-independence) (3.1)
- 3 ways to implement (load) them:
  - Statically linked into the [kernel](glossary:kernel) (baked in)
  - Selectively loaded at boot
  - Dynamically loaded while running (for [hot-plugging](glossary:hot-plugging) — loaded when you plug in a USB device)
- Reliability problems:
  - [Drivers](glossary:device-driver) are the main cause of OS failures → 85% of Windows XP crashes were [drivers](glossary:device-driver)
  - 70% of Linux [kernel](glossary:kernel) code is [drivers](glossary:device-driver), with 7x more bugs than the [kernel](glossary:kernel)
  - Why: written by less experienced developers + an explosion of variety (35,000 [drivers](glossary:device-driver) and 120,000 versions for XP)
